## Запросы, порядок и ошибки

### Кодирование: порядок, ошибки и предел параллелизма

Даны компонент EncodingComponent и сервис EncodingService с готовой логикой кодирования строк. Необходимо реализовать функциональность кодирования данных в компоненте.
```ts
class EncodingService {
  encode(data: string): Observable<string> {
    // уже существующая реализация
    // кодирует строку
  }
}

type IncomingData = string;
type EncodedData = string;
class EncodingComponent {
  constructor(private readonly encodingService: EncodingService) {}
  encode(data$: Observable<IncomingData>): Observable<EncodedData> {
    // твоя реализация
  }
}
```
Изменяем у метода типы входных данных и результата.
Теперь вместо потока метод принимает массив.
```ts
type IncomingData = { id: string; data: string };
type EncodedData = IncomingData & { res: string };
class EncodingComponent {
  constructor(private readonly encodingService: EncodingService) {}
  encode(data: readonly IncomingData[]): Observable<EncodedData[]> {
    // твоя реализация
  }
}
```
Тот же метод, но в случае ошибки вместо закодированной строки возвращает null.
Плюс дополнительные требования описаны в комментарии.
Ошибка отдельного кодирования не должна прерывать обработку остальных элементов.
```ts
type IncomingData = { id: string; data: string };
type EncodedData = IncomingData & { res: string | null };
class EncodingComponent {
  constructor(private readonly encodingService: EncodingService) {}
  encode(data: readonly IncomingData[]): Observable<EncodedData[]> {
    // твоя реализация
    // сохраняет порядок данных в массиве результата
    // обрабатывает ошибки при кодировании
    // для оптимизации производительности кодирует не больше 3 строк одновременно
  }
}
```

> [!example]- Разбор
>
> Для последовательного потока подходит concatMap(value => service.encode(value)); для независимой обработки — mergeMap с оговорённым пределом. Для массива с сохранением порядка помечаю каждую запись входным индексом, запускаю максимум три внутренних потока, ловлю ошибку внутри каждого и собираю результаты по индексам.
>
> ~~~ts
> return from(data.map((item, index) => ({ item, index }))).pipe(
>   mergeMap(({ item, index }) =>
>     defer(() => this.encodingService.encode(item.data)).pipe(
>       take(1),
>       defaultIfEmpty(null),
>       catchError(() => of(null)),
>       map(res => ({ index, value: { ...item, res } })),
>     ), 3),
>   toArray(),
>   map(items => items.sort((a, b) => a.index - b.index).map(item => item.value)),
> );
> ~~~
>
> На каждую строку здесь ожидается один результат. Если источник завершился без значения, возвращается null; если он вообще не завершается, понадобится тайм-аут. defer превращает синхронный throw сервиса в ошибку потока, а toArray после завершения пустого входа выдаёт [].
>
> Проверяю обратный порядок ответов, отказ среднего элемента, пустой массив, отписку и предел в три активные операции. Сортировка результата стоит O(n log n). Её можно убрать, записывая значения в заранее выделенный массив по индексам; каждая подписка должна получить собственный массив.

### Поиск, фильтрация и сброс страницы

Есть страница, на которой отображен список компаний, есть возможность поиска компании по названию, фильтрации по типу,
а также переключения страниц. Необходимо реализовать логику работы данной страницы. Примем, что дочерние компоненты уже реализованы.
При написании логики необходимо учесть, что при поиске и фильтрации должна сбрасываться страница.
```ts
// company-list.component.ts - компонент списка компаний
@Component({
  selector: 'company-list',
  template: ` <search-panel (search)="onSearch($event)"></search-panel>
    <filter-panel (search)="onFilter($event)"></filter-panel>
    <companies [companies]="companies$ | async"></companies>
    <pagination-panel (pageChange)="onPageChange($event)"></pagination-panel>`,
})
export class CompanyListComponent {
  companies$ = new BehaviorSubject<Company[]>([]);
  // ваш код здесь
  onSearch(companyName: string) {
    // ваш код здесь
  }
  onFilter(companyType: string) {
    // ваш код здесь
  }
  onPageChange(page: number) {
    // ваш код здесь
  }
  getCompanies(
    companyName: string,
    companyType: string,
    page: number,
  ): Observable<Company[]> {
    // метод уже реализован
  }
}
```

> [!example]- Разбор
>
> Храню одно состояние запроса {name,type,page}. Событие search или filter создаёт новое состояние с page=1, pageChange меняет только page. Один общий поток состояния проходит сравнение значимых полей и switchMap к getCompanies. Так изменение фильтра не порождает промежуточный запрос со старой страницей, как при независимых несогласованных subjects.
>
> Ошибка ловится внутри switchMap, иначе весь поток перестанет реагировать на следующие действия. Состояния loading/error/data отделены; шаблон использует одну подписку либо разделённый поток. Например, на странице 5 пользователь меняет тип: должен уйти запрос нового типа со страницей 1, а не два запроса 5 и 1. Проверки: первичная загрузка, повтор одинакового фильтра, смена страницы, быстрый ввод, поздний ответ и восстановление после ошибки.

### API-запросы через Observable и Promise

Задача в несколько шагов.
Даны HTTP-запросы, обёрнутые в Observable и Promise.
1. Сколько уйдёт запросов?
```ts
const obs$ = httpClient.get('https://tinkoff.ru'); // Стандартный HttpClient из Angular
const promise = fetch('https://tinkoff.ru');
```

2. Сколько запросов уйдёт в таком случае?
```ts
const obs$ = httpClient.get('https://tinkoff.ru'); // Стандартный HttpClient из Angular
const promise = fetch('https://tinkoff.ru');
obs$.subscribe(console.log);
obs$.subscribe(console.log);
obs$.subscribe(console.log);
promise.then(console.log);
promise.then(console.log);
promise.then(console.log);
```

3. Сколько раз выведется сообщение в консоль в каждом из случаев?
4. Что можно сделать, чтобы с Observable запрос уходил один раз?
5. Что произойдёт при share() и повторной подписке через 15 секунд?
```ts
const obs$ = httpClient.get('https://tinkoff.ru').pipe(share()); // Стандартный HttpClient из Angular, использован оператор share()
const promise = fetch('https://tinkoff.ru');
obs$.subscribe(console.log);
obs$.subscribe(console.log);
obs$.subscribe(console.log);
setTimeout(() => {
  obs$.subscribe(console.log);
}, 15000);
promise.then(console.log);
promise.then(console.log);
promise.then(console.log);
```

Уточните время завершения первого запроса относительно повторной подписки через 15 секунд. share не равен постоянному кэшу ответа.

> [!example]- Разбор
>
> Без подписок HttpClient Observable не запускает запрос, а вызов fetch уже запускает свою операцию: в первом варианте один запрос. Во втором три subscribe создают три HTTP-операции плюс один fetch. При обычном успешном ответе каждый subscribe и каждый then вызывают свой console.log: по три для каждой группы. Это не учитывает отдельные сетевые preflight/redirect.
>
> share объединяет одновременных подписчиков активного источника, но по умолчанию после completion сбрасывает его. Если HTTP завершился до 15 секунд, поздняя подписка создаст новый запрос; если ещё активен — присоединится к нему. Promise.then добавляет обработчик того же исхода и не повторяет fetch.
>
> Если позднему подписчику тоже нужен успешный ответ, использую shareReplay и отдельно задаю срок хранения и сброс кэша. Объединить текущие запросы и хранить уже полученный ответ — разные задачи.
>
> Проверяю это управляемым HTTP-источником: подписываю троих до ответа, затем ещё одного после ответа. Отдельно воспроизвожу ошибку и отписку всех потребителей. Так видно, в какой момент начинается новый запрос и когда возвращается прежний результат.

### Выбор switchMap, mergeMap, concatMap и exhaustMap

Предоставлены `userId$: Observable<string>` и `userService.getUser(id): Observable<User>`. Реализовывать HTTP-клиент не нужно. Подберите обработку для каждого независимого варианта и объясните порядок результатов:

1. Важен только последний ID; старые результаты нужно игнорировать.
2. Нужны все пользователи, но запросы выполняются по одному.
3. Нужны все пользователи; порядок завершения не важен, запросы могут идти параллельно.
4. Одновременно разрешено не больше трёх запросов.
5. Что изменится при exhaustMap: какие ID будут проигнорированы, пока запрос активен?

Обсудите операторы высшего порядка, реальную отмену запроса и обработку ошибки внутреннего потока. Сравните Observable и Promise.

> [!example]- Разбор после самостоятельной попытки
>
> В первом варианте switchMap переключится на новый внутренний поток. Во втором concatMap дождётся завершения предыдущего и сохранит очередь. Для третьего и четвёртого подходит mergeMap с нужным пределом параллельности.
>
> exhaustMap ведёт себя иначе: пока внутренний поток работает, новые внешние значения пропускаются. При выборе оператора учитываю и очистку источника: отписка остановит внешнюю работу только тогда, когда источник реализует такую отмену.
>
>
> Для A→B при медленном A switchMap оставит результат B, concatMap сначала дождётся A и лишь затем начнёт B, mergeMap может выдать B раньше A. mergeMap(project,3) ограничит число активных внутренних подписок, но сохранит порядок завершения, а не входа. exhaustMap проигнорирует B, пока A активен; после завершения A новый C будет принят.
>
> catchError внутри проекции позволяет обработать отказ одного запроса и продолжить слушать новые ID. catchError снаружи может завершить всю исходную последовательность заменяющим потоком. Проверяю временные диаграммы и число активных операций. Отписка от Promise-обёртки не отменяет уже запущенный Promise, тогда как источник с AbortController может остановить поддерживающий отмену запрос.
### Показ сообщения об ошибке

Покажите результат запроса. При ошибке покажите уведомление на пять секунд, затем закройте его. Учитывайте самостоятельное закрытие пользователем.
```ts
/* Реализовать следующую логику
  1. Отправляем запрос на сервер
  2. Если запрос завершился ошибкой - показываем уведомление об ошибке,
            которое висит 5 секунд, затем исчезает
  3. Если запрос завершился успешно - показываем уведомление с результатом запроса*/ interface NotificationService {
  /**
   * Показывает пользователю уведомление
   * @return: поток, при подписке на поток будет показано уведомление, при завершении потока уведомление будет закрыто.
   * Также пользователь может закрыть уведомление самостоятельно, в этом случае поток завершится сам
   */
  showNotification$(text: string, type: 'error' | 'info'): Observable<void>;
}
let request$: Observable<string>; // при подписке отправит запрос на сервер
let notificationService: NotificationService; // экземпляр NotificationService
```

> [!example]- Разбор
>
> Превращаю исход запроса в уведомление через switchMap; ошибочную ветку обрабатываю catchError. Для ошибки ограничиваю showNotification$(message,'error') через takeUntil(timer(5000)). Успешную ветку оставляю по контракту сервиса или задаю отдельное правило длительности. Если пользователь закрыл сообщение раньше, поток завершается сам.
>
> У showNotification$ должен быть teardown, который закрывает уведомление и освобождает ресурсы при отписке. Если закрытие записано только в callback complete внутреннего источника, takeUntil может его не вызвать. Поэтому очистку помещаю в teardown или finalize и проверяю её при ручном закрытии и отмене.
>
> Проверки управляемыми часами: сообщение видно до пяти секунд и скрыто после, ручное закрытие раньше не приводит ко второму действию, уничтожение компонента очищает таймер, успешный ответ не оформляется как ошибка. Не логирую сырой ответ с личными данными как текст уведомления.

## Подписки и синхронные источники

### Превратить браузерное API в Observable

Родилось из практической задачи:
Есть браузерное API для MutationObserver
Выглядит оно так:

```ts
// Создаём экземпляр наблюдателя с указанной функцией колбэка
const observer = new MutationObserver(callback); // Начинаем наблюдение за настроенными изменениями целевого элемента
observer.observe(target, config);
// Позже можно остановить наблюдение
observer.disconnect();
```

По аналогии с функцией fromEvent, надо создать функцию fromMutationObserver(target, config), которая возвращает Observable, который передаёт каждое уведомление MutationObserver
Обязательно предусмотреть остановку MutationObserver, когда он уже не нужен

> [!example]- Разбор
>
> Создаю наблюдателя при подписке, а disconnect возвращаю как teardown. Каждая независимая подписка получает свой экземпляр; общее выполнение добавляется отдельно при необходимости.
>
> ~~~ts
> function fromMutationObserver(target: Node, config: MutationObserverInit) {
>   return new Observable<MutationRecord[]>(subscriber => {
>     const observer = new MutationObserver(records => subscriber.next(records));
>     try {
>       observer.observe(target, config);
>     } catch (error) {
>       observer.disconnect();
>       subscriber.error(error);
>     }
>     return () => observer.disconnect();
>   });
> }
> ~~~
>
> Передаю массив записей одного уведомления, а не придумываю событие для каждой записи без согласования. API доступно только в браузере; SSR-ветка требует явного поведения. Проверки: подписка начинает наблюдение, изменение выдаёт записи, отписка прекращает доставку, повторная подписка независима, неверная конфигурация даёт error. Обработчик не должен бесконечно менять наблюдаемый DOM в ответ на своё же изменение.

### DI-токен потока видимости страницы

Создайте DI-токен, по которому можно получить Observable изменений видимости страницы.
> [!note]- Подсказка
> у document есть событие `visibilitychange`.

> [!example]- Разбор
>
> Создаю InjectionToken<Observable<boolean>> с фабрикой. В браузере получаю DOCUMENT через DI. При подписке defer читает текущее visibilityState, а fromEvent(document,'visibilitychange') сообщает о следующих изменениях. События преобразую в boolean и убираю повторы через distinctUntilChanged.
>
> Начальное значение выдаю сразу: иначе подписчик узнает состояние только после первого переключения вкладки.
>
> Если нужен общий поток, добавляю shareReplay({bufferSize:1,refCount:true}); defer обеспечивает новое чтение при новом подключении после отсутствия подписчиков. На сервере выбираю явное значение или отсутствие такого сценария, не обращаясь к глобальному document.
>
> Проверки: начально видимая/скрытая вкладка, два подписчика, отписка последнего, повторная подписка и серверный запуск. visibilityState отражает видимость документа; видимая вкладка может оставаться без внимания пользователя.

### Параллельные подписки

Есть поток interval(100).pipe(take(5),map(() => Math.random())). Что увидим в консоли в каждом отдельном варианте? Как получить одинаковые значения в двух подписках? Сравните общую подписку и повтор ранее полученных значений.

```js
// Вариант A:
const stream$ = interval(100).pipe(
  take(5),
  map(() => Math.random()),
);
stream$.subscribe((v) => console.log(v));
stream$.subscribe((v) => console.log(v));
```

```js
// Вариант B (отдельная программа):
const stream$ = interval(100).pipe(
  take(5),
  map(() => Math.random()),
);
stream$.subscribe((v) => console.log(v));
setTimeout(() => stream$.subscribe((v) => console.log(v)), 1000);
```

> [!example]- Разбор
>
> В A две подписки создают два interval и независимо вызывают Math.random: всего по пять значений у каждой. Совпадение случайного значения возможно, но общего источника нет. В B второй такой же независимый процесс стартует через секунду, после завершения первого, и тоже выдаёт пять значений.
>
> share ставлю после map(Math.random), чтобы подписчики разделяли не только источник, но и создание случайного числа. Если поставить share перед map, каждый подписчик выполнит свой map и получит собственное значение.
>
> Для позднего подписчика нужен replay. Размер буфера выбираю по задаче: shareReplay({bufferSize:1,refCount:true}) сохраняет последнее значение завершившегося источника, а не все пять значений.
>
> В проверке считаю запуски источника и моменты выдачи значений с управляемым scheduler. Случайные числа могут совпасть, поэтому их неравенство не подходит для надёжного теста. Размер replay-буфера ограничиваю.

### Два синхронных потока: пары всех значений

Первый поток синхронно выдаёт два значения и завершается, второй — одно и завершается. Получите обе пары в указанном порядке. Объясните, почему обычный combineLatest при выбранном порядке подписки может потерять первое значение.

```ts
const first$ = new Observable((observer) => {
  observer.next('first_stream_first_event');
  observer.next('first_stream_second_event');
  observer.complete();
});

const second$ = new Observable((observer) => {
  observer.next('second_stream_first_event');
  observer.complete();
});
```

Ожидаемые пары:

```text
[first_stream_first_event, second_stream_first_event]
[first_stream_second_event, second_stream_first_event]
```

> [!example]- Разбор
>
> При combineLatest([first$,second$]) first$ успевает синхронно выдать оба значения до появления значения второго потока. Когда second$ выдаёт значение, у combineLatest сохранено только последнее first$, поэтому получается одна пара. zip тоже не решает условие: одному значению second$ соответствует только один элемент очереди first$.
>
> Для этих конечных потоков можно получить массивы через toArray, дождаться их через forkJoin и построить декартово произведение, сохраняя порядок первого потока. Это даст обе требуемые пары и не повторит побочные эффекты источников. Цена — память для всех значений и ожидание завершения; для бесконечных потоков такой вариант не подходит.
>
> Другой вариант first$.pipe(concatMap(a => second$.pipe(map(b => [a,b])))) создаёт две подписки second$: он допустим только при явно согласованном повторении источника. Проверки: конкретные две пары, число подписок, пустой поток и ошибка. Перестановка аргументов combineLatest случайно помогает этой синхронной форме, но не задаёт общий контракт «все пары».
