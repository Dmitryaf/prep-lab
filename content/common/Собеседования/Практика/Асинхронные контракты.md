# Асинхронные контракты

[[Собеседования/00. Карта раздела|Карта банка]]

Два самостоятельных упражнения на JavaScript. Сначала согласуй контракт и проверочные примеры, затем напиши решение. Код работает с переданными зависимостями: настоящие серверы и сокеты для проверки не нужны.

## Запросы через одно соединение: ответы не по порядку

**Формат раунда:** Написание кода
**Этап кода:** advanced

Через одно открытое соединение отправляются независимые запросы. Ответы могут прийти в любом порядке, дважды или не прийти вовсе. Реализуй `createRequestClient(transport, timeoutMs)`, возвращающий `request(payload, { signal }?)` и `close()`.

Транспорт предоставляет синхронный `send({ id, payload })`: он отправляет сообщение либо выбрасывает ошибку. `subscribe(onMessage, onClose)` регистрирует обработчики и возвращает функцию отписки; при регистрации события не вызываются. Адаптер уже разобрал и проверил входящий JSON. Ответ имеет форму `{ id, ok: true, value }` либо `{ id, ok: false, error }`. Вызов обработчика даже прямо из `send` допустим.

Каждый запрос получает новый ID в пределах экземпляра клиента. Promise завершается своим ответом, ошибкой отправки/сервера, отменой или таймаутом. Неизвестные и повторные ответы игнорируются. При закрытии отклоняются все ожидающие запросы, удаляются таймеры и подписки; новые запросы отклоняются. `close()` повторно безопасен. Это окончательное закрытие экземпляра, без reconnect и автоматических повторов. Клиент снимает свои подписки, а владелец транспорта закрывает сам сокет.

**Критерии ответа:** Сопоставляю по ID; регистрирую ожидание до send; любой исход очищает таймер и abort listener; закрытие отклоняет все pending и блокирует новые запросы; поздний ответ не восстанавливает завершённую операцию.

> [!example]- Разбор: одна таблица ожиданий и единая очистка
>
> Map связывает ID с функцией завершения. Эта функция сначала удаляет запись и ресурсы, затем завершает Promise. Поэтому повторный ответ, таймаут после отмены и повторный close не меняют результат.
>
> ```js
> // checked-example: request-multiplexer
> function createRequestClient(transport, timeoutMs = 5000) {
>   if (!Number.isFinite(timeoutMs) || timeoutMs <= 0) {
>     throw new Error('Invalid timeout');
>   }
>   const pending = new Map();
>   let sequence = 0;
>   let closed = false;
>   let unsubscribe = () => {};
>
>   function close() {
>     if (closed) return;
>     closed = true;
>     for (const finish of [...pending.values()]) {
>       finish(false, new Error('Closed'));
>     }
>     unsubscribe();
>   }
>
>   unsubscribe = transport.subscribe((message) => {
>     const finish = pending.get(message.id);
>     if (!finish) return;
>     finish(message.ok, message.ok ? message.value : new Error(message.error));
>   }, close);
>
>   function request(payload, { signal } = {}) {
>     if (closed) return Promise.reject(new Error('Closed'));
>     if (signal?.aborted) return Promise.reject(new Error('Aborted'));
>     // Счётчик не переиспользуется в пределах этого соединения.
>     if (sequence === Number.MAX_SAFE_INTEGER) {
>       return Promise.reject(new Error('ID space exhausted'));
>     }
>     const id = `request-${++sequence}`;
>     return new Promise((resolve, reject) => {
>       let timer;
>       const abort = () => finish(false, new Error('Aborted'));
>       function finish(ok, value) {
>         if (!pending.delete(id)) return;
>         clearTimeout(timer);
>         signal?.removeEventListener('abort', abort);
>         if (ok) resolve(value);
>         else reject(value);
>       }
>       pending.set(id, finish);
>       timer = setTimeout(() => finish(false, new Error('Timeout')), timeoutMs);
>       signal?.addEventListener('abort', abort, { once: true });
>       try {
>         transport.send({ id, payload });
>       } catch (error) {
>         finish(false, error);
>       }
>     });
>   }
>   return { request, close };
> }
> ```
>
> Отправь A и B, верни сначала ответ B: первый Promise всё ещё должен ждать A. После timeout повторный ответ с тем же ID игнорируется. Отдельно проверь ошибку send, отказ сервера, уже отменённый signal, отмену во время ожидания и закрытие с несколькими pending.
>
> Поиск ожидания в Map обычно занимает O(1), память — O(p), где p — число незавершённых запросов. Таймаут удаляет старые ожидания, но новые могут поступать быстрее, чем завершаются прежние. Для такого потока нужен предел числа запросов и правило перегрузки: замедлить отправителя или отказать в новом запросе. Отмена ожидания на клиенте не гарантирует остановку уже принятой серверной команды. Занятый цикл событий может обработать таймаут позже заданного срока.

> [!followup]- Как изменить close на мягкую остановку с конечным сроком ожидания уже отправленных запросов?
>
> Разделите состояние клиента на `open → draining → closed`. При вызове `close()` сразу запретите новые `request`, но оставьте подписку и записи в `pending`. В `draining` уже начатые запросы завершаются обычным путём: ответом, ошибкой отправки, отменой или своим таймаутом. После последнего завершения снимите подписку и отмените таймер остановки; если общий срок вышел раньше, отклоните оставшиеся ожидания через тот же `finish`. Повторный `close()` возвращает один Promise завершения, не продлевая срок.
>
> Например, при лимите 2 секунды A отвечает через 300 мс и получает результат, B остаётся без ответа и отклоняется на дедлайне. Обработчик фактического закрытия транспорта сразу отклоняет оба незавершённых ожидания: ждать больше нечего. Зафиксируйте состояние и Promise до очистки, чтобы повторный вызов и синхронный ответ из `send` не запустили её дважды. Владелец по-прежнему закрывает сам сокет. Таймер не прерывает занятый цикл событий, а отклонение Promise не отменяет команду на сервере.

> [!followup]- Как ограничить количество pending и обработать reconnect, не повторив команду с неизвестным исходом?
>
> До записи в `pending` проверьте предел незавершённых запросов. При заполнении возвращайте ошибку перегрузки или ставьте запрос в отдельную ограниченную очередь с дедлайном. Освобождайте слот через единый `finish` после любого исхода, в том числе синхронной ошибки. Для восстановления соединения создавайте новый экземпляр, а обработчики старого отвязывайте: его запоздавшие ответы не должны совпасть с ID в новом `pending`.
>
> Например, соединение оборвалось после отправки команды создания заказа. Это неизвестный исход: сервер мог сохранить заказ и потерять только ответ. Повторить команду безопасно лишь при серверной дедупликации по тому же ключу операции либо после сверки состояния. ID корреляции ответа живёт в пределах соединения; ключ операции должен переживать переподключение. Новые запросы можно отправлять после восстановления, не поднимая старые автоматически.

## Пакетная загрузка по ID с частичным кэшем

**Формат раунда:** Написание кода
**Этап кода:** main

Базовый этап — пакетная загрузка без кэша. Реализуй `createLoader(fetchBatch)`, возвращающий асинхронную `getByIds(ids)`. Вход — массив непустых строк. `fetchBatch(ids)` возвращает Promise с Map значений по ID, порядок записей может отличаться от входа. Результат getByIds — массив в исходном порядке, включая дубликаты. Пустой вход возвращает пустой массив без запроса. Если в ответе отсутствует любой запрошенный ID, отклони Promise; значение undefined при наличии ключа допустимо. Ошибку загрузчика передай вызывающему коду.

Пример: `['b', 'a', 'b']` и ответ `Map([['a', 10], ['b', 20]])` дают `[20, 10, 20]`. В базовом этапе каждый непустой вызов делает ровно один fetchBatch; массив передаётся копией. Кэш и совместное ожидание добавляются только в следующих этапах.

**Критерии ответа:** Соблюдаю порядок и дубликаты; отличаю отсутствие ключа от undefined; пустой вход не вызывает загрузку; проверяю вход и полноту ответа; отказ передаётся вызывающему коду. Кэш и защита от гонок не входят в базовую оценку.
**Изучить:** [[Фронтенд/JavaScript/05. Асинхронность/02. Promise — базовая модель и цепочки|Promise и ошибки]], [[Фронтенд/JavaScript/07. Массивы и коллекции/03. Map, Set, WeakMap и WeakSet|Map и наличие ключа]]

> [!example]- Разбор: порядок определяется входом
>
> ```js
> // checked-example: batch-base
> function createLoader(fetchBatch) {
>   return async function getByIds(ids) {
>     if (
>       !Array.isArray(ids) ||
>       Array.from(ids).some((id) => typeof id !== 'string' || !id)
>     ) {
>       throw new Error('IDs must be non-empty strings');
>     }
>     const input = [...ids];
>     if (!input.length) return [];
>     const result = await fetchBatch([...input]);
>     if (!(result instanceof Map)) throw new Error('Expected Map');
>     return input.map((id) => {
>       if (!result.has(id)) throw new Error(`Missing result: ${id}`);
>       return result.get(id);
>     });
>   };
> }
> ```
>
> Array.from перед проверкой превращает пустые позиции разреженного массива в undefined: они отклоняются как неверные ID до обращения к загрузчику. Обход ответа вместо input потерял бы порядок и повторы. `has` нужен даже при undefined. При отклонении Promise функция не отдаёт частичный массив. Проверь обратный порядок Map, пустой массив, дубликаты, отсутствующий ID и ошибку загрузчика.

### Кэш готовых значений

Добавь `createCachedLoader(fetchBatch, cache = new Map())`. Между вызовами сохраняй готовые значения; загружай одним запросом только уникальные отсутствующие ID. Пока рассматриваем последовательные вызовы. Проверяй полноту новой пачки до записи любого её значения. Ошибка не попадает в кэш. Внешний код не меняет cache во время загрузки, Срок хранения и вытеснение записей на этом этапе не нужны.

Пример: cache содержит a → вызов `['b', 'a', 'b']` отправляет только `['b']`; следующий `['a', 'b']` ничего не загружает. undefined в cache — попадание.

**Критерии ответа:** Использую has, исключаю повторные ID новой пачки, сохраняю исходный порядок; неполный или ошибочный ответ не загрязняет кэш; повтор после отказа запускает запрос.
**Изучить:** [[Фронтенд/Архитектура/03. API, кэш и синхронизация данных#Cache|Кэш]], [[Фронтенд/JavaScript/07. Массивы и коллекции/03. Map, Set, WeakMap и WeakSet|Map и Set]]

> [!example]- Разбор: сначала проверка всей пачки
>
> ```js
> // checked-example: batch-cache-stage
> function createCachedLoader(fetchBatch, cache = new Map()) {
>   return async function getByIds(ids) {
>     if (
>       !Array.isArray(ids) ||
>       Array.from(ids).some((id) => typeof id !== 'string' || !id)
>     ) {
>       throw new Error('IDs must be non-empty strings');
>     }
>     const input = [...ids];
>     const missing = [...new Set(input)].filter((id) => !cache.has(id));
>     if (missing.length) {
>       const result = await fetchBatch(missing);
>       if (!(result instanceof Map)) throw new Error('Expected Map');
>       for (const id of missing) {
>         if (!result.has(id)) throw new Error(`Missing result: ${id}`);
>       }
>       for (const id of missing) cache.set(id, result.get(id));
>     }
>     return input.map((id) => cache.get(id));
>   };
> }
> ```
>
> Этот этап не объединяет одновременные запросы: два вызова могут одновременно не найти один ID в кэше и оба запросить его. Следующий этап устраняет такой повтор.

### Общие ожидания пересекающихся загрузок

Реализуй `createCachedLoader(fetchBatch, cache?)`, возвращающий `getByIds(ids)`. Вход — массив непустых строк. Результат — массив значений в **том же порядке**, включая дубликаты. Например, для `['b', 'a', 'b']` результат содержит значение b дважды. Значение `undefined` может быть настоящим попаданием кэша: проверяй наличие ключа.

`cache` — переданный Map готовых значений. Для уникальных ID, которых нет ни в кэше, ни среди уже выполняющихся загрузок, один вызов `getByIds` делает один `fetchBatch(missingIds)`. Тот возвращает Promise с Map значений по ID; порядок ответа произвольный. Для каждого запрошенного ID обязана быть запись. Если хотя бы одной нет, вся эта новая пачка считается ошибочной и не попадает в кэш. Лишние записи игнорируются.

Пересекающиеся вызовы ожидают один и тот же незавершённый Promise для общего ID. Ошибка освобождает ожидание и допускает повторный запрос, не записывая ошибку в кэш. Уже успешные независимые пачки сохраняются. Пустой вход возвращает пустой массив без сетевого вызова. На этом этапе записи не устаревают и не сбрасываются, отмены нет; во время загрузки никто извне не изменяет cache. Данные одного экземпляра принадлежат одному контексту доступа, например одной пользовательской сессии.

**Критерии ответа:** Отличаю отсутствующий ключ от undefined; запрашиваю каждый недостающий ID один раз; храню готовые значения отдельно от незавершённых загрузок; сохраняю порядок и дубликаты; удаляю ожидания после отказа и проверяю всю пачку до записи.

**Изучить:** [[Фронтенд/JavaScript/05. Асинхронность/06. Паттерны асинхронного кода#Дедупликация запросов|Дедупликация запросов]], [[Фронтенд/Архитектура/03. API, кэш и синхронизация данных#Cache|Кэш и его срок жизни]], [[Фронтенд/JavaScript/07. Массивы и коллекции/03. Map, Set, WeakMap и WeakSet|Map и наличие ключа]]

**Уточнения**

- Как добавить invalidation во время pending, чтобы старый ответ не восстановил удалённые данные?
- Что должна означать отмена одного потребителя, когда другой ждёт тот же ID, и когда можно отменить транспорт?

> [!example]- Разбор: готовые значения отдельно от выполняющихся запросов
>
> Сначала находим ID, которые ещё не загружены и не ожидаются, и сохраняем их Promise в inFlight. fetchBatch вызывается позже, в микрозадаче, поэтому следующий синхронный вызов уже найдёт эти ожидания. Один вызов к внешнему API обслуживает всю новую пачку; для каждого ID создаётся своё ожидание результата.
>
> ```js
> // checked-example: partial-cache
> function createCachedLoader(fetchBatch, cache = new Map()) {
>   const inFlight = new Map();
>   return function getByIds(ids) {
>     if (
>       !Array.isArray(ids) ||
>       Array.from(ids).some((id) => typeof id !== 'string' || !id)
>     ) {
>       return Promise.reject(new Error('IDs must be non-empty strings'));
>     }
>     const input = [...ids];
>     const missing = [...new Set(input)].filter(
>       (id) => !cache.has(id) && !inFlight.has(id),
>     );
>     if (missing.length) {
>       const batch = Promise.resolve()
>         .then(() => fetchBatch(missing))
>         .then((result) => {
>           if (!(result instanceof Map)) throw new Error('Expected Map');
>           // Проверяем всю пачку до помещения отдельных значений в кэш.
>           for (const id of missing) {
>             if (!result.has(id)) throw new Error(`Missing result: ${id}`);
>           }
>           return result;
>         });
>       for (const id of missing) {
>         const promise = batch.then((result) => {
>           const value = result.get(id);
>           cache.set(id, value);
>           return value;
>         });
>         inFlight.set(id, promise);
>         const clear = () => inFlight.delete(id);
>         promise.then(clear, clear);
>       }
>     }
>     return Promise.all(
>       input.map((id) => (cache.has(id) ? cache.get(id) : inFlight.get(id))),
>     );
>   };
> }
> ```
>
> Если a уже есть в кэше, вызов `getByIds(['b', 'a', 'b'])` отправляет только b, но возвращает три значения. Если до ответа запустить `getByIds(['b', 'c'])`, новая пачка содержит только c, а b ожидается совместно. После ошибки загрузки b следующий вызов снова обращается к fetchBatch.
>
> Простое соединение значений из кэша и ответа нарушит входной порядок. Отклонённый Promise нужно удалить: иначе следующий вызов снова получит прежнюю ошибку вместо нового запроса. Promise.all отклоняет общий результат при первом отказе, но не отменяет другие пачки. Здесь кэш растёт с количеством разных ID; для долгой работы нужны предел размера и политика обновления. Объекты возвращаются по ссылке: если требуется независимое редактирование, вызывающий код создаёт черновик.

> [!followup]- Как добавить invalidation во время pending, чтобы старый ответ не восстановил удалённые данные?
>
> Храните для каждого ID поколение или объект текущей загрузки. `invalidate(id)` удаляет готовое значение и отделяет прежний `pending` от текущего поколения. Следующий запрос может запустить новую загрузку. Старая пачка по-прежнему проверяется целиком на полноту, но при публикации каждое значение записывается только в своё актуальное поколение. В очистке действует та же проверка: старый `finally` не может удалить новый `pending`.
>
> Например, пачка A запросила `x` и `y`. После удаления `x` пачка B запрашивает его заново. Если A придёт последней, она может заполнить неизменившийся `y`, но не восстановит прежний `x`. Для потребителей A определите отдельно: разрешено ли получить начатый снимок либо ожидание отклоняется при invalidation. Если удаление связано с отзывом доступа, отклонение прежнего ожидания важно так же, как запрет записи в кэш.

> [!followup]- Что должна означать отмена одного потребителя, когда другой ждёт тот же ID, и когда можно отменить транспорт?
>
> Отменяйте ожидание конкретного потребителя, а общую загрузку сохраняйте, пока её результат кому-то нужен. Храните один транспортный запрос для пачки и учёт активных потребителей по её ID. У каждого вызова `getByIds` свой Promise, подписка на сигнал и очистка; дубликаты внутри одного вызова не создают новых потребителей. Если кэш должен наполняться даже без подписчиков, это отдельное основание не отменять транспорт.
>
> Например, A ждёт `[x, y]`, B ждёт `[y]`. Отмена A отклоняет только его результат. Транспорт нужен для `y`, даже если никто больше не ждёт `x`: один `AbortController` отменяет всю пачку, а не отдельную запись. Когда потребителей нет, можно оборвать пачку, если `fetchBatch` принимает сигнал. Транспорт может проигнорировать отмену, поэтому поздний результат сверяйте с текущим ожиданием перед изменением кэша.

### Сброс кэша во время запроса

Вернись к варианту «Кэш готовых значений» и добавь `invalidate(id)`. Теперь запрос A может ещё выполняться, когда запись сброшена и стартовал B. A должен завершить свой Promise для исходного потребителя, но не имеет права восстановить сброшенную запись или затереть более свежий ответ B в общем кэше. Каждый новый запрос по одному ID получает версию; только последняя несброшенная версия записывает результат. Объединение pending в этом самостоятельном этапе не требуется.

Пример: A(a) → invalidate(a) → B(a) → B вернул 2 → A вернул 1. Результат B равен `[2]`, результат A равен `[1]`, в cache остаётся 2; новый вызов получает 2 без сети.

**Критерии ответа:** Версии меняются при запросе и invalidate; поздний ответ не пишет в общий кэш; каждый потребитель получает результат своей операции; полнота пачки проверяется до записи; сброс готового значения работает.
**Изучить:** [[Фронтенд/API браузера/05. Fetch, CORS и сетевые запросы/03. AbortController и race condition в запросах|Актуальность операции]], [[Фронтенд/Архитектура/03. API, кэш и синхронизация данных#Cache|Срок жизни кэша]]

> [!example]- Разбор: версия защищает общий кэш
>
> ```js
> // checked-example: batch-version-stage
> function createVersionedLoader(fetchBatch, cache = new Map()) {
>   const versions = new Map();
>   const advance = (id) => {
>     const version = (versions.get(id) ?? 0) + 1;
>     versions.set(id, version);
>     return version;
>   };
>   function invalidate(id) {
>     advance(id);
>     cache.delete(id);
>   }
>   async function getByIds(ids) {
>     if (
>       !Array.isArray(ids) ||
>       Array.from(ids).some((id) => typeof id !== 'string' || !id)
>     ) {
>       throw new Error('IDs must be non-empty strings');
>     }
>     const input = [...ids];
>     const values = new Map();
>     const missing = [];
>     const requestedVersions = new Map();
>     for (const id of new Set(input)) {
>       if (cache.has(id)) values.set(id, cache.get(id));
>       else {
>         missing.push(id);
>         requestedVersions.set(id, advance(id));
>       }
>     }
>     if (missing.length) {
>       const result = await fetchBatch(missing);
>       if (!(result instanceof Map)) throw new Error('Expected Map');
>       for (const id of missing) {
>         if (!result.has(id)) throw new Error(`Missing result: ${id}`);
>       }
>       for (const id of missing) {
>         const value = result.get(id);
>         values.set(id, value);
>         if (versions.get(id) === requestedVersions.get(id))
>           cache.set(id, value);
>       }
>     }
>     return input.map((id) => values.get(id));
>   }
>   return { getByIds, invalidate };
> }
> ```
>
> Локальная values удерживает результат именно этого вызова, даже если общий кэш сброшен. AbortSignal сам по себе не гарантировал бы такую защиту. Этот вариант не объединяет одновременные запросы. Если совместить два этапа, ключ общего ожидания должен учитывать версию, а очистка старой загрузки — проверять, что удаляет именно своё ожидание.
