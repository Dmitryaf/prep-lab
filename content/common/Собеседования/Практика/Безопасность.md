## Защита аутентификации

Клиент-серверное приложение для ритейла. Необходимо спроектировать защитные механизмы обнаружения, реагирования и предотвращения для системы аутентификации, которые защитят от атак и угроз на учетные данные пользователей и захват доступа:
• подбор доступа с чужими утёкшими учётными данными
• проверка частых паролей на множестве учётных записей
• перебор паролей
• выяснение существующих логинов
• ненадёжное восстановление пароля
• навязывание идентификатора сессии
• действия от имени пользователя и утечка доступных данных при XSS
• подделка действия в существующей сессии через CSRF

> [!example]- Разбор
>
> Начинаю с того, как атакующий пытается войти: перебирает пароли одного аккаунта, проверяет частый пароль на многих аккаунтах или использует пары логин/пароль из утечки. Ограничения нужны на сервере — по учётной записи и другим признакам атаки. Только IP недостаточно: запросы могут приходить с разных адресов. При этом жёсткая блокировка аккаунта позволит атакующему мешать законному владельцу. Поэтому добавляю обнаружение аномалий и второй фактор или другой устойчивый способ входа. Ответы входа и восстановления не должны выдавать существование логина текстом или заметной разницей времени.
>
> После успешного входа меняю идентификатор сессии, ограничиваю её срок и предусматриваю отзыв. Cookie получает подходящие Secure, HttpOnly и SameSite. HttpOnly мешает чтению cookie скриптом, но не запрещает XSS выполнять действия в текущей сессии. Поэтому отдельно устраняю небезопасный вывод и применяю защиту от CSRF для автоматически приложенных credentials.
>
> Для восстановления создаю случайный одноразовый токен с ограниченным сроком и проверяю все шаги на сервере. В журналах связываю попытку с результатом, но не записываю пароль, OTP или токен. Затем проверяю обычный вход, неверные данные, одновременные попытки и отзыв сессии. Отдельный случай — законные пользователи за одним общим IP: ограничения не должны без причины лишать их доступа.

## Защита от злоупотребления отправкой SMS

Компания регулярно подвергается спам - атаке. Хакеры регулярно запрашивают код подтверждения по смс. В результате компания несет убытки из-за больших затрат на отправку смс. Что можно предложить бизнесу, чтобы решить эту проблему?

> [!example]- Разбор
>
> Сначала смотрю, сколько запросов к API действительно превращаются в оплаченные SMS: по каким номерам и направлениям, с какой стоимостью и долей успешных подтверждений. Затем ставлю ограничения до вызова SMS-провайдера — на номер, пользователя или сессию, дополняя их другими признаками злоупотребления. Нужны также общая квота расходов и возможность быстро остановить аномальный поток. Пока действует таймер повторной отправки, новый клик не должен создавать ещё одну платную SMS.
>
> При подозрительном поведении возможна дополнительная проверка, но CAPTCHA не заменяет серверные лимиты. Ограничение только по IP блокирует пользователей общего адреса и не останавливает распределённые запросы. Использую возможности провайдера по направлениям и контролю затрат, не открываю ненужные дорогие направления без продуктовой причины.
>
> Проверки: параллельные запросы одного номера, смена IP, повтор после истечения окна, ошибка провайдера и легитимный пользователь после ограничения. Логирую причину отказа и агрегированные затраты, не сам код. Нужны понятный таймер повторной попытки и способ восстановления доступа; «отключить SMS всем» может уменьшить расходы ценой сломанного входа.

## CSRF при переводе денег через JSON API

Дана спецификация HTTP метода для перевода денежных средств. Вопросы:
• Может ли злоумышленник перевести деньги с чужого счета при помощи CSRF?
• Какие условия должны быть выполнены для возможности эксплуатации CSRF?
Спецификация:
```
POST /api/v1/pay HTTP/2
Host: www.tinkoff.ru
Content-Type: application/json

{"srcAccount": 1111111111, "dstAccount": 2222222222, "moneyAmount": 100}
```

> [!example]- Разбор
>
> Начну с авторизации запроса. Если браузер автоматически прикладывает cookie сессии при обращении с чужого сайта, нужно проверить защиту от CSRF. Если код вручную добавляет Authorization, условия будут другими. Далее смотрю, проверяет ли сервер CSRF-токен и Origin, какие правила SameSite заданы cookie и какие Content-Type принимает метод.
>
> Cross-origin fetch с application/json обычно требует предварительного запроса CORS. Браузер отправит основной запрос только после разрешения сервера. Но если сервер разрешает посторонний origin вместе с credentials или принимает тот же перевод через простой Content-Type без preflight, этот барьер может исчезнуть. Поэтому нужно проверить саму возможность отправить перевод: запрет читать ответ не всегда мешает выполнить действие.
>
> В разрешённом тестовом окружении проверяю запрос с доверенного и постороннего origin, отсутствие/неверный токен, неожиданный Content-Type и отсутствие credentials. Отдельно проверяю право текущего пользователя на srcAccount: CSRF-защита не заменяет авторизацию. [OWASP: CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## Восстановление пароля

1. Дана ручка для восстановления пароля по e-mail. Например:
```
POST /api/restore HTTP/2
Host: id.service.ru
Content-Type: application/json
Origin: https://id.service.ru
Referer: https://id.service.ru/restore-password-by-email

{"email":"user@mail.example.ru"}
```

2. На указанную почту приходит ссылка на восстановление пароля `https://id.service.ru/restore/1678371465`

3. При переходе по ссылке у пользователя запрашивается ОТП (например, приходит смс на телефон)
```
POST /api/restore/1678371465 HTTP/2
Host: id.service.ru
Content-Type: application/json
Origin: https://id.service.ru
Referer: https://id.service.ru/restore/1678371465

{"otp":"123"}
```

4. После успешного ввода ОТП пользователю предлагается сменить пароль.
```
POST /api/restore/1678371465 HTTP/2
Host: id.service.ru
Content-Type: application/json
Origin: https://id.service.ru
Referer: https://id.service.ru/restore/1678371465

{"new_pass":"qwe123"}
```

Вопросы:
• Что будете проверять во время аудита?

> [!example]- Разбор
>
> Сервер должен помнить, на каком шаге находится восстановление: запрос создан, OTP подтверждён, смена пароля разрешена, операция уже использована. Прямой POST со сменой пароля до подтверждения OTP должен получить отказ. Подтверждение привязываю к одному запросу и аккаунту, чтобы код от другого восстановления нельзя было использовать здесь.
>
> Проверяю, для чего нужен числовой ID в ссылке: он может только находить запрос восстановления, а разрешение на смену пароля — давать отдельный секрет. Такой секрет должен быть случайным, одноразовым и ограниченным по сроку. Для короткого OTP особенно важны серверный лимит попыток и запрет повторного использования. Первый ответ не должен раскрывать существование email, а адрес ссылки нельзя строить из непроверенного Host.
>
> Проверки: прямой переход к смене пароля без OTP, неверный/истёкший код, перенос между аккаунтами, два параллельных завершения и повтор после успеха. После смены определяю отзыв существующих сессий и уведомление владельца. Пароль и токены не попадают в URL/логи. [OWASP: восстановление пароля](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## Модель угроз загрузки аватарки

Пользователь загружает аватарку через метод `upload`. API сохраняет имя файла в БД, связывает его с пользователем и кладёт изображение в файловое хранилище. Браузер получает и отображает изображение через метод `get`.

Назовите угрозы, расставьте приоритеты и предложите защиту для каждой границы. Схема развёртывания не предоставлена: уточните права, домен выдачи, доступность файлов и путь хранения, прежде чем объявлять конкретную уязвимость.

> [!example]- Разбор после самостоятельной попытки
>
> Сначала проверяю, кто загружает файл и чью аватарку меняет: сервер берёт пользователя из сессии и не позволяет подменить его одним userId. Затем проверяю сам файл. Нужны ограничения на размер запроса, число загрузок и количество пикселей после декодирования. Расширение и Content-Type прислал клиент, поэтому по ним одним формат не определяют. Разрешённое растровое изображение декодируют и заново кодируют; повреждённые файлы и слишком большие изображения отклоняют.
>
> Хранилище получает сгенерированный ключ, а не пользовательский путь. Имя файла не может выйти из каталога или заменить существующий объект; в БД оно записывается параметризованным запросом. Для выдачи задаются корректный Content-Type и nosniff. Если допускается SVG или иной активный формат, нужен отдельный контракт очистки/изоляции; для простой аватарки проще ограничиться растровыми форматами. Приватные изображения проверяют права и при чтении, а публичную выдачу можно отделить от origin приложения без его cookie.
>
> Проверки: попытка заменить аватарку другого пользователя, имя с ../, HTML под расширением .png, повреждённый файл, маленький сжатый файл с огромными размерами и превышение квоты. После отказа прежняя аватарка остаётся доступной; ошибка записи БД не оставляет бесконечные бесхозные файлы. TLS защищает передачу, но не заменяет эти проверки.
>

## Аудит форм денежного перевода

Есть два сценария: перевод между своими счетами, включая валютные, и перевод на сторонний счёт по номеру карты. Какие проверки интерфейса и серверного API необходимы? Макеты и точные поля не предоставлены: обсуждайте сценарии, а для аудита конкретной формы сначала запросите её контракт.

> [!example]- Разбор после самостоятельной попытки
>
> Перед отправкой пользователь должен видеть, с какого счёта и кому переводит деньги, сумму, валюту, комиссию и итог списания. При отказе введённые данные остаются в форме. Сервер заново проверяет право списания, получателя, остаток и лимиты: значениям из браузера доверять нельзя. Для суммы нужен точный денежный формат и согласованное округление, иначе расчёт через float может дать ошибку.
>
> Два параллельных перевода не должны оба потратить один остаток: проверка и запись выполняются в согласованной серверной транзакции. Повтор после двойного клика или потери ответа использует один ключ логической операции; сервер возвращает прежний результат. Таймаут оставляет исход неизвестным — интерфейс проверяет статус перевода, сохраняя ключ, вместо новой отправки с новым ключом. Изменившиеся курс или комиссия требуют повторного подтверждения по контракту.
>
> Проверяю чужой счёт, отрицательную/слишком большую сумму, точность и границы округления, истечение котировки, два конкурирующих запроса и потерю ответа после списания. Итог: одно подтверждённое списание, согласованные баланс и история, отсутствие раскрытия чужих данных. CSRF-защита и безопасный вывод проверяются отдельно; disabled помогает интерфейсу, но не защищает API.
>
