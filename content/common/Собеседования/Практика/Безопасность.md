## Защита аутентификации

Клиент-серверное приложение для ритейла. Необходимо спроектировать защитные механизмы обнаружения, реагирования и предотвращения для системы аутентификации, которые защитят от атак и угроз на учетные данные пользователей и захват доступа:
• подбор доступа с чужими утёкшими учётными данными
• проверка частых паролей на множестве учётных записей
• перебор паролей
• выяснение существующих логинов
• ненадёжное восстановление пароля
• навязывание идентификатора сессии
• действия от имени пользователя и утечка доступных данных при XSS
• подделка действия в существующей сессии через CSRF

> [!example]- Разбор
>
> Разделяю угрозы по границе защиты. Для credential stuffing и перебора нужны серверные ограничения по учётной записи и дополнительным сигналам, обнаружение аномалий и второй фактор/устойчивый способ входа. Один IP-лимит обходится распределённой атакой; жёсткая блокировка аккаунта по чужим попыткам может стать отказом в обслуживании. Ответы входа и восстановления не должны раскрывать наличие логина содержимым и очевидными различиями времени.
>
> После успешного входа меняю идентификатор сессии, ограничиваю её срок и предусматриваю отзыв. Cookie получает подходящие Secure, HttpOnly и SameSite. HttpOnly мешает чтению cookie скриптом, но не запрещает XSS выполнять действия в текущей сессии. Поэтому отдельно устраняю небезопасный вывод и применяю защиту от CSRF для автоматически приложенных credentials.
>
> Восстановление использует случайный одноразовый токен, ограничения попыток и серверную проверку всех переходов. Наблюдаемость связывает попытки и результаты без записи паролей, OTP и токенов. Проверки включают успешный вход, ошибку, конкурирующие попытки, отзыв сессии и законного пользователя за общим NAT. Защита не сводится к CAPTCHA или кнопке disabled.

## Защита от злоупотребления отправкой SMS

Компания регулярно подвергается спам - атаке. Хакеры регулярно запрашивают код подтверждения по смс. В результате компания несет убытки из-за больших затрат на отправку смс. Что можно предложить бизнесу, чтобы решить эту проблему?

> [!example]- Разбор
>
> Сначала отделяю запрос к API от фактически оплаченной отправки и измеряю частоту, стоимость, направления и долю успешных подтверждений. Лимиты ставлю перед обращением к SMS-провайдеру: на номер, пользователя/сессию и дополнительные сигналы, с общей квотой расходов и аварийным ограничением. Повторный клик в пределах cooldown не должен создавать новую оплачиваемую операцию.
>
> При подозрительном поведении возможна дополнительная проверка, но CAPTCHA не заменяет серверные лимиты. Ограничение только по IP блокирует пользователей общего адреса и не останавливает распределённые запросы. Использую возможности провайдера по направлениям и контролю затрат, не открываю ненужные дорогие направления без продуктовой причины.
>
> Проверки: параллельные запросы одного номера, смена IP, повтор после истечения окна, ошибка провайдера и легитимный пользователь после ограничения. Логирую причину отказа и агрегированные затраты, не сам код. Нужны понятный таймер повторной попытки и способ восстановления доступа; «отключить SMS всем» может уменьшить расходы ценой сломанного входа.

## CSRF при переводе денег через JSON API

Дана спецификация HTTP метода для перевода денежных средств. Вопросы:
• Может ли злоумышленник перевести деньги с чужого счета при помощи CSRF?
• Какие условия должны быть выполнены для возможности эксплуатации CSRF?
Спецификация:
```
POST /api/v1/pay HTTP/2
Host: www.tinkoff.ru
Content-Type: application/json

{"srcAccount": 1111111111, "dstAccount": 2222222222, "moneyAmount": 100}
```

> [!example]- Разбор
>
> По одному HTTP-примеру нельзя определить уязвимость. Проверяю, чем авторизуется запрос и приложит ли браузер эти credentials с чужого origin. Cookie-сессия и вручную добавляемый Authorization имеют разные условия. Затем проверяю серверную проверку CSRF-токена/Origin, SameSite и строгую обработку Content-Type.
>
> application/json обычно вызывает CORS preflight при cross-origin fetch. Но защита исчезает при небезопасном разрешении origin с credentials или если сервер также принимает тело через простой Content-Type, который можно отправить без preflight. Запрет прочитать ответ сам по себе не доказывает запрет выполнить действие. Сервер должен отвергать неподходящие способы вызова и проверять намерение по принятому механизму защиты.
>
> В разрешённом тестовом окружении проверяю запрос с доверенного и постороннего origin, отсутствие/неверный токен, неожиданный Content-Type и отсутствие credentials. Отдельно проверяю право текущего пользователя на srcAccount: CSRF-защита не заменяет авторизацию. [OWASP: CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## Восстановление пароля

1. Дана ручка для восстановления пароля по e-mail. Например:восстановление
```
POST /api/restore HTTP/2
Host: id.service.ru
Content-Length: 29
Content-Type: application/jsonOrigin: id.service.ruReferer: https://id.service.ru/restore-password-by-email
  {"email":"user@mail.example.ru"}
```

2. На указанную почту приходит ссылка с на восстановление пароля`https://id.service.ru/restore/1678371465`

3. При переходе по ссылке у пользователя запрашивается ОТП (например, приходит смс на телефон)
```
POST /api/restore/1678371465 HTTP/2
Host: id.service.ru
Content-Length: 14
Content-Type: application/jsonOrigin: id.service.ruReferer: https://id.service.ru/restore/1678371465
    {"otp":"123"}
```

4. После успешного ввода ОТП пользователю предлагается сменить пароль.
```
POST /api/restore/1678371465 HTTP/2
Host: id.service.ru
Content-Length: 21
Content-Type: application/jsonOrigin: id.service.ruReferer: https://id.service.ru/restore/1678371465
    {"new_pass":"qwe123"}
```

Вопросы:
• Что будете проверять по время аудита?

> [!example]- Разбор
>
> Проверяю серверный автомат состояний: создан запрос → подтверждён фактор → разрешена смена пароля → операция использована. Нельзя разрешать последний POST только потому, что UI уже показал форму. Подтверждение OTP привязано к этому запросу и аккаунту; чужой или старый идентификатор не должен переносить разрешение.
>
> Числовой идентификатор в URL выглядит предсказуемым, но сам по себе ещё не доказывает обход: проверяю его роль и наличие отдельного секретного токена. Секрет должен быть случайным, ограниченным по сроку и одноразовым. Для короткого OTP нужны строгие серверные ограничения попыток и запрет повторного использования. Ответ на первый запрос не раскрывает наличие email; адрес ссылки не строится из недоверенного Host без проверки.
>
> Проверки: прямой переход к смене пароля без OTP, неверный/истёкший код, перенос между аккаунтами, два параллельных завершения и повтор после успеха. После смены определяю отзыв существующих сессий и уведомление владельца. Пароль и токены не попадают в URL/логи. [OWASP: восстановление пароля](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## Модель угроз загрузки аватарки

Пользователь загружает аватарку через метод `upload`. API сохраняет имя файла в БД, связывает его с пользователем и кладёт изображение в файловое хранилище. Браузер получает и отображает изображение через метод `get`.

Назовите угрозы, расставьте приоритеты и предложите защиту для каждой границы. Схема развёртывания не предоставлена: уточните права, домен выдачи, доступность файлов и путь хранения, прежде чем объявлять конкретную уязвимость.

> [!example]- Разбор после самостоятельной попытки
>
> Проверьте права на загрузку и чтение, обработку имени и содержимого файла, допустимые размер и формат, защиту БД параметрами запроса, безопасную выдачу изображения и сообщения об ошибках. TLS защищает передачу, но не устраняет опасное содержимое или ошибку авторизации. Сканирование файла и ORM сами по себе не гарантируют безопасность.
>

## Аудит форм денежного перевода

Есть два сценария: перевод между своими счетами, включая валютные, и перевод на сторонний счёт по номеру карты. Какие проверки интерфейса и серверного API необходимы? Макеты и точные поля не предоставлены: обсуждайте сценарии, а для аудита конкретной формы сначала запросите её контракт.

> [!example]- Разбор после самостоятельной попытки
>
> Проверьте принадлежность счёта и полномочия, сумму и валюту, конвертацию и округление, защиту от повторной отправки и гонок, раскрытие чужого баланса и данных владельца карты, CSRF и безопасный вывод. Ограничьте размер и формат чисел. Серверная проверка обязательна; недоступная кнопка не защищает перевод.
>
