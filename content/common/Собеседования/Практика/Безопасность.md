## Защита аутентификации

Клиент-серверное приложение для ритейла. Необходимо спроектировать защитные механизмы обнаружения, реагирования и предотвращения для системы аутентификации, которые защитят от атак и угроз на учетные данные пользователей и захват доступа:
• подбор доступа с чужими утёкшими учётными данными
• проверка частых паролей на множестве учётных записей
• перебор паролей
• выяснение существующих логинов
• ненадёжное восстановление пароля
• навязывание идентификатора сессии
• действия от имени пользователя и утечка доступных данных при XSS
• подделка действия в существующей сессии через CSRF

## Защита от злоупотребления отправкой SMS

Компания регулярно подвергается спам - атаке. Хакеры регулярно запрашивают код подтверждения по смс. В результате компания несет убытки из-за больших затрат на отправку смс. Что можно предложить бизнесу, чтобы решить эту проблему?

Дана спецификация HTTP метода для перевода денежных средств. Вопросы:


## Восстановление пароля

1. Дана ручка для восстановления пароля по e-mail. Например:восстановление
```
POST /api/restore HTTP/2
Host: id.service.ru
Content-Length: 29
Content-Type: application/jsonOrigin: id.service.ruReferer: https://id.service.ru/restore-password-by-email
  {"email":"user@mail.example.ru"}
```

2. На указанную почту приходит ссылка с на восстановление пароля`https://id.service.ru/restore/1678371465`

3. При переходе по ссылке у пользователя запрашивается ОТП (например, приходит смс на телефон)
```
POST /api/restore/1678371465 HTTP/2
Host: id.service.ru
Content-Length: 14
Content-Type: application/jsonOrigin: id.service.ruReferer: https://id.service.ru/restore/1678371465
    {"otp":"123"}
```

4. После успешного ввода ОТП пользователю предлагается сменить пароль.
```
POST /api/restore/1678371465 HTTP/2
Host: id.service.ru
Content-Length: 21
Content-Type: application/jsonOrigin: id.service.ruReferer: https://id.service.ru/restore/1678371465
    {"new_pass":"qwe123"}
```

## Модель угроз загрузки аватарки

Пользователь загружает аватарку через метод `upload`. API сохраняет имя файла в БД, связывает его с пользователем и кладёт изображение в файловое хранилище. Браузер получает и отображает изображение через метод `get`.

Назовите угрозы, расставьте приоритеты и предложите защиту для каждой границы. Схема развёртывания не предоставлена: уточните права, домен выдачи, доступность файлов и путь хранения, прежде чем объявлять конкретную уязвимость.

> [!example]- Разбор после самостоятельной попытки
>
> Проверьте права на загрузку и чтение, обработку имени и содержимого файла, допустимые размер и формат, защиту БД параметрами запроса, безопасную выдачу изображения и сообщения об ошибках. TLS защищает передачу, но не устраняет опасное содержимое или ошибку авторизации. Сканирование файла и ORM сами по себе не гарантируют безопасность.
>

## Аудит форм денежного перевода

Есть два сценария: перевод между своими счетами, включая валютные, и перевод на сторонний счёт по номеру карты. Какие проверки интерфейса и серверного API необходимы? Макеты и точные поля не предоставлены: обсуждайте сценарии, а для аудита конкретной формы сначала запросите её контракт.

> [!example]- Разбор после самостоятельной попытки
>
> Проверьте принадлежность счёта и полномочия, сумму и валюту, конвертацию и округление, защиту от повторной отправки и гонок, раскрытие чужого баланса и данных владельца карты, CSRF и безопасный вывод. Ограничьте размер и формат чисел. Серверная проверка обязательна; недоступная кнопка не защищает перевод.
