# Инженерные решения

[[Собеседования/00. Карта раздела|Карта банка]]

Объясни, какую проблему решаешь, почему выбрал этот подход и как проверишь результат. Затем назови условие, при котором решение придётся изменить.

Выбери упражнение, уточни условия и предложи решение. Назови ограничения, затем сравни с разбором. Документацией можно пользоваться.

## 1. Спроектировать экран при неполных требованиях

Нужно сделать таблицу бронирований с фильтрами, редактированием и несколькими операторами. Объём данных, права и требования к актуальности не заданы.

Ожидаемый результат: пять важных вопросов, схема частей, владелец данных, путь сохранения, состояния ошибки и первый поставляемый срез. Затем добавляются два условия: записей 100 000; другой оператор может менять ту же запись.

> [!question]- Разбор
> Сначала уточни, что операторы делают чаще всего, сколько записей нужно показывать, кто может их менять и насколько свежими должны быть данные. Раздели таблицу, форму и API.
>
> Для 100 000 записей предложи фильтрацию и пагинацию на сервере. При сохранении передавай версию записи: если другой оператор успел её изменить, покажи конфликт и сохрани введённый текст. Права проверяет сервер. Первой версией может стать просмотр списка и редактирование одного поля с обработкой загрузки, успеха и ошибки.

Усложнение: часть полей зависит от внешнего сервиса, который отвечает нестабильно. Объясни, какой результат можно показать частично и почему неизвестное значение нельзя заменить нулём.

## 2. Разобрать код без переписывания всего модуля

В форме `form` — ref с объектом данных, `api.save` возвращает канонически сохранённый объект:

```ts
async function submit() {
  saving.value = true;
  const submitted = { ...form.value };
  form.value = await api.save(submitted);
  await api.loadHistory();
  saving.value = false;
}
```

Назови три проблемы по последствиям. Для самой опасной предложи минимальную проверку. Затем выясняется, что в форме есть вложенный массив строк.

> [!question]- Разбор
> При отказе `saving` может остаться `true`; поздний ответ затирает новый ввод; ошибка истории смешивается с результатом уже успешного сохранения. Поверхностная копия не изолирует вложенные изменения. Сначала договорись о снимке данных и повторном submit, затем раздели результат записи и дополнительное чтение, обеспечь завершение состояния ожидания. `finally` для нескольких параллельных команд без общего правила тоже может снять индикатор слишком рано.

Проверка: управляемый Promise, редактирование после отправки, затем завершение старого ответа. Для ошибки истории отдельно проверь, что UI сохраняет факт успешной записи и не предлагает повторить команду вслепую.

## Перенос экрана на новую UI-библиотеку

**ID вопроса:** 3. Декомпозиция и оценка

Нужно перенести работающий экран на новую UI-библиотеку. На экране есть таблица с фильтрами, форма редактирования и диалог подтверждения. Как проверить, что новая библиотека подходит, и в каком порядке переносить части экрана?

> [!answer]- Ответ
> Сначала перенести один сложный компонент вместе с его сценарием: например, форму с валидацией, фокусом и ошибкой сохранения. Проверить, какие возможности даёт библиотека, а что нужно сохранить в своём коде. Затем переносить остальные части небольшими шагами, проверяя совместимость старых и новых компонентов.
>
> Логику загрузки и сохранения лучше отделить от компонентов библиотеки. Тогда замена таблицы или поля не меняет правила работы с данными. При переносе проверить клавиатуру, длинный текст, адаптивность и важные состояния формы.
>
> До оценки уточняю границы переноса: готова ли тема UI kit, есть ли нужные состояния таблицы и формы, сохраняются ли API и поведение экрана, какие браузеры проверяем. Разбиваю работу на проверяемые шаги и называю диапазон для каждого с учётом проверки и исправлений. Риск несовместимости сначала проверяю на сложном компоненте; его результат может изменить оценку остального экрана.
>
> Трудозатраты разработчика и дата выпуска — разные величины. В оценке отдельно показываю своё время, работу reviewer/QA и ожидание их доступности. Например, 15–25 часов моей работы не обещают выпуск через три дня: ещё нужны согласованные окна проверки и выпуска. После пилота пересматриваю диапазон и объясняю, какие предположения подтвердились.

**Уточнения**
- Как перенести экран частями, сохранив его работоспособность?
- Что делать, если у нового компонента нет нужного поведения?
- Как оценить перенос диапазоном и пересчитать его, если нужного поведения нет в UI kit?

> [!followup]- Как оценить перенос диапазоном и пересчитать его, если нужного поведения нет в UI kit?
>
> Для одного экрана можно оценить пилот, перенос формы и таблицы, интеграционные проверки, исправления после review и выпуск. Числа зависят от исходного состояния: готовый UI kit и неизменный API сокращают неизвестность, но не отменяют проверку поведения. Пример с явными предположениями и суммой этапов — в материале «Инженерные решения и работа команды».
>
> Если пилот показывает отсутствие нужного поведения, выбираю допустимую альтернативу с владельцем требований: временно сохранить старый компонент, изменить сценарий или написать адаптер. Для адаптера сначала ограниченно проверяю самое рискованное взаимодействие. Затем заменяю оценку затронутого этапа и пересчитываю итог; не добавляю неопределённый «запас на всё» и не меняю дату молча.

**Изучить:** [[Фронтенд/Архитектура/08. Постепенная миграция Vue 2 и Vuex|Постепенная миграция]] [[Фронтенд/Архитектура/10. Инженерные решения и работа команды#Разбиение и оценка|Пример оценки и пересмотра]]

> [!followup]- Как перенести экран частями, сохранив его работоспособность?
>
> Разбейте экран по сценариям, сохранив общее состояние и контракт API. Сначала зафиксируйте поведение таблицы с фильтрами, редактирования и подтверждения: значения по умолчанию, доступность, обработку ошибки, возврат фокуса. Проверьте наиболее рискованный компонент небольшим прототипом и переносите по одному законченному фрагменту, оставляя соседние части на старой библиотеке.
>
> Например, если диалог имеет узкие входы `open`, `confirm`, `cancel`, можно заменить его первым и сохранить прежнюю обработку подтверждения. Затем перенесите форму со сценариями ошибок и только после этого таблицу, проверив работу фильтра, сортировки и URL. На каждом шаге прогоните совместный сценарий «отфильтровать → открыть → изменить → подтвердить». Если две библиотеки конфликтуют глобальными стилями или управлением фокусом, проверьте изоляцию заранее: иначе поэтапный перенос создаст новые дефекты.

> [!followup]- Что делать, если у нового компонента нет нужного поведения?
>
> Опишите недостающее поведение через наблюдаемый сценарий. Сначала проверьте документированные API: слот, controlled state, события или настройку. Если ими можно восполнить разницу, добавьте небольшую обёртку с контрактом вашего экрана. Если требование затрагивает внутренние правила компонента, оцените сохранение старого компонента или изменение пользовательского требования.
>
> Например, фильтр таблицы должен оставаться доступным с клавиатуры и сохраняться в URL. Обёртка может хранить состояние фильтра снаружи и передавать его через публичные props. Если для корректной навигации нужно обращаться к приватным узлам разметки и перехватывать внутренние события, такая интеграция будет ломаться при обновлении библиотеки. Прототипом проверьте самое спорное поведение и согласуйте упрощение только после оценки влияния на пользователей.

## Почему setTimeout не исправляет гонку запросов?

**ID вопроса:** 4. Провести техническое ревью и помочь коллеге

В поиске добавили задержку setTimeout(..., 500), чтобы старый ответ не заменял результаты нового запроса. Исправляет ли это гонку? Как воспроизвести ошибку и проверить решение?

> [!answer]- Ответ
> Задержка меняет момент отправки, но не порядок завершения запросов. Нужно запустить поиск A, затем B, завершить B первым, а A — последним. На экране должны остаться результаты B.
>
> Можно отменять предыдущий запрос и проверять актуальность результата перед применением. В тесте порядок завершения задаётся управляемыми Promise, без ожидания случайной задержки.

**Критерии ответа:** Два запроса, обратный порядок ответов, проверка актуальности и воспроизводимый тест.

## Когда модульному приложению нужны микрофронтенды?

**ID вопроса:** 5. Защитить решение и изменить его при новых условиях

Сначала команда маленькая и выпускает всё вместе. Ты выбрал модульное приложение. Через год несколько команд требуют независимых релизов. Какие исходные предпосылки изменились? Что должно появиться до выбора микрофронтендов?

> [!question]- Разбор
> Теперь команды хотят выпускать свои части независимо. Сначала выясни, что мешает им в текущем приложении: общая сборка, связанные изменения или согласование релизов. Затем определи границы модулей, общие API и ответственность за совместимость. Микрофронтенды стоит выбирать, если независимый выпуск оправдывает дополнительную работу по интеграции и поддержке версий.

## Переход с устаревшей сборки

**Формат раунда:** Проектирование

Сборка занимает пять минут, конфигурация устарела. Как решить, что обновлять, и провести переход без потери возможностей?

> [!example]- Разбор
>
> Сначала измеряю этапы: установка зависимостей, проверка типов, преобразование, минификация, карты исходников и плагины. Разделяю холодную/повторную сборку, dev startup/HMR и CI production build. Пять минут могут уходить в типы или сеть; смена bundler сама по себе их не устранит.
>
> Составляю список того, что делает нынешняя сборка: точки входа, переменные окружения, aliases, стили, ресурсы, workers, динамические импорты, поддержка браузеров, полифиллы, source maps и плагины. Фиксирую пользовательские сценарии и исходные измерения. Делаю один представительный экран с трудной интеграцией на новой конфигурации, сравниваю поведение и артефакты. Не совмещаю без необходимости обновление фреймворка, всех зависимостей и сборщика.
>
> Переношу оставшиеся возможности небольшими проверяемыми этапами; временно сохраняю старый путь сборки для сравнения и возврата. Проверяю production-раздачу, прямые маршруты, целевые браузеры, кэш/старые вкладки и карты ошибок. В CI использую сопоставимые ресурсы и фиксированные зависимости, повторяю замеры. Переход закончен, когда сценарии и контракт поставки сохранены, узкое место уменьшилось и прежняя конфигурация больше не нужна.

**Критерии ответа:** исходные измерения и ограничения; представительный пример; совместимость; постепенный переход; проверка и возврат.

## Пересмотр поддержки старых браузеров

**Формат раунда:** Проектирование

Совместимость со старыми браузерами заметно увеличивает стоимость каждой задачи. Как обосновать изменение политики поддержки?

> [!example]- Разбор
>
> Смотрю, какие браузеры и версии используют наши пользователи, какие действия они выполняют и что обещано клиентам. Проверяю, не исключает ли сама аналитика старые браузеры: отсутствие событий может быть следствием сломанного приложения. Оцениваю цену полифиллов, обходов, тестирования и отказа от возможностей, сопоставляю её с ценностью затронутых пользователей.
>
> Предлагаю конкретную матрицу: полная поддержка, сохранение основного сценария с ограничениями или прекращение поддержки определённых версий. Решение согласуется с владельцем продукта и действующими обязательствами, а не принимается только разработчиком по проценту трафика. Возможны progressive enhancement и облегчённый сценарий вместо полного отказа.
>
> План перехода включает уведомление затронутых клиентов, дату изменения, доступный путь обновления и метрики неуспешных действий. Проверяю build targets, синтаксис и runtime API отдельно: транспиляция не добавляет все отсутствующие API. После выпуска наблюдаю ошибки и обращения поддержки в выбранной группе; документация и CI должны проверять одну и ту же матрицу.

**Критерии ответа:** исходные измерения и ограничения; представительный пример; совместимость; постепенный переход; проверка и возврат.

## Переход на новую мажорную версию фреймворка

**Формат раунда:** Проектирование

Проект нужно перевести на новую мажорную версию фреймворка. Как определить объём работы, порядок перехода и условия выпуска?

> [!example]- Разбор
>
> Сначала фиксирую причину перехода и ограничения: поддержка, необходимая возможность, срок и критические пользовательские пути. По руководству миграции и описанию целевого релиза составляю список несовместимых изменений. Проверяю router/store, UI-библиотеки, SSR, инструменты сборки, тесты, Node и браузеры; не обновляю все зависимости без различения обязательных и необязательных изменений.
>
> Выбираю небольшой, но представительный срез: маршрут с формой, асинхронными данными и внешним компонентом. Обновляю зависимости и применяю codemod с просмотром diff. По результату оцениваю оставшуюся работу. Совместимый режим или поэтапный перенос использую только если они поддерживаются и не создают два конкурирующих владельца состояния; иначе готовлю отдельную ветку с короткими интеграциями и понятным окном переключения.
>
> До выпуска проверяю основные сценарии, контракты компонентов, SSR/гидратацию при их наличии, доступность, размер сборки и производительность в сопоставимых условиях. Выпускаю ограниченно с метриками ошибок и возможностью отката. Откат включает совместимость сохранённых данных и старых вкладок: вернуть один пакет недостаточно, если формат уже изменён. После стабильной работы убираю временную совместимость.
