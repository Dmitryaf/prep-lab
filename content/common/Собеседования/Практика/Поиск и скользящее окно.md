# Поиск и скользящее окно

[[Собеседования/00. Карта раздела|Карта банка]]

Эти упражнения полезны при алгоритмическом раунде. Сначала зафиксируй контракт, нарисуй один пример и назови сложность простого решения. Затем выбирай более эффективную структуру данных.

## Суммарная неудовлетворённость покупателей

**Формат раунда:** Написание кода
**Этап кода:** advanced

Каталог содержит числовые характеристики товаров `goods`, а массив `needs` — желаемые значения покупателей. Каждый выбирает товар с минимальной абсолютной разницей `Math.abs(good - need)`. Запас не ограничен: один товар может подойти нескольким покупателям. Реализуй `totalDissatisfaction(goods, needs)`, возвращающую сумму этих минимальных разниц.

Примеры: `[8, 3, 5]` и `[5, 6]` дают 1; `[5]` и `[3, 5, 10, 105]` дают 107. Равная удалённость двух товаров не влияет на сумму. Товары не удаляются из каталога после выбора.

Учебный контракт: плотные массивы целых чисел от −1 000 000 000 до 1 000 000 000, входные массивы менять нельзя. Пустой массив покупателей даёт 0, включая пустой каталог. При непустом списке покупателей и пустом каталоге выбрасывается ошибка. Если сумма выходит за точный целочисленный диапазон Number, также нужна ошибка, а не тихое округление.

**Критерии ответа:** Выбираю ближайшее значение независимо для каждого покупателя; проверяю оба соседа позиции вставки и края; не расходую товары и не меняю вход; считаю сложность сортировки и всех поисков.

**Изучить:** [[Собеседования/Темы/Алгоритмы и программирование#Как работает двоичный поиск?|Границы двоичного поиска]], [[Собеседования/Темы/Алгоритмы и программирование#Как оценивать время работы и дополнительную память?|Время и память]]

**Уточнения**

- Как изменится решение, если оба массива уже отсортированы или каталог используется многими запросами?
- Почему ограниченный запас товаров превращает независимый выбор ближайшего значения в другую задачу?

> [!example]- Разбор: позиция вставки и два соседа
>
> Сортируем копию каталога численно. Для каждой потребности находим первый товар не меньше неё. Ближайший товар — либо он, либо его предшественник: все остальные находятся дальше с той же стороны.
>
> ```js
> // checked-example: nearest-product
> function totalDissatisfaction(goods, needs) {
>   for (const values of [goods, needs]) {
>     if (!Array.isArray(values)) throw new TypeError('Expected integer arrays');
>     for (const value of values) {
>       if (!Number.isInteger(value) || Math.abs(value) > 1_000_000_000) {
>         throw new TypeError('Expected bounded integer values');
>       }
>     }
>   }
>   if (needs.length === 0) return 0;
>   if (goods.length === 0) throw new RangeError('Empty catalogue');
>   const sorted = [...goods].sort((a, b) => a - b);
>   let total = 0;
>   for (const need of needs) {
>     let left = 0;
>     let right = sorted.length;
>     while (left < right) {
>       const middle = left + Math.floor((right - left) / 2);
>       if (sorted[middle] < need) left = middle + 1;
>       else right = middle;
>     }
>     const after = left < sorted.length ? sorted[left] - need : Infinity;
>     const before = left > 0 ? need - sorted[left - 1] : Infinity;
>     total += Math.min(before, after);
>     if (!Number.isSafeInteger(total))
>       throw new RangeError('Total exceeds safe integer');
>   }
>   return total;
> }
> ```
>
> При `goods = [-10, -4, -4]`, `needs = [-20, -7, 0]` расстояния равны 10, 3 и 4; сумма — 17. Повторы товаров не мешают поиску, а повтор покупателя добавляет ещё одно расстояние. Проверяй потребности левее всех товаров, правее всех товаров и точное совпадение.
>
> Для n товаров и m покупателей время O(n log n + m log n), плюс O(n + m) на валидацию. Дополнительная память O(n) для копии каталога; исходный массив сохраняется. Это осознанная цена неизменности, поэтому O(1) памяти здесь обещать нельзя. Для многократных обращений к неизменному каталогу отсортированную копию можно подготовить один раз.

> [!followup]- Как изменится решение, если оба массива уже отсортированы или каталог используется многими запросами?
>
> Если `goods` и `needs` уже отсортированы, держите один индекс в каталоге. Для каждого следующего `need` перемещайте его вперёд, пока следующий товар не дальше текущего. Положение ближайшего товара для неубывающих потребностей не сдвигается влево: граница выбора двух товаров находится посередине между ними. Получаем `O(goods.length + needs.length)` времени и `O(1)` дополнительной памяти.
>
> Если один каталог обслуживает много произвольных наборов потребностей, отсортируйте его копию один раз. Для каждого `need` бинарным поиском найдите первый товар не меньше него и сравните с предыдущим, где он существует. Для `[3, 5, 8]` и потребности 6 достаточно сравнить 5 и 8. Поиск стоит `O(log n)` на покупателя. Сохраните проверки пустого каталога и безопасной суммы; заранее решите, когда обновлять индекс при изменениях каталога.

> [!followup]- Почему ограниченный запас товаров превращает независимый выбор ближайшего значения в другую задачу?
>
> При ограниченном запасе выбор одного покупателя меняет варианты остальных. Оптимизировать нужно суммарное распределение, а не брать ближайший свободный товар в порядке поступления. Например, есть по одному товару с характеристиками 0 и 4, потребности — 3 и 4. Жадный выбор отдаст товар 4 первому, сумма будет `1 + 4 = 5`. Оптимально назначить ему 0, а второму оставить 4: сумма 3.
>
> На числовой прямой с ценой `|good - need|` пересекающиеся назначения можно распутать без роста стоимости. Поэтому при равном числе товаров и покупателей оптимально сопоставить отсортированные ряды. Если товаров больше, нужно выбрать подмножество: динамическое программирование решает, пропустить очередной товар или назначить следующему покупателю. Если запас меньше спроса, сначала задайте правило для необслуженных покупателей; исходная функция такой результат не определяет.

## Минимум в окне потоковых данных

**Формат раунда:** Написание кода
**Этап кода:** advanced

Реализуй `SlidingWindowMin(width)` с методами `add(value)` и `getMin()`. Окно содержит последние `width` добавленных чисел. Новое значение вытесняет самое старое, когда окно заполнено. Это окно по количеству добавлений, а не по времени и не по числу разных значений.

`width` — положительное безопасное целое. Значения — конечные числа. До первого add метод `getMin()` возвращает `undefined`; при прогреве возвращает минимум уже добавленных значений, не дожидаясь полного окна. `getMin()` ничего не удаляет. Неверный ввод отклоняется и не занимает позицию в потоке. Для окна 3 поток `[2, 4, 4, 6]` даёт минимумы `[2, 2, 2, 4]`.

**Критерии ответа:** Удаляю устаревшие элементы по позиции, сохраняю корректность при равных значениях, определяю пустое окно и прогрев; получаю O(1) для getMin и амортизированное O(1) для add с O(width) памяти.

**Уточнения**

- Почему более старое значение, не меньше нового, больше никогда не станет минимумом будущего окна?
- Что потребуется изменить для окна по времени, особенно если события приходят не по порядку?

> [!example]- Разбор: монотонная очередь кандидатов
>
> Храним только возможные будущие минимумы: пары `{ index, value }` с возрастающими индексами и значениями. Из головы убираем устаревшие позиции. Из хвоста убираем значения не меньше нового: новое выгоднее и проживёт дольше. При равенстве достаточно оставить более новое значение.
>
> ```js
> // checked-example: window-min
> class SlidingWindowMin {
>   #width;
>   #deque = [];
>   #head = 0;
>   #nextIndex = 0;
>
>   constructor(width) {
>     if (!Number.isSafeInteger(width) || width <= 0) {
>       throw new RangeError('Invalid width');
>     }
>     this.#width = width;
>   }
>
>   add(value) {
>     if (typeof value !== 'number' || !Number.isFinite(value)) {
>       throw new TypeError('Expected a finite number');
>     }
>     if (this.#nextIndex === Number.MAX_SAFE_INTEGER) {
>       throw new RangeError('Index space exhausted');
>     }
>     const index = this.#nextIndex++;
>     while (
>       this.#head < this.#deque.length &&
>       this.#deque[this.#head].index <= index - this.#width
>     ) {
>       this.#head++;
>     }
>     while (
>       this.#deque.length > this.#head &&
>       this.#deque.at(-1).value >= value
>     ) {
>       this.#deque.pop();
>     }
>     this.#deque.push({ index, value });
>     // Не используем shift на каждом шаге и не храним старый префикс вечно.
>     if (this.#head >= this.#width) {
>       this.#deque = this.#deque.slice(this.#head);
>       this.#head = 0;
>     }
>   }
>
>   getMin() {
>     return this.#deque[this.#head]?.value;
>   }
> }
> ```
>
> Удаление по позиции принципиально: две четвёрки занимают два места, хотя имеют одинаковое значение. В окне 3 после `[2, 4, 4, 6]` двойка уже вышла. В окне 1 после каждого add минимум равен новому значению. Проверь отрицательные числа, растущую и убывающую последовательности, длинные серии одинаковых значений и многократный getMin без add.
>
> Каждая пара добавляется один раз и удаляется не более одного раза: обработка N элементов занимает O(N) суммарно. Отдельный add может удалить O(width) кандидатов, поэтому время именно амортизированное. Срез копирует не более width активных элементов после минимум width сдвигов головы; это тоже O(N) суммарно. Активная очередь и ещё не удалённый префикс занимают O(width), getMin — O(1). Защита счётчика останавливает поток до потери точности индексов Number; для ещё более долгого потока потребуется перенумерация или BigInt.

> [!followup]- Почему более старое значение, не меньше нового, больше никогда не станет минимумом будущего окна?
>
> Пусть старое значение `a` добавлено раньше нового `b`, причём `a >= b`. В каждом будущем окне, где ещё есть `a`, уже есть `b`: его индекс больше, поэтому он выходит из окна позже. Значит, удаление `a` из очереди кандидатов сохраняет минимум. Для равных значений можно оставить более новое, если контракт возвращает только число.
>
> Например, при ширине 3 после последовательности `[7, 5, 5]` достаточно хранить второй элемент со значением 5, потому что первый исчезнет раньше. При добавлении 6 он останется минимумом. Сравнивайте сроки жизни по индексам добавления, а не по значениям. Из головы дека удаляются истёкшие кандидаты; с хвоста — те, кого вытеснило новое значение. Каждая запись удаляется не более одного раза, поэтому добавление амортизированно стоит `O(1)`.

> [!followup]- Что потребуется изменить для окна по времени, особенно если события приходят не по порядку?
>
> Определите время окна и границы, например `(now - duration, now]`. Если события приходят в порядке своих timestamp, монотонный дек остаётся пригоден: вместо индекса храните время и удаляйте просроченные записи в том числе при чтении, когда новых событий нет. Если окно основано на времени получения, этот порядок проще обеспечить, но результат уже не отражает время события.
>
> Для event time при переупорядочивании можно буферизовать до watermark с согласованным допустимым опозданием. По мере продвижения watermark выпускайте накопленные события с timestamp не позже него в порядке времени и применяйте дек. Например, значение с временем 10:01, пришедшее после 10:02, учитывается, если окно ещё не закрыто. Решите, что делать с более поздним событием: отбросить и учесть метрикой либо пересчитать и отправить поправку. Без границы опоздания одновременно гарантировать окончательный ответ и ограниченную задержку нельзя.
