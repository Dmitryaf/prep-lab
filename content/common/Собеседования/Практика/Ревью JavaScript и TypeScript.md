# Ревью JavaScript и TypeScript

[[Собеседования/00. Карта раздела|Карта банка]]

Нужно не найти максимальное количество замечаний, а выделить риски по влиянию и предложить проверяемое улучшение.

## 1. Запрос без обработки HTTP-ошибки



```ts
async function loadUser(id: string) {
  const response = await fetch(`/api/users/${id}`)
  return response.json() as Promise<User>
}
```

Разобрать код состояния HTTP, проверку данных во время выполнения, отмену, тип ошибки и ответственность функции.

> [!example]- Разбор простыми словами
>
> Проверь response.ok до json. Прочитай данные как unknown и проверь ожидаемые поля; as не проверяет ответ сервера. Id кодируй для сегмента URL. Отмену передавай параметром, если она нужна вызывающему сценарию. HTTP 404, сетевая ошибка и неверный JSON должны оставаться различимыми.
>
> ```js
> // checked-example: review-http-user
> async function loadUser(id, { signal } = {}) {
>   const response = await fetch(`/api/users/${encodeURIComponent(id)}`, { signal });
>   if (!response.ok) throw new Error(`HTTP ${response.status}`);
>   const data = await response.json();
>   if (data === null || typeof data !== 'object' ||
>       typeof data.id !== 'string' || typeof data.name !== 'string') {
>     throw new Error('Invalid user response');
>   }
>   return data;
> }
> ```
>
> Контракт здесь требует строковые id и name. Проверь успешный ответ, id со слешем, 404 без чтения тела, неверную форму JSON, ошибку разбора JSON и передачу signal. Загрузчик не решает, какой результат актуален для экрана: это обязанность потребителя. В приложении с общим обработчиком ошибок можно ввести отдельные классы ошибок; для этой задачи достаточно сохранить причину отказа, не превращая любой отказ в пустой объект.
>
> Основание: [MDN — Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch). Решение и проверки составлены для этого упражнения.


**Критерии ответа:** Различаю HTTP, транспорт и контракт JSON; кодирую id, сохраняю отмену и предлагаю проверку каждого отказа.

**Изучить:** [[Фронтенд/API браузера/05. Fetch, CORS и сетевые запросы/03. AbortController и race condition в запросах|Механизм и пример]]

**Уточнения**
- API вернул 200 и объект неверной формы. Где проверить контракт и какой результат увидит вызывающий код?
- Пользователь сменил id до завершения запроса. Какая часть решения относится к загрузчику, а какая к потребителю?

## 2. Последовательная загрузка

```ts
for (const id of ids) {
  result.push(await loadItem(id))
}
```

Обсудить необходимость порядка, лимит конкурентности, partial failure и размер `ids` до замены на `Promise.all`.

> [!example]- Разбор простыми словами
>
> Если запросы независимы и их немного, Promise.all(ids.map(loadItem)) сокращает общее ожидание. Если есть лимит сервера — используй пул; если один результат нужен следующему — оставь последовательность. Выбери отдельно: первый отказ прерывает общий результат или нужны все статусы.

## 3. Небезопасный публичный контракт

```ts
function updateSettings(key: string, value: any): any {
  settings[key] = value
  return settings
}
```

Предложить типобезопасный API, определить допустимые ключи и решить, нужна ли мутация.

> [!example]- Разбор простыми словами
>
> Свяжи ключ и значение: `function updateSettings<K extends keyof Settings>(key: K, value: Settings[K])`. Меняй только выбранное поле либо возвращай новый объект — в зависимости от того, кто владеет состоянием. Параметр типа проверяет допустимые сочетания ключа и значения при компиляции. Полученные извне данные всё равно проверяются во время работы программы.

## 4. Скрытая квадратичная сложность



```ts
const rows = orders.map(order => ({
  ...order,
  user: users.find(user => user.id === order.userId),
}))
```

Оценить реальный масштаб, построить индекс и обсудить отсутствующего пользователя.

> [!example]- Разбор простыми словами
>
> Сначала построй Map из users по id, затем для каждого заказа возьми пользователя по userId. В обычной модели Map время меняется с O(orders × users) на O(orders + users), появляется память под индекс. Для отсутствующего пользователя выбери явный результат, а для повторяющихся id — правило разрешения дубля.
>
> ```js
> // checked-example: review-user-index
> function joinOrders(orders, users) {
>   const byId = new Map();
>   for (const user of users) {
>     if (!byId.has(user.id)) byId.set(user.id, user);
>   }
>   return orders.map(order => ({ ...order, user: byId.get(order.userId) }));
> }
> ```
>
> Договоримся, что id — строки. `find` возвращал первое совпадение: поэтому повторный id не перезаписываем. Отсутствующий пользователь остаётся undefined, входные массивы и объекты не меняются. Проверь дубли id, отсутствующего пользователя и пустые массивы. Для малого списка цена индекса может превысить выигрыш; при повторных запросах индекс имеет смысл переиспользовать только с корректной инвалидацией. Оценка линейного времени предполагает среднюю константную стоимость операций Map; стандарт не требует конкретной реализации хеш-таблицей.
>
> Основание: [MDN — Map](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Map). Решение и проверки составлены для этого упражнения.


**Критерии ответа:** Оцениваю время и память, сохраняю правило первого совпадения, проверяю отсутствие пользователя и не мутирую входы.

**Изучить:** [[Фронтенд/JavaScript/08. Копирование объектов и иммутабельность/01. Ссылки и поверхностное копирование|Механизм и пример]]

**Уточнения**
- В users два объекта с одним id. Как сохранить поведение исходного find?
- Данных мало и обновления частые. Когда построение индекса не даёт пользы?

## Ошибка при сужении типа

**ID вопроса:** 5. Ошибка narrowing

```ts
type Result = { data: User } | { error: string }

function render(result: Result) {
  return result.data.name
}
```

Исправь описание типов и покажи, как проверка общего отличительного поля позволяет выбрать нужный вариант объединения.

> [!example]- Разбор простыми словами
>
> Сначала проверь `'data' in result`, затем читай result.data.name; в другой ветке показывай result.error. Для расширяемого контракта удобно добавить `status: 'success' | 'error'` в разные варианты и сужать по status. Утверждение `as` только скроет проблему.

## Порядок ревью

1. Уточнить назначение и ограничения кода.
2. Сначала назвать correctness и security risks.
3. Затем обработку ошибок и крайние случаи.
4. После этого — читаемость, типизацию, тестируемость и performance.
5. Не переписывать всё без необходимости.
