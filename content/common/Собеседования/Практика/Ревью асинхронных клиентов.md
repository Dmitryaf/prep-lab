# Ревью асинхронных клиентов

[[Собеседования/00. Карта раздела|Карта банка]]

## Ревью клиента флагов: остановка и поздний ответ

**Формат раунда:** Ревью кода

Клиент хранит начальные флаги, обновляет их с заданным интервалом, предоставляет `getToggle`, `start`, `stop`, `forceUpdate`.

Найди ошибки в порядке действий, покажи воспроизводящие сценарии и исправь их. Контракт: constructor запускает периодическое обновление; повторный `start` ничего не дублирует; `stop` отменяет текущую попытку и запрещает её поздний результат. `forceUpdate` разрешён и после остановки, делает одно обновление без возобновления периодических запросов; одновременные вызовы объединяются. Ошибка сохраняет последние хорошие данные. Интервал отсчитывается после завершения попытки.

```js
// Учебный код с намеренными ошибками.
class TogglesClient {
  constructor(initialData, { url, interval }) {
    this.data = initialData;
    this.url = url;
    this.interval = interval;
    this.start();
  }
  getToggle(key) { return this.data[key]; }
  start() {
    this.timer = setTimeout(() => {
      this.forceUpdate().finally(() => this.start());
    }, this.interval);
  }
  stop() { clearTimeout(this.timer); }
  async forceUpdate() {
    const response = await fetch(this.url);
    this.data = await response.json();
  }
}
```

> [!example]- Разбор и исправленное решение
>
> Главная ошибка: `stop` очищает таймер, но уже начавшийся запрос позднее изменит данные и вызовет `start`. Повторные `start` создают независимые цепочки таймеров. Ручное обновление может пересечься с автоматическим, и поздний ответ затрёт свежий. HTTP 503 не отклоняет `fetch` сам по себе. Rejection из автоматического запроса остаётся необработанным.
>
> Нужно отдельно хранить, включены ли периодические запросы и какая попытка сейчас актуальна. После `stop` старый запрос больше не должен менять данные или запускать следующий таймер. `AbortController` пытается остановить запрос, а сравнение с текущей попыткой защищает состояние, даже если транспорт игнорирует отмену. Объединение параллельных обновлений выбрано явно: `forceUpdate` не обещает второй запрос после уже выполняющегося.
>
> ```js
> // checked-example: review-toggles
> class TogglesClient {
>   #data;
>   #url;
>   #interval;
>   #running = false;
>   #timer = null;
>   #flight = null;
>
>   constructor(initialData, { url, interval }) {
>     if (!Number.isFinite(interval) || interval <= 0)
>       throw Error('Invalid interval');
>     this.#data = { ...initialData };
>     this.#url = url;
>     this.#interval = interval;
>     this.start();
>   }
>   getToggle(key) {
>     return Object.hasOwn(this.#data, key) ? this.#data[key] : undefined;
>   }
>   #clearTimer() {
>     clearTimeout(this.#timer);
>     this.#timer = null;
>   }
>   #schedule() {
>     if (!this.#running || this.#flight || this.#timer !== null) return;
>     this.#timer = setTimeout(() => {
>       this.#timer = null;
>       // Ручной вызов возвращает ошибку вызывающему; polling сохранит данные.
>       this.forceUpdate().catch(() => {});
>     }, this.#interval);
>   }
>   start() {
>     if (this.#running) return;
>     this.#running = true;
>     this.#schedule();
>   }
>   stop() {
>     this.#running = false;
>     this.#clearTimer();
>     const old = this.#flight;
>     this.#flight = null;
>     old?.controller.abort();
>   }
>   forceUpdate() {
>     if (this.#flight) return this.#flight.promise;
>     this.#clearTimer();
>     const flight = { controller: new AbortController(), promise: null };
>     this.#flight = flight;
>     flight.promise = Promise.resolve()
>       .then(async () => {
>         const response = await fetch(this.#url, {
>           signal: flight.controller.signal,
>         });
>         if (!response.ok) throw Error(`HTTP ${response.status}`);
>         const data = await response.json();
>         if (!data || typeof data !== 'object' || Array.isArray(data)) {
>           throw Error('Invalid toggle data');
>         }
>         if (this.#flight !== flight) return false;
>         this.#data = data;
>         return true;
>       })
>       .finally(() => {
>         if (this.#flight !== flight) return;
>         this.#flight = null;
>         this.#schedule();
>       });
>     return flight.promise;
>   }
> }
> ```
>
> Проверка: начни запрос A, вызови `stop`, затем `start` и запрос B. Заверши B, затем A: остаются данные B и один таймер. Отдельно проверь два `start`, общий Promise двух `forceUpdate`, HTTP/JSON-ошибку и ручное обновление остановленного клиента. Если abort проигнорирован, старый сетевой запрос может физически продолжаться, но не влияет на актуальное состояние.
>
> Для диагностики полезно хранить последнюю ошибку и время успешного обновления; при повторных отказах увеличивать задержку. В решении фоновый вызов перехватывает ошибку и сохраняет прежние данные, но пока не записывает её в журнал. Вложенные объекты флагов в этом примере считаются неизменяемыми потребителем. getToggle читает только собственные ключи: отсутствующий флаг constructor или toString не должен возвращать свойство прототипа.

**Критерии ответа:** Воспроизвожу гонку stop/in-flight, разделяю остановку расписания и актуальность результата, сохраняю данные при отказе, проверяю повторный start и ручное обновление.

**Уточнения**
- Транспорт проигнорировал abort, а новый запрос уже завершён. Что защищает данные и расписание?
- Чем должна отличаться ошибка ручного forceUpdate от ошибки фонового polling для вызывающего кода?

> [!followup]- Транспорт проигнорировал abort, а новый запрос уже завершён. Что защищает данные и расписание?
>
> `AbortController` пытается остановить работу, а право менять состояние защищает идентичность попытки. При `stop()` сначала отзовите право старой попытки на публикацию: смените поколение и отсоедините её от `inFlight`, затем вызовите `abort()`. Перед заменой флагов проверяйте идентичность после всех `await`. В `finally` очищайте только собственный `inFlight`; планируйте следующий тик, только если polling включён и поколение расписания совпадает.
>
> Проверка: A начал polling, затем `stop()`, ручной B вернул новые флаги, A игнорирует отмену и заканчивается последним. Флаги должны остаться от B, а новый тик не появиться. Ещё проверьте быстрый `stop → start`: старая попытка не вправе ни отменить новый таймер, ни создать второй. Если A физически продолжает работать, гарантировать отсутствие перекрытия транспорта нельзя; гарантировать корректность состояния можно.

> [!followup]- Чем должна отличаться ошибка ручного forceUpdate от ошибки фонового polling для вызывающего кода?
>
> Ручной `forceUpdate()` возвращает Promise конкретной попытки. При отказе он отклоняется, чтобы вызывающий код мог показать ошибку обновления или предложить повтор. Фоновый polling запускает тот же механизм, но перехватывает отказ в своей точке входа, пишет диагностическое событие и, если ещё активен, планирует следующий тик. В обоих случаях последние валидные флаги остаются доступными.
>
> Например, при HTTP 503 пользователь после нажатия «Обновить» видит сообщение о неудаче, а обычный периодический отказ не порождает всплывающее окно и необработанный Promise. Если ручной вызов присоединился к фоновому, оба ждут один сетевой запрос: фон обрабатывает отказ для себя, ручной вызов всё равно видит отклонение. В журнале ошибок отличайте штатную отмену через `stop()` от отказа сервера.

## Ревью клиента аналитики: очередь во время отправки

**Формат раунда:** Ревью кода

Метод `queueEvent(event)` добавляет событие, `sendNow()` отправляет накопленное, отправка также выполняется периодически. Событие содержит `type`, `version`, `args`, `timestamp`; тело запроса — JSON-массив.

Найди потерю и дублирование событий, определи поведение при ошибке и исправь код. События — JSON-совместимые неизменяемые снимки; за раз отправляется одна пачка. Одновременный `sendNow` ждёт текущую отправку; новые события остаются в очереди до следующей. При ошибке отправляемая пачка возвращается перед более новыми событиями. Метод `close` освобождает расписание и запрещает новые операции; текущая отправка может завершиться. Долговечная очередь после перезагрузки вне этого упражнения.

```js
// Учебный код с намеренными ошибками.
class AnalyticsClient {
  constructor(url, interval) {
    this.url = url;
    this.events = [];
    setInterval(() => this.sendNow(), interval);
  }
  queueEvent(event) { this.events.push(event); }
  async sendNow() {
    if (!this.events.length) return;
    await fetch(this.url, {
      method: 'POST',
      body: JSON.stringify(this.events),
    });
    this.events = [];
  }
}
```

> [!example]- Разбор и исправленное решение
>
> Сценарий потери: A отправляется, B добавляется во время запроса, успех A очищает и B. Два параллельных `sendNow` отправляют A дважды. HTTP-ошибка считается успехом; таймер не освобождается, нет обработки rejection. Сохранение ссылки на объект позволяет чужому коду менять ещё не отправленное событие.
>
> Отделим отправляемую пачку от очереди. Пока она в работе, новые события накапливаются отдельно. Успех подтверждает только эту пачку; отказ возвращает её в начало очереди. Очередь нельзя очищать целиком после `await`. Таймер запускает следующую попытку после завершения предыдущей; `close` запрещает его восстановление.
>
> ```js
> // checked-example: review-analytics
> class AnalyticsClient {
>   #events = [];
>   #url;
>   #interval;
>   #flight = null;
>   #timer = null;
>   #closed = false;
>
>   constructor(dataUrl, interval) {
>     if (!Number.isFinite(interval) || interval <= 0)
>       throw Error('Invalid interval');
>     this.#url = dataUrl;
>     this.#interval = interval;
>     this.#schedule();
>   }
>   #schedule() {
>     if (this.#closed || this.#flight || this.#timer !== null) return;
>     this.#timer = setTimeout(() => {
>       this.#timer = null;
>       this.sendNow().catch(() => {});
>     }, this.#interval);
>   }
>   queueEvent(event) {
>     if (this.#closed) throw Error('Closed');
>     // Контракт принимает только JSON-совместимое событие.
>     const snapshot = JSON.parse(JSON.stringify(event));
>     this.#events.push(snapshot);
>   }
>   sendNow() {
>     if (this.#closed) return Promise.reject(Error('Closed'));
>     if (this.#flight) return this.#flight;
>     clearTimeout(this.#timer);
>     this.#timer = null;
>     if (!this.#events.length) {
>       this.#schedule();
>       return Promise.resolve();
>     }
>     const batch = this.#events;
>     this.#events = [];
>     this.#flight = Promise.resolve()
>       .then(async () => {
>         const response = await fetch(this.#url, {
>           method: 'POST',
>           headers: { 'Content-Type': 'application/json' },
>           body: JSON.stringify(batch),
>         });
>         if (!response.ok) throw Error(`HTTP ${response.status}`);
>       })
>       .catch((error) => {
>         this.#events = batch.concat(this.#events);
>         throw error;
>       })
>       .finally(() => {
>         this.#flight = null;
>         this.#schedule();
>       });
>     return this.#flight;
>   }
>   close() {
>     this.#closed = true;
>     clearTimeout(this.#timer);
>     this.#timer = null;
>   }
> }
> ```
>
> Проверь порядок: A отправляется, приходит B, отказ A — следующая пачка содержит A,B. При успехе A следующий запрос содержит только B. Проверь HTTP 503, два `sendNow`, изменение исходного объекта, пустую очередь и `close` во время запроса. Заголовок описывает тело, а `response.ok` отделяет HTTP-успех от состоявшегося сетевого обмена.
>
> Пока клиент работает, новые события больше не теряются при завершении старой отправки. Однако потеря ответа после записи на сервере приведёт к повторной доставке. Чтобы не учитывать событие дважды, нужен стабильный ID и проверка повтора на сервере. Для долгой работы также задают предел очереди, задержку повторов и обработку ошибок 4xx, которые повтор не исправит; учитывают согласие на аналитику и сохранение очереди между запусками. Закрытие вкладки или `close` может оставить неотправленные события, и `sendBeacon` сам по себе этого не исключает.

**Критерии ответа:** Разделяю batch и новые события, сериализую отправку, восстанавливаю очередь при сетевом/HTTP-отказе, объясняю границу дедупликации и жизненный цикл таймера.

> [!followup]- Ответ сервера потерян после записи пакета. Как повторить запрос без повторного учёта тех же данных?
>
> Назначьте отправляемому пакету стабильный ключ до первого обращения и повторяйте тот же пакет с тем же ключом. Сервер должен атомарно сохранить запись о ключе и применить события либо дедуплицировать каждое событие по стабильному ID. Запрос с тем же ключом и другим набором событий отвергайте. Новые события живут отдельно и образуют следующий пакет; не меняйте тело уже начатого пакета при повторе.
>
> Например, сервер записал `[A, B]`, но ответ потерялся. Клиент повторяет `[A, B]` с прежним ключом, сервер возвращает ранее сохранённый итог без повторного учёта. Если допускается частичная запись пакета, нужен контракт результата по событиям и дедупликация на уровне события. Храните ключи не меньше согласованного горизонта повторов: после истечения срока повтор снова может учесть данные.

> [!followup]- Сервер недоступен час. Как ограничить очередь, не обещая невозможную доставку всех событий?
>
> Ограничьте очередь по числу событий и байтам, задайте максимальный возраст. Когда она заполнена, применяйте явную политику: отклонять новые события, вытеснять старые либо сохранять только приоритетные. Учитывайте отправляемый пакет в общем бюджете и фиксируйте потери по причине. Повторы запускайте с увеличиваемой задержкой, разбросом и ограничением частоты, сохраняя порядок повторяемого пакета.
>
> Например, в памяти помещается 500 событий. При часовом отказе продукт может предпочесть свежие сигналы аналитики и вытеснять самые старые, но эта политика должна быть видна в метрике потерь. События, которые нельзя терять, требуют другого канала с устойчивым хранением и подтверждениями. Даже дисковая очередь конечна и должна иметь правила переполнения; она лишь переживает перезапуск, который не покрывает исходный контракт упражнения.
