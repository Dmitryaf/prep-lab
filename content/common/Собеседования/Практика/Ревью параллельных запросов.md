# Ревью параллельных запросов

## Лимит запросов, порядок результатов и раннее завершение

**Формат раунда:** Ревью кода
**Критерии ответа:** Показываю превышение лимита и ранний возврат, сохраняю порядок входа, заполняю свободный слот сразу; отделяю прекращение запуска от отмены уже начатой работы.

Исходная задача описывает параллельное получение элементов с ограничением числа запросов. Ниже — самостоятельно созданная JavaScript-версия с намеренными дефектами, а не код из интервью. В исходнике ошибки сервера исключены; обработка отказа добавлена здесь как явно отдельное требование.

На входе массив `ids`, целый `limit >= 1` и `get(id)`, возвращающая Promise. Результат должен соответствовать порядку `ids`, включая повторяющиеся ID. В одном вызове одновременно работает не больше `limit` запросов. Освободившийся слот заполняется без ожидания остальной группы. Пустой массив даёт `[]`. При отказе итоговый Promise отклоняется, новые запросы больше не запускаются; уже запущенные операции продолжаются, поскольку `get` не поддерживает отмену.

```js
async function brokenMapLimit(ids, limit, get) {
  const values = [];
  ids.forEach(async id => {
    values.push(await get(id));
  });
  return values;
}
```

Найдите наблюдаемые ошибки. Предложите проверки с управляемыми Promise: первый запрос медленнее второго, один отклоняется, вход пустой, лимит превышает длину входа. Затем исправьте функцию. Фиксированная обработка пачками соблюдает лимит, но не удовлетворяет требованию немедленно занимать свободный слот.

> [!answer]- Разбор и исправление
>
> `forEach` игнорирует возвращённые Promise: функция возвращает результат до загрузки, запускает весь массив одновременно и записывает значения в порядке завершения. Отказы вложенных async-функций не связаны с итоговым Promise. `limit` не используется.
>
> Создадим не более `limit` работников. Каждый резервирует индекс до `await`, сохраняет результат на эту позицию и затем берёт следующую работу. JavaScript выполняет синхронное резервирование последовательно; блокировка для счётчика здесь не нужна.
>
> ```js
> // checked-example: review-map-limit
> async function mapLimit(ids, limit, get) {
>   if (!Number.isInteger(limit) || limit < 1) throw new RangeError('Invalid limit');
>   const result = new Array(ids.length);
>   let next = 0;
>   let failed = false;
>   async function worker() {
>     while (!failed && next < ids.length) {
>       const index = next++;
>       try {
>         result[index] = await get(ids[index]);
>       } catch (error) {
>         failed = true;
>         throw error;
>       }
>     }
>   }
>   await Promise.all(Array.from({ length: Math.min(limit, ids.length) }, worker));
>   return result;
> }
> ```
>
> При `limit=2` сначала идут A и B. Если B завершился, сразу запускается C, даже если A ещё ждёт. Ответы остаются на исходных позициях. `Promise.all` наблюдает все worker-Promise, поэтому последующий отказ другого работника не становится необработанным rejection. После обнаруженного отказа новые элементы не берутся. Уже выполняющийся запрос невозможно отменить одним флагом: для этого нужен отдельный контракт `AbortSignal` у загрузчика.
>
> Число вызовов при успехе равно длине входа; память O(n) для результата и O(min(n, limit)) для работников. Общий глобальный лимит нескольких одновременных запусков — другая задача, здесь у каждого вызова свой счётчик.
