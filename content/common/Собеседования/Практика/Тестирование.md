## Форма: результат, ошибка и повтор

Название сохраняется через `save(title)`. Контракт: пробелы по краям убираются; пустое название не отправляется; пока запрос активен, повторный submit игнорируется. При ошибке ввод сохраняется, появляется `role="alert"`, повтор разрешён. Успех сообщает родителю `{ id, title }` из ответа ровно один раз, ошибка ничего не сообщает. API принимает строку и возвращает Promise объекта либо отклоняет его с Error; политика повторов здесь не нужна.

В `TitleForm.vue` есть ошибки. Напиши тесты контрактов, исправь только выявленные причины. Что намеренно не проверять на уровне этого компонента?

```vue
<script setup lang="ts">
import { ref } from 'vue';
type Item = { id: string; title: string };
const props = defineProps<{ save: (title: string) => Promise<Item> }>();
const emit = defineEmits<{ saved: [item: Item] }>();
const title = ref('');
const pending = ref(false);
const error = ref('');
async function submit() {
  pending.value = true;
  try {
    const item = await props.save(title.value);
    emit('saved', item);
  } catch {
    title.value = '';
    error.value = 'Не удалось сохранить';
  } finally {
    pending.value = false;
  }
}
</script>
<template>
  <form @submit.prevent="submit">
    <label>Название <input v-model="title" name="title"></label>
    <button :disabled="pending">Сохранить</button>
    <p v-if="error" role="alert">{{ error }}</p>
  </form>
</template>
```

Используй управляемый Promise в mock `save`: проверь UI до resolve/reject и после него. Отдельно отправь submit самой форме второй раз: блокировка кнопки и защита обработчика — разные вещи. После ошибки запусти успешную попытку; старое сообщение не должно оставаться. Не ограничивай тест утверждением `save` был вызван.

> [!example]- Разбор — базовое решение
>
> Основные ошибки: пустой ввод не проверяется и не нормализуется, повторный вызов во время запроса не блокируется, обработчик ошибки стирает введённый текст. В исходном компоненте достаточно заменить `submit`:
>
> ```js
> // core-example: title-submit
> async function submit() {
>   if (pending.value) return;
>   const normalized = title.value.trim();
>   if (!normalized) {
>     error.value = 'Введите название';
>     return;
>   }
>   pending.value = true;
>   error.value = '';
>   try {
>     const item = await props.save(normalized);
>     emit('saved', item);
>   } catch {
>     error.value = 'Не удалось сохранить';
>   } finally {
>     pending.value = false;
>   }
> }
> ```
>
> Снимок `normalized` относится к одной операции. При ошибке `title` сохраняется, а новая отправка очищает прежнее сообщение об ошибке. Событие содержит объект сервера. Проверка повторного запуска работает и при прямой отправке формы во время ожидания.
>
> Ключевой тест VTU/Vitest после подключения TitleForm и управляемого Promise:
>
> ```js
> const request = deferred(); // {promise, resolve, reject}
> const save = vi
>   .fn()
>   .mockReturnValueOnce(request.promise)
>   .mockResolvedValueOnce({ id: '1', title: 'Название' });
> const wrapper = mount(TitleForm, { props: { save } });
> try {
>   await wrapper.get('input').setValue('  Название  ');
>   await wrapper.get('form').trigger('submit');
>   await wrapper.get('form').trigger('submit');
>   expect(save).toHaveBeenCalledTimes(1);
>   expect(save).toHaveBeenCalledWith('Название');
>   expect(wrapper.get('button').element.disabled).toBe(true);
>   request.reject(new Error('offline'));
>   await flushPromises();
>   expect(wrapper.get('input').element.value).toBe('  Название  ');
>   expect(wrapper.get('[role="alert"]').text()).toBe('Не удалось сохранить');
>   expect(wrapper.emitted('saved')).toBeUndefined();
>   await wrapper.get('form').trigger('submit');
>   await flushPromises();
>   expect(wrapper.emitted('saved')).toEqual([[{ id: '1', title: 'Название' }]]);
> } finally {
>   wrapper.unmount();
> }
> ```
>
> deferred создаётся обычным Promise с сохранёнными resolve/reject; mount и flushPromises импортируются из @vue/test-utils, vi/expect — из vitest. Тестовый runner для mount использует DOM-среду. Отдельным коротким тестом отправьте пробелы и проверьте, что save не вызван. Ожидание одного nextTick не заменяет завершение внешнего Promise. Серверные транзакции и реальная доставка не входят в этот компонентный тест; для них нужна отдельная проверка интеграции.

**Критерии ответа:** Тестами ловлю пустой ввод, отсутствие trim, двойной submit, потерю ввода при ошибке и лишнее событие saved.

## Гонка запросов: старый ответ и старый finally

Возьми собственную реализацию [[Собеседования/Практика/Vue#useFetch: реактивный адрес и состояния запроса|useFetch]]. Для этой проверки закрепи контракт: при смене URL данные очищаются, loading=true, error=null; состояние принадлежит последнему запросу. Отмена не гарантирует, что тестовый транспорт перестанет выдавать результат. После остановки scope новые результаты не применяются.

Напиши Vitest-тест через маленький компонент-хост или `effectScope`. Подставь transport с независимыми управляемыми Promise A и B. Запусти A, поменяй URL, запусти B. Проверь три разные последовательности:

1. B успешно заканчивается, затем A возвращает данные.
2. A заканчивается, пока B ещё pending: старый finally не снимает loading B.
3. B успешен, затем A отклоняется: старый catch не заменяет актуальное состояние ошибкой.

Добавь отказ именно B и остановку scope до ответа. В каждом тесте ожидай регистрацию нужного запроса перед его завершением; не используй `setTimeout(100)`. Если реализация принимает fetch, подставь Response с нужным JSON, а не объект другого интерфейса.

> [!example]- Разбор — базовое решение
>
> Один базовый useFetch с указанным контрактом. Вход — ref строки URL, transport имеет интерфейс fetch. При новом URL очищается прежнее состояние. JSON намеренно не типизирован: проверка схемы — отдельная обязанность API-адаптера.
>
> ```js
> // core-example: core-use-fetch
> import { ref, watch } from 'vue';
> export function useFetch(url, transport = fetch) {
>   const data = ref(null);
>   const error = ref(null);
>   const loading = ref(false);
>   watch(
>     url,
>     async (value, previous, onCleanup) => {
>       let current = true;
>       const controller = new AbortController();
>       onCleanup(() => {
>         current = false;
>         controller.abort();
>       });
>       data.value = null;
>       error.value = null;
>       loading.value = true;
>       try {
>         const response = await transport(value, { signal: controller.signal });
>         if (!response.ok) throw new Error('HTTP ' + response.status);
>         const body = await response.json();
>         if (current) data.value = body;
>       } catch (reason) {
>         if (current) error.value = reason;
>       } finally {
>         if (current) loading.value = false;
>       }
>     },
>     { immediate: true },
>   );
>   return { data, error, loading };
> }
> ```
>
> Для теста создайте effectScope, ref('/a') и transport, сохраняющий независимые deferred для каждого вызова. Создание useFetch должно происходить внутри scope.run. После `url.value='/b'` дождитесь nextTick и подтвердите, что зарегистрированы оба запроса. Завершайте их объектом `new Response(JSON.stringify({name:'B'}))`, а не произвольным DTO; затем используйте flushPromises для цепочки json/await.
>
> В сценарии B→A после обоих завершений data должно оставаться B, error — null, loading — false. В сценарии A→ожидающий B после A loading должен быть true и data — null. В сценарии успешный B→reject A не должна появиться ошибка. Отдельно отклоните B — ошибка видна, loading=false; верните HTTP 500 — тоже ошибка, а не успешный JSON.
>
> Перед ответом вызовите scope.stop, сохраните значения трёх ref, доставьте старый результат и сравните значения. Очистка ресурсов должна отменить запрос, но тестовый источник намеренно завершает Promise даже после отмены. Это проверяет обе гарантии: попытку отмены и запрет устаревшей записи. scope.stop вызывается в finally теста. Если убрать проверку актуальности только из finally, сценарий «A завершился, B ещё ожидает» должен перестать проходить — иначе тест не замечает эту ошибку.

**Критерии ответа:** Управляю порядком A/B и отдельно проверяю data, error, loading, поздний reject и stop scope.

## Таймер уведомления

Используй механизм [[Собеседования/Практика/Vue#Таймер сообщения и смена значения|таймера сообщения]], но сделай `Notice.vue` с входом `{ id, text } | null` и событием `expired(id)`. Событие приходит через 7000 мс после появления уведомления; новый id заменяет старый, даже если text совпадает. Компонент не меняет props. После unmount событие не приходит. Это отдельный публичный контракт для тестирования, а не доступ к закрытым ref.

Напиши компонент и тесты с `vi.useFakeTimers()`: до границы 6999 мс события нет, на 7000 мс есть один нужный id; B, пришедшее через 6000 мс после A, живёт собственные 7000 мс; null и unmount отменяют ожидание. Сравни два одинаковых текста с разными id. Покажи, как тест восстанавливает таймеры и освобождает wrapper при любой ошибке. Что изменится, если callback дополнительно ждёт Promise?

> [!example]- Разбор — базовое решение
>
> Notice владеет одним таймером на текущий id. Watcher очищает прежний таймер до нового ожидания и при удалении компонента; событие сообщает id, а не меняет props.
>
> ```vue
> <!-- core-example: core-notice -->
> <script setup>
> import { watch } from 'vue';
> const props = defineProps(['notice']);
> const emit = defineEmits(['expired']);
> watch(
>   () => props.notice?.id,
>   (id, previous, onCleanup) => {
>     if (id == null) return;
>     const timer = setTimeout(() => emit('expired', id), 7000);
>     onCleanup(() => clearTimeout(timer));
>   },
>   { immediate: true },
> );
> </script>
> <template>
>   <p v-if="notice" role="status">{{ notice.text }}</p>
> </template>
> ```
>
> В VTU/Vitest включите fake timers до mount. После появления A продвиньте время на 6999: expired отсутствует; ещё на 1 — массив событий равен `[ ['A'] ]`. Для замены: через 6000 мс установите B с тем же text и другим id через ожидаемый setProps. Через 1000 мс A не должен сработать; через ещё 5999 событий нет; последняя 1 мс даёт только B. Не запускайте все таймеры сразу — это скрывает неверную границу.
>
> Для null повторите начало, затем `await wrapper.setProps({notice: null})` и продвиньте часы: событий нет. Для unmount уничтожьте wrapper до границы и проверьте отсутствие новых emitted. В finally всегда вызывайте unmount и vi.useRealTimers; каждый сценарий использует новый wrapper и часы.
>
> Смена текста при прежнем id в этом контракте не перезапускает срок. Если это нужно продукту, измените контракт явно. Если callback ждёт Promise, используйте асинхронное продвижение таймеров и дождитесь очереди Promise/Vue; fake timers сами по себе не гарантируют завершение всего продолжения.

**Критерии ответа:** Проверяю границы 6999/7000, замену по id, одинаковый текст, null и unmount без старого события.

## Подписка: смена пользователя и unmount

Возьми [[Собеседования/Практика/Vue#Подписка на статус друга|подписку на статус друга]]. Уточнённый адаптер `subscribe(id, callback)` возвращает `unsubscribe()`. Источник может доставить уже поставленный в очередь callback после отписки. UI показывает статус только текущего id; при замене пользователя — «неизвестно» до нового события.

Сделай управляемый тестовый источник, сохраняющий обработчики и активные подписки. Через Vue Test Utils (VTU) смени A на B, доставь новое событие B и позднее событие A. Проверь интерфейс, освобождение A, отсутствие подписок после удаления компонента и независимость повторного подключения. Объясни, какая проверка обнаружит утечку, а какая — устаревшую запись. Не подменяй весь composable: тогда его жизненный цикл не проверяется.

> [!example]- Разбор — базовое решение
>
> Отписка освобождает ресурс, флаг active запрещает применять уже поставленный в очередь callback. Для одного строкового id и стабильного адаптера subscribe достаточно такого компонента:
>
> ```vue
> <!-- core-example: core-friend -->
> <script setup>
> import { ref, watch } from 'vue';
> const props = defineProps(['id', 'subscribe']);
> const status = ref('неизвестно');
> watch(
>   () => props.id,
>   (id, previous, onCleanup) => {
>     status.value = 'неизвестно';
>     let active = true;
>     const unsubscribe = props.subscribe(id, (value) => {
>       if (active) status.value = value;
>     });
>     onCleanup(() => {
>       active = false;
>       unsubscribe();
>     });
>   },
>   { immediate: true },
> );
> </script>
> <template>
>   <p role="status">{{ status }}</p>
> </template>
> ```
>
> Fake хранит массив `{id, callback, active}`. subscribe добавляет запись, возвращаемая функция ставит active=false. Метод обычной доставки вызывает только активные callbacks, а метод lateDelivery вызывает сохранённый callback даже после отписки. Последний нужен для проверки старой записи.
>
> Через mount передайте A и fake.subscribe, проверьте один активный ресурс. После `await wrapper.setProps({id:'B'})` A неактивен, B активен, UI показывает «неизвестно». Доставьте B='online', затем поздний A='offline', дождитесь nextTick: UI остаётся online. После unmount активных записей нет. Позднее событие B не меняет сохранённое состояние; при новом mount возникает ровно одна новая активная подписка и начальное «неизвестно».
>
> Проверка числа активных подписок обнаруживает утечку, а проверка текста после `lateDelivery` — применение устаревшего события. Нужны обе проверки. Все обёртки компонентов освобождаются в `finally`. В этой задаче подписка синхронно возвращает функцию отписки. Если создание подписки может завершиться ошибкой или выполняется асинхронно, дополнительно нужны обработка ошибки и отмена незавершённого создания.

**Критерии ответа:** Раздельно подтверждаю отсутствие активной подписки и неприменение позднего события; проверяю повторный mount.

## Интеграция Router, Pinia и API

В учебном приложении есть `/organizations/:org/orders?page=...`, список заказов и переход на `/organizations/:org/orders/:id`. Store кэширует страницы, запрос зависит от организации и номера страницы. После возврата фильтр и страница сохраняются; смена организации исключает чужие данные. API: `GET /api/organizations/:org/orders?page=N` возвращает `{ items, nextPage }`; 403 показывает отсутствие доступа без старых строк.

Напиши интеграционный тест страницы с реальными Router, Pinia и дочерним списком, подменив HTTP-границу. Создавай новый router и store для каждого теста. Пройди страницу 2→заказ→назад и A→B с задержанным ответом A. Проверь URL, аргументы запроса и видимые строки; затем отказ доступа. Выбери один контракт компонента для unit-теста и один браузерный риск, который это окружение не проверит. В отчёте явно назови, что backend здесь fake.

> [!example]- Проверка тестов
>
> Заглушка RouterLink, подмена всего хранилища и снимок разметки оболочки не проверяют совместную работу частей приложения. Нужно дождаться готовности маршрутизатора и нужного ответа, изолировать кэш, восстановить параметры URL и проверить отсутствие данных A. Тестовое DOM-окружение не подтверждает реальную геометрию страницы, серверные права или фактический сетевой контракт.

## Playwright: сохранение с неопределённым результатом

На тестовом стенде форма заявки делает `POST /api/requests` с ключом операции, получает `{ id, status }` и показывает результат. В заданном варианте сервер сохраняет заявку, но ответ теряется. Клиент после reload умеет восстановить операцию через согласованный status endpoint и не создаёт вторую заявку.

Сначала опиши предусловия и недостающий контракт восстановления: где сохраняется идентичность операции и как сервер находит её после reload? Затем напиши ключевой Playwright-тест успеха с реальным тестовым backend, изолированными данными и проверкой сохранения после reload. Отдельным браузерным интеграционным тестом через `page.route` воспроизведи потерю ответа: fake должен запомнить принятую заявку и вернуть её статус при восстановлении. Проверь UI и число **созданных** записей, а не только число POST. Это упражнение на учебном стенде, без реальной оплаты и внешних сервисов.

Выбирай элементы по роли/названию, используй ожидающие assertions. Уточни очистку данных и параллельные запуски. Что route-тест не доказывает о реальной идемпотентности backend? Как дополнительно проверить 422 и доступность ошибки без создания десятка однотипных e2e?

> [!example]- Разбор — базовое решение
>
> Сначала нужен конкретный учебный контракт. Перед POST клиент создаёт operationId и сохраняет его вместе с отправляемым снимком в storage; повтор той же операции использует тот же id. Сервер связывает id с пользователем и телом команды, атомарно создаёт запись и сохраняет исход. Повтор с тем же id и иным телом — конфликт. Статус возвращается по GET `/api/operations/:operationId`. Сам ключ не заменяет авторизацию.
>
> После потери ответа UI показывает «Результат уточняется». При reload он читает сохранённый id и получает статус; успех подтверждается записью с id, а не отсутствием сетевой ошибки. Если статус неизвестен, это ещё не разрешение создать новую операцию. Правило повторного POST с тем же ключом, срок хранения ключа и атомарность принадлежат backend-контракту.
>
> Ключ браузерного интеграционного теста с fake API:
>
> ```js
> const records = new Map(); // создаётся внутри каждого теста, переживает reload страницы
> await page.route('**/api/requests', async (route) => {
>   const body = route.request().postDataJSON();
>   const key = body.operationId;
>   if (!records.has(key))
>     records.set(key, { id: 'request-1', status: 'created' });
>   // Запись уже есть, но браузер не получает подтверждение.
>   await route.abort('failed');
> });
> await page.route('**/api/operations/*', async (route) => {
>   const key = decodeURIComponent(
>     new URL(route.request().url()).pathname.split('/').at(-1),
>   );
>   const record = records.get(key);
>   await route.fulfill({
>     status: record ? 200 : 404,
>     json: record || { status: 'unknown' },
>   });
> });
> await page.goto('/lab/requests');
> await page.getByLabel('Название').fill('Учебная заявка');
> await page.getByRole('button', { name: 'Создать заявку' }).click();
> await expect(page.getByRole('status')).toHaveText('Результат уточняется');
> await page.reload();
> await expect(page.getByRole('status')).toHaveText('Создано: request-1');
> expect(records.size).toBe(1);
> ```
>
> Это пример для описанного учебного стенда; `/lab/requests` и API не являются endpoint платформы Projects Map. import test/expect и настройка baseURL задаются проектом стенда. Fake специально хранит факт создания до обрыва, а reload не очищает Map в тестовом процессе. Если клиент создаст новый ключ после reload, GET не подтвердит прежний результат и тест не пройдёт. Если он пошлёт второй POST с новым ключом, размер Map поймает дубль. Защиту backend от изменённого тела такой сокращённый fake не доказывает.
>
> Настоящий e2e запускают без page.route: создают изолированный тестовую организацию и пользователя, отправляют форму, проверяют запись через тестовый API чтения или БД, обновляют страницу и сравнивают id. Контрольный повтор с тем же operationId должен оставлять одну запись; другие данные запроса с тем же id должен дать согласованный конфликт. Данные убирают в finally по уникальному testRunId, не очищая общий каталог. Для 422 отдельный интеграционный тест проверяет доступную ошибку, сохранение ввода и отсутствие записи.
>
> Если тестового backend нет, эту внешнюю гарантию нельзя объявить проверенной. Браузерный fake подтверждает восстановление клиента в заданном сценарии, а не атомарность и настоящую идемпотентность сервера.

**Критерии ответа:** Различаю неизвестный исход и отказ; сохраняю идентичность через reload и проверяю число записей, не только POST.

## Нестабильный тест и границы подмен

Тест иногда падает в CI, локально проходит. Две параллельные suite используют один аккаунт и запись с названием «Проверка». Найди причины, предложи порядок диагностики по trace/network/console и перепиши тест. Не начинай с увеличения retries.

```ts
import { test, expect } from '@playwright/test';

test('сохранение', async ({ page }) => {
  await page.goto('/requests/new');
  await page.locator('input').first().fill('Проверка');
  await page.locator('.btn-primary').click();
  await page.waitForTimeout(500);
  const message = await page.locator('.toast').textContent();
  expect(message).toBe('Сохранено');
});
```

В новой версии сначала задай устойчивый контракт результата и уникальные данные, затем напиши assertions. Выбери, где проверять потерю ответа, CSS-положение тоста, отправляемый DTO и серверную уникальность. Как отличить дефект приложения от недостатка ожидания или общей fixture? Назови критерий подтверждения исправления, включая параллельный запуск.

> [!example]- Проверка тестов
>
> Фиксированная пауза, случайный первый input, привязка к CSS и общие данные дают разные причины отказа. Нужны доказательства из упавшего запуска, изоляция и ожидание наблюдаемого состояния. Retries помогают расследованию, но успешный повтор не исправляет причину. Не следует переносить все проверки на самый дорогой уровень.
