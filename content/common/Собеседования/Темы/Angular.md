## Чем компонент Angular отличается от директивы и сервиса?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Компонент управляет шаблоном, директива меняет поведение существующего элемента, сервис содержит общую логику и зависимости. Внедрение зависимостей выбирает экземпляр по токену и области поставщика. Конкретные API и жизненный цикл проверяют по версии проекта.
>
> Поле ввода с подписью и ошибкой оформляют компонентом, поведение выделения текста — директивой, общий API-клиент — сервисом. Сервис не обязан быть глобальным: область provider определяет, какие потребители разделяют его экземпляр.
>

> [!followup]- Что такое автономный компонент Angular и как он подключает зависимости шаблона?
>
> Автономный компонент можно подключить без объявления в `NgModule`: зависимости его шаблона перечисляют в `imports` самого компонента. Например, карточка импортирует `UserAvatar` и `AsyncPipe`, если использует их в HTML. Это область доступных шаблону компонентов, директив и pipes, а не список экземпляров сервисов.
>
> Для совместимости с версиями, где standalone не был значением по умолчанию, в примере можно явно написать `standalone: true`. Провайдеры сервисов по-прежнему задают отдельно. Перенос компонента в standalone сам по себе не делает его лениво загружаемым и не создаёт глобальный сервис: загрузку определяет маршрут/динамический import, экземпляры — иерархия DI.

> [!followup]- Как различаются экземпляры сервиса при provider в компоненте и на уровне приложения?
>
> Provider на уровне приложения позволяет потребителям соответствующего injector разделять один экземпляр. `providers: [EditorState]` у компонента создаёт область для конкретного экземпляра компонента и его доступных DI-потомков. Две открытые формы с таким provider получают независимые черновики.
>
> Поиск зависимости идёт по иерархии: ближайший подходящий provider может перекрыть корневой. Поэтому случайное повторное объявление общего кэша в компоненте объясняет, почему соседние виджеты перестали разделять состояние. Проверка проста: изменить значение через один потребитель и сравнить значение/идентичность сервиса у второго. Термин «singleton» всегда требует области: корень одного приложения, а не все вкладки браузера.

> [!followup]- Зачем Angular нужен InjectionToken и почему одинаковое описание не делает токены одинаковыми?
>
> `InjectionToken<T>` задаёт ключ DI для значения, у которого нет подходящего runtime-класса: конфигурации, функции или объекта с интерфейсом. Интерфейс TypeScript после компиляции исчезает, поэтому сам по себе ключом внедрения быть не может.
>
> ```ts
> export const API_URL = new InjectionToken<string>('API_URL');
> // provider: { provide: API_URL, useValue: '/api' }
> // consumer: readonly apiUrl = inject(API_URL);
> ```
>
> Provider и consumer должны импортировать один объект `API_URL`. Два вызова `new InjectionToken('API_URL')` создают разные токены, хотя описание одинаковое; описание помогает диагностике, а не сравнению. В тесте можно заменить provider на тестовый URL, не меняя потребителя и не подменяя глобальные переменные.

> [!followup]- Почему метод Angular-сервиса теряет this при передаче callback и как это исправить?
>
> Значение `this` определяется способом вызова JavaScript-функции. В `service.save()` получатель сохранён; при передаче `subscribe(service.save)` библиотека получает только функцию и не обязана вызывать её с `service` в качестве `this`.
>
> Если `save` обращается к `this.http`, используй `subscribe(value => service.save(value))`, один раз привяжи метод через `bind` либо объяви поле-стрелку `save = value => { ... }`. Выбор зависит от API и требований к стабильности ссылки.
>
> Это не дефект Angular DI: внедрение вернуло правильный объект, но способ вызова потерял получателя. При регистрации DOM listener сохрани одну и ту же привязанную функцию для добавления и удаления; новый `bind` при удалении создаст другую ссылку.

## Как работают сигналы и computed?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Сигнал хранит значение и позволяет отслеживать чтение. computed выводит значение из зависимостей, вычисляется лениво и кэширует результат. Изменение зависимости делает старый результат неактуальным. Интерфейс только для чтения не запрещает глубокое изменение содержащегося объекта.
>
> Список выбранных товаров хранится в signal, итог вычисляется через computed. Изменение отслеживаемого состояния делает производное значение неактуальным до следующего вычисления; сетевой запрос и его ошибки требуют отдельного сценария.
>

> [!followup]- Как Angular computed отслеживает динамические зависимости при условном чтении сигналов?
>
> `computed` зависит только от сигналов, прочитанных при последнем вычислении. Зависимости появляются и исчезают при изменении выбранной ветки; Angular не собирает все имена сигналов из исходного кода.
>
> ```ts
> const showTotal = signal(false);
> const price = signal(100);
> const label = computed(() =>
>   showTotal() ? `Стоимость: ${price()}` : 'Скрыто'
> );
>
> label();            // 'Скрыто': прочитан только showTotal
> price.set(200);      // не инвалидирует текущий label
> showTotal.set(true);
> label();            // 'Стоимость: 200': price стал зависимостью
> price.set(300);
> label();            // 'Стоимость: 300'
> showTotal.set(false);
> label();            // 'Скрыто': зависимость от price удалена
> ```
>
> `computed` ленивый: изменение зависимости делает кэш неактуальным, а вычисление происходит при следующем чтении. Поэтому в проверке нужно действительно прочитать `label()` после переключения ветки, прежде чем судить о новом наборе зависимостей.
>
> Граница механизма — реактивное чтение getter. Глубокая мутация `product().price = 300` сама по себе не сообщает об изменении сигнала; обновляй объект через `set` или `update` с новым значением. Для зависимых вычислений сохраняй чистую функцию, а сетевые запросы и очистку ресурсов организуй отдельно. См. [динамические зависимости Angular Signals](https://angular.dev/guide/signals#computed-signal-dependencies-are-dynamic).

> [!followup]- Когда использовать set и update у Angular signal и как обновлять содержащийся в нём объект?
>
> `set(next)` заменяет значение известным новым, а `update(previous => next)` вычисляет новое из текущего. Для счётчика удобен `count.update(n => n + 1)`, для ответа сервера — `users.set(response)`.
>
> В объектном состоянии возвращай новый объект: `profile.update(p => ({ ...p, name: 'Анна' }))`. По умолчанию равенство определяется через `Object.is`; изменение `profile().name` не вызывает setter, а возврат прежнего мутированного объекта может не уведомить потребителей.
>
> `update` выполняет синхронное преобразование, а не организует очередь сетевых транзакций. Не помещай в него `async` и не рассчитывай на защиту от устаревшего HTTP-ответа: идентичность запроса и проверка актуальности нужны отдельно.

> [!followup]- Когда Angular effect подходит для побочного действия и как освобождать его ресурсы?
>
> `effect` связывает реактивное состояние с императивной внешней системой: например, передаёт текущие данные библиотеке графиков или сохраняет настройку в storage. Обычную сумму товаров выражай через `computed`, чтобы не заводить вторую копию производного состояния.
>
> ```ts
> effect(onCleanup => {
>   const text = query();
>   const id = setTimeout(() => console.log(text), 300);
>   onCleanup(() => clearTimeout(id));
> });
> ```
>
> Чтение `query()` происходит синхронно внутри effect и становится зависимостью. Если перенести его внутрь таймера, оно уже не будет отслеживаться; поэтому callback использует захваченный `text`. Cleanup уберёт прежний таймер перед повторным запуском и при уничтожении effect. Эффект создают в допустимом injection context либо передают injector; время выполнения и DOM-измерения требуют соответствующего API версии проекта.

> [!followup]- Чем сигнал Angular отличается от Observable при чтении состояния и обработке событий?
>
> Сигнал отвечает на вопрос «какое значение сейчас»: его читают синхронным вызовом. Observable описывает последовательность уведомлений во времени, включая ошибку и завершение; подписка может запускать работу. Поэтому текущий выбранный пользователь удобен как signal, а ввод с debounce и отменой предыдущего HTTP-запроса — как поток.
>
> Преобразование `toSignal(stream$, { initialValue: ... })` подписывается на поток и предоставляет последнее значение. Не создавай такое преобразование многократно в getter: появятся дополнительные подписки. `toObservable(signal)` передаёт изменения состояния в поток, но не является журналом каждого промежуточного `set`.
>
> Для команд «сохранить два раза» с одинаковыми данными нужен поток событий или явный метод: одинаковое состояние сигнала не обязано породить новое уведомление.

## Как работают проверка изменений и OnPush?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверка изменений сравнивает привязанные значения и обновляет представление. OnPush позволяет пропускать неподходящие поддеревья, но не запрещает обновления: их могут вызвать новые входные свойства, события, сигналы или явная отметка. Уточняю версию Angular и использование Zone.js.
>
> OnPush-компонент с входным объектом нельзя считать обновлённым после скрытой мутации этого объекта родителем. Проверяют реальные триггеры — новые входные значения, события и реактивные уведомления; OnPush не означает «отрисовать только один раз».
>

> [!followup]- Как AsyncPipe обновляет Angular-компонент с OnPush и управляет подпиской?
>
> `AsyncPipe` подписывается на Observable или принимает Promise, возвращает последнее полученное значение и отмечает компонент для проверки при обновлении. Поэтому шаблон OnPush-компонента может обновляться при эмиссиях одного и того же объекта Observable: новая ссылка на входной stream не обязательна.
>
> Например, `{{ userName$ | async }}` показывает новые имена из потока. При уничтожении представления pipe освобождает подписку; при замене ссылки на источник переключается на новый. До первого значения результат может быть `null`, что следует учесть в шаблоне.
>
> Не вызывай в шаблоне функцию, каждый раз создающую новый cold HTTP Observable: pipe будет переключать подписку, провоцируя запросы. Сохрани источник в поле и отдельно обработай его ошибку; pipe не заменяет UI-состояния загрузки и отказа.

> [!followup]- Чем markForCheck отличается от немедленной проверки Angular-представления?
>
> `markForCheck()` помечает представление как нуждающееся в проверке. Это способ сообщить Angular об изменении, которое само не создало подходящего уведомления для OnPush-компонента. Метод не означает «прямо сейчас синхронно перерисовать DOM».
>
> Если сторонняя библиотека вызвала callback и тот изменил обычное поле компонента, после присваивания можно вызвать `cdr.markForCheck()`. Для состояния, уже читаемого как signal, обычно достаточно изменения сигнала. `detectChanges()` проверяет представление и потомков непосредственно и нужен для других, более специальных сценариев.
>
> У отсоединённого через `detach()` представления одна отметка не возвращает участие в обычных проверках: требуется `reattach()` либо явно организованная локальная проверка. В тесте проверяют видимый текст после предусмотренного цикла, а не сам вызов метода.

> [!followup]- Почему мутация входного объекта может не обновить OnPush-компонент Angular?
>
> Если родитель меняет `user.name`, сохраняя прежнюю ссылку `user`, Angular не получает нового значения этого входа. Поддерево OnPush может быть пропущено, и экран останется прежним. Предпочтительное обновление — `user = { ...user, name: 'Анна' }`.
>
> Это не обещание, что мутация никогда не станет видна. Событие внутри поддерева или другой триггер проверки может случайно показать изменённое поле. Именно поэтому ошибка часто выглядит нестабильно: после постороннего клика имя внезапно обновляется.
>
> Проверяй внешний сценарий: родитель обновляет данные без клика в дочернем компоненте. Согласованный контракт неизменяемых входов делает такое поведение предсказуемым; `readonly` TypeScript помогает разработчику, но сам по себе не замораживает вложенные объекты во время выполнения.

> [!followup]- Что означает ExpressionChangedAfterItHasBeenCheckedError в Angular и где искать причину?
>
> Ошибка означает, что во время дополнительной проверки в режиме разработки Angular обнаружил изменение уже проверенного выражения. Она выявляет нестабильный порядок обновлений, а не требование отключить dev-проверки.
>
> Например, шаблон прочитал `loading = true`, а `ngAfterViewInit` синхронно изменил его на `false`. Другой пример — getter шаблона, возвращающий разные результаты при одинаковом состоянии. Начни со стека ошибки и старого/нового значения, затем найди запись между двумя чтениями.
>
> Если значение известно заранее, вычисли его при инициализации до проверки представления; производные значения делай чистыми. Для действий, действительно требующих готового DOM, используй соответствующий render hook. Отсутствие этой ошибки в production не доказывает правильность потока данных: экран всё ещё может отображать несогласованное состояние.

> [!followup]- Почему setTimeout не является универсальным исправлением ошибок проверки изменений Angular?
>
> `setTimeout` переносит запись в другую задачу и может скрыть `ExpressionChangedAfterItHasBeenCheckedError`, но не объясняет, почему данные менялись после проверки. Он добавляет задержку, промежуточное состояние и ресурс, который нужно очищать при уничтожении компонента.
>
> Если итог зависит от входов, вычисляй его из входов; если начальное значение известно до отображения — устанавливай при корректной инициализации. Если задача действительно должна ждать DOM, выбери render hook, а не произвольные миллисекунды. Внешнее изменение обычного поля может требовать уведомления через `markForCheck`, а не таймера.
>
> Например, исправление `setTimeout(() => valid = check())` лучше заменить явной валидацией при изменении данных. Таймер оправдан для настоящей временной семантики — debounce или задержанного уведомления — с проверкой отмены.

## Чем формы на основе шаблона отличаются от реактивных форм?

> [!answer]- Короткий ответ — 30–90 секунд
>
> В первом случае форму описывают в шаблоне; во втором явно создают модель полей и групп в коде. Для сложных зависимостей явная модель облегчает проверку и обработку правил. При асинхронной проверке нужны состояния ожидания, ошибки и отмены.
>
> В форме с условными полями и взаимной проверкой паролей явная модель FormGroup помогает управлять значениями и валидаторами. Для небольшой формы шаблонный подход может быть достаточным; серверная проверка нужна в обоих случаях.
>

> [!followup]- Где проверять связанные поля Angular-формы, например совпадение паролей?
>
> Правило, зависящее от двух полей, размещают на их общем `FormGroup`. Валидатор читает оба значения и возвращает объект ошибки либо `null`; он не должен менять поля или запускать побочные действия.
>
> ```ts
> const samePassword: ValidatorFn = group => {
>   const a = group.get('password')?.value;
>   const b = group.get('confirmation')?.value;
>   return a === b ? null : { passwordMismatch: true };
> };
> ```
>
> Обязательность каждого поля проверяют отдельно: два пустых значения равны, но ещё не составляют допустимый пароль. Сообщение о несовпадении показывают рядом с подтверждением по `form.hasError('passwordMismatch')`, учитывая touched/попытку отправки. В шаблонной форме аналогичное правило оформляют директивой-валидатором общей группы. Сервер повторяет значимые проверки независимо от клиента.

> [!followup]- Как задать обязательные страну, улицу и дом в Angular-форме адреса?
>
> Представь адрес отдельной группой с тремя контролами и валидаторами каждого поля. Ошибка должна относиться к конкретному пропуску: «Укажите страну», «Введите улицу», «Введите дом», а не только к форме целиком.
>
> `Validators.required` проверяет отсутствие значения, но строка из пробелов требует отдельного правила или согласованной нормализации. Не превращай дом в число: значения вроде `12А` и `5/2` могут быть допустимы по контракту адреса.
>
> При отправке пометь поля touched и переведи фокус к первой ошибке. Если выбор улицы ещё загружается, покажи это состояние отдельно. Отключённые контролы исключаются из обычного значения и валидации группы: нельзя считать отключённое обязательное поле успешно заполненным только потому, что `form.valid` истинно.

> [!followup]- Как сбрасывать зависимые поля Angular-формы при смене страны и не принять старый ответ?
>
> При смене страны прежняя улица и дом могут стать недействительными: их нужно сбросить вместе со списком вариантов, затем загрузить улицы новой страны. Пока список не готов, поле улицы отключают и объясняют причину.
>
> Подписку на `country.valueChanges` можно построить через `distinctUntilChanged` и `switchMap`. Внутри переключения сбрасывают зависимые контролы; поздний ответ прежней страны не должен заполнить новый список. Если сбросы подписаны друг на друга, явно выбери, где нужен `emitEvent: false`, чтобы избежать цикла, не потеряв полезные уведомления.
>
> Отдельно продумай начальную загрузку существующего адреса: она не должна стирать сохранённую улицу как пользовательская смена страны. Проверка: быстро выбрать A, затем B, завершить ответ A последним и убедиться, что доступны только улицы B.

> [!followup]- Как ControlValueAccessor связывает пользовательский компонент ввода с Angular Forms?
>
> `ControlValueAccessor` — адаптер между контролом формы и вашим UI. `writeValue` принимает значение от формы, `registerOnChange` сохраняет callback для пользовательского изменения, `registerOnTouched` — callback для потери взаимодействия, `setDisabledState` отражает отключение.
>
> У составного поля даты выбор дня вызывает сохранённый `onChange(date)`, уход фокуса из всего поля — `onTouched()`. Вызов `writeValue` обновляет отображение, но не должен вызывать `onChange`: иначе программная запись ошибочно возвращается в форму как новый ввод и может зациклиться.
>
> Адаптер регистрируют через `NG_VALUE_ACCESSOR` как multi-provider. Проверяют оба направления, reset, disabled и touched; валидаторы и доступная подпись остаются отдельной ответственностью. CVA не делает произвольный компонент полноценным полем без реализации клавиатуры и фокуса.

## Чем ng-content, ng-container и ng-template отличаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> ng-content размещает переданное содержимое. ng-container группирует части шаблона без отдельного элемента DOM. ng-template определяет фрагмент, который можно создать позже. Доступность дочерних элементов зависит от того, когда и где создано представление.
>
> Общая карточка принимает содержимое через ng-content. ng-container позволяет группировать условную часть без дополнительного div, а ng-template описывает фрагмент, который появится только при предусмотренном создании представления.
>

> [!followup]- Как ng-content проецирует содержимое в Angular-компонент и чем это отличается от его собственного шаблона?
>
> `ng-content` отмечает место, куда Angular помещает содержимое, переданное между тегами компонента. Карточка может иметь собственную рамку и два слота: `<ng-content select="[card-title]" />` для заголовка и обычный `<ng-content />` для остального.
>
> Выражения переданного содержимого принадлежат контексту родителя, который его написал. Переменные внутреннего шаблона карточки автоматически там не появляются. Это позволяет оболочке управлять расположением, не присваивая себе данные пользователя карточки.
>
> `ng-content` — специальный механизм компилятора, а не обычный DOM-элемент. Его условное скрытие не является надёжным способом лениво создавать переданное содержимое. Если карточка должна управлять моментом создания или передавать контекст, передай `TemplateRef` и создавай представление через `NgTemplateOutlet`.

> [!followup]- Чем ViewChild отличается от ContentChild в Angular и когда результат запроса доступен?
>
> `ViewChild` ищет в собственном представлении компонента, а `ContentChild` — в содержимом, которое ему передал родитель. У карточки внутренний элемент закрытия относится к view, проецируемая панель действий — к content. Запросы не предназначены для произвольного проникновения во внутренние шаблоны других компонентов.
>
> Для декораторных динамических запросов результат view доступен в `ngAfterViewInit`, content — в `ngAfterContentInit`. Если элемент условный, он может отсутствовать и позже исчезнуть; код обязан учитывать `undefined`. Современные signal queries позволяют читать результат реактивно.
>
> `static: true` выбирают лишь для действительно постоянно присутствующего узла, который нужен раньше: такой запрос не обновляется при последующих изменениях view. Проверка только первоначального появления не покрывает закрытие и повторное открытие условной панели.

> [!followup]- Как NgTemplateOutlet создаёт представление из ng-template и передаёт ему контекст?
>
> `ng-template` хранит описание фрагмента, а `NgTemplateOutlet` создаёт из `TemplateRef` встроенное представление. Контекст задаёт данные, которые фрагмент читает через `let-`.
>
> ```html
> <ng-template #row let-item let-pos="index">
>   <span>{{ pos + 1 }}. {{ item.name }}</span>
> </ng-template>
> <ng-container
>   [ngTemplateOutlet]="row"
>   [ngTemplateOutletContext]="{ $implicit: user, index: 0 }" />
> ```
>
> `let-item` получает `$implicit`, а `let-pos="index"` — именованное поле. Это удобно для таблицы, позволяющей родителю определить отображение ячейки, пока сама таблица управляет строками.
>
> В standalone-компонент импортируют `NgTemplateOutlet`. Сам по себе `ng-template` не появляется в DOM как видимое содержимое; его нужно инстанцировать. Контекст данных не заменяет DI и не отменяет правила владения состоянием.

> [!followup]- Что перечисляют в imports автономного Angular-компонента и почему provider этого не заменяет?
>
> В `imports` перечисляют компоненты, директивы и pipes, используемые шаблоном, либо NgModule, который экспортирует нужные декларации. Например, для реактивной формы подключают `ReactiveFormsModule`, для собственного `<app-avatar>` — его standalone-компонент.
>
> Импорт TypeScript в начале файла только делает символ доступным коду; он не всегда делает декларацию доступной шаблону. И наоборот, `providers: [SomeService]` настраивает DI, а не разрешает использовать HTML-селектор сервиса.
>
> Если `app-avatar` распознаётся в одном компоненте, но не в соседнем, проверь их собственные области импортов: standalone-зависимости не наследуются просто по расположению файлов. Не-standalone компонент подключают через экспортирующий его NgModule, а не добавляют в standalone imports напрямую.

> [!followup]- Что проверить при ошибке неизвестного Angular-элемента перед добавлением CUSTOM_ELEMENTS_SCHEMA?
>
> Сначала проверь написание selector, импорт нужного компонента в standalone `imports` либо его declaration/export/import в NgModule. Затем убедись, что ошибка относится именно к Angular-компоненту, а не к настоящему Web Component.
>
> Если написано `<app-profile>`, но `ProfileComponent` не подключён к текущему шаблону, схема только подавит диагностику: Angular не создаст отсутствующий компонент и его поведение не появится. Для подключённого Custom Element с дефисом в имени `CUSTOM_ELEMENTS_SCHEMA` может быть уместна, вместе с фактической регистрацией элемента.
>
> `NO_ERRORS_SCHEMA` ещё шире отключает полезные проверки и скрывает опечатки свойств. После исправления проверь действие компонента и его inputs, а не только исчезновение ошибки компиляции.
