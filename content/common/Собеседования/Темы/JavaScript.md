## Какие типы есть в JavaScript и как отличить примитив от объекта?

> [!answer]- Короткий ответ — 30–90 секунд
>
> В JavaScript семь примитивных типов: undefined, null, boolean, number, bigint, string и symbol. Массивы, обычные объекты и функции относятся к объектам. Примитивное значение неизменяемо: метод строки возвращает новое значение, а присваивание меняет то, какое значение хранится в переменной.
>
> Объект можно изменить через его свойства. При `const a = {count: 1}; let b = a; b.count = 2` обе переменные указывают на один объект, поэтому `a.count` равно 2. Если затем присвоить b другой объект, a останется связан с первым: передаётся значение ссылки, а не сама переменная вызывающего кода.
>
> typeof полезен, но имеет особенности: для null возвращает "object", для функции — "function", для NaN — "number". Массив проверяют Array.isArray, NaN — Number.isNaN. Для данных API мало узнать тип контейнера: нужно проверить обязательные поля и их значения.

**Практика:** [[Собеседования/Практика/JavaScript#Мутация объекта и замена параметра|Самостоятельная задача]]

> [!followup]- Почему typeof null не позволяет распознать обычный объект?
>
> typeof null возвращает строку "object" из-за исторического поведения языка. Это не делает null объектом: у него нет свойств, и обращение к ним выбросит TypeError. Первичная проверка объекта — value !== null && typeof value === 'object'.
>
> Но она пропустит массивы, Date и другие объекты. Если нужен массив, используют Array.isArray; если объект конкретного формата — проверяют его поля и их типы. На собеседовании стоит уточнить, что означает «обычный объект»: проверка категории значения и проверка структуры входных данных решают разные задачи.

> [!followup]- Что произойдёт после присваивания объекта второй переменной и изменения его свойства?
>
> Обе переменные будут хранить ссылку на один объект. Изменение свойства через любую из них видно через другую. Присваивание второй переменной нового объекта меняет только эту переменную и не перенаправляет первую.
>
> ~~~js
> const first = { count: 1 };
> let second = first;
> second.count = 2;
> console.log(first.count); // 2
> second = { count: 3 };
> console.log(first.count); // 2
> ~~~
>
> const запрещает переназначить переменную, но не делает объект неизменяемым. Это различие помогает объяснить и передачу аргументов: функция получает копию значения ссылки, поэтому может мутировать общий объект, но не присвоить новое значение переменной вызывающего кода.

> [!followup]- Почему typeof NaN равен number и чем проверить NaN?
>
> NaN — специальное значение числового типа Number, обозначающее неопределённый числовой результат, например 0 / 0. Поэтому typeof возвращает "number". Сравнение value === NaN не подходит: NaN не равен самому себе при ===.
>
> Для проверки без преобразований используют Number.isNaN(value). Оно вернёт true для NaN и false для строки 'abc'. Глобальная isNaN сначала преобразует аргумент в число и для 'abc' вернёт true, что легко перепутать с проверкой типа. Если нужен конечный числовой ввод, отдельно преобразуют строку и применяют Number.isFinite, учитывая пустой ввод: Number('') равен 0.

## Как передаются аргументы и чем мутация отличается от присваивания?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Аргументы передаются по значению. Для объекта копируется значение ссылки: изменение свойства видно вызывающему, замена параметра другим объектом — нет. const запрещает переприсваивание переменной, но не изменение объекта.
>
> Если функция редактирования получает объект пользователя и меняет `user.name`, изменится и объект вызывающего кода. Чтобы форма позволяла отменить изменения, создают отдельный черновик; вложенные объекты тоже нужно отделить, если форма их редактирует.
>

> [!followup]- Почему spread не создаёт независимую копию вложенного объекта?
>
> В объектном spread копируются значения собственных перечисляемых свойств. Если значение — ссылка на объект, копируется ссылка, а не весь вложенный объект. Поэтому {...source} создаёт новый верхний уровень, но source.user и copy.user могут указывать на одного пользователя.
>
> Для независимого изменения вложенного поля копируют каждый изменяемый уровень: const copy = {...source, user: {...source.user, name: 'Анна'}}. Нетронутые ветви можно разделять. Если нужна самостоятельная копия всего графа поддерживаемых данных, рассматривают structuredClone; функции и DOM-узлы им не копируются. Сначала определяют требуемую независимость, а не выбирают глубокое копирование автоматически.

> [!followup]- Почему Object.freeze не защищает вложенные объекты от изменения?
>
> Object.freeze действует на собственные свойства переданного объекта: запрещает добавление и удаление, делает свойства данных незаписываемыми. Он не проходит рекурсивно по значениям этих свойств. Замороженный объект может содержать изменяемый user, поэтому state.user.name всё ещё можно поменять.
>
> ~~~js
> 'use strict';
> const state = Object.freeze({ user: { name: 'Анна' } });
> state.user.name = 'Ольга';
> console.log(state.user.name); // Ольга
> try { state.user = {}; } catch (error) {
>   console.log(error.name); // TypeError
> }
> ~~~
>
> Рекурсивное замораживание требует обработки циклов и типов: например, freeze экземпляра Map не запрещает map.set. Для состояния приложения часто проще контролировать обновления и использовать неизменяемые операции.

## Чем == отличается от === и Object.is?

> [!answer]- Короткий ответ — 30–90 секунд
>
> == допускает преобразования типов, === сравнивает без них. Object.is считает NaN равным NaN и различает +0 и -0. Сравнение объектов этими операторами проверяет идентичность ссылок.
>
> В выборе строки таблицы два объекта `{ id: 42 }` не равны по ссылке. Если важна одна и та же запись после повторной загрузки, сравнивают устойчивый `id`, а не сами объекты. `===` обычно выбирают для предсказуемого сравнения без преобразований.
>

**Уточнения**

- Почему [] == false возвращает true, хотя пустой массив truthy?
- Почему null == undefined, но null !== undefined?
- Как SameValueZero влияет на ключи Map и уникальность Set?

> [!followup]- Почему [] == false возвращает true, хотя пустой массив truthy?
>
> При == действуют правила сравнения с преобразованием типов, а условие if использует преобразование в boolean. Это разные операции. При [] == false значение false становится 0; пустой массив преобразуется в примитив '', затем в число 0. В итоге сравниваются два нуля.
>
> ~~~js
> console.log([] == false); // true
> console.log(Boolean([])); // true
> console.log([] === false); // false
> ~~~
>
> Любой обычный объект, в том числе пустой массив, truthy. Для проверки отсутствия элементов используют array.length === 0. В прикладном коде явное сравнение и === обычно понятнее, чем использование цепочки неявных преобразований.

> [!followup]- Почему null == undefined, но null !== undefined?
>
> В правилах нестрогого равенства null и undefined считаются равными друг другу. === не выполняет такое сближение: это разные типы и разные значения. При этом null == 0 возвращает false: нельзя объяснять все сравнения == предварительным преобразованием обоих операндов в число.
>
> Проверка value == null иногда осознанно используется как сокращение value === null || value === undefined. Она не отбрасывает 0, false или пустую строку. Такой стиль стоит согласовать в проекте; для значения по умолчанию при null или undefined обычно подходит оператор ??.

> [!followup]- Как SameValueZero влияет на ключи Map и уникальность Set?
>
> Map сравнивает ключи, а Set — элементы по SameValueZero. Для примитивов это похоже на ===, но NaN совпадает с NaN; +0 и -0 также считаются одним значением. Поэтому new Set([NaN, NaN, 0, -0]).size равен 2.
>
> Объекты сравниваются по идентичности, а не по набору полей. Два отдельных объекта {id: 1} дадут два элемента Set. Object.is тоже считает NaN равным себе, но различает +0 и -0. Если нужна уникальность сущностей по id, надо явно использовать id как ключ Map, а не ожидать структурного сравнения.

### Чем поверхностное равенство отличается от глубокого?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Поверхностное сравнение проверяет только непосредственные поля: вложенные объекты должны быть теми же объектами по ссылке. Глубокое сравнение заходит внутрь них и проверяет содержимое. Для него нужно заранее решить, что считать равным у Date, Set и объектов с циклическими ссылками.
>
>
> Например, {user:{id:1}} и ещё один такой объект имеют одинаковые листья, но разные ссылки user. Поверхностное сравнение полей вернёт false, глубокое по выбранным правилам может вернуть true. Для Date нужно сравнивать время, для Set решить, важен ли порядок, для циклов хранить уже посещённые пары. Без этого «рекурсивно сравнить всё» может зациклиться или дать неверный ответ.
### Почему два объекта с одинаковыми полями не равны через ===?

**ID вопроса:** Что такое сравнение ссылок в UI?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Две переменные равны по ссылке, если указывают на один объект. Новый объект с теми же полями имеет другую ссылку; мутация сохраняет ссылку. UI-библиотека может опираться на это для мемоизации, поэтому выбираю обновление по её контракту.
>
>
> const a = {x:1}; const b = a; const c = {x:1}: a===b даёт true, a===c — false. После b.x=2 значение a.x тоже 2, но a===b остаётся true. Значит, сравнение ссылок отвечает на вопрос идентичности, а не неизменности содержимого.
## Как работают преобразования типов и логические условия?

> [!answer]- Короткий ответ — 30–90 секунд
>
> В условии значение преобразуется в логическое. Пустые массивы и объекты считаются истинными. Преобразование в число или строку зависит от операции: + может объединять строки; другие арифметические операторы обычно преобразуют операнды в числа. Формат и конечность числового значения нужно проверять явно.
>
> Для количества товара `count || 1` ошибочно заменит допустимый ноль единицей; `count ?? 1` заменит только отсутствующее значение. Данные поля ввода остаются строками: перед расчётом проверяют формат и преобразуют значение явно.
>

**Уточнения**

- Когда значение по умолчанию нужно задавать через ??, а не ||?
- Почему optional chaining не заменяет проверку типа значения?

> [!followup]- Какие значения falsy и почему пустые массив и объект не входят в этот список?
>
> false, 0, -0, 0n, пустая строка, null, undefined и NaN дают false при приведении к boolean. Остальные обычные значения truthy: в частности, строки '0' и 'false', пустой массив и пустой объект. В браузере есть историческое исключение document.all, на котором не следует строить прикладную логику.
>
> Поэтому if (items) не проверяет, есть ли элементы в массиве, а if (amount) отвергает допустимый ноль. Проверку выбирают по смыслу: items.length > 0, amount !== undefined или явная проверка диапазона. Условие должно выражать бизнес-правило, а не случайно совпадать с truthiness.

> [!followup]- Когда значение по умолчанию нужно задавать через ??, а не ||?
>
> Оператор || возвращает правый операнд для любого falsy значения слева. Оператор ?? — только для null и undefined. Если громкость 0 означает тишину, volume || 50 неожиданно включит звук, а volume ?? 50 сохранит 0. Так же различаются false и пустая строка.
>
> Сначала определяют, какие значения допустимы в предметной области. ?? не проверяет корректность: NaN, отрицательная громкость и строка сохранятся. Их проверяют отдельно. Оба оператора вычисляют правую часть только при необходимости, поэтому дорогую функцию получения значения по умолчанию не нужно вызывать заранее.

> [!followup]- Почему optional chaining не заменяет проверку типа значения?
>
> Оператор ?. останавливает цепочку только на null или undefined. Он не проверяет, что значение имеет ожидаемый тип. Например, ({save: 1}).save?.() выбросит TypeError: save существует, но не является функцией. А user?.name может вернуть число, если такое поле пришло с сервера.
>
> Для внешних данных нужна проверка схемы или явные проверки typeof и структуры. Optional chaining полезен для действительно необязательных частей уже понятного контракта. Он также не спасёт от ReferenceError для совсем необъявленного имени и не подавляет исключение, которое выбросил вызванный метод.

### Чем valueOf отличается от toString?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Оба метода помогают получить из объекта примитив, например число или строку. При преобразовании к числу обычно первым вызывается valueOf, к строке — toString. Если есть Symbol.toPrimitive, используется он. Date отличается: при преобразовании без предпочтения числа или строки он обычно выбирает строку.
>
>
> Для обычного объекта с valueOf(){return 7} и toString(){return 'seven'} выражение Number(obj) получает 7, String(obj) — 'seven'. При числовой подсказке обычно сначала пробуют valueOf, при строковой — toString; первый примитив завершает преобразование. Если оба возвращают объекты, возникает TypeError. Symbol.toPrimitive, когда задан, имеет приоритет.
### Что такое короткое замыкание логических операторов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> &&, || и ?? могут не вычислить правую часть и возвращают значение операнда, а не обязательно boolean. ?? реагирует только на null/undefined, || — на все falsy.
>
>
> 0 || 10 возвращает 10, а 0 ?? 10 возвращает 0. В false && save() функция не вызывается; в 'ready' || load() тоже. Для проверки полезно поставить счётчик в правой части и предсказать одновременно значение и число вызовов. Не смешиваю ?? с &&/|| без скобок: такой синтаксис запрещён.

> [!followup]- Как короткое замыкание влияет на вызовы функций и побочные эффекты?
>
> В выражении a && b правая часть вычисляется только при truthy значении a; в a || b — только при falsy; в a ?? b — только при null или undefined. Поэтому isReady && send() иногда вызывает send, а иногда нет. Результат выражения — значение одного из операндов, не обязательно boolean.
>
> Когда важно подчеркнуть действие, if (isReady) send() часто читается яснее. При диагностике нужно проверять не только итоговое значение, но и какие функции реально вызвались. Нельзя бездумно переносить вызов в отдельную переменную: это сделает ранее условный побочный эффект безусловным.

> [!followup]- Как приоритет &&, || и ?? влияет на условие?
>
> && имеет более высокий приоритет, чем ||: a || b && c читается как a || (b && c). Однако выполнение всё равно идёт с коротким замыканием, поэтому при truthy a остальная часть не вычисляется. Скобки полезны, если выражение иначе приходится расшифровывать.
>
> Смешивание ?? с && или || без скобок запрещено синтаксически. Нужно явно выбрать смысл: (value ?? fallback) || last либо value ?? (fallback || last). Например, при value = 0 результаты могут различаться: первый вариант перейдёт к last, второй сохранит ноль.

> [!followup]- Где optional chaining прекращает вычисление и как скобки меняют результат?
>
> В непрерывной цепочке user?.profile.name при null или undefined в user дальнейшие обращения пропускаются. Но если user существует, а profile отсутствует, чтение name выбросит ошибку: для необязательного profile нужно user?.profile?.name.
>
> Скобки могут оборвать цепочку: (user?.profile).name попытается прочитать name у undefined даже при отсутствующем user. Побочные эффекты внутри пропущенного обращения тоже не выполняются: в value?.[index++] счётчик не увеличится, если value равен null. Поэтому ?. следует расставлять согласно контракту каждого уровня данных, а не добавлять в случайное место выражения.

> [!followup]- Как не потерять допустимый 0 при проверке условия или выборе значения по умолчанию?
>
> Если 0 — допустимое количество, координата или громкость, условие if (value) и выражение value || fallback не подходят: ноль falsy. Для отсутствующего значения используют value == null либо явные сравнения с null и undefined; для значения по умолчанию — value ?? fallback.
>
> Но «передано» и «валидно» — разные проверки. Для количества можно потребовать Number.isInteger(value) && value >= 0. Строка '0' truthy, но это ещё не число: преобразование и обработка пустого ввода должны быть отдельным шагом. Полезные пограничные примеры — 0, undefined, '', NaN и отрицательное число.

## Что такое область видимости, hoisting и TDZ?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Область видимости определяет, к какой переменной относится имя в данном месте кода. У var область функции, у let и const — блока. Вложенная область может затенить внешнее имя: поиск начинается изнутри и идёт наружу.
>
> Hoisting объясняет, почему имя может быть известно ещё до строки объявления: JavaScript заранее подготавливает переменные в области видимости. var получает undefined, объявленная через function функция обычно сразу готова к вызову. Имена let и const тоже уже известны, но пользоваться ими до инициализации нельзя. Сам текст программы при этом не переставляется.
>
> TDZ (temporal dead zone, «временная мёртвая зона») — период от входа в область этой привязки до её инициализации. Чтение или запись в этот период вызывает ReferenceError, даже через typeof. В `let value = expression` сначала вычисляется expression, затем инициализируется value. Поэтому `let value = value` тоже ошибочно. После `let value;` значение равно undefined. const дополнительно запрещает последующее переприсваивание, но не изменение свойств объекта.

- Чем объявление функции отличается от const fn = function () {} до выполнения строки?

> [!example]- Проверка на примере
>
> Сравни: `let n = 7; { console.log(n); let n = 9; }` и тот же блок без внутреннего let. В первом случае будет ReferenceError: внутренняя привязка затеняет внешнюю уже до своей инициализации. Во втором выведется 7. Время вызова тоже важно: `const read = () => n; let n = 9; read();` допустимо, потому что чтение происходит после инициализации.

**Критерии ответа:** Объясняю границы TDZ, отличаю создание привязки от инициализации и присваивания; предсказываю затенение без запуска кода.

> [!followup]- Почему typeof для необъявленного имени возвращает строку, а для имени в TDZ выбрасывает ошибку?
>
> typeof missingName специально допускает отсутствие объявления и возвращает "undefined". Но если лексическое имя let, const или class уже есть в текущей области видимости, оно затеняет внешние имена с начала этой области. До инициализации привязка находится в temporal dead zone, и доступ к ней запрещён даже через typeof.
>
> Например, внутри блока typeof count перед let count = 1 выбросит ReferenceError. Это не проверка существования глобального count: обращение относится к локальному имени. Исправление — перенести проверку после инициализации или устранить ошибочное затенение, а не ловить исключение как штатный способ доступа.

> [!followup]- Чем объявление функции отличается от const fn = function () {} до выполнения строки?
>
> Обычное function declaration в своей области создаёт и инициализирует привязку функции до последовательного выполнения её операторов. Поэтому вызов перед строкой объявления работает. У const fn = function () {} сначала существует неинициализированная лексическая привязка; до выполнения объявления чтение fn вызывает ReferenceError.
>
> С var fn = function () {} картина другая: до присваивания fn равен undefined, поэтому попытка вызова даёт TypeError. Это различие между наличием привязки и готовностью вызываемого значения. Для функции внутри условного блока отдельно учитывают область видимости и строгий режим; примеры hoisting лучше разбирать в модуле или однозначном блоке.

> [!followup]- Почему let в заголовке for даёт отдельную привязку каждой итерации, а var — общую?
>
> Для let в заголовке for язык создаёт отдельные привязки между итерациями. Замыкание каждой итерации сохраняет доступ к своему i. У var привязка одна в области функции, поэтому все callbacks читают её окончательное значение после цикла.
>
> ~~~js
> const withLet = [], withVar = [];
> for (let i = 0; i < 3; i++) withLet.push(() => i);
> for (var j = 0; j < 3; j++) withVar.push(() => j);
> console.log(withLet.map(fn => fn()).join(',')); // 0,1,2
> console.log(withVar.map(fn => fn()).join(',')); // 3,3,3
> ~~~
>
> Причина не в таймере: пример воспроизводится без асинхронности. Если let объявить снаружи цикла, callbacks тоже будут использовать одну внешнюю привязку.

### Что такое глобальное окружение?

>
> globalThis даёт доступ к глобальному объекту, но глобальные лексические let/const не обязаны быть его свойствами. В браузере и Node окружения различаются, как и script/модуль. Предположение о window делает код непереносимым.
>
>
> В обычном script браузера var score=1 обычно создаёт window.score, а let level=2 создаёт глобальную лексическую привязку без window.level. В ES-модуле верхнеуровневые объявления относятся к модулю. Поэтому проверять пример нужно с тем же режимом script/module; результат в консоли DevTools не всегда заменяет отдельный файл.
## Что такое замыкание и где оно полезно?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Функция сохраняет доступ к переменным из того места, где её создали. Она может пользоваться ими даже после того, как внешняя функция закончила работу. Это и есть замыкание.
>
> Например, обработчик поиска с `debounce` должен помнить таймер между нажатиями клавиш. Таймер хранится во внешней функции, а возвращённый обработчик читает и меняет его. Глобальная переменная для этого не нужна.
>
> Если создать такой обработчик для другого поля, у него будет свой таймер. Функция при этом видит текущее значение переменной, а не её копию на момент создания.

> [!followup]- Почему два вызова фабрики счётчика имеют независимое состояние?
>
> Каждый вызов функции создаёт своё лексическое окружение. Если фабрика объявляет let count = 0 и возвращает () => ++count, возвращённая функция сохраняет доступ к count именно этого вызова. Два вызова фабрики дают две независимые привязки, хотя код функции одинаковый.
>
> Если же count вынесен в область модуля, все созданные функции работают с общим счётчиком. Поэтому при неожиданном разделении состояния сначала проверяют, где объявлена переменная, а не где вызывается callback. Замыкание сохраняет доступ к привязке: оно видит её последующие изменения, а не копирует начальное значение навсегда.

> [!followup]- Почему debounce нужно создать один раз, а не заново на каждый ввод?
>
> Debounce хранит в замыкании таймер предыдущего вызова. Следующий вызов того же wrapper отменяет этот таймер и ставит новый. Если при каждом событии создавать новый debounce, у каждого экземпляра будет собственный таймер: отменять предыдущую работу окажется нечем, и запустятся все отложенные действия.
>
> Wrapper создают один раз на время жизни нужной подписки или компонента. При завершении этого времени снимают обработчик и отменяют ожидающий таймер, если реализация предоставляет cancel. В реактивном интерфейсе отдельно проверяют актуальность прочитанных данных: стабильный wrapper не должен случайно удерживать устаревшее значение, захваченное при создании.

> [!followup]- Как освобождение подписки связано с временем жизни замыкания?
>
> Источник событий хранит ссылку на обработчик, а обработчик может через замыкание удерживать состояние, DOM-элемент или большой массив. Пока источник доступен и подписка активна, этот граф объектов может оставаться достижимым даже после ухода с экрана.
>
> При завершении сценария вызывают unsubscribe или removeEventListener с тем же обработчиком, отменяют таймеры и другую ожидающую работу. Само замыкание не означает утечку: если больше нет достижимых ссылок, сборщик может освободить и функцию, и её окружение. Для проверки сравнивают несколько циклов открытия/закрытия и исследуют retaining paths в heap snapshot, а не только разовый объём памяти.

## От чего зависит this?

> [!answer]- Короткий ответ — 30–90 секунд
>
> У обычной функции this определяется способом вызова. В `user.save()` получатель — user; если сохранить `const save = user.save` и вызвать save отдельно, связь с user потеряна. В строгом режиме такой вызов получает undefined. call/apply сразу вызывают функцию с указанным this, а bind возвращает новую связанную функцию.
>
> Стрелка берёт this из внешнего окружения при создании: собственный this у неё не появляется от вызова через точку, call или bind. У вызова с new есть отдельное правило: this — создаваемый экземпляр. Поэтому решение для callback зависит от контракта: `user.save.bind(user)` фиксирует получателя, а `() => user.save()` вызывает актуальный метод объекта.

> [!followup]- Что изменится, если после создания callback заменить user.save?
>
> Зависит от того, сохранена ли сама функция или отложено чтение свойства. bind запоминает текущую функцию и получателя. Стрелка () => user.save() читает свойство save при каждом вызове, поэтому увидит заменённый метод.
>
> ~~~js
> const user = { save() { return 'old'; } };
> const bound = user.save.bind(user);
> const live = () => user.save();
> user.save = () => 'new';
> console.log(bound()); // old
> console.log(live()); // new
> ~~~
>
> Если переменную user тоже переназначать, стрелка увидит новое значение этой привязки, а bound останется связан с прежним объектом. Выбор зависит от контракта: нужен конкретный обработчик на момент регистрации или актуальный метод на момент события.

> [!followup]- Может ли call изменить this стрелки?
>
> Нет. У стрелки нет собственного this: она использует this внешнего лексического окружения. call, apply и bind не переопределяют его, хотя call/apply передают аргументы, а bind может фиксировать аргументы.
>
> Если обычный метод объекта возвращает стрелку, она сохранит this этого вызова метода. Но стрелка, записанная прямо в литерале объекта, не получает сам объект как this: литерал не создаёт окружение this. В ES-модуле верхнеуровневый this равен undefined. Чтобы получатель зависел от вызова obj.method(), используют обычный метод, а не стрелку.

> [!followup]- Как ведёт себя связанная через bind функция при вызове с new?
>
> Если исходная функция допускает вызов с new, связанная тоже может быть конструктором. При таком вызове заранее связанный this игнорируется: конструктор работает с новым экземпляром. Связанные аргументы при этом сохраняются.
>
> ~~~js
> function User(name) { this.name = name; }
> const receiver = {};
> const BoundUser = User.bind(receiver, 'Анна');
> const instance = new BoundUser();
> console.log(instance.name); // Анна
> console.log(receiver.name); // undefined
> console.log(instance instanceof User); // true
> ~~~
>
> bind не делает стрелку конструктором: new для неё всё равно выбросит TypeError. Для обычного конструктора также действует правило явно возвращённого объекта: он может стать результатом new вместо созданного экземпляра.

### Чем call, apply и bind различаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> call вызывает функцию с аргументами по отдельности, apply — с массивоподобным набором; bind возвращает новую функцию с зафиксированным this и, при необходимости, частью аргументов.
>
>
> Методы отличаются способом передачи аргументов и моментом вызова:
>
> ```js
> function sum(a, b) {
>   return this.base + a + b;
> }
>
> sum.call({ base: 1 }, 2, 3);    // 6
> sum.apply({ base: 1 }, [2, 3]); // 6
>
> const add = sum.bind({ base: 1 }, 2);
> add(3); // 6
> ```
>
> Стрелочная функция берёт `this` из окружения: эти методы не заменят её `this`. Каждый вызов `bind` создаёт новую функцию. Для последующего `removeEventListener` сохраните её ссылку.
## Как работают прототипы, class и new?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда у объекта нет собственного свойства, JavaScript ищет его по цепочке прототипов до null. Метод может храниться в прототипе и быть общим для экземпляров, но this при вызове `item.method()` указывает на item.
>
> При `new Constructor()` создаётся объект, его внутренний прототип связывается с Constructor.prototype, затем конструктор вызывается с новым this. Если обычный конструктор явно возвращает другой объект, результатом new станет он; возвращённый примитив обычно игнорируется.
>
> class использует ту же прототипную модель, но имеет дополнительные правила: вызов без new запрещён, тело выполняется в строгом режиме, доступны закрытые поля. `Constructor.prototype` — обычное свойство функции-конструктора; внутренний прототип экземпляра получают через Object.getPrototypeOf. Это разные связи.

> [!followup]- Что создаёт Object.create(null)?
>
> Объект с внутренним прототипом null. В его цепочке нет Object.prototype, поэтому он не наследует toString, hasOwnProperty и специальный унаследованный setter __proto__. Такой объект иногда используют как словарь строковых ключей без конфликтов с именами методов прототипа.
>
> Проверять собственный ключ можно через Object.hasOwn(dictionary, key), а не dictionary.hasOwnProperty(key). При этом ключи объекта остаются строками или символами; для произвольных ключей удобнее Map. Отсутствие прототипа не заменяет проверку входных данных: небезопасное последующее слияние словаря в другой объект может снова создать проблему.

> [!followup]- Что произойдёт при затенении унаследованного свойства своим?
>
> При чтении JavaScript сначала ищет собственное свойство. Если оно есть, одноимённое свойство прототипа скрыто для обычного обращения, но остаётся в прототипе и доступно другим экземплярам. Удаление собственного свойства снова открывает унаследованное значение.
>
> Обычное присваивание создаёт собственное свойство, если унаследованное свойство данных записываемо и объект расширяем. Есть важные исключения: унаследованный setter будет вызван, а незаписываемое свойство данных не позволит так создать новое. Поэтому при неожиданном результате проверяют Object.hasOwn, дескрипторы и прототип, а не предполагают, что любая запись всегда затеняет значение.

> [!followup]- Почему методы класса не нужно копировать в каждый экземпляр?
>
> Обычный метод, объявленный в теле class, хранится в прототипе класса. Экземпляры находят одну функцию по цепочке прототипов, а при instance.method() она получает конкретный instance как this. Общий код метода не означает общего состояния: поля могут принадлежать каждому экземпляру.
>
> Поле вида handler = () => {} создаёт отдельную функцию для каждого экземпляра и лексически фиксирует this. Это удобно для callback, но отличается по размещению и расходу памяти. Обычный метод при передаче без получателя может потерять this; тогда связывание выбирают осознанно и сохраняют созданный callback, если его позже нужно снять.

### Почему изменение prototype встроенных объектов опасно?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Изменение встроенного прототипа затрагивает все объекты, которые его используют в этом окружении. Например, добавленный метод Array.prototype может совпасть с методом библиотеки или будущего стандарта. Обычно проще написать отдельную функцию. Если нужен polyfill, его поведение должно соответствовать спецификации и поддерживаемой среде.
>
>
> Добавленный Array.prototype.last может позже получить другое стандартное значение или совпасть с методом зависимости. Если свойство перечисляемое, оно ещё и появится в for...in. Object.defineProperty с enumerable:false решает лишь перечисление, но не конфликт имён и контрактов. Отдельная last(array) локализует поведение.
### Как хранить приватные данные объекта?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Можно оставить данные внутри замыкания, объявить поле класса через # или хранить их отдельно в WeakMap. Внешний код получает только разрешённые методы доступа. Важное различие: private в TypeScript обычно проверяет компилятор, а доступ к #field ограничен и во время выполнения.
>
>
> class Counter { #value=0; increment(){return ++this.#value;} } не позволяет внешнему коду читать #value обычным доступом. TypeScript private value ограничивает использование при проверке типов, но после компиляции обычное поле может остаться доступным. WeakMap удобен для дополнительных данных по объекту без изменения его публичной формы; ключ не должен удерживаться другой ненужной сильной ссылкой.
## Что такое дескриптор свойства?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Дескриптор задаёт value/writable либо get/set, а также enumerable/configurable. Это позволяет управлять чтением, записью и перечислением. При создании нового свойства через defineProperty пропущенные writable/enumerable/configurable равны false. При изменении существующего свойства пропущенные атрибуты сохраняются; у обычного поля литерала эти три флага равны true.
>
> Геттер может представлять вычисляемое поле `fullName`, не храня вторую копию имени. Неперечисляемое служебное поле не попадёт в `Object.keys`, но это не защита данных: доступ по имени остаётся возможным.
>

> [!followup]- Какие свойства возвращают Object.keys, for...in и Reflect.ownKeys?
>
> Object.keys возвращает собственные перечисляемые строковые ключи. for...in перебирает перечисляемые строковые ключи как самого объекта, так и его прототипов. Reflect.ownKeys возвращает все собственные ключи, включая неперечисляемые и символы; прототипы не обходит.
>
> Например, символ служебного поля не попадёт в Object.keys, а унаследованный enumerable-метод может попасть в for...in. Если нужен обход только собственных данных через for...in, добавляют Object.hasOwn(obj, key), но чаще проще сразу выбрать Object.keys. Неперечисляемость не скрывает свойство от прямого чтения и не является механизмом защиты секретов.

> [!followup]- Чем getter отличается от обычного поля и что произойдёт при копировании объекта?
>
> Getter — функция получения значения, вызываемая при чтении свойства. Он может вычислять результат из других полей; хранить отдельное значение для этого свойства необязательно. Но чтение потенциально выполняет код, имеет стоимость и может выбросить исключение.
>
> При {...source} собственный перечисляемый getter вызывается, а его результат записывается в копию как обычное свойство данных. Сам accessor не переносится. Если требуется сохранить дескрипторы, используют Object.getOwnPropertyDescriptors и Object.defineProperties либо Object.create с дескрипторами. Это всё ещё не глубокая копия и не универсальное клонирование экземпляра с внутренними или закрытыми полями.

> [!followup]- Чем Object.preventExtensions, Object.seal и Object.freeze ограничивают объект?
>
> preventExtensions запрещает добавлять собственные свойства, но существующие могут оставаться изменяемыми и удаляемыми. seal дополнительно делает свойства неконфигурируемыми: удаление и смена их устройства запрещены, однако записываемые значения ещё можно менять. freeze дополнительно делает свойства данных незаписываемыми.
>
> Все три операции поверхностные. Вложенные объекты могут меняться, а setter замороженного accessor-свойства всё ещё может выполнять код. В строгом режиме многие запрещённые записи выбрасывают TypeError; вне него некоторые молча игнорируются. Поэтому замораживание полезно как ограничение контракта объекта, но не как универсальная защита всего графа данных или внутренних состояний Map и Set.

### Как работает оператор in и проверка наличия свойства?

> [!answer]- Короткий ответ — 30–90 секунд
>
> in ищет свойство по всей цепочке прототипов; Object.hasOwn проверяет собственное. Сравнение с undefined не различает отсутствие и явно установленное undefined.
>
>
> Для const item=Object.create({enabled:true}); item.value=undefined выражение 'enabled' in item истинно, Object.hasOwn(item,'enabled') ложно, а Object.hasOwn(item,'value') истинно. item.value===undefined не различает отсутствующее поле и явно сохранённое undefined. Это важно при применении частичного обновления настроек.
## Когда использовать Map, Set, WeakMap и WeakSet?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Map хранит ключи любых типов, Set — уникальные значения. WeakMap/WeakSet не удерживают объектные ключи от сборки мусора и не перечисляются. Их используют для метаданных объектов. Скорость Map против object зависит от операции и движка.
>
> `Set` удобно хранит идентификаторы выбранных строк без дублей, `Map` — записи по идентификатору. `WeakMap` подходит для метаданных DOM-элемента: запись не должна сама удерживать удалённый элемент. Но её нельзя использовать, если нужен обход всех записей.
>

> [!followup]- Как Map и Set сохраняют порядок вставки при обновлении и повторном добавлении?
>
> Итерация Map и Set идёт в порядке первого добавления оставшихся элементов. Вызов map.set для существующего ключа обновляет значение, но не переносит ключ в конец. Аналогично повторный set.add уже существующего элемента не меняет позицию.
>
> Если сначала удалить ключ или элемент, а затем добавить заново, он окажется в конце. Это можно использовать при управлении порядком кэша, но Map сам по себе не реализует LRU: чтение не обновляет позицию, лимит и вытеснение нужно организовать отдельно. Если нужен порядок по имени или числу, требуется отдельная сортировка представления.

> [!followup]- Почему JSON.stringify не сохраняет содержимое Map и Set и как передать его?
>
> Без специального преобразования JSON.stringify(new Map()) и JSON.stringify(new Set()) дают '{}': их записи не являются обычными собственными перечисляемыми строковыми свойствами. Для Map можно договориться о формате массива пар [...map], для Set — массива [...set], затем восстановить new Map(data) или new Set(data).
>
> Но формат должен описывать типы значений. JSON не сохраняет BigInt напрямую, идентичность объектов и связи между одинаковыми ссылками; ключ-объект после восстановления будет новым объектом. Для локальной передачи поддерживаемых структур подходит structured clone. Для API нужен явный сериализуемый контракт, а не надежда на автоматическое восстановление коллекций.

> [!followup]- Что означает слабая ссылка на ключ WeakMap и почему его нельзя перечислить?
>
> WeakMap не удерживает ключ от сборки мусора только фактом его присутствия в коллекции. Это удобно для метаданных, связанных с объектом: когда объект больше нигде не нужен, запись не должна сохранять его жизнь. WeakMap не даёт size и перебора ключей, чтобы наблюдаемое поведение не зависело от непредсказуемого момента сборки мусора.
>
> Допустимы объекты и незарегистрированные символы; строки, числа и Symbol.for() ключами не подходят. Слабость не отменяет другие сильные ссылки на объект. Поэтому WeakMap не заменяет unsubscribe и явное освобождение ресурсов, а момент удаления записи нельзя использовать как надёжный сигнал завершения работы.
>
> Источник: [MDN — WeakMap](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakMap).

> [!followup]- Почему Set хранит два объекта с одинаковыми полями и как убрать дубли по id?
>
> Set сравнивает объекты по идентичности. Два литерала {id: 1} создают разные объекты, поэтому размер new Set([{id: 1}, {id: 1}]) равен 2. Повторное добавление той же ссылки новый элемент не создаёт.
>
> Если уникальность определяется id, используют Map с id как ключом или отдельный Set идентификаторов. При этом выбирают правило конфликта: первое значение, последнее или объединение. Например, new Map(items.map(item => [item.id, item])) сохраняет последнее значение для каждого id. Сравнение всего объекта через JSON.stringify ненадёжно как универсальная замена: формат, порядок свойств и неподдерживаемые значения требуют отдельного решения.

### Можно ли хранить порядок шагов процесса в ключах объекта?

**ID вопроса:** Почему нельзя полагаться на порядок ключей как бизнес-контракт?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Для порядка шагов лучше использовать массив или отдельное поле позиции. У ключей объекта есть свои правила перечисления: например, ключи, обозначающие целочисленные индексы, идут по возрастанию, даже если добавлялись иначе. При передаче данных другой системе её правила тоже нужно учитывать.
>
>
> Object.keys({'10':'later','2':'first',name:'x'}) перечислит индексные ключи 2,10 перед name, независимо от желаемого порядка шагов. Массив [{id:'10'}, {id:'2'}] хранит порядок явно. Map сохраняет порядок вставки, но при обмене с API всё равно нужен согласованный формат передачи последовательности.
## Как скопировать сложный объект?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Сначала определяю, что должно стать независимым. Spread и Object.assign создают поверхностную копию: вложенные объекты сохраняют общие ссылки. Для изменения одного поля обычно достаточно скопировать путь к нему, сохранив остальные ветви — так проще увидеть, что изменилось.
>
> structuredClone умеет глубоко копировать поддерживаемые значения, включая циклические ссылки, Map и Date, но не является копировщиком произвольного поведения: функции и DOM-узлы не клонируются. Пользовательские прототипы и дескрипторы тоже нельзя считать сохранёнными. JSON stringify/parse подходит только для заранее ограниченной JSON-модели: он теряет некоторые значения и не поддерживает циклы.
>
> Поэтому способ копирования — часть контракта данных. Копировать всё на каждом обновлении может быть дорого и нарушать полезную идентичность неизменившихся объектов.

> [!followup]- Почему изменение copy.user.name может изменить исходный объект после {...source}?
>
> Spread создаёт новый внешний объект, но поле user в нём содержит прежнюю ссылку. Поэтому copy !== source, а copy.user === source.user. Запись copy.user.name меняет общий вложенный объект, доступный и через source.
>
> Чтобы обновить только имя без мутации исходного состояния, копируют путь: const copy = {...source, user: {...source.user, name: 'Анна'}}. Остальные ветви сохраняют свои ссылки, что полезно для сравнения изменений в UI. Проверка исправления должна смотреть не только новое имя, но и сохранность source.user.name, новую ссылку user и прежние ссылки нетронутых ветвей.

> [!followup]- Что потеряется при JSON-копии Date, undefined или функции?
>
> JSON.parse(JSON.stringify(value)) восстанавливает JSON-данные, а не исходные типы JavaScript. Date обычно превращается в ISO-строку; свойства объекта со значениями undefined или функцией пропускаются. В массиве такие элементы становятся null. Прототип пользовательского класса и методы не восстанавливаются.
>
> Кроме потерь есть ошибки: циклическая ссылка и BigInt без специальной обработки приводят к исключению при сериализации. Поэтому JSON-копия допустима только для заранее ограниченного формата. Для поддерживаемого графа данных можно выбрать structuredClone: он сохраняет Date и циклы, но тоже не копирует функции и не является универсальной копией экземпляра класса.

> [!followup]- Как обновить вложенное поле без глубокой копии всего дерева?
>
> Создать новые объекты только вдоль пути к изменяемому полю, а нетронутые ветви переиспользовать. Это структурное разделение: оно сохраняет исходное состояние и делает изменение заметным по ссылкам на нужных уровнях.
>
> ~~~js
> const source = { user: { name: 'Анна' }, settings: { dark: true } };
> const copy = { ...source, user: { ...source.user, name: 'Ольга' } };
> console.log(source.user.name); // Анна
> console.log(copy.user === source.user); // false
> console.log(copy.settings === source.settings); // true
> ~~~
>
> Для массива аналогично создают новый массив и заменяют только изменяемый элемент. Глубокая копия всех ветвей обычно добавляет работу и уничтожает полезную стабильность ссылок. При этом разделяемые ветви после обновления тоже нельзя мутировать.

## Как работают методы массивов map, filter, reduce и sort?

> [!answer]- Короткий ответ — 30–90 секунд
>
> map возвращает новый массив результатов callback; filter — новый массив элементов, для которых условие истинно. Они не делают глубокую копию элементов: изменение свойства объекта внутри callback может затронуть исходные данные. reduce сводит последовательность к одному результату, передавая накопитель между вызовами.
>
> Для суммы `items.reduce((sum, item) => sum + item.price, 0)` начальный 0 задаёт результат и для пустого списка. Без начального значения первый элемент становится накопителем; пустой массив вызывает TypeError. map подходит для преобразования всех элементов, find — для одного первого совпадения, filter — для всех совпадений.
>
> sort меняет сам массив. По умолчанию сравнивает строковые представления, поэтому числа сортируют с `(a, b) => a - b`. Чтобы сохранить исходный порядок, используют копию `[...items].sort(compare)` или toSorted в поддерживаемой среде. Это всё ещё поверхностная копия. Стоимость нескольких проходов и побочные эффекты callback оценивают по объёму данных, а не запрещают цепочки методов заранее.

> [!followup]- Что вернёт reduce на пустом массиве с начальным значением и без него?
>
> С переданным initialValue reduce пустого массива вернёт это значение и не вызовет callback. Без initialValue нет первого элемента, из которого можно взять аккумулятор, поэтому возникнет TypeError. На непустом массиве без начального значения первый существующий элемент становится аккумулятором, а обработка начинается со следующего.
>
> Начальное значение выбирают по операции: 0 для суммы, [] для собираемого списка, объект для индекса. Оно также задаёт ожидаемый тип аккумулятора. Для массива с пропусками reduce пропускает отсутствующие элементы; массив из одних пропусков без initialValue тоже не даёт стартового значения. Пустой набор нужно проверять как отдельный сценарий.

> [!followup]- Почему map может изменить исходные объекты, хотя возвращает новый массив?
>
> map создаёт новый массив результатов, но передаёт callback исходные элементы. Если элемент — объект, callback получает ссылку на этот объект. Присваивание item.done = true мутирует его, даже если callback затем возвращает item в новый массив.
>
> Для неизменяемого обновления можно вернуть {...item, done: true}; вложенные изменяемые поля тоже требуют копирования соответствующего пути. Если callback оставляет объект без изменений, ту же ссылку можно сохранить. Проверяют два разных свойства: новый ли контейнер массива и какие ссылки на элементы изменились.

> [!followup]- Почему [2, 10, 1].sort() не даёт числовой порядок?
>
> Без compareFn sort сравнивает строковые представления элементов, поэтому результат будет [1, 10, 2]. Для обычных конечных чисел передают (a, b) => a - b. Компаратор возвращает отрицательное число, ноль или положительное число; boolean не задаёт корректный симметричный порядок.
>
> sort меняет исходный массив. Если это состояние интерфейса, используют копию [...items].sort(compare) либо поддерживаемый окружением toSorted(compare). Значения NaN и смешанные типы требуют отдельного правила. При диагностике проверяют и сам порядок, и то, не мутировал ли код коллекцию, которую другие части приложения считали неизменной.

### Когда цикл удобнее и быстрее цепочки map и filter?

**ID вопроса:** Почему функциональные методы не всегда оптимальны?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Цепочка map/filter может создавать промежуточные массивы; reduce бывает менее читаемым. Выбор делаю по ясности и измеренной стоимости на реальном объёме. Ручной цикл тоже может содержать ошибки и не быть быстрее.
>
>
> При поиске первого подходящего элемента find или цикл с break не строят полный результат. filter(...).map(...) удобен для преобразования всего набора, но создаёт промежуточный массив. Сравниваю реализацию на характерном объёме и проверяю одинаковые результаты, особенно если callback имеет побочные эффекты: слияние проходов может изменить их порядок.
### Почему async forEach часто ошибочен?

> [!answer]- Короткий ответ — 30–90 секунд
>
> forEach не собирает и не ожидает Promise обработчиков. Для последовательности использую for...of с await; для независимых операций map и Promise.all с ограничением параллелизма при необходимости.
>
>
> await items.forEach(async item => save(item)) ожидает undefined от forEach, а не завершение сохранений. Для последовательности: for (const item of items) await save(item). Для независимого набора: await Promise.all(items.map(save)). Проверка с управляемыми Promise показывает, когда внешний код продолжается и куда приходит ошибка.
## Что такое перебираемый объект, итератор и генератор?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Перебираемый объект предоставляет метод Symbol.iterator, возвращающий итератор с next(). Функция-генератор создаёт итератор и приостанавливает выполнение на yield. for...of читает значения по этому протоколу; for...in перечисляет доступные строковые ключи перечисляемых свойств.
>
> Генератор может отдавать элементы дерева по одному для `for...of`, сохраняя позицию обхода между `yield`. Потребитель останавливается, когда нашёл нужный элемент, без создания массива всех результатов; глубину рекурсии всё равно нужно учитывать.
>

> [!followup]- Что делают методы return() и throw() у генератора?
>
> `return(value)` просит завершить генератор с указанным результатом, а `throw(error)` возобновляет его так, будто ошибка выброшена в точке текущего `yield`. Генератор может поймать эту ошибку внутри и продолжить выдавать значения. Если подходящего `catch` нет, ошибка выйдет к вызывающему.
>
> Например, генератор открывает ресурс внутри `try`, выдаёт строки в цикле и закрывает его в `finally`. `break` из `for...of` вызывает `return()` итератора, и уже начавшийся генератор выполнит `finally`. Если в самом `finally` есть `yield`, первый `return()` может вернуть `done: false`, поэтому для очистки не стоит выдавать значения из `finally`. Вызов `return()` до первого `next()` вообще не запускает тело генератора.

> [!followup]- Что делает yield* при делегировании другому итератору?
>
> `yield* iterable` передаёт наружу значения вложенного итератора, а после его завершения само выражение получает итоговое `value` из результата с `done: true`. Это удобно для обхода дерева: `yield node; for (const child of node.children) yield* walk(child);`.
>
> Например, если подгенератор выдаёт `yield 1` и заканчивает `return 99`, то `const code = yield* child()` выдаст потребителю 1, а 99 запишет в `code`; сам по себе `for...of` 99 не покажет. Делегирование передаёт вызовы `next` и при наличии соответствующих методов — `throw`/`return`. Отдать массив одним значением можно через `yield array`; `yield* array` отдаст его элементы по одному. В рекурсивном обходе делегирование не убирает расход стека.

> [!followup]- Как работают асинхронный итератор и for await...of?
>
> У асинхронного перебираемого объекта `Symbol.asyncIterator` возвращает итератор, чей `next()` даёт Promise результата `{ value, done }`. `for await...of` ожидает очередной шаг, выполняет тело и запрашивает следующий. Так можно получать данные постранично, не загружая все страницы заранее.
>
> Например, `async function* pages()` получает страницу через `await load(cursor)`, выдаёт её и сохраняет новый курсор. Потребитель обрабатывает `for await (const page of pages())`; при `break` он закрывает итератор через `return()`, если метод есть, и ждёт закрытия. Цикл также может принять синхронный iterable, но сам не создаёт параллелизм и не ограничивает буфер у источника, который независимо отправляет данные.

### Чем перечисляемость свойств отличается от перебираемости объекта?

> [!answer]- Короткий ответ — 30–90 секунд
>
> enumerable — флаг перечисляемости свойства, а iterable — поддержка получения значений через Symbol.iterator. Обычный объект может иметь перечисляемые поля и не быть перебираемым; массив поддерживает оба механизма с разной семантикой.
>
>
> for...in по {a:1} перечисляет ключ a, но for...of по тому же объекту бросит TypeError без Symbol.iterator. У массива for...of читает значения, а Object.keys перечисляет собственные enumerable-ключи. Пользовательский iterator может возвращать значения, вообще не совпадающие со свойствами объекта.
### Что такое lazy evaluation?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Вычисление откладывается до потребления. Генератор продолжает работу при вызове `next()` и останавливается на следующем `yield`. Потребитель может взять первые несколько элементов, не вычисляя оставшиеся.
>
>
> В function* values(){yield expensiveA();yield expensiveB()} создание iterator ещё не вызывает expensiveA. Первый next вычисляет только A; B выполнится при следующем продвижении. Если потребитель вызовет [...values()], он всё равно материализует весь результат. При раннем выходе освобождение ресурса размещают в finally генератора и учитывают вызов return.
### Когда нужны асинхронные генераторы?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда данные приходят постепенно и потребитель должен ждать каждое следующее значение: страницы API, сообщения, потоковый разбор. Генератор даёт удобный for await...of, но контракт отмены/ошибок и размер буфера нужно определить.
>
>
> Генератор страниц может дождаться fetchPage(cursor), yield записи и лишь после продолжения потребителем запросить следующую страницу. Так потребитель управляет темпом без загрузки всех страниц заранее. При break из for await...of нужно завершить генератор и очистить ресурсы; отмена уже выполняющегося fetch требует отдельного AbortSignal.
## Как работает цикл событий в браузере?

> [!answer]- Ответ и разбор
>
> Цикл событий помогает браузеру выбирать, какую работу выполнять дальше. Текущий JavaScript-код сначала выполняется до конца: таймер или ответ сервера не могут прервать его посередине.
>
> После текущей задачи браузер выполняет микрозадачи — например, обработчики `.then()` готовых Promise. Если они добавили новые микрозадачи, те тоже должны выполниться. Затем браузер получает возможность обновить экран и перейти к следующей задаче, например обработчику таймера.
>
> ```js
> console.log('Начало');
>
> setTimeout(() => {
>   console.log('Таймер');
> }, 0);
>
> Promise.resolve().then(() => {
>   console.log('Promise');
> });
>
> console.log('Конец');
> ```
>
> Вывод: **Начало → Конец → Promise → Таймер**. Первые две строки выводит текущий код, затем выполняется микрозадача Promise, а потом — таймер.
>
> Нулевая задержка таймера не означает «выполнить прямо сейчас». И экран обновляется не после каждой задачи: браузер выбирает момент для следующего кадра. Поэтому длинный цикл или непрерывная цепочка микрозадач могут мешать вводу и отрисовке.

> [!followup]- Когда выполняется executor new Promise, а когда callback then?
>
> Executor вызывается синхронно внутри new Promise. resolve меняет состояние Promise, но обработчик then запускается как микрозадача после завершения текущего синхронного кода, даже если Promise уже выполнен к моменту подписки.
>
> ~~~js
> console.log('A');
> const ready = new Promise((resolve) => {
>   console.log('B');
>   resolve('D');
> });
> ready.then(console.log);
> console.log('C');
> // A, B, C, D
> ~~~
>
> Тяжёлый цикл в executor всё равно блокирует основной поток. Для проверки порядка достаточно этого примера; для проверки отзывчивости нужна запись в браузере. Promise организует получение результата, но не переносит вычисление на другой поток.

> [!followup]- Почему await Promise.resolve() в тяжёлом цикле может не помочь интерфейсу?
>
> Продолжение после await уже выполненного Promise попадает в микрозадачи. Браузер обрабатывает их до перехода к следующей задаче и возможности обновить отображение. Если продолжение снова выполняет часть тяжёлой работы и ставит микрозадачу, очередь долго не освобождается: формально async-функция приостанавливается, но ввод и кадры всё ещё ждут.
>
> Для разбивки работы нужна граница, позволяющая браузеру обработать другие задачи: например, поддерживаемый scheduler.yield() с fallback через setTimeout. Это не обещание кадра после каждой порции. Размер порции выбирают по времени на целевом устройстве; для независимого большого вычисления рассматривают Worker. Проверка — ввод и кадры во время всего расчёта, а также совпадение результата с исходным алгоритмом. [Разбиение длительных задач](https://web.dev/articles/optimize-long-tasks).

> [!followup]- Почему порядок requestAnimationFrame и таймера нельзя без условий считать универсальным?
>
> setTimeout ставит задачу после минимальной задержки, а requestAnimationFrame вызывает callback в ходе обновления отображения перед перерисовкой. Это разные механизмы планирования. Между ними нет общего правила «rAF всегда раньше timeout» для любого места вызова: важны момент относительно кадра, готовность таймера, занятость потока и видимость вкладки.
>
> Если после изменения DOM поставить оба callback, журнал одного запуска показывает лишь этот запуск. В скрытой вкладке rAF может приостанавливаться, а таймеры ограничиваться. Для анимации используют rAF и его timestamp, для требования «не раньше заданного времени» — таймер с проверкой времени. Тестировать следует нужный контракт, а не выведенный из одного эксперимента универсальный порядок.

### Как связаны очередь микрозадач и рендеринг?

> [!answer]- Короткий ответ — 30–90 секунд
>
> На контрольной точке очередь микрозадач должна опустеть; непрерывное добавление микрозадач может задержать следующую задачу и отрисовку. requestAnimationFrame вызывается при обновлении изображения перед отрисовкой, но не гарантирует фиксированную частоту.
>
>
> Если callback queueMicrotask снова ставит себя в микрозадачи без конца, браузер не достигнет следующей возможности отрисовки. Замена тяжёлого цикла на цепочку Promise не делает ввод отзывчивым. Проверяю это коротким ограниченным примером и профилем, а не запускаю бесконечную очередь на рабочей странице.
### Какие ограничения у setTimeout?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Задержка — минимальное ожидание перед допустимым запуском, а не точный срок. Занятый стек, очереди и ограничения фоновой вкладки задержат обработчик. Для периодической async-работы часто лучше планировать следующий запуск после завершения текущего.
>
>
> setTimeout(log,0) выполняет log после текущего синхронного кода и положенных микрозадач, а не немедленно. Если запрос в setInterval длится дольше интервала, новые запуски могут перекрываться. Рекурсивный setTimeout после await запроса задаёт паузу между завершением и следующим стартом; нужно обработать отказ и остановку владельца.
### Как объяснить JavaScript как однопоточный язык?

> [!answer]- Короткий ответ — 30–90 секунд
>
> В одном JavaScript-агенте код выполняется последовательно: два обработчика не работают одновременно на одном стеке. При этом браузер может ждать сеть параллельно с выполнением JS, а Worker выполняет свой код на отдельном агенте. Асинхронная операция поэтому не обязательно означает второй поток JavaScript.
>
>
> Два fetch могут ожидать сеть одновременно, но их callbacks в одном обычном документе не исполняют JS в один и тот же момент. Web Worker имеет отдельный агент и может считать параллельно; обмен сообщениями или SharedArrayBuffer требует отдельного контракта данных. Поэтому async-функция с тяжёлым циклом всё ещё блокирует поток вызывающего документа.
### Почему задачи браузера нельзя считать одной общей очередью FIFO?

> [!answer]- Короткий ответ — 30–90 секунд
>
> HTML определяет разные источники задач и выбор очередей средой выполнения. Порядок связан с источником и состоянием цикла событий. Для ответа на конкретный пример использую гарантии API, а не универсальный рисунок одной очереди.
>
>
> Таймер и поступившее сообщение относятся к разным источникам; их глобальный порядок не выводится только из того, какой API вызван первым. Для двух задач одного источника и конкретного алгоритма есть свои гарантии. На интервью разделяю гарантированный порядок синхронного кода/микрозадач и порядок событий, который зависит от готовности сети и среды.
## Что гарантируют Promise и async/await?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Promise представляет результат операции, который может появиться позже: он сначала pending, затем переходит в fulfilled или rejected и больше не меняет итог. Вызов then возвращает новый Promise: возвращённое значение становится его результатом, выброшенная ошибка — причиной отклонения; возвращённый Promise определяет дальнейшее ожидание цепочки.
>
> async-функция всегда возвращает Promise. await приостанавливает продолжение этой функции до результата, но не блокирует весь поток. Код до первого await выполняется синхронно. Ошибку ожидаемой операции можно обработать try/catch; просто вызвать async-функцию без await внутри try недостаточно для перехвата её будущего rejection.
>
> Promise не запускает код автоматически в фоне и не предоставляет отмену операции. Параллельность запросов зависит от того, когда их запустили, а не от присутствия слова Promise.

> [!followup]- Что случится, если забыть return перед вложенным Promise в then?
>
> Callback then без return завершается значением undefined. Вложенная асинхронная работа продолжается отдельно: следующий then не ждёт её, а catch внешней цепочки не получает её будущий rejection.
>
> ~~~js
> // Ошибка: сохранение не включено в цепочку.
> loadUser().then(user => { saveUser(user); }).then(showDone);
>
> // Исправление: ждём сохранение и передаём ошибку дальше.
> loadUser().then(user => saveUser(user)).then(showDone).catch(showError);
> ~~~
>
> В тесте saveUser возвращает управляемый Promise: до resolve подтверждение showDone не появляется, после reject вызывается showError. Синхронное исключение внутри callback всё же отклонит внешнюю цепочку даже без return; проблема именно в потерянном результате асинхронной операции. Намеренная фоновая работа возможна, но тогда ей отдельно нужны обработчик ошибки и понятный жизненный цикл. [Цепочки Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Using_promises).

> [!followup]- Когда последовательные await можно безопасно заменить Promise.all?
>
> Когда операции независимы по входам и побочным эффектам, допустимо запустить их одновременно и дождаться всех результатов:
>
> ~~~js
> const [profile, settings] = await Promise.all([
>   loadProfile(userId),
>   loadSettings(userId),
> ]);
> ~~~
>
> Вызовы запускают работу при вычислении аргументов; Promise.all объединяет ожидание. Если второй запрос требует id, полученный из первого, либо должен выполняться только после успешной записи первого, такая замена меняет контракт. Также проверяю ограничения сервера на число одновременных обращений.
>
> Promise.all сохраняет входной порядок результатов и отклоняется при первом наблюдаемом отказе. Остальные операции автоматически не отменяются и не откатываются. Для независимых виджетов с частичным успехом удобнее отдельные состояния или allSettled. Проверка: оба загрузчика вызваны до завершения первого; второй завершается раньше, но результаты сохраняют правильные позиции; при отказе одного не появляется ложное сообщение об успехе всего сценария. [Promise.all](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all).

> [!followup]- Чем catch после then отличается от второго аргумента того же then?
>
> Второй аргумент `then(onValue, onError)` ловит отклонение исходного Promise. Если `onValue` выбросит ошибку или вернёт отклонённый Promise, она отклонит *результат* `then` и не попадёт в соседний `onError`. `promise.then(onValue).catch(onError)` обрабатывает отказ исходной операции и ошибку в `onValue`.
>
> Например, `load().then(parse, showNetworkError)` отправит в `showNetworkError` отклонение `load`, но ошибка `parse` останется в возвращённом Promise. `load().then(parse).catch(showLoadOrParseError)` покрывает оба случая. Если ошибки нужно различать, добавьте контекст на нужном этапе. В обоих вариантах обработчик, который возвращает обычное значение, переводит цепочку в успех; чтобы отказ дошёл дальше, бросьте ошибку или верните отклонённый Promise.

### Что такое thenable?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Thenable — объект с методом then, который Promise и await умеют ожидать как обещанный результат. Это позволяет работать с другими реализациями Promise. Поэтому объект с таким методом не всегда возвращается как обычное значение: await использует его then, чтобы получить результат.
>
>
> await {then(resolve){resolve(42)}} даёт 42, хотя объект не создан через new Promise. Если получение свойства then бросает ошибку, ожидающий Promise отклоняется. Поэтому библиотека, принимающая PromiseLike, должна учитывать поведение thenable, а не проверять только instanceof Promise.
### Почему Promise не делает вычисление неблокирующим?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Исполнитель Promise и код до первого await работают синхронно на текущем потоке. Даже продолжение после await может выполнить длинный CPU-цикл и блокировать UI. Для тяжёлого вычисления нужны фоновый исполнитель, дробление работы либо другой алгоритм.
>
>
> Исполнитель запускается сразу, поэтому цикл блокирует текущий поток:
>
> ```js
> new Promise(resolve => {
>   heavyLoop();
>   resolve();
> });
> ```
>
> Даже если перед `heavyLoop()` поставить `await Promise.resolve()`, цикл выполнится на том же потоке, в микрозадаче. Для переноса вычисления на другой поток нужен, например, Web Worker.
### Что произойдёт, если вызвать resolve или reject несколько раз?

**ID вопроса:** Что означает единственное завершение Promise?

> [!answer]- Короткий ответ — 30–90 секунд
>
> После resolve/reject последующие попытки изменить исход игнорируются; принятие thenable может ждать его исход. Это не запрещает исполнителю продолжить выполнять побочные эффекты после resolve.
>
>
> Первая попытка завершения определяет исход, но выполнение исполнителя продолжается:
>
> ```js
> const result = new Promise((resolve, reject) => {
>   resolve(1);
>   reject(new Error('late')); // исход уже выбран
>   console.log('after');     // выполнится
> });
>
> result.then(console.log); // 1
> ```
>
> `resolve` не прерывает функцию как `return`. Если первым вызовом передать ещё ожидающий Promise, внешний Promise примет его будущий исход; последующий `reject` уже не изменит этот выбор.
### Чем цепочка Promise отличается от вложенных then?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Возврат Promise из then связывает завершение и ошибки в одну цепочку. Вложенный then без return создаёт независимую работу и затрудняет передачу ошибок. Использую линейную цепочку или async/await по ясности.
>
>
> return loadUser().then(user => loadOrders(user.id)) связывает ожидание обоих шагов. Внутри callback вариант { loadOrders(user.id); } без return завершает внешнюю цепочку раньше и не передаёт ей будущую ошибку loadOrders. Тест с задержанным вторым Promise обнаруживает преждевременный успех.
## Чем отличаются Promise.all, allSettled, race и any?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Эти методы нужны, когда мы ждём несколько результатов, например ответы нескольких запросов:
>
> - `Promise.all` — нужны все результаты. Если хотя бы один Promise отклонится, общий Promise тоже отклонится. Результаты идут в порядке переданных Promise, а не скорости их выполнения.
> - `Promise.allSettled` — нужен отчёт по каждому: что выполнилось, а что завершилось ошибкой. Он ждёт всех.
> - `Promise.race` — берём первый результат, включая ошибку.
> - `Promise.any` — берём первый успешный результат. Если все завершились ошибкой, получаем `AggregateError`.
>
> Например, для страницы, которой нужны и профиль, и настройки, подходит `all`. Для отправки нескольких файлов с отдельным результатом каждого — `allSettled`.
>
> Оставшиеся запросы сами не отменяются. У пустого массива тоже разное поведение: `all` и `allSettled` дают пустой массив, `any` — ошибку, а `race` остаётся в ожидании.

> [!followup]- Что произойдёт с остальными fetch после ошибки Promise.all?
>
> Остальные `fetch` продолжат работу: `Promise.all` меняет состояние своего результирующего Promise, но не управляет уже запущенными запросами. Например, A отклоняется из-за сетевого сбоя, `all` сразу отклоняется, а B всё ещё может получить ответ или завершить серверную запись.
>
> Если результаты больше не нужны, передайте всем запросам общий `AbortSignal` и вызовите `controller.abort()` при отказе группы. Сервер при этом мог уже выполнить побочный эффект; отмена клиента не делает запись транзакционной. Также `fetch` сам по себе не отклоняется при HTTP 404 или 500: чтобы такой статус привёл к отказу `Promise.all`, проверьте `response.ok` и отклоните запрос по договорённости.

> [!followup]- Как отличается timeout через race от отмены fetch?
>
> `Promise.race` с таймером завершает ожидание первым результатом, но `fetch` остаётся запущенным. Например, UI через секунду показывает таймаут, а запрос всё ещё читает ответ. Чтобы отменить запрос и чтение тела, передайте сигнал в `fetch` и отмените его через `AbortController` или `AbortSignal.timeout(ms)` в поддерживаемой среде.
>
> При ручном таймере очищайте его после завершения операции и учитывайте весь нужный этап: `await fetch(...)` возвращает ответ после получения заголовков, а `await response.json()` читает тело позже. Для POST отмена ожидания не доказывает, что операция не произошла: перед повтором нужны идемпотентный контракт или запрос состояния.

> [!followup]- Как обрабатывается пустой массив в каждом методе?
>
> `Promise.all([])` и `Promise.allSettled([])` дают исполненный Promise со значением `[]`. `Promise.any([])` даёт отклонённый Promise с `AggregateError` и пустым `errors`: успешного исхода нет. `Promise.race([])` остаётся pending, потому что нет участника, который мог бы завершиться первым.
>
> Например, пустой пакет заданий для `all` завершится успешно и не запустит ни одного действия, а ожидание `await Promise.race(tasks)` при пустом `tasks` не продолжится. Проверьте пустой список до вызова `race`, если операция должна закончиться. Даже для уже исполненного или отклонённого результата обработчик `then`/`catch` запускается асинхронно.

### Как проверить корректность собственной реализации Promise.all?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверяю, что результаты сохраняют входной порядок, обычные значения и thenable обрабатываются, пустой вход завершается, а отказ одного элемента отклоняет общий Promise. Остальные операции при этом продолжаются. Если функция должна заменять Promise.all, нужны также поддержка iterable и обработка ошибок при получении элементов.
>
>
> Создаю A и B с управляемым завершением, передаю [A,7,B], завершаю B первым и A вторым: ожидаю [a,7,b]. Отдельно проверяю пустой iterable, thenable, исключение iterator и отказ одного элемента. После отказа наблюдаю, что прочие операции сами не отменились. Если функция принимает только массивы, указываю это в её API.
### В каком порядке Promise.all возвращает результаты запросов?

**ID вопроса:** Почему порядок результатов не равен порядку завершения?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Promise.all возвращает результаты в том порядке, в котором ему передали операции. Если вместо этого добавлять каждый готовый результат через push, порядок будет зависеть от скорости выполнения. Выбирать нужно по задаче: соответствие исходному списку или выдача по мере готовности.
>
>
> Если slow относится к первому URL, а fast ко второму, await Promise.all([slow,fast]) всё равно возвращает [slowResult,fastResult]. При ручной реализации сохраняю результат по исходному индексу. Порядок запуска, завершения и порядок выдачи — три разных свойства, их проверяют отдельно.
## Как отменять запросы и предотвращать гонки?

**Практика React:** [[Собеседования/Практика/React#Поиск: от списка до гонок запросов|Проверить на задаче]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Передаю AbortSignal поддерживающему API, отменяю старую операцию и проверяю актуальность результата. Отмена не означает откат уже выполненного действия на сервере. Для записи нужны серверная идемпотентность и согласованный статус.
>
> Поиск по строке «vue» может завершиться раньше предыдущего поиска «v». При смене строки отменяют старый запрос и перед записью проверяют номер текущей операции. Такая проверка защищает интерфейс и тогда, когда внешняя операция фактически не поддерживает отмену.
>

> [!example]- Если попросят подробнее
>
> Проверяют последовательность A → B → ответ B → ответ A. Перед началом сохраняют номер новой операции; перед записью данных сравнивают его с номером текущей. При отмене или закрытии экрана также делают старую операцию неактуальной.
>
> Проверка относится не только к данным: поздняя ошибка A не должна перекрыть успешный B, а finally старого запроса не должен сбросить loading нового. AbortController помогает остановить поддерживающую отмену работу, но проверка актуальности защищает сам эффект в интерфейсе.
>
> Для операции записи отмена клиентского ожидания не доказывает отмену на сервере. Если ответ потерян, результат выясняют по согласованному статусу операции, а повтор выполняют по контракту идемпотентности.

> [!followup]- Достаточно ли AbortController, если сервер уже обработал запрос?
>
> Нет: отмена fetch прекращает клиентское ожидание и связанные этапы получения ответа, но не является транзакционным откатом на сервере. Если запись уже зафиксирована, abort не удалит её.
>
> Для чтения при смене фильтра отменяю ненужный запрос и отдельно проверяю актуальность результата. Для создания заказа использую поддерживаемый сервером ключ идемпотентности и способ узнать исход той же операции: повтор с новым ключом может создать дубль. Проверка — сервер сохранил запись, ответ потерялся, клиент повторил действие; результатом должна остаться одна операция. Реальная бизнес-отмена требует отдельной серверной команды и её правил.

> [!followup]- Как проверить актуальность результата без поддержки отмены?
>
> Каждому запуску присваиваю номер; применять данные, ошибку и loading может только актуальный запуск. При уходе со страницы инвалидирую номер. Это защищает отображение, но не прекращает сетевую работу и не откатывает серверные побочные эффекты.
>
> ~~~js
> let generation = 0;
> async function load(id) {
>   const mine = ++generation;
>   showLoading(true);
>   try {
>     const value = await read(id);
>     if (mine === generation) showData(value);
>   } catch (error) {
>     if (mine === generation) showError(error);
>   } finally {
>     if (mine === generation) showLoading(false);
>   }
> }
> function dispose() {
>   generation++;
> }
> ~~~
>
> read и show-функции здесь — зависимости экрана. Проверяю последовательность A→B с завершением B→A, позднюю ошибку A и завершение после dispose. Экран должен сохранить результат B; для каждого независимого поиска нужен собственный счётчик.

> [!followup]- Почему finally старого запроса не должен выключать loading нового?
>
> finally выполняется при завершении конкретной операции, а общий loading часто означает состояние последнего запроса экрана. Если A стартовал, затем B, а A завершился первым, безусловное loading=false от A преждевременно скроет индикатор B. Такая же гонка возможна при отмене A.
>
> Для режима «показываем последний запрос» сохраняю номер запуска и в finally меняю состояние только при совпадении с актуальным номером. Если индикатор означает «есть хотя бы одна операция», нужен счётчик или набор активных операций с удалением своей записи, а не проверка последнего номера. Тест намеренно завершает A, пока B ещё ожидает: индикатор должен остаться, затем исчезнуть после B.

### Как использовать AbortSignal в собственном API?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Принимаю сигнал, проверяю уже aborted, подписываюсь на abort и снимаю listener после завершения. Определяю тип ошибки и освобождение ресурсов. Отмена должна завершать ожидание и освобождать ресурсы.
>
>
> В delay(ms,signal) сначала проверяю signal.aborted, затем ставлю таймер и listener abort. Успех очищает listener, отмена очищает таймер и отклоняет ожидание с signal.reason. {once:true} снимает listener после abort, но не после обычного успеха. Проверки: сигнал уже отменён, отмена до/после завершения и независимые вызовы; один исход не должен дважды выполнять очистку.
### Как должна вести себя функция, если переданный AbortSignal уже отменён?

**ID вопроса:** Что такое контракт отмены?

> [!example]- Разбор
>
> До запуска побочного действия проверяю signal.aborted. Если сигнал уже отменён, Promise-API сразу возвращает отклонённое ожидание с signal.reason, не запускает запрос/таймер и не ждёт нового события abort: оно уже произошло. Для синхронного API можно использовать signal.throwIfAborted().
>
> Пример проверки: создать controller, вызвать abort(reason), затем вызвать delay(100, controller.signal). Ожидание должно отклониться с этой причиной, а число созданных таймеров остаться нулём. Сам сигнал одноразовый: для новой операции после отмены нужен новый controller. Если работа уже началась раньше, отдельно определяют её очистку; отмена клиентского ожидания не откатывает серверную запись.
### Как завершить ожидание Promise по тайм-ауту?

**ID вопроса:** Как безопасно реализовать ограничение времени вокруг Promise?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Таймаут ограничивает ожидание и по возможности отменяет операцию; Promise.race сам по себе её не останавливает. Таймер очищаю при любом исходе и различаю таймаут, отмену и другие ошибки.
>
>
> Для fetch создаю контроллер, запускаю таймер его abort, затем в finally очищаю таймер. Если внешняя операция не поддерживает отмену, race ограничит только ожидание; её поздний результат всё равно нельзя применять как актуальный. Проверяю быстрый успех, быстрый отказ, истечение срока и внешнюю отмену; сообщение пользователю зависит от фактической причины.
### Как в однопоточном JavaScript возникает гонка запросов?

**ID вопроса:** Почему асинхронный код может иметь гонку асинхронных операций в одном потоке?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Между await другие продолжения меняют общее состояние. Два чтения старого значения и последующие записи дают потерянное обновление даже без двух JS-потоков. Нужны очередь, проверка версии или атомарная операция сервера.
>
>
> Запускаются A и B; B завершается первым и записывает свежие данные, затем A заменяет их старыми. Каждая запись выполнялась последовательно на одном потоке, но логический порядок нарушен. Номер операции перед применением результата решает именно эту гонку чтений; для конкурентной серверной записи нужна проверка версии или иной контракт на сервере.

> [!followup]- Как защитить критическую секцию в асинхронном JavaScript?
>
> Критическая секция — чтение, решение и запись общего состояния, которые должны выглядеть одной операцией. Даже на одном потоке `await` между ними позволяет другому продолжению прочитать прежнее значение. Если действие чисто локальное, по возможности вынесите ожидание наружу и сделайте саму проверку и запись синхронными.
>
> Например, два вызова читают `count = 0`, ждут запрос и оба пишут 1. Можно сначала дождаться запросов, затем делать `count += 1` без `await` между чтением и записью. Если ожидание внутри секции неизбежно, пропускайте операции через очередь/мьютекс и освобождайте его в `finally`. Это защищает только участников одной очереди; для нескольких вкладок или клиентов нужен общий механизм в хранилище или на сервере.

> [!followup]- Как проверка версии защищает от конкурентного изменения записи?
>
> Прочитайте данные вместе с их версией и передайте ожидаемую версию при сохранении. Сервер должен одной атомарной операцией сравнить версию и выполнить запись: например, `UPDATE docs SET body = $1, version = version + 1 WHERE id = $2 AND version = $3`. Если обновлено ноль строк, запись исчезла или изменилась; выясните причину и покажите конфликт либо перечитайте данные и пересчитайте изменение.
>
> Два клиента редактируют версию 7. Первый сохраняет версию 8; второй больше не может затереть её своей копией версии 7. В HTTP ту же идею реализует `If-Match` с ETag. Проверка отдельным `SELECT` перед безусловным `UPDATE` оставляет окно гонки, а автоматический повтор старого тела может вернуть потерянное изменение.

> [!followup]- Почему блокировка кнопки в интерфейсе не предотвращает конкурентные записи?
>
> `disabled` блокирует повторный клик на конкретной странице. Другая вкладка, другой пользователь или повтор после сетевого сбоя по-прежнему могут отправить запрос. Даже локально важно поставить флаг до первого `await`, иначе два вызова успеют стартовать до блокировки.
>
> Для сохранения документа сервер может отклонять запись со старой версией. Для операции создания заказа повтор одного намерения защищают ключом идемпотентности, а невозможность создать два заказа на один ресурс — соответствующим ограничением или транзакцией. Это разные задачи: одинаковый запрос и разные конкурентные запросы. Кнопка улучшает UX и уменьшает случайные дубли, но корректность данных обеспечивается там, где фиксируется запись.

## Чем debounce отличается от throttle?

**ID вопроса:** Чем отложенный вызов отличается от ограничения частоты?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Debounce объединяет серию частых вызовов: обычно функция выполняется после паузы заданной длины. Это удобно для поиска после окончания ввода. Throttle ограничивает частоту выполнения в непрерывном потоке: например, обработчик scroll может срабатывать не чаще заданного интервала.
>
> Поведение на первой и последней границе нужно оговорить: leading запускает в начале, trailing — после ожидания. Обёртка хранит таймер и последние аргументы в замыкании; её создают один раз на время жизни обработчика. При уничтожении владельца отменяют отложенный вызов.
>
> Debounce уменьшает число запусков, но не устраняет гонку уже отправленных запросов. Для поиска отдельно требуется защита от устаревшего ответа.

**Критерии ответа:** Рисую временную шкалу вызовов, различаю debounce/throttle и объясняю очистку ресурсов и защиту от старого ответа.

> [!followup]- Что случится, если создавать debounce внутри каждого input-handler?
>
> Каждый вызов создаст новое замыкание со своим таймером. Следующий `input` не увидит таймер предыдущего вызова и не сможет его отменить. Если пользователь введёт `a`, `ab`, `abc` быстрее задержки, уйдут все три запроса чуть позже, а не один запрос для `abc`.
>
> Создайте обёртку один раз на время жизни поля: `const scheduleSearch = debounce(search, 300);`, а обработчик вызывает `scheduleSearch(input.value)`. При удалении компонента отмените её отложенный вызов. Если поиск уже стартовал до следующего ввода, debounce его не остановит; для таких запросов отдельно используют сигнал отмены и/или проверку актуальности ответа.

> [!followup]- Нужен ли завершающий вызов при непрерывном scroll?
>
> Trailing-вызов нужен, когда последнее состояние обязательно должно попасть в обработчик. При throttle только с leading обработчик может выполниться в точке 0, затем пропустить последний scroll в точке 90 при интервале 100 мс. Для визуального индикатора это оставит устаревшую позицию. Trailing запускает обработчик с последними аргументами при завершении текущего интервала, даже если новых событий больше нет.
>
> Если задача только периодически измерять скорость или отправлять необязательную телеметрию, последний вызов может быть лишним. Для анимации часто достаточно объединять обновления в один `requestAnimationFrame` с чтением последней позиции. Для действий именно после прекращения прокрутки нужен debounce или подходящее событие окончания, а не просто trailing throttle.

> [!followup]- Почему отмена таймера не отменяет уже отправленный запрос?
>
> `clearTimeout` отменяет запланированный вызов, пока он ещё не начал выполняться. После того как обработчик вызвал `fetch`, таймер уже сделал свою работу; сетевой запрос живёт по отдельному контракту.
>
> Например, после паузы поиск по `'ab'` ушёл на сервер, затем пользователь вводит `'abc'`. Отмена очередного debounce-таймера не остановит `'ab'`. Храните `AbortController` активного запроса, при необходимости отменяйте его и привязывайте применение результата к номеру актуального поиска. Номер особенно полезен, если ответ уже пришёл или используемый клиент не поддерживает сигнал. Очистка таймера и отмена активного запроса обе нужны при уходе со страницы.

## Как работает сборка мусора и откуда берутся утечки?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Современные движки JavaScript собирают недостижимые объекты, включая недостижимые циклы ссылок. Утечка возникает, когда ненужные данные остаются достижимыми через обработчики, таймеры, кэши, замыкания или удалённые узлы DOM. Причину ищу по удерживающим ссылкам в снимке памяти.
>
> Обработчик на `window`, который замыкает состояние уже закрытого экрана, оставляет путь к этим данным. Удаление компонента из DOM само по себе не удаляет глобальный listener: его снимают при завершении экрана и проверяют удерживающие ссылки в снимке памяти.
>

> [!followup]- Когда WeakMap помогает избежать удержания объектов и чего он не решает?
>
> WeakMap подходит для дополнительных данных, связанных с объектом-ключом: сама запись не удерживает такой ключ от сборки. Например, metadata.set(domNode, measurements) позволяет не хранить отдельный обычный Map, который бессрочно удерживал бы удалённые узлы. Время сборки не определено; содержимое WeakMap нельзя перечислить для надёжной логики очистки.
>
> Если domNode ещё удерживается глобальным обработчиком или массивом, WeakMap это не исправляет. Он также не ограничивает размер обычного кэша по строковым ID и не вызывает disconnect/unsubscribe. Проверяю цепочку сильных ссылок в heap snapshot, а не пытаюсь тестом дождаться GC к конкретной миллисекунде. [WeakMap](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakMap).

> [!followup]- Кто останавливает созданные таймеры, наблюдения и запросы?
>
> Ответственность принадлежит владельцу ресурса: компоненту, эффекту, сервису или явной сессии, которая его создала. При завершении этого времени жизни вызываются clearTimeout/clearInterval, disconnect, unsubscribe, abort или API уничтожения виджета. Общий ресурс нельзя закрывать при уходе одного потребителя, если он ещё нужен другим.
>
> Например, экран создаёт ResizeObserver и interval: одна функция dispose освобождает оба, вызывается при уходе и безопасна при повторном вызове. Уже поставленный callback дополнительно проверяет актуальность владельца. Проверяю повторный вход/выход, отсутствие новых вызовов после ухода и стабильное число активных подписок. Назначение владельца важнее предположения, что framework автоматически очистит всё, созданное внутри callback.

> [!followup]- Как отличить утечку памяти от прогрева кэша при повторении сценария?
>
> Сначала повторяю один сценарий на одинаковых данных: открыть экран, выполнить действие, закрыть и дать приложению завершить работу. Сравниваю несколько циклов, объём живых объектов после сборки и их удерживающие ссылки. Сам рост выделенной памяти или пилообразный график до GC не доказывает утечку.
>
> Кэш может вырасти при первом входе и затем выйти на ограниченное плато. Если каждый повтор оставляет ещё один контейнер и listener, ищу путь от корня к этому контейнеру. Учитываю, что консоль и выбранные в DevTools объекты сами могут удерживать ссылки. После исправления повторяю тот же цикл и проверяю исчезновение конкретного удержания, а не только меньшее случайное число мегабайт.

> [!followup]- Почему сборка мусора не заменяет явное освобождение внешних ресурсов?
>
> GC управляет достижимостью JavaScript-объектов, но не является договором о своевременной остановке работы. Таймер с callback может сам удерживать состояние экрана, а соединение или подписка — продолжать получать события. Удаление DOM-узла не означает закрытия всех связанных ресурсов.
>
> Например, удалён график, но callback WebSocket продолжает обновлять его модель. Владелец явно снимает подписку и, если соединение больше никому не нужно, закрывает его. Финализаторы нельзя использовать для гарантированной бизнес-очистки: запуск и время не гарантируются. Тест проверяет, что после dispose больше нет событий и запросов, а не только уменьшение heap. Общее соединение требует учёта потребителей, чтобы очистка одного графика не отключила остальные.

### Когда замыкание удерживает слишком много памяти?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда долгоживущая функция остаётся достижимой и ей нужен объект из окружения. Снимаю подписки, ограничиваю кеш и сокращаю удерживаемые данные.
>
>
> Обработчик на window, замкнувший модель закрытого редактора, остаётся достижимым через список listeners. Пока обработчик нужен среде, модель может оставаться в памяти. После removeEventListener с той же функцией и удаления других ссылок возможность сборки возвращается. В снимке памяти после нескольких открытий и закрытий смотрю, какая цепочка ссылок удерживает объект. Общий график памяти не покажет саму причину.
### Почему нельзя предсказать момент сборки мусора?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Время освобождения памяти не является контрактом программы. Не рассчитываю на GC для закрытия соединения, снятия listener или сохранения данных. Очистку делаю явно на завершении сценария.
>
>
> Даже после obj=null память может оставаться выделенной до удобного для движка момента. WeakRef и FinalizationRegistry не дают надёжного срока уборки. Подписку или соединение закрываю при завершении сценария явно; финализатор не должен быть единственным способом сохранить пользовательские данные.
### Как отличить утечку памяти от кеша?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Кеш хранит данные ради повторного использования; утечка удерживает то, что уже не нужно. Смотрю, перестаёт ли память расти при повторении одного сценария и какие ссылки удерживают объекты. У кеша должны быть предел размера и правило удаления старых записей.
>
>
> После десяти одинаковых открытий кэш может достичь лимита и стабилизироваться, а забытые подписки продолжат добавляться на каждом цикле. Сравниваю несколько снимков после одинакового сценария и ищу конкретные удерживаемые объекты. Даже полезный кэш без лимита может быть дефектом: название cache не оправдывает бесконечный рост.
## Как обрабатывать ошибки синхронного и асинхронного кода?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Ловлю ошибку там, где могу восстановиться или сообщить понятный результат. try/catch не ловит будущую ошибку отдельно вызванного обработчика. Promise нужно ожидать, возвращать вызывающей стороне или явно обрабатывать через catch. Не подменяю ошибку успехом и сохраняю данные для диагностики.
>
> Обработчик сохранения формы должен дождаться `save()` и показать ошибку, сохранив введённые данные. Если вызвать `save()` без `await` внутри `try`, отклонение Promise не попадёт в этот `catch`; для фонового действия нужен явный обработчик отказа.
>

> [!followup]- Зачем передавать исходную ошибку в поле cause?
>
> `new Error('Не удалось загрузить настройки', { cause: error })` добавляет контекст текущей операции и сохраняет исходное значение. У вызывающего кода остаётся осмысленное сообщение, а логгер может отдельно показать причину, её тип и стек, если причиной был объект `Error`.
>
> Например, низкоуровневый вызов сообщает о разрыве соединения, а слой настроек уточняет, какая операция не завершилась. Соединение текстов через шаблонную строку теряет структурную причину; просто повторный `throw error` сохраняет оригинал, но не добавляет нужного контекста. `cause` может быть произвольным значением, поэтому проверяйте его тип. Клиенту показывайте понятное сообщение, а технические подробности сохраняйте в диагностике.

> [!followup]- Чем доменная ошибка отличается от транспортной и как их обрабатывать?
>
> Доменная ошибка описывает правило операции: «товар закончился», «версия документа устарела». Интерфейс может предложить изменить корзину или перечитать документ. Транспортная означает, что обмен не завершился как ожидалось: обрыв соединения, таймаут или некорректный ответ. Клиент иногда не знает, успел ли сервер изменить данные.
>
> Например, HTTP 409 с согласованным кодом `VERSION_CONFLICT` — доменный конфликт; обрыв до чтения ответа оставляет итог неизвестным. В адаптере переводите известные ответы в устойчивые коды, а сетевые сбои выделяйте отдельно. Не распознавайте доменные ошибки по тексту сообщения и не считайте каждый 4xx сетевым сбоем: статус и тело нужно трактовать по контракту API.

> [!followup]- Какие ошибки стоит повторять и где ограничивать число попыток?
>
> Повторяйте только временный сбой и только операцию, для которой повтор безопасен. Например, чтение каталога после разрыва соединения можно повторить с растущей задержкой и случайным разбросом; запрос с ошибкой валидации останется неверным, пока данные не исправят.
>
> Задайте предел по попыткам и общему времени, учитывайте `Retry-After` при подходящем ответе и прекращайте ожидание по сигналу отмены. Для записи с неясным исходом используйте согласованный ключ идемпотентности или сначала проверьте состояние. Повторы лучше контролировать в одном слое: если UI, клиент и прокси каждый делают по три попытки, нагрузка на сервер может умножиться.

> [!followup]- Почему try/catch вокруг setTimeout не ловит отклонение Promise из его обработчика?
>
> Внешний `try` заканчивается после регистрации таймера. Позже среда вызывает обработчик отдельно; она не включает возвращённый `async`-обработчиком Promise в исходный вызов. Ошибка может стать необработанным rejection.
>
> Обработайте ошибку внутри функции, которую запускает таймер:
>
> ```js
> setTimeout(async () => {
>   try {
>     await save();
>   } catch (error) {
>     reportError(error);
>   }
> }, 100);
> ```
>
> Такой `try/catch` перехватит и синхронный `throw` из `save`, и отклонение возвращённого Promise. Если ошибку должен обработать вызывающий код, оформите ожидание таймера как `delay(100)` и выполните `await delay(100); await save();` внутри его `try`.

### Чем синхронный throw отличается от Promise.reject?

> [!answer]- Короткий ответ — 30–90 секунд
>
> throw прерывает текущий стек; Promise.reject создаёт отклонённый Promise. В async-функции throw становится отказом возвращённого Promise. Вызывающий должен обработать именно соответствующий канал ошибки.
>
>
> try { Promise.reject(error); } catch {} не перехватит будущую обработку rejection. В async-функции нужно await внутри try либо return promise.catch(handler). А синхронный throw в вызываемой обычной функции сразу попадёт в окружающий catch. Проверяю, что внешний вызов получает отказ, а не «успех» с потерянным результатом.
### Почему цепочка then может продолжиться после catch?

> [!answer]- Короткий ответ — 30–90 секунд
>
> catch — обработчик rejection, возвращающий новый Promise. Возврат обычного значения восстанавливает успешную цепочку; throw или возврат rejected Promise сохраняет ошибку. Это позволяет восстановиться, но легко скрыть сбой.
>
>
> Promise.reject('fail').catch(() => 0).then(value => ...) передаст 0 в then. Если catch только console.error и ничего не возвращает, дальше пойдёт fulfilled с undefined. Для сохранения отказа нужно throw error; для восстановления — осмысленное значение, которое подходит следующему шагу.
### Почему ошибка в finally может скрыть исходную?

> [!answer]- Короткий ответ — 30–90 секунд
>
> throw либо отклонённый результат finally может заменить предыдущий исход. Очистка должна быть надёжной, а ошибки — сохранять причинную цепочку. Не делаю return в finally без явного понимания последствий.
>
>
> Ошибка в `finally` заменяет первоначальное отклонение:
>
> ```js
> Promise.reject(original)
>   .finally(() => {
>     throw cleanupError;
>   })
>   .catch(error => {
>     console.log(error === cleanupError); // true
>   });
> ```
>
> Возврат обычного значения из `Promise.finally` сохраняет прежний результат. Если очистка тоже может завершиться ошибкой, сохраните исходную причину до её запуска, чтобы сообщить об обеих ошибках.
## Как устроены модули ESM и CommonJS?

> [!answer]- Короткий ответ — 30–90 секунд
>
> ESM использует import и export, статически анализируемые зависимости, живые привязки экспортируемых переменных и собственную область видимости. CommonJS использует require и module.exports; обычная загрузка синхронна. Динамический import возвращает Promise. Совместимость зависит от среды выполнения и сборщика.
>
> Редактор диаграмм можно загрузить через `import()` только при открытии соответствующего экрана. Пользователь не получает его код при первом посещении главной страницы, если сборщик действительно выделяет отдельный chunk; ошибка загрузки требует отдельного состояния интерфейса.
>

> [!followup]- Чем цикл зависимостей в ESM отличается от цикла в CommonJS?
>
> В ESM импорты ссылаются на живые привязки. Цикл возможен, но чтение импортированного `const` до инициализации вызовет `ReferenceError`. В CommonJS при циклическом `require` Node может отдать модулю незавершённый объект `exports`, поэтому раннее чтение поля нередко вернёт `undefined`.
>
> Например, если A и B вычисляют экспортируемые константы сразу при загрузке, а каждая зависит от константы другой, перестановка импортов только меняет место сбоя. Выделите общую зависимость в третий модуль или перенесите совместную инициализацию в явный вызов после загрузки обоих. Цикл, в котором модули только объявляют функции и вызывают их после инициализации, может работать, но всё равно усложняет управление зависимостями.

> [!followup]- Когда сборщик может удалить неиспользуемый экспорт и что меняют побочные эффекты?
>
> Статические импорты и экспорты ESM позволяют сборщику увидеть, какие привязки используются. Если из модуля импортировали только `formatDate`, неиспользуемая чистая `formatMoney` может исчезнуть из сборки. При этом запуск кода верхнего уровня должен сохраниться, если он имеет наблюдаемый побочный эффект.
>
> Например, модуль при загрузке регистрирует компонент или импортирует CSS. Если объявить такой файл свободным от побочных эффектов, сборщик может выкинуть импорт и сломать приложение. В webpack поле `sideEffects` помогает указать, какие файлы сохранять. Фактическое удаление зависит от сборщика, режима оптимизации и формы модуля; проверяйте выходной bundle, особенно при CommonJS и динамическом обращении к экспортам.

> [!followup]- Чем default export отличается от именованных экспортов ESM?
>
> Модуль может иметь один экспорт с именем `default` и несколько именованных экспортов. У default имя выбирает импортирующий код: `import Editor from './editor.js'`. Именованные импортируют в фигурных скобках по объявленному имени и при необходимости переименовывают: `import { createEditor as create } from './editor.js'`.
>
> У модуля `export default Editor; export function createEditor() { … }` оба вида экспорта доступны одновременно. Неиспользуемость экспорта и возможность tree shaking определяет сборщик; форма `default` сама по себе не выключает оптимизацию. Отдельный нюанс: `export default value` экспортирует значение выражения при вычислении, тогда как `export { value as default }` экспортирует живую привязку `value`. Правила импорта CommonJS из ESM определяет среда, это не то же самое, что обычный ESM-экспорт.

> [!followup]- Как top-level await влияет на загрузку ESM и его импортёров?
>
> `await` на верхнем уровне ESM позволяет модулю завершить инициализацию асинхронно. Модули, которые статически от него зависят, начнут выполнять своё тело после завершения нужных зависимостей. Независимые ветки графа при этом могут выполняться; весь event loop не блокируется.
>
> Например, `config.mjs` экспортирует `const config = await loadConfig()`. Импортёр увидит готовую конфигурацию, но старт приложения теперь зависит от сети, а отказ загрузки отклонит и динамический `import()` импортёра. Для необязательной функции часто лучше явно вызывать асинхронный загрузчик при открытии экрана. В CommonJS top-level await недоступен; в Node синхронный `require` ESM не загрузит граф с асинхронной оценкой.

### Когда динамический import полезен?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Динамический import позволяет загрузить код, когда он понадобился, и уменьшить начальную загрузку страницы. Пока файл загружается, интерфейс показывает ожидание; при сбое — способ повторить попытку. Сборка и обновление кеша должны сохранять доступность нужных файлов. Слишком мелкое разбиение увеличивает число загрузок и расходы на них.
>
>
> Редактор PDF можно загрузить при открытии редактора, пока остальные страницы используют лёгкий entry. Проверяю граф сборки: статический импорт той же библиотеки из общего модуля может сохранить её в начальном наборе. Для старой вкладки тестирую доступность прежнего chunk после нового выпуска и понятное восстановление без потери ввода.
## Как читать строки Unicode без повреждения символов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Строка JavaScript состоит из кодовых единиц UTF-16. length и индексы считают их; spread и for...of обходят кодовые точки, но не все видимые пользователю символы. Для составных эмодзи и сочетаний с диакритикой нужен разбор графем, например через Intl.Segmenter. Сначала определяю, что задача считает символом.
>
> При ограничении длины имени пользователь ожидает считать видимые символы. Семейный эмодзи занимает несколько кодовых точек, поэтому даже `[...text].length` может не соответствовать этому ожиданию; для такого ограничения нужна сегментация графем.
>

> [!followup]- Как Intl.Segmenter помогает считать и обрезать видимые символы?
>
> Создайте `Intl.Segmenter(locale, { granularity: 'grapheme' })` и перебирайте `segment(text)`. Запись содержит текст графемы в `segment` и начальную позицию в UTF-16 в `index`. Графема часто соответствует одному видимому пользователю символу, даже если в ней несколько кодовых точек.
>
> Например, у `'👩‍💻x'` два сегмента: первый с индексом 0, второй с индексом 5. Для ограничения в одну графему можно взять `text.slice(0, 5)`. Не используйте `index` как счётчик графем; ведите отдельный счётчик. Сегментация не нормализует строку и не измеряет ширину на экране. Для старой среды проверьте доступность API или используйте Unicode-совместимую реализацию.

> [!followup]- Что такое суррогатная пара UTF-16 и почему её нельзя резать по одному индексу?
>
> Кодовая точка выше U+FFFF кодируется двумя единицами UTF-16: старшим и младшим суррогатами. Например, `'😀'.length === 2`, а `'😀'.slice(0, 1)` оставляет один старший суррогат, который не представляет самостоятельный символ.
>
> Для обхода кодовых точек используйте `for...of` или `Array.from(text)`; если нужны смещения для `slice`, увеличивайте их на `cp.length`. `codePointAt(i)` объединит корректную пару при позиции старшего суррогата, но произвольный индекс всё ещё может указывать на младший. Строка JS может уже содержать одиночный суррогат, и обход его не исправляет. Для видимых составных символов дополнительно нужна сегментация по графемам.

> [!followup]- Зачем нормализовать Unicode-строки перед сравнением?
>
> Один и тот же текст может иметь разные последовательности кодовых точек. Например, `'\u00e9'` и `'e\u0301'` канонически эквивалентны, но `===` даст `false`. После `normalize('NFC')` они совпадут и будут одинаковыми ключами `Map`.
>
> Нормализуйте в одном месте по согласованному контракту, например при построении ключа поиска; если нужен исходный ввод, храните его отдельно. NFC сохраняет каноническую эквивалентность, а NFKC дополнительно сводит некоторые совместимые формы (например, полноширинную букву к обычной), что может быть нежелательно для идентификаторов. Нормализация не заменяет сравнение с учётом регистра или языка и не делает похожие символы разных алфавитов одинаковыми.

> [!followup]- Как сравнивать Unicode-строки без учёта регистра с учётом языка?
>
> Для пользовательского сравнения задайте язык и нужную чувствительность через `Intl.Collator`. Если нужно игнорировать регистр, но отличать диакритику, используйте `sensitivity: 'accent'` и проверяйте `collator.compare(a, b) === 0`. Например, в турецком `'I'` сопоставляется с `'ı'`, а `'İ'` — с `'i'`; простое `toLowerCase()` не учитывает эту пару правил.
>
> Для сортировки переиспользуйте один Collator на набор строк. Его сравнение не создаёт канонический ключ, который можно положить в `Map`, и поведение зависит от выбранного языка. Если речь о стабильном техническом идентификаторе, явно задайте правила нормализации и регистра в контракте вместо локали интерфейса.

## Что такое регулярные выражения и какие у них риски?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Регулярное выражение подходит для ограниченного распознавания текста. Произвольную вложенную грамматику надёжнее разбирать отдельным парсером. Большое число возвратов при подборе может блокировать поток. Учитываю длину текста, Unicode и изменение lastIndex у выражений с флагами g или y.
>
> Регулярное выражение полезно для проверки согласованного формата кода заказа. Для HTML или вложенных выражений используют парсер. При обработке пользовательского текста проверяют длинные неуспешные входы: некоторые шаблоны резко замедляются именно на них.
>

> [!followup]- Как флаги g и y меняют lastIndex и повторные проверки RegExp?
>
> С `g` движок ищет совпадение начиная с `lastIndex` и может перескочить вперёд; с `y` совпадение должно начинаться строго в `lastIndex`. Успешный `exec`/`test` обновляет позицию до конца совпадения, неудачный сбрасывает её в 0.
>
> Например, `const re = /a/g; re.test('a'); re.test('a');` даёт `true`, затем `false`: второй тест начал поиск с позиции 1. Для независимой проверки уберите `g/y` или явно сбрасывайте `lastIndex`; для токенизации `y` полезен, когда нельзя молча пропустить неверный символ. При ручном цикле по `exec` совпадение нулевой длины требует явного продвижения позиции, иначе цикл может не закончиться.

> [!followup]- Как безопасно искать пользовательский текст внутри регулярного выражения?
>
> Если введённый текст должен совпадать буквально, не вставляйте его в шаблон как синтаксис. Для поиска подстроки достаточно `includes`. Когда нужен именно составной RegExp, в поддерживаемых средах применяйте `RegExp.escape(input)` к буквальному фрагменту, а флаги и окружающий шаблон определяйте сами.
>
> Например, для ввода `a.b` точка должна совпасть только с точкой; `new RegExp(RegExp.escape('a.b'), 'u')` найдёт `a.b`, но не `axb`. Полное экранирование учитывает не только метасимволы, но и соседние escape-последовательности в шаблоне. Для среды без API нужен совместимый polyfill или отказ от динамического RegExp. Это не заменяет ограничение размера входа и проверку сложности остальной части выражения.

> [!followup]- Почему вложенный JSON следует разбирать парсером, а не регулярным выражением?
>
> У JSON есть вложенные массивы и объекты, а кавычки, фигурные скобки и запятые внутри строки не являются разделителями. RegExp JavaScript не отслеживает произвольную глубину таких конструкций. `JSON.parse` разбирает грамматику и отклоняет неверный документ; затем отдельно проверьте типы и поля полученного значения.
>
> Например, у `{"body":"a } b","items":[{"id":1}]}` поиск первой `}` завершится в строке `body`, а поиск последней не поможет с несколькими документами подряд. Если JSON встроен в поток, сначала задайте границы сообщений (например, по длине или отдельным строкам в NDJSON), затем разбирайте каждое целиком. Ограничивайте размер документа на входе.

> [!followup]- Как распознать и предотвратить ReDoS в регулярном выражении?
>
> ReDoS возможен, когда неуспешный поиск вынуждает движок перебрать слишком много вариантов. Признак риска — повторяемые части, способные по-разному разделить один и тот же участок строки. Особенно важны проверки длинных входов, которые почти совпадают и ломаются на последнем символе.
>
> Для кода заказа из букв и цифр задайте один ограниченный шаблон вроде `/^[A-Z0-9]{1,32}$/` и проверьте длину до запуска. Для сложного формата рассмотрите последовательный парсер; добавьте проверку времени на граничных вводах в отдельном процессе, чтобы зависание не остановило основной тест. Не полагайтесь на `setTimeout` рядом с синхронным RegExp: таймер не сработает, пока поток занят поиском.

## Как устроена мемоизация функции?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Кэш связывает входные значения с результатом. Это полезно для дорогой чистой функции с повторяющимися входами. Определяю равенство ключей, срок хранения, предел памяти и поведение при ошибке асинхронного результата. JSON.stringify не является универсальным способом получить ключ.
>
> Повторный расчёт группировки большого списка можно пропустить, если входная версия не изменилась. Но кэш по ссылке на массив станет неверным при его мутации; нужны неизменяемые входы либо явная версия. Кэш с любыми пользовательскими ключами ограничивают по размеру.
>

Изучить: [[Собеседования/Практика/JavaScript#Мемоизация функции с очисткой кэша|реализация и срок жизни кэша]].

> [!followup]- Как мемоизация должна учитывать this у метода?
>
> Обёртка должна передавать получателя исходной функции через `fn.apply(this, args)` и включать его в ключ, если метод читает состояние получателя. Для объектов можно хранить отдельный кеш на экземпляр в `WeakMap`. Обычная функция сохраняет динамический `this` при вызове метода; стрелочная обёртка захватит `this` места объявления.
>
> Например, `price(qty)` умножает число на `this.rate`. Два объекта с тарифами 5 и 8 при `qty = 2` должны получить 10 и 16, даже если используют одну обёртку. Отдельный кеш на объект не решает мутацию самого тарифа: при изменении нужен сброс, версия состояния или отказ от мемоизации. Для свободного вызова функции без объекта задайте отдельный контракт.

> [!followup]- Как строить ключ мемоизации, если аргументы содержат циклические ссылки?
>
> Для сравнения по идентичности используйте вложенные `Map` для примитивов и `WeakMap` для объектных аргументов; на каждом уровне ключ — очередной аргумент. Тогда цикл внутри объекта обходить вообще не нужно. `JSON.stringify` циклического объекта бросит ошибку, а простое удаление циклов может дать одинаковый ключ разным графам.
>
> Например, `const node = {}; node.self = node;` можно положить ключом в `WeakMap`, и повторный вызов с тем же `node` получит прежний результат. Другой самоссылочный объект будет другим ключом, а изменение полей `node` не изменит его идентичность. Если нужна структурная эквивалентность графов, придётся явно определить порядок свойств, учёт общих ссылок и типов; часто достаточно неизменяемого id и версии.

> [!followup]- Когда нужно сбрасывать кеш мемоизации?
>
> Сбрасывайте запись, когда меняется зависимость, от которой зависит результат. Если ключ состоит из id товара, а цена зависит ещё от тарифа, добавьте версию тарифа к ключу или удаляйте связанные записи при обновлении тарифа. Мутация объекта с тем же адресом не создаёт новый ключ.
>
> TTL ограничивает, сколько времени допустим старый результат, но не гарантирует свежесть сразу после изменения. Для кеша дорогого чистого вычисления от неизменяемых аргументов достаточно ограничения памяти, для ответа сервера часто нужны и явное обновление, и TTL. Удаляйте старые версии: включение версии в ключ само по себе их не освобождает.

> [!followup]- Как LRU ограничивает размер кеша мемоизации?
>
> При попадании помечайте запись как недавно использованную; при превышении лимита удаляйте самую давно использованную. В JS можно хранить порядок в `Map`: `delete(key); set(key, value)` переносит существующий ключ в конец, один `set` — нет.
>
> При ёмкости 2 после вызовов A, B, A, C останутся A и C. Для кеширования результата `undefined` проверяйте `has`, а не истинность `get`. LRU полезен при повторном доступе к небольшому рабочему набору, но не гарантирует свежесть значения и не ограничивает байты, если размеры результатов сильно различаются.

> [!followup]- Как кешировать Promise и не сохранять отказ навсегда?
>
> Кладите в кеш незавершённый Promise сразу после создания, чтобы два параллельных запроса к одному ключу ожидали одну загрузку. При отклонении обычно удаляйте запись, чтобы следующий вызов мог повторить запрос. Перед удалением проверьте, что в кеше всё ещё лежит именно этот Promise: старый отказ не должен удалить более новую запись.
>
> Например, два экрана одновременно запрашивают один профиль, и сеть используется один раз. Если один экран уходит, отмена общего запроса затронет и второй. Поэтому отделите прекращение ожидания конкретным потребителем от отмены общей работы. Также решите, хранить ли исполненный результат и с каким TTL.

### Как выбрать кеш для функции с объектными аргументами?

> [!answer]- Короткий ответ — 30–90 секунд
>
> WeakMap позволяет сохранить результат для конкретного объекта и найти его при повторном вызове с тем же объектом. Это работает, пока данные, от которых зависит результат, не изменились. Если одинаковое содержимое разных объектов должно давать один ключ, нужны отдельные правила его построения и ограничение размера такого кеша.
>
>
> Если const options={limit:10} использован как WeakMap-ключ, а затем options.limit=20, прежний результат под тем же ключом устаревает. Подход работает для неизменяемых объектов или при явной инвалидации. Сериализация ключа требует стабильных правил для порядка полей и специальных значений; бесконечный Map строковых ключей тоже требует ограничения.
### Когда можно возвращать кешированный Promise?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда нескольким вызывающим нужен результат одной и той же операции: они могут ждать один Promise вместо повторного запроса. Нужно решить, сколько хранить успешный результат, удалять ли запись после ошибки и как отмена одного потребителя повлияет на остальных. Иначе следующий вызов может получить старый отказ вместо новой попытки.
>
>
> Два одновременных чтения одного документа могут ждать один inFlight Promise. В finally удаляю именно этот Promise из Map, чтобы старое завершение не удалило более новое выполнение. Если нужно хранить и успешный результат, отдельно задаю срок его актуальности (TTL) и удаление записи при изменении данных. Отмена одного потребителя не должна неожиданно отменить запрос, нужный другому.

Изучить: [[Собеседования/Практика/JavaScript#Deduplication запросов|один Promise для одинакового запроса]].
## Чем композиция отличается от наследования?

> [!answer]- Короткий ответ — 30–90 секунд
>
> При композиции объект использует другие объекты или функции для части работы. При наследовании новый класс расширяет базовый и должен подходить везде, где ожидают базовый тип. Если нужно лишь переиспользовать несколько действий, отдельные функции или зависимости часто проще большой иерархии классов.
>
> Загрузка файла, проверка формата и запись в хранилище могут быть отдельными зависимостями сервиса импорта. В тесте заменяют хранилище, не наследуя целую иерархию импортёров. Наследование оправдано, если экземпляры действительно взаимозаменяемы по контракту.
>

> [!followup]- Какие принципы SOLID помогают выбрать композицию или наследование?
>
> Композиция упрощает разделение обязанностей и замену зависимостей. Импортёр может принимать интерфейсы `validate` и `store`, а не наследовать класс, который знает каждый формат и способ записи. Новый валидатор подключается отдельно, тест заменяет только хранилище.
>
> В терминах SOLID здесь полезны единая ответственность, зависимость от контракта и возможность расширять поведение заменой части. Для наследования главный вопрос — подстановка: выполнит ли подтип обещания базового типа для каждого допустимого вызова? Если да, наследование может выразить модель. Если нужны лишь общие несколько строк, функция или компонент обычно связывают части слабее.

> [!followup]- Что принцип подстановки Лисков требует от подтипа?
>
> Клиент базового типа должен работать с подтипом без новых условий и неожиданных результатов. Совместимая сигнатура сама по себе не гарантирует совместимость поведения: подтип не должен требовать больше от входа или обещать меньше на выходе.
>
> Например, если контракт `Storage.save` принимает любой корректный документ и сохраняет его, класс «только для чтения» с методом `save`, который всегда бросает, нарушает этот контракт. Выделите интерфейс `Reader` и отдельно `Writer`, чтобы клиент просил ровно нужное. Если базовый тип явно допускает отказ из-за прав доступа, такой отказ может быть частью контракта; правило определяется обещаниями, а не именем метода.

> [!followup]- Что такое mixin и когда он усложняет композицию?
>
> Mixin добавляет общий набор методов разным типам, не заставляя их наследовать один общий предметный класс. Например, функция принимает базовый класс и возвращает подкласс с методом `dispose` для управления подписками. При этом механизм всё ещё может строиться на наследовании; mixin описывает способ повторно применить поведение.
>
> Следите за конфликтами имён и скрытыми требованиями: если два mixin определяют `dispose`, важен порядок применения и вызов `super`. Если поведение не должно становиться частью публичного типа, проще передать объект очистки в конструктор. Копирование методов через `Object.assign` также не переносит автоматически закрытое состояние класса.

> [!followup]- Как функция высшего порядка помогает компоновать поведение?
>
> Функция высшего порядка принимает функцию или возвращает её. Обёртка может добавить измерение времени, журналирование или проверку аргументов к любому обработчику с согласованным контрактом, не создавая подкласс.
>
> Например, `withTiming(loadUser)` возвращает функцию, которая вызывает `loadUser`, ждёт ответ и пишет длительность в `finally`. Это оставляет результат и ошибку операции доступными вызывающему. Проверьте границу: синхронная обёртка не должна незаметно превращать синхронную функцию в асинхронную; метод может требовать сохранения `this`, а порядок нескольких обёрток влияет на поведение. Например, измерение вокруг retry охватывает все попытки, внутри retry — одну.

> [!followup]- Как различить Strategy, Decorator и Factory при композиции?
>
> Strategy заменяет *способ* работы, Decorator оборачивает существующую работу, Factory решает, *что создать*. Для загрузки данных стратегия может выбирать локальный или удалённый источник. Декоратор измеряет длительность вызова выбранного источника. Фабрика собирает нужный источник с учётом конфигурации.
>
> Выбирать паттерн полезно по вопросу: «чем выполнить?», «что добавить вокруг?» или «как получить экземпляр?». Нередко достаточно функции или параметра конструктора. Важно, чтобы стратегии соблюдали один контракт, декоратор сохранял обещания исходной операции, а фабрика не скрывала зависимости, которые важны для вызывающего кода. Один объект может участвовать во всех трёх ролях в разных местах.

## Что даёт иммутабельность?

> [!answer]- Короткий ответ — 30–90 секунд
>
> При неизменяемом обновлении старая версия данных остаётся прежней, а изменение создаёт новую. Это удобно для сравнения состояния и отмены действий. Обычно копируют только изменённую ветвь, а остальные части используют повторно. Нужна память для новых объектов и единое правило: общие части больше не менять на месте.
>
> При изменении количества в корзине создают новый массив и новый объект изменённой позиции, сохраняя остальные ссылки. Так можно сравнить версии и вернуть предыдущую при отмене. Если вложенные объекты продолжают мутироваться, старый снимок тоже изменится.
>

> [!followup]- Как совместно использовать неизменённые части структуры при обновлении состояния?
>
> Копируйте только контейнеры на пути к изменению. В корзине можно создать новый массив через `map`, заменить изменившуюся позицию объектом `{ ...line, qty: 2 }`, а для остальных вернуть прежние объекты. Корень и изменённая ветвь получат новые ссылки, прежняя версия останется пригодной для отмены.
>
> Это называют structural sharing. Например, `next[0] === prev[0]` для неизменённой позиции помогает не пересчитывать её представление. Копирование обычного массива всё равно обходит его элементы; техника экономит глубокое копирование, а не делает любое обновление O(1). Если затем мутировать общий вложенный объект, изменятся обе версии, поэтому соблюдайте тот же контракт на всех путях записи.

> [!followup]- Когда поверхностное сравнение обнаруживает изменение состояния?
>
> Поверхностное сравнение проверяет непосредственные поля по значению примитива или по ссылке на объект. Оно работает, когда изменение вложенного значения сопровождается новой ссылкой на каждый изменённый контейнер. Если изменить `state.cart[0].qty++` на месте, ссылка на `cart` останется прежней и сравнение её не заметит.
>
> Обратный случай тоже важен: `{ ...state.cart[0] }` без изменения данных создаёт новую ссылку и может вызвать лишний пересчёт. Сохраняйте прежние ссылки для неизменённых частей. Договоритесь, какие поля сравниваются: сравнение корневой ссылки и сравнение непосредственных полей — две разные проверки. Мутация внешним кодом обходит обе, если ссылки не меняются.

> [!followup]- Почему readonly в TypeScript не замораживает объект во время выполнения?
>
> `readonly` ограничивает записи через конкретный тип при компиляции. Оно не меняет дескриптор свойства в JavaScript, не копирует значение и обычно не применяется глубоко. Например, `const view: Readonly<{ settings: { dark: boolean } }> = mutable` запрещает присвоить `view.settings`, но позволяет изменить `view.settings.dark`; изменение через `mutable` тоже видно в `view`.
>
> Для защиты непосредственных собственных свойств во время выполнения есть `Object.freeze`, однако он поверхностный и не превращает `Map` в неизменяемую коллекцию. Если цель — гарантировать старый снимок, нужны договорённость об обновлении, закрытый доступ к изменяемым объектам или целевая копия. Типовая аннотация и runtime-защита решают разные задачи.

### Почему Object.freeze не гарантирует полную неизменяемость?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Он фиксирует собственные свойства одного объекта. Вложенные объекты требуют отдельной обработки; внутреннее состояние некоторых коллекций не защищается так же, как обычные поля. Deep freeze должен учитывать циклы и типы.
>
>
> const value=Object.freeze({nested:{count:0}}) запрещает замену value.nested, но value.nested.count++ остаётся возможным. Object.freeze(new Map()) не запрещает Map.set, потому что записи коллекции не являются обычными собственными свойствами. Для глубокого контракта нужно отдельно определить допустимые типы и обработку циклов.
### Какие операции меняют исходные данные?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Например, push/splice/sort меняют массив; map/filter/slice возвращают другой массив, но его элементы могут ссылаться на те же объекты. Object.assign меняет первый аргумент. Проверяю мутацию в контракте функции.
>
>
> После const copy=items.slice(); copy[0].name='new' изменится и объект в items[0], если это та же ссылка. А copy.push(...) изменяет только новый массив. В тесте проверяю отдельно массив и вложенные объекты; слово «копия» без глубины копирования недостаточно.

> [!followup]- Когда применять toSorted и toSpliced и как учитывать поддержку среды?
>
> `array.toSorted(compare)` возвращает отсортированный массив, а `array.toSpliced(start, count, ...items)` — массив после замены диапазона; исходный массив они не меняют. В отличие от `splice`, `toSpliced` возвращает итоговую коллекцию, а не удалённые элементы. Обе операции поверхностные, поэтому объекты внутри остаются общими.
>
> Например, `[3, 1, 2].toSorted((a, b) => a - b)` даёт `[1, 2, 3]`. Проверьте минимальные браузеры и Node: настройка TypeScript `lib` даёт типы, но не polyfill. Для плотного массива подойдёт `[...items].sort(compare)`; если важны дырки в массиве, проверяйте поведение отдельно, поскольку копирующие методы читают их как `undefined`.

> [!followup]- Что именно защищает Object.freeze и какие данные остаются изменяемыми?
>
> `Object.freeze(obj)` запрещает расширять объект и менять его собственные дескрипторы; собственные поля данных становятся недоступными для записи. В строгом режиме `obj.x = 2` бросит при замороженном `x`. Без строгого режима такая запись обычно игнорируется.
>
> Заморозка поверхностная: у `Object.freeze({ config: { retries: 2 } })` всё ещё можно менять `config.retries`. Setter существующего аксессора может менять другое состояние, а `Object.freeze(new Map()).set('x', 1)` меняет внутренние записи карты. Если нужен неизменяемый снимок, заранее определите, какие значения он содержит, и примените подходящую копию или специализированное представление. Freeze не делает из произвольного объекта «глубоко readonly».

> [!followup]- Как понять, затронет ли мутация другие ссылки на данные?
>
> Присваивание объекта копирует ссылку, поэтому `const b = a; b.items.push(x)` меняет тот же массив, который виден через `a`. Spread меняет только верхний уровень: `const b = { ...a }` даёт новый объект, но `a.items === b.items` по-прежнему истинно.
>
> Если меняете список в новой версии, создайте новый список; если меняете один элемент, создайте и новый объект элемента. Например, `{ ...a, items: a.items.map(updateOne) }` помогает сохранить старый снимок, если `updateOne` не мутирует аргумент. Полная копия нужна только когда требуется разорвать все соответствующие связи; её возможности зависят от типов данных.

## Чем чистая функция отличается от функции с побочными эффектами?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Чистая функция при одинаковых входных значениях возвращает одинаковый результат и не меняет внешнее состояние. Ввод-вывод, чтение времени, случайность и изменение аргументов — побочные эффекты. Их удобно отделять от вычислительного ядра, чтобы проще проверять логику.
>
> Расчёт итоговой цены удобно сделать функцией от товаров и правил скидки, а запрос товаров и запись заказа оставить снаружи. Тесту расчёта тогда не нужны сеть и часы; текущую дату для акции передают явно, если она влияет на результат.
>

> [!followup]- Может ли функция высшего порядка быть чистой?
>
> Да. Сам факт, что функция принимает или возвращает другую функцию, не создаёт побочного эффекта. `const byRate = rate => amount => amount * rate` возвращает вычисление, зависящее только от захваченного тарифа и суммы. Массив `items.map(line => line.qty * line.price)` также не требует внешних эффектов при чистом callback.
>
> Но `map` не делает переданный callback чистым: если callback отправляет запрос или мутирует исходный объект, эффект остаётся. Отдельно оценивайте построение обёртки и вызов возвращённой функции. Например, `withLogging(fn)` может ничего не записывать при создании, но её результат пишет журнал при каждом вызове.

> [!followup]- Почему идемпотентная операция может быть нечистой?
>
> Идемпотентность описывает эффект повторов: после второго одинакового вызова целевое состояние такое же, как после первого. Чистота требует вычисления из аргументов без изменения внешнего состояния. `setEnabled(true)` меняет состояние, но повтор не меняет его дальше. Значит, эта запись может быть идемпотентной и при этом нечистой.
>
> В обратную сторону чистая `x => x + 1` не идемпотентна при композиции: `f(f(1))` отличается от `f(1)`. Для сетевой операции заранее определите, какие эффекты входят в контракт. Установка одного флага может быть идемпотентна для состояния, но отдельное уведомление на каждый вызов сделает повторы заметными.

> [!followup]- Как каррирование и частичное применение помогают выделить чистое вычисление?
>
> Частичное применение фиксирует часть аргументов, например `const withVat = net => total(net, 0.2)`. Каррирование представляет многоаргументную функцию цепочкой одноаргументных: `const total = rate => net => net * (1 + rate)`. В обоих случаях можно заранее зафиксировать правило и переиспользовать расчёт.
>
> Например, UI читает ставку из настроек один раз и передаёт её при создании функции; тест затем вызывает функцию с конкретной суммой без чтения настроек. Замыкание само по себе не гарантирует чистоту: если оно читает изменяемый объект настроек или пишет журнал, результат или эффект может зависеть от внешнего состояния.

## Для чего нужны Proxy и Reflect?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Proxy перехватывает операции над объектом, например чтение и запись. Reflect предоставляет стандартные операции, которые удобно вызвать из перехватчика. На этом можно строить реактивность и адаптеры. Важно соблюдать инварианты объекта и учитывать, что обёртка отличается от исходного объекта по ссылке.
>
> Например, адаптер может журналировать чтение полей и передавать операцию исходному объекту. `Reflect.get(target, key, receiver)` сохраняет получателя операции: getter может прочитать другое поле через тот же прокси. Обёртка не является копией объекта и не должна нарушать ограничения неизменяемых свойств.
>

> [!followup]- Какие операции перехватывают get, set и deleteProperty у Proxy?
>
> Чтение `proxy.key` вызывает ловушку `get`, присваивание — `set`, `delete proxy.key` — `deleteProperty`. В ловушке можно сообщить об изменении и делегировать стандартную операцию через `Reflect.get`, `Reflect.set` или `Reflect.deleteProperty`. Ловушки записи и удаления возвращают признак успеха.
>
> Например, журнал изменений публикует событие удаления только если удаление действительно прошло и поле существовало. Нельзя сообщить об успешном удалении собственного неконфигурируемого поля: движок проверяет инварианты Proxy. В строгом режиме отказ при записи или удалении через синтаксис может стать `TypeError`. Эти ловушки не перехватывают все операции: у `Object.defineProperty` отдельный trap.

> [!followup]- Зачем передавать receiver в Reflect.get и Reflect.set внутри Proxy?
>
> `receiver` — получатель исходной операции. При чтении getter увидит его как `this`, а при записи он важен для вызова setter и правил записи унаследованных свойств. Поэтому прозрачная обёртка обычно делает `Reflect.get(target, key, receiver)`.
>
> Например, у объекта `get label() { return this.name; }` чтение `proxy.label` с правильным receiver приводит к чтению `name` снова через прокси. Если написать `target[key]`, getter получит `target` и внутреннее чтение обойдёт перехватчик. У класса с закрытым полем это поведение требует отдельного решения: прокси не получает приватный бренд исходного экземпляра и такой getter может бросить.

> [!followup]- Почему Proxy может ломать доступ к приватным полям класса?
>
> #field требует, чтобы this был подходящим экземпляром класса. Движок проверяет специальную внутреннюю отметку — приватный бренд. Прокси является отдельным объектом и не получает эту отметку от своей цели. Например, метод `read() { return this.#value; }` работает как `instance.read()`, но может бросить при `new Proxy(instance, {}).read()`, потому что `this` — прокси.
>
> Можно построить узкий адаптер, который вызывает нужные методы с оригинальным экземпляром, или не проксировать этот тип вообще. Автоматическая привязка всех методов к `target` меняет идентичность функций, семантику `this` и может обойти другие traps. Для объектов с внутренними слотами, например `Map`, похожий эффект возникает по другой причине: прокси не получает их внутренние слоты.

> [!followup]- Чем исходный объект отличается от Proxy при сравнении и хранении в коллекциях?
>
> Прокси и его цель — две разные ссылки: `proxy !== raw`. `Map`, `Set` и `WeakMap` различают их как ключи, даже если чтение полей через прокси полностью совпадает. Например, `cache.set(raw, data)` не даст попадания при `cache.get(proxy)`.
>
> На границе подсистемы используйте согласованное представление: ключ по стабильному id или единый способ оборачивать объект. Два вызова `new Proxy(raw, {})` тоже дают разные ключи; фабрика может переиспользовать обёртку через `WeakMap`. Если реактивная библиотека даёт доступ к raw, запись напрямую может обойти её отслеживание, поэтому не храните исходную ссылку как альтернативный путь изменения состояния.

## Чем Number отличается от BigInt?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Number использует числа двойной точности IEEE 754; целые точно представлены только в безопасном диапазоне. BigInt хранит большие целые, но не дроби; его нельзя смешивать с Number в арифметике без явного преобразования. Для денег выбирают согласованную модель округления и представления.
>
> Идентификатор из API, превышающий безопасный диапазон целых, нельзя сначала преобразовать в `Number`: точность уже потеряется. Его передают строкой либо согласованным `BigInt`-представлением. Десятичные деньги нельзя автоматически решить одним BigInt без масштаба и правил округления.
>

> [!followup]- Почему 0.1 + 0.2 не равно 0.3 в JavaScript?
>
> `Number` хранит двоичные числа с конечной точностью. Десятичные 0.1 и 0.2 не представляются точно, поэтому округление входов и суммы даёт `0.30000000000000004`. Это не особенность оператора `+` и не ошибка форматирования строки.
>
> Для приблизительных величин сравнивайте с допустимой погрешностью, выбранной под масштаб данных. `Number.EPSILON` описывает шаг около 1, а не универсальный порог. Для фиксированных денежных единиц можно считать в центах: 10 + 20 = 30, если диапазон целых безопасен. При процентах и делении всё равно нужны правила округления; BigInt сам по себе дроби не хранит.

> [!followup]- Что проверяет Number.isSafeInteger и когда он нужен?
>
> Метод возвращает `true` только для числовых целых от `-(2**53 - 1)` до `2**53 - 1` без приведения типа. В этом диапазоне соседние целые различимы. Например, `Number.isInteger(2**53)` истинно, но `Number.isSafeInteger(2**53)` ложно; `2**53 + 1 === 2**53`.
>
> Проверяйте безопасный диапазон входов и результата, если точность важна: два безопасных числа могут дать небезопасную сумму. Для больших идентификаторов получайте строку или BigInt из исходного представления. Если большой JSON number уже распарсился в округлённый `Number`, проверка может обнаружить проблему, но не восстановит исходные цифры.

> [!followup]- Как передавать BigInt через JSON без потери точности?
>
> Стандартный `JSON.stringify` не сериализует BigInt без явного преобразования. Для API удобен согласованный строковый формат: `{ "total": "9007199254740993" }`. На чтении проверьте, что поле соответствует десятичной грамматике и ограничению длины, затем вызовите `BigInt(value)`.
>
> Например, `9007199254740993n.toString()` сохраняет все цифры, а преобразование в `Number` теряет точность. Для общих объектов можно использовать replacer и reviver с явным тегом типа, но тег может совпасть с обычными данными: схема с известными полями проще. Не преобразуйте все строки с цифрами автоматически: код `"001"` и числовое значение могут иметь разный смысл.

> [!followup]- Как BigInt делит целые и что происходит с остатком?
>
> Деление BigInt отбрасывает дробную часть по направлению к нулю: `5n / 2n === 2n` и `-5n / 2n === -2n`. Остаток имеет знак делимого, например `-5n % 2n === -1n`. Деление на `0n` бросает `RangeError`, а смешивание `5n / 2` — `TypeError`.
>
> Если делите 5 денежных единиц между двумя получателями, результат 2 каждому оставляет 1, которую нужно распределить по согласованному правилу. Для округления вниз отрицательной дроби одного оператора `/` недостаточно: при ненулевом остатке и разных знаках операндов скорректируйте частное. Для денежных расчётов сначала зафиксируйте масштаб и правило округления.

### Что отличает NaN и Infinity от обычных чисел?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Это значения типа number. NaN не равен себе при ===, поэтому применяю Number.isNaN; Number.isFinite проверяет конечность без приведения. Деление number на ноль не всегда бросает исключение.
>
>
> 0/0 даёт NaN, 1/0 — Infinity, -1/0 — -Infinity, и typeof каждого результата равен 'number'. Number.isNaN('x') ложно, а глобальный isNaN('x') истинно после преобразования. Для пользовательского числового ввода проверяю и парсинг, и конечность: Number('') даёт 0, что может нарушать контракт обязательного значения.

> [!followup]- Чем глобальный isNaN отличается от Number.isNaN?
>
> Глобальный `isNaN(value)` сначала приводит вход к числу; `Number.isNaN(value)` проверяет только само числовое значение `NaN`. Например, `isNaN('abc')` даёт `true`, `Number.isNaN('abc')` — `false`, а `isNaN('')` — `false`, потому что пустая строка становится нулём.
>
> Для числового поля сначала проверьте, что непустой ввод соответствует ожидаемому формату, затем преобразуйте и примените `Number.isFinite`, если бесконечность запрещена. `Number.isNaN(Number(value))` сообщает только о неудаче преобразования и не отличает пустой ввод от нуля. Некоторые значения, например `Symbol()`, при неявном приведении глобальным `isNaN` бросают ошибку.

> [!followup]- Когда JavaScript различает -0 и 0?
>
> Строгое равенство считает их равными, но `Object.is(-0, 0)` даёт `false`. Знак заметен, например, при делении: `1 / -0` даёт `-Infinity`. Для `Map` и `Set` ключи `0` и `-0` совпадают; стандартное строковое и JSON-представление тоже обычно теряет знак.
>
> Пример из вычислений: `Math.sign(-0)` возвращает `-0`, поэтому проверка через `=== 0` не различает направление. Если знак не нужен предметной области, нормализуйте оба варианта к нулю перед хранением. Если он важен, например для численной диагностики, проверяйте через `Object.is` и задайте явный формат передачи.

> [!followup]- Как обнаружить переполнение Number и отличить его от потери точности?
>
> `Number.MAX_VALUE * 2` даёт `Infinity`: результат вышел за представимый конечный диапазон. `Number.isFinite` обнаружит это, если по контракту число должно быть конечным. Но потеря точности возможна гораздо раньше: `2**53 + 1` остаётся конечным и округляется до `2**53`.
>
> Например, для целого счётчика проверяйте `Number.isSafeInteger` после вычисления либо используйте BigInt. Для физических величин контролируйте масштаб промежуточных вычислений: `(large * large) / large` может переполниться, хотя эквивалентный результат конечен. Не считайте любое `Infinity` переполнением: его также даёт деление ненулевого Number на ноль.

> [!followup]- Чем Number.parseInt отличается от Number при разборе строки?
>
> `Number.parseInt(text, radix)` читает начальный допустимый фрагмент целого; `Number(text)` требует, чтобы вся непустая строка после пробелов имела допустимую числовую форму. Например, `Number.parseInt('12px', 10)` даёт 12, `Number('12px')` — `NaN`, а для `'1e3'` результаты 1 и 1000.
>
> Префиксный разбор пригоден, если единица измерения уже согласована. Для обязательного целого поля сначала проверьте всю строку и только затем диапазон: `Number(' ')` даёт 0, а `Number('0x10')` — 16, что может быть нежелательно. `parseInt` не подходит для усечения уже числового значения: число сначала превращается в строку, иногда в экспоненциальной записи.

## Что такое обратный вызов и promisify?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Обратный вызов — функция, которую передают другой функции, чтобы та могла вызвать её в нужный момент. promisify оборачивает API с callback: вместо передачи обработчика вызывающий получает Promise и может использовать await. Обёртка должна сохранить способ передачи ошибки, this и нужные результаты. Сам Promise не переносит вычисление в другой поток.
>
> Для старого API с callback вида `(error, result)` обёртка вызывает `reject(error)` при ошибке и `resolve(result)` при успехе. Для многократных событий, например сообщений WebSocket, один Promise не заменяет подписку: он завершится только один раз.
>

> [!followup]- Что означает callback с ошибкой первым аргументом и как его promisify?
>
> У типичного Node callback форма `(err, value)`: при ошибке передают её первым аргументом, при успехе — `null` и результат вторым. Promise-адаптер отклоняет операцию при ошибке и иначе исполняется значением. Например, `util.promisify(fs.readFile)` позволяет ожидать чтение через `await`.
>
> Обёртка должна соответствовать фактическому API: если метод читает `this`, привяжите экземпляр или вызывайте адаптер как метод. Если успешных аргументов несколько, стандартный адаптер может вернуть только первый, и тогда нужен явный контракт или custom promisify. Для событий, где callback вызывается многократно, используйте подписку или async iterable.

> [!followup]- Что делать, если исходный callback может быть вызван несколько раз?
>
> Один Promise примет только первое завершение: второй `resolve` или `reject` не изменит итог. Но второй callback может всё равно выполнить логирование, очистку или другие действия внутри обёртки. Для одноразового API защитите обработчик флагом до побочных эффектов и по возможности диагностируйте нарушение контракта.
>
> Например, после первого результата код удаляет временную подписку. Дублированный callback не должен снова вызывать освобождение или записывать ответ. Если повторные вызовы задуманы (уведомления о ходе загрузки), Promise может описывать только финальный результат, а прогресс отдавайте отдельной подпиской.

> [!followup]- Как после promisify выполнить операции последовательно или параллельно?
>
> Для последовательности запускайте каждую операцию только после предыдущего `await`: `for (const path of paths) await read(path)`. Для независимых операций `await Promise.all(paths.map(path => read(path)))` запускает их до ожидания группы и возвращает результаты во входном порядке.
>
> Если B использует токен из A, сначала дождитесь A. Если это чтение двух независимых файлов, их можно запустить вместе. Уже созданный Promise обычно представляет запущенную работу: массив Promise и последовательное ожидание его элементов не превращают запуск в очередь. Для ограничения параллелизма храните функции, запускающие работу, и отдавайте их фиксированному числу работников.

## Как реализовать интерфейс EventEmitter?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Храню подписчиков по имени события и предоставляю отписку. Явно определяю однократную подписку, порядок вызовов, обработку ошибок и изменение списка во время отправки события. Без отписки обработчики могут удерживать данные и вызываться повторно.
>
> Сервис соединения может публиковать `connected`, `message` и `disconnected`, а экран подписываться только на нужные события. Возвращаемая отписка позволяет закрыть экран без накопления слушателей. Контракт отдельно задаёт, что происходит, если один слушатель выбросил ошибку.
>

>
> Снимок задаёт стабильный набор и порядок вызовов на одно событие. Например, обработчик A удаляет B и добавляет C. Если `emit` итерирует копию, B ещё получит текущее событие, C — только следующее. Без копии результат зависит от способа хранения и того, как коллекция реагирует на изменение во время обхода.
>
> Оговорите контракт явно: иногда нужна отписка с немедленным эффектом, тогда проверяйте активность подписки перед вызовом. Одноразового слушателя удаляйте до его вызова, чтобы рекурсивный `emit` не запустил его повторно. Копирование стоит O(k) на событие с k слушателями; для большинства небольших локальных emitter это простой способ получить предсказуемое поведение.

> [!followup]- Как EventEmitter должен обрабатывать асинхронные слушатели?
>
> Синхронный `emit` вызывает слушателей по порядку и не ждёт их Promise. Например, два `async`-обработчика стартуют в порядке регистрации, но второй может завершиться раньше. Отклонение Promise не становится исключением из `emit`; для фоновых слушателей нужна обработка отказов. Node `EventEmitter` поддерживает `captureRejections` для направления таких отказов в обработчик ошибок.
>
> Если вызывающему нужен итог, предусмотрите отдельный `emitAsync`. Последовательное ожидание сохраняет порядок завершения; параллельный запуск с `allSettled` собирает все исходы, но не гарантирует порядок эффектов. Укажите, должно ли исключение синхронного слушателя остановить отправку остальным.

> [!followup]- Как поддержать шаблоны имён событий в EventEmitter?
>
> Сначала определите простую грамматику, например точное имя `user.created` и `user.*` для одного сегмента. При `emit('user.created')` найдите точных и подходящих шаблонных слушателей, затем вызовите их в согласованном порядке. Снимок подписок предотвращает неожиданное влияние изменений посреди отправки.
>
> Договоритесь, должен ли один callback вызываться дважды, если он подписан и на точное имя, и на шаблон. Для редких событий достаточно просмотреть список шаблонов; при большом потоке полезно индексировать подписки по первому сегменту. Не превращайте пользовательский шаблон напрямую в произвольный RegExp. Если wildcard не нужен реальным потребителям, точные имена и явные подписки проще.

> [!followup]- Как ограничить память, занимаемую подписками EventEmitter?
>
> Сделайте `on` возвращающим функцию отписки и привяжите её к времени жизни владельца. `once` удаляйте до вызова, а пустой список события удаляйте из карты. Иначе ссылка на обработчик удержит его замыкание, например состояние закрытого экрана.
>
> Например, открытие и закрытие окна сто раз не должно оставлять сто слушателей. Проверяйте число подписчиков в повторном сценарии и добавьте диагностический порог. В Node `setMaxListeners` меняет порог предупреждения, а не вводит жёсткий лимит. Если нужны квоты для внешних подписчиков, проверяйте их при регистрации и возвращайте явный отказ; произвольное вытеснение подписки меняет семантику событий.

### Чем event listener отличается от присваивания onclick?

> [!answer]- Короткий ответ — 30–90 секунд
>
> addEventListener допускает несколько обработчиков и управление capture/once/passive/сигнал. onclick задаёт один обработчик свойства. Для removeEventListener нужна та же функция и соответствующий capture.
>
>
> button.onclick=first; button.onclick=second оставляет second в этом свойстве. Два addEventListener с разными функциями сохраняют оба обработчика. Для удаления не требуется тот же объект options, но должны совпасть тип, ссылка функции и capture. passive сообщает, что обработчик не отменяет действие через preventDefault; это не делает тяжёлый callback быстрым.
### Почему повторный listener может давать двойное действие?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Каждая регистрация новой функции создаёт отдельную подписку. При повторном создании без отписки событие вызывает несколько обработчиков. Проверяю время жизни и идентичность функций, а не добавляю флаг в обработчик.
>
>
> Два addEventListener('click', sameHandler) с одинаковым capture не создают две одинаковые регистрации. А () => save() при каждом mount — новая функция, поэтому регистрируется отдельно. Проверяю несколько переходов на экран и обратно: один клик должен давать один вызов, а после ухода глобальный обработчик не должен оставаться активным.
## Что такое строгий режим?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Строгий режим запрещает ряд небезопасных исторических правил: неявное создание глобальной переменной становится ошибкой, отдельный вызов обычной функции получает undefined в this. Другие неоднозначные операции тоже могут вызвать исключение. Модули ESM и тела классов работают в строгом режиме.
>
> Опечатка `selectedId = id` без объявленной переменной в ESM вызовет ошибку, вместо случайного создания глобального состояния. Поэтому проблема обнаруживается в месте записи, а не проявляется позже как конфликт между экранами.
>

**Уточнения**

- Как строгий режим меняет поведение delete?
- Что произойдёт при записи в readonly-свойство в строгом режиме?
- Чем строгий режим классического скрипта отличается от режима ESM?

> [!followup]- Как строгий режим меняет поведение delete?
>
> `delete obj.key` удаляет конфигурируемое собственное свойство. Если свойство неконфигурируемое, строгий режим бросает `TypeError`, а нестрогий обычно возвращает `false`. `delete name` для простой ссылки на переменную в строгом режиме запрещён синтаксически: ошибка возникает до выполнения.
>
> Например, `delete Object.freeze({ x: 1 }).x` в модуле бросит. Чтобы получить логический признак отказа без исключения в обычном случае, используйте `Reflect.deleteProperty(obj, 'x')`. Удаление собственного поля может открыть одноимённое унаследованное свойство; операция не удаляет его из прототипа. Удаление отсутствующего поля обычно успешно и не доказывает, что оно существовало.

> [!followup]- Что произойдёт при записи в readonly-свойство в строгом режиме?
>
> Присваивание свойству с `writable: false` или getter без setter в строгом режиме бросает `TypeError`; в нестрогом коде такая запись обычно игнорируется. Например, у `const state = Object.freeze({ count: 1 })` попытка `state.count = 2` внутри ESM сразу покажет ошибку.
>
> Это правило относится к runtime-дескриптору, а не к `readonly` TypeScript. `Reflect.set(state, 'count', 2)` в обычном случае вернёт `false` и позволит явно обработать отказ. Защита ссылки на поле не защищает вложенные данные: если значение поля — изменяемый объект, его содержимое можно менять без присваивания самому полю.

> [!followup]- Чем строгий режим классического скрипта отличается от режима ESM?
>
> Классический скрипт включает строгий режим директивой `'use strict'` в начале файла или тела функции. ESM всегда строгий и даёт отдельную область видимости верхнего уровня. Тело класса тоже строгое независимо от окружающего скрипта.
>
> В браузерном классическом скрипте верхнеуровневый `this` указывает на глобальный объект даже с директивой, а в ESM он `undefined`. В отдельном вызове обычной строгой функции `this` также `undefined`. При переносе скрипта в модуль глобальные переменные и порядок загрузки нужно проверить отдельно: Node CommonJS оборачивает код файла в функцию, поэтому его верхний уровень отличается от классического браузерного скрипта.

## Когда использовать Symbol?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Для уникальных ключей и стандартных протоколов, например Symbol.iterator. Это позволяет избежать столкновений имён, но не обеспечивает секретность: Reflect.ownKeys возвращает и символьные ключи.
>
> Библиотека может хранить служебные метаданные под своим Symbol, не перезаписывая пользовательское поле с совпавшим строковым именем. Для реализации перебора используется именно стандартный `Symbol.iterator`, а не новый Symbol с похожим описанием.
>

- Чем Symbol.for отличается от Symbol и когда нужен общий ключ?

> [!followup]- Чем Symbol.for отличается от Symbol и когда нужен общий ключ?
>
> `Symbol('name')` создаёт новый уникальный символ при каждом вызове; `Symbol.for('name')` возвращает один символ для одного строкового ключа в общем реестре. Поэтому два модуля могут договориться об одном служебном ключе без передачи ссылки.
>
> Например, для протокола плагинов используйте согласованное имя `Symbol.for('my-app/plugin-meta')` и при диагностике получите ключ через `Symbol.keyFor`. Символ из `Symbol('my-app/plugin-meta')` иметь тот же ключ не будет. Используйте пространство имён, иначе независимый код может выбрать ту же строку. Это не механизм секретности и не способ передавать символы между процессами; реестр не заменяет сериализацию.

> [!followup]- Что происходит с Symbol при сериализации объекта в JSON?
>
> `JSON.stringify` пропускает свойства с символьным ключом. Символьное значение в строковом поле объекта тоже пропускается, в массиве становится `null`, а в качестве корневого значения даёт `undefined` вместо JSON-текста.
>
> Например, `JSON.stringify({ [Symbol('meta')]: 1, x: Symbol('v'), y: 2 })` даст `'{"y":2}'`. Если метаданные нужны получателю, преобразуйте их в согласованное строковое поле или схему с тегами. Описание символа не восстанавливает его идентичность: два `Symbol('v')` различны. Для известного `Symbol.for` можно договориться о передаче ключа реестра, но обычные локальные символы так не кодируются.

> [!followup]- Как стандартные символы подключают объект к протоколам языка?
>
> Движок обращается к заранее определённым символам. `Symbol.iterator` задаёт синхронный перебор, `Symbol.asyncIterator` — асинхронный, `Symbol.toPrimitive` — преобразование к примитиву. Создать `Symbol('iterator')` недостаточно: это другой ключ.
>
> Например, объект диапазона может реализовать `*[Symbol.iterator]() { for (let i = this.start; i < this.end; i++) yield i; }`, и `for...of` будет получать числа по одному. Метод должен выполнять контракт итератора: новый обход обычно получает новый итератор, иначе повторный проход по диапазону может оказаться пустым. Стандартные символы полезны, когда объект действительно должен участвовать в протоколе, а обычный метод достаточно ясен для локального API.

## Как работать с датой и часовыми поясами?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Date хранит момент в миллисекундах от эпохи Unix. Форматирование и календарные операции зависят от часового пояса. В API согласовываю формат, смещение и смысл даты без времени. Сравниваю моменты, а не локально отформатированные строки.
>
> Встреча в календаре — момент с согласованным часовым поясом, а день рождения — календарная дата без времени. Преобразование дня рождения через UTC-полночь может показать предыдущий день в другом поясе; эти два смысла нельзя объединять одним контрактом.
>

> [!followup]- Как переход на летнее время влияет на планирование по местным часам?
>
> При переводе часов местное время может не существовать или встретиться дважды. Например, в Нью-Йорке при весеннем переходе время 02:30 пропускается, а осенью 01:30 бывает дважды с разными UTC-смещениями. Одного `'01:30'` недостаточно, чтобы выбрать момент.
>
> Для расписания храните календарное время и идентификатор зоны, например `America/New_York`; при расчёте очередного запуска применяйте явную политику для пропуска и повтора. Для прошедшего события храните точный момент. Не вычисляйте локальную встречу прибавлением 24 часов к прошлой: в день перехода местное время сдвинется. Тестируйте даты по обе стороны перехода в выбранной зоне.

> [!followup]- Что стоит хранить в UTC, а что требует календарной даты или часового пояса?
>
> UTC удобен для точных моментов: время отправки запроса или оплаченной покупки храните как epoch либо ISO-строку с `Z`. Например, `2025-01-10T12:00:00Z` обозначает один момент независимо от настроек компьютера; часовой пояс выбирается при показе.
>
> Дата рождения `2000-01-10` означает день календаря, поэтому добавлять полночь UTC и потом переводить её в локальный пояс не нужно. Повторяющаяся встреча «09:00 по Берлину» требует и местного времени, и зоны, поскольку смещение меняется. Согласуйте формат на границе API: строка без явного смещения неоднозначна для полей, которые должны означать момент.

> [!followup]- Как форматировать один момент для разных пользователей через Intl.DateTimeFormat?
>
> Передайте форматтеру локаль, зону и нужные части: `new Intl.DateTimeFormat('ru-RU', { timeZone: 'Asia/Yekaterinburg', dateStyle: 'medium', timeStyle: 'short' })`. Он отобразит момент в заданной зоне без изменения исходного `Date`. При выводе таблицы переиспользуйте один форматтер для одинаковых настроек.
>
> Например, `12:00Z` будет показано как `17:00` в Екатеринбурге. Если части даты нужны отдельным элементам интерфейса, используйте `formatToParts`; не разбирайте локализованную строку обратно как дату. Локаль определяет оформление, а `timeZone` — отображаемое календарное время. Форматтер не превращает строку без зоны в однозначный момент.

> [!followup]- Почему прибавить календарный день не всегда значит прибавить 24 часа?
>
> Календарное «завтра в то же местное время» вычисляется по дате и зоне. «Через 24 часа» прибавляет фиксированную длительность к моменту. В Нью-Йорке с 12:00 8 марта до 12:00 9 марта 2025 года прошло 23 часа из-за перехода часов; через ровно 24 часа было бы 13:00.
>
> Для срока действия токена используйте длительность или момент истечения. Для ежедневного напоминания вычисляйте следующий местный календарный день в нужной зоне. `Date.setDate` использует зону окружения, а не произвольную выбранную зону; для расписания в другой зоне нужен подходящий календарный API или библиотека.

## Почему eval и Function нежелательны для пользовательских выражений?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Они исполняют код, усложняют анализ и создают риск внедрения. Для ограниченной грамматики нужен парсер и интерпретатор разрешённых операций. CSP может блокировать динамическую компиляцию.
>
> Для пользовательской формулы цены разрешают числа, переменные и выбранные арифметические операции. Парсер строит выражение, интерпретатор вычисляет только разрешённые узлы; `eval` дал бы формуле возможность выполнять произвольный JavaScript.
>

**Уточнения**

- Как рекурсивный разбор заменяет eval для арифметической формулы?
- Как задать разрешённые операции и переменные в интерпретаторе выражений?

> [!followup]- Как рекурсивный разбор заменяет eval для арифметической формулы?
>
> Разбейте текст на токены, затем разберите ограниченную грамматику: выражение складывает термы, терм умножает множители, множитель — число, переменная или выражение в скобках. В скобках вызывается разбор выражения рекурсивно. Так получается AST, который можно вычислить разрешёнными операциями.
>
> Например, `2 * (price + 1)` превращается в умножение числа на узел сложения. При `price = 3` интерпретатор вернёт 8. Доступа к свойствам, вызовов функций и произвольного JavaScript в грамматике нет. Проверьте, что разобран весь ввод, а не корректный префикс. Ограничьте длину и вложенность, чтобы глубоко вложенные скобки не исчерпали стек.

> [!followup]- Как задать разрешённые операции и переменные в интерпретаторе выражений?
>
> Разрешайте только явно перечисленные виды узлов и операторы. Например, число, именованная переменная и бинарные `+`, `-`, `*`, `/`. Интерпретатор обрабатывает известный оператор через `switch`, а переменную ищет по точному имени в `Map` разрешённых значений. Не выполняйте фрагменты текста как код.
>
> Например, `price * qty` допустимо при двух переданных числах, а неизвестное имя, обращение к свойству или вызов функции парсер отвергает. Дополнительно определите семантику деления на ноль, числовой диапазон и ограничения размера AST. Список разрешённых имён сам по себе не делает произвольный JavaScript безопасным: именно ограниченная грамматика исключает лишние действия.

> [!followup]- Как интерпретатор формул должен сообщать о некорректном вводе?
>
> Различайте ошибку синтаксиса, неизвестное имя и ошибку вычисления. Например, `2 * )` — ожидается выражение на позиции закрывающей скобки; `price + tax` при неизвестной `tax` — ошибка имени; `1 / 0` — ошибка вычисления, если бесконечность запрещена контрактом.
>
> Парсер должен либо разобрать весь текст, либо вернуть диагностируемый отказ с позицией. Не вычисляйте частично разобранное выражение и не возвращайте ноль вместо ошибки: такой результат может стать ценой заказа. На входе ограничьте размер и глубину; на выходе проверьте числовой диапазон. В интерфейсе можно подчеркнуть проблемный токен и оставить исходный ввод для исправления.

## Как отправить много запросов, выполняя не больше трёх одновременно?

**ID вопроса:** Как безопасно ограничить параллелизм?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Запускаю не больше N активных операций и выдаю следующую после завершения одной. Отдельно задаю порядок результатов, остановку после ошибки, отмену, ограничение времени и поведение пустого входа. Promise.all уже запущенных операций не ограничивает их.
>
> Для загрузки 100 файлов можно держать не более трёх активных запросов, беря следующий из очереди после завершения одного. В очередь передают функции запуска, а не уже созданные Promise: иначе все запросы стартуют до ограничения.
>

Изучить: [[Собеседования/Практика/JavaScript#Ограничение конкурентности|работающий Promise pool]].

**Уточнения**

> [!followup]- Как ограничение конкурентности создаёт backpressure для поставщика запросов?
>
> Пусть работник запрашивает следующее задание, только когда освободилось место. Для `AsyncIterable` диспетчер держит не больше трёх выполняющихся задач и продолжает чтение по мере их завершения. Так медленная сеть естественно замедляет чтение следующей порции вместо роста очереди в памяти.
>
> Если поставщик сам отправляет события, остановка чтения недостаточна: нужен протокол паузы, ограниченный буфер или явная политика переполнения. Например, задачи из читаемого файла можно запрашивать по мере освобождения слотов, а неконтролируемый поток метрик — агрегировать или сбрасывать по контракту. Ограничение активных запросов и лимит задач в ожидании — разные настройки.

> [!followup]- Что класть в очередь и как из неё запускать не более трёх запросов?
>
> Кладите функции запуска или описания задач, не готовые Promise. Диспетчер берёт первые три задания, а при завершении любого освобождает слот в `finally` и берёт следующее. Для фиксированного массива достаточно общего индекса и трёх работников; индекс нужно увеличить до `await`.
>
> Например, после запуска A, B и C первым заканчивается B, поэтому запускается D, даже если A ещё активна. Если нужен результат во входном порядке, пишите его по исходному индексу. Отдельно задайте поведение ошибки: остановить новые задачи или продолжить; уже начатые задачи не остановятся сами. При пустом входе очередь сразу возвращает пустой результат.

> [!followup]- Как учитывать повторные попытки в ограничении на три одновременных запроса?
>
> Определите, ограничиваете ли вы *логические задания* или *активные сетевые попытки*. В простой схеме каждый из трёх работников ведёт задание до конца и держит свой слот даже во время задержки перед повтором. Это сохраняет лимит и упрощает состояние, но может временно оставить сеть без работы.
>
> Если лимит относится только к запросам, после ошибки освободите сетевой слот, запланируйте повтор на будущее и пропустите его через тот же диспетчер. Не запускайте повтор напрямую из таймера: тогда активных попыток может стать больше трёх. Общий дедлайн, максимум попыток и сигнал отмены должны относиться ко всему заданию, включая ожидание повтора.

> [!followup]- Означают ли три активных запроса три сетевых соединения?
>
> Нет. Пул ограничивает число задач в коде, а транспорт управляет соединениями отдельно. HTTP/2 может выполнять несколько запросов параллельно по одному соединению, HTTP/1.1 может использовать несколько или ждать свободного соединения. Браузер и клиентская библиотека имеют собственные ограничения и политики переиспользования.
>
> Например, три одновременных `fetch` на один HTTP/2 origin могут стать тремя потоками одного соединения. Если цель — ограничить нагрузку приложения, считайте активные запросы. Если цель — ограничить сокеты на сервере, настраивайте транспортный пул и измеряйте соединения. Учтите чтение тела ответа: слот, освобождённый после одних заголовков, может не ограничивать активные загрузки.

## Чем итеративный обход отличается от рекурсивного?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Рекурсия хранит незавершённые вызовы на стеке; итеративный обход использует цикл, явный стек или очередь. Для рекурсии нужны условие завершения и учёт глубины. Более короткая запись не защищает от переполнения стека.
>
> Дерево категорий с неизвестной глубиной можно обходить явным стеком. Если нужны переходы по уровням, используют очередь. Для графа добавляют множество посещённых узлов, иначе цикл в данных не даст обходу завершиться.
>

**Уточнения**

- Когда выбрать итеративный DFS, а когда BFS?
- Как избежать зацикливания при итеративном обходе графа?
- Почему нельзя полагаться на оптимизацию хвостовых вызовов в JavaScript?

> [!followup]- Когда выбрать итеративный DFS, а когда BFS?
>
> DFS идёт вглубь и хранит стек незавершённых ветвей; BFS обходит по слоям и хранит очередь фронта. Для поиска кратчайшего пути по числу рёбер в невзвешенном графе BFS подходит: узел впервые достигается с минимальным расстоянием. Для полного обхода глубокого дерева DFS с явным стеком убирает риск переполнения стека вызовов.
>
> Например, для проверки существования категории можно взять DFS, а для поиска ближайшего предка по неориентированным связям — BFS. В графе оба требуют учёта посещённых; для BFS лучше не делать `shift()` на длинном массиве, а использовать индекс головы или кольцевую очередь. Для взвешенных рёбер BFS минимизирует только число переходов.

> [!followup]- Как избежать зацикливания при итеративном обходе графа?
>
> Помечайте вершину посещённой при добавлении в стек или очередь, чтобы не планировать её повторно. Например, в цикле A → B → C → A последнее ребро ведёт к уже отмеченной A и не создаёт нового задания. Время обхода с представлением списками смежности — O(V + E) для достижимой части.
>
> Если цель не просто завершить обход, а определить наличие направленного цикла, одного `visited` мало: переход к полностью обработанной вершине может быть обычной общей ветвью. Для DFS различайте активные вершины текущего пути и завершённые; ребро в активную вершину обнаруживает цикл. Ключ посещения должен соответствовать идентичности вершины.

> [!followup]- Почему нельзя полагаться на оптимизацию хвостовых вызовов в JavaScript?
>
> Хвостовой вызов — это вызов, после которого функция сразу возвращает его результат: `return loop(next)`. В `return 1 + loop(next)` нужно сохранить кадр для сложения, поэтому вызов не хвостовой. ECMAScript описывает хвостовые позиции, но поддержку в конкретной среде нельзя считать универсальной.
>
> Например, хвостовой обход списка на сотни тысяч элементов может завершиться переполнением стека в одной из целевых сред. Для линейного обхода перепишите его циклом; для дерева используйте явный стек. Проверка на небольшом входе не подтверждает безопасность при глубоком вводе, а синтаксис `return` сам по себе не гарантирует хвостовую позицию.

### Почему глубокая рекурсия опасна даже при O(n)?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Количество операций может быть линейным, но глубина вызовов расходует стек, ограниченный средой выполнения. Для длинной цепочки использую итеративный обход и явно храню состояние.
>
>
> Обход связного списка из n узлов рекурсией одновременно удерживает n кадров вызова, поэтому имеет O(n) дополнительной памяти стека. Цикл по next делает тот же линейный проход с O(1) служебной памятью. Для дерева явный стек сохраняет нужные ветви и позволяет контролировать рост; проверяю длинную цепочку отдельно от широкого неглубокого дерева.
## Что проверять при ревью JavaScript?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Сначала выясняю, что функция должна принимать и возвращать. Затем проверяю, не меняет ли она общие данные, правильно ли ждёт асинхронную работу, передаёт ошибки и освобождает ресурсы. После этого оцениваю понятность кода и стоимость выполнения. Спорное поведение разбираю на небольшом примере.
>
> В поиске проверяю не только правильный `fetch`, но и последовательность: ввод A → ввод B → ответ B → ответ A. Если старый результат способен заменить новый, корректность отдельных вызовов не спасает весь сценарий.
>

- Как затенение переменной может скрыть ошибку при ревью?

> [!answer]- Если попросят подробнее — перенос после return
>
> **Короткая проверка ASI:** предскажи результат `return` с переносом перед объектом. Перенос может завершить return; форматирование и lint предотвращают такой дефект. Знать эту ловушку полезно при чтении кода, отдельного экзамена на правила вставки `;` не требуется.

> [!followup]- Как обнаружить пропущенный return при ревью JavaScript?
>
> Проверьте каждую ветку функции, результат которой использует вызывающий. У стрелки с блоком результат нужно вернуть явно: `items.map(x => { x.id; })` создаёт массив `undefined`, а `items.map(x => x.id)` — массив идентификаторов.
>
> В цепочке Promise пропущенный `return` особенно коварен: `then(() => { save(); })` не ждёт сохранение, и следующая ступень может показать успех раньше времени. `then(() => save())` передаёт ожидание и ошибку дальше. Явный возвращаемый тип, линтер и тест с отложенным Promise помогают, но намеренное действие без результата, например `forEach`, не требует `return`.

> [!followup]- Какие ошибки вызывают проверки на falsy-значения?
>
> `if (!value)` и `value || fallback` считают отсутствующими также `0`, `false`, `''` и `NaN`. Например, `pageSize || 20` заменит явно заданный ноль, хотя ноль может означать «не загружать». Если отсутствие выражается `null` или `undefined`, используйте `value ?? 20` или явную проверку.
>
> Выбирайте проверку по смыслу: для обязательного имени пустая строка может быть недопустима, а `NaN` у числового поля нужно отдельно отклонить через `Number.isFinite`. Наличие ключа в `Map` проверяйте через `has`, когда `undefined` — допустимое сохранённое значение. Проверяйте примеры с нулём, пустой строкой и false.

> [!followup]- Как затенение переменной может скрыть ошибку при ревью?
>
> Внутренняя переменная с тем же именем перекрывает внешнюю в своей области видимости. Например, `let result; if (ok) { const result = parse(text); } return result;` всегда возвращает внешнее `undefined`, хотя внутри вычисление выполнено.
>
> При ревью проследите, какое объявление читает или меняет каждая ветка. Здесь можно вернуть результат прямо из `if` или присвоить внешней переменной без повторного объявления. Запрет затенения в линтере помогает поймать случайность, но не заменяет осмысленные имена и проверку потока данных. Вложенный параметр с тем же именем может быть намеренным; опасно прежде всего там, где код выглядит как запись в уже существующее состояние.

> [!followup]- Как заметить неограниченный кеш и выбрать ограничение?
>
> Спросите, сколько разных ключей может появиться за жизнь процесса и что удаляет запись. `new Map()` с ключом из каждого поискового запроса будет удерживать результаты даже после закрытия страницы, если карта живёт в модуле. Повторное использование небольшого набора в тесте эту проблему не показывает.
>
> Выберите лимит по числу или весу записей, политику вытеснения и при необходимости срок свежести. `WeakMap` годится, когда ключи — объекты и запись должна жить не дольше ключа, но не ограничивает память, пока объекты достижимы. Для проверки прогоните поток разных ключей и убедитесь, что лимит соблюдается, а вытесненный результат можно безопасно вычислить заново.

## Как повторять неудачный запрос и когда прекратить попытки?

**ID вопроса:** Как организовать повторные попытки?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Повторяю только допустимые операции с ограниченным числом попыток, общим сроком, увеличением задержки и случайным разбросом. Для записи сначала обеспечиваю безопасность повторения. Учитываю Retry-After и отмену; бесконечные повторы могут перегрузить сервис.
>
> После временного отказа чтение списка можно повторить с увеличенной задержкой. Повтор создания заказа требует согласованного ключа идемпотентности и проверки результата: потерянный ответ не означает, что сервер не создал заказ.
>

Изучить: [[Собеседования/Практика/JavaScript#fetchRetry с задержкой|простой повтор GET и дополнительные условия]].

**Уточнения**

- Как повторять запрос после HTTP 429 или 503?
- Почему сетевой таймаут после записи не означает, что её можно повторить?
- Что включить в бюджет повторных попыток запроса?
- Как circuit breaker останавливает запросы к неисправному сервису?

> [!followup]- Как повторять запрос после HTTP 429 или 503?
>
> `429 Too Many Requests` сигнализирует об ограничении частоты, `503 Service Unavailable` — о временной недоступности. Если сервер передал `Retry-After`, учитывайте его: это число секунд или HTTP-дата. Когда требуемая пауза выходит за дедлайн, завершите операцию, а не повторяйте раньше.
>
> Например, чтение списка после `429` с `Retry-After: 10` можно повторить не раньше чем через 10 секунд, если пользователь ещё ждёт. Без заголовка используйте ограниченную растущую задержку со случайным разбросом. `fetch` вернёт HTTP-ответ на 429/503, поэтому проверьте статус сами. Допустимость повтора всё равно зависит от идемпотентности операции и общего бюджета.

> [!followup]- Почему сетевой таймаут после записи не означает, что её можно повторить?
>
> Таймаут описывает отсутствие ответа у клиента. Сервер мог не получить запрос, ещё обрабатывать его или уже зафиксировать изменение. Например, заказ создан, но соединение оборвалось до ответа; повтор обычного POST создаст второй заказ.
>
> Используйте один идентификатор намерения для всех попыток, если сервер поддерживает идемпотентный ключ: он должен связать ключ с запросом и итогом, а не просто принять заголовок. Другой вариант — узнать состояние по известному идентификатору и продолжить по ответу. Если безопасного способа нет, сообщите, что результат не удалось подтвердить. Таймаут клиента или `abort()` сами по себе не откатывают серверную запись.

> [!followup]- Что включить в бюджет повторных попыток запроса?
>
> Ограничьте не только количество повторов, но и общее время операции: сетевые ожидания, очереди и задержки между попытками. Например, при общем дедлайне 5 секунд нельзя запустить очередную попытку на 4 секунды после того, как уже потрачено 4.5 секунды. Перед каждым повтором проверяйте оставшееся время и отмену.
>
> Определите, что считается попыткой: «до трёх» обычно включает начальный запрос. Учитывайте `Retry-After` и выбранные коды ошибок. Передавайте дедлайн через уровни, чтобы клиент, API и прокси не тратили отдельный полный бюджет каждый. Ранний успех останавливает таймеры, а ошибка валидации завершает операцию сразу.

> [!followup]- Как circuit breaker останавливает запросы к неисправному сервису?
>
> При серии отказов circuit breaker переходит в открытое состояние и временно отклоняет новые вызовы без похода в сервис. После паузы он допускает ограниченное число проверочных запросов; если сервис восстановился, обычный трафик возобновляется, иначе пауза начинается снова.
>
> Например, при длительных таймаутах сервиса рекомендаций страница может показать основной контент без рекомендаций. Это защищает очередь и освобождает время на исправные части. Не открывайте breaker на ожидаемых доменных отказах вроде неверных аргументов. Порог, окно и область действия выбирайте по метрикам; breaker дополняет таймауты и бюджет повторов, но не делает небезопасную запись пригодной для повторения.

## Что такое деструктуризация и значения по умолчанию?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Деструктуризация извлекает свойства или элементы. Значение по умолчанию применяется при undefined, но не при null. Остаточный параметр собирает оставшиеся значения. Обычное извлечение значения из реактивного объекта может потерять связь с последующей заменой свойства.
>
> В `const { pageSize = 20 } = settings` явный `null` не станет `20`. Если контракт считает `null` отсутствием, это обрабатывают отдельно. При редактировании реактивных настроек извлечённое число также не сохраняет связь с последующей записью в исходный объект.
>

**Уточнения**

- Как задать значения по умолчанию при вложенной деструктуризации?
- Как переименовать переменную при деструктуризации и задать ей значение по умолчанию?
- Может ли деструктуризация вызвать getter и побочный эффект?
- Когда срабатывает параметр по умолчанию и как совместить его с деструктуризацией?

> [!followup]- Как задать значения по умолчанию при вложенной деструктуризации?
>
> `const { page: { size = 20 } = {} } = settings;` задаёт 20 для отсутствующего `size` и подставляет пустой объект, если `page` отсутствует или равен `undefined`. Но при `{ page: null }` извлечение свойства бросит: значение по умолчанию не срабатывает для `null`.
>
> Если контракт допускает оба вида отсутствия, разделите шаги: `const { size = 20 } = settings.page ?? {};`. Теперь `page: null` обработается, но `size: null` останется `null`, пока не примените отдельное правило. Для данных из API сначала проверьте, что `settings` имеет ожидаемую форму; вложенная деструктуризация сама не является валидатором.

> [!followup]- Как переименовать переменную при деструктуризации и задать ей значение по умолчанию?
>
> `const { pageSize: size = 20 } = settings;` читает свойство `pageSize` и создаёт локальную переменную `size`. Переменной `pageSize` это объявление не создаёт. Если `settings.pageSize` равен `undefined`, результат — 20; при явном нуле результат — 0.
>
> Переименование удобно при двух источниках: `const { id: userId } = user; const { id: orderId } = order;`. Ключи исходных объектов остаются прежними, и изменение локальной переменной не записывает свойство обратно. Если извлечённый результат является объектом, его ссылка всё ещё общая, поэтому мутация его полей видна через источник.

> [!followup]- Может ли деструктуризация вызвать getter и побочный эффект?
>
> Да. Деструктуризация читает свойства обычным способом, поэтому getter или `get`-ловушка Proxy может выполниться, вернуть значение или бросить. Например, `const { profile } = source` сразу вызывает getter `profile`, даже если переменная будет использована позже.
>
> Значение по умолчанию применяется после чтения: `const { profile = empty } = source` не обойдёт getter, а подставит `empty` лишь при результате `undefined`. Rest-часть читает оставшиеся собственные перечисляемые свойства, что тоже может вызывать getters. Не считайте деструктуризацию произвольного объекта чистым копированием; для конфигурации с эффектами удобнее явный метод или одна контролируемая операция чтения.

> [!followup]- Когда срабатывает параметр по умолчанию и как совместить его с деструктуризацией?
>
> Внешнее значение по умолчанию подставляет объект, а внутреннее — его поле:
>
> ```js
> function list({ limit = 20 } = {}) {
>   return limit;
> }
>
> list();                  // 20
> list(undefined);         // 20
> list({});                // 20
> list({ limit: 0 });       // 0
> list({ limit: null });    // null
> list(null);              // TypeError
> ```
>
> Значения по умолчанию срабатывают только для `undefined`. Поэтому `null` в поле сохраняется, а попытка разобрать сам `null` как объект вызывает ошибку.
>
> Выражение параметра вычисляется при каждом вызове, где нужен default, и может обращаться к параметрам слева. Например, `function range(start, end = start + 1)` использует конкретный `start`. Для внешнего API уточните, считаются ли null и undefined одинаковыми, и нормализуйте их явно; не пытайтесь исправить неверную форму только значениями по умолчанию.

## Чем частичное применение отличается от каррирования?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Частичное применение фиксирует некоторые аргументы функции. Каррирование преобразует функцию нескольких аргументов в цепочку функций одного аргумента. Оба приёма помогают композиции, но нужны только тогда, когда делают API понятнее.
>
> Фиксация адреса API или локали в функции создаёт удобную настроенную операцию, например форматирование всех цен одного экрана. Цепочка вида `format(locale)(currency)(amount)` — каррирование; она полезна, только если отдельные ступени действительно переиспользуются.
>

- Как каррировать функцию с переменным числом аргументов?
- Как сохранить this при частичном применении и каррировании метода?

> [!followup]- Почему sum(1)(2) — пример каррирования?
>
> `const sum = a => b => a + b;` превращает сложение двух чисел в две одноаргументные функции. `sum(1)` возвращает функцию, сохранившую 1 в замыкании; вызов с 2 даёт 3. Промежуточный результат можно переиспользовать: `const addOne = sum(1)`.
>
> Если исходная функция `add(a, b)`, обёртка `const addOne = b => add(1, b)` делает частичное применение без переделки исходного API. Для двух аргументов результаты выглядят похоже; для трёх различие видно лучше: каррирование требует `f(a)(b)(c)`, а частичное применение может оставить вызов `partial(b, c)`. Выбирайте форму, которую потребители будут использовать регулярно.

> [!followup]- Почему function.length не всегда подходит для автоматического каррирования?
>
> `fn.length` считает параметры до первого значения по умолчанию; rest-параметр не учитывается. Например, у `function price(qty, rate = 1, discount) {}` длина 1, хотя функция принимает ещё два полезных значения. Автоматическая обёртка по `length` может вызвать исходную функцию слишком рано.
>
> Если нужен универсальный адаптер, передайте арность явно и определите, допускается ли по несколько аргументов на шаг. Для конкретной функции короткая обёртка часто яснее, например `qty => rate => discount => price(qty, rate, discount)`.

> [!followup]- Как каррировать функцию с переменным числом аргументов?
>
> Нужен явный сигнал окончания: из `sum(1)(2)` невозможно узнать, появится ли ещё `(3)`. Можно договориться о завершающем вызове без аргументов — `sum(1)(2)(3)()` — или о методе `result()`. Другой вариант — передать ожидаемое количество аргументов при создании обёртки.
>
> Частичное применение проще, если завершение уже выражено обычным вызовом: `const withOne = (...rest) => sum(1, ...rest)`. Тогда `withOne(2, 3)` сразу даёт итог. Не полагайтесь на `function.length` для rest-функции и не используйте неявное преобразование к числу как завершение, если API должен быть понятным и типизируемым.

> [!followup]- Как сохранить this при частичном применении и каррировании метода?
>
> У JavaScript `this` обычного метода зависит от способа вызова. Если вынести `const f = obj.method` и вызвать его отдельно, получатель потеряется. Для фиксированного объекта можно сделать `const partial = obj.method.bind(obj, firstArg)` или `rest => obj.method(firstArg, rest)`.
>
> Если получатель должен определяться при вызове обёртки, используйте обычную функцию и делегируйте через `fn.call(this, firstArg, ...rest)`. В каррированной цепочке заранее определите, на какой ступени захватывается получатель: например, `obj.prepare(arg)` возвращает стрелку, которая сохраняет `this` первого вызова. Стрелочная обёртка, созданная вне метода, не получит `this` от объекта, на котором её позже вызовут.

## Как выбирать между обратным вызовом, Promise и потоком событий?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Обратный вызов удобен для простого уведомления, Promise — для одного окончательного исхода, Observable — для последовательности событий с подпиской и операторами. Выбор зависит от количества результатов, отмены и обработки ошибок.
>
> Получение профиля имеет один результат и естественно выражается Promise. Состояние соединения и входящие сообщения меняются многократно: для них нужны обработчики или поток с явной отпиской. Превращение первого сообщения в Promise не покрывает весь жизненный цикл.
>

**Уточнения**

> [!followup]- Чем общий источник событий отличается от отдельного запуска на подписку?
>
> Общий источник уже существует или разделяет одну работу: два подписчика на соединение получают сообщения одного WebSocket. Источник на подписку создаёт работу при каждом `subscribe`: две подписки на холодный поток загрузки могут отправить два запроса.
>
> Выберите модель по стоимости и смыслу данных. Для живой ленты обычно нужен общий источник, а для отдельного задания каждого экрана — отдельный запуск. У общего источника решите, кто запускает и останавливает работу и видит ли новый подписчик прошлые значения. Разделение подписки не означает replay: без отдельной политики новый подписчик может получить только следующие события.

> [!followup]- Что должна делать функция unsubscribe и когда её вызывать?
>
> `unsubscribe` прекращает доставку данных этому потребителю и освобождает принадлежащие подписке ресурсы: снимает listener, очищает таймер или отменяет принадлежащий ей запрос. Вызывайте её при завершении компонента или смене источника. Повторный вызов должен быть безопасен.
>
> Например, при выборе другого чата снимите старую подписку до регистрации новой, чтобы сообщения старого чата не попадали в экран. Если источник общий, отписка одного потребителя не обязана закрывать WebSocket; это делает владелец источника или правило последней подписки. Уже запущенный callback может продолжиться после отписки, поэтому долгие обработчики дополнительно проверяют актуальность перед записью результата.

> [!followup]- Как обработать backpressure в потоке событий?
>
> Сначала выясните, может ли потребитель управлять скоростью источника. У pull-протокола, например async iterable, он запрашивает следующий элемент после обработки текущего. У push-источника без паузы нужна политика: ограничить буфер, объединять события, отбрасывать устаревшие либо сохранять их во внешней очереди.
>
> Для координат курсора обычно достаточно последней точки за кадр. Для событий оплаты терять элементы нельзя: нужна надёжная очередь и подтверждение обработки или замедление поставщика. `debounce` может сократить число вызовов, но не даёт универсальной гарантии доставки. Задайте поведение при полном буфере и измеряйте очередь: бесконечное накопление превращает задержку в расход памяти.

> [!followup]- Как отличить терминальную ошибку потока от ошибки отдельного элемента?
>
> У RxJS вызов `error` завершает подписку: после него новых `next` не будет. Если ошибка не должна останавливать остальные данные, передайте её значением вроде `{ ok: false, itemId, error }` либо перехватите внутри операции обработки одного элемента.
>
> Например, сбой чтения одного файла не обязан прерывать импорт остальных; недоступность общего соединения может завершить поток и потребовать новой подписки. В RxJS место `catchError` определяет, завершится ли внутренний запрос или вся цепочка. При повторном подключении отдельно решите, какие данные нужно догнать и как не обработать их дважды; retry не восстанавливает пропущенные события автоматически.

## Как выполнить асинхронные операции строго по очереди?

**ID вопроса:** Что такое последовательное выполнение операций?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Следующая операция начинается после завершения предыдущей. Очередь должна сохранять порядок и учитывать ошибки, чтобы не зависнуть после первого отказа. Политика «оставить только последнее действие» имеет другой смысл и требует отдельного контракта.
>
> Два сохранения одной формы могут прийти на сервер в обратном порядке. Очередь запускает второе после первого, но отдельно решают, продолжать ли после ошибки. Для нескольких клиентов нужна ещё серверная проверка версии: локальная очередь их не координирует.
>

**Уточнения**

- Как собрать последовательную очередь операций на цепочке Promise?
- Как отменять ожидающую и уже запущенную задачу в последовательной очереди?
- Как не допустить бесконечного роста последовательной очереди?

> [!followup]- Как собрать последовательную очередь операций на цепочке Promise?
>
> Храните «хвост» очереди. Каждая новая задача создаёт свой результат через `const result = tail.then(() => task());`. Чтобы отказ не закрыл всю очередь, отдельно обновите хвост: `tail = result.then(() => undefined, () => undefined);`. Вызывающему верните `result`, тогда он увидит собственную ошибку.
>
> Например, если сохранение A отклонилось, B начнётся после его завершения, но A останется отказом для своего обработчика. Начальное значение хвоста — исполненный Promise, а `task` — функция запуска. Если B зависит от успешного A, продолжать нельзя по этому контракту: нужна явная отмена следующих задач или зависимость результатов.

> [!followup]- Как отменять ожидающую и уже запущенную задачу в последовательной очереди?
>
> Ожидающее задание можно убрать или пометить отменённым и пропустить перед вызовом его функции. Уже запущенной задаче передайте `AbortSignal`: она должна обработать сигнал и завершиться. Очередь освобождает слот после фактического завершения, иначе следующая операция начнётся одновременно с ещё работающей старой.
>
> Например, при уходе со страницы снимите ещё не начатое автосохранение и попытайтесь отменить активный запрос. Если сервер уже сохранил данные, отмена клиента этого не изменит. Обязательно завершите Promise удалённого задания согласованным отказом, чтобы вызывающий не ждал бесконечно. Проверка сигнала до запуска закрывает гонку отмены между постановкой и выполнением.

> [!followup]- Как не допустить бесконечного роста последовательной очереди?
>
> Ограничьте число ожидающих заданий или их суммарный вес и задайте, что делать при перегрузке. Можно замедлить поставщика, вернуть «очередь заполнена» или заменить ещё не начатое действие более свежим, если промежуточные версии не важны.
>
> Например, для автосохранения допустимо держать активное сохранение и последний снимок в ожидании, а промежуточные снимки объединять. Для операций списания пропуск недопустим; при переполнении нужен отказ до принятия либо долговечное хранилище. Отслеживайте время ожидания и длину очереди: увеличение буфера само по себе не исправит постоянно более медленного потребителя.

## Что такое прототипное загрязнение?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Необработанные ключи пользовательского ввода могут изменить прототип через небезопасное слияние и повлиять на другие объекты. Нужны валидация схемы, безопасные коллекции и обновлённые зависимости.
>
> Опасен универсальный merge настроек из JSON, разрешающий специальные ключи без проверки. Принимают только поля известной схемы и не допускают небезопасного обхода `__proto__` или `constructor.prototype`; фильтрация одного имени не исправляет любой алгоритм слияния.
>

**Уточнения**

- Почему при слиянии внешних данных учитывают __proto__, constructor и prototype?
- Как проверка собственных свойств помогает при защите от прототипного загрязнения?
- Когда словарь с пустым прототипом защищает от опасных имён ключей?

> [!followup]- Почему при слиянии внешних данных учитывают __proto__, constructor и prototype?
>
> Эти имена связаны с прототипами и могут вести к унаследованным свойствам, если универсальное глубокое слияние обходит произвольные пользовательские пути. Проверка одного `__proto__` не защищает алгоритм, который продолжает идти через унаследованный конструктор.
>
> Для настроек импортируйте известные поля по схеме, например `theme` и `pageSize`, и создавайте результат из этих значений. Для произвольных ключей используйте `Map` или словарь без прототипа, а при обходе объектов проверяйте собственность свойства. Валидацию применяйте на каждом уровне, который разрешено записывать. Вложенный ключ, который входная схема не допускает, должен быть отклонён до операции слияния.

> [!followup]- Как проверка собственных свойств помогает при защите от прототипного загрязнения?
>
> `Object.hasOwn(obj, key)` отличает собственное поле от унаследованного. `key in obj` видит оба, а `obj.hasOwnProperty(key)` может не существовать у словаря без прототипа или быть переопределён. Например, чтение `isAdmin` из входного объекта должно опираться на проверенное собственное булево поле, а не на случайное значение из цепочки прототипов.
>
> Для перебора входа выбирайте `Object.keys` или `Object.entries`, если нужны только собственные перечисляемые строковые поля. Но собственный ключ ещё не означает допустимый: внешний объект может содержать любое имя. Валидация схемы и безопасная запись на стороне получателя остаются обязательными.

> [!followup]- Когда словарь с пустым прототипом защищает от опасных имён ключей?
>
> `Object.create(null)` создаёт словарь без унаследованных методов и аксессоров. Имена вроде `constructor` и `__proto__` можно хранить в нём как обычные собственные ключи, не переходя к прототипу. Например, для динамического индекса групп `dict[group]` читает только собственное значение, если оно было записано.
>
> У словаря нет `hasOwnProperty` и `toString`; используйте `Object.hasOwn(dict, key)` и явное преобразование при необходимости. Защита относится только к этому контейнеру: если затем без проверки переложить поля в обычный объект или начать обход его вложенных значений, опасная запись может появиться снова. Для произвольных ключей и гарантированного порядка часто удобнее `Map`.

## Как освободить таймеры и подписки, созданные внутри функции?

**ID вопроса:** Как определить контракт освобождения ресурсов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Код, создавший таймеры и подписки, должен дать способ их остановить — например, вернуть функцию dispose. В ней снимают обработчики, очищают таймеры и отменяют принадлежащую этому вызову работу. Вызывающий запускает очистку, когда результат больше не нужен. Повторный вызов очистки должен быть безопасным.
>
> Композиционная функция, создавшая таймер и listener, должна связать их с жизненным циклом компонента либо вернуть `dispose`. Повторный вызов освобождения не должен снова менять бизнес-состояние. Удаление визуального элемента не заменяет остановку внешних ресурсов.
>

**Уточнения**

> [!followup]- Что означает идемпотентное освобождение таймеров и подписок?
>
> Повторный `dispose()` оставляет ресурсы в том же освобождённом состоянии и не повторяет побочные действия. Установите признак закрытия перед очисткой, чтобы повторный или рекурсивный вызов сразу вернулся. Остановите таймер, снимите конкретный listener и отмените принадлежащую ресурсу работу.
>
> Например, уход со страницы и обработчик ошибки могут оба вызвать `dispose`; счётчик активных подписок должен уменьшиться один раз. Проверьте гонку: callback, который уже выполняется, иногда может завершиться после очистки. Ему нужен сигнал отмены или проверка `disposed` перед применением результата. Если очистка может завершиться ошибкой, отдельно определите, повторяются ли неудавшиеся шаги.

> [!followup]- Как объединить очистку нескольких ресурсов в один dispose?
>
> Регистрируйте функцию очистки сразу после успешного создания ресурса и вызывайте накопленные функции при завершении. Обратный порядок полезен при зависимостях: снимите слушатель, затем закройте соединение, на котором он зарегистрирован. Очистка должна работать и при частично завершившейся инициализации.
>
> Например, подключение создано, но регистрация второго обработчика бросила; уже зарегистрированные действия всё равно нужно выполнить. После завершения отпустите ссылки на функции очистки. Если действия асинхронны, верните Promise и обеспечьте ожидание вызывающим. Один общий `dispose` принадлежит владельцу ресурсов, а общий для нескольких экранов источник закрывается по своему контракту.

> [!followup]- Что делать, если один из шагов освобождения ресурсов бросил ошибку?
>
> Продолжайте очищать независимые ресурсы, затем сообщите накопленные ошибки. Иначе исключение при закрытии соединения может оставить таймер или DOM-listener активным. Оборачивайте отдельные cleanup-функции, собирайте причины и при необходимости возвращайте `AggregateError`; для зависимых шагов соблюдайте нужный порядок.
>
> Если освобождение выполняется после основной ошибки, не затирайте её исключением из `finally`: сохраните обе причины, а основную оставьте понятной вызывающему. Например, диагностируйте одновременно отказ импорта и отказ закрытия временного файла. Для асинхронного cleanup ждите завершения действий; простое создание нескольких Promise не подтверждает, что ресурсы освобождены.

### Когда нужно возвращать unsubscribe?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда подписка переживает текущий вызов и удерживает обработчик. Возвращённая функция освобождения ресурсов делает время жизни явным и позволяет владельцу компонента завершить ресурс. Не оставляю отписку только на сборщик мусора.
>
>
> Функция subscribe(handler) регистрирует обработчик и возвращает () => listeners.delete(handler). Владелец вызывает её при unmount или смене ресурса; повторный вызов должен быть безопасен. Проверки: после unsubscribe новые события не доставляются, другая подписка продолжает работать, замкнутые ресурсы больше не удерживаются этой регистрацией.
## Когда нужен автомат состояний вместо набора флагов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда комбинации флагов допускают невозможные состояния или переходы трудно проверить. Явно задаю состояния и разрешённые события, включая загрузку, ошибку и отмену. Для простой модели отдельная библиотека не обязательна.
>
> В форме оплаты независимые флаги `loading`, `success` и `error` допускают противоречивые сочетания. Состояния `idle`, `submitting`, `success`, `error` и разрешённые переходы делают правила явными; повторное нажатие в `submitting` можно отклонить.
>

> [!followup]- Как discriminated union описывает допустимые состояния автомата?
>
> Задайте каждой форме уникальный тег и поля только этой формы. Например, `type State = { kind: 'idle' } | { kind: 'submitting'; requestId: number } | { kind: 'success'; orderId: string } | { kind: 'error'; message: string }`. После проверки `state.kind === 'success'` TypeScript знает, что есть `orderId`, а невозможная смесь `success` и `error` не нужна.
>
> Используйте исчерпывающий `switch` с проверкой `never`, чтобы добавление нового состояния требовало обновить обработчики. Тип описывает допустимые снимки состояния, но сам не запрещает переход из `idle` прямо в `success`. Переходы проверяйте в reducer или другом едином месте.

> [!followup]- Как проверить, разрешён ли переход автомата состояний?
>
> Опишите переход функцией от текущего состояния и события. Например, `SUBMIT` из `idle` даёт `submitting`, `RESOLVE` из `submitting` — `success`, а повторный `SUBMIT` во время отправки игнорируется или даёт явный отказ по контракту.
>
> Держите правило в одном reducer, а запуск запроса и другие эффекты снаружи привязывайте к принятому переходу. Тогда тест может перебрать пары «состояние + событие» без браузера и сети. Отдельно решите, что означает неверное событие: ошибка разработчика, устаревшее уведомление или нормальный пользовательский ввод. Тип состояния защищает форму данных, но фактические переходы всё равно зависят от текущего значения.

> [!followup]- Как автомат защищается от устаревшего результата асинхронной операции?
>
> Храните идентификатор операции в состоянии ожидания и включайте его в события завершения. Принимайте результат, только если состояние всё ещё ожидает именно этот id. Например, поиск A начался раньше B, ответ B пришёл первым, а поздний `RESOLVE(A)` не может вернуть состояние к старым данным.
>
> При новой операции отмените старую через сигнал, если это поддерживается, но проверку id сохраните: ответ мог уже прийти или отмена могла не остановить источник. Это защита состояния конкретного клиента. Если операции пишут на сервере, их эффекты требуют отдельного механизма, например версии записи или идемпотентного ключа.

## Что значит идемпотентная функция?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Идемпотентное действие можно повторить без дополнительного изменения целевого состояния: после второго раза оно такое же, как после первого. Это не то же самое, что чистота функции. Операция записи тоже может быть идемпотентной — например, если сервер распознаёт повтор по одному ключу.
>
> Установка `isRead = true` идемпотентна: повтор не добавляет нового эффекта. Увеличение счётчика на единицу — нет, даже если записано чистой функцией. Для математической функции проверяют `f(f(x)) = f(x)`, например при нормализации пробелов.
>

> [!followup]- Почему HTTP PUT считается идемпотентным и что это гарантирует?
>
> По HTTP семантика PUT задаёт состояние ресурса по известному URI. Если клиент дважды отправил одно и то же представление в `PUT /profile/42`, ожидаемый эффект на ресурс соответствует одному запросу. Коды ответа могут отличаться: первый запрос создал ресурс, второй обновил существующий.
>
> Логи и метрики отдельных обращений могут различаться; идемпотентность относится к запрошенному эффекту. Если обработчик вместо установки поля прибавляет значение или повторно отправляет письмо как часть действия, такой контракт не соответствует ожидаемому эффекту PUT. Кроме того, одинаковый повтор может затереть более новую правку другого клиента: для защиты от этого нужны условия вроде `If-Match`.

> [!followup]- Когда идемпотентность разрешает повторить запрос после сбоя?
>
> Когда повтор того же намерения не добавит нового эффекта. Например, если ответ создания заказа потерян, повтор с тем же согласованным ключом позволяет серверу вернуть уже созданный заказ. Ключ должен переживать сетевой повтор, а сервер должен атомарно связать его с результатом и отклонять несовместимое тело для того же ключа.
>
> Идемпотентность делает повтор допустимым, но не обязательным: ошибку формата не исправит ещё один запрос, а истёкший дедлайн останавливает попытки. Проверьте время хранения ключа и поведение параллельных повторов. Для новой операции создайте новый ключ; генерация нового ключа на каждую попытку разрушает защиту.

> [!followup]- Как сделать обработчик повторно доставленного события идемпотентным?
>
> Используйте стабильный id события и фиксируйте обработку атомарно вместе с локальным изменением. Например, в одной транзакции вставьте id в таблицу с уникальным ключом и измените статус заказа. При повторной доставке конфликт уникальности означает, что эффект уже зафиксирован.
>
> Если сохранить id отдельно до эффекта, сбой между шагами потеряет действие; если после — сбой может привести к двойной обработке. Для внешнего вызова одна локальная транзакция этого не решает: нужен идемпотентный контракт получателя или отдельный протокол доставки. Определите срок хранения id по возможному окну повторов и отдельно решите обработку событий, пришедших не по порядку.
