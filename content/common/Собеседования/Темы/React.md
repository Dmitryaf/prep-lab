## Что делает компонент и что такое JSX?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Компонент описывает интерфейс для текущих props и state. JSX преобразуется в описание элементов; строка с тегами внутри выражения остаётся текстом. React вычисляет результат и применяет необходимые изменения к DOM. Запросы и мутации внешних объектов не должны происходить во время рендера.

**Уточнения**
- Почему onClick={save()} отличается от onClick={save}?
- Что покажет 0 && <Panel />?

**Изучить:** [[Фронтенд/React/01. React, компоненты и JSX|объяснение, пример и ограничения]].

> [!followup]- Почему onClick={save()} отличается от onClick={save}?
>
> `onClick={save}` передаёт функцию для будущего клика. `onClick={save()}` вызывает её во время рендера и передаёт результат вызова. Если `save` отправляет запрос или меняет state, действие произойдёт до нажатия и может повторяться при каждом рендере.
>
> Чтобы передать аргумент, используй `onClick={() => save(id)}`. Исключение возможно, когда `save()` намеренно является чистой фабрикой и возвращает обработчик, но это другой контракт. Проверка: после первоначального render сохранений нет; после одного клика — одно. StrictMode помогает обнаруживать нечистый рендер, но не является причиной неправильного вызова.

> [!followup]- Что покажет 0 && <Panel />?
>
> Выражение вернёт число `0`, и React покажет его текстом. Оператор `&&` возвращает один из операндов, а не обязательно boolean; React скрывает `false`, `null` и `undefined`, но числа отображает.
>
> Поэтому `{items.length && <Panel />}` при пустом массиве оставляет на экране ноль. Запиши `{items.length > 0 && <Panel />}` либо `{items.length ? <Panel /> : null}`. Это важно и вне списков: счётчик непрочитанных может законно равняться нулю, поэтому заранее реши, нужно ли отображать число или условно показывать компонент. Простая проверка обоих состояний массива обнаруживает ошибку.

## Как передавать данные и содержимое между компонентами?

**Практика:** [[Собеседования/Практика/React#Контракт поля и композиция|Проверить на задаче]]

**Критерии ответа:** Называю владельца состояния, контракт props и callback, показываю композицию через children и отличаю входное значение от самостоятельного черновика.
**Изучить:** [[Фронтенд/React/02. Props, callbacks и композиция|Механизм, пример и ограничения]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Родитель передаёт данные через props, ребёнок сообщает о действиях через callback props. Общий state находится у общего владельца. children и props с JSX задают содержимое; render prop передаёт данные в функцию построения содержимого. Для поля, которое обновляется извне, value и callback предотвращают появление второй копии имени.

**Уточнения**
- Когда нужен самостоятельный черновик?
- Почему нельзя вызывать Hooks внутри render prop?

> [!followup]- Когда нужен самостоятельный черновик?
>
> Самостоятельный черновик нужен, когда пользователь временно отклоняется от сохранённого значения и может применить или отменить изменения. Например, диалог редактирования имени инициализируется серверным именем, но печать не меняет карточку профиля до успешного сохранения.
>
> Явно определяю момент инициализации: открытие редактора или выбор другой сущности. useState(initialName) использует начальное значение при создании состояния, а не синхронизирует его с каждым новым prop. Безусловный effect, копирующий props в draft, способен затереть ввод при фоновом обновлении. Для той же сущности новые серверные данные обрабатываю по договорённости: принять при отсутствии правок или показать конфликт.
>
> Проверяю: пользователь изменил имя, родитель перерендерился — черновик сохранён; «Отмена» не изменила сохранённое имя; переход к другому пользователю не показывает чужой черновик. Смена key может намеренно сбросить редактор, если потеря прежнего черновика допустима. Обычному управляемому полю без «Применить/Отмена» отдельная копия props обычно не нужна. [Когда state не нужно синхронизировать эффектом](https://react.dev/learn/you-might-not-need-an-effect).

> [!followup]- Почему нельзя вызывать Hooks внутри render prop?
>
> Render prop — callback, который другой компонент может вызвать условно, многократно или вообще пропустить. Вызовы `useState` и `useEffect` внутри него нарушают стабильный порядок Hooks и не создают самостоятельную идентичность компонента.
>
> Вместо `renderItem={item => { const [open] = useState(false); ... }}` создай `Item` с Hook на верхнем уровне и возвращай `<Item item={item} />`. В списке добавь стабильный key сущности. Тогда React управляет состоянием каждой строки как отдельного компонента. Сам callback может вычислять JSX без Hooks; проблема возникает именно при попытке привязать React-состояние к произвольно вызываемой функции.

## Почему после setState значение осталось прежним?

**Практика:** [[Собеседования/Практика/React#Снимок состояния и производные значения|Проверить на задаче]]

**Критерии ответа:** Объясняю снимок состояния конкретного рендера, очередь обновлений и функциональную форму setter; предсказываю результат нескольких обновлений.
**Изучить:** [[Фронтенд/React/03. Состояние и обновления|Механизм, пример и ограничения]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Setter запрашивает следующий рендер, но переменная текущего рендера остаётся его снимком. Два setCount(count + 1) передадут одно и то же число. Два функциональных updater последовательно используют результат предыдущего шага. Функции обновления должны быть чистыми: отправка запроса внутри updater может повториться.

**Уточнения**
- Когда вычисляется начальный state?
- Почему лог после setter не доказывает, что обновления не было?

> [!followup]- Почему лог после setter не доказывает, что обновления не было?
>
> Setter запрашивает обновление, но не переприсваивает переменную текущего вызова компонента. Обработчик продолжает видеть снимок того рендера, в котором был создан.
>
> ~~~js
> // При count === 0:
> setCount(count + 1);
> console.log(count); // 0; следующий рендер получит 1
> ~~~
>
> Проверяю результат через интерфейс после обработки обновления или наблюдаю count в effect с зависимостью [count], если нужно диагностировать применённое состояние. await setCount(...) не помогает: setter не возвращает Promise завершения рендера. Для нескольких прибавлений использую setCount(c => c + 1), чтобы каждый updater получил результат предыдущего.
>
> При установке значения, равного текущему по Object.is, React может пропустить обновление экрана; это отдельная причина. Старый log сам по себе не отличает её от обычного снимка состояния. [Документация useState](https://react.dev/reference/react/useState).

> [!followup]- Когда вычисляется начальный state?
>
> Аргумент `useState` определяет начальное состояние при монтировании. В `useState(buildInitial())` JavaScript вызывает `buildInitial` при каждом рендере, хотя React после первого раза игнорирует переданное начальное значение. Ленивый вариант `useState(buildInitial)` передаёт функцию и избегает этих повторных вычислений.
>
> Инициализатор должен быть чистым: StrictMode в разработке может вызвать его повторно для проверки. Запросы, запись storage и изменение внешних объектов туда не помещают. Новый prop `initialValue` также не переинициализирует существующий state. Для намеренного нового редактора можно сменить key; для обновления действующего черновика нужен отдельный контракт, учитывающий пользовательские правки.

## Почему таймер видит старые props или state?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Таймер замкнул значения того рендера, в котором был создан. Для прибавления к текущему state обычно достаточно функционального setter. Для внешней подписки выбирают пересоздание по зависимостям, ref после commit или подходящий Effect Event. Нельзя просто убрать зависимость: это сохраняет старое замыкание.

**Уточнения**
- Какая версия callback нужна по контракту?
- Может ли функциональный setter обновить произвольный prop?

**Изучить:** [[Фронтенд/React/03. Состояние и обновления#Почему таймер видит старое состояние|объяснение, пример и ограничения]]. [[Фронтенд/JavaScript/02. Области видимости и замыкания/03. Замыкания|Замыкания JavaScript]]

> [!followup]- Какая версия callback нужна по контракту?
>
> Сначала реши, что означает отложенное действие. Подтверждение отправленного сообщения должно использовать снимок текста и адресата на момент отправки. Периодическое уведомление о текущем состоянии, наоборот, может требовать последнюю версию callback.
>
> Для снимка обычное замыкание правильно. Для актуального обработчика внешней подписки подходят пересоздание подписки по зависимостям или Effect Event в поддерживаемой версии React. Ref обновляют после commit, чтобы не публиковать значения незавершённого рендера.
>
> Проверка различает требования: запусти таймер, измени адресата, дождись срабатывания и сравни получателя с заранее выбранным контрактом. «Всегда брать последнее» не исправляет бизнес-ошибку, если действие принадлежит прежнему адресу.

> [!followup]- Может ли функциональный setter обновить произвольный prop?
>
> Нет. `setCount(previous => previous + 1)` получает актуальное предыдущее значение именно `count`. Он не обновляет замкнутые props и не даёт доступ к текущему состоянию родителя.
>
> В `setCount(n => n + step)` значение `n` берётся из очереди обновлений, а `step` остаётся значением рендера, создавшего callback. Если интервал должен учитывать новый `step`, пересоздай его по зависимости либо организуй чтение последнего значения через подходящий механизм.
>
> Prop принадлежит родителю: чтобы изменить его, вызови переданный callback, например `onStepChange(next)`. Функциональный updater полезен для перехода одного state, но не заменяет явное владение данными и корректные зависимости внешних подписок.

## Нужно ли хранить производные данные в state?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Если значение полностью вычисляется из props/state, обычно вычисляй его при рендере. filteredUsers и isEmpty не нужны как независимые состояния рядом с users/query. Второй state создаёт риск рассогласования и лишний цикл через effect. useMemo добавляет кэш вычисления при необходимости, но не является условием корректности.

**Уточнения**
- Когда отдельная копия оправдана?
- Как отличается черновик от производного значения?

**Изучить:** [[Фронтенд/React/03. Состояние и обновления#Один источник и производные данные|объяснение, пример и ограничения]].

> [!followup]- Когда отдельная копия оправдана?
>
> Отдельное состояние оправдано, когда значение может намеренно расходиться с источником. Например, форма редактирует черновик профиля, а сохранённый профиль остаётся прежним до подтверждения. Нужны явные правила «начать редактирование», «сохранить», «отменить» и обработки внешнего обновления.
>
> Для `filteredUsers`, полностью определяемого `users` и `query`, отдельный state обычно избыточен: его вычисляют при рендере. Кэш дорогого вычисления через `useMemo` не превращает результат в самостоятельные данные.
>
> Проверочный вопрос: может ли пользователь законно изменить копию, не изменив источник? Если нет, синхронизирующий effect скорее создаёт вторую точку истины и дополнительный рендер, чем решает задачу.

> [!followup]- Как отличается черновик от производного значения?
>
> Производное значение однозначно вычисляется из текущих входов: итог корзины определяется товарами и количеством. Черновик содержит самостоятельное намерение пользователя: введённый адрес может отличаться от последнего сохранённого адреса.
>
> Поэтому обновление серверного профиля автоматически меняет производное отображение, но не должно молча стирать несохранённый черновик. Для формы сохраняют исходную ревизию и признак изменения, затем предлагают обновить, объединить или отменить правки по продуктовому контракту.
>
> Простой сценарий проверки: пользователь набрал новый телефон, затем фоновый запрос вернул старый. Черновик должен остаться введённым. При смене редактируемого пользователя допустим отдельный reset или новый key; это уже смена сущности, а не вычисление производного значения.

## Как key влияет на состояние компонента?

**Практика:** [[Собеседования/Практика/React#Перестановка строк и черновики|Проверить на задаче]]

**Критерии ответа:** Связываю сохранение состояния с типом, позицией и ключом элемента; разбираю перестановку списка и намеренный сброс состояния.
**Изучить:** [[Фронтенд/React/04. Рендер и идентичность|Механизм, пример и ограничения]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Стабильный key помогает React сохранить экземпляр соответствующей сущности среди соседей. Индекс изменяемого списка может привязать введённый текст к другой строке, случайный key пересоздаёт компонент. Изменение key иногда намеренно сбрасывает редактор. Сначала нужно решить, должен ли черновик сохраняться.

> [!followup]- Какая роль у типа и положения компонента?
>
> State привязан к идентичности компонента в дереве React. Тот же тип на том же месте у родителя сохраняет состояние; смена props сама по себе его не сбрасывает. Замена типа, например Editor на Preview, удаляет прежний компонент вместе с состоянием его поддерева.
>
> Key уточняет положение среди соседей: в списке стабильный id позволяет связать переместившуюся строку с прежним состоянием. Но одинаковый key у разных типов не делает их одним компонентом, а ключ не переносит state между разными родителями.
>
> Проверка: ввести текст в Editor, поменять его title — ввод остаётся; изменить key на id другой записи — редактор начинает с нового начального состояния. Отдельно переставить строки со стабильными ключами: черновики следуют за сущностями. Не объявляю функцию компонента внутри рендера родителя: каждый вызов создаёт новый тип функции и может неожиданно сбрасывать state. [Сохранение и сброс состояния](https://react.dev/learn/preserving-and-resetting-state).

> [!followup]- Почему key не передаётся обычным prop?
>
> `key` используется самим React для сопоставления элементов среди соседей и сохранения их состояния. Он является частью описания элемента, а не входными данными дочернего компонента. Поэтому чтение `props.key` не даёт идентификатор записи.
>
> Если строке нужен ID, передай его отдельно: `<UserRow key={user.id} userId={user.id} />`. Один ID здесь выполняет две разные роли: React сопоставляет экземпляр, а компонент обращается к предметной сущности.
>
> Уникальность key требуется среди соседей данного списка, не во всём приложении. Смена key пересоздаёт состояние компонента; нельзя использовать случайное значение только ради отсутствия предупреждения, иначе ввод и фокус будут сбрасываться.

## Чем render отличается от commit?

**Практика:** [[Собеседования/Практика/React#Диагностика лишних обновлений|Проверить на задаче]]

**Критерии ответа:** Отделяю вычисление результата от изменения DOM, объясняю чистоту рендера и почему вычисление может не завершиться commit.
**Изучить:** [[Фронтенд/React/04. Рендер и идентичность|Механизм, пример и ограничения]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Render вычисляет описание интерфейса, commit применяет согласованный результат. Повторный вызов компонента не означает изменение каждого DOM-узла. Render может быть повторён или отброшен, поэтому должен быть чистым. Состояние сохраняется, пока React узнаёт тот же экземпляр по месту, типу и key.

**Уточнения**
- Почему console.log не измеряет число DOM-изменений?
- Что запускает повторную работу компонента?

> [!followup]- Почему console.log не измеряет число DOM-изменений?
>
> Log в теле React-компонента считает вызовы функции в этой среде, а не применение изменений к DOM. Во время render React вычисляет описание интерфейса; работа может быть повторена или не дойти до commit. Даже завершённый render способен дать тот же результат, поэтому число вызовов не равно числу изменённых узлов.
>
> В development StrictMode дополнительно вызывает render для поиска нечистой логики. Для стоимости обновления использую Profiler и запись браузера, а для фактических DOM-изменений — соответствующее наблюдение, понимая его границы. Например, родитель обновился, ребёнок снова вычислен, но его текст остался прежним. Удаление лишнего log не оптимизирует этот путь. [Render и commit](https://react.dev/learn/render-and-commit).

> [!followup]- Что запускает повторную работу компонента?
>
> В React повторный render связан с обновлением состояния компонента, рендером родителя, изменением читаемого context или подписанного внешнего store. Новое значение props приходит через работу родителя; это не отдельная очередь обновлений самого дочернего компонента. Планировщик может группировать и повторять работу.
>
> Например, родитель хранит поисковый текст и передаёт ребёнку заново созданный объект options. memo может не пропустить такой render из-за новой ссылки; собственный state и context ребёнка тоже не блокируются memo. Сначала профилирую дорогую ветку, затем сужаю владельца состояния и стабилизирую действительно нужные зависимости. Одинаковое значение обновления может быть пропущено React, поэтому обещать ровно один вызов функции на каждый setState некорректно.

## Когда нужен useEffect и зачем очистка ресурсов?

**ID вопроса:** Когда нужен useEffect и зачем cleanup?

**Практика:** [[Собеседования/Практика/React#Ревью подписки и вложенного таймера|Проверить на задаче]]

**Критерии ответа:** Отличаю вычисление интерфейса от синхронизации с внешней системой; объясняю зависимости эффекта, вызов функции очистки и освобождение ресурсов.
**Изучить:** [[Фронтенд/React/05. Эффекты и внешние системы|Механизм, пример и ограничения]] [[Фронтенд/JavaScript/02. Области видимости и замыкания/03. Замыкания|Замыкания JavaScript]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Эффект синхронизирует компонент с внешней системой: подпиской, таймером или виджетом. При смене зависимостей React вызывает прежнюю функцию очистки ресурсов, затем заново выполняет эффект. При удалении компонента освобождается последняя связь. Производное значение обычно вычисляют при рендере, действие пользователя выполняют в обработчике. Очистка должна освобождать именно тот ресурс, который создал эффект.

**Уточнения**
- Почему async setup не подходит?
- Что произойдёт при смене documentId?

> [!followup]- Почему async setup не подходит?
>
> Функция setup, переданная useEffect, должна сразу вернуть функцию очистки либо ничего. async-функция всегда возвращает Promise, поэтому React не получает из неё синхронный cleanup.
>
> Оставляю setup обычной функцией, асинхронную работу запускаю внутри. До её запуска создаю AbortController и флаг актуальности; возвращаемая функция сразу может пометить операцию устаревшей и отменить запрос. Внутренний async-вызов обрабатывает ошибки, а перед записью результата проверяет актуальность. Возврат cleanup из вложенной async-функции тоже не передаст его React.
>
> Проверка: начать загрузку, удалить компонент до ответа, затем завершить Promise — результат не применяется. Если ресурс создаётся только после await, проверяю актуальность и сразу освобождаю поздно созданный ресурс: cleanup мог уже отработать до его появления. [Контракт setup и cleanup](https://react.dev/reference/react/useEffect).

> [!followup]- Что произойдёт при смене documentId?
>
> Если подписка использует documentId, он входит в зависимости эффекта. После commit со сменой A на B React вызывает cleanup прежнего эффекта для A, затем setup для B; при удалении компонента освобождается последняя подписка. Cleanup замыкает конкретный unsubscribe или ресурс своего запуска, а не ищет «текущий документ» в изменяемой переменной.
>
> Проверяю журнал подписок: подключить A → отключить A → подключить B → отключить B при unmount. Отдельно доставляю отложенное событие A после перехода: оно не должно менять данные B. Одного unsubscribe может быть недостаточно для уже запущенной асинхронной обработки, поэтому результат проверяется по актуальности операции. Видимые данные тоже связываю с documentId, чтобы прежнее содержимое не показывалось под заголовком B до выполнения эффекта. [Синхронизация с внешней системой](https://react.dev/learn/synchronizing-with-effects).

## Почему в разработке эффект выполняется повторно?

> [!answer]- Короткий ответ — 30–90 секунд
>
> StrictMode дополнительным циклом подключения и очистки проверяет устойчивость ресурса к повторному подключению. Исправлять нужно очистку, а не скрывать повтор флагом. Дополнительные проверки включают и функции, которые должны быть чистыми. Сообщения в режиме разработки не дают универсальной гарантии числа вызовов в сборке для выпуска.

**Уточнения**
- Останутся ли два активных слушателя?
- Зависит ли проверка от размещения StrictMode?

**Изучить:** [[Фронтенд/React/04. Рендер и идентичность#StrictMode и повторяемость|объяснение, пример и ограничения]].

> [!followup]- Останутся ли два активных слушателя?
>
> После проверочного setup → cleanup → setup в development должен остаться один активный слушатель, если cleanup симметричен setup. Если очистки нет или removeEventListener получает другую функцию, прежняя подписка останется. Два новых callback с одинаковым текстом — разные ссылки.
>
> Например, effect создаёт handleResize, передаёт его в addEventListener и возвращает функцию, снимающую именно handleResize с тем же capture. После окончательного unmount слушателей этого владельца должно быть ноль. Проверяю эффект по событиям и числу активных подписок: один resize — один вызов, после ухода — ни одного. Повторная регистрация точно того же listener с тем же типом/capture дедуплицируется браузером, поэтому слепой подсчёт строк addEventListener тоже недостаточен.

> [!followup]- Зависит ли проверка от размещения StrictMode?
>
> Да. Согласно текущему контракту React, когда StrictMode охватывает корень приложения, development-проверка включает дополнительный цикл Effect setup/cleanup при первом монтировании. Если StrictMode включён только для поддерева, React не выполняет этот начальный дополнительный цикл эффектов: дочерние эффекты без соответствующих родительских не должны создавать проверочную последовательность, невозможную в production.
>
> Другие проверки StrictMode у поддерева сохраняются. Поэтому при диагностике уточняю версию React и место границы, а не обещаю «все эффекты всегда дважды». Отсутствие дополнительного цикла не доказывает правильность cleanup: повторное монтирование в приложении всё равно возможно. Проверяю реальный вход/выход и смену зависимостей. [StrictMode](https://react.dev/reference/react/StrictMode).

## Как выбирать зависимости эффекта?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Dependencies отражают используемые реактивные значения, а React сравнивает их через Object.is. Новый объект или функция могут перезапускать связь. Сначала проверь, можно ли создать объект внутри setup или убрать ненужный effect. Исключение реального входа из массива создаёт устаревшее поведение.

**Уточнения**
- Когда допустим useEffectEvent?
- Почему это не способ обойти exhaustive-deps?

**Изучить:** [[Фронтенд/React/05. Эффекты и внешние системы#Зависимости и замыкания|объяснение, пример и ограничения]].

> [!followup]- Когда допустим useEffectEvent?
>
> `useEffectEvent` подходит для части логики effect, которая должна видеть последние committed props/state, но не должна сама пересоздавать внешнюю связь. Например, подключение чата зависит от `roomId`, а уведомление о подключении использует текущую тему оформления.
>
> Effect Event читает `theme` при вызове; effect сохраняет `roomId` в зависимостях. Смена темы меняет оформление следующего уведомления, не переподключая чат. Смена комнаты обязана переподключить его.
>
> API используют в поддерживаемой версии React и с подходящим eslint-plugin-react-hooks. Возвращённую функцию вызывают из effect-логики, включая зарегистрированный там callback, а не передают как обычный `onClick` или prop другому компоненту.

> [!followup]- Почему это не способ обойти exhaustive-deps?
>
> Зависимости effect описывают, когда связь с внешней системой должна перестроиться. Если запрос зависит от `userId`, скрыть `userId` внутри Effect Event означает потерять нужный новый запрос при смене пользователя. Последнее прочитанное значение не заменяет сам факт повторной синхронизации.
>
> Разделяй реактивный вход и нерективное сопровождение: подключение зависит от комнаты, оформление сообщения о подключении — от текущей темы. Только вторую часть можно вынести в Effect Event без переподключения по теме.
>
> Проверка: по очереди изменить каждое входное значение и заранее записать, должна ли перезапуститься связь. Если должна, значение остаётся зависимостью. Подавление линтера без такого объяснения обычно скрывает ошибку жизненного цикла.

## Чем useLayoutEffect отличается от useEffect?

> [!answer]- Короткий ответ — 30–90 секунд
>
> useLayoutEffect позволяет измерить DOM и скорректировать положение до показа кадра, блокируя перерисовку браузера. Большинству внешних связей достаточно useEffect. Нельзя считать useEffect безусловно выполняющимся строго после paint во всех ситуациях. Эффекты не исполняются при серверном рендеринге.

**Уточнения**
- Где разместить измерение tooltip?
- Что произойдёт при тяжёлом расчёте в layout effect?

**Изучить:** [[Фронтенд/React/06. Refs и работа с DOM#Когда нужен useLayoutEffect|объяснение, пример и ограничения]].

> [!followup]- Где разместить измерение tooltip?
>
> Если tooltip нужно измерить и скорректировать до показа кадра, используй `useLayoutEffect`: после добавления DOM измерь `getBoundingClientRect`, вычисли позицию и обнови состояние. Это предотвращает видимый скачок из предварительной позиции.
>
> Измерение зависит от реального расположения якоря, размеров tooltip, viewport и выбранной системы координат. При `position: fixed` обычно используют viewport-координаты; для абсолютного позиционирования требуется учёт containing block. Прокрутка и изменение размеров могут потребовать повторного расчёта и cleanup слушателей.
>
> Не измеряй DOM во время render. Проверяй положение в настоящем браузере, в том числе около края экрана и внутри прокручиваемого контейнера: jsdom не рассчитывает реальную геометрию.

> [!followup]- Что произойдёт при тяжёлом расчёте в layout effect?
>
> `useLayoutEffect` выполняется до того, как браузер покажет обновлённый кадр, и блокирует этот показ. Если внутри сортировать большой массив или выполнять долгий цикл, пользователь увидит задержку, а ввод и анимация могут зависнуть.
>
> Оставь там только необходимые чтения геометрии и короткую коррекцию. Чистое вычисление перенеси в подходящий слой и измерь стоимость; тяжёлую независимую обработку можно вынести в Worker. Перенос в обычный `useEffect` устраняет необходимость ждать перед этим кадром, но сам синхронный расчёт всё равно блокирует основной поток, когда начнётся.
>
> Проверяй Performance-профиль и задержку взаимодействия, а не только количество render: один длинный effect способен испортить интерфейс без дополнительных рендеров.

## Когда нужен ref вместо state?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Ref сохраняет значение между рендерами, но изменение current не запрашивает новый render. Он подходит для DOM-узла, таймера или служебного флага. Видимое значение обычно должно быть state. Обновление ref во время рендера ради последних props может утечь из рендера, который не был применён.

**Уточнения**
- Почему после setOpen(true) ref может оставаться null?
- Когда нужна callback ref?

**Изучить:** [[Фронтенд/React/06. Refs и работа с DOM|объяснение, пример и ограничения]].

> [!followup]- Почему после setOpen(true) ref может оставаться null?
>
> Setter запрашивает следующий render, но не добавляет условный DOM-узел немедленно в текущем обработчике. В `setOpen(true); inputRef.current?.focus()` поле ещё может отсутствовать, поэтому ref остаётся `null`.
>
> Свяжи фокус с фактическим появлением узла: callback ref либо effect/layout effect после commit при `open`. Если ref уже был установлен для постоянно присутствующего поля, ситуация другая — фокус можно поставить непосредственно.
>
> Не лечи проблему случайной задержкой `setTimeout(100)`: она не задаёт надёжной связи с commit. Проверь открытие, закрытие и повторное открытие; если поле скрыто или disabled, наличие DOM-узла ещё не гарантирует возможность фокусировки.

> [!followup]- Когда нужна callback ref?
>
> Callback ref удобна, когда действие должно происходить при присоединении конкретного DOM-узла: поставить фокус условному полю, подключить ResizeObserver или зарегистрировать элемент списка в Map. Обычный object ref сохраняет узел, но изменение `current` само не запускает effect и render.
>
> В React 19 callback ref может вернуть функцию очистки; для более раннего кода учитывают вызов с `null`. При замене callback React может очищать прежнюю связь и подключать новую, поэтому стабильность функции иногда существенна.
>
> Проверь удаление и повторное создание узла, а в StrictMode — дополнительный цикл подключения/очистки. Наблюдатель или запись Map должны исчезать вместе с узлом, иначе старые элементы будут удерживаться в памяти.

## Для чего нужен createPortal и как в нём работают события?

**ID вопроса:** Что делает портал и чего он не делает?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Портал размещает DOM в другом контейнере, сохраняя принадлежность React-дереву. Context и React-события продолжают следовать этому дереву. Это полезно для окна вне обрезающего контейнера, но не реализует доступный dialog автоматически. Фокус, Escape, фон и возврат фокуса нужно проектировать отдельно.

**Уточнения**
- Сработает ли обработчик React-предка при клике внутри портала?
- Где проверять геометрию?

**Изучить:** [[Фронтенд/React/06. Refs и работа с DOM#Портал и модальное окно|объяснение, пример и ограничения]].

> [!followup]- Сработает ли обработчик React-предка при клике внутри портала?
>
> Да: React-событие распространяется по React-дереву, даже если DOM портала физически находится в другом контейнере. Если модальное окно создано внутри компонента с `onClick`, клик в его портальном содержимом может вызвать этот обработчик.
>
> Это отличается от нативного распространения по DOM-предкам. Например, React-обработчик строки может сработать от кнопки в модальном окне, хотя окно добавлено в `document.body`. При необходимости останови распространение внутри окна либо измени расположение портала в React-дереве.
>
> Не используй один этот факт как проверку доступности модального окна: фокус, Escape, недоступный фон и возврат фокуса требуют отдельной реализации и браузерного сценария.

> [!followup]- Где проверять геометрию?
>
> Геометрию портала проверяют в браузере, где реально работают layout, scrolling, containing blocks и clipping. DOM-тест может подтвердить контейнер и текст, но нулевые или искусственные размеры jsdom ничего не говорят о положении окна.
>
> Для tooltip открой страницу у нижнего и правого края viewport, прокрути контейнер якоря, измени масштаб и размер окна. Проверь, что позиция следует за якорем и содержимое не обрезается. Для dialog дополнительно проверь перекрытие и прокрутку длинного содержимого.
>
> Сам `createPortal` меняет место DOM-вставки; он не рассчитывает координаты и не гарантирует верхний слой поверх всех контекстов. Скриншот дополняет проверку координат, а интерактивный сценарий проверяет поведение при изменениях.

## Два компонента вызывают один custom hook. Будет ли у них общее состояние?

**ID вопроса:** Что переиспользует custom hook?

**Практика:** [[Собеседования/Практика/React#Custom hook и независимость состояния|Проверить на задаче]]

**Критерии ответа:** Объясняю повторное использование логики и независимость состояния вызовов; соблюдаю порядок Hooks и показываю контракт входов и результата.
**Изучить:** [[Фронтенд/React/07. Custom hooks|Механизм, пример и ограничения]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Custom hook объединяет логику с Hooks, но не делает состояние общим автоматически. Два вызова useCounter имеют независимые состояния. Hook выполняется в составе рендера вызывающего компонента; его входы и правила очистки образуют контракт. Для общего значения нужен общий владелец или внешний источник.

**Уточнения**
- Чем отличается от обычной функции?
- Как гарантировать независимость двух поисков?

> [!followup]- Как гарантировать независимость двух поисков?
>
> Каждый вызов useSearch должен иметь собственные useState/useRef и собственную очистку эффекта. Таймер, AbortController и номер актуального запроса нельзя хранить в общей переменной модуля: ввод в одном поиске тогда способен отменить запрос другого. Входные параметры передаются явно, каждый экземпляр обновляет только свои данные, ошибку и pending.
>
> Проверка: одновременно смонтировать поиск сотрудников и поиск документов, запустить оба, изменить запрос первого, затем завершить второй. Второй показывает свой результат и не отменяется. Удалить первый — второй остаётся работоспособным. Отдельно завершить устаревший запрос первого и проверить, что он не заменил его новый результат.
>
> Custom hook переиспользует логику, а не автоматически общую ячейку state. Но он может читать общий Context или внешний кэш — тогда данные намеренно общие по контракту источника. Ключи такого кэша должны включать вид поиска, организацию и параметры; независимые черновики ввода остаются локальными. [Переиспользование логики через Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks).

> [!followup]- Чем отличается от обычной функции?
>
> Custom hook — функция, которая использует React Hooks и вызывается по их правилам из компонента или другого Hook. Префикс `use` позволяет инструментам проверять этот контракт. Обычная функция вычисления может вызываться где угодно, если сама не обращается к Hooks.
>
> `useCounter()` объединяет `useState` и операции счётчика, но каждый вызов получает собственное состояние в вызывающем компоненте. `calculateTotal(items)` просто возвращает число и не имеет React-жизненного цикла.
>
> Общее имя Hook не создаёт общий store. Если двум панелям нужен один счётчик, подними состояние к общему владельцу или подключи общий внешний источник. Проверяй независимость двумя одновременно смонтированными экземплярами, а не последовательным открытием одного.

## Почему Hooks нельзя вызывать условно?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Для обычных Hooks стабильный порядок вызовов позволяет React связать состояние между рендерами. Условный вызов useState/useEffect или вызов после условного return меняет этот порядок. Условие работы помещают внутрь effect, сохраняя вызов hook. У API use отдельные правила; исключение не распространяется на остальные Hooks.

**Уточнения**
- Можно ли вызвать hook из onClick?
- Как отключить подписку по enabled?

**Изучить:** [[Фронтенд/React/07. Custom hooks#Правила Hooks|объяснение, пример и ограничения]].

> [!followup]- Можно ли вызвать hook из onClick?
>
> Обычный Hook нельзя вызвать из обработчика клика: обработчик выполняется вне render, и React не может привязать такой вызов к стабильному порядку состояния компонента. Вызови Hook на верхнем уровне, а в обработчик передай возвращённую операцию.
>
> ```jsx
> const [count, setCount] = useState(0);
> return <button onClick={() => setCount(n => n + 1)}>Добавить</button>;
> ```
>
> Аналогично `useSearch()` может вернуть `search`, которую допустимо вызвать по клику. Отличай вызов Hook от вызова обычной функции, полученной из Hook. Исключения API `use` для условных чтений не разрешают произвольно вызывать `useState` или `useEffect` в событиях.

> [!followup]- Как отключить подписку по enabled?
>
> Hook вызывают безусловно, а условие работы помещают внутрь effect. При `enabled === false` effect ничего не подключает; при переходе из true в false React сначала выполняет cleanup прежней подписки.
>
> ```jsx
> useEffect(() => {
>   if (!enabled) return;
>   const unsubscribe = source.subscribe(handleMessage);
>   return unsubscribe;
> }, [enabled, source, handleMessage]);
> ```
>
> Здесь контракт `subscribe` предполагает возврат функции; для RxJS cleanup будет `() => subscription.unsubscribe()`. При изменении источника или обработчика прежняя связь также очищается. Проверка: после выключения новые события не меняют UI, повторное включение создаёт ровно одну активную подписку. Условный вызов самого `useEffect` нарушил бы порядок Hooks.

## Чем управляемый input отличается от неуправляемого?

> [!answer]- Короткий ответ — 30–90 секунд
>
> В controlled-поле value или checked задаёт React-state, а обработчик сообщает об изменении владельцу. В uncontrolled-поле значение хранит DOM; defaultValue задаёт начальное значение, FormData читает его при отправке. Нельзя случайно переключать режим через undefined. Оба подхода требуют ясного контракта сброса, ошибок и внешнего обновления.

**Уточнения**
- Как работает checkbox?
- Почему useState(initialValue) не синхронизирует новый prop?

**Изучить:** [[Фронтенд/React/08. Формы и события|объяснение, пример и ограничения]].

> [!followup]- Как работает checkbox?
>
> У управляемого checkbox состояние задаётся boolean-пропом `checked`, а обработчик читает `event.target.checked`. `value` задаёт отправляемое значение, но не переключает галочку.
>
> ```jsx
> <input type="checkbox" checked={accepted}
>   onChange={event => setAccepted(event.target.checked)} />
> ```
>
> Для неуправляемого начального состояния используют `defaultChecked`. В нативной `FormData` непомеченный checkbox обычно отсутствует, а помеченный отправляет своё `name` и `value` либо стандартное `on`. Поэтому серверный контракт должен различать отсутствие поля и явный false.
>
> Сохраняй один режим на всё время жизни поля и связывай его с подписью: клик по label и Space на фокусированном checkbox должны переключать состояние.

> [!followup]- Почему useState(initialValue) не синхронизирует новый prop?
>
> Начальное значение используется при монтировании компонента. При следующих рендерах React сохраняет его state независимо от нового `initialValue`; иначе любое обновление родителя стирало бы пользовательский ввод.
>
> Если родитель полностью владеет полем, передавай `value` и `onChange` без локальной копии. Если нужен черновик, явно определи начало редактирования и reset. Смена key подходит для новой сущности, например `key={userId}`, когда прежний черновик по контракту должен исчезнуть.
>
> Безусловный effect, копирующий prop в state, опасен: фоновое обновление исходных данных может перезаписать введённый текст. Проверь внешнее обновление во время редактирования и заранее выбери, сохранять ли черновик, показывать конфликт или сбрасывать его.

## Как не потерять ввод при ошибке сохранения?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Черновик сохраняется отдельно от результата запроса. Пока операция выполняется, интерфейс показывает pending и соблюдает выбранные ограничения повторной отправки. При ошибке черновик остаётся и доступен повтор. Если разрешён ввод во время запроса, успех относится к отправленному снимку, а не автоматически к новому тексту.

**Уточнения**
- Что меняет потеря ответа после успешной записи?
- Достаточен ли disabled для идемпотентности?

**Изучить:** [[Фронтенд/React/08. Формы и события#Отправка с сохранением ввода|объяснение, пример и ограничения]].

> [!followup]- Что меняет потеря ответа после успешной записи?
>
> Таймаут не означает, что сервер отверг сохранение: он мог записать данные, а ответ потерялся. Интерфейс должен сохранить черновик и показать неопределённый исход, затем восстановить результат по идентификатору операции или перечитать ресурс.
>
> Повтор создания с новым идентификатором может породить дубль. Для одной логической операции сохраняй idempotency key и повторяй запрос с ним; сервер обязан связывать ключ с исходом и проверять совместимость тела.
>
> Если пользователь успел изменить текст, успех старого запроса относится к отправленному снимку. Нельзя очистить новый черновик только потому, что удалось подтвердить прежнее сохранение. Проверка должна моделировать успешную запись с потерянным ответом, а не только HTTP-ошибку до записи.

> [!followup]- Достаточен ли disabled для идемпотентности?
>
> Нет. `disabled` ограничивает обычное взаимодействие с конкретной кнопкой, но не повтор после таймаута, новую вкладку, перезагрузку или прямой HTTP-запрос. Даже клиентская блокировка всех путей отправки не гарантирует единственную серверную запись.
>
> Для операции создания сервер принимает устойчивый ключ одной логической отправки, сохраняет результат и при повторе возвращает его без повторного эффекта. Клиент хранит ключ, пока исход неизвестен, и создаёт новый только для нового намерения.
>
> Кнопку всё равно полезно отключить и показать pending: это уменьшает случайные дубли и объясняет ожидание. Но проверка идемпотентности отправляет одинаковый запрос дважды и считает записи на сервере, а не проверяет атрибут кнопки.

## Когда выбирать useReducer и Context?

**Практика:** [[Собеседования/Практика/React#Выбор владельца состояния|Проверить на задаче]]

**Критерии ответа:** Разделяю правила переходов состояния и способ передачи значения; объясняю область владельца, обновление потребителей и цену общего контекста.
**Изучить:** [[Фронтенд/React/09. Управление состоянием|Механизм, пример и ограничения]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> useReducer собирает правила перехода в чистой функции и удобен для связанных действий. Context доставляет значение потомкам без промежуточной передачи props. Их можно сочетать, но ни один механизм сам по себе не является кэшем серверных данных. Для локального поля useState проще; внешний store выбирают при конкретных требованиях к потребителям и подпискам.

**Уточнения**
- Где выполнить запрос?
- Почему один большой Context может оказаться дорогим?

> [!followup]- Где выполнить запрос?
>
> Reducer оставляю чистым: он получает state и action и вычисляет следующий state. Запрос запускаю в обработчике команды пользователя, например submit, либо в effect, если нужно синхронизировать чтение с текущими параметрами экрана. Уже принятый слой загрузки данных также может владеть запросом.
>
> Обработчик отправляет действия saveStarted, saveSucceeded или saveFailed; это названия наших событий, не API React. Если возможны конкурирующие операции, событие несёт requestId, а reducer игнорирует исход неактуального запроса. Context лишь доставляет state/dispatch нужным компонентам, сам по себе он не выполняет загрузку.
>
> Проверка: повторный вызов reducer с теми же аргументами не отправляет запрос и возвращает тот же результат по смыслу. Один submit отправляет одну команду, отказ не стирает draft. Запись заказа не следует привязывать к effect «изменился state»: повторная синхронизация может повторить бизнес-действие. [Чистота reducer](https://react.dev/reference/react/useReducer), [события и эффекты](https://react.dev/learn/you-might-not-need-an-effect).

> [!followup]- Почему один большой Context может оказаться дорогим?
>
> Потребитель useContext подписан на значение контекста целиком. Когда value провайдера меняется по Object.is, React обновляет читающих этот контекст потребителей, даже если конкретный компонент использует лишь одно поле. memo не блокирует обновление самого потребляемого Context.
>
> Например, в value лежат theme, user и текст поиска. Каждый символ меняет общий объект, поэтому панель профиля тоже получает обновление. Новый объект value при любом рендере провайдера может добавлять лишние обновления даже без изменения содержимого.
>
> Сначала измеряю стоимость в Profiler. Затем оставляю локальный ввод у владельца, разделяю независимо меняющиеся контексты; для reducer можно разделить state и стабильный dispatch. useMemo помогает сохранить ссылку при неизменных зависимостях, но не устраняет обновления при реальном изменении общего значения. Если нужны выборочные подписки на части большого состояния, рассматриваю подходящий store. Маленький редкий Context не требует оптимизации только из-за размера объекта. [Обновление потребителей Context](https://react.dev/reference/react/useContext).

## Как предотвратить гонку запросов?

**Практика:** [[Собеседования/Практика/React#Поиск: от списка до гонок запросов|Проверить на задаче]]

**Критерии ответа:** Показываю отмену и проверку актуальности результата; запоздалые данные и finally старого запроса не меняют состояние нового.
**Изучить:** [[Фронтенд/React/10. Запросы и серверное состояние|Механизм, пример и ограничения]]

> [!answer]- Короткий ответ — 30–90 секунд
>
> Свяжи результат с входными параметрами и запрещай устаревшим операциям менять данные, ошибку и признак загрузки. AbortController экономит ресурсы, но загрузчик может проигнорировать сигнал отмены. Функция очистки или идентификатор запроса защищают запись; сравнение ключа при рендере скрывает данные другой организации ещё до следующего эффекта. Отдельно проверяй поздний успех и позднюю ошибку старого запроса.

**Уточнения**
- Что будет при пустом query?
- Может ли старый finally убрать текущий pending?

> [!followup]- Что будет при пустом query?
>
> Сначала определю контракт: в этом поиске пустой или состоящий из пробелов query означает «не искать». Проверку делаю по нормализованному значению. Но ранний return не должен оставлять предыдущую операцию актуальной: при переходе к пустому запросу очищаю таймер, инвалидирую старый запуск и по возможности отменяю сеть. Для пустого ключа показываю пустой список, отсутствие ошибки и pending=false.
>
> Если данные очищаются только внутри effect, при первом рендере пустого поля ещё может появиться старый список. Поэтому вывод связываю с текущим ключом запроса и не показываю несовпадающий результат. Поздние success/catch/finally предыдущего поиска не должны менять состояние пустого поиска.
>
> Проверка: запрос «Анна» запущен, поле очищено, старый ответ приходит после очистки — список остаётся пустым, загрузка не возвращается. Отдельно проверить очистку до срабатывания debounce. Если продукт трактует пустой query как «показать всех», нужен обычный запрос с этим ключом; это другой договорённый сценарий, а не универсальное правило React.

> [!followup]- Может ли старый finally убрать текущий pending?
>
> Да. finally выполняется после успеха и ошибки, в том числе после отмены запроса. Если A завершился, пока B ещё загружается, безусловный setPending(false) из A скрывает индикатор B.
>
> Проверка актуальности должна защищать все записи состояния: data, error и pending. Для эффекта удобно создать локальный active=true и в cleanup установить false; в then/catch/finally изменять состояние только при active. Для нескольких запусков внутри одного владельца можно использовать requestId и сравнивать его с текущим. AbortController дополняет эту защиту, но не заменяет её: загрузчик может игнорировать сигнал.
>
> Тест с управляемыми Promise: запустить A, затем B, завершить A — pending остаётся true; завершить B — становится false. Повторить со старым rejection и отменой A. Для полного интерфейсного контракта pending, как и данные, связан с ключом текущих параметров, чтобы состояние A не изображало загрузку B. [Очистка и гонки при загрузке](https://react.dev/learn/synchronizing-with-effects).

## Чем серверное состояние отличается от локального?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Локальный черновик принадлежит интерфейсу, серверные данные имеют внешний источник и могут устаревать. Кэш связывает их с ключом, правилами актуальности и обновлением после мутаций. Context лишь передаёт значение, а useMemo лишь кэширует вычисление. При смене пользователя или организации нельзя смешивать прежние данные с новым контекстом.

**Уточнения**
- Какие параметры включить в query key?
- Когда инвалидировать кэш?

**Изучить:** [[Фронтенд/React/10. Запросы и серверное состояние#Где заканчивается ручной effect|объяснение, пример и ограничения]].

> [!followup]- Какие параметры включить в query key?
>
> Ключ должен различать запросы, способные вернуть разные данные: ресурс, ID организации/пользователя в нужной области, фильтры, сортировку, страницу или cursor, локаль, если она меняет ответ. Например, `['users', orgId, { term, role, sort }]` отделяет поиск в разных организациях.
>
> Нормализация должна совпадать с контрактом API: если сервер считает пробелы значимыми, нельзя бездумно применять trim только к ключу. Токен доступа обычно не помещают в ключ как секрет; используют безопасную идентичность сессии/области и очистку при смене пользователя.
>
> Ключ отвечает за идентичность, а не за актуальность: даже правильно адресованный результат может устареть и требовать refetch или invalidation.

> [!followup]- Когда инвалидировать кэш?
>
> Инвалидируй данные, которые могла изменить подтверждённая мутация: после переименования пользователя — его карточку и списки, где имя показывается или влияет на сортировку/поиск. Если сервер вернул полный достоверный новый объект, карточку можно обновить непосредственно, а затронутые списки перечитать.
>
> Не очищай весь кэш автоматически после любого действия: это вызывает лишние запросы и теряет полезные результаты. Составь связь между изменением и зависимыми представлениями. При смене пользователя или организации нужна отдельная политика изоляции данных.
>
> Проверь два одновременно открытых представления одного ресурса. Успех формы при устаревшем списке означает, что мутация обработана локально, но согласование серверного состояния ещё не завершено.

## Как работает optimistic update?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Интерфейс временно показывает ожидаемый результат до подтверждения сервера. Нужны признак ожидания, обработка отказа и согласование с подтверждёнными данными. При параллельных изменениях откат к прежнему снимку состояния может стереть новую правку. useOptimistic помогает описать временное состояние интерфейса внутри Action, но не выполняет серверную операцию и не решает конфликт данных.

**Уточнения**
- Что будет, если A упал после успешного B?
- Как отличить отказ от неизвестного исхода?

**Изучить:** [[Фронтенд/React/10. Запросы и серверное состояние#Запись и optimistic update|объяснение, пример и ограничения]].

> [!followup]- Что будет, если A упал после успешного B?
>
> Наивный rollback к снимку до A может стереть уже подтверждённый B. Например, A оптимистично добавил реакцию, B изменил заголовок, B успешно сохранился, затем ошибка A восстановила весь старый объект вместе со старым заголовком.
>
> Откатывай изменение конкретной операции либо пересчитывай UI из подтверждённой основы и оставшихся оптимистичных операций. Если операции конфликтуют над одним полем, используй согласованный порядок, версии ресурса или повторное чтение сервера.
>
> Каждая операция должна иметь ID и свой статус. Проверка завершает B раньше A и убеждается, что после отказа A сохраняется результат B. `useOptimistic` помогает построить временное отображение, но не определяет серверную политику конфликтов.

> [!followup]- Как отличить отказ от неизвестного исхода?
>
> Отказ подтверждён, когда серверный контракт однозначно сообщает, что действие не принято: например, валидация вернула ошибки до записи. Обрыв связи или таймаут оставляет исход неизвестным: ответ мог потеряться после успешной записи.
>
> При подтверждённом отказе убирают оптимистичное изменение и объясняют исправление. При неизвестном исходе сохраняют идентификатор операции и показывают проверку результата; повтор используют с тем же idempotency key. Слепой откат и новая отправка могут визуально отрицать уже выполненное действие и создать дубль.
>
> Даже HTTP 500 не всегда доказывает отсутствие побочного эффекта — это зависит от серверной транзакции. API должен предоставлять способ согласовать итог, а UI — отличать «не принято» от «пока не удалось подтвердить».

## Как связаны URL и состояние экрана?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Параметры адреса задают открытый ресурс и разделяемые фильтры. useParams читает путь, useSearchParams — query; Back и reload должны восстанавливать экран из URL. Независимая копия фильтра в state может расходиться с адресом. Для ввода по буквам часто используют replace, а для перехода к другому ресурсу — новую запись истории.

**Уточнения**
- Почему Link работает, а прямой URL возвращает 404?
- Чем Declarative Mode отличается от Data Mode?

**Изучить:** [[Фронтенд/React/11. Маршрутизация|объяснение, пример и ограничения]].

> [!followup]- Почему Link работает, а прямой URL возвращает 404?
>
> Клиентский Link меняет маршрут внутри уже загруженного приложения. Прямой переход или reload сначала запрашивает этот путь у сервера; если сервер ищет физический файл `/users/42`, он может вернуть 404 до запуска React.
>
> Для SPA настраивают fallback маршрутов приложения на HTML-вход, сохраняя отдельные правила API и статических ресурсов. Для SSR сервер должен реально обработать маршрут и вернуть нужный ответ. Нельзя переписывать любой неизвестный путь в успешный HTML: иначе отсутствующий JS-файл получит HTML и сломается загрузка.
>
> Проверка включает вставку вложенного URL в новую вкладку, reload, query-параметры и действительно неизвестный маршрут. Успех навигации кнопкой не покрывает серверную маршрутизацию.

> [!followup]- Чем Declarative Mode отличается от Data Mode?
>
> В Declarative Mode React Router связывает URL с компонентами и предоставляет навигацию через `BrowserRouter`, `Routes`, `Route`. Загрузку данных и мутации приложение организует отдельно. Data Mode использует data router, например `createBrowserRouter` и `RouterProvider`, и добавляет route loaders, actions, pending-состояния и обработку ошибок маршрута.
>
> Если переход должен загрузить карточку до показа содержимого и повторно проверить данные после action, Data Mode даёт общий жизненный цикл маршрута. Небольшому SPA с уже существующим слоем запросов может хватить Declarative Mode.
>
> Выбор режима не равен выбору SSR: серверное формирование HTML и Framework Mode имеют отдельные возможности и настройки. Сравнивай API установленной версии роутера.

## Почему memo не остановил перерисовку?

> [!answer]- Короткий ответ — 30–90 секунд
>
> memo сравнивает props и может пропустить работу, но не блокирует собственный state или используемый Context. Новая функция или объект нарушают сравнение по ссылке. Сначала локализуй дорогую работу через Profiler и браузерный Performance. Если тормозит layout или слишком большой DOM, мемоизация вычислений не устраняет эту причину.

**Уточнения**
- Стоит ли мемоизировать любой callback?
- Что меняется при включённом Compiler?

**Изучить:** [[Фронтенд/React/12. Производительность#Context и мемоизация|объяснение, пример и ограничения]].

> [!followup]- Стоит ли мемоизировать любой callback?
>
> Нет. `useCallback` сохраняет ссылку между рендерами при неизменных зависимостях; он не ускоряет сам вызов функции. Польза появляется, когда стабильная ссылка позволяет пропустить дорогой render memo-компонента или не пересоздавать реальную подписку.
>
> Для обычной кнопки `onClick={() => setOpen(true)}` мемоизация часто ничего полезного не меняет. Если один callback стабилен, но рядом каждый раз создаётся новый объект prop, ожидаемого пропуска render может не быть.
>
> Сначала найди дорогой участок профилировщиком, затем проверь эффект изменения. Не удаляй зависимости ради стабильности: получится устаревшее замыкание. Корректность компонента должна сохраняться и без этого кэша.

> [!followup]- Что меняется при включённом Compiler?
>
> React Compiler может автоматически мемоизировать значения, функции и части вычисления компонентов, поэтому необходимость ручных `memo`, `useMemo` и `useCallback` уменьшается. Это оптимизация кода, соблюдающего правила React, а не замена правильному состоянию и эффектам.
>
> Гонка запросов, мутация props или неверные зависимости остаются ошибками даже при успешной компиляции. Внешние интеграции, зависящие от идентичности функций, требуют понимания своего контракта.
>
> Не удаляй все ручные мемоизации механически: сначала проверь конфигурацию, покрытие компилятора и профили representative-сценариев. Сравнивай одинаковую сборку и данные до/после; число render само по себе не доказывает ускорение, если время уходит на layout или сеть.

## Чем useDeferredValue и transition отличаются от debounce?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Deferred value и transition позволяют отложить несрочное отображение, чтобы ввод оставался отзывчивым. Debounce ограничивает частоту запуска работы по времени. Deferred value сам по себе не уменьшает число сетевых запросов, transition не переносит вычисление в Worker. Управляемый input должен обновляться срочно.

**Уточнения**
- Как обозначить устаревший список?
- Почему один большой синхронный расчёт всё ещё блокирует поток?

**Изучить:** [[Фронтенд/React/12. Производительность#Срочный ввод и дорогой список|объяснение, пример и ограничения]].

> [!followup]- Как обозначить устаревший список?
>
> Сравни текущий ввод и значение, по которому показан список: например, `isStale = query !== deferredQuery`. При различии можно показать «Обновляем результаты» и визуально ослабить прежний список, сохранив читаемость и доступное уведомление.
>
> Важно, чтобы подпись объясняла, каким запросу и организации принадлежат данные. При смене организации прежние строки нельзя просто оставить затемнёнными: их нужно скрыть, если контракт запрещает межорганизационный показ.
>
> `useDeferredValue` откладывает отображение, но не вводит фиксированную задержку и не ограничивает HTTP-запросы. Для debounce и защиты от поздних ответов нужны отдельные механизмы. Проверяй, что выбор старой строки во время обновления либо разрешён осознанно, либо заблокирован понятным способом.

> [!followup]- Почему один большой синхронный расчёт всё ещё блокирует поток?
>
> Transition меняет приоритет React-обновлений, но не переносит JavaScript в другой поток. Функция, переданная в `startTransition`, начинает выполняться сразу; длинный синхронный цикл внутри неё занимает основной поток до своего завершения.
>
> Если фильтрация миллиона записей длится 300 мс, оборачивание её в transition не делает её прерываемой посередине. Помогают уменьшение объёма работы, индекс, разбиение на части с отдачей управления или Worker. React может прерывать поддерживаемую работу render между участками, но не произвольную непрерывную функцию.
>
> Проверяй long tasks и задержку ввода в Performance. Debounce уменьшает число запусков, однако каждый оставшийся тяжёлый запуск всё ещё способен заморозить интерфейс.

## Какие ошибки ловит Error Boundary?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Граница позволяет изолировать ошибку рендера дочернего дерева и показать запасное содержимое. Она не заменяет обработку обычного отказа fetch или обычного обработчика клика и не ловит собственную ошибку. Область границы выбирают по тому, какую часть экрана можно потерять. После исправления причины нужен понятный способ повторить операцию или пересоздать дерево.

**Уточнения**
- Где показать HTTP 422?
- Что будет при ошибке загрузки lazy-компонента?

**Изучить:** [[Фронтенд/React/13. Ошибки, Suspense и серверный рендеринг#Что ловит Error Boundary|объяснение, пример и ограничения]].

> [!followup]- Где показать HTTP 422?
>
> Если 422 по контракту означает ошибки проверки формы, покажи их в самой форме: рядом с конкретными полями и при необходимости в общей сводке. Сохрани ввод, свяжи сообщения через `aria-describedby`, пометь ошибочные поля и обеспечь переход к первой ошибке.
>
> Обычный `fetch` не отклоняет Promise только из-за статуса 422: адаптер должен проверить `response.ok` и разобрать согласованное тело ошибки. Это ожидаемый результат операции, а не обязательно ошибка render для Error Boundary.
>
> Неизвестный формат ответа обрабатывают как общий сбой без выдуманных полевых ошибок. Проверка отправляет некорректные данные, получает 422 и убеждается, что пользователь может исправить поле и повторить, не набирая всё заново.

> [!followup]- Что будет при ошибке загрузки lazy-компонента?
>
> Пока Promise импорта ожидается, ближайший Suspense может показывать fallback. Если Promise отклонён, React передаёт ошибку ближайшей Error Boundary: индикатор ожидания не является обработчиком неудачной загрузки.
>
> Предусмотри понятное сообщение и восстановление. Например, после обновления приложения старый HTML может ссылаться на удалённый chunk; перезагрузка получает новую версию ресурсов. Простое повторное монтирование того же `lazy` не гарантирует новый import, поскольку React кэширует результат загрузчика.
>
> Проверь именно отказ загрузки chunk и работу остального экрана. Слишком широкая Error Boundary может заменить всё приложение, хотя отказал один раздел; граница должна соответствовать допустимой области потери интерфейса.

## Когда Suspense показывает запасное содержимое?

**ID вопроса:** Когда Suspense показывает fallback?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда поддерживающий Suspense дочерний ресурс приостанавливает рендер, граница показывает ожидание. Типичный пример — lazy-загрузка кода компонента. Обычный fetch в effect не активирует Suspense; для данных нужна поддерживающая интеграция. Ошибка ресурса и ожидание ресурса — разные состояния, поэтому Error Boundary остаётся отдельным механизмом.

**Уточнения**
- Почему lazy объявляют вне компонента?
- Может ли слишком широкая граница спрятать полезный экран?

**Изучить:** [[Фронтенд/React/13. Ошибки, Suspense и серверный рендеринг#Suspense и lazy|объяснение, пример и ограничения]].

> [!followup]- Почему lazy объявляют вне компонента?
>
> `lazy` возвращает новый тип компонента. Если создавать его внутри render, каждый повтор может дать React новую идентичность, привести к сбросу состояния и непредсказуемому поведению дочернего дерева.
>
> ```jsx
> const Settings = lazy(() => import('./Settings'));
> function Page() {
>   return <Suspense fallback={<p>Загрузка</p>}><Settings /></Suspense>;
> }
> ```
>
> Объявление на уровне модуля не означает немедленный сетевой запрос: загрузчик lazy вызывается, когда React впервые пытается отрисовать компонент. Для переключения между заранее известными панелями объяви стабильные lazy-типы отдельно. Проверь, что изменение состояния родителя не сбрасывает введённый текст уже загруженной панели; один успешный первый показ этого не обнаружит.

> [!followup]- Может ли слишком широкая граница спрятать полезный экран?
>
> Да. Если один Suspense охватывает всю страницу, приостановка маленького дочернего раздела может заменить fallback весь охваченный участок. Пользователь потеряет уже полезную навигацию или прочитанный контент ради одного ожидающего виджета.
>
> Размещай границы по смысловым этапам готовности: каркас страницы остаётся, список и подробности могут иметь отдельные состояния ожидания. Не дроби до каждого элемента без необходимости — это создаёт множество мерцающих индикаторов и сложный поток чтения.
>
> Для обновлений уже показанного содержимого transition может помочь сохранить предыдущий экран, но конкретное поведение зависит от расположения и ключей границ. Проверяй первоначальную загрузку и повторный переход отдельно: это разные пользовательские ситуации.

## Как искать причину hydration mismatch в React?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Найди первый отличающийся узел и сравни серверные данные с первым клиентским результатом. Проверь дату, случайность, locale/timezone, storage и HTML-вложенность. Передай одинаковые начальные данные или явно примени клиентское состояние после подключения. Подавление предупреждения не устраняет причину и не подтверждает корректность интерфейса.

**Уточнения**
- Почему нужен холодный reload?
- Что может скрыть переход внутри уже загруженного приложения?

**Изучить:** [[Фронтенд/React/13. Ошибки, Suspense и серверный рендеринг#Гидратация: сервер и первый рендер клиента|объяснение, пример и ограничения]].

> [!followup]- Почему нужен холодный reload?
>
> Hydration происходит, когда клиентский React подключается к HTML, подготовленному сервером. Переход внутри уже работающего приложения может рисовать только на клиенте и вообще не пройти этот путь.
>
> Холодный reload вложенного URL позволяет сравнить серверный HTML с первым клиентским render: одинаковы ли данные, локаль, время, случайные ID, разметка и состояние из storage. Для воспроизведения важно действительно получить документ с сервера, а не восстановить страницу из истории с сохранённым состоянием.
>
> Проверь консоль и первый различающийся узел. Одна успешная перезагрузка в своём часовом поясе не покрывает другой timezone или сохранённые настройки пользователя; добавь случаи, соответствующие найденной причине.

> [!followup]- Что может скрыть переход внутри уже загруженного приложения?
>
> Он может обойти начальное серверное формирование HTML, hydration и загрузку состояния из browser storage. Клиент уже знает пользователя, локаль и ширину окна, поэтому компонент выглядит правильно, хотя при прямом открытии сервер отдаёт другой первый результат.
>
> Например, тема читается из `localStorage` во время первого клиентского render, а сервер показал светлую тему. Внутренний переход использует уже установленную тему и не воспроизводит расхождение.
>
> Проверяй и клиентскую навигацию, и прямое открытие маршрута с чистой/сохранённой сессией. Не подавляй предупреждение глобально через `suppressHydrationWarning`: это узкая escape hatch, а не способ согласовать два разных дерева или исправить неверный первоначальный экран.

## Чем SSR отличается от Server Components?

> [!answer]- Короткий ответ — 30–90 секунд
>
> SSR производит первоначальный HTML. Server Components определяют серверную границу исполнения компонентов и передачу их результата клиентскому дереву. Клиентский компонент тоже может участвовать в серверном формировании HTML. use client и use server работают в поддерживающей среде и имеют разные назначения; обычный Vite SPA не получает RSC от добавления директивы.

**Уточнения**
- Где допустим useState?
- Обозначает ли use server серверный компонент?

**Изучить:** [[Фронтенд/React/13. Ошибки, Suspense и серверный рендеринг#SSR, Server Components и Next.js|объяснение, пример и ограничения]].

> [!followup]- Где допустим useState?
>
> `useState` допустим в Client Component или custom hook, вызываемом таким компонентом. Server Components не имеют интерактивного клиентского состояния и не используют `useState` для обработчиков браузера.
>
> При этом Client Component может участвовать в SSR: его начальный HTML формируется на сервере, затем в браузере происходит hydration и дальнейшие обновления state. Поэтому «исполняется при серверном render» не равно «Server Component».
>
> В поддерживающей RSC-среде директива `use client` обозначает клиентскую границу модулей. В обычном SPA компоненты уже исполняются на клиенте, а добавление директивы не создаёт серверную архитектуру. Выбирай небольшую интерактивную границу, когда остальное содержимое можно оставить серверным.

> [!followup]- Обозначает ли use server серверный компонент?
>
> Нет. `use server` помечает Server Functions, которые поддерживающая среда позволяет вызывать с клиента через серверную границу. Server Components определяются архитектурой RSC и расположением в графе модулей, а не этой директивой.
>
> Например, серверная функция сохранения может принимать данные формы и выполнять мутацию; серверный компонент может читать данные и возвращать JSX без `use server`. Полученные от клиента аргументы функции необходимо проверять и авторизовать на сервере: директива не делает вызов доверенным.
>
> В обычном Vite SPA строка-директива сама не поднимает сервер и RPC. Нужна конкретная поддерживающая сборка/фреймворк. Это различие предотвращает ошибочное размещение секретов в модуле, который фактически попадает в клиентский bundle.

## Что проверять в тесте React-компонента?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверяй доступное имя поля, действия пользователя и результат в DOM. Для запроса нужны ожидание, успех, пустой результат, ошибка и обратный порядок ответов; для подписки — новый обработчик и очистка ресурсов. Управляемые Promise и часы делают сценарии воспроизводимыми. jsdom не подтверждает реальную геометрию, захват указателя, скорость или управление фокусом в браузере.

**Уточнения**
- Почему тест только на вызов setter слабее?
- Какие сценарии требуют настоящего браузера?

**Изучить:** [[Фронтенд/React/14. Тестирование и практикум|объяснение, пример и ограничения]].

> [!followup]- Почему тест только на вызов setter слабее?
>
> Вызов setter доказывает лишь внутреннее действие, но не результат для пользователя. Компонент может вызвать правильную функцию и всё равно показать старые данные из неверного memo, скрыть сообщение или привязать значение не к тому полю.
>
> Лучше ввести текст через доступное поле, нажать кнопку и проверить результат в DOM: новое значение, ошибку или сохранённый черновик. Для гонки запросов управляй порядком Promise и проверяй список вместе с индикатором загрузки.
>
> Проверки вызова API полезны как дополнительное доказательство корректных аргументов и отсутствия лишней отправки. Они не заменяют наблюдение экрана. Такой тест также меньше привязан к тому, хранит ли реализация состояние в нескольких setter или одном reducer.

> [!followup]- Какие сценарии требуют настоящего браузера?
>
> Настоящий браузер нужен для поведения, зависящего от layout и платформы: положение tooltip, переполнение, scrolling, sticky, drag с pointer capture, реальный Tab-порядок, фокус dialog и загрузка ресурсов. Производительность также измеряют браузерным профилем, а не временем unit-теста.
>
> Например, DOM-тест подтверждает, что ошибка связана с полем через `aria-describedby`; браузерный сценарий проверяет перевод фокуса и отсутствие перекрытия сообщения. Проверка со screen reader дополнительно подтверждает реальное объявление.
>
> Unit-тесты остаются полезны для переходов состояния и управляемых гонок Promise. Выбирай среду под утверждение: снимок HTML не доказывает отсутствие горизонтальной прокрутки, а один скриншот не доказывает управление клавиатурой.

## Зачем нужны Actions и useActionState?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Actions связывают асинхронное действие с обновлением интерфейса, а useActionState хранит результат и признак ожидания. Функция получает предыдущее состояние перед данными действия; при отправке формы эти данные обычно представлены FormData. Ожидаемые ошибки можно вернуть как данные для формы. Клиентский Action не становится серверной функцией автоматически; правила очистки полей нужно сверить с требованиями интерфейса.

**Уточнения**
- Где разместить useFormStatus?
- Что произойдёт с uncontrolled-полями после успешного form action?

**Изучить:** [[Фронтенд/React/08. Формы и события#Actions в React 19|объяснение, пример и ограничения]].

> [!followup]- Где разместить useFormStatus?
>
> `useFormStatus` вызывают в компоненте, который находится внутри нужного `<form>`. Он читает статус родительской формы, а не формы, которую тот же компонент лишь возвращает ниже по дереву.
>
> ```jsx
> function SubmitButton() {
>   const { pending } = useFormStatus();
>   return <button disabled={pending}>Сохранить</button>;
> }
> // <form action={save}><Fields /><SubmitButton /></form>
> ```
>
> Если вызвать Hook в компоненте, создающем этот `<form>`, `pending` не будет отражать его отправку. Hook также не превращает произвольный `fetch` по клику в form action. Проверь, что pending начинается при отправке именно этой формы, а соседняя независимая форма остаётся доступной.

> [!followup]- Что произойдёт с uncontrolled-полями после успешного form action?
>
> После успешного выполнения функции `action` React сбрасывает uncontrolled-поля формы. Это удобно для отправленного сообщения, но опасно, если приложение считает возвращённую ошибку обычным успешным завершением и рассчитывает сохранить ввод автоматически.
>
> Ожидаемые ошибки часто возвращают через `useActionState`; при таком контракте отдельно управляй сохранением значений и поведением reset. Controlled-поля принадлежат state, поэтому их сброс определяется обновлением этого state.
>
> Проверь три случая: подтверждённый успех, возвращённые ошибки валидации и исключение. Если во время отправки разрешён новый ввод, успешный ответ старого снимка не должен молча уничтожать новый текст. Выбор action API не освобождает от явного контракта черновика.

## Как устроен поток данных в Redux и когда нужен внешний store?

> [!answer]- Короткий ответ — 30–90 секунд
>
> UI отправляет action через dispatch, reducer вычисляет следующее состояние, а подписанные потребители получают выбранные данные. Reducer остаётся чистым. Внешний store полезен для общего состояния с несколькими независимыми потребителями, диагностикой действий и явными переходами; для локального поля достаточно состояния компонента. Кэш API имеет свои правила актуальности.

**Уточнения**

- Чем selector отличается от action?
- Почему запрос нельзя выполнять в reducer?
- Чем Redux отличается от Context и useReducer?

**Критерии ответа:** Объясняю цепочку изменения, чистоту reducer и основание выбора; не объявляю store обязательным.

**Изучить:** [[Фронтенд/React/09. Управление состоянием#Однонаправленный поток: Flux и Redux|Поток данных и небольшой пример]]

> [!followup]- Чем selector отличается от action?
>
> Action описывает событие или намерение изменить состояние: например, `{ type: 'cart/itemAdded', payload: item }`. Selector читает state и возвращает нужную часть или производное значение, например сумму корзины. Сам selector ничего не dispatch-ит и не меняет store.
>
> Reducer получает предыдущее состояние и action, вычисляет следующее; подписанный UI затем повторно выбирает данные через selector. Мемоизированный selector может избежать дорогого повторного вычисления, если входы прежние.
>
> Не помещай мутацию или HTTP-запрос в selector: его могут вызывать многократно в диагностике и render. Проверка selector — одинаковый state даёт одинаковый результат без побочных эффектов; проверка action/reducer — конкретное событие вызывает ожидаемый переход.

> [!followup]- Почему запрос нельзя выполнять в reducer?
>
> Reducer должен быть чистой функцией: для одинаковых state и action возвращать одинаковое следующее состояние без внешних эффектов. HTTP-запрос зависит от времени и сети, а его запуск при повторном вычислении reducer способен повторить запись.
>
> Асинхронную работу размещают в middleware, thunk или слое запросов. Она dispatch-ит отдельные события начала, успеха и отказа; reducer синхронно обновляет состояние по каждому из них. Например, `saveStarted` задаёт pending, `saveSucceeded` сохраняет серверную ревизию.
>
> Это позволяет воспроизводить историю действий и тестировать переходы без сети. Чистота также запрещает случайные ID, текущую дату и мутацию входного state внутри reducer; нужные значения передают в action.

> [!followup]- Чем Redux отличается от Context и useReducer?
>
> `useReducer` хранит состояние у React-владельца и описывает переходы; Context доставляет значение потомкам. Вместе они подходят для общего состояния ограниченного поддерева. Redux предоставляет внешний store, подписки, middleware и общую модель действий, а экосистема добавляет инструменты диагностики и работы с серверными данными.
>
> Для черновика одной формы Redux обычно не обязателен. Для разделяемых между удалёнными частями приложения процессов с трассировкой действий он может быть полезен. Context сам не делает селективную подписку на произвольное поле: изменение переданного value обновляет его потребителей по правилам React.
>
> Выбирай по владельцу, времени жизни и способам изменения состояния. Ни один из вариантов автоматически не решает актуальность HTTP-кэша или конфликты параллельных записей.
