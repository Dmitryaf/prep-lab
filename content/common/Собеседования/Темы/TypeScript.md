## Что TypeScript проверяет и чего не гарантирует?

> [!answer]- Короткий ответ — 30–90 секунд
>
> TypeScript проверяет статические типы; большая часть сведений о типах удаляется при компиляции. Он не проверяет фактический JSON от сервера и не доказывает бизнес-корректность программы. На границах нужны проверка данных, преобразование и понятная обработка ошибки.
>
> Ответ API может объявлять `price: number`, а фактически прислать строку. Компилятор не увидит сетевые данные: после получения нужна проверка во время выполнения до расчёта цены. Написанное `as Product` такой проверкой не является.
>

**Уточнения**

- Почему as Product не защитит расчёт цены от строки в ответе API?
- Что проверяет satisfies и чего он не делает во время исполнения?
- Какие ошибки strict помогает заметить до запуска?

**Критерии ответа:** Разделяю проверку до запуска и проверку во время выполнения; показываю, почему as и сгенерированный тип не проверяют фактический JSON.

## Чем any, unknown и never отличаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> any отключает значительную часть проверки для значения: можно вызывать неизвестные свойства, а ошибки распространяются дальше без предупреждения. unknown означает «значение есть, но его тип пока неизвестен»: присвоить можно что угодно, использовать как строку или объект — только после проверки или небезопасного утверждения. Поэтому unknown подходит для данных с внешней границы.
>
> `never` означает невозможное значение. Он появляется, например, после проверки всех вариантов объединения или у функции, которая всегда бросает исключение. Для обычной функции без полезного результата используется `void`.
>
> В API предпочитаю unknown с проверкой; any оставляю для осознанной границы миграции. never помогает проверить полноту обработки вариантов.

**Уточнения**

- Почему data.name нельзя читать у unknown без проверки?
- Как `never` помогает заметить новый необработанный вариант объединения?
- Превращает ли as User значение unknown в проверенного пользователя?

**Критерии ответа:** Могу безопасно обработать unknown, объяснить риск any и отличить never от void.

## Как работают сужение типа и отличительное поле?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Если значение имеет несколько возможных типов, проверка в коде помогает TypeScript уточнить доступные операции. Например, после `typeof value === "string"` внутри ветки доступны строковые методы. Это называется сужением типа; оно учитывает проверки и поток выполнения.
>
> Для сложных состояний удобно общее отличительное поле с литеральным значением: `{status: "success", data: User}` или `{status: "error", error: string}`. После проверки status доступны поля соответствующего варианта. Так невозможные сочетания лучше исключать моделью, а не набором независимых boolean-флагов.
>
> Функция проверки типа может объявить результат как `value is User`. TypeScript доверяет этой записи, поэтому сама функция должна проверить объект, `null`, массивы и типы обязательных полей.

**Уточнения**

- Почему typeof null недостаточно для проверки объекта?
- Чем объединение вариантов состояния удобнее нескольких независимых флагов?
- Как заметить, что после добавления status обработчик стал неполным?

**Критерии ответа:** Разбираю все варианты объединения по общему отличительному полю без `as` и объясняю, какие поля и значения проверяет функция.

## Когда использовать type и interface?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Оба способа описывают свойства объекта и могут использовать параметры типов. `interface` расширяется через `extends`; объявления одного интерфейса могут объединяться. `type` задаёт имя любому типу: объекту, объединению, кортежу, примитиву или результату преобразования типов.
>
> Для описания объекта подходят оба способа, поэтому важны соглашения проекта. Для объединения нескольких вариантов состояния используют type. Если API должен позволять дополнять существующее объявление интерфейса новыми полями, может быть полезен interface. Пересечение A & B требует одновременно выполнить требования обоих типов: несовместимые свойства могут получить тип never.
>
> Оба описания типов стираются при преобразовании в JavaScript. Ни type, ни interface не проверяет полученный JSON во время работы программы и не создаёт объект.

**Уточнения**

- Что произойдёт с двумя объявлениями одного interface?
- Что значит {id: string} & {id: number}?
- Можно ли описать объединение типов через `interface`?

**Критерии ответа:** Выбираю способ описания по необходимости объединять варианты или расширять интерфейс; объясняю объединение объявлений и понимаю, что описание типа не проверяет данные во время работы программы.

**Изучить:** [[Фронтенд/TypeScript/02. Псевдонимы типов и интерфейсы|Полное объяснение]]

**Практика:** [[Фронтенд/TypeScript/09. Практикум по TypeScript|Проверить на задаче]]

## Зачем нужны обобщённые типы?

**ID вопроса:** Зачем нужны обобщённые типы — generics?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Параметр типа сохраняет связь между аргументами и результатом, не фиксируя один конкретный тип заранее. В `function first<T>(items: T[]): T | undefined { return items[0]; }` массив строк даёт строку или `undefined`, а массив пользователей — пользователя или `undefined`. При использовании `any` эта связь потеряется.
>
> Ограничение `T extends {id: string}` позволяет использовать id внутри функции, сохраняя остальные свойства конкретного T снаружи. Компилятор часто выводит T из аргумента; вручную указывать его нужно не всегда.
>
> Параметр типа полезен, когда связывает типы аргументов и результата. Если `T` ни с чем не связан, он может только усложнить описание функции. Проверка полученных данных во время выполнения остаётся отдельной задачей.

> [!example]- Если попросят подробнее
>
> Здесь тип результата определяется конкретным выбранным полем. `T` описывает объект, `K` — один из его ключей, а `T[K]` — тип значения этого ключа.
>
> ```ts
> function getValue<T extends object, K extends keyof T>(obj: T, key: K): T[K] {
>   return obj[key];
> }
>
> const user = { id: 42, name: 'Анна' };
> const userName: string = getValue(user, 'name');
> const userId: number = getValue(user, 'id');
> ```
>
> Ключ `"email"` для этого объекта компилятор отклонит. Утверждать результат через `as` не нужно. Для объекта из сети реальные поля проверяются до вызова: параметры типов сами такую проверку не выполняют.
>
> [Ограничения параметров типов и keyof в документации TypeScript](https://www.typescriptlang.org/docs/handbook/2/generics.html#using-type-parameters-in-generic-constraints).

**Уточнения**

- Почему first<T> лучше first(items: any[]): any?
- Как ограничить ключ параметром K extends keyof T?
- Почему функция parse<T>(json: string): T без проверки не доказывает правильность данных?

**Критерии ответа:** Типизирую небольшую функцию без потери типа результата; объясняю constraint и поведение пустого входа.

## Как работают keyof, typeof и доступ T[K]?

> [!answer]- Короткий ответ — 30–90 секунд
>
> keyof даёт набор допустимых ключей типа. typeof в позиции типа получает тип существующего значения. T[K] описывает тип свойства по ключу. Вместе они позволяют связать объект, допустимый ключ и точный результат функции getValue.
>
> В редакторе профиля `keyof User` ограничивает допустимые поля, а `User[K]` задаёт тип нового значения для выбранного поля. Нельзя передать строку вместо числа возраста, если сигнатура сохраняет связь конкретного ключа и значения.
>

**Уточнения**

- Record
- индексная сигнатура
- необязательное поле
- noUncheckedIndexedAccess

## Что такое отображаемые и условные типы?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Отображаемый тип преобразует набор свойств, например делает их необязательными. Условный тип выбирает результат по проверке extends. Когда проверяется непосредственно параметр типа, условие может применяться отдельно к вариантам объединения. infer позволяет извлечь часть структуры, например тип результата функции.
>
> `Partial<User>` подходит для объекта частичного обновления, `Pick<User, "id" | "name">` — для небольшой проекции данных. Это только преобразования типов: допустимость изменения конкретного поля и непустой PATCH проверяются по отдельному контракту.
>

Изучить: [[Собеседования/Практика/TypeScript#Построить вспомогательный тип по шагам|разобрать запись по частям]].

**Уточнения**

- Partial/Required/Readonly/Pick/Omit
- отключение распределения условного типа по объединению
- ReturnType

## Чем утверждение типа отличается от проверки?

> [!answer]- Короткий ответ — 30–90 секунд
>
> as и оператор ! после выражения меняют представление компилятора, но не проверяют и не исправляют данные. Условие во время выполнения действительно проверяет значение. satisfies проверяет соответствие типу, сохраняя более точный выведенный тип выражения. Не использую утверждение для сокрытия неизвестного результата API.
>
> Объект настройки маршрутов можно проверить через `satisfies`, сохранив конкретные ключи для последующего вывода типов. Для ответа сети это не замена проверке: неизвестные данные сначала валидируют, а не убеждают компилятор утверждением `as`.
>

**Уточнения**

- JSON.parse
- DOM поиск
- проверка лишних свойств

## Как работают структурная типизация и проверка лишних полей?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Совместимость обычно определяется набором свойств, а не названием типа. Для нового объектного литерала в некоторых позициях дополнительно проверяются лишние поля. Переменная с более широкой структурой может быть совместима. Поэтому ошибка литерала не означает, что все объекты с дополнительным полем запрещены.
>
> Объект полного профиля можно передать функции, которой нужны только `id` и `name`. Лишние данные физически не исчезнут: если функция отправляет весь объект дальше, тип узкого параметра не предотвращает случайную передачу дополнительных полей.
>

**Уточнения**

- метка номинального типа
- поля private
- параметры функций

## Чем объединение типов отличается от пересечения?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Объединение допускает одно из нескольких значений; для особых операций нужно уточнить вариант. Пересечение требует одновременно выполнить ограничения нескольких типов. Противоречивые требования к полю могут дать never. Эти операции над типами сами по себе не объединяют объекты в работающей программе.
>
> Ответ сохранения может быть либо `{ ok: true, id }`, либо `{ ok: false, error }`. Пересечение `User & Permissions` описывает объект, содержащий обе части; чтобы создать его во время выполнения, всё равно нужна операция над самими данными.
>

**Уточнения**

- Общее отличительное поле
- необязательные свойства
- interface extends

## Как типизировать функцию с разными вариантами вызова?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Если результат зависит от типа входа, использую обобщённый параметр или перегрузки. Сигнатура реализации должна покрыть все разрешённые вызовы. Независимые варианты часто проще выразить объединением типов, чем длинным списком перегрузок. Проверяю удобство вывода и ошибки на примерах вызывающего кода.
>
> Обёртка над функцией может сохранить типы её аргументов и результата вместо `(...args: any[]) => any`. Перегрузки нужны, когда варианты вызова дают разные результаты; если все варианты возвращают одно и то же, часто достаточно объединения параметров.
>

**Уточнения**

- необязательные аргументы
- кортеж для остаточных параметров
- ReturnType для перегруженной функции

## Как типизировать динамический словарь?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Record<K,V> или индексная сигнатура задают допустимые ключи и значения. Но тип словаря со строковым ключом не гарантирует фактическое наличие любой строки. Учитываю отсутствие значения, настройки проверки индексного доступа и контракт Map.get. Конечный набор ключей отличается от произвольного string.
>
> Для кэша пользователей по `id` отсутствие записи — нормальное состояние. `Map.get(id)` явно возвращает `User | undefined`; для объектного словаря учитывают `noUncheckedIndexedAccess`, иначе статический тип может скрыть отсутствие ключа.
>

**Уточнения**

- noUncheckedIndexedAccess
- ключи прототипа
- реестр меню

## Что гарантирует readonly?

> [!answer]- Короткий ответ — 30–90 секунд
>
> readonly ограничивает присваивание через конкретный тип и обычно действует неглубоко. Другая ссылка может позволить изменить тот же объект. ReadonlyArray запрещает изменяющие методы через эту типизированную ссылку. Замораживание объекта во время выполнения — отдельный механизм.
>
> Функция расчёта может принимать `readonly CartItem[]`, чтобы случайно не вызвать `sort` или `push` на входе. Это не запрещает другим участникам менять тот же массив и не делает вложенные объекты неизменяемыми во время выполнения.
>

> [!example]- Если попросят подробнее
>
> Запрет действует через конкретный типизированный доступ. `readonly items: CartItem[]` запрещает заменить поле `items`, но не запрещает `items.push()`. Для запрета изменения самого массива через эту ссылку нужен `readonly CartItem[]` или `ReadonlyArray<CartItem>`.
>
> Даже readonly-массив не делает свойства его объектов readonly. `Object.freeze` — отдельная операция времени выполнения и тоже неглубокая. Поэтому в ответе нужно назвать, что именно защищается: поле, контейнер или вложенные данные.
>
> [Документация TypeScript о readonly](https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties).

## Чем enum отличается от объединения литералов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> enum обычно создаёт объект во время выполнения; объединение литералов существует только в типовой модели. Для набора строк часто достаточно строковых литералов и объекта с константами. Поведение const enum и совместимость нужно проверять по настройкам компиляции и способу потребления библиотеки.

> Статусы, приходящие из API строками `draft` и `published`, удобно описать объединением литералов. Если нужны значения во время выполнения, добавляют объект `as const`; принадлежность неизвестной строки этому набору всё равно проверяют.
>

## Как типизировать ошибки и асинхронный API?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Promise<T> описывает успешный результат, но стандартный тип не кодирует тип отклонения. Значение catch проверяю как unknown. Ожидаемые предметные исходы можно вернуть объединением с отличительным полем. Не выдаю статический тип успешного результата за гарантию отсутствия сетевой ошибки.
>
> Ожидаемый отказ сохранения, например конфликт версии, можно вернуть отдельным вариантом результата. Сетевой сбой остаётся возможным отклонением Promise; обработчик `catch` уточняет неизвестное значение, прежде чем читать `message`.
>

**Уточнения**

- ошибка instanceof
- Result
- отмена

## Что такое кортеж и кортеж с переменным хвостом?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Кортеж описывает позиции и тип каждой позиции, включая необязательные элементы и хвост. Кортеж с переменным набором позволяет сохранять типы аргументов обёртки или композиции функций. Обычный массив T[] не задаёт точного количества и назначения элементов.
>
> Координаты `[longitude, latitude]` имеют фиксированные позиции, поэтому кортеж понятнее `number[]`. В обёртке над callback кортеж аргументов сохраняет их число и типы; он не проверяет диапазон географических координат во время выполнения.
>

**Уточнения**

- Parameters
- ConstructorParameters
- вывод типа

## Как проверять данные внешнего API?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Тип TypeScript описывает ожидание программы, но сервер может вернуть другую структуру. Поэтому полученный JSON на границе рассматриваю как unknown и проверяю его во время исполнения: обязательные поля, их типы, допустимые значения и вложенные структуры. Это можно сделать небольшим валидатором или схемой.
>
> После успешной проверки преобразую данные в модель приложения. Неожиданный ответ должен дать понятную ошибку или безопасный отказ, а не молча превратиться в «пустой успех». `as User` только заставляет компилятор доверять разработчику; значения он не преобразует.
>
> Сетевой сбой, HTTP-ошибка, невалидный JSON и нарушение схемы — разные этапы. Например, fetch обычно не отклоняет Promise на 404: сначала проверяют response.ok, затем разбирают и валидируют тело.

## Чем private и protected отличаются от приватных полей JavaScript?

> [!answer]- Короткий ответ — 30–90 секунд
>
> private и protected ограничивают доступ в типовой модели TypeScript. Поля с префиксом # имеют ограничения доступа во время выполнения по правилам JavaScript. Это разные механизмы. Они не заменяют проверку полномочий пользователя и защиту данных, отправленных за пределы приложения.
>
> TypeScript `private` помогает запретить доступ в проверяемом исходном коде, но не заменяет защиту во время выполнения. Поле `#token` обеспечивает языковую приватность внутри класса; это всё равно не место для серверного секрета в браузерном приложении.
>

**Уточнения**

- подкласс
- преобразование в JavaScript
- доступ к структуре объекта во время выполнения

## Как уменьшить риск слишком сложных типов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Начинаю с понятной модели состояний и входов, затем добавляю необходимые связи между типами. Сигнатура должна помогать вызывающему коду и проверять реальный контракт. Проверяю положительные и отрицательные примеры компиляции; сложный тип, который трудно объяснить и поддерживать, может быть хуже более явного интерфейса.
>
> Тип конфигурации таблицы должен помогать выбрать существующий ключ и корректно типизировать значение ячейки. Если ошибка компилятора стала нечитаемой, лучше вынести именованные части и упростить контракт, чем добавлять новые уровни условных типов.
>

- рекурсивные условные типы
- стоимость проверки компилятором
