## Что TypeScript проверяет и чего не гарантирует?

> [!answer]- Короткий ответ — 30–90 секунд
>
> TypeScript проверяет статические типы; большая часть сведений о типах удаляется при компиляции. Он не проверяет фактический JSON от сервера и не доказывает бизнес-корректность программы. На границах нужны проверка данных, преобразование и понятная обработка ошибки.
>
> Ответ API может объявлять `price: number`, а фактически прислать строку. Компилятор не увидит сетевые данные: после получения нужна проверка во время выполнения до расчёта цены. Написанное `as Product` такой проверкой не является.
>

**Уточнения**

- Что проверяет satisfies и чего он не делает во время исполнения?
- Какие ошибки strict помогает заметить до запуска?

**Критерии ответа:** Разделяю проверку до запуска и проверку во время выполнения; показываю, почему as и сгенерированный тип не проверяют фактический JSON.

> [!followup]- Почему as Product не защитит расчёт цены от строки в ответе API?
>
> Утверждение as Product меняет только представление компилятора. Полученное значение остаётся прежним: если price пришёл строкой, сложение с числом может склеить строки, а вызов числового метода — упасть. Утверждение не преобразует строку и не проверяет контракт.
>
> Ответ внешнего API принимают как unknown, проверяют структуру и тип price, затем отдельно — допустимость значения, например Number.isFinite(price) и неотрицательность. Если контракт разрешает числовую строку, преобразование делают явно и проверяют результат. Только после успешной проверки данные передают расчёту; ошибку формата обрабатывают на границе, сохраняя контекст запроса.

> [!followup]- Что проверяет satisfies и чего он не делает во время исполнения?
>
> satisfies проверяет совместимость выражения с типом, не заменяя его тип широкой аннотацией целиком. Это удобно для реестра настроек: можно проверить допустимые значения и сохранить конкретные ключи. Контекст типизации при этом способен влиять на вывод литералов — считать его полностью отсутствующим неверно.
>
> ~~~ts
> const routes = { home: '/', account: '/account' } satisfies Record<string, string>;
> type Route = keyof typeof routes;
> const valid: Route = 'home';
> // @ts-expect-error: такого ключа в реестре нет
> const invalid: Route = 'settings';
> ~~~
>
> Во время исполнения оператор исчезает. Он не проверит сетевой JSON, не удалит лишние данные и не заменит валидатор. Для unknown нужна проверка фактического значения.
>
> Источник: [TypeScript — satisfies](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html).

> [!followup]- Какие ошибки strict помогает заметить до запуска?
>
> strict включает семейство строгих проверок: например, неявный any у параметра без выводимого типа, использование потенциальных null/undefined и несовместимость ряда функциональных типов. Это позволяет заметить опасный доступ к необязательному полю или неопределённый контракт аргумента до запуска.
>
> Но strict не включает все полезные опции: noUncheckedIndexedAccess и exactOptionalPropertyTypes настраиваются отдельно. Явный any и утверждения типа всё ещё могут обойти проверку, а фактические данные API компилятор не видит. При миграции смотрят конкретную диагностику, исправляют модель или проверку значения и не гасят ошибки массовыми as и !.

## Чем any, unknown и never отличаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> any отключает значительную часть проверки для значения: можно вызывать неизвестные свойства, а ошибки распространяются дальше без предупреждения. unknown означает «значение есть, но его тип пока неизвестен»: присвоить можно что угодно, использовать как строку или объект — только после проверки или небезопасного утверждения. Поэтому unknown подходит для данных с внешней границы.
>
> `never` означает невозможное значение. Он появляется, например, после проверки всех вариантов объединения или у функции, которая всегда бросает исключение. Для обычной функции без полезного результата используется `void`.
>
> В API предпочитаю unknown с проверкой; any оставляю для осознанной границы миграции. never помогает проверить полноту обработки вариантов.

> [!followup]- Почему data.name нельзя читать у unknown без проверки?
>
> unknown означает, что значение может быть чем угодно, включая null, число или объект без name. Компилятор поэтому не разрешает чтение произвольного свойства. Сначала проверяют категорию значения, затем наличие и тип нужного поля.
>
> Для имени проверка может последовательно требовать data !== null, typeof data === 'object', 'name' in data и typeof data.name === 'string'. После неё строковые операции безопасны в пределах проверенного контракта. Проверка одного name ещё не доказывает весь User с другими обязательными полями. В отличие от any, unknown заставляет явно обозначить эту границу доверия.

> [!followup]- Как `never` помогает заметить новый необработанный вариант объединения?
>
> После разбора всех вариантов discriminated union в оставшейся ветке значение имеет тип never. Если позже добавить новый вариант и забыть обработчик, присваивание в never перестанет компилироваться. Это проверяет полноту разбора известных компилятору вариантов.
>
> ~~~ts
> type Result = { status: 'ok'; value: number } | { status: 'error'; message: string };
> function describe(result: Result): string {
>   switch (result.status) {
>     case 'ok': return String(result.value);
>     case 'error': return result.message;
>     default: {
>       const missing: never = result;
>       throw new Error('Unexpected result: ' + String(missing));
>     }
>   }
> }
> ~~~
>
> Добавление варианта status: 'pending' потребует новой ветки. Но утверждение типа на непроверенном JSON может нарушить модель: внешние значения сначала валидируют. never сам не проверяет runtime-данные.

> [!followup]- Превращает ли as User значение unknown в проверенного пользователя?
>
> Нет: после as User компилятор разрешит работу как с User, но фактическое значение не изменится. Если там null или объект без нужных полей, ошибка проявится при использовании. Такое утверждение лишь переносит ответственность за правильность предположения на автора.
>
> Для внешних данных нужна функция разбора или схема, которая проверяет все обязательные поля и возвращает User либо ошибку. Пользовательскому предикату value is User компилятор тоже доверяет, поэтому его реализацию нужно проверять на некорректных данных. Утверждение допустимо, когда инвариант доказан другим способом, а причина локально понятна; оно не должно маскировать неизвестный контракт.

## Как работают сужение типа и отличительное поле?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Если значение имеет несколько возможных типов, проверка в коде помогает TypeScript уточнить доступные операции. Например, после `typeof value === "string"` внутри ветки доступны строковые методы. Это называется сужением типа; оно учитывает проверки и поток выполнения.
>
> Для сложных состояний удобно общее отличительное поле с литеральным значением: `{status: "success", data: User}` или `{status: "error", error: string}`. После проверки status доступны поля соответствующего варианта. Так невозможные сочетания лучше исключать моделью, а не набором независимых boolean-флагов.
>
> Функция проверки типа может объявить результат как `value is User`. TypeScript доверяет этой записи, поэтому сама функция должна проверить объект, `null`, массивы и типы обязательных полей.

> [!followup]- Почему typeof null недостаточно для проверки объекта?
>
> В JavaScript typeof null возвращает 'object'. Поэтому условие typeof value === 'object' оставляет возможность null, и TypeScript при strictNullChecks учитывает её. Перед чтением свойства добавляют value !== null.
>
> Но и эта пара условий допускает массивы, Date и другие объекты. Для конкретного входного формата проверяют наличие нужных полей и тип каждого значения, при необходимости исключают массив через Array.isArray. Сужение означает доказанный набор свойств в данной ветке, а не превращение любого объекта в предметный тип. Полезные тесты валидатора: null, массив, пустой объект и объект с неверным типом поля.

> [!followup]- Чем объединение вариантов состояния удобнее нескольких независимых флагов?
>
> Флаги loading, hasError и hasData допускают комбинации, смысл которых может быть не определён: например, ошибка без сообщения или «успех» без данных. Объединение связывает состояние с обязательными полями: {status: 'loading'}, {status: 'success', data: User}, {status: 'error', error: string}.
>
> После проверки status компилятор знает доступные поля. Это упрощает отрисовку и проверку переходов. Модель должна отражать продуктовый сценарий: если при повторной загрузке показываются прежние данные, нужно явно описать такой вариант, а не запрещать его ради красивого union. Типы ограничивают допустимые значения, но сами не выполняют переходы.

> [!followup]- Как заметить, что после добавления status обработчик стал неполным?
>
> В switch по отличительному полю проверяют, что после всех веток остаток имеет тип never, либо передают его функции assertNever(value: never). При добавлении варианта этот вызов получает реальный тип необработанного состояния и вызывает ошибку компиляции.
>
> Простой default с возвратом пустой строки такой защиты не даёт: новый вариант тихо попадёт в него. Полезно временно добавить состояние и убедиться, что проверка падает именно в обработчике. Отдельно проверяют пользовательский результат каждой ветки и валидируют входные данные: полнота switch относительно TypeScript-типа не означает полноту относительно любого JSON.

## Когда использовать type и interface?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Оба способа описывают свойства объекта и могут использовать параметры типов. `interface` расширяется через `extends`; объявления одного интерфейса могут объединяться. `type` задаёт имя любому типу: объекту, объединению, кортежу, примитиву или результату преобразования типов.
>
> Для описания объекта подходят оба способа, поэтому важны соглашения проекта. Для объединения нескольких вариантов состояния используют type. Если API должен позволять дополнять существующее объявление интерфейса новыми полями, может быть полезен interface. Пересечение A & B требует одновременно выполнить требования обоих типов: несовместимые свойства могут получить тип never.
>
> Оба описания типов стираются при преобразовании в JavaScript. Ни type, ни interface не проверяет полученный JSON во время работы программы и не создаёт объект.

**Уточнения**

- Что произойдёт с двумя объявлениями одного interface?
- Что значит {id: string} & {id: number}?
- Можно ли описать объединение типов через `interface`?

**Критерии ответа:** Выбираю способ описания по необходимости объединять варианты или расширять интерфейс; объясняю объединение объявлений и понимаю, что описание типа не проверяет данные во время работы программы.

**Изучить:** [[Фронтенд/TypeScript/02. Псевдонимы типов и интерфейсы|Полное объяснение]]

**Практика:** [[Фронтенд/TypeScript/09. Практикум по TypeScript|Проверить на задаче]]

> [!followup]- Что произойдёт с двумя объявлениями одного interface?
>
> В одной подходящей области объявления интерфейса с одним именем объединяются. Если одно содержит id, а другое name, результирующий интерфейс требует оба поля. Повторное свойство должно иметь совместимое объявление; нельзя безнаказанно объявить id сначала string, затем number.
>
> Механизм полезен для предусмотренного расширения типов библиотеки и module augmentation. Но случайное глобальное объявление может неожиданно объединиться с чужим. Поэтому учитывают область видимости и модульность файла. Type alias повторно объявлять так нельзя. Объединение интерфейсов существует только на уровне типов и не добавляет поля реальным объектам.

> [!followup]- Что значит {id: string} & {id: number}?
>
> Пересечение требует выполнить оба ограничения одновременно. У свойства id должен получиться тип string & number, то есть never: обычного значения, одновременно являющегося строкой и числом, нет. Это не выбор одного из типов и не правило «последний победил».
>
> Такой тип обычно указывает на конфликт контрактов. Если требуется заменить тип поля, сначала исключают его через Omit<Original, 'id'>, затем добавляют новое описание. Если допустимы два разных варианта, рассматривают объединение. Операция & не выполняет слияние объектов во время исполнения; фактическое объединение через spread имеет собственные правила перезаписи свойств.

> [!followup]- Можно ли описать объединение типов через `interface`?
>
> Непосредственно объявить interface как A | B нельзя: интерфейс описывает объектный контракт, а для объединения используют type Result = Success | Failure. Также интерфейс не может extends произвольное объединение с различающимися наборами полей.
>
> При этом отдельные варианты удобно описать интерфейсами, а затем объединить type alias. Сам interface может содержать свойство с union, например status: 'ok' | 'error', но это не связывает статус с другими полями так же строго, как объединение целых объектов. Выбор синтаксиса определяется требуемой моделью, а не общим правилом «interface лучше type».

## Зачем нужны обобщённые типы?

**ID вопроса:** Зачем нужны обобщённые типы — generics?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Параметр типа сохраняет связь между аргументами и результатом, не фиксируя один конкретный тип заранее. В `function first<T>(items: T[]): T | undefined { return items[0]; }` массив строк даёт строку или `undefined`, а массив пользователей — пользователя или `undefined`. При использовании `any` эта связь потеряется.
>
> Ограничение `T extends {id: string}` позволяет использовать id внутри функции, сохраняя остальные свойства конкретного T снаружи. Компилятор часто выводит T из аргумента; вручную указывать его нужно не всегда.
>
> Параметр типа полезен, когда связывает типы аргументов и результата. Если `T` ни с чем не связан, он может только усложнить описание функции. Проверка полученных данных во время выполнения остаётся отдельной задачей.

> [!example]- Если попросят подробнее
>
> Здесь тип результата определяется конкретным выбранным полем. `T` описывает объект, `K` — один из его ключей, а `T[K]` — тип значения этого ключа.
>
> ```ts
> function getValue<T extends object, K extends keyof T>(obj: T, key: K): T[K] {
>   return obj[key];
> }
>
> const user = { id: 42, name: 'Анна' };
> const userName: string = getValue(user, 'name');
> const userId: number = getValue(user, 'id');
> ```
>
> Ключ `"email"` для этого объекта компилятор отклонит. Утверждать результат через `as` не нужно. Для объекта из сети реальные поля проверяются до вызова: параметры типов сами такую проверку не выполняют.
>
> [Ограничения параметров типов и keyof в документации TypeScript](https://www.typescriptlang.org/docs/handbook/2/generics.html#using-type-parameters-in-generic-constraints).

> [!followup]- Почему first<T> лучше first(items: any[]): any?
>
> Generic сохраняет связь: массив пользователей даёт пользователя, массив строк — строку. any стирает её и позволяет вызывающему коду обращаться к несуществующим полям без предупреждения. Для потенциально пустого массива результат должен включать undefined.
>
> Например, function first<T>(items: readonly T[]): T | undefined { return items[0]; } принимает и обычный, и readonly-массив, не требуя права его менять. Если нужно обещать результат без undefined, вход должен гарантировать непустоту, например кортеж readonly [T, ...T[]]. Сам параметр T не проверяет элементы во время исполнения и не устраняет пустой массив.

> [!followup]- Как ограничить ключ параметром K extends keyof T?
>
> keyof T задаёт допустимые ключи, а отдельный K сохраняет конкретный выбранный ключ. Возвращаемый T[K] связывает результат именно с его свойством, вместо объединения всех значений объекта.
>
> ~~~ts
> function get<T, K extends keyof T>(object: T, key: K): T[K] {
>   return object[key];
> }
> const user = { name: 'Анна', age: 30 };
> const age: number = get(user, 'age');
> // @ts-expect-error: отсутствующее свойство
> get(user, 'email');
> // @ts-expect-error: age имеет числовой тип
> const text: string = get(user, 'age');
> ~~~
>
> Если ключ пришёл произвольной строкой из API, его сначала проверяют. Утверждение key as keyof T не доказывает наличие свойства. Необязательный ключ также может дать undefined в результате.

> [!followup]- Почему функция parse<T>(json: string): T без проверки не доказывает правильность данных?
>
> Вызывающий код выбирает T, но тип стирается при компиляции: JSON.parse не получает описания ожидаемой структуры. Функция, которая лишь возвращает JSON.parse(json) as T, позволяет обещать любой тип независимо от содержимого строки. Корректный JSON может при этом быть неверным User.
>
> Без валидатора честный результат — unknown. Для получения T парсер должен принять runtime-схему или функцию проверки и действительно применить её к разобранным данным. Разделяют ошибку синтаксиса JSON и ошибку структуры/значений. Так generic сохраняет связь с реальным проверяющим механизмом, а не создаёт видимость безопасности одной аннотацией.

## Как работают keyof, typeof и доступ T[K]?

> [!answer]- Короткий ответ — 30–90 секунд
>
> keyof даёт набор допустимых ключей типа. typeof в позиции типа получает тип существующего значения. T[K] описывает тип свойства по ключу. Вместе они позволяют связать объект, допустимый ключ и точный результат функции getValue.
>
> В редакторе профиля `keyof User` ограничивает допустимые поля, а `User[K]` задаёт тип нового значения для выбранного поля. Нельзя передать строку вместо числа возраста, если сигнатура сохраняет связь конкретного ключа и значения.
>

> [!followup]- Чем Record с конечным набором ключей отличается от Record<string, V>?
>
> Record<'home' | 'settings', Page> требует свойства для обоих известных ключей. Это удобно для полного реестра: пропущенный пункт заметит компилятор. Record<string, Page> описывает значения произвольных строковых ключей, но не создаёт бесконечное число записей в объекте.
>
> При чтении неизвестного ключа фактически может прийти undefined. Это отражают через noUncheckedIndexedAccess, явный Page | undefined или Map.get. Для необязательного подмножества известных ключей подходит Partial<Record<Key, Page>>. Record преобразует только тип; он не заполняет объект и не валидирует словарь, полученный снаружи.

> [!followup]- Что ограничивает индексная сигнатура и как она влияет на именованные поля?
>
> Сигнатура [key: string]: number говорит, что доступные строковые свойства должны иметь числовые значения. Поэтому добавление обычного поля title: string в тот же тип конфликтует с сигнатурой: именованные свойства тоже должны ей соответствовать.
>
> Если у сущности есть метаданные и динамический словарь другого типа, проще разделить их: {title: string, values: Record<string, number>}. Это яснее, чем расширять значение индекса до большого union ради одного исключения. Индексная сигнатура не гарантирует, что каждый ключ существует; при чтении динамических данных отдельно учитывают undefined и настройки компилятора.

> [!followup]- Как необязательное поле влияет на T[K] и последующее чтение значения?
>
> Если User содержит name?: string, то User['name'] при strictNullChecks включает undefined: поле может отсутствовать. Индексированный доступ извлекает тип свойства вместе с этой возможностью, а не превращает его в обязательное.
>
> Перед строковой операцией значение проверяют, используют optional chaining или осмысленное значение по умолчанию. NonNullable<User['name']> уберёт null/undefined из типа, но не исправит фактические данные. exactOptionalPropertyTypes уточняет допустимость записи undefined в необязательное поле; при чтении отсутствующего свойства undefined всё равно остаётся возможным. Проверку наличия и правило записи не стоит смешивать.

> [!followup]- Что меняет noUncheckedIndexedAccess при чтении словаря и массива?
>
> Опция добавляет возможность undefined там, где тип индексируемой структуры не гарантирует наличие элемента: например, у словаря с произвольным строковым ключом и при доступе к обычному массиву по индексу. Это обнаруживает код, который молча считает любую запись существующей.
>
> Именованное обязательное свойство и известная допустимая позиция кортежа имеют более сильный контракт. Для обычного массива проверка длины не всегда даёт компилятору нужное сужение индексного доступа; часто проще сохранить элемент в переменную и проверить её или использовать for...of. Опция не меняет runtime и не входит автоматически в strict.
>
> Источник: [TypeScript — noUncheckedIndexedAccess](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html).

## Что такое отображаемые и условные типы?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Отображаемый тип преобразует набор свойств, например делает их необязательными. Условный тип выбирает результат по проверке extends. Когда проверяется непосредственно параметр типа, условие может применяться отдельно к вариантам объединения. infer позволяет извлечь часть структуры, например тип результата функции.
>
> `Partial<User>` подходит для объекта частичного обновления, `Pick<User, "id" | "name">` — для небольшой проекции данных. Это только преобразования типов: допустимость изменения конкретного поля и непустой PATCH проверяются по отдельному контракту.
>

Изучить: [[Собеседования/Практика/TypeScript#Построить вспомогательный тип по шагам|разобрать запись по частям]].

> [!followup]- Что меняют Partial, Required, Readonly, Pick и Omit и копируют ли они объект?
>
> Partial делает свойства необязательными, Required — обязательными, Readonly запрещает запись через полученный тип, Pick оставляет выбранные свойства, Omit исключает выбранные. Это преобразования типов, обычно одного уровня; они не создают новый объект и не меняют существующий.
>
> Например, Omit<User, 'password'> не удалит password при передаче реального User в функцию с таким параметром. Для безопасного ответа API нужно явно сформировать объект разрешённых полей. Partial<User> также не задаёт полноценный контракт PATCH: пустой объект, неизменяемый id и вложенные обновления требуют отдельных правил и runtime-проверки.

> [!followup]- Когда условный тип распределяется по union и как отключить это поведение?
>
> Если слева от extends стоит непосредственно параметр типа, условный тип применяется отдельно к вариантам объединения. Проверка string | number таким способом может дать объединение результатов для string и number. Оборачивание сторон в кортежи заставляет проверить тип целиком.
>
> ~~~ts
> type Each<T> = T extends string ? 'text' : 'other';
> type Whole<T> = [T] extends [string] ? 'text' : 'other';
> const each: Each<string | number> = 'text';
> const whole: Whole<string | number> = 'other';
> // @ts-expect-error: объединение целиком не является string
> const invalid: Whole<string | number> = 'text';
> ~~~
>
> Нужное поведение зависит от задачи: отфильтровать варианты по одному или проверить контракт всего объединения. Это вычисление типов, а не цикл над данными.
>
> Источник: [TypeScript — conditional types](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html).

> [!followup]- Как ReturnType получает результат функции и когда нужен Awaited?
>
> ReturnType<F> извлекает статический тип возвращаемого значения из типа функции F. Для существующей функции пишут ReturnType<typeof load>, потому что сам load — значение, а typeof в позиции типа получает его тип.
>
> Если load возвращает Promise<User>, ReturnType даст Promise<User>, а не User. Для результата ожидания подходит Awaited<ReturnType<typeof load>>. Эти операции не вызывают функцию, не ожидают реальный Promise и не проверяют ответ сервера. Они полезны, чтобы не дублировать контракт в нескольких местах; но контракт низкоуровневой функции не всегда стоит автоматически превращать в публичный тип приложения.

## Чем утверждение типа отличается от проверки?

> [!answer]- Короткий ответ — 30–90 секунд
>
> as и оператор ! после выражения меняют представление компилятора, но не проверяют и не исправляют данные. Условие во время выполнения действительно проверяет значение. satisfies проверяет соответствие типу, сохраняя более точный выведенный тип выражения. Не использую утверждение для сокрытия неизвестного результата API.
>
> Объект настройки маршрутов можно проверить через `satisfies`, сохранив конкретные ключи для последующего вывода типов. Для ответа сети это не замена проверке: неизвестные данные сначала валидируют, а не убеждают компилятор утверждением `as`.
>

> [!followup]- Почему успешный JSON.parse ещё не означает, что получен нужный тип данных?
>
> JSON.parse проверяет синтаксис JSON. Строка 'null', число и объект с неверным price могут быть корректным JSON, но не соответствовать модели приложения. В стандартной типизации результат JSON.parse имеет any, поэтому дальнейшие ошибки легко скрываются.
>
> На границе лучше присвоить результат переменной unknown и передать валидатору. Он проверяет обязательные поля, типы и нужные ограничения, затем возвращает предметное значение либо понятную ошибку. Ошибку синтаксиса и ошибку контракта полезно различать для диагностики. Оборачивание JSON.parse в generic без такой проверки только меняет статическое обещание.

> [!followup]- Почему as HTMLInputElement после querySelector может скрыть ошибку?
>
> querySelector может вернуть null, а найденный элемент не обязательно input. Утверждение as HTMLInputElement не меняет ни отсутствие узла, ни его фактический класс. Обращение к value затем может упасть или работать не по ожидаемому контракту.
>
> Для произвольного селектора проверяют найденный узел, например через instanceof HTMLInputElement в соответствующем документе. Типовой аргумент querySelector<HTMLInputElement> тоже является обещанием компилятору, а не runtime-проверкой селектора. Для чужого iframe учитывают отдельные конструкторы его окна. В компонентном коде сначала используют принятую работу с refs и жизненным циклом, чтобы не искать ещё не созданный узел.

> [!followup]- Почему лишнее поле запрещено в литерале, но может пройти через переменную?
>
> Для свежего объектного литерала в контексте известного типа TypeScript дополнительно проверяет лишние свойства. Это помогает заметить опечатку. Переменная с более широкой структурой может быть совместима по обычным структурным правилам, если содержит все требуемые свойства.
>
> Например, объект с id и secret можно передать функции, ожидающей только id. Тип параметра не удалит secret: сериализация всего аргумента передаст и его. Поэтому эту проверку нельзя использовать как фильтр API-данных. Если нужны только разрешённые поля, создают явную проекцию; для внешнего входа применяют выбранные правила runtime-валидации.

## Как работают структурная типизация и проверка лишних полей?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Совместимость обычно определяется набором свойств, а не названием типа. Для нового объектного литерала в некоторых позициях дополнительно проверяются лишние поля. Переменная с более широкой структурой может быть совместима. Поэтому ошибка литерала не означает, что все объекты с дополнительным полем запрещены.
>
> Объект полного профиля можно передать функции, которой нужны только `id` и `name`. Лишние данные физически не исчезнут: если функция отправляет весь объект дальше, тип узкого параметра не предотвращает случайную передачу дополнительных полей.
>

> [!followup]- Зачем нужна метка номинального типа для строковых идентификаторов?
>
> Структурно UserId и OrderId, заданные просто как string, взаимозаменяемы. Метка, например пересечение строки с readonly-свойством на unique symbol, позволяет компилятору различать эти роли и ловить случайную передачу идентификатора заказа вместо пользователя.
>
> Метка сама не проверяет формат и обычно не существует в runtime. Её назначают в одном понятном месте после нужной проверки или получения доверенного значения. Если повсюду писать as UserId, защита теряет смысл. Такой приём полезен там, где путаница реальна и дорого обходится; каждому локальному string отдельный бренд обычно не нужен.

> [!followup]- Как private-поля влияют на структурную совместимость классов?
>
> Обычно классы сравниваются по структуре экземпляра. Но при наличии private или protected совместимость учитывает происхождение таких членов: одноимённые private-поля из двух независимых классов не делают экземпляры совместимыми. Общий унаследованный член имеет общее происхождение.
>
> Это позволяет получить ограничение, похожее на номинальное, внутри структурной системы. При этом private TypeScript в первую очередь ограничивает доступ на уровне компилятора и отличается от JavaScript-поля #secret с runtime-приватностью. Для настоящего сокрытия данных нельзя полагаться только на стираемый модификатор. Проверяют отдельно совместимость типов и фактическую доступность поля в JavaScript.

> [!followup]- Почему функция с меньшим числом параметров может подойти как callback?
>
> Callback вправе игнорировать аргументы, которые ему передаёт вызывающий код. Поэтому функция, использующая только value, может подходить туда, где её вызовут с value и index. Обратное небезопасно: функция, требующая второй аргумент, не должна попадать туда, где его не обещают.
>
> Совместимость типов самих параметров — отдельный вопрос. При strictFunctionTypes обычные функциональные типы проверяются строже: обработчик только одного узкого варианта не подходит для любого широкого входа. У методов есть исключения совместимости, поэтому нельзя свести правило к сравнению количества аргументов. Сигнатура должна описывать реальные разрешённые вызовы.

## Чем объединение типов отличается от пересечения?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Объединение допускает одно из нескольких значений; для особых операций нужно уточнить вариант. Пересечение требует одновременно выполнить ограничения нескольких типов. Противоречивые требования к полю могут дать never. Эти операции над типами сами по себе не объединяют объекты в работающей программе.
>
> Ответ сохранения может быть либо `{ ok: true, id }`, либо `{ ok: false, error }`. Пересечение `User & Permissions` описывает объект, содержащий обе части; чтобы создать его во время выполнения, всё равно нужна операция над самими данными.
>

> [!followup]- Как общее отличительное поле помогает разобрать объединение объектов?
>
> Каждый вариант получает одноимённое поле с отдельным литеральным значением, например ok: true и ok: false. Проверка этого поля позволяет компилятору выбрать вариант целиком: в успешной ветке появляется id, в ошибочной — error.
>
> Если написать один объект с ok: boolean, id?: string и error?: string, связь ослабнет: возможны оба поля или отсутствие обоих. Отличительное поле должно быть частью проверенного контракта, а не случайной строкой из сети. Для полноты обработчика добавляют проверку остатка через never и отдельно продумывают изменение модели при новом варианте ответа.

> [!followup]- Почему набор необязательных свойств не всегда заменяет объединение вариантов?
>
> Тип {email?: string, phone?: string} допускает объект без обоих полей и объект с обоими. Он не выражает требование «выбран конкретный канал и у него есть адрес». Лучше задать варианты с отличительным полем: {kind: 'email', email: string} | {kind: 'phone', phone: string}.
>
> Если нужно строго запретить чужое поле, дополнительно моделируют этот запрет и учитывают правила лишних свойств и optional-полей. Сам union не является универсальной проверкой точного состава объекта. Для внешних данных ограничения проверяются во время исполнения; тип помогает не нарушать уже принятую модель внутри приложения.

> [!followup]- Чем конфликт свойств при interface extends отличается от пересечения типов?
>
> При extends несовместимое переопределение унаследованного свойства обычно даёт ошибку в самом объявлении интерфейса. Это быстро показывает конфликт. Пересечение A & B может быть допустимым объявлением типа, но несовместимые требования к свойству сведут его к never, и проблема проявится при попытке построить значение.
>
> Например, string и number для одного id не означают замену типа в дочернем контракте. Если замена намеренная, явно исключают поле из основы через Omit и добавляют новый вариант. Если контракты должны выполняться одновременно, конфликт нужно решить по смыслу данных, а не спрятать утверждением типа.

## Как типизировать функцию с разными вариантами вызова?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Если результат зависит от типа входа, использую обобщённый параметр или перегрузки. Сигнатура реализации должна покрыть все разрешённые вызовы. Независимые варианты часто проще выразить объединением типов, чем длинным списком перегрузок. Проверяю удобство вывода и ошибки на примерах вызывающего кода.
>
> Обёртка над функцией может сохранить типы её аргументов и результата вместо `(...args: any[]) => any`. Перегрузки нужны, когда варианты вызова дают разные результаты; если все варианты возвращают одно и то же, часто достаточно объединения параметров.
>

> [!followup]- Как необязательный аргумент отличается от аргумента с undefined в типе?
>
> В function find(id?: string) аргумент можно не передавать; внутри он имеет тип string | undefined. В function find(id: string | undefined) позиция остаётся обязательной, хотя передаваемое значение может быть undefined. Параметр со значением по умолчанию получает его при пропуске или undefined, но не при null.
>
> Выбор должен соответствовать реальному API. Не следует делать параметры callback необязательными лишь потому, что конкретному обработчику они не нужны: это означает, что вызывающая сторона вправе их не предоставить. Если варианты аргументов связаны между собой, лучше выразить комбинации кортежами или перегрузками.

> [!followup]- Как кортеж для rest-параметров сохраняет связь между аргументами?
>
> Объединение кортежей может описать разрешённые наборы аргументов целиком. Это сильнее, чем независимые объединения для каждого параметра, которые разрешили бы неверные комбинации.
>
> ~~~ts
> function send(...args: ['count', number] | ['name', string]) {
>   if (args[0] === 'count') return args[1].toFixed(0);
>   return args[1].toUpperCase();
> }
> send('count', 2);
> send('name', 'Анна');
> // @ts-expect-error: count требует число
> send('count', 'два');
> ~~~
>
> Проверка первого элемента сужает связанный вариант кортежа. Решение подходит для небольшого ясного набора вызовов; огромный union команд может быть удобнее представить объектами с отличительным полем. Во время исполнения всё равно нужен код, выполняющий действие.

> [!followup]- Какой результат даст ReturnType для перегруженной функции?
>
> ReturnType извлекает тип результата из последней доступной сигнатуры перегрузки, а не моделирует выбор перегрузки для конкретного аргумента. Поэтому результат вызова и результат ReturnType могут иметь разную точность.
>
> ~~~ts
> declare function convert(value: string): number;
> declare function convert(value: number): string;
> declare function convert(value: string | number): string | number;
> const specific: number = convert('42');
> type Result = ReturnType<typeof convert>; // string | number
> const result: Result = '42';
> // @ts-expect-error: boolean не входит в результат
> const invalid: Result = true;
> ~~~
>
> Сигнатура реализации обычной перегруженной функции не становится дополнительным публичным вариантом вызова. Если нужна точная зависимость входа и выхода в преобразовании типов, её описывают отдельно, а не ожидают от ReturnType анализа всех возможных вызовов.
>
> Источник: [TypeScript — вывод из перегрузок](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html).

## Как типизировать динамический словарь?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Record<K,V> или индексная сигнатура задают допустимые ключи и значения. Но тип словаря со строковым ключом не гарантирует фактическое наличие любой строки. Учитываю отсутствие значения, настройки проверки индексного доступа и контракт Map.get. Конечный набор ключей отличается от произвольного string.
>
> Для кэша пользователей по `id` отсутствие записи — нормальное состояние. `Map.get(id)` явно возвращает `User | undefined`; для объектного словаря учитывают `noUncheckedIndexedAccess`, иначе статический тип может скрыть отсутствие ключа.
>

> [!followup]- Как учесть отсутствие записи при чтении динамического словаря?
>
> У Record<string, User> в runtime может не быть запрошенного ключа. noUncheckedIndexedAccess отражает это при чтении как User | undefined. Затем значение сохраняют в переменную и проверяют перед использованием; запасное поведение зависит от задачи: загрузить, показать отсутствие или вернуть ошибку.
>
> Если опция не включена, возможность отсутствия можно явно задать типом значения либо использовать Map<string, User>, у которого get возвращает User | undefined. Non-null assertion после индексного доступа не создаёт запись. Для полного реестра с конечным набором ключей контракт другой: наличие каждого известного ключа можно потребовать статически.

> [!followup]- Почему обычный объект-словарь требует внимания к ключам прототипа?
>
> У обычного объекта есть прототип. Поэтому чтение dictionary['toString'] может найти унаследованное свойство, хотя свою запись приложение не добавляло. Оператор in тоже учитывает цепочку прототипов. Для проверки собственного ключа используют Object.hasOwn.
>
> Если ключи произвольные, удобнее Map или словарь с null-прототипом через Object.create(null). Но типизация сама не создаёт нужный runtime-объект: Record<string, Value> не удаляет прототип и не защищает небезопасное слияние входных ключей. Разделяют проверку собственного наличия, проверку значения и способ построения словаря; особенно внимательно работают с данными извне.

> [!followup]- Как типизировать реестр меню и заметить пропущенный пункт?
>
> Для заранее известного набора разделов используют Record<MenuId, MenuItem>, где MenuId — union конкретных ключей. Новый ключ в union заставит дополнить полный реестр. satisfies позволяет проверить объект реестра и сохранить его конкретную структуру для дальнейшего вывода типов.
>
> Если пункты могут отсутствовать по настройке, это другой контракт: Partial<Record<MenuId, MenuItem>> и обработка отсутствия. Права доступа лучше применять к полному реестру отдельным шагом; скрытый пункт меню не заменяет серверную авторизацию. Для внешней конфигурации TypeScript недостаточно: её формат проверяют при загрузке.

## Что гарантирует readonly?

> [!answer]- Короткий ответ — 30–90 секунд
>
> readonly ограничивает присваивание через конкретный тип и обычно действует неглубоко. Другая ссылка может позволить изменить тот же объект. ReadonlyArray запрещает изменяющие методы через эту типизированную ссылку. Замораживание объекта во время выполнения — отдельный механизм.
>
> Функция расчёта может принимать `readonly CartItem[]`, чтобы случайно не вызвать `sort` или `push` на входе. Это не запрещает другим участникам менять тот же массив и не делает вложенные объекты неизменяемыми во время выполнения.
>

> [!example]- Если попросят подробнее
>
> Запрет действует через конкретный типизированный доступ. `readonly items: CartItem[]` запрещает заменить поле `items`, но не запрещает `items.push()`. Для запрета изменения самого массива через эту ссылку нужен `readonly CartItem[]` или `ReadonlyArray<CartItem>`.
>
> Даже readonly-массив не делает свойства его объектов readonly. `Object.freeze` — отдельная операция времени выполнения и тоже неглубокая. Поэтому в ответе нужно назвать, что именно защищается: поле, контейнер или вложенные данные.
>
> [Документация TypeScript о readonly](https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties).

> [!followup]- Защищает ли Readonly<T> вложенные объекты?
>
> Readonly<T> делает readonly собственные свойства описываемого уровня, но не преобразует типы вложенных объектов рекурсивно. Поэтому заменить state.user может быть запрещено, а изменить state.user.name — разрешено. Тип readonly также не вызывает Object.freeze.
>
> Если контракт требует запретить вложенную запись, у вложенного объекта тоже задают readonly-поля. Даже тогда другая изменяемая ссылка может менять тот же runtime-объект. Это ограничение операций через определённое типизированное представление, а не универсальная неизменяемость данных. Для проверки полезно отдельно попробовать замену ветви, изменение поля и запись через существующий изменяемый alias.

> [!followup]- Что нужно изменить в типе для запрета записи во вложенные поля?
>
> Нужно описать readonly на каждом требуемом уровне, например Readonly<{user: Readonly<{name: string}>}>. Для вложенного массива выбирают readonly-массив и отдельно readonly-тип его элементов, если запрещена и мутация элементов.
>
> Рекурсивный DeepReadonly может сократить описание, но его контракт зависит от структур: функции, Map, Set, классы и циклические модели нельзя бездумно приравнять к обычному объекту полей. Часто достаточно явно описать несколько границ состояния. Такой тип не выполняет глубокое замораживание в runtime и не устраняет изменяемые ссылки на тот же объект; правила обновления данных остаются частью архитектуры.

> [!followup]- Что даёт as const и замораживает ли оно данные во время выполнения?
>
> Const assertion сохраняет узкие литеральные типы, делает свойства объектного литерала readonly, а литерал массива — readonly-кортежем. Это полезно для фиксированных настроек и получения union из списка значений. Но as const не вызывает Object.freeze и не блокирует изменение через другую допустимую ссылку.
>
> ~~~ts
> const values = [1, 2];
> const config = { mode: 'quiet', values } as const;
> values.push(3);
> console.log(config.values.length); // 3
> // @ts-expect-error: нельзя переназначить readonly-свойство
> config.mode = 'quiet';
> ~~~
>
> Внешний массив values сохраняет свой изменяемый тип: const assertion не делает ранее созданный объект глубоко неизменяемым. Проверять нужно и выведенный тип, и реальные изменения данных.
>
> Источник: [TypeScript — const assertions](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-4.html).

## Чем enum отличается от объединения литералов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> enum обычно создаёт объект во время выполнения; объединение литералов существует только в типовой модели. Для набора строк часто достаточно строковых литералов и объекта с константами. Поведение const enum и совместимость нужно проверять по настройкам компиляции и способу потребления библиотеки.
>
> Статусы, приходящие из API строками `draft` и `published`, удобно описать объединением литералов. Если нужны значения во время выполнения, добавляют объект `as const`; принадлежность неизвестной строки этому набору всё равно проверяют.
>

- Как работает обратное отображение у числового enum в TypeScript?
- Как enum и объединение литералов отличаются по размеру сборки?

> [!followup]- Как работает обратное отображение у числового enum в TypeScript?
>
> Обычный числовой enum компилируется в runtime-объект с двумя направлениями. Для `enum Status { Draft = 1, Published = 2 }` выражения `Status.Draft` и `Status[1]` дают соответственно 1 и `'Draft'`. Поэтому `Object.keys(Status)` содержит и имена, и строковые представления числовых ключей.
>
> У строкового enum такого обратного отображения нет. Если нужны варианты для UI, лучше явно перечислить нужные значения или фильтровать результат по согласованному типу; механическое `Object.values` числового enum даст смесь. При двух именах с одним числом обратный ключ укажет на последнее присваивание, так что он не годится для восстановления исходного имени.

> [!followup]- Как enum и объединение литералов отличаются по размеру сборки?
>
> Объединение `type Status = 'draft' | 'published'` удаляется при компиляции; обычный enum создаёт runtime-объект. Числовой enum дополнительно генерирует обратные записи. Если значения нужны только для проверки типов, литеральное объединение не добавит JavaScript.
>
> Если нужны варианты для dropdown или runtime-валидации, сам набор всё равно должен существовать, например `const statuses = ['draft', 'published'] as const; type Status = typeof statuses[number];`. Фактический вклад enum в bundle зависит от сборщика, минификации и использования экспорта; сравнивайте итоговые файлы. `const enum` может подставляться значениями, но у него свои ограничения на границе библиотек и при трансформации отдельных файлов.

> [!followup]- Какие ограничения isolatedModules накладывает на использование enum?
>
> `isolatedModules` предупреждает о конструкциях, которые нельзя надёжно преобразовать, видя только один файл. В частности, нельзя ссылаться на член *ambient const enum*: его значение объявлено в типах, а runtime-объекта может не быть. Проблема особенно заметна у библиотеки, публикующей такой `const enum` в `.d.ts`.
>
> Например, `declare const enum Mode { Read = 1 }` и `Mode.Read` требуют подстановки числа, но пофайловый трансформер не обязан читать чужую декларацию. Обычный enum не запрещён этим флагом. Для общедоступных констант удобно опубликовать runtime-объект `as const` и вывести из него тип. У локального `const enum` проверьте фактический emit своей цепочки сборки.

## Как типизировать ошибки и асинхронный API?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Promise<T> описывает успешный результат, но стандартный тип не кодирует тип отклонения. Значение catch проверяю как unknown. Ожидаемые предметные исходы можно вернуть объединением с отличительным полем. Не выдаю статический тип успешного результата за гарантию отсутствия сетевой ошибки.
>
> Ожидаемый отказ сохранения, например конфликт версии, можно вернуть отдельным вариантом результата. Сетевой сбой остаётся возможным отклонением Promise; обработчик `catch` уточняет неизвестное значение, прежде чем читать `message`.
>

> [!followup]- Когда instanceof надёжно сужает ошибку в catch?
>
> `catch (error)` при строгой настройке получает `unknown`. `if (error instanceof Error)` позволяет безопасно обратиться к `message` в типичном случае, а проверка собственного класса помогает различить ошибки одного процесса. Но JavaScript разрешает бросить строку или объект, а `Error` из другого realm может иметь другой прототип.
>
> Например, `throw 'offline'` не пройдёт `instanceof Error`, поэтому нужен общий fallback. Ошибка от сервера после JSON не является экземпляром локального класса; проверяйте валидированные поля и код предметной ошибки. Не заменяйте проверку `error as Error`: утверждение не создаёт поля и не доказывает происхождение значения.

> [!followup]- Когда вернуть Result вместо отклонённого Promise?
>
> Для ожидаемого исхода, который вызывающий должен обработать явно, подходит discriminated union: `type Result<T> = { ok: true; value: T } | { ok: false; code: 'conflict' | 'invalid' };`. `Promise<Result<Order>>` означает, что успешный обмен может закончиться предметным отказом, например конфликтом версии, и интерфейс предложит перечитать данные.
>
> Сетевой сбой может остаться отклонением Promise, если таков контракт; `Promise<T>` не типизирует rejection. Можно также перевести транспортную ошибку в отдельный вариант Result, если потребители должны её обрабатывать единообразно. Главное — документировать границу: отсутствие ветки `ok: false` не означает отсутствия исключений во время выполнения.

> [!followup]- Как описать отмену асинхронной операции в TypeScript API?
>
> Принимайте `AbortSignal` и явно опишите, что получит вызывающий при отмене. Например, `loadProfile(id: string, signal?: AbortSignal): Promise<Profile>` передаёт сигнал в `fetch` и прекращает дальнейшую обработку, если сигнал сработал. Если отмена — ожидаемый исход интерфейса, можно вернуть вариант `{ ok: false, code: 'cancelled' }`.
>
> У сигнала есть `reason`, и он не обязан быть экземпляром конкретного класса. Не определяйте любую отмену только по строке сообщения. Для собственной долгой работы проверяйте сигнал до старта и между этапами, снимайте listener после завершения. Отмена не следует из `Promise<T>` и не отменяет серверный побочный эффект, уже произошедший до сигнала.

## Что такое кортеж и кортеж с переменным хвостом?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Кортеж описывает позиции и тип каждой позиции, включая необязательные элементы и хвост. Кортеж с переменным набором позволяет сохранять типы аргументов обёртки или композиции функций. Обычный массив T[] не задаёт точного количества и назначения элементов.
>
> Координаты `[longitude, latitude]` имеют фиксированные позиции, поэтому кортеж понятнее `number[]`. В обёртке над callback кортеж аргументов сохраняет их число и типы; он не проверяет диапазон географических координат во время выполнения.
>

**Уточнения**

- Как Parameters сохраняет кортеж аргументов функции?
- Как ConstructorParameters извлекает аргументы конструктора?
- Как TypeScript выводит позиции кортежа при передаче аргументов через rest?

> [!followup]- Как Parameters сохраняет кортеж аргументов функции?
>
> `Parameters<F>` извлекает параметры функции как кортеж, сохраняя порядок, необязательные позиции и rest-хвост. Например, `Parameters<(id: string, refresh?: boolean) => void>` даёт `[id: string, refresh?: boolean]`. Это позволяет обёртке передать `...args`, сохранив вызовы `load('a')` и `load('a', true)`.
>
> Для перегруженной функции утилита извлекает параметры последней сигнатуры, а не автоматически переносит все перегрузки. Обобщённая сигнатура также может потерять связь между параметрами и результатом при отдельном извлечении типов. Если оборачиваете конкретный метод, учтите `this` отдельно: он не входит в обычный кортеж аргументов.

> [!followup]- Как ConstructorParameters извлекает аргументы конструктора?
>
> `ConstructorParameters<typeof Service>` извлекает кортеж из сигнатуры `new`. `typeof Service` здесь означает тип самого конструктора, а `Service` — тип экземпляра. Например, у `class Service { constructor(url: string, retries?: number) {} }` результатом будет `[url: string, retries?: number]`.
>
> Так можно типизировать фабрику с теми же аргументами: `function create(...args: ConstructorParameters<typeof Service>) { return new Service(...args); }`. Если нужен тип создаваемого экземпляра из конструктора, используйте `InstanceType`. Извлечённый кортеж не даёт права вызвать приватный конструктор и не заменяет runtime-валидацию аргументов из конфигурации.

> [!followup]- Как TypeScript выводит позиции кортежа при передаче аргументов через rest?
>
> Контекст определяет, видит ли TypeScript позиции или только общий массив. `const pair = ['id', 2]` обычно имеет тип `(string | number)[]`, а `['id', 2] as const` — `readonly ['id', 2]`. Если нужны изменяемые позиции с широкими типами, объявите `const pair: [string, number] = ['id', 2]`.
>
> Для адаптера `function capture<T extends unknown[]>(...args: T): T { return args; }` вызов `capture('id', 2)` выводит `[string, number]`. В отличие от общего массива, кортеж годится для передачи в функцию с двумя фиксированными параметрами. `as const` делает тип readonly и сужает литералы, но во время выполнения массив не замораживает.

## Как типизировать событие DOM и Vue-компонент?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Различаю target и currentTarget, проверяю фактический элемент и учитываю возможность null. Типы входных свойств и событий Vue должны описывать контракт, а не скрывать его за any. Для чтения DOM учитываю querySelector и момент монтирования. Проверка шаблонов требует подходящего инструмента, например vue-tsc.
>
> В обработчике ввода сначала проверяют, что `event.target` — `HTMLInputElement`, и только затем читают `value`. Для компонента событие `save` описывают с типом полезной нагрузки, чтобы вызывающий код не передал произвольный объект.
>

> [!followup]- Как обобщённый Vue-компонент связывает тип props и payload события?
>
> Задайте параметр типа в `<script setup lang="ts" generic="T">`. Например, `defineProps<{ items: readonly T[] }>()` и `defineEmits<{ select: [item: T] }>()` позволяют вывести тип выбранного элемента из переданного массива. Типы шаблона проверяйте `vue-tsc`; runtime-данные всё равно должны пройти валидацию на границе API. Обобщение не даёт Vue возможности проверить произвольный `T` при исполнении.

> [!followup]- Как типизировать Vue-кнопку, которая может отрисовать button или a?
>
> Опишите допустимые варианты через отличительный prop: например, `{ as?: 'button'; disabled?: boolean; href?: never } | { as: 'a'; href: string; disabled?: never }`. В шаблоне разветвитесь по `as`, чтобы связать конкретный элемент с его атрибутами. `<Action as="a" href="/docs" />` допустим; кнопка с `href` не соответствует контракту.
>
> У ссылки нет нативного `disabled`, а у кнопки внутри формы стоит явно выбирать `type`, обычно `button` для действия без submit. Если передаёте атрибуты вручную, не распространяйте их одновременно на обе ветки. Не усложняйте тип универсальным «любой тег», пока компоненту нужны только два понятных варианта.

> [!followup]- Как типизировать ref на DOM-элемент или компонент во Vue?
>
> Для DOM-ref учитывайте `null` до монтирования и после удаления узла. В подходящей версии Vue можно использовать `useTemplateRef<HTMLInputElement>('search')` вместе с `ref="search"` в шаблоне. Универсальный вариант — `const search = ref<HTMLInputElement | null>(null)` и совпадающее имя ref. Затем `search.value?.focus()` учитывает отсутствие элемента.
>
> Для ref на компонент типизируйте только нужный публичный интерфейс. Компоненты с `<script setup>` явно открывают методы через `defineExpose`; внутреннее состояние от этого не становится публичным. `v-if` может снова сделать ref пустым после монтирования, а утверждение `!` не меняет порядок жизненного цикла. Проверяйте шаблон и скрипт вместе через `vue-tsc`.

> [!followup]- Как сузить тип DOM-события, чтобы безопасно прочитать значение поля?
>
> `event.target` имеет общий тип `EventTarget | null` и при делегировании может указывать на дочерний элемент. Проверьте `if (event.target instanceof HTMLInputElement)`, прежде чем читать `value`. Если интересует именно элемент, на котором зарегистрирован обработчик, проверьте `event.currentTarget` вместо `target`.
>
> Например, для прямого `input`-обработчика можно прочитать `const value = target.value` до `await`. `currentTarget` привязан к текущей доставке события и после асинхронной паузы может быть `null`. У кастомного события Vue тип полезной нагрузки задаётся отдельно в `defineEmits`: событие `save` с объектом формы не нужно приводить к DOM `Event`.

## Как проверять данные внешнего API?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Тип TypeScript описывает ожидание программы, но сервер может вернуть другую структуру. Поэтому полученный JSON на границе рассматриваю как unknown и проверяю его во время исполнения: обязательные поля, их типы, допустимые значения и вложенные структуры. Это можно сделать небольшим валидатором или схемой.
>
> После успешной проверки преобразую данные в модель приложения. Неожиданный ответ должен дать понятную ошибку или безопасный отказ, а не молча превратиться в «пустой успех». `as User` только заставляет компилятор доверять разработчику; значения он не преобразует.
>
> Сетевой сбой, HTTP-ошибка, невалидный JSON и нарушение схемы — разные этапы. Например, fetch обычно не отклоняет Promise на 404: сначала проверяют response.ok, затем разбирают и валидируют тело.

> [!followup]- Как обработать null вместо объекта или строку вместо числового id?
>
> JSON принимаю как unknown. Сначала исключаю null и массив, затем проверяю поля. typeof null возвращает "object", поэтому одной проверки typeof недостаточно. Строка "42" не является числовым id: если контракт требует число, это ошибка схемы, а не повод молча вызвать Number. Утверждение as ничего не преобразует. [TypeScript: narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html).
>
> Для контракта «id — положительное безопасное целое» проверка может выглядеть так:
>
> ~~~ts
> function parseId(value: unknown): number {
>   if (
>     value === null ||
>     typeof value !== "object" ||
>     Array.isArray(value) ||
>     !("id" in value)
>   ) {
>     throw new Error("Ожидался объект с id");
>   }
>   const id = value.id;
>   if (typeof id !== "number" || !Number.isSafeInteger(id) || id <= 0) {
>     throw new Error("Некорректный id");
>   }
>   return id;
> }
> ~~~
>
> Проверяю null, {}, {id: "42"}, {id: 0}, дробное число и корректный объект. Остальные обязательные поля проверяются отдельно. Если API официально допускает строковые идентификаторы, сохраняю их строками либо явно описываю допустимое преобразование; числовое преобразование может потерять ведущие нули и точность больших id.

> [!followup]- Как показать пользователю отказ без потери ранее введённых данных?
>
> Разделяю черновик, статус запроса и подтверждённую серверную модель. Ошибка сети, HTTP, разбора JSON или схемы ответа меняет статус и сообщение, но не подменяет введённые значения пустым объектом и не закрывает форму. Пользователю сообщаю, что результат не подтверждён, и оставляю возможность исправить ввод или повторить допустимую операцию.
>
> Например, сохранение имени вернуло 200 с неожиданной структурой. Не показываю «Сохранено» только по статусу: ответ ещё должен пройти проверку контракта. При этом запись на сервере могла состояться. Сначала можно сверить состояние через чтение или статус операции; слепой повтор создания опасен без защиты API от дублей.
>
> Если ввод разрешён во время запроса, храню отправленный снимок или ревизию черновика. Успех старой отправки не должен очищать текст, введённый позднее. Проверяю это управляемой задержкой, а также отказами 500, невалидным JSON и неправильной схемой. Все проверки должны сохранять текущий текст и корректно снимать pending. fetch сам по себе не считает HTTP 500 отклонённым Promise: статус проверяется отдельно. [MDN: обработка ответа fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch#checking_response_status).

> [!followup]- Какие проверки остаются при генерации типов из OpenAPI?
>
> Типы, сгенерированные из OpenAPI, проверяют использование API в TypeScript, но не гарантируют форму конкретного ответа. Всё равно проверяйте статус и тип ответа, обрабатывайте невалидный JSON и валидируйте используемые поля: типы, обязательность, допустимые значения и вложенность. Из схемы можно генерировать и runtime-валидатор, если генератор действительно его создаёт и клиент вызывает его.
>
> Например, тип `User` требует `id: string`, но сервер может вернуть `{ "id": 12 }` при рассинхронизации версий. Обычная типовая генерация этого не остановит. После структурной проверки остаются предметные правила, которых схема не выражает, например связь двух полей. Не выдавайте неожиданный ответ за пустой успешный результат.

## Чем private и protected отличаются от приватных полей JavaScript?

> [!answer]- Короткий ответ — 30–90 секунд
>
> private и protected ограничивают доступ в типовой модели TypeScript. Поля с префиксом # имеют ограничения доступа во время выполнения по правилам JavaScript. Это разные механизмы. Они не заменяют проверку полномочий пользователя и защиту данных, отправленных за пределы приложения.
>
> TypeScript `private` помогает запретить доступ в проверяемом исходном коде, но не заменяет защиту во время выполнения. Поле `#token` обеспечивает языковую приватность внутри класса; это всё равно не место для серверного секрета в браузерном приложении.
>

> [!followup]- Какие поля доступны подклассу: private, protected и #private?
>
> Подкласс может обращаться к `protected`-членам базового класса в рамках правил TypeScript. К `private` базового класса исходный код подкласса обратиться не может. JavaScript-поле `#token` доступно только в лексической области класса, где объявлено; одноимённое `#token` в подклассе — другое поле.
>
> Например, базовый клиент может предоставить `protected buildUrl()` как точку расширения и хранить внутренний идентификатор в `#requestId`. Если подклассу нужно значение, базовый класс может открыть небольшой метод вместо поля. `protected` поддерживает контракт для наследников, но само по себе не закрывает доступ на уровне JS; для runtime-ограничения нужен `#` или замыкание.

> [!followup]- Во что компилируются private/protected и #private при генерации JavaScript?
>
> Модификаторы `private` и `protected` TypeScript удаляются из JavaScript: поле остаётся обычным свойством, если оно объявлено как runtime-поле. Например, `private count = 0` не превращается в `#count`. `#count` остаётся нативным приватным полем при соответствующем target; при понижении target TypeScript может использовать `WeakMap` и вспомогательные проверки.
>
> Точный emit зависит от target, настроек полей и трансформера. Поэтому для библиотечного контракта проверьте фактический выход сборки, а не только успешную проверку типов. Независимо от выбранного представления приватность внутри объекта не является механизмом разграничения прав между клиентом и сервером.

> [!followup]- Можно ли прочитать private-поле по имени во время выполнения?
>
> Обычное TypeScript-поле `private token` после компиляции доступно как JavaScript-свойство; модификатор проверяет исходный код, а не закрывает объект. `Object.keys` покажет поле, если оно собственное и перечисляемое. У нативного `#token` строка `'token'` или `'#token'` не обращается к закрытому слоту; `Reflect.ownKeys` его не перечисляет.
>
> Например, `Object.assign({}, instance)` может перенести обычное поле, но не `#token`. Это важно для диагностики и сериализации: явно собирайте объект ответа из разрешённых полей. Приватность слота не мешает самому классу вернуть значение через метод и не позволяет безопасно хранить серверный секрет в браузерном коде.

## Как уменьшить риск слишком сложных типов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Начинаю с понятной модели состояний и входов, затем добавляю необходимые связи между типами. Сигнатура должна помогать вызывающему коду и проверять реальный контракт. Проверяю положительные и отрицательные примеры компиляции; сложный тип, который трудно объяснить и поддерживать, может быть хуже более явного интерфейса.
>
> Тип конфигурации таблицы должен помогать выбрать существующий ключ и корректно типизировать значение ячейки. Если ошибка компилятора стала нечитаемой, лучше вынести именованные части и упростить контракт, чем добавлять новые уровни условных типов.
>

> [!followup]- Когда полезны рекурсивные условные типы и как ограничить их сложность?
>
> Они полезны, когда результат зависит от вложенной формы входного типа. Например, `type Unwrap<T> = T extends PromiseLike<infer U> ? Unwrap<U> : T` рекурсивно раскрывает вложенные Promise-подобные значения; в реальном API эту задачу уже решает `Awaited<T>`.
>
> Рекурсии нужен понятный базовый случай, а сложность растёт при широких объединениях и глубокой вложенности. Не пытайтесь вычислить все возможные пути произвольной модели, если потребителю достаточно ключей одного уровня или явных настроек. Проверьте тип на самом глубоком поддерживаемом входе и объяснимость ошибки. Если TypeScript жалуется на чрезмерную глубину, упрощайте контракт вместо зависимости от конкретного внутреннего лимита компилятора.

> [!followup]- Как измерить, что сложные типы замедляют проверку TypeScript?
>
> Снимите показатели на одинаковом наборе файлов и настройках через `tsc --extendedDiagnostics`: сравните время проверки и число инстанцирований. Для поиска горячего участка используйте трассу `--generateTrace` на небольшом воспроизводимом примере. Замерьте несколько запусков при одинаковом режиме инкрементальности.
>
> Например, если тип путей таблицы строит объединение всех вложенных ключей для десятков моделей, сравните его с контрактом из явных колонок. Упростить часто помогают именованные промежуточные типы, уменьшение распределения условных типов по union и более узкие входы. Время `tsc` — отдельная метрика от размера JavaScript и скорости приложения; ускорение одной не доказывает другое.

> [!followup]- Как проверить публичный типовой API на правильные и неправильные вызовы?
>
> Пишите небольшие примеры потребителя и компилируйте их с теми же настройками, что у поддерживаемой среды. Положительный пример проверяет не только отсутствие ошибки, но и полезный вывод: колонка `age` должна давать обработчику `number`. Отрицательный пример с `// @ts-expect-error` проверяет запрет неизвестного ключа; если ошибка исчезнет, директива станет неиспользуемой.
>
> Один ожидаемый отказ может скрыть другую ошибку на той же строке, поэтому держите пример минимальным и меняйте один аргумент. Для библиотеки проверяйте публичный импорт и при необходимости сгенерированные `.d.ts`. Типовые проверки не заменяют тест поведения во время исполнения или валидацию ответа сервера.
