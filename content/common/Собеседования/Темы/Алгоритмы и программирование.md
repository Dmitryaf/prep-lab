## Как оценивать время работы и дополнительную память?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Оцениваю рост числа операций и объёма дополнительной памяти при увеличении входа. Учитываю сортировку, копирование и вложенные поиски. Различаю худший, средний и амортизированный случай. O(N) описывает характер роста, а не точное число миллисекунд.
>
> Поиск выбранных записей через `selectedIds.includes()` для каждой строки может потребовать O(n·m). Предварительный Set обычно даёт ожидаемые O(n+m) времени и O(m) дополнительной памяти; оценка учитывает построение множества, а не только основной цикл.
>

> [!followup]- Как различить O(1), O(log n), O(n), O(n log n) и O(n²) на примерах?
>
> Зафиксируйте, что такое n и какая операция считается. Чтение известной позиции плотного массива — O(1) в обычной модели; двоичный поиск делит диапазон пополам — O(log n); один полный проход — O(n). Сортировка слиянием обрабатывает n элементов на каждом из O(log n) уровней, то есть O(n log n); перебор всех пар — O(n²).
>
> Оценивайте память отдельно: два вложенных цикла не обязаны выделять квадратичную память. Если список n заказов проверяется по m идентификаторам через `includes`, пишите O(n·m), а не O(n²), пока размеры не связаны. Отдельно уточняйте, где оценка худшая, ожидаемая или амортизированная.

> [!followup]- Как ограничения входа влияют на выбор алгоритма и оценку ресурсов?
>
> Сначала выясните максимальный размер, диапазон значений, наличие сортировки и помещается ли вход в память. Для 30 элементов проверка всех пар может быть проще и достаточна, для 100 тысяч она означает примерно пять миллиардов пар. Если числа лежат в небольшом диапазоне K, таблица частот даёт O(n + K), но при огромном K хеш-таблица экономнее.
>
> Проверьте граничные данные, которые меняют применимость: отрицательные числа нарушают монотонность простого окна по сумме, а большие суммы могут потерять точность Number. Не подменяйте пределы задачи средним размером. Если вход потоковый, учтите, сколько элементов нужно держать одновременно, и можно ли перечитать их для второго прохода.

## Чем массив отличается от связного списка?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Массив позволяет обращаться по индексу; в связном списке для поиска позиции обычно нужно пройти по ссылкам. Вставка в список выполняется за O(1), если нужный узел уже известен. Для массива стоимость зависит от операции и представления. Плотное размещение элементов может лучше использовать кэш процессора.
>
> Каталог удобно представлять массивом для перебора и доступа по индексу. Связный список облегчает вставку рядом с уже известным узлом, но поиск этого узла сам может быть линейным; во фронтенде это редко достаточная причина заменить массив.
>

> [!followup]- Почему добавление в конец динамического массива обычно амортизированно O(1)?
>
> Динамический массив хранит запас ёмкости. Пока запас есть, добавление занимает одну позицию. Когда места нет, массив выделяет более крупное хранилище и переносит элементы; эта отдельная вставка стоит O(n). При геометрическом увеличении, например удвоении, суммарное число переносов за n вставок остаётся O(n), поэтому средняя стоимость на последовательности операций постоянна.
>
> Это модель динамического массива, а не гарантия для любого JavaScript Array: движок выбирает представление, особенно для разреженных массивов. Вставка в начало или середину обычно требует сдвигать элементы. Если важны задержки отдельных операций, амортизированная оценка сама по себе не ограничивает пиковое время.

> [!followup]- Чем отличаются затраты памяти массива и связного списка?
>
> У плотного динамического массива есть хранилище элементов и запас неиспользованной ёмкости. У связного списка каждый узел хранит значение и ссылку на следующий, а двусвязный — ещё и на предыдущий; отдельные выделения памяти и служебные поля тоже стоят места. Обе структуры используют O(n), но постоянные множители и локальность обращения различаются.
>
> Например, проход по плотному массиву чисел обычно лучше использует кеш процессора, чем обход цепочки объектов. Список может быть полезен, если операции уже получают нужный узел и постоянно меняют связи. Не переносите устройство низкоуровневого массива на любой JS Array: фактическое представление и расход памяти зависят от движка и элементов.

> [!followup]- Как развернуть односвязный список и не потерять хвост?
>
> При развороте на месте держите `prev`, `current` и сохранённый `next`. Пока `current` существует, сначала сохраните `current.next`, затем направьте `current.next` на `prev` и сдвиньте обе рабочие ссылки. Новый корень — `prev` после прохода.
>
> У A → B → C после первого шага A указывает на null, а сохранённый `next` даёт продолжить с B. В конце получится C → B → A. Время O(n), память O(1), но исходные узлы меняются: другая ссылка на A увидит уже хвост. Если мутация запрещена, создайте новые узлы. Для пустого списка верните null, а циклический вход должен быть запрещён или проверен отдельно.

> [!followup]- Как реализовать очередь без постоянного сдвига массива?
>
> Для массива используйте индекс головы и добавляйте элементы в конец. Извлекая, читайте `items[head]` и увеличивайте `head`. Очищайте освобождённую ячейку, чтобы отпустить ссылку; периодически уплотняйте хранилище, когда префикс стал достаточно велик. Более предсказуемая ограниченная очередь — кольцевой буфер.
>
> Связный список тоже подходит: держите голову и хвост, добавляйте за хвост, удаляйте голову. При удалении последнего узла обнулите обе ссылки. Эти операции постоянны без поиска узла, но для каждого элемента нужен отдельный узел. Если очередь маленькая, обычный `shift()` может быть достаточным; выбирайте структуру по реальной частоте и размеру.

## Как устроена хеш-таблица?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Хеш направляет ключ в область хранения; совпадения хеша обрабатываются выбранным способом разрешения коллизий. Ожидаемый поиск часто имеет сложность O(1), но худший случай зависит от реализации и данных. Важны заполненность таблицы, изменение её размера и правило равенства ключей.
>
> Map с пользователями по id избавляет от линейного поиска пользователя для каждой строки заказа. Коллизия хешей не означает равенство ключей: структура должна различить их. Ожидаемая быстрая операция не равна гарантии одинакового времени любого входа.
>

> [!followup]- Чем открытая адресация отличается от цепочек при коллизиях хешей?
>
> При цепочках бакет хранит несколько записей с одним индексом хеша; поиск проверяет ключи в соответствующем бакете. При открытой адресации сами записи лежат в таблице, и при занятой ячейке алгоритм проверяет другие позиции по заданной последовательности, например по очереди соседние.
>
> Если два ключа попали в бакет 3, цепочки оставят оба рядом в бакете, а линейное пробирование поставит второй в следующую подходящую ячейку. При удалении в открытой адресации нельзя всегда просто сделать слот пустым: поиск может преждевременно остановиться; используют метки или перестройку. Ожидаемое время зависит от хеширования и заполненности; совпадение хеша не означает равенства ключей.

> [!followup]- Почему специально подобранные ключи могут замедлить хеш-таблицу и как снизить риск?
>
> Если много ключей попадает в одну область таблицы, поиск проверяет всё больше записей. Например, при цепочках один бакет с n записями превращается в линейный поиск; последовательные вставки с проверкой дубликатов могут стоить O(n²) суммарно.
>
> Для входов из ненадёжного источника ограничивайте количество и размер ключей, используйте зрелую структуру и проверяйте задержки на граничном объёме. В реализациях также применяют случайное начальное состояние хеша или другую структуру для переполненных бакетов. Расширение таблицы помогает обычной высокой заполненности, но не гарантирует исправление одинаковых хешей. ECMAScript не предписывает конкретную внутреннюю хеш-функцию `Map`; не обещайте ей O(1) в худшем случае.

> [!followup]- Когда выбрать Map, а когда обычный объект для словаря?
>
> `Map` принимает ключи любого типа и сохраняет порядок их добавления. `map.set(1, 'number')` и `map.set('1', 'string')` создают две записи. В обычном объекте оба обращения приводятся к одному строковому ключу; собственные ключи объекта — строки или символы, а целочисленные индексы перечисляются особо.
>
> Для фиксированной модели `{ id, title }` объект удобнее, в том числе для JSON. Для динамического словаря с произвольными ключами `Map` обычно яснее: есть `size`, `has` и прямой обход пар. Если нужен именно объект со строковыми ключами из ввода, рассмотрите пустой прототип и явную проверку собственных полей. `JSON.stringify` не сериализует записи `Map` автоматически.

## Когда нужны стек, очередь и двусторонняя очередь?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Стек возвращает последний добавленный элемент первым и полезен для обхода в глубину или отмены действий. Очередь возвращает первый добавленный элемент первой и нужна для обхода в ширину и последовательной обработки. Двусторонняя очередь поддерживает оба конца. Проверяю реальную стоимость операций: Array.shift может быть дорогим на большой очереди.
>
> Стек подходит для истории отмены, очередь — для последовательной отправки задач, deque — для работы с обоих концов. У большой очереди на массиве повторный `shift()` может быть дорогим: используют индекс начала или подходящую структуру.
>

> [!followup]- Как кольцевой буфер реализует очередь с фиксированной ёмкостью?
>
> Храните массив фиксированной ёмкости, индекс головы и число элементов. Новая запись кладётся в позицию `(head + size) % capacity`, извлечение читает голову и сдвигает её по модулю. Так ячейки переиспользуются без сдвига остальных элементов. `size` отличает пустой буфер от полного, даже когда позиции совпадают.
>
> Например, при ёмкости 3 после вставки A, B, C и удаления A следующая запись D займёт освободившуюся первую ячейку, но порядок выдачи будет B, C, D. Определите политику переполнения: отказ, ожидание или замена самого старого. Для нулевой ёмкости запретите вставку до расчёта по модулю; при удалении очищайте ссылку.

> [!followup]- Как получить минимум или максимум стека за O(1)?
>
> Вместе с каждым элементом храните минимум префикса до него: при `push(x)` новый минимум равен `min(x, прежний минимум)`, при `pop` удаляется вся пара. Верхняя пара сразу даёт текущий минимум; максимум хранится аналогично. Для `[3, 1, 1, 4]` после удаления 4 и одного 1 минимум остаётся 1.
>
> Операции требуют постоянного числа действий и O(n) памяти. Можно хранить второй стек только для новых минимумов, но нужно учитывать равные значения: записывать дубликат либо счётчик. У пустого стека минимума нет, выберите явный контракт результата. Если значения сравниваются не как числа, используйте согласованный компаратор.

> [!followup]- Как монотонная deque находит максимум скользящего окна?
>
> Храните индексы кандидатов по убыванию их значений. При добавлении правого элемента удалите с хвоста кандидатов, которые не больше него: новый элемент не хуже и останется в окне дольше. С головы уберите индексы, вышедшие за левую границу. Первый индекс даёт максимум текущего окна.
>
> Например, для `[1, 3, 2, 5]` и окна 2 максимумы — `[3, 3, 5]`. Каждый индекс добавляется и удаляется не более одного раза, поэтому время O(n), память O(k) при ширине k. Храните именно индексы, чтобы отличать одинаковые значения и сроки их выхода. Укажите контракт для `k = 0` и `k > n`.

## Как работает двоичный поиск?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Использую монотонное условие и сужаю диапазон, сохраняя правило о его границах. За каждую итерацию диапазон должен уменьшаться. Уточняю, нужен первый или последний подходящий элемент и что возвращать при отсутствии ответа. Типичные ошибки — смешение включённой и исключённой границы.
>
> Для отсортированных временных отметок можно найти первую запись не раньше заданного времени. Важно искать именно границу, а не произвольное равное значение; пустой диапазон и несколько одинаковых отметок проверяют отдельно.
>

> [!followup]- Как найти нижнюю и верхнюю границы двоичным поиском?
>
> Ищите первую истинную позицию на полуинтервале `[lo, hi)`, начиная с `0` и `n`. Если условие истинно на `mid`, положите `hi = mid`; иначе `lo = mid + 1`. Для нижней границы условие `a[mid] >= x`, для верхней — `a[mid] > x`. Когда границы совпали, это ответ; `n` означает, что подходящей позиции нет.
>
> У `[1, 2, 2, 4]` для 2 нижняя граница равна 1, верхняя — 3. Их разность даёт число совпадений, а диапазон включает индексы 1 и 2. Данные должны быть отсортированы тем же порядком, который использует предикат. Для пустого массива обе границы 0.

> [!followup]- Как двоичный поиск должен работать с повторяющимися элементами?
>
> Сначала уточните, нужен любой индекс, первый, последний или все повторы. Поиск с возвратом при равенстве может дать любой из одинаковых элементов. Для первого найдите нижнюю границу и проверьте, что она в массиве и значение равно цели. Для последнего возьмите позицию перед верхней границей и тоже проверьте совпадение.
>
> Например, в `[2, 2, 2, 5]` для 2 первый индекс 0, последний 2. Для 3 нижняя и верхняя границы обе равны 3: это позиция вставки, не найденный индекс. Две границы за O(log n) дают диапазон повторов; если нужны сами элементы, их чтение добавляет O(k).

> [!followup]- Как вычислить середину двоичного поиска без переполнения и побитовых ловушек?
>
> Для неотрицательных границ используйте `lo + Math.floor((hi - lo) / 2)`. В языках с целыми фиксированной ширины это избегает переполнения суммы `lo + hi` при допустимых границах. В JS побитовое `(lo + hi) >> 1` хуже: оно приводит операнд к 32-битному целому.
>
> Например, при `lo = 2**30` и `hi = 2**30 + 4` сдвиг суммы даёт отрицательное число, а формула с разностью — `2**30 + 2`. Даже `>>>` оставляет только 32 бита. Для обычных индексов Array числовой формулы достаточно; если диапазон сам больше безопасных целых, нужен другой числовой тип и соответствующее представление данных.

> [!followup]- Как двоичным поиском найти ближайший элемент отсортированного массива?
>
> Найдите нижнюю границу цели: первый индекс со значением не меньше `x`. Кандидатов максимум два — элемент на этой позиции и предыдущий. Сравните расстояния и явно решите ничью, например выбирайте меньшее значение. Если граница 0 или n, есть только один сосед; пустой массив требует отдельного результата.
>
> У `[1, 4, 8]` для цели 6 кандидаты 4 и 8 находятся на одинаковом расстоянии. Для цели 10 выбирается 8, хотя точного совпадения нет. На точном совпадении нижняя граница также даёт первый дубликат. Оценка O(log n) предполагает отсортированный вход, постоянный доступ по индексу и корректный расчёт расстояния в используемом числовом диапазоне.

## Когда применять два указателя и скользящее окно?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Когда порядок или свойства задачи позволяют двигать границы без повторного полного перебора. Для скользящего окна нужно правило, по которому расширение и сужение приближает к цели. Например, обычный поиск суммы окном может быть некорректен при отрицательных числах. Сначала проверяю условия применимости.
>
> В отсортированном массиве два указателя ищут пару с нужной суммой без перебора всех пар. Для минимального окна с достаточной суммой правило движения границ зависит от знака значений: отрицательные числа могут нарушить монотонность.
>

> [!followup]- Почему два указателя находят пару с заданной суммой в отсортированном массиве?
>
> Поставьте указатели на первый и последний элементы. Если сумма меньше цели, текущий левый элемент не подойдёт ни с одним доступным правым: справа уже максимальное значение. Поэтому двигайте левый. Если сумма больше цели, симметрично уменьшайте правый. Остановитесь при совпадении или встрече указателей.
>
> У `[1, 3, 5, 8]` для цели 8 сначала `1 + 8 = 9`, уменьшаем правый; `1 + 5 = 6`, увеличиваем левый; `3 + 5 = 8`. Время O(n), память O(1) для уже отсортированного массива. Без сортировки аргумент неверен; если нужны исходные индексы, предварительная сортировка потребует сохранять их или использовать другой подход.

> [!followup]- Как скользящее окно находит подстроку без повторяющихся символов?
>
> Держите левую границу и последнее положение каждого символа. Если очередное вхождение уже внутри окна, перенесите левую границу сразу за него. Если оно слева от окна, границу не двигайте назад. После обработки символа обновляйте максимум длины.
>
> Для `'abba'` вторая `b` сдвигает начало к индексу 2. Последняя `a` уже встречалась на позиции 0, но она за окном, поэтому максимум остаётся 2. Словарь и один проход дают ожидаемое O(n) времени. Сначала определите, что считается символом: UTF-16, кодовая точка или графема. Позиции окна и длину нужно считать в одной выбранной единице.

> [!followup]- Когда префиксные суммы подходят лучше скользящего окна?
>
> Префикс `P[i]` — сумма первых i элементов, поэтому сумма диапазона `[l, r)` равна `P[r] - P[l]`. После O(n) подготовки запрос суммы занимает O(1). Если нужно посчитать подмассивы с суммой `target`, идите слева направо и прибавляйте частоту уже встреченной суммы `P[r] - target`. Инициализируйте частоту нулевого префикса единицей.
>
> Для `[3, -2, 2]` и цели 3 подходят первый элемент и весь массив. Отрицательное число ломает монотонность обычного окна по сумме, но не меняет равенство префиксов. Обновляйте частоту после подсчёта текущего ответа, иначе при цели 0 посчитаете пустой диапазон. Учитывайте точность сумм и счётчика.

> [!followup]- Как проверить подпоследовательность двумя указателями и чем это отличается от окна?
>
> Подпоследовательность сохраняет порядок, но допускает пропуски. Идите указателем по длинной строке, а второй двигайте только при совпадении с очередным символом образца. Как только весь образец совпал, ответ положительный. Для `'ace'` в `'abcde'` используются позиции 0, 2 и 4; непрерывного окна `'ace'` в строке нет.
>
> Раннее совпадение безопасно: оно оставляет больше позиций для остальных символов образца. Время O(n + m) при последовательном чтении и O(1) памяти для индексируемых единиц. Пустой образец всегда подходит. Если задача считает графемы или кодовые точки, сравнивайте их, а не отдельные UTF-16 единицы.

## Как обходить дерево и граф?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Обход в глубину использует рекурсию или явный стек; обход в ширину — очередь. В невзвешенном графе обход в ширину находит минимальное число рёбер до вершины. Для графа отмечаю посещённые вершины и учитываю несвязные части. У глубокого дерева рекурсия может переполнить стек.
>
> Меню категорий обходят в глубину для вложенного отображения; ближайшую связь в невзвешенном графе ищут в ширину. В графе пользователей нужен набор посещённых вершин, чтобы повторные связи не приводили к бесконечному обходу.
>

> [!followup]- Как обнаружить цикл при обходе графа в глубину?
>
> В ориентированном графе различайте ещё не посещённую вершину, активную вершину в текущем пути и полностью завершённую. Ребро в активную вершину замыкает цикл; ребро в завершённую может быть нормальной общей зависимостью. Например, A → B → C → A даёт цикл, а два пути из A в C сами по себе — нет.
>
> В простом неориентированном графе ребро обратно к родителю не считается циклом; ребро к другой уже посещённой вершине может его обнаружить. При параллельных рёбрах различайте id рёбер, а не только родительскую вершину. Обойдите все компоненты, если нужно проверить весь граф, а не только достижимую часть.

> [!followup]- Что меняется при обходе ориентированного графа?
>
> У направленного ребра A → B разрешён переход из A в B, но не обратно, если обратного ребра нет. Список смежности содержит исходящие рёбра; обход из A находит только то, что достижимо по направлениям. Например, задача, которая зависит от библиотеки, может «видеть» библиотеку, но обратный обход потребует отдельного индекса входящих рёбер.
>
> Проверьте, какой результат нужен: достижимость, порядок зависимостей или сильные компоненты. Топологическая сортировка возможна только без направленных циклов. Если ребро означает «A зависит от B», порядок сборки требует B перед A, поэтому направление представления и интерпретацию итогового порядка нужно согласовать явно.

> [!followup]- Как найти связные компоненты и что меняется для направленных рёбер?
>
> В неориентированном графе проходите все вершины. Из каждой ещё не посещённой запустите BFS или DFS: всё, что он посетит, образует очередную компоненту. У A—B, C—D и изолированной E получится три компоненты. Со списками смежности время O(V + E); память — O(V) для отметок и обхода.
>
> В направленном графе уточните смысл: слабая связность игнорирует направления, сильная требует достижимости в обе стороны. Например, A → B соединяет их слабо, но не сильно. Для сильных компонент нужен алгоритм вроде Косарайю или Тарьяна; обычный запуск DFS из первой вершины решает только достижимость.

> [!followup]- Что такое LCA и как найти общего предка двух узлов дерева?
>
> LCA — самый глубокий узел, являющийся предком обеих вершин; вершина считается своим предком. Если есть ссылки на родителя, выровняйте глубины двух узлов, затем поднимайте оба по одному уровню до встречи. Например, у братьев ответ — их родитель, а для узла и его потомка — сам узел.
>
> Для одного запроса это O(h), где h — высота, если глубины и родители известны или вычисляются подъёмом. Для многих запросов можно заранее сохранить предков на расстояниях 1, 2, 4 и так далее: O(n log n) подготовки, O(log n) на запрос. В общем графе общего ближайшего предка может не быть или он может быть не единственным; нужен контракт корневого дерева.

## Как выбрать сортировку?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Учитываю размер входа, устойчивость порядка равных элементов, дополнительную память, худший случай и возможность изменять исходные данные. Сортировки подсчётом и по разрядам требуют ограничений на ключи. В JavaScript функция сравнения должна задавать согласованный порядок; перед оценкой сложности уточняю выбранный алгоритм и среду.
>
> При сортировке заказов по статусу важно определить порядок внутри одинакового статуса. Можно сохранить предыдущий порядок устойчивой сортировкой или явно задать второй ключ, например дату и id. Сортировка огромной выдачи на клиенте не заменяет серверный контракт страниц.
>

**Уточнения**

- Когда выбрать быструю сортировку, слияние или сортировку кучей?
- Что гарантирует устойчивая сортировка и когда это важно?

> [!followup]- Когда выбрать быструю сортировку, слияние или сортировку кучей?
>
> Quicksort для массива обычно даёт ожидаемое O(n log n) с хорошим выбором опорного элемента, но возможен худший случай O(n²); стандартная реализация неустойчива. Сортировка слиянием гарантирует O(n log n), легко сохраняет порядок равных и в обычной версии для массива требует O(n) буфера. Heapsort гарантирует O(n log n), работает на месте и обычно неустойчив.
>
> Например, если при одинаковом статусе заказов нужно сохранить порядок поступления, подходит стабильное слияние. Если память жёстко ограничена, а равные элементы можно переставлять, подходит heapsort. Для `Array.prototype.sort` нельзя по названию угадать алгоритм движка: спецификация требует стабильность, но не конкретный способ сортировки.

> [!followup]- Что гарантирует устойчивая сортировка и когда это важно?
>
> Устойчивая сортировка сохраняет исходный взаимный порядок элементов, которые компаратор считает равными. Если заказы уже отсортированы по времени, стабильная сортировка по статусу оставит хронологию внутри каждой группы, когда сравнение одинаковых статусов возвращает 0.
>
> JavaScript требует стабильности от `Array.prototype.sort`; `sort` при этом меняет исходный массив. При сортировке по нескольким ключам можно использовать один компаратор или сначала отсортировать по второстепенному ключу, затем стабильно по главному. Стабильность не гарантирует одинаковый порядок при разном исходном входе: если выдача и пагинация требуют однозначности, добавьте уникальный ключ последним критерием.

> [!followup]- Как написать числовой компаратор для Array.sort?
>
> Для конечных чисел по возрастанию используйте `(a, b) => a - b`: отрицательный результат ставит a раньше b, положительный — позже, ноль означает равенство. Без компаратора элементы обычно сравниваются как строки, поэтому `[2, 10, 1].sort()` даст `[1, 10, 2]`.
>
> Нельзя возвращать только `a > b`: это даёт 0 или 1 и нарушает согласованность порядка для обратной пары. Для данных с `NaN` заранее определите, отклонять такие записи или помещать их в конец. Для BigInt сравнивайте через `<`/`>` и возвращайте числовые `-1`, `0` или `1`: разность двух BigInt не является подходящим результатом компаратора.

## Что такое динамическое программирование?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Разбиваю задачу на повторяющиеся подзадачи и сохраняю их результаты. Определяю состояние, переходы и начальные случаи; доказываю, что переход действительно рассматривает нужные варианты. Затем выбираю порядок вычисления и сокращаю память, если это допустимо. Простое кэширование любой функции ещё не означает, что решена такая задача.
>
> В задаче подбора купюр результат для суммы используют для вычисления следующих сумм, вместо повторного перебора одинаковых вариантов. Состояние должно учитывать ограничения количества купюр, если они есть: таблица только по сумме может стать недостаточной.
>

> [!followup]- Чем вычисление сверху вниз отличается от вычисления снизу вверх в DP?
>
> Сверху вниз начинайте с целевого состояния, рекурсивно находите нужные подзадачи и кешируйте ответы. Снизу вверх задайте порядок, в котором зависимости уже посчитаны, и заполните таблицу циклами. Переходы и базовые случаи могут быть одинаковыми, меняется способ вычисления.
>
> Например, минимальное число купюр для суммы S можно вычислять из ответов для `S - denomination`. Мемоизация посетит только достижимые состояния, но использует стек. Табличная версия проходит суммы от 0 до S и проще ограничивает память, если переходы используют лишь несколько последних состояний. Если зависимости цикличны, обычная рекурсия или произвольный порядок таблицы не решат задачу без дополнительной модели.

> [!followup]- Как выбрать состояние и порядок обновления для задачи о рюкзаке?
>
> В рюкзаке 0/1 состояние `dp[c]` хранит максимальную ценность при вместимости c после обработки части предметов. Для очередного предмета веса w и ценности v сравнивайте пропуск с `dp[c - w] + v`. При одномерной таблице идите по c от большой вместимости к w, чтобы брать предыдущее состояние, а не повторно использовать тот же предмет.
>
> Например, один предмет веса 2 и ценности 5 при вместимости 4 даёт 5. Проход по возрастанию ошибочно получит 10; такой порядок подходит для неограниченного использования предметов. Время O(nC), память O(C) для значения; это псевдополиномиально по числовой вместимости C. Для восстановления списка предметов нужны дополнительные данные или повторные вычисления.

> [!followup]- Как построить динамическое программирование для возрастающей подпоследовательности?
>
> Состояние `dp[i]` — длина лучшей строго возрастающей подпоследовательности, заканчивающейся элементом i. Изначально она равна 1. Для всех `j < i` с `a[j] < a[i]` улучшайте `dp[i]` через `dp[j] + 1`. Ответ — максимум состояний, а для пустого входа 0.
>
> В `[3, 1, 2, 5, 4]` лучший результат 3, например `[1, 2, 4]`; элементы необязательно соседние. Если нужна сама последовательность, сохраняйте предыдущий индекс при улучшении. Этот вариант требует O(n²) времени и O(n) памяти; для одной длины на больших входах можно поддерживать минимальные хвосты и обновлять их двоичным поиском за O(n log n). Для неубывающей версии правило равенства меняется.

> [!followup]- Почему число состояний DP может стать слишком большим?
>
> Стоимость зависит от числа различных состояний и работы на переход. Например, таблица по вместимости C и второму лимиту B содержит до `(C + 1)(B + 1)` записей на слой. Если добавить множество использованных объектов, маска из n бит может породить до `2**n` состояний. Мемоизация устраняет повторы, но не ограничивает число достижимых вариантов.
>
> Сначала оцените диапазоны параметров и уберите измерения, не влияющие на будущие решения. Если состояния разрежены, храните только достигнутые. Слои можно переиспользовать, когда переход смотрит только на предыдущий, но это экономит память, а не время перебора. Не сокращайте состояние ценой потери ограничения, которое меняет допустимые ответы.

## Чем жадный алгоритм отличается от динамического программирования?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Жадный алгоритм каждый раз делает локально лучший выбор. Чтобы получить правильный общий результат, нужно доказать допустимость этого выбора. Динамическое программирование рассматривает необходимые состояния и переходы. Для размена денег жадный выбор не универсален: произвольные номиналы и лимиты купюр могут его нарушить.
>
> При номиналах 1, 3 и 4 жадный выбор для суммы 6 даст 4+1+1, хотя 3+3 использует меньше купюр. Этот контрпример показывает, почему локально самая большая купюра не гарантирует оптимальный результат для произвольного набора.
>

> [!followup]- Как контрпример показывает, что жадный выбор не оптимален?
>
> Найдите вход, где первый локально выгодный шаг исключает лучший общий ответ. Например, при выборе непересекающихся встреч правило «взять самую короткую» на интервалах `[0,4)`, `[4,8)` и `[3,5)` выбирает короткую встречу, которая пересекает обе остальные. Можно было взять две длинные, поэтому правило неверно.
>
> Один такой вход опровергает универсальную корректность; успешные примеры её не доказывают. Контрпример помогает увидеть, что оптимизировать: здесь важнее освободить время раньше, а не минимизировать длину выбранной встречи. Проверяйте точную цель: если встречи имеют разные веса, правило для максимального количества может перестать работать.

> [!followup]- Почему для максимального числа совместимых интервалов выбирают раннее окончание?
>
> Отсортируйте интервалы по времени окончания и берите следующий, чьё начало не раньше конца предыдущего. Первый выбранный интервал оставляет не меньше времени для остальных, чем первый интервал любого оптимального решения. Поэтому в оптимальном решении можно заменить его первый выбор на самый ранний конец без потери количества; дальше повторить рассуждение.
>
> Например, из `[1,4)`, `[2,3)` и `[3,5)` алгоритм берёт вторую и третью встречи. Условие `start >= end` допускает касание для полуоткрытых интервалов; для закрытых договоритесь отдельно. Время O(n log n) на сортировку. Если нужно максимизировать вес, а не число встреч, этот обмен может менять ценность и потребуется другой алгоритм.

> [!followup]- Почему банкомат с ограниченным запасом купюр не всегда может выбирать самые крупные?
>
> Крупнейшая доступная купюра может оставить сумму, которую невозможно добрать. Например, нужно выдать 60, есть одна купюра 50 и три по 20, а десяток нет. Жадный выбор 50 застрянет на 10; правильный ответ — три по 20.
>
> Для произвольных номиналов и остатков используйте ограниченный поиск или DP, учитывающий, сколько купюр каждого номинала доступно. Определите критерий: любая выдача, минимум купюр или сохранение редкого номинала. В реальном банкомате найденную комбинацию нужно подтвердить по актуальному остатку и атомарно зарезервировать; алгоритм выбора сам по себе не защищает от конкурентного изменения запаса.

> [!followup]- Как доказать корректность жадного алгоритма, а не только проверить примеры?
>
> Покажите, что жадный шаг совместим хотя бы с одним оптимальным решением. В доказательстве обменом берут оптимальное решение, заменяют его первый отличающийся шаг жадным и доказывают, что допустимость и качество сохранились. Затем то же рассуждение применяется к оставшейся задаче.
>
> Например, при выборе максимального числа встреч замена первой встречи на заканчивающуюся раньше не мешает остальным встречам. Если заменить встречу нельзя без потери веса, доказательство не переносится на взвешенный вариант. Явно укажите предположения и правило ничьей. Тесты и перебор маленьких входов хорошо ищут контрпример, но не заменяют аргумент для всех размеров.

## Что такое куча и когда она нужна?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Куча быстро предоставляет минимальный или максимальный элемент и поддерживает вставку и удаление за логарифмическое время. При этом все элементы не хранятся в полностью отсортированном порядке. Она полезна для очереди с приоритетом, отбора K лучших и слияния нескольких отсортированных потоков.
>
> Для top-K самых дорогих товаров можно держать min-heap размера K: очередной подходящий товар заменяет текущий минимум. Не требуется сортировать весь список. Куча даёт быстрый крайний элемент, но не полный отсортированный обход.
>

> [!followup]- Как бинарная куча хранится в массиве и поддерживает порядок?
>
> Бинарная куча — почти полное двоичное дерево. Для индекса i дети в массиве лежат на `2i + 1` и `2i + 2`, родитель на `floor((i - 1)/2)`. В min-heap каждый родитель не больше детей, поэтому корень — минимум, но остальные позиции не полностью отсортированы.
>
> При вставке добавьте элемент в конец и поднимайте его, пока он меньше родителя. При удалении корня поставьте последний элемент на его место и опускайте, меняясь с меньшим ребёнком. Например, `[1, 4, 2]` уже корректная min-heap. Корень читается за O(1), восстановление порядка после вставки или удаления стоит O(log n).

> [!followup]- Почему построение бинарной кучи снизу вверх занимает O(n)?
>
> Возьмите массив целиком и выполните `siftDown` для каждого внутреннего узла, начиная с последнего родителя и двигаясь к корню. Дети к этому моменту уже образуют кучи. Большинство узлов расположено близко к листьям и может спуститься лишь на один или несколько уровней, поэтому сумма работ линейна.
>
> Узлов с высотой хотя бы h порядка `n / 2**h`, а сумма этих количеств по h не превышает константу, умноженную на n. Последовательная вставка n элементов даёт другую верхнюю границу O(n log n). Bottom-up heapify меняет порядок исходного массива; если его надо сохранить, сначала сделайте копию.

> [!followup]- Как изменить приоритет записи в куче по известному индексу?
>
> Замените приоритет и восстановите инвариант в нужном направлении. В min-heap уменьшение приоритета может потребовать подъёма к родителю, увеличение — спуска к меньшему ребёнку. При известной позиции это O(log n), но позиции меняются при каждой перестановке.
>
> Например, если приоритет задания понизился численно с 9 до 2, поднимайте его, пока родитель больше 2. Для обновления по id храните `Map<id, index>` и меняйте обе записи при каждом обмене, удалении или вставке. Без карты поиск позиции по id стоит O(n). Альтернатива — добавить новую запись и игнорировать устаревшую при чтении, учитывая рост памяти.

> [!followup]- Как куча должна выбирать элемент при равных приоритетах?
>
> Обычная куча не обещает порядок среди равных. Если раньше добавленное задание должно выполняться первым, сравнивайте пару `(priority, sequence)`, где `sequence` — возрастающий номер вставки. При одинаковом приоритете меньший номер выигрывает.
>
> Например, задачи A и B обе имеют приоритет 5, но A добавлена первой: компаратор по паре поднимет A раньше B даже после перестановок внутри кучи. Если есть бизнес-критерий, например время дедлайна, используйте его до номера. Определите, сохраняет ли обновление приоритета прежний номер или считается новой постановкой; решение заметно потребителям очереди.

## Как проверить алгоритм на границах?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверяю пустой вход, один элемент, повторы, равные результаты, отрицательные числа, максимальный размер и отсутствие ответа. Не добавляю удобные гарантии, которых нет в условии. Отдельно проверяю требуемые свойства: сохранение порядка, кратности, исходного массива и допустимой памяти.
>
> Для поиска первой записи с нужной датой проверяют пустой массив, все записи раньше границы, все позже и равные значения. Сравнение с простым линейным решением на небольших входах помогает обнаружить ошибку границ двоичного поиска.
>

> [!followup]- Какие проверки на переполнение и потерю точности нужны алгоритму на JavaScript?
>
> Проверьте входы около `Number.MAX_SAFE_INTEGER`, суммы и произведения за безопасным диапазоном, а также побитовые операции, которые приводят Number к 32-битному представлению. Например, два отдельных безопасных счётчика могут дать неточную сумму, а побитовый midpoint — отрицательный индекс при больших неотрицательных границах.
>
> Для точных больших целых сравнивайте результат с эталоном на BigInt; при промежуточных дробях выберите правила погрешности или округления. Отдельно проверьте, что вычисление не превращается в `Infinity`, если ожидается конечный результат. Валидация входа по диапазону не заменяет анализ промежуточных значений; иногда лучше изменить порядок вычислений или хранить только остаток.

> [!followup]- Как проверить, что алгоритм не меняет входные данные?
>
> Сначала зафиксируйте контракт: разрешены ли перестановка массива и изменение вложенных объектов. В тесте сохраните значения до вызова и сравните после него. Для массива объектов проверьте и порядок, и вложенные поля: `slice()` копирует контейнер, но не защищает записи от изменений.
>
> Например, сортировка копии должна вернуть ожидаемый порядок, а исходный массив — сохранить прежние ссылки на тех же позициях. В строгом режиме можно заморозить подготовленную фикстуру на нужных уровнях, чтобы случайная запись сразу дала ошибку. `Object.freeze` поверхностный и не ловит мутацию содержимого `Map`, поэтому выбирайте проверку под структуру данных.

> [!followup]- Как property-based тестирование помогает проверить границы алгоритма?
>
> Задайте свойства, которые должны выполняться для многих сгенерированных входов. Для сортировки: результат упорядочен, содержит те же элементы с той же кратностью, а исходный массив не изменился, если это обещано. Генератор должен давать пустые массивы, повторы, равные ключи и значения около числовых границ.
>
> При сбое сохраните seed и уменьшенный контрпример, чтобы его можно было повторить. Например, свойство «после сортировки все элементы присутствуют» не замечает потерю дубля, пока не проверяются частоты. Генерация дополняет примеры и проверку сложности, но не доказывает корректность на всех входах; неверное или слишком слабое свойство может пропустить ошибку.

> [!followup]- Как получить независимый эталон для теста алгоритма?
>
> Для небольших входов используйте простой алгоритм, который легко проверить, даже если он медленный. Например, для нижней границы эталон — линейный поиск первого элемента `>= x` с результатом `n` при отсутствии, а проверяемый код использует двоичный поиск. Сравните результаты на сгенерированных массивах с повторами и крайними значениями.
>
> Для оптимизационной задачи переберите все допустимые варианты небольшого входа и посчитайте оптимум напрямую. Сохраняйте одинаковый контракт (пустой вход, правила ничьей, числовая точность), но не копируйте переходы и границы из основной реализации: одна и та же ошибка может попасть в обе версии. Производительность эталона не обязана соответствовать production-ограничениям.

## Как связаны ООП, SOLID и интерфейсы?

> [!answer]- Короткий ответ — 30–90 секунд
>
> ООП объединяет данные и поведение; SOLID помогает обсуждать обязанности объектов, расширение, подстановку и направление зависимостей. Интерфейс задаёт контракт. Подтип должен сохранять обещания этого контракта. Принципы не требуют создавать класс или интерфейс для каждой операции — решение должно упрощать конкретные изменения.
>
> Сервис сохранения может зависеть от небольшого интерфейса хранилища, а не от конкретного localStorage или API. Это позволяет менять инфраструктуру и проверять сценарий отдельно; не требуется создавать интерфейс для каждой функции без такой границы.
>
> На этом примере SRP — разделить причину изменения формы и способ хранения; OCP — подключить другой адаптер через тот же контракт, когда такая заменяемость нужна. ISP — дать сохраняющему сценарию только возможность записи, а читающему — чтения. DIP направляет зависимость сценария на нужный ему контракт. LSP проверяет поведение замены: успешная запись должна означать обещанный результат, а не просто совпадение имён методов. Расширение через адаптер не запрещает исправлять существующий код.

> [!followup]- принцип подстановки Лисков
>
> Сначала формулирую обещание. Для учебного хранилища после успешного save(id, text) последующий load(id) возвращает text, пока хранилище живо и запись не изменена другой операцией. Разрешены произвольные непустые строковые id. Ошибка записи отклоняет Promise; UI не должен показывать успех. Контракт здесь не обещает сохранение после перезапуска приложения.
>
> ~~~ts
> type DraftReader = { load(id: string): Promise<string | undefined> };
> type DraftWriter = { save(id: string, text: string): Promise<void> };
>
> function createMemoryDrafts(): DraftReader & DraftWriter {
>   const data = new Map<string, string>();
>   return {
>     async load(id) { return data.get(id); },
>     async save(id, text) { data.set(id, text); },
>   };
> }
>
> async function submitDraft(writer: DraftWriter, id: string, text: string) {
>   await writer.save(id, text);
>   return 'Сохранено';
> }
>
> // Тип подходит, но обещание записи нарушено:
> const fakeReadOnly: DraftWriter = { async save() {} };
> ~~~
>
> Если подставить fakeReadOnly, submitDraft покажет успех без записи. Типизатор проверяет форму объекта, но не этот эффект. Другой пример нарушения — адаптер внезапно принимает только числовые id, хотя клиенту обещали любые непустые строки: замена усилила предусловие. Исправление — не выдавать режим чтения за возможность записи. Передавать ему DraftReader, а действие сохранения показывать только при наличии настоящего DraftWriter; права всё равно проверяет сервер.
>
> Проверка контракта: сохранить строку и прочитать её, перезаписать значение, сохранить пустой текст и id с буквами; отдельно заставить save отклонить Promise и убедиться, что submitDraft не вернул «Сохранено». При условии сохранения после reload память уже не годится: нужно другое хранилище и проверка после повторного открытия. Это изменение обещаний, а не вопрос наследования через class. [Поведенческая подстановка — Liskov и Wing](https://www.cs.cmu.edu/~wing/publications/LiskovWing94.pdf), [структурная совместимость TypeScript](https://www.typescriptlang.org/docs/handbook/type-compatibility).

> [!followup]- инверсия зависимостей
>
> DIP относится к направлению зависимости: правило сохранения черновика зависит от нужной ему операции, а инфраструктурный адаптер реализует этот контракт. Передача зависимости аргументом — один из способов это устроить, сама по себе она ещё не гарантирует хорошую границу.
>
> ~~~ts
> type DraftWriter = { save(id: string, text: string): Promise<void> };
>
> function createSubmitDraft(writer: DraftWriter) {
>   return async (id: string, text: string) => {
>     await writer.save(id, text);
>     return 'Сохранено';
>   };
> }
> ~~~
>
> На входе приложения выбираем адаптер и один раз собираем сценарий: createSubmitDraft(apiDrafts). В тесте передаём память или реализацию, отклоняющую запись. Сам сценарий не импортирует fetch, localStorage или контейнер зависимостей. Передавать ему целый SDK с десятками методов только ради save — слабая граница: изменения SDK продолжают затрагивать бизнес-код.
>
> Проверяю два вызова с разными реализациями без изменения сценария: запись происходит через переданный объект, ошибка доходит вызывающему коду. UI отвечает за индикатор и уведомление, адаптер — за протокол, сценарий — за порядок действия. Если второй реализации и отдельной причины изменения нет, дополнительный контейнер и иерархия классов не нужны. Обычная функция-параметр тоже может выразить контракт.

> [!followup]- Как композиция помогает соблюсти границы ответственности в ООП?
>
> Составьте объект из зависимостей с узкими контрактами. Например, `SaveDraft` принимает `DraftRepository`, который умеет сохранять черновик. Сценарий решает, когда и что сохранить, а реализация репозитория — отправить запрос или записать локально. Тест передаёт поддельное хранилище без наследования сценария.
>
> Польза появляется, когда части меняются по разным причинам или их действительно нужно заменять. Если код — один прямой вызов и границы пока нет, интерфейс и фабрика могут добавить лишние шаги. Композиция не освобождает зависимости от соблюдения общего контракта: например, локальное и сетевое хранилище должны согласованно описывать ошибки сохранения.

> [!followup]- Как инкапсуляция помогает сохранять инварианты объекта?
>
> Спрячьте изменяемые детали и оставьте операции, которые могут проверить правила. Например, корзина предоставляет `addItem` и `setQuantity`, проверяющие количество, вместо прямого доступа к массиву и полям. Тогда нельзя случайно обойти проверку при обновлении из другого экрана.
>
> В JS можно держать данные в приватном поле или замыкании. Если getter возвращает сам изменяемый массив, внешние вызовы всё равно обойдут проверки; верните снимок или операции чтения, учитывая вложенные объекты. TypeScript `private` ограничивает обращения в проверяемом исходнике, а `#` защищает поле во время выполнения. Инкапсуляция не заменяет серверную валидацию входа.

## Какие шаблоны проектирования полезны во фронтенде?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Стратегия позволяет менять алгоритм, фабрика — способ создания объекта, декоратор — добавлять поведение, наблюдатель — сообщать об изменениях, адаптер — связывать разные контракты. Сначала объясняю решаемую задачу и цену подхода, затем называю шаблон.
>
> Стратегия может выбирать расчёт доставки, адаптер — приводить ответы разных API к одной модели, фабрика — создавать настроенный клиент, декоратор — добавлять журналирование. Название полезно, когда объясняет конкретную изменяемую часть решения.
>

> [!followup]- внедрение зависимостей
>
> При dependency injection вызывающий код передаёт нужную зависимость явно: createSubmitDraft(writer) получает объект с save(id, text). Тест передаёт память или ошибающийся writer, а приложение — API-адаптер. Сам сценарий не выбирает источник данных.
>
> При Service Locator сценарий сам вызывает services.get('draftWriter'). Его потребность спрятана внутри тела, а тесту приходится готовить реестр и учитывать его состояние. Передача всего services аргументом не делает зависимости столь же явными: функция по-прежнему может запрашивать из него что угодно. Сборка конкретных зависимостей на входе приложения — нормальная граница; важно, чтобы поиск не был разбросан по бизнес-коду.
>
> Проверка: два экземпляра сценария с разными writer должны независимо сохранять данные, без переустановки глобального реестра. Если изменили только способ хранения, алгоритм сценария не меняется. DI не требует специальной библиотеки: аргумента функции достаточно. Контейнер оправдан, когда реально нужно управлять сборкой и временем жизни многих зависимостей; он не отменяет выбор понятного контракта. [Общие принципы DI и сравнение с Service Locator](https://developer.android.com/training/dependency-injection).

> [!followup]- Как выбрать время жизни Singleton во фронтенде?
>
> Сначала определите, в какой области действительно должен существовать один экземпляр: приложение, вкладка, пользовательская сессия или запрос SSR. Экспорт модуля обычно переиспользуется в пределах одного графа загрузки, но не объединяет разные вкладки и процессы. Например, один менеджер уведомлений на приложение разумен, а глобальное состояние пользователя в серверном модуле может перейти между SSR-запросами.
>
> Создавайте экземпляр на уровне владельца и передавайте зависимым частям. Тогда его можно заменить в тесте и закрыть подписки при выходе из сессии. Если нужна общая работа между вкладками, требуется отдельный протокол координации; название Singleton этого не даёт.

> [!followup]- Когда абстрактная фабрика полезна для связанных компонентов фронтенда?
>
> Абстрактная фабрика создаёт семейство совместимых частей за одним контрактом. Например, для предпросмотра она создаёт фиктивный источник файлов и фиктивное хранилище, а для рабочей среды — согласованные API-клиенты. Код импорта получает обе части из выбранного семейства и не проверяет режим на каждом шаге.
>
> Она полезна, если компонентов несколько, они должны согласованно меняться и есть реальные варианты. Если меняется только один клиент, хватит простой фабрики или передачи зависимости. Контракты частей всё равно задайте отдельно: тестовое семейство должно воспроизводить существенные успешные и ошибочные исходы, а не просто возвращать заглушку на любой вызов.

> [!followup]- Когда шина событий уместна во фронтенде и где она скрывает зависимости?
>
> Шина позволяет опубликовать событие без прямой связи со всеми слушателями. Например, приложение публикует `session-expired`, а открытые независимые экраны закрывают свои окна. Контракт должен назвать событие, тип данных, владельца подписки и правила обработки ошибок.
>
> Для передачи значения от родителя ребёнку проще props и явное событие; для разделяемого состояния с текущим значением — store. Если обязательный шаг сохранения спрятать за произвольным слушателем, вызывающему трудно узнать, выполнился ли он. Используйте шину для уведомлений, снимайте подписки по жизненному циклу и учитывайте, что новый подписчик обычно не получает уже прошедшее событие.
