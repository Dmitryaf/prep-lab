## Что происходит от ввода URL до появления страницы?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Браузер разбирает адрес и определяет, можно ли использовать локальный кэш или уже открытое соединение. Если нужен сетевой доступ, он разрешает имя через DNS, устанавливает транспортное соединение и для HTTPS согласует защищённый канал. Затем отправляет HTTP-запрос и получает ответ. Конкретные шаги зависят от кэшей, версии протокола, redirects и Service Worker.
>
> HTML можно разбирать по мере поступления. Браузер строит DOM, обнаруживает стили, скрипты и изображения; CSS участвует в вычислении стилей. Обычный синхронный script может остановить парсинг HTML, а async/defer меняют порядок загрузки и выполнения.
>
> Для отображения рассчитываются стили и геометрия, формируются команды рисования, затем слои объединяются. Первая видимая картинка ещё не означает полную готовность страницы: ресурсы и JS могут продолжать работу.

> [!followup]- Какие этапы исчезнут при повторном переходе с кэшем и готовым соединением?
>
> При пригодной записи DNS-кэша не нужен новый DNS-запрос, а при переиспользовании соединения — новое его установление и TLS-handshake. Свежий HTTP-кэш может отдать ресурс без сети. Устаревший ресурс иногда требует проверки и ответа 304: тело не скачивается, но сетевой обмен остаётся.
>
> Обычная повторная навигация всё равно может заново разбирать HTML и выполнять код. Возврат через back/forward cache — другой сценарий: браузер способен восстановить сохранённую страницу целиком. Поэтому сначала уточняют тип перехода и смотрят Timing, источник ответа и pageshow.persisted, а не обещают, что кэш убирает все этапы загрузки.

> [!followup]- Чем async отличается от defer для классического script?
>
> Для внешних классических скриптов оба атрибута позволяют скачивание параллельно разбору HTML. async запускает готовый скрипт без гарантии порядка относительно соседних async-скриптов; выполнение может прервать разбор документа. defer откладывает выполнение до окончания разбора HTML и сохраняет порядок таких скриптов в документе.
>
> Если app.js зависит от vendor.js, два async не обеспечивают зависимость. Для независимой аналитики async может подходить. Для inline-классического скрипта defer не даёт такого поведения. Загрузка без блокировки парсера не устраняет стоимость выполнения JavaScript: длинная задача всё равно задержит реакцию интерфейса.
>
> Источник: [MDN — script](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script).

> [!followup]- Почему HTML уже виден, а кнопка ещё не реагирует?
>
> Браузер может показать серверную разметку до загрузки, выполнения приложения и подключения обработчиков. При SSR кнопка становится интерактивной после соответствующей инициализации или гидратации. Другая причина — главный поток занят длинной задачей: обработчик есть, но событие ждёт обработки.
>
> Сначала проверяют загрузку чанков и ошибки запуска, наличие обработчика, перекрывающие элементы и disabled, затем запись Performance вокруг клика. Решение зависит от причины: уменьшение стартового JavaScript, разделение тяжёлой работы, более ранняя инициализация нужного элемента. Если действие пока невозможно, интерфейс должен честно показывать состояние ожидания. Один ранний FCP не доказывает готовность приложения к работе.

## Что такое DOM и CSSOM?

> [!answer]- Короткий ответ — 30–90 секунд
>
> DOM представляет структуру документа, CSSOM — правила CSS и стили, доступные через API браузера. Они участвуют в построении изображения страницы, но узел DOM сам по себе не равен пикселям на экране. Изменение документа может потребовать пересчёта стилей и расположения элементов.
>
> Добавление строки в таблицу меняет DOM, а изменение класса может изменить её рассчитанные стили и размеры. Само наличие строки в дереве не гарантирует видимость: она может быть скрыта, перекрыта или находиться за пределами экрана.
>

> [!followup]- Как DOM и CSSOM участвуют в построении дерева отрисовки?
>
> DOM описывает структуру документа, CSSOM — правила стилей. Браузер сопоставляет правила элементам, вычисляет стили и формирует структуры для размещения и рисования. В учебной модели это дерево отрисовки; оно не является простой копией DOM.
>
> Узел с display: none не создаёт боксов, а псевдоэлемент может участвовать в отрисовке без отдельного DOM-узла. Далее определяются геометрия, команды рисования и композиция. На практике полезно связать изменение с этапом: правка цвета обычно не требует новой геометрии, а ширины — может. Реальные внутренние деревья движков сложнее этой модели.

> [!followup]- Что меняется при display: none и остаётся ли элемент в DOM?
>
> Элемент остаётся в DOM, но он и его потомки не создают боксов для раскладки. Он не занимает место, не рисуется и обычно исключается из дерева доступности. Это отличается от удаления узла: ссылки, состояние объекта и зарегистрированные обработчики остаются.
>
> Переключение display может изменить геометрию соседей и потребовать layout. Скрипты и таймеры компонента сами по себе от скрытия не останавливаются, поэтому display: none не заменяет управление жизненным циклом. При измерении скрытого элемента многие геометрические свойства дают нулевой размер; измерять будущую раскладку нужно после появления подходящих условий.

> [!followup]- Чем visibility: hidden отличается от display: none и opacity: 0?
>
> visibility: hidden скрывает элемент, сохраняя занимаемое место в раскладке; обычно он не получает фокус и исключается из дерева доступности. display: none убирает создаваемые элементом боксы, поэтому соседние элементы могут переместиться.
>
> opacity: 0 делает содержимое прозрачным, но само по себе не отключает попадание указателя, клавиатурный фокус и доступность. Невидимая кнопка может продолжить перехватывать действия. Кроме того, потомок visibility: hidden может явно вернуть visibility: visible. Поэтому способ скрытия выбирают по требуемому месту, взаимодействию и доступности, а результат проверяют мышью, клавиатурой и в accessibility tree.

> [!followup]- Почему ::before виден на странице, хотя отдельного узла нет в DOM?
>
> ::before и ::after — псевдоэлементы, которые позволяют создать стилизуемое содержимое, связанное с исходным элементом. При подходящем content они могут формировать боксы и участвовать в раскладке, но не становятся обычными дочерними DOM-узлами. querySelector не вернёт ::before как Element.
>
> Их стили можно исследовать в DevTools или через getComputedStyle(element, '::before'). Для декоративной иконки это удобно; важный текст, название кнопки и содержание формы лучше размещать в семантической разметке. Нельзя считать CSS-generated content универсальной заменой доступного имени и интерактивного элемента.

## Чем пересчёт расположения отличается от перерисовки и объединения слоёв?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Layout вычисляет размеры и положение элементов. Paint формирует их визуальное содержимое, например текст, фон и границы. Compositing объединяет подготовленные слои в итоговый кадр. Это разные стадии, поэтому одинаково заметное изменение может иметь разную стоимость.
>
> Изменение ширины часто требует layout и последующего paint. Изменение цвета обычно не меняет геометрию, но требует paint. transform и opacity при подходящих условиях могут обновляться на стадии compositing, однако отдельный слой и бесплатная анимация не гарантированы.
>
> Особенно дорог цикл «записать стиль → прочитать геометрию» много раз: чтение может заставить браузер немедленно пересчитать layout. Сначала измеряю Performance, группирую чтения и записи, уменьшаю объём работы и проверяю на слабом устройстве.

> [!followup]- Почему offsetHeight после изменения width может вызвать синхронный layout?
>
> После изменения width прежняя геометрия может стать неактуальной. Чтобы вернуть корректный offsetHeight, браузеру приходится вычислить стили и расположение прямо во время выполнения JavaScript, не дожидаясь обычного этапа кадра. Чередование записи и чтения в цикле многократно повторяет эту работу — layout thrashing.
>
> Сначала подтверждают forced reflow в Performance и находят цепочку записей/чтений. Затем группируют необходимые измерения и изменения, сокращают число измеряемых узлов или используют результат ResizeObserver, если сценарий допускает асинхронное уведомление. Перенос всего цикла в requestAnimationFrame сам по себе не устраняет чередование зависимых записей и чтений.

> [!followup]- Почему will-change на всех элементах может ухудшить ситуацию?
>
> will-change — подсказка о предстоящих изменениях, позволяющая браузеру заранее подготовить оптимизации. Массовое и постоянное применение может увеличить число слоёв, расход памяти и работу с ними. На телефоне это способно ухудшить плавность вместо ожидаемого ускорения.
>
> Сначала находят дорогой этап в Performance и проверяют, нужна ли подсказка конкретному анимируемому элементу. Если нужна, включают её заранее и снимают после завершения сценария. transform и opacity часто позволяют обойти layout, но не гарантируют бесплатную отрисовку любого содержимого. Эффект оценивают по кадрам и памяти на целевом устройстве, а не по наличию will-change в CSS.

> [!followup]- Что гарантирует requestAnimationFrame, а чего он не исправляет?
>
> requestAnimationFrame планирует одноразовый callback перед будущей перерисовкой, когда браузер предоставляет такую возможность. Для продолжения анимации его запрашивают снова; прогресс считают по времени, а не по числу вызовов. Частота не обязана быть 60 Гц, а в скрытой вкладке callbacks могут приостанавливаться.
>
> Он не выносит вычисления с главного потока и не делает тяжёлую функцию быстрее. Если callback долго считает или вызывает повторные синхронные layout, кадры продолжат теряться. Также callback не является обещанием, что пользователь увидит каждый промежуточный шаг. Оптимизируют саму работу, а requestAnimationFrame используют для согласования визуальных обновлений с кадрами.

## Как загружаются обычные, async, defer и модульные скрипты?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Обычный скрипт без async и defer приостанавливает разбор HTML до загрузки и выполнения. async выполняется после загрузки без гарантии порядка. defer выполняется после разбора документа, сохраняя порядок обычных скриптов. Модульные скрипты по умолчанию также отложены и загружают зависимости. Положение тега — лишь часть условий выполнения.
>
> Для двух обычных внешних скриптов, где второй использует первый, `defer` сохраняет порядок выполнения. `async` подходит независимому скрипту: порядок загрузки не задаёт надёжную зависимость между ним и приложением.
>

>
> Если код подключился поздно, событие уже могло пройти. Надёжная схема: при document.readyState === 'loading' подписаться на DOMContentLoaded один раз, иначе выполнить инициализацию сразу. Подписка на load отвечает на другой вопрос и часто откладывает работу без необходимости. Отдельно нельзя считать любые продолжения после await частью синхронного выполнения стартового скрипта.
>
> Источник: [MDN — DOMContentLoaded](https://developer.mozilla.org/en-US/docs/Web/API/Document/DOMContentLoaded_event).

> [!followup]- В каком порядке выполняются динамически добавленные классические script?
>
> Внешние классические скрипты, созданные через document.createElement('script'), по умолчанию ведут себя асинхронно. Порядок append не гарантирует порядок выполнения: маленький второй файл может загрузиться раньше первого.
>
> Если нужен порядок нескольких таких скриптов, перед вставкой задают script.async = false для каждого. Либо явно загружают следующий после успешного load предыдущего и обрабатывают error. Это не стоит путать с defer у скриптов в исходном HTML. Для модулей зависимости лучше выражать import. Готовность подключённого SDK тоже может требовать его отдельного сигнала после выполнения файла.

> [!followup]- Как async меняет загрузку и выполнение модульного скрипта?
>
> Модуль без async обычно начинает выполнение после разбора документа; его зависимости загружаются как граф модулей. Атрибут async позволяет начать выполнение, как только нужный граф готов, не ожидая окончания разбора HTML и порядка соседних скриптов. Зависимости самого модуля при этом никуда не исчезают.
>
> Такой модуль не должен предполагать, что произвольный элемент ниже по HTML уже создан. Порядок между независимыми async-точками входа тоже нельзя использовать как контракт. Для обязательной зависимости нужен import, а готовность DOM и асинхронных данных проверяют отдельно. defer на module не добавляет обычному модулю нового режима.
>
> Источник: [MDN — script](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script).

> [!followup]- Чем preload скрипта отличается от его подключения и когда нужен modulepreload?
>
> link rel="preload" as="script" заранее запрашивает ресурс, но сам не выполняет его. Выполнение всё равно требует script или другого механизма подключения. Для модулей существует modulepreload: он готовит ресурс в системе загрузки модулей и может помочь раньше получить нужные зависимости.
>
> Предзагрузка полезна, если ресурс действительно критичен и браузер обнаруживает его поздно. URL и режим запроса должны согласоваться с последующим использованием, иначе возможна повторная загрузка. Массовый preload конкурирует за сеть с более важными ресурсами. Проверяют waterfall, повторные запросы и реальное время готовности экрана; одно наличие preload не доказывает ускорение.

## Как распространяется событие DOM?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Событие проходит путь от внешних узлов к цели в фазе capture, обрабатывается на цели и, если этот тип события всплывает, идёт обратно в фазе bubbling. addEventListener по умолчанию слушает всплытие; параметр capture позволяет выбрать другую фазу.
>
> `event.target` — исходная цель события, а currentTarget — узел, чей обработчик выполняется сейчас. На этом основано делегирование: один обработчик контейнера находит нужный элемент через target/closest и проверяет, что он относится к контейнеру.
>
> preventDefault отменяет стандартное действие, если событие допускает отмену; stopPropagation прекращает дальнейшее распространение, но само действие не отменяет. Для снятия обработчика нужны тот же callback и совпадающий capture либо сигнал AbortController.

> [!followup]- Что делать, если target — иконка внутри кнопки?
>
> event.target указывает на исходный элемент события: при клике по вложенной иконке это не обязательно кнопка. Если обработчик установлен на самой кнопке, используют event.currentTarget. При делегировании на контейнер ищут подходящего предка через target.closest('button[data-action]'), предварительно проверив target instanceof Element.
>
> Найденная кнопка должна принадлежать нужному контейнеру: проверяют container.contains(button), а при вложенных виджетах — дополнительные границы. Действие определяют по явному атрибуту, не по тексту иконки. Для Shadow DOM возможен retargeting; тогда рассматривают composedPath и контракт компонента, а не обходят инкапсуляцию случайными селекторами.

> [!followup]- Почему preventDefault не заменяет stopPropagation?
>
> preventDefault отменяет действие браузера, связанное с отменяемым событием: например, переход по ссылке или отправку формы. Событие при этом продолжает распространяться, и родительский обработчик может выполниться. stopPropagation останавливает дальнейшее распространение, но не отменяет действие по умолчанию.
>
> Кроме того, stopPropagation не останавливает другие обработчики на том же узле; для этого есть stopImmediatePropagation. preventDefault не действует в passive-обработчике и для неотменяемого события. При двойном действии сначала выясняют, кто его запускает: браузер, вложенный обработчик или обработчик родителя. Безусловное подавление событий может сломать делегирование и доступность.

> [!followup]- Как снять обработчик и почему новая стрелка не подходит?
>
> removeEventListener сопоставляет тип события, ссылку на callback и флаг capture. Новая стрелка с тем же текстом — другой объект функции, поэтому она не снимет прежнюю подписку. Обработчик сохраняют в переменной и передают одну ссылку при добавлении и удалении.
>
> Флаги passive и once не участвуют в таком сопоставлении, а capture должен совпасть. Альтернатива для группы подписок — передать signal одного AbortController при регистрации и вызвать abort при завершении сценария. Для поиска повторных вызовов проверяют места регистрации, повторные монтирования и cleanup, а не только тело обработчика.

## Чем localStorage, sessionStorage, cookie и IndexedDB отличаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> localStorage и sessionStorage синхронно хранят строки; sessionStorage относится к сессии вкладки. Cookie передаются с HTTP-запросами по правилам их атрибутов. IndexedDB асинхронно хранит структурированные данные и поддерживает транзакции. Выбор зависит от объёма, срока хранения и требований безопасности.
>
> Тему оформления можно хранить в localStorage, большие офлайн-черновики — в IndexedDB. Cookie с HttpOnly подходит для предусмотренной сервером сессии, но браузер прикладывает её автоматически: защита действий должна учитывать CSRF.
>

> [!followup]- Что делать, если браузерное хранилище достигло квоты?
>
> Квота зависит от API, браузера, режима и доступного места. Нельзя считать, что любая успешная запись сегодня гарантирует место завтра. navigator.storage.estimate() даёт приблизительные usage и quota для управляемого хранилища origin, но не резервирует место и не заменяет обработку ошибки записи.
>
> При QuotaExceededError сохраняют несохранённые данные в памяти, объясняют пользователю состояние, предлагают экспорт или синхронизацию и удаляют только восстановимый кэш по известной политике. IndexedDB требует обработки ошибок запросов и транзакций. Нельзя показывать «сохранено» до подтверждения записи или молча очищать пользовательские черновики ради освобождения места.
>
> Источник: [MDN — квоты хранилищ](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

> [!followup]- Может ли браузер удалить данные сайта и как защищать важные черновики?
>
> Данные в IndexedDB и Cache Storage обычно хранятся в режиме best-effort и могут быть вытеснены браузером. Пользователь также может очистить данные сайта, а приватный режим обычно ограничивает срок их хранения. Поэтому единственная локальная копия не равна гарантированному долговременному хранению.
>
> Для подходящего сценария можно запросить navigator.storage.persist() и проверить результат, но отказ допустим, а очистку пользователем это не отменяет. Для важных черновиков нужны экспорт, резервная копия или подтверждённая серверная синхронизация. При запуске приложение должно корректно переживать отсутствие кэша, сохраняя различие между восстановимыми ресурсами и пользовательскими данными.
>
> Источник: [MDN — сохранность данных](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

> [!followup]- Какие браузерные данные разделяются между вкладками одного сайта?
>
> В обычном контексте вкладки одного origin разделяют localStorage и базу IndexedDB; sessionStorage дополнительно разделён по верхнеуровневой вкладке. Origin включает схему, хост и порт. Cookie имеют собственные правила Domain, Path, Secure и SameSite, поэтому их область нельзя описать только словами «тот же сайт».
>
> Общее хранилище не делает состояние приложения автоматически согласованным. Вкладки должны получать уведомления и разрешать конкурирующие изменения. Например, localStorage read-modify-write может потерять обновление из другой вкладки; для атомарной операции подходят транзакция IndexedDB или серверный контроль версии. Во встроенных сторонних контекстах дополнительно учитывают разделение хранилищ браузером.

> [!followup]- Что защищает HttpOnly у cookie и чего эта настройка не решает?
>
> HttpOnly запрещает доступ к cookie через JavaScript страницы, например document.cookie. Это снижает риск прямого чтения сессионного токена при XSS. Но браузер продолжает отправлять cookie в подходящих HTTP-запросах, включая запросы, инициированные скриптом.
>
> Поэтому XSS всё ещё может выполнять действия от имени пользователя, а HttpOnly сам по себе не решает CSRF. Нужны защита от внедрения скриптов, подходящие Secure и SameSite, серверные проверки запросов и правила сессии. Флаг устанавливается сервером через Set-Cookie. Проверяют отдельно недоступность токена скрипту и корректную авторизацию запроса, а не трактуют HttpOnly как полный запрет злоупотребления сессией.

> [!followup]- Когда срабатывает storage и почему его не получает вкладка, которая записала данные?
>
> storage уведомляет другие документы, разделяющие соответствующее хранилище, об изменении из другой страницы. Вкладка, вызвавшая localStorage.setItem, сама это событие не получает: своё состояние она обновляет обычным способом. Для localStorage уведомление доступно другим подходящим вкладкам того же origin.
>
> У sessionStorage область уже: другие документы того же origin внутри той же верхнеуровневой вкладки, например iframe, но не отдельные вкладки. В обработчике проверяют key, storageArea и newValue; при удалении значение может быть null. Уведомление не превращает последовательность чтение–изменение–запись в транзакцию и не разрешает конфликты автоматически.
>
> Источник: [MDN — storage event](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event).

## Что делает Service Worker?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Это обработчик событий, работающий отдельно от страницы. Он может перехватывать запросы, управлять кэшем и поддерживать работу без сети. У него собственный жизненный цикл установки и активации, прямого доступа к DOM нет. При обновлении нужно учитывать версии кэша и совместимость с открытыми страницами.
>
> Для офлайн-чтения справки Service Worker может отдавать ранее сохранённые ресурсы. После выпуска новой версии старый worker ещё может обслуживать открытые страницы; стратегия обновления должна согласовать код страницы, worker и версии кэша.
>

> [!followup]- Почему Service Worker требует защищённый контекст и как его проверять локально?
>
> Service Worker может перехватывать запросы управляемых страниц и отдавать ответы, поэтому его регистрация ограничена защищённым контекстом. В production это обычно HTTPS. Для локальной разработки браузеры считают localhost и loopback-адреса потенциально доверенными; произвольный HTTP-адрес в локальной сети не получает такое исключение автоматически.
>
> При проблеме проверяют window.isSecureContext, наличие navigator.serviceWorker, origin, путь скрипта и scope, затем ошибку регистрации. Не стоит обходить требования отключением защиты браузера и считать результат рабочим для пользователей. На телефоне открытие dev-сервера по HTTP-IP компьютера отличается от localhost на самом компьютере.

> [!followup]- Почему Service Worker продолжает отдавать старые файлы после релиза?
>
> Новая версия worker может быть установлена, но ждать активации, пока страницы используют предыдущую. Кроме того, код cache-first способен возвращать старые ответы из прежнего кэша. Это отдельные причины, поэтому проверяют активный controller, состояния installing/waiting/active и фактический источник ответа в Network.
>
> Для релиза согласуют версию HTML и ресурсов, именуют кэши и удаляют устаревшие кэши приложения в нужный момент. skipWaiting и clients.claim не являются универсальным исправлением: немедленное переключение может соединить открытую страницу старой версии с новым worker. Обновление проверяют в уже открытой вкладке с прошлой версией, включая переходы, offline и восстановление сети.

> [!followup]- Достаточно ли unregister, чтобы Service Worker перестал влиять на страницу и исчез его кэш?
>
> Нет. unregister снимает регистрацию, но не является синхронной остановкой всех выполняемых операций и не удаляет Cache Storage. Уже управляемые страницы могут продолжать использовать текущий worker до завершения своего жизненного цикла. Поэтому наличие успешного результата unregister ещё не доказывает чистое окружение.
>
> Для диагностики отдельно проверяют registration, navigator.serviceWorker.controller и кэши приложения, затем открывают новый контекст после завершения старых клиентов. Удаление конкретных кэшей — отдельная осознанная операция; очищать все данные origin нельзя, если там есть пользовательские черновики. Также проверяют, не регистрирует ли приложение worker снова при запуске.
>
> Источник: [MDN — unregister](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/unregister).

> [!followup]- Почему Service Worker нельзя использовать как постоянно работающий фоновый процесс?
>
> Браузер запускает worker для событий и может завершить его между ними. Глобальные переменные не являются надёжным долговременным состоянием, а setInterval не гарантирует постоянную работу после закрытия страницы. Service Worker также не имеет доступа к DOM.
>
> Асинхронную обработку события связывают с event.waitUntil, а ответ на fetch — с respondWith, соблюдая правила конкретного события. Важное состояние сохраняют в IndexedDB. Background Sync и Push имеют ограничения поддержки, разрешений и планирования; это не точный будильник. Для гарантированного выполнения бизнес-операции используют сервер, а на клиенте продумывают повтор, идемпотентность и восстановление после прерывания.

## Как общаются вкладки и окна?

> [!answer]- Короткий ответ — 30–90 секунд
>
> BroadcastChannel передаёт сообщения между контекстами одного источника. Событие storage уведомляет другие подходящие контексты об изменении веб-хранилища. postMessage позволяет явно передавать сообщения между окнами. При получении проверяю источник и структуру данных.
>
> После выхода из аккаунта вкладка может сообщить другим вкладкам о смене сессии через BroadcastChannel. Это уведомление интерфейса, а не отзыв доступа на сервере. Сообщения от iframe через postMessage принимают только после проверки origin и отправителя.

>
> Нужно описать подключение и отключение клиентов, ошибки и восстановление: worker не является гарантированно вечным сервером. Проверяют поддержку в целевых браузерах и условиях встраивания, а не только наличие API на рабочей машине. Если нужна лишь рассылка небольших событий, BroadcastChannel обычно проще; общий исполнитель оправдан при действительно общем ресурсе.
>
> Источник: [MDN — SharedWorker](https://developer.mozilla.org/en-US/docs/Web/API/SharedWorker).

> [!followup]- Как две вкладки могут потерять обновление общего состояния и что с этим делать?
>
> Обе вкладки могут прочитать значение 5, независимо увеличить его и записать 6. Последняя запись перезапишет предыдущую, хотя ожидалось 7. Уведомление через storage или BroadcastChannel сообщает об изменении, но само не делает read-modify-write атомарным.
>
> Решение выбирают по владельцу данных: транзакция IndexedDB для локальной операции, серверная версия/ETag для серверной сущности, либо согласованная блокировка для конкретного браузерного сценария. Дополнительно определяют правило конфликта и повторы. Проверка должна воспроизводить две конкурирующие операции с одинаковой исходной версией; последовательные клики в одной вкладке эту ошибку не обнаружат.

> [!followup]- Что такое window.opener и почему на него нельзя полагаться для связи окон?
>
> opener может указывать на окно, которое открыло текущее. Но ссылка может отсутствовать из-за noopener, способа открытия или политики Cross-Origin-Opener-Policy. Современные ссылки с target="_blank" обычно ведут себя как noopener, поэтому предположение «новое окно всегда знает родителя» ненадёжно.
>
> Если связь нужна, её проектируют явно: проверяют наличие окна и договариваются о сообщениях с проверкой origin, источника и структуры данных. Если связь не нужна, сохраняют изоляцию через noopener. Наличие ссылки не разрешает читать DOM другого origin. Для same-origin вкладок без отношения родитель–потомок иногда проще BroadcastChannel.

> [!followup]- Зачем postMessage нужен точный targetOrigin и какие проверки делает получатель?
>
> targetOrigin ограничивает origin окна, которому можно доставить сообщение. Для известного получателя задают точные схему, хост и порт вместо '*': окно могло перейти на другой сайт между получением ссылки и отправкой. URL-путь в это ограничение не входит.
>
> Получатель проверяет event.origin, при ожидаемой паре окон также event.source, затем тип сообщения и схему payload. Допустимый origin не делает любое содержимое безопасным: данные нельзя исполнять как код или без проверки вставлять как HTML. postMessage обеспечивает транспорт, а доверие и разрешённые действия определяет протокол приложения.
>
> Источник: [MDN — postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage).

## Как работает история одностраничного приложения?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Маршрутизатор сопоставляет URL с экраном и использует History API либо фрагмент адреса после #. Для прямого открытия маршрута сервер должен отдавать нужную страницу приложения. В URL сохраняют состояние, необходимое для ссылок, повторного открытия и кнопок «назад» и «вперёд».
>
> Фильтры каталога и номер страницы сохраняют в query-параметрах, чтобы ссылку можно было отправить и восстановить кнопкой «Назад». Прямое открытие `/orders/42` требует подходящего ответа сервера: клиентский router ещё не запущен в момент первого запроса.
>

**Уточнения**

- Когда использовать pushState и replaceState и что вызывает popstate?

> [!followup]- Когда использовать pushState и replaceState и что вызывает popstate?
>
> pushState добавляет запись истории, replaceState меняет текущую. Они обновляют URL в пределах допустимого origin и state без загрузки новой страницы, но сами не вызывают popstate. Приложение обновляет экран непосредственно при программной навигации, а popstate обрабатывает при обходе истории, например кнопками «Назад» и «Вперёд».
>
> Для нового значимого перехода обычно нужен pushState; для нормализации URL или промежуточного ввода фильтра — replaceState, чтобы не засорять историю. На reload сервер должен уметь обслужить маршрут. Проверяют прямое открытие ссылки, Back/Forward и согласованность URL, интерфейса и state, а не только изменение адресной строки.

> [!followup]- Как хранить фильтры в URL и не получить рассинхронизацию с состоянием экрана?
>
> В URL помещают состояние, которое полезно восстановить или передать ссылкой: поисковый запрос, сортировку, номер страницы. При чтении параметры разбирают и проверяют, применяют значения по умолчанию и исключают неизвестные значения. Секреты и чувствительные данные в URL не кладут: он попадает в историю и другие журналы.
>
> Важно назначить понятный источник состояния и обрабатывать Back/Forward: если URL изменился, фильтры и запрос данных должны обновиться. Для частого ввода можно использовать replaceState, для значимого перехода — pushState. Проверяют reload, скопированную ссылку, очистку параметров и отмену устаревших запросов.

> [!followup]- Как вернуть пользователя к прежней позиции после повторной загрузки?
>
> Сначала определяют, что нужно восстановить: маршрут, фильтр, страницу списка, раскрытый элемент или прокрутку. Воспроизводимую часть состояния кодируют в URL, данные текущей вкладки при необходимости — в sessionStorage. У браузера есть автоматическое восстановление прокрутки; нельзя одновременно без согласования включать своё и полагаться на штатное.
>
> Для длинного асинхронного списка простой scrollTo до загрузки элементов не сработает. Надёжнее сохранить идентификатор видимого элемента и смещение, восстановить данные и лишь затем позицию. Отсутствующий элемент требует разумного запасного поведения. Проверяют reload и Back/Forward отдельно, в том числе при медленной загрузке и изменившемся наборе данных.

## Зачем нужна семантика HTML?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Подходящие элементы дают смысл, встроенное поведение и поддержку вспомогательных технологий: button для действия, a для перехода, label для подписи поля. У div с обработчиком нажатия клавиатуру, фокус и роли придётся реализовать отдельно. Семантический элемент обычно проще и надёжнее.
>
> Для удаления строки выбирают `button type="button"`, для открытия карточки — ссылку. Пользователь получает правильную клавиатурную активацию и возможность открыть ссылку в новой вкладке; имитация этих действий через div создаёт дополнительные обязанности.
>

> [!followup]- Что даёт семантическая form по сравнению с набором полей и div-кнопкой?
>
> form задаёт понятную группу для ввода и отправки. Связанные label дают полям доступные имена, подходящие type помогают вводу и встроенной проверке, button type="submit" запускает штатный сценарий отправки. Поле name нужно для включения его значения в обычную отправку формы или FormData.
>
> Обработчик ставят на submit формы, а не только на click кнопки, чтобы учитывать отправку клавиатурой и другие способы. В SPA при необходимости вызывают preventDefault и выполняют свою отправку. Кнопкам посторонних действий внутри формы явно задают type="button". Встроенная валидация улучшает UX, но не заменяет проверку данных сервером.

> [!followup]- Как выбрать уровни заголовков и почему их нельзя использовать только ради размера текста?
>
> Заголовки описывают иерархию содержания: название страницы, раздел, подраздел. Размер и внешний вид задают CSS, а уровень h1–h6 выбирают по структуре. Пользователь программы чтения с экрана может перемещаться по заголовкам и понимать страницу без последовательного прослушивания всего текста.
>
> На практике проверяют список заголовков отдельно от оформления: понятны ли темы, нет ли случайных скачков уровней и пустых названий. Компоненту карточки полезно позволять выбрать подходящий уровень в контексте страницы, сохраняя одинаковый вид. Требование «все карточки всегда h2» может сломать вложенную структуру.

> [!followup]- Как main, nav, header и другие области помогают ориентироваться на странице?
>
> Семантические области дают вспомогательным технологиям ориентиры: основное содержимое, навигацию, вступительную часть и дополнительные материалы. Пользователь может перейти к нужной области, не проходя все ссылки подряд. На обычной странице выделяют один активный main и дают различимые имена нескольким навигациям.
>
> Контекст имеет значение: header внутри article не равен глобальной шапке страницы, а section становится полезным ориентиром при подходящем доступном имени. Не нужно превращать каждый контейнер в landmark: слишком много областей тоже затрудняет поиск. Проверяют фактическое accessibility tree и переходы между областями, а не только названия тегов в шаблоне.

> [!followup]- Почему role и aria-атрибуты не заменяют поведение нативного HTML-элемента?
>
> ARIA сообщает вспомогательным технологиям роль, имя и состояние, но сама не добавляет клавиатурное управление и нативные действия. div role="button" не начинает автоматически получать фокус, нажиматься Space/Enter и работать как submit-кнопка. Всё это пришлось бы реализовать и проверить отдельно.
>
> Поэтому для обычного действия выбирают button, для перехода — ссылку с href, для поля — подходящий input. ARIA добавляют там, где нативной семантики недостаточно, например для связи с описанием или состояния раскрытия. Неверные aria-атрибуты могут сделать правильную разметку хуже, поэтому проверяют поведение клавиатурой и объявляемые имя, роль, состояние.

## Как проверять доступность интерфейса?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Начинаю с пользовательского сценария: можно ли найти элемент, понять его назначение, выполнить действие и узнать результат без мыши и только визуальных подсказок. Предпочитаю семантические button, input, label и заголовки: они дают базовое поведение и сведения вспомогательным технологиям.
>
> Клавиатурой проверяю Tab/Shift+Tab, Enter/Space для подходящих элементов, видимый фокус и отсутствие ловушек. У диалога проверяю доступное название, начальный фокус, удержание его в модальном окне и возврат к инициатору. У формы — связь label с полем, доступное сообщение ошибки и сохранение ввода. Динамический результат объявляют там, где он иначе останется незаметным.
>
> Отдельно проверяю контраст, увеличение текста, узкую ширину и настройку уменьшения анимации. Автоматический сканер помогает найти часть ошибок; реальное прохождение сценария клавиатурой и программой чтения с экрана дополняет его. Отсутствие предупреждений сканера не доказывает доступность.

> [!followup]- Куда переместится фокус после открытия и закрытия диалога?
>
> При открытии модального диалога фокус переводят внутрь на подходящий элемент: поле, безопасное действие или статический заголовок с tabindex="-1", если сначала важно прочитать содержимое. Tab и Shift+Tab должны оставаться внутри, а фон — быть недоступным для взаимодействия. Обычно Escape закрывает диалог.
>
> При закрытии фокус возвращают к вызвавшему элементу. Если его больше нет, выбирают логичную следующую точку сценария. У диалога должно быть доступное имя. Нативный dialog.showModal() помогает с модальностью, но выбор начального фокуса и весь путь открытия/закрытия всё равно проверяют клавиатурой и программой чтения с экрана.
>
> Источник: [WAI-ARIA APG — модальный диалог](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

> [!followup]- Как связать ошибку формы с конкретным полем и сообщить о ней программе чтения с экрана?
>
> Поле получает понятный label, признак aria-invalid="true" при ошибке и связь с текстом ошибки через aria-describedby с id сообщения. Текст объясняет конкретную проблему и способ исправления; одного красного цвета недостаточно. Если описание уже есть, его id сохраняют рядом с id ошибки.
>
> После неудачной отправки можно перевести фокус на сводку ошибок со ссылками или на первое неверное поле, исходя из размера формы. Для ошибки, появившейся без перемещения фокуса, используют подходящее live-уведомление, избегая повторного объявления на каждый символ. Проверяют фактическое озвучивание, исправление ошибки и снятие aria-invalid, а не только наличие атрибутов.

> [!followup]- Почему div с обработчиком click не равен button?
>
> button уже имеет роль, доступное имя из содержимого, клавиатурный фокус, активацию клавиатурой и состояние disabled. div с click даёт только реакцию на конкретное событие. Добавление role="button" сообщает роль, но не реализует остальное поведение.
>
> Если действие действительно кнопка, используют button и задают type="button" внутри формы, когда отправка не нужна. Если это переход, выбирают ссылку с href. При нестандартном элементе пришлось бы вручную учитывать Tab, Enter, Space, предотвращение нежелательной прокрутки и отключение — и проверять всё это. CSS позволяет оформить нативный элемент без потери его поведения.

## Как работают каскад и специфичность CSS?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Если несколько CSS-правил задают одно свойство, браузер выбирает победителя по каскаду. Сначала учитываются применимость правила, происхождение, важность и слои каскада; специфичность сравнивается уже среди конкурирующих правил на соответствующем уровне. Если остальные условия равны, выигрывает более позднее правило.
>
> Специфичность удобно сравнивать по группам: ID, затем классы/атрибуты/псевдоклассы, затем теги/псевдоэлементы. Это не обычная сумма баллов: много классов не превращаются в ID. `!important` меняет важность декларации, а не её специфичность.
>
> Наследование — отдельный механизм: часть свойств получает значение родителя, когда на самом элементе нет выбранного значения. При отладке сначала смотрю в DevTools, какое правило выиграло и почему, затем исправляю границу стилей, а не добавляю important наугад.

> [!followup]- Может ли более специфичный селектор проиграть из-за cascade layer?
>
> Да. Порядок слоёв сравнивается раньше специфичности. Для обычных author-деклараций правило из более позднего слоя побеждает правило из раннего, даже если его селектор проще.
>
> ```css
> @layer base, components;
> @layer base { #save { color: red; } }
> @layer components { .button { color: blue; } }
> ```
>
> У элемента `id="save" class="button"` цвет синий. Обычные стили вне слоёв имеют приоритет над обычными слоёными стилями. Для `!important` порядок слоёв обратный: важные объявления ранних слоёв сильнее поздних, а слоёные важные — сильнее внеслоевых важных.
>
> Поэтому при отладке сначала проверяют origin, importance и layer, затем специфичность внутри соответствующего уровня. Увеличение числа классов не преодолеет проигрыш слоя.

> [!followup]- Почему десять классов не равны одному ID?
>
> Специфичность сравнивается лексикографически по группам: сначала ID, затем классы/атрибуты/псевдоклассы, затем типы/псевдоэлементы. Это не десятичное число с переносом разряда. Поэтому `(1,0,0)` сильнее `(0,10,0)` при прочих равных условиях каскада.
>
> Например, `#panel` выигрывает у `.a.b.c.d.e.f.g.h.i.j`, если оба правила конкурируют в одном origin, importance и layer. `!important` не добавляет специфичность, а меняет другой уровень сравнения.
>
> Для снижения веса полезен `:where(...)`, у которого специфичность нулевая. Не строй длинный селектор ради борьбы с ID: лучше поправить границу стилей или порядок слоёв, чтобы переопределение оставалось понятным.

> [!followup]- Почему явно заданный цвет элемента побеждает унаследованный от родителя?
>
> Наследование применяется, когда свойство элемента не получило собственного значения по соответствующим правилам. Селектор родителя не конкурирует специфичностью с селектором ребёнка: они относятся к разным элементам.
>
> ```css
> #parent { color: red; }
> span { color: blue; }
> ```
>
> Внутренний `span` будет синим, хотя ID родителя специфичнее селектора тега. Чтобы взять родительский цвет явно, можно задать `color: inherit`; чтобы удалить конкретное правило, сначала выясни его роль в каскаде.
>
> Это объясняет, почему добавление `!important` к цвету родителя не заставляет все дочерние элементы наследовать его поверх их собственных цветов. Проверяй computed style самого проблемного узла и отдельно цепочку наследования.

## Как устроена блочная модель CSS?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Блок включает содержимое, внутренние отступы, границы и внешние отступы. При box-sizing: border-box заданная ширина включает внутренние отступы и границы, но не внешние. В некоторых блочных контекстах вертикальные внешние отступы схлопываются. Итоговые размеры также зависят от способа размещения элементов.
>
> Поле `width: 100%` с padding при content-box может выйти за ширину родителя. border-box включает padding и border в заданную ширину, но margin остаётся снаружи; в flex/grid отдельно проверяют минимальный размер содержимого.
>

> [!followup]- Как min-width и max-width ограничивают заданную ширину CSS-блока?
>
> `width` задаёт предпочтительный размер, а `min-width` и `max-width` ограничивают результат. Например, `width: 100%; max-width: 60rem` позволяет блоку занимать доступную ширину, но не растягиваться чрезмерно на большом экране. Если минимум больше максимума, минимум имеет приоритет.
>
> Размер считается с учётом `box-sizing`: при `border-box` padding и border входят в заданную ширину, margin — нет. У flex/grid-элементов автоматический минимум может зависеть от содержимого и мешать сжатию; иногда нужен `min-width: 0`.
>
> Проверь узкий контейнер и длинную неразрывную строку. Одно `max-width: 100%` не гарантирует, что содержимое, фиксированные потомки и внешние отступы не создадут переполнение.

> [!followup]- Как min-content, max-content и fit-content связывают ширину блока с содержимым?
>
> `min-content` соответствует минимальному размеру с разрешёнными переносами, `max-content` — размеру без мягких переносов, а `fit-content` ограничивает размер по содержимому доступным пространством в пределах intrinsic-границ.
>
> Для короткой подписи `width: fit-content` позволяет рамке охватывать текст, не занимая всю строку. Длинное слово или URL всё равно может создать большой min-content размер, если переносы запрещены. `overflow-wrap: anywhere` меняет доступные точки переноса и помогает тексту сжаться.
>
> Не считай intrinsic-размер фиксированной константой: он зависит от шрифта, текста, языка и CSS. Проверка с одной короткой английской подписью не покрывает локализацию, увеличение текста и длинные идентификаторы.

> [!followup]- Почему содержимое переполняет CSS-блок и как выбрать способ обработки?
>
> Переполнение возникает, когда содержимое требует больше места, чем получило: фиксированная ширина потомка, длинный URL, padding при content-box, автоматический минимум flex/grid или фиксированная высота. Сначала найди источник в DevTools, затем выбери поведение по смыслу.
>
> Тексту можно разрешить перенос, таблице — локальную горизонтальную прокрутку, изображению — `max-width: 100%`. `overflow: hidden` лишь обрезает лишнее и может спрятать полезный текст или outline фокуса; это не универсальное исправление.
>
> Проверяй страницу с длинными данными и zoom. Если горизонтально прокручивается весь документ, хотя требовалась только таблица, ограничение поставлено не на того владельца или его родитель сам не умеет сжиматься.

> [!followup]- Когда вертикальные margin схлопываются и почему отступы не всегда складываются?
>
> У обычных блоков вертикальные внешние отступы соседей могут объединяться. Два положительных margin 20px и 30px обычно дают 30px, а не 50px. Схлопывание возможно также между родителем и первым/последним ребёнком при отсутствии разделяющих условий.
>
> Padding, border и новый block formatting context могут изменить поведение. Например, `display: flow-root` у родителя предотвращает схлопывание его отступов с потомками. У flex/grid-элементов margin между собой таким образом не схлопываются; для регулярных интервалов часто проще `gap`.
>
> Отрицательные margin имеют отдельные правила объединения, поэтому формула «всегда взять максимум» неполна. При отладке проверяй реальный formatting context, а не только значения двух CSS-деклараций.

## Когда использовать Flexbox и Grid?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Flexbox удобен для размещения элементов вдоль главной оси с учётом поперечной. Grid позволяет совместно управлять строками и столбцами. Оба способа поддерживают сложную раскладку; выбираю по связям между элементами и требованиям к расположению, а не только по правилу «одна или две оси».
>
> Панель с кнопками и поиском удобно выстроить через Flexbox. Для формы с согласованными колонками подписей и полей подходит Grid. Перенесённые строки flex-контейнера не становятся одной общей сеткой колонок.
>

> [!followup]- Почему перенос строк Flexbox не выравнивает колонки между строками?
>
> Каждая строка многострочного flex-контейнера распределяет свободное место самостоятельно. flex-grow и justify-content действуют в пределах своей строки, поэтому границы элементов первой строки не задают колонки для второй. Если в первой строке три карточки, а в последней две, последние могут растянуться шире.
>
> Когда важны общие колонки, задаю Grid, например:
>
> ~~~css
> .cards {
>   display: grid;
>   grid-template-columns: repeat(3, minmax(0, 1fr));
>   gap: 1rem;
> }
> ~~~
>
> При уменьшении доступной ширины число колонок нужно уменьшить подходящим правилом адаптации. Для проверки достаточно пяти карточек, разных длин заголовков и ширины возле точки переноса: колонки Grid должны сохранять общие границы, последняя строка — оставлять свободную ячейку.
>
> Flexbox можно настроить на одинаковый flex-basis, но такая раскладка требует самостоятельно согласовать размеры и отступы; общей системы колонок у неё не появляется. Если нужны только переносимые теги или кнопки с естественной шириной, независимость строк как раз удобна. [MDN: перенос flex-элементов](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Flexible_box_layout/Wrapping_items).

> [!followup]- Как min-width: 0 помогает полю поиска в узкой flex-панели?
>
> Flex-элемент по умолчанию может иметь автоматическую минимальную ширину, связанную с содержимым. Поэтому flex-shrink: 1 не всегда позволяет полю или его обёртке сжаться: минимальный размер останавливает сжатие, и панель выходит за границы. min-width: 0 снимает этот нижний предел у нужного flex-элемента. [MDN: min-width](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/min-width).
>
> ~~~css
> .toolbar { display: flex; gap: 0.5rem; }
> .search { flex: 1 1 0; min-width: 0; }
> .search input {
>   width: 100%;
>   min-width: 0;
>   box-sizing: border-box;
> }
> .toolbar button { flex: 0 0 auto; }
> ~~~
>
> Здесь .search — непосредственный flex-элемент, внутри которого находится input. Если flex-элементом является само поле, правило нужно ему. При вложенных flex-контейнерах проверяю и ограничивающие обёртки.
>
> Проверяю панель с длинным текстом и кнопкой на малой ширине: поле сжимается, кнопка доступна, страница не получает горизонтальную прокрутку. min-width: 0 не делает содержимое автоматически переносимым и не спасает панель, которая физически уже суммы кнопок и отступов. Тогда нужны перенос панели, другая композиция или явная работа с переполнением текста.

> [!followup]- Когда minmax(0, 1fr) полезнее колонки с фиксированной шириной?
>
> `minmax(0, 1fr)` подходит колонке, которая должна занять оставшееся место и уметь сжаться при узком контейнере. Фиксированная ширина подходит известному размеру, например боковой панели, но не адаптивной области основного содержимого.
>
> ```css
> .layout {
>   display: grid;
>   grid-template-columns: 16rem minmax(0, 1fr);
>   gap: 1rem;
> }
> .content { min-width: 0; overflow-wrap: anywhere; }
> .table-scroll { overflow-x: auto; }
> @media (max-width: 40rem) {
>   .layout { grid-template-columns: minmax(0, 1fr); }
> }
> ```
>
> В обычной колонке `1fr` автоматический минимум может учитывать минимальный размер содержимого. Длинная строка или таблица тогда расширяет сетку сверх контейнера. Нулевой минимум разрешает самой колонке стать уже содержимого; `1fr` распределяет оставшееся пространство.
>
> Это не удаляет переполнение внутри ячейки: для текста выбирают перенос, для широкой таблицы — локальную прокрутку. На маленьком экране сама панель `16rem` тоже может перестать помещаться, поэтому отдельный breakpoint переводит раскладку в одну колонку. Проверка: длинный URL и широкая таблица при узком viewport и увеличенном масштабе; горизонтально прокручивается таблица, а не вся страница. См. [minmax()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/minmax).

## Как работают position и контексты наложения?

> [!answer]- Короткий ответ — 30–90 секунд
>
> position определяет способ размещения элемента и связь с содержащим блоком. z-index сравнивает уровни внутри контекста наложения; большое значение не позволяет выйти за его пределы. transform и ряд других свойств могут создавать новый контекст. При ошибке наложения проверяю всю цепочку предков.
>
> Если выпадающее меню скрыто под соседним блоком, увеличение z-index внутри своего контекста может ничего не изменить. Проверяют предков с transform и overflow: наложение и обрезание — разные ограничения, а перенос меню в другой контейнер меняет обе связи.
>

> [!followup]- Как overflow у предков влияет на position: sticky?
>
> Sticky ориентируется на ближайшего предка с механизмом прокрутки, который могут создать `overflow: auto`, `scroll` или `hidden`, даже если этот предок фактически не прокручивается. Поэтому случайный `overflow: hidden` на обёртке способен изменить ожидаемое прилипание к viewport.
>
> Нужен хотя бы один inset со значением, отличным от `auto`, по нужной оси, например `top: 0`, и место для перемещения внутри containing block. Если родитель почти той же высоты, что sticky-элемент, заметного движения не будет. Flex/grid stretch также может растянуть элемент и убрать полезный диапазон.
>
> Проверяй всю цепочку предков, вычисленные overflow по обеим осям и высоты. Увеличение z-index решает наложение, но не выбор scroll container и не нехватку пространства.

> [!followup]- Почему position: fixed внутри transform может двигаться вместе с предком?
>
> Обычно fixed позиционируется относительно viewport. Но предок с `transform`, отличным от `none`, создаёт containing block для fixed-потомков; тогда их координаты привязаны к этому предку, и при его прокрутке/движении элемент уже не ведёт себя как глобально закреплённый.
>
> Например, модальное окно внутри `.page { transform: translateZ(0) }` может оказаться ограничено геометрией страницы. Проверь computed styles предков и перенеси глобальный overlay в подходящий контейнер, если это соответствует структуре приложения.
>
> `z-index: 999999` не меняет containing block. Кроме transform, аналогичное влияние могут иметь другие свойства, например некоторые значения contain/filter; диагностировать нужно фактическую цепочку, а не один найденный CSS-класс.

> [!followup]- Как перенос overlay в другую часть DOM помогает при clipping и stacking context?
>
> Перенос в контейнер возле `body` может вывести меню из обрезающего `overflow` и локального stacking context. React Portal или Vue Teleport сохраняют компонентную связь, меняя физическое положение DOM.
>
> После переноса пересмотри координаты: измерение якоря через `getBoundingClientRect` даёт viewport-координаты, которые подходят fixed-позиционированию, но не автоматически любому absolute-контейнеру. Также могут измениться наследуемые CSS-переменные и селекторы предков.
>
> Это не готовая реализация dialog: фокус, Escape, inert-фон и возврат фокуса требуют своего контракта. Если нужен настоящий top layer, рассмотрите нативный dialog/popover по требованиям. Проверяй реальный браузер с прокруткой и вложенными контейнерами, а не только факт вставки узла в body.

> [!followup]- Что такое содержащий блок и почему position: absolute не всегда отсчитывается от родителя?
>
> Containing block задаёт систему координат и базу для ряда размеров/процентов. У absolute-элемента им обычно становится ближайший подходящий предок, например с `position`, отличным от static; это не обязательно непосредственный DOM-родитель. Некоторые свойства вроде transform тоже могут создавать containing block.
>
> Если значок должен стоять в углу карточки, задай карточке `position: relative`, а значку — `position: absolute; top: ...; right: ...`. Без этого он может привязаться к более дальнему контейнеру.
>
> Не путай containing block со stacking context: первое определяет геометрию, второе — порядок наложения. DevTools помогает проверить обоих предков; увеличение z-index не исправит ошибочную систему координат.

> [!followup]- Как проверить карточку, которая используется и на странице, и в узкой панели?
>
> Проверяю один компонент в двух контейнерах одновременно при одинаковой ширине окна: например, в основной области 800 px и боковой панели 280 px. Потом плавно меняю ширину контейнеров, добавляю длинный заголовок, пустые данные, ошибку и увеличенный текст. Смотрю, остаются ли видны действия, не обрезается ли содержимое и совпадает ли визуальный порядок с клавиатурным.
>
> Если переключение раскладки зависит от места карточки, использую размер её контейнера:
>
> ~~~css
> .card-host { container-type: inline-size; }
> .card { display: grid; gap: 1rem; }
> @container (min-width: 32rem) {
>   .card { grid-template-columns: 10rem minmax(0, 1fr); }
> }
> ~~~
>
> Размер запрашивается у предка .card-host, а правило меняет дочернюю .card. Базовая раскладка остаётся пригодной для узкой области. Media query по viewport не различит широкую страницу и узкую панель в одном окне. [MDN: container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries).
>
> Порог выбираю по моменту, когда содержимому действительно хватает места. Проверка одного скриншота на 390 px не подтверждает работу всех промежуточных размеров. Container query тоже не исправит фиксированную ширину внутренней картинки или неразрывный текст — их ограничения проверяются отдельно.

> [!followup]- Почему фиксированная высота часто ломается при увеличении текста?
>
> При увеличении текста меняются высота строки и количество переносов, а фиксированная высота блока не обязана вырасти. В итоге текст выходит наружу, накладывается на соседние элементы или обрезается через overflow: hidden. Такой же эффект дают перевод с более длинными словами и дополнительные сообщения об ошибках.
>
> Для текстовой карточки обычно оставляю высоту по содержимому, а минимальный визуальный размер задаю через min-height:
>
> ~~~css
> .notice {
>   min-height: 3rem;
>   padding: 0.75rem 1rem;
>   box-sizing: border-box;
> }
> ~~~
>
> Проверяю увеличение текста до 200%, длинную локализованную подпись и состояние с ошибкой: весь смысл и кнопки должны оставаться доступны. Увеличение масштаба страницы проверяю отдельно: оно также меняет доступную ширину и количество строк. [MDN: height и увеличение текста](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/height#accessibility).
>
> Фиксированная высота допустима для области с собственным прокручиванием, изображения или другого явно ограниченного элемента. Для текстовой области тогда нужно осознанно обеспечить доступ ко всему содержимому, видимый фокус и работу прокрутки; простое скрытие переполнения не решает проблему.

> [!followup]- Как отличить нужную горизонтальную прокрутку таблицы от переполнения всей страницы?
>
> У таблицы должен быть отдельный ограниченный контейнер с `overflow-x: auto`, а ширина документа должна укладываться в viewport. В grid/flex-раскладке самому контейнеру может понадобиться `min-width: 0`, иначе intrinsic-размер таблицы растянет родителя.
>
> Проверяй `tableWrapper.scrollWidth > tableWrapper.clientWidth` при узком экране и одновременно отсутствие лишнего `document.documentElement.scrollWidth`. Затем прокрути таблицу клавиатурой и убедись, что подписи и управление доступны.
>
> Не ставь `overflow-x: hidden` на body ради зелёной проверки: это может просто спрятать последнюю колонку и часть интерфейса. Широкая таблица допустимо сохраняет структуру, но остальные блоки страницы должны адаптироваться и не уезжать вместе с ней.

## Как оптимизировать изображения и шрифты?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Подбираю формат и размер изображения, использую srcset, sizes и picture, заранее задаю геометрию. Отложенную загрузку применяю к неприоритетным изображениям. Для шрифтов учитываю набор символов, предварительную загрузку и font-display. Ресурс, от которого зависит LCP, нельзя бездумно загружать с задержкой.
>
> Главному изображению товара задают размеры, чтобы избежать скачка раскладки, и подходящие варианты srcset. Картинки ниже экрана можно загрузить позже; задержка главного изображения, определяющего LCP, ухудшит первый показ.
>

> [!followup]- Что даёт CDN для изображений и какие параметры важны для кэша?
>
> CDN может отдавать изображение из близкого к пользователю узла и кэшировать преобразованные варианты. Но первый промах всё равно обращается к origin, а слишком большой исходник не становится подходящим только из-за смены домена. Проверяю размер, формат, качество и выбранный браузером вариант вместе с задержкой сети.
>
> Если URL кодирует width, quality и format, каждый нужный вариант должен попадать в корректный cache key. При выборе формата по заголовку Accept требуется согласованная политика вариантов у CDN. Бесконтрольное число размеров уменьшает долю попаданий; фиксированный набор вариантов проще прогревать и ограничивать. Проверяю HIT/MISS, холодный/повторный запрос и обновление изображения. Приватные файлы требуют проверки доступа и правил кэширования, иначе общий кэш может раскрыть их.

> [!followup]- Что гарантирует img.decode() и когда его полезно ждать?
>
> decode() возвращает Promise, который выполняется, когда изображение декодировано и готово к использованию; при ошибке он отклоняется. Это удобно для управляемой замены: загрузить новую картинку вне DOM, дождаться декодирования и затем заменить прежнюю. Завершение Promise не означает, что новый кадр уже показан на экране.
>
> При быстром выборе A→B перед заменой дополнительно проверяю актуальность запроса, иначе поздняя A вытеснит B. Обрабатываю отказ decode, сохраняю размеры контейнера и проверяю неверный URL/формат. Не стоит без необходимости задерживать вставку основного LCP-изображения через такую последовательность: раннее обнаружение ресурса браузером тоже важно. [HTMLImageElement.decode](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode).

> [!followup]- Как выбрать запасной шрифт, чтобы уменьшить скачок текста при загрузке?
>
> Выбираю системный fallback с близкой шириной символов и вертикальными метриками. При необходимости настраиваю метрики через size-adjust и overrides ascent/descent/line-gap с проверкой поддержки. Это уменьшает изменение переносов и высоты, но не гарантирует совпадения всех глифов. Явный line-height помогает стабилизировать строки, не исправляя различие ширин текста.
>
> font-display управляет поведением во время загрузки: swap быстрее показывает fallback, но допускает последующую замену; optional может оставить запасной шрифт при медленном открытии. Выбор зависит от требований к тексту и бренду. Проверяю русский/латинский текст, разные начертания, узкий экран и медленную сеть. Предзагрузка всех шрифтов может конкурировать с более важными ресурсами. [Практика загрузки шрифтов](https://web.dev/articles/font-best-practices).

> [!followup]- Всегда ли вариативный шрифт легче нескольких отдельных начертаний?
>
> Нет. Один variable font может заменить много файлов и дать промежуточные значения осей, но для страницы с единственным обычным начертанием он может быть тяжелее одного специализированного файла. Сравниваю фактически используемые начертания, набор символов и сжатый вес, а не количество файлов само по себе.
>
> Например, интерфейс использует regular и bold: сравниваю два WOFF2 с вариативным вариантом того же семейства и нужным набором символов. Ограничение набора через subsetting должно сохранять реальные языки и необходимые глифы; unicode-range влияет на выбор загружаемых подмножеств. Проверяю computed font, синтетическое начертание, переносы и число запросов на разных страницах. Не загружаю неиспользуемые оси и языки только ради универсальности.

## Что такое Shadow DOM?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Shadow DOM изолирует внутреннее дерево и стили компонента, но не создаёт полноценную границу безопасности. При распространении событий целевой элемент может подменяться для внешнего наблюдателя; выход события за границу зависит в том числе от composed. Нужно отдельно проверять фокус, оформление и доступность компонента.
>
> Web Component может скрыть внутреннюю разметку кнопки от обычных селекторов страницы. Для оформления наружу предоставляют пользовательские CSS-переменные или parts; для уведомления о действии — событие с нужными параметрами bubbles и composed.
>

> [!followup]- Как Custom Elements связаны с Shadow DOM и обязательно ли использовать их вместе?
>
> Custom Elements позволяют зарегистрировать собственный HTML-элемент с поведением, например `customElements.define('user-card', UserCard)`. Shadow DOM создаёт отдельное внутреннее DOM-дерево и область стилей. Эти механизмы независимы: custom element может использовать обычный light DOM, а shadow root можно создать на подходящем обычном элементе.
>
> Жизненный цикл custom element включает подключение и отключение от документа. Созданные listener, observer и таймеры должны иметь корректное освобождение, учитывая повторное подключение.
>
> Имя autonomous custom element содержит дефис. Регистрация не делает элемент автоматически доступной кнопкой или полем формы: семантика, клавиатура и участие в форме требуют отдельной реализации и проверки.

> [!followup]- Как slot распределяет содержимое в Shadow DOM и кому принадлежат переданные узлы?
>
> `<slot>` обозначает место отображения light DOM-узлов внутри композиции shadow tree. Именованный slot принимает элементы с соответствующим атрибутом `slot`, а безымянный — оставшееся подходящее содержимое. Если ничего не назначено, показывается fallback внутри slot.
>
> Переданный узел не становится обычным внутренним потомком shadow root: он остаётся в light DOM. Поэтому запросы и стили нужно строить с учётом этой границы. Например, внешний `<span slot="title">` оформляется внешними правилами, а компонент может предоставить ограниченные slot-стили.
>
> Событие `slotchange` сообщает об изменении назначения узлов, но не обо всех глубоких мутациях текста внутри уже назначенного узла. Для таких задач выбирают отдельное наблюдение или явное состояние.

> [!followup]- Как ::part позволяет оформлять внутренние элементы Shadow DOM?
>
> Компонент помечает разрешённый внутренний элемент атрибутом `part`, например `<button part="trigger">`. Потребитель пишет `user-menu::part(trigger) { border-radius: 0.5rem; }`, не обращаясь к закрытой внутренней структуре селекторами.
>
> Это публичный CSS-контракт: имя part следует версионировать так же внимательно, как prop. Можно изменить внутренние обёртки, сохранив `trigger`, и пользовательский стиль продолжит работать. Для вложенных shadow-компонентов может понадобиться `exportparts`.
>
> `::part` не превращает весь shadow DOM в обычную доступную область селекторов и не раскрывает произвольных потомков. Для темы часто достаточно custom properties; parts нужны там, где разрешается более точное оформление конкретной части.

> [!followup]- Как bubbles, composed и composedPath влияют на события через Shadow DOM?
>
> `bubbles` управляет всплытием, а `composed` — возможностью пройти границу shadow root. Для собственного публичного уведомления часто используют `new CustomEvent('selected', { detail, bubbles: true, composed: true })`.
>
> Снаружи `event.target` может быть переназначен на host, чтобы не раскрывать внутреннюю структуру. `event.composedPath()` показывает путь распространения с учётом границ; содержимое закрытого shadow root скрывается от внешнего наблюдателя. Поэтому делегирование по `target.matches(...)` может не увидеть внутреннюю кнопку.
>
> Не выставляй composed всем внутренним событиям автоматически: наружу должен выходить стабильный предметный контракт. Проверяй listener внутри компонента, на host и на document; native click и созданный CustomEvent имеют разные значения флагов по умолчанию.

## Как безопасно вставить пользовательский текст?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Текст вставляю через textContent или обычный вывод с экранированием во фреймворке. Если действительно нужен HTML, требуется подходящая очистка и ясное правило доверия источнику. Произвольные данные API нельзя напрямую передавать в innerHTML или другой API вставки HTML.
>
> Комментарий с текстом `<img ...>` должен отображаться как текст. Если продукт разрешает форматированный HTML, очищают его по разрешённой схеме; замена нескольких подстрок не является надёжным HTML-санитайзером. Экранирование текста не заменяет проверку схемы URL в ссылке.
>

> [!followup]- Как предотвратить XSS при выводе пользовательского текста?
>
> Используй текстовый sink: `textContent`, интерполяцию Vue или обычное JSX-выражение. Тогда строка `<img src=x onerror=...>` отображается как текст, а не создаёт исполняемую разметку. Данные API не становятся доверенными только потому, что пришли с вашего backend.
>
> Если продукт разрешает форматированный HTML, нужен поддерживаемый sanitizer с явно разрешёнными тегами, атрибутами и URL-схемами. Ручная замена `<script>` неполна: исполнение возможно через обработчики, опасные URL и другие контексты.
>
> Защита зависит от места вставки: экранирование HTML-текста не проверяет URL, CSS или JavaScript. CSP и Trusted Types дополняют безопасное проектирование sinks, но не оправдывают произвольный `innerHTML`.

> [!followup]- Почему безопасный вывод текста не заменяет проверку пользовательского URL?
>
> URL в `href` или `src` имеет собственную семантику. Даже если значение корректно экранировано как атрибут, схема `javascript:` в ссылке может означать выполнение кода, а ссылка на посторонний домен — нежелательное перенаправление.
>
> Разбирай значение через `new URL(value, base)` и разрешай нужные протоколы, например только `https:` и `http:`. Если ссылка обязана быть внутренней, дополнительно сравни origin и допустимый путь. Относительные адреса проверяй после разрешения относительно контролируемой базы.
>
> Не применяй проверку «начинается с https» регулярным выражением: URL содержит кодирование, пробелы и альтернативные формы записи. Для отображаемого названия ссылки по-прежнему нужен текстовый вывод. Допустимые протоколы определяет конкретная функция продукта.

> [!followup]- Почему пользовательский SVG нельзя считать безопасной картинкой при вставке в DOM?
>
> SVG — разметка с собственными элементами, ссылками и возможностями активного содержимого. Вставка недоверенного SVG через `innerHTML` создаёт DOM, поэтому требует проверки и очистки подходящим sanitizer, а не только проверки расширения файла.
>
> Контекст загрузки важен: SVG как ресурс `<img>` имеет более строгие ограничения, чем inline SVG или документ в `object`/iframe. Поэтому нельзя переносить безопасность одного способа отображения на другой.
>
> Для пользовательского аватара проще разрешить проверенные форматы либо обработать изображение на сервере по согласованной политике. Если inline SVG действительно нужен, ограничь элементы, атрибуты и внешние ссылки. Тест должен проверять фактический путь вставки, а не только MIME-строку ответа.

> [!followup]- Что дают Trusted Types при работе с опасными HTML-sinks?
>
> Trusted Types позволяют требовать типизированные значения для опасных sinks вроде `innerHTML`, если соответствующая CSP-политика включена и поддерживается браузером. При enforced `require-trusted-types-for 'script'` строка без подходящей default policy отклоняется; если default policy есть, браузер сначала передаёт строку ей. Доверенное значение создаётся через разрешённую policy.
>
> Policy должна реально проверять или очищать вход, например перед созданием `TrustedHTML`. Функция `createHTML: value => value` лишь маркирует произвольную строку доверенной и сохраняет уязвимость. Централизация policy делает пути вставки обозримыми и пригодными для аудита.
>
> Это дополнительный барьер DOM XSS, а не автоматический sanitizer и не замена серверной авторизации. Проверяй поддержку целевых браузеров, нарушения CSP и fallback; обычный пользовательский текст проще вообще не направлять в HTML-sink.

## Когда нужны MutationObserver, ResizeObserver и IntersectionObserver?

> [!answer]- Короткий ответ — 30–90 секунд
>
> MutationObserver наблюдает изменения DOM, ResizeObserver — размеры, IntersectionObserver — пересечение с областью наблюдения. Выбираю API под нужное событие, отключаю наблюдение при завершении и избегаю циклов, в которых обработчик вызывает новое изменение. Пересечение не гарантирует, что каждый пиксель элемента виден пользователю.
>
> Для подгрузки списка наблюдают пересечение нижнего маркера через IntersectionObserver. Размер контейнера графика наблюдают через ResizeObserver. MutationObserver полезен для изменений чужого DOM; собственное состояние приложения лучше читать через его владельца, а не восстанавливать по изменению разметки.
>

> [!followup]- Когда для отложенной загрузки нужен IntersectionObserver, а когда достаточно loading="lazy"?
>
> Для обычных изображений и iframe сначала используй нативный `loading="lazy"`: браузер сам выбирает момент загрузки. Задай размеры изображения, чтобы зарезервировать место и избежать скачка layout. Изображение первого важного экрана, особенно LCP, обычно не следует откладывать без причины.
>
> IntersectionObserver нужен, когда требуется собственное действие при приближении: загрузить тяжёлый виджет, подготовить следующую страницу или применить отдельный порог. `rootMargin` позволяет начать заранее, а после одноразового запуска узел можно перестать наблюдать.
>
> Пересечение не доказывает, что пользователь действительно увидел содержимое: оно может быть перекрыто. Проверяй медленную сеть, прокрутку назад и повторное монтирование; ошибка загрузки должна иметь понятное состояние.

> [!followup]- Как организовать постепенную загрузку списка при прокрутке через IntersectionObserver?
>
> Наблюдай отдельный sentinel после последней строки. При пересечении запускай следующую страницу только если `!loading && hasMore`; сохраняй cursor и предотвращай параллельные запросы одной страницы. После успеха добавляй записи с дедупликацией по устойчивому ID.
>
> На ошибке сохрани уже загруженный список и предложи явный повтор. Callback может вызываться многократно, но повтор не гарантирован, если sentinel после добавления короткой страницы остался видимым без пересечения нового порога. После append явно перепроверь видимость и с лимитом догрузи следующую страницу либо оставь кнопку; не создавай бесконтрольный цикл.
>
> Предусмотри доступную кнопку «Загрузить ещё» и сохранение позиции. Infinite scroll не ограничивает память автоматически: длинному списку могут понадобиться виртуализация DOM и отдельное ограничение кэша данных.

> [!followup]- Кто останавливает созданные таймеры, наблюдения и запросы?
>
> Ресурсом управляет тот владелец, который определяет время его жизни: компонент, composable/hook, экран или сервис. Создание и cleanup должны находиться рядом: `clearTimeout`, `observer.disconnect`, снятие listener и abort запроса входят в один сценарий освобождения.
>
> Например, observer размеров графика создаётся при появлении контейнера и отключается при его удалении или замене. Если запрос может проигнорировать abort, дополнительно запрещают позднему результату менять уже неактуальное состояние.
>
> Удаление DOM само по себе не завершает таймер или Promise. Проверь повторные mount/unmount и событие после cleanup. Если ресурс намеренно общий для нескольких экранов, его владелец должен считать потребителей или иметь явно более длинное время жизни.

> [!followup]- Почему ResizeObserver может вызвать цикл изменения размеров и как его устранить?
>
> Если callback измеряет элемент и каждый раз меняет его размер так, что возникает новое измерение, создаётся обратная связь. Например, `width = observedWidth + 10` не имеет устойчивого результата и будет увеличивать блок снова и снова.
>
> Сначала проверь, можно ли выразить раскладку через CSS. Если запись нужна, сравни требуемый размер с уже установленным и выбирай правило, сходящееся к стабильному состоянию. Разделение наблюдаемого контейнера и изменяемого содержимого иногда убирает цикл.
>
> `requestAnimationFrame` может перенести запись на следующий кадр, но не исправляет бесконечное правило: получится цикл между кадрами. Проверяй отсутствие повторяющихся уведомлений и ошибок ResizeObserver, а также стабильность размера после внешнего изменения.

## Как работает форма в браузере?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Форма объединяет поля, отправку и встроенную проверку данных. В приложении preventDefault позволяет перехватить отправку, но не заменяет проверку на сервере. Кнопка без явного type внутри формы обычно отправляет её; это важно учитывать для дополнительных действий.
>
> Кнопка «Показать пароль» внутри формы должна иметь `type="button"`, иначе может неожиданно отправить её. Отправку обрабатывают на форме, чтобы нажатие Enter и кнопки шло одним путём; сервер проверяет данные независимо от браузерной валидации.
>

> [!followup]- Как обрабатывать отправку формы клавишей Enter?
>
> Обрабатывай событие `submit` самой формы, а не только click кнопки. Тогда нажатие основной кнопки и неявная отправка через Enter проходят один путь валидации и сохранения.
>

> [!followup]- Как disabled влияет на взаимодействие, валидацию и данные HTML-формы?
>
> Отключённый контрол обычно не получает фокус, не участвует в пользовательском вводе, constraint validation и отправляемой `FormData`. Поэтому disabled-поле с заполненным ID не стоит считать надёжным способом передать этот ID серверу.
>
> Если значение должно оставаться доступным для чтения и отправки, у поддерживающих это полей может подойти `readonly`; оно имеет другую семантику. `aria-disabled="true"` лишь сообщает состояние вспомогательным технологиям и само не блокирует click или отправку.
>
> При pending можно отключить submit, но объяснить ожидание нужно текстом/статусом. Не отключай все поля до чтения FormData, иначе потеряешь их значения. Клиентский disabled также не заменяет серверную проверку допустимости операции.

> [!followup]- Как autocomplete помогает браузеру правильно заполнять форму?
>
> `autocomplete` описывает назначение поля: `name`, `email`, `street-address`, `current-password`, `new-password`, `one-time-code` и другие токены. Это помогает автозаполнению, менеджерам паролей и пользователям, которым трудно повторно вводить данные.
>
> Например, поле нового пароля помечают `autocomplete="new-password"`, а не пытаются отключить все подсказки. Для нескольких адресов используют секции и уточнения billing/shipping, чтобы браузер не смешивал получателя и плательщика.
>
> Атрибут не заменяет `name`, label и серверную валидацию. Браузер может не выполнить пожелание `off`, особенно для учётных данных. Проверяй реальное автозаполнение: значение может меняться не так, как при обычном последовательном вводе клавиш.

> [!followup]- Какие поля попадают в FormData и как работать с повторяющимися именами и файлами?
>
> `new FormData(form)` собирает успешные контролы с `name`: обычные значения, выбранные варианты и File-объекты. Disabled-поля и непомеченные checkbox обычно отсутствуют. Несколько полей с одним именем требуют `getAll(name)`, а `get(name)` вернёт только первое значение.
>
> Если данные зависят от нажатой submit-кнопки, используй соответствующий submitter при создании FormData в поддерживаемой среде. Для загрузки через fetch передай FormData как body и не выставляй вручную multipart Content-Type: браузер добавит правильный boundary.
>
> Проверяй форму с несколькими файлами, пустыми полями и checkbox. TypeScript-тип не превращает полученную строку в число: преобразование и валидация должны следовать серверному контракту.

## Как искать утечку DOM?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Повторяю создание и удаление компонентов, сравниваю снимки памяти и ищу удалённые узлы, которые всё ещё удерживаются ссылками. Частые причины — обработчики на document или window, наблюдатели, таймеры и сторонние виджеты без освобождения ресурсов. Проверяю путь ссылок до удерживающего объекта.
>
> Несколько раз открывают и закрывают экран со сторонним редактором и проверяют, возвращается ли число удерживаемых объектов к ожидаемому уровню. Если удалённый контейнер остаётся связан с глобальным listener, вызывают API уничтожения редактора и снимают внешние подписки.
>

> [!followup]- Как heap snapshot помогает найти причину удержания удалённого DOM?
>
> После повторяемого открытия/закрытия экрана снимаю сравнительные снимки heap и ищу detached-узлы, которые должны были исчезнуть. Для подозрительного узла смотрю Retainers — цепочку ссылок до удерживающего корня. Detached означает отсутствие в документе, но само по себе не доказывает ошибку: узел мог быть намеренно сохранён для повторного использования.

Убираю диагностические ссылки из консоли и учитываю законный ограниченный кэш. Timeline помогает заметить рост и GC, а снимок объясняет, кто удерживает конкретный объект; эти инструменты решают разные задачи. [Chrome: поиск проблем памяти](https://developer.chrome.com/docs/devtools/memory-problems).

> [!followup]- Как делегирование событий связано с утечками DOM?
>
> Делегирование размещает один listener на общем предке и определяет нужный элемент по пути события, например через `target.closest('[data-action]')`. Это удобно для динамических строк и уменьшает число обработчиков, но само по себе не гарантирует отсутствие утечки.
>
> Глобальный listener на document может замыкать удалённый контейнер или Map всех строк и удерживать их после закрытия экрана. Владелец должен снять listener и очистить ненужные ссылки. Для Shadow DOM учитывают retargeting и composedPath.
>
> Проверка: несколько раз открыть/закрыть список, сравнить heap и найти retaining path удалённого узла. Число listeners полезно для диагностики, но сборщик способен удалить недостижимый узел вместе с его собственным listener.

> [!followup]- Кто останавливает созданные таймеры, наблюдения и запросы?
>
> Владелец времени жизни компонента обязан закрывать созданные внешние связи: global listener, observer, таймер, сторонний виджет и запрос. Cleanup размещают рядом с созданием, чтобы было видно, что именно удерживает ссылки.
>
> Например, редактор создаёт listener на window, замыкающий DOM-контейнер. Удаление контейнера из документа не разрывает ссылку от window; нужен `editor.destroy()` или соответствующее снятие listener. При смене узла прежнюю связь тоже освобождают.
>
> Проверяй retaining path в heap snapshot после повторных циклов открытия/закрытия. Не называй любую оставшуюся ссылку утечкой: кэш может намеренно хранить объект ограниченное время. Важно, есть ли владелец, предел хранения и реальная необходимость удержания.

## Чем Web Worker отличается от Service Worker?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Web Worker выполняет задачи приложения и общается с основным потоком сообщениями. Service Worker обрабатывает события собственного жизненного цикла и сетевые события в своей области действия. У обоих нет прямого доступа к DOM, но возможности и правила времени жизни различаются.
>
> Разбор большого файла можно передать Web Worker, который вернёт результат сообщением. Service Worker нужен для сетевых и офлайн-сценариев, а не как обычный вычислительный работник. Передача больших данных тоже имеет цену копирования либо передачи владения.
>

> [!followup]- Чем Dedicated Worker отличается от Shared Worker?
>
> Dedicated Worker создаётся для конкретного владельца и обменивается сообщениями через `postMessage` и события message. Shared Worker может обслуживать несколько подходящих контекстов одного origin через отдельные MessagePort, например координировать общую связь нескольких вкладок.
>
> Оба исполняются вне основного потока и не имеют прямого доступа к DOM. Для тяжёлого разбора файла обычно достаточно Dedicated Worker; Shared Worker оправдан, когда действительно требуется совместный процесс и протокол между потребителями.
>
> Учитывай поддержку целевых браузеров, закрытие портов, идентификацию клиентов и время жизни. Shared Worker не является гарантированно бессрочным сервером и не заменяет устойчивое хранение; важное состояние должно переживать его завершение.

> [!followup]- Как Service Worker обеспечивает работу без сети и почему одного кэша недостаточно?
>
> Service Worker может перехватывать fetch в своей области и возвращать сохранённые ответы: оболочку приложения, документы или данные по выбранной стратегии. При установке/обновлении определяют, что кэшировать и когда удалять старые версии.
>
> Кэш ресурсов позволяет открыть экран offline, но не решает сохранение пользовательских изменений. Для них нужен локальный outbox, идентификаторы операций, повтор, проверка авторизации и разрешение конфликтов после возвращения сети. Персональные данные нельзя случайно смешивать между пользователями одного устройства.
>
> Проверяй первое посещение, повторное offline-открытие и обновление версии. Если ресурсы никогда не были скачаны, service worker не создаст их из ничего; offline-сценарий должен объяснять, что доступно сейчас.

> [!followup]- Как завершаются Web Worker и Service Worker и где нельзя хранить единственную копию данных?
>
> Dedicated Worker можно немедленно остановить через `worker.terminate()`; код внутри worker может вызвать `self.close()`. Незавершённая работа не получает гарантированного финального callback, поэтому нужный результат следует передавать и подтверждать заранее.
>
> Service Worker управляется браузером и может останавливаться между событиями. Его глобальные переменные не являются долговременным хранилищем. Для асинхронной работы конкретного события используют предусмотренные `waitUntil`/`respondWith`, а устойчивые данные сохраняют в IndexedDB или другом подходящем хранилище.
>
> Не строй service worker на бесконечном таймере как постоянно запущенный daemon. Проверка должна пережить остановку и новый запуск worker, восстановив состояние из хранения, а не только работать в одной непрерывной сессии.

> [!followup]- Что означает передача владения ArrayBuffer в Worker?
>
> При `worker.postMessage({ buffer }, [buffer])` ArrayBuffer передаётся через transfer list. Отправитель теряет доступ к прежнему содержимому: буфер становится detached, а получатель получает владение данными. Это позволяет избежать обычного копирования большого бинарного payload.
>
> TypedArray сама не является transferable, но можно передать её `.buffer`; учитывай, что этим буфером могут пользоваться и другие views, которые тоже потеряют доступ. Если буфер есть только в transfer list, но на него нет ссылки в payload сообщения, отправитель всё равно потеряет владение, а получатель не сможет получить к нему доступ. Поэтому включай буфер и в сообщение.
>
> Если данные нужны обеим сторонам, выбери копирование или отдельно спроектированную shared-memory модель. SharedArrayBuffer имеет другие требования и синхронизацию. Проверка после transfer должна подтвердить недоступность старого буфера и корректность результата у worker.

## Чем коллекции DOM отличаются от массива?

> [!answer]- Короткий ответ — 30–90 секунд
>
> NodeList и HTMLCollection имеют собственный набор методов. В зависимости от API коллекция может обновляться вместе с DOM либо оставаться снимком. Для получения массива использую Array.from или, если поддерживается перебор, оператор spread. Изменение DOM во время обхода живой коллекции меняет её состав.
>
> `querySelectorAll()` даёт снимок NodeList, а `getElementsByClassName()` — живую HTMLCollection. Если удалять элементы при обходе живой коллекции по индексам, индексы сдвигаются; сначала создают массив либо выбирают обход с учётом этой семантики.
>

> [!followup]- Какой результат возвращает querySelectorAll и обновляется ли он после изменения DOM?
>
> `querySelectorAll` возвращает статический NodeList всех совпадений в порядке документа. Если совпадений нет, это пустая коллекция, не null. Добавленные позже элементы не появляются в уже полученном результате.

> Статичен состав, а не сами узлы: изменение свойства найденного элемента видно через сохранённую ссылку. Удалённый из DOM узел также может оставаться в NodeList, пока коллекция его удерживает.
>
> Для нового состояния выполни запрос снова. Некорректный CSS-selector вызывает SyntaxError; если часть selector получена из ID пользователя, используй подходящее экранирование, например CSS.escape. Проверка должна различать пустой допустимый результат и ошибку синтаксиса, а не обрабатывать оба как отсутствие элементов.

> [!followup]- Чем children отличается от childNodes и как безопасно обходить children при удалении?
>
> `children` возвращает живую HTMLCollection только непосредственных дочерних элементов. `childNodes` включает также текстовые и другие узлы и тоже является живой коллекцией. Поэтому пробелы в HTML могут влиять на childNodes, но не добавляют элементы в children.
>
> При удалении во время прямого обхода индексы живой коллекции сдвигаются: следующий узел можно пропустить. Сделай снимок `Array.from(parent.children)` либо удаляй `firstElementChild` в цикле до его отсутствия, если требуется очистить всё.
>
> Это не рекурсивный поиск всех потомков. Для вложенных совпадений нужен querySelectorAll с соответствующим selector. Выбирай API по нужной глубине и типу узлов.

> [!followup]- Почему у DOM-коллекции нет map и как преобразовать её без потери смысла?
>
> NodeList и HTMLCollection не являются массивами и не обязаны иметь методы Array.prototype. Для отображения в массив используй `Array.from(nodes, node => node.textContent)` или `[...nodes].map(...)`, если коллекция поддерживает итерацию.
>
> Преобразование фиксирует текущий состав, но сохраняет ссылки на те же DOM-узлы. Оно не копирует поддеревья и не делает элементы независимыми от документа. Для больших коллекций учитывай дополнительный массив.
>
> Если нужно только пройти по узлам и выполнить действие, достаточно поддерживаемого `for...of` или NodeList.forEach; создавать массив ради каждого обхода необязательно. При мутации живой коллекции снимок, напротив, помогает избежать сдвига индексов.

> [!followup]- Когда поиск DOM-элемента возвращает null и как правильно обработать отсутствие?
>
> `querySelector` и `getElementById` возвращают null, если элемента нет. Это может быть нормальным состоянием условного интерфейса или признаком ошибки момента/области поиска. `querySelectorAll` вместо этого возвращает пустой NodeList.
>
> Если элемент обязателен для запуска виджета, проверь результат и сообщи понятную ошибку инициализации. Если он необязателен, пропусти действие явно. TypeScript non-null assertion `!` только подавляет проверку типов и не создаёт DOM-узел.
>
> При условном render связывай действие с появлением элемента через ref/lifecycle, а не случайным таймером. Проверь как наличие, так и отсутствие узла, чтобы `null.addEventListener` не превращал нормальный закрытый экран в исключение.

## Как управлять фокусом после изменения интерфейса?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Фокус переношу, когда это нужно для сценария: при открытии диалога, ошибке формы или удалении выбранного элемента. После закрытия диалога возвращаю его инициатору. Обновление компонента само по себе не должно сбрасывать ввод или перемещать пользователя в неожиданное место.
>
> После удаления строки, в которой была активная кнопка, фокус переводят на следующую подходящую строку или управление списком. После ошибки формы его можно направить к сводке ошибок; без правила пользователь клавиатуры может потерять своё место.
>

> [!followup]- Как устойчивый key помогает сохранять фокус при обновлении списка?
>
> Устойчивый key связывает компонент и DOM с конкретной сущностью. При перестановке строк React/Vue может сохранить тот же input и его фокус, вместо того чтобы пересоздать узел или привязать состояние к другой записи.
>
> Индекс как key в изменяемом списке сохраняет позицию, а не идентичность. После вставки первой строки введённый текст или фокус может оказаться у другого пользователя. Случайный key пересоздаёт элементы при каждом render.
>
> Стабильный key не определяет, куда перевести фокус после удаления активной строки. Для этого нужен отдельный контракт: следующая строка, предыдущая или управление списком. Проверяй вставку, перестановку и удаление с реально сфокусированным полем.

> [!followup]- Когда autofocus полезен, а когда неожиданно отнимает фокус?
>
> Автофокус уместен при явном переходе в новый сценарий, например открытии диалога поиска. Безусловный фокус при каждом обновлении компонента может отнять ввод у другого поля, прокрутить страницу и открыть экранную клавиатуру на телефоне.
>
> Назначай фокус после фактического появления доступного узла и только при нужном переходе состояния. При закрытии dialog возвращай его инициатору, если тот ещё существует. Для длинного диалога начальной точкой может быть заголовок с `tabindex="-1"`, а не первое поле далеко ниже.
>
> Проверь клавиатуру и мобильный экран. Сам атрибут autofocus не реализует удержание фокуса внутри модального окна и не обеспечивает недоступность фонового интерфейса.

> [!followup]- Как tabindex влияет на программный фокус и порядок Tab?
>
> `tabindex="0"` включает элемент в обычный порядок клавиатурной навигации, а `tabindex="-1"` позволяет программно сфокусировать его, обычно исключая из последовательного Tab-порядка. Положительные значения задают отдельный приоритет и часто создают запутанную навигацию при изменении страницы.
>
> Для сводки ошибок или заголовка dialog подходит `-1`: код переводит туда фокус после события. Для обычного действия лучше настоящая button, у которой уже есть клавиатурная семантика, вместо div с tabindex.
>
> Tabindex не добавляет роль, обработку Enter/Space или доступное имя. Проверь порядок через всю страницу и обратный Shift+Tab; локально правильный компонент может нарушить общий маршрут фокуса.

> [!followup]- Как сообщать screen reader об изменениях интерфейса, не перемещая фокус без необходимости?
>
> Для фонового статуса используй подходящую live region, например `role="status"`, чтобы сообщить «Результаты обновлены» без переноса фокуса из поля. Срочную ошибку можно объявить через alert, но не нужно делать все сообщения assertive.
>
> Когда пользователь явно открывает dialog или отправляет невалидную форму, перевод фокуса может быть частью сценария: к заголовку диалога, сводке или первому ошибочному полю. Сообщения связывают с полями через aria-describedby и сохраняют доступные имена.
>
> Не дублируй одновременно одно и то же объявление несколькими механизмами. Автоматическая проверка ARIA полезна, но фактический текст и порядок озвучивания проверяют со screen reader и клавиатурой в целевых сочетаниях браузера и платформы.

## Как управлять CSS в большом приложении?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Использую принятые границы стилей: БЭМ, CSS Modules либо другой согласованный способ. Общие цвета, размеры и правила размещения отделяю от деталей отдельного компонента. Именование и изоляция не отменяют каскад, адаптивность и доступность.
>
> Общие значения цветов и отступов задают через tokens, а специфичные стили карточки держат в её области. Генерация уникальных имён классов уменьшает случайные совпадения селекторов, но наследуемые свойства и глобальные правила всё равно могут влиять на компонент.
>

> [!followup]- Как БЭМ разделяет блок, элемент и модификатор в общих CSS-компонентах?
>
> Блок обозначает самостоятельную часть интерфейса, элемент — её внутреннюю часть, модификатор — вариант или состояние. Например, `.card`, `.card__title`, `.card--selected`. Имена выражают принадлежность и уменьшают случайные совпадения в глобальном CSS.
>
> Модификатор обычно применяется вместе с базовым классом: `class="card card--selected"`. Элемент не обязан повторять всю DOM-вложенность в имени; `.card__title` остаётся тем же контрактом после добавления технической обёртки.
>
> БЭМ — соглашение, не механизм браузерной изоляции. Наследование, глобальные selectors и специфичность продолжают действовать. Не смешивай несколько схем именования без причины; проверяй, что компонент можно использовать в другом контейнере без зависимости от случайных внешних предков.

> [!followup]- Почему scoped CSS во Vue не даёт полной изоляции компонента?
>
> Vue scoped CSS преобразует selectors, добавляя служебные атрибуты, а не создаёт Shadow DOM. Это ограничивает совпадения локальных правил, но глобальные стили, наследуемые свойства и CSS-переменные по-прежнему влияют на компонент.
>
> Корневой элемент дочернего компонента может получать scoped-стили родителя для раскладки. `:deep`, `:slotted` и `:global` намеренно расширяют область воздействия по своим правилам. Поэтому утверждение «scoped полностью защищает от внешнего CSS» неверно.
>
> Например, глобальный `button { font: ... }` способен изменить кнопку внутри scoped-компонента. Проверяй общий reset, тему и соседние приложения. Для публичного оформления лучше предоставлять tokens/props/parts по выбранной технологии, чем зависеть от внутренних deep-selectors.

> [!followup]- Как выбирать rem, em и vw для масштабируемого интерфейса?
>
> `rem` связан с размером шрифта корневого элемента, `em` — с размером шрифта элемента, а в `font-size` с унаследованным размером; `vw` — с шириной viewport. Для типографики и общих отступов часто удобен rem, для внутренних пропорций кнопки — em.
>
> Чистый `font-size: 2vw` может сделать текст слишком мелким на узком экране и неудобным при пользовательском масштабировании. Ограничивай fluid-размер через `clamp` и сохраняй разумные относительные границы.
>
> Не заменяй все px автоматически: тонкая граница и адаптивная типографика имеют разные задачи. Проверяй увеличение текста, вложенные em и длинную локализацию; выбор относительных единиц сам по себе не гарантирует доступность.

> [!followup]- Чем псевдокласс отличается от псевдоэлемента и что нельзя прятать в generated content?
>
> Псевдокласс выбирает состояние или отношение существующего элемента: `:hover`, `:focus-visible`, `:checked`, `:nth-child`. Псевдоэлемент обозначает определённую часть отображения, например `::before`, `::after`, `::first-line`.
>
> Для видимого клавиатурного фокуса используй `:focus-visible`, а декоративную иконку можно разместить в `::before`. Но важный текст кнопки или единственное сообщение об ошибке лучше держать в DOM: generated content имеет ограничения доступности, копирования и взаимодействия.
>
> Не считай `:hover` достаточным состоянием интерактивного элемента — клавиатура и сенсорное управление работают иначе. Проверяй реальные состояния focus/disabled/checked, а не только скриншот мыши над элементом.

> [!followup]- Как учитывать схлопывание margin при проектировании CSS-компонентов?
>
> Не полагайся на случайное сложение вертикальных margin между внутренними блоками и контейнером. Отступ первого ребёнка может схлопнуться с родительским и выглядеть как внешний отступ всего компонента; изменение border или display затем неожиданно меняет раскладку.
>
> Для внутренних расстояний часто проще применять padding контейнера и gap в flex/grid. Если нужен обычный блочный поток без схлопывания с потомками, подходит `display: flow-root`, учитывая его влияние на formatting context.
>
> Не вводи повсюду `overflow: hidden` только ради этого: оно ещё и обрезает содержимое. Проверь карточку отдельно и внутри нескольких контейнеров, с первым/последним элементом и без них; компонент должен иметь ясную границу внешних и внутренних отступов.

> [!followup]- Как организовать z-index в большом приложении без бесконечного увеличения чисел?
>
> Задай небольшую согласованную шкалу слоёв по ролям: обычный контент, dropdown, закреплённая панель, modal, уведомления. Затем проверь, какие предки создают stacking context через transform, opacity и другие свойства.
>
> Числа сравниваются внутри контекста. Dropdown с `z-index: 9999` не выйдет поверх соседнего контекста, если его родитель целиком расположен ниже. Решение может быть в уровне родителя, переносе overlay или использовании нативного top layer.
>
> Отдельно анализируй clipping от overflow: высокий z-index не отменяет обрезание. Визуальная проверка должна включать сочетания компонентов, например modal поверх sticky-header и dropdown внутри modal, а не каждый слой по отдельности.

## Когда применять sendBeacon для телеметрии?

> [!answer]- Короткий ответ — 30–90 секунд
>
> sendBeacon ставит небольшой POST-запрос в очередь без обычного чтения ответа. Возвращаемое логическое значение означает принятие в очередь, а не подтверждение доставки.
>
> Для небольшой телеметрии при уходе со страницы sendBeacon удобен тем, что не требует ждать ответа в UI, но событие может не дойти. Для бизнес-записи, которую нельзя потерять, нужен подтверждаемый контракт.
>

Проверенные детали API: [sendBeacon](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon).

> [!followup]- Почему телеметрию лучше отправлять при visibilitychange, чем ждать unload?
>
> Переход документа в `hidden` часто является последним наблюдаемым событием перед закрытием или остановкой страницы, особенно на мобильных устройствах. `unload` может не произойти и способен мешать эффективному использованию back/forward cache.
>
> Обработчик `visibilitychange` проверяет `document.visibilityState === 'hidden'` и отправляет небольшой накопленный пакет через sendBeacon. Скрытие бывает и обычным переключением вкладки, поэтому событие нельзя считать окончательным завершением сессии; пакеты нуждаются в ID и дедупликации.
>
> Не откладывай единственную копию критичных данных до этого момента. Пользователь или ОС могут завершить процесс без удобного callback. Для важных изменений нужен обычный подтверждаемый сценарий сохранения, пока страница ещё активна.

> [!followup]- Когда fetch с keepalive полезнее sendBeacon и какие ограничения сохраняются?
>
> `fetch(..., { keepalive: true })` полезен, если нужен другой HTTP-метод, настройка запроса или доступ к ответу, пока контекст ещё жив. Браузер может продолжить такой запрос после ухода страницы; sendBeacon предоставляет более узкий API небольшого POST без чтения ответа.
>
> Keepalive не разрешает отправлять произвольно большой файл и не отменяет ограничения CORS, авторизации и бюджета тела запроса. После уничтожения страницы нельзя рассчитывать, что её JavaScript обработает Promise, даже если сеть завершила отправку.
>
> Для небольшой телеметрии выбирай простой подход по контракту. Для бизнес-записи сохраняй идентификатор операции и способ восстановить результат при следующем открытии; keepalive сам не даёт подтверждённой доставки.

> [!followup]- Как подтвердить доставку события, если sendBeacon вернул true?
>
> `true` означает только принятие данных в очередь браузера. Оно не подтверждает получение сервером, обработку или запись в БД. `false` говорит, что поставить пакет в очередь не удалось; UI не должен выдавать это за успешную доставку.
>
> Если подтверждение обязательно, используй обычный запрос с ответом и устойчивый ID операции, сохраняй неподтверждённые события локально и повторяй с дедупликацией на сервере. После перезапуска можно запросить состояние или повторить тот же пакет.
>
> Для необязательной аналитики допустима документированная потеря части событий. Для оплаты, согласования или сохранения документа такой контракт недостаточен. Проверка должна наблюдать серверный итог, а не только return value браузерного API или запись в Network.
