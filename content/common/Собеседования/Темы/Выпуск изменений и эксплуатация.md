## Как устроены коммит, ветка, слияние и rebase?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Коммит хранит снимок файлов и ссылки на родительские коммиты. Ветка — изменяемая ссылка на коммит. Слияние соединяет истории; rebase переносит изменения на другое основание и создаёт новые коммиты с другими идентификаторами. До изменения истории проверяю рабочую директорию, выбранную ветку, удалённую ветку и чужие изменения.
>
> Ветка задачи и главная ветка могут указывать на разные цепочки коммитов. Merge сохраняет связь историй, rebase создаёт новые коммиты поверх другой базы. Переписывание опубликованной цепочки влияет на коллег, использующих прежние идентификаторы.
>

> [!followup]- Как убедиться, что разрешение конфликта сохранило поведение обеих сторон?
>
> До разрешения конфликта формулирую, какое поведение добавляла каждая сторона, и читаю общий предок и обе версии конфликтного участка. Совпадение строк не равно совпадению намерений. Например, одна ветка добавила AbortController в поиск, другая — проверку номера запроса перед обновлением pending. Выбор целиком ours или theirs потеряет часть защиты.
>
> Во время обычного merge результат можно сравнить с обеими сторонами через git diff --ours и git diff --theirs до завершения разрешения; затем проверяю итоговый staged diff. При rebase смысл сторон отличается, поэтому ориентируюсь на конкретные коммиты и их изменения, а не на бытовое понимание «моё». [Git: проверка результата слияния](https://git-scm.com/book/en/v2/Git-Tools-Advanced-Merging).
>
> Проверяю сценарий каждой ветки и их сочетание: новый поиск отменяет старый запрос, поздний finally не снимает индикатор нового, уход со страницы освобождает ресурсы. Запускаю относящиеся к ним тесты и проверку типов. Отсутствие маркеров конфликта и успешная сборка подтверждают лишь часть результата: семантический конфликт может остаться в соседних файлах, которые Git слил автоматически.

> [!followup]- Почему после rebase меняются идентификаторы коммитов?
>
> Идентификатор коммита вычисляется из содержимого всего объекта: ссылки на дерево файлов, родителей, автора и времени, коммитера и сообщения. При rebase Git повторно применяет изменения к новой базе, создавая коммиты с другими родителями. Даже когда текст патча тот же, объект и его ID уже другие.
>
> Например, если `C` был потомком `B`, а его изменения перенесли на `D`, получится `C'` с родителем `D`. Последующие перенесённые коммиты тоже меняют родителей. При операции без переноса конкретный ID может сохраниться, а некоторые изменения могут оказаться уже применёнными. Переписывание опубликованной ветки требует согласования с теми, кто построил работу на прежних коммитах.

> [!followup]- Что означает detached HEAD и как сохранить полезный коммит?
>
> Detached HEAD означает, что `HEAD` указывает прямо на коммит, а не через имя ветки. Так можно посмотреть тег или старую версию. Новые коммиты создавать можно, но они не двигают ни одну ветку. Чтобы сохранить работу, оставаясь на полезном коммите, создайте ветку: `git switch -c rescue-work`.
>
> Если уже переключились, найдите нужный ID в `git reflog`, проверьте снимок через `git show <id>` и закрепите его командой `git branch rescue-work <id>`. Например, исправление, сделанное во время проверки старого релиза, затем можно перенести из этой ветки. Reflog локален и записи могут истечь; для долговременного хранения нужна именованная ссылка.

## Как отменить изменение в Git?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Способ зависит от того, сохранено ли изменение в коммите и опубликован ли коммит. git revert добавляет коммит, отменяющий прежнее изменение. git reset перемещает ссылку ветки и, в зависимости от режима, меняет индекс и рабочие файлы. Для общей опубликованной истории обычно безопаснее отмена новым коммитом.
>
> Для уже используемого командой коммита revert сохраняет историю и добавляет обратное изменение. Для незакоммиченных файлов сначала проверяют diff и нужность правок. Нельзя выбирать reset только потому, что он короче по числу команд.
>

> [!followup]- Как отменить изменения файла с помощью git restore?
>
> Сначала проверьте `git diff -- file` и `git diff --staged -- file`. Команда `git restore -- file` восстанавливает рабочий файл из индекса, поэтому убирает только изменения поверх уже подготовленной версии. `git restore --staged -- file` убирает файл из staging, возвращая индекс к HEAD, но оставляет рабочую копию.
>
> Например, в staging уже добавлена правка поля формы, а после неё появились отладочные строки. Обычный restore удалит отладку, сохранив подготовленную правку. `git restore --source=HEAD --staged --worktree -- file` вернёт обе копии к HEAD; применяйте его только если обе группы правок больше не нужны. Restore не перемещает ветку, а отброшенные незакоммиченные строки reflog обычно не вернёт.

> [!followup]- Когда использовать git stash и как безопасно вернуть правки?
>
> `git stash` временно убирает незакоммиченные правки, когда нужно переключиться на другую работу. Просмотрите diff, затем сохраните нужную область с именем, например `git stash push -m 'form draft' -- src/form.ts`. По умолчанию неотслеживаемые файлы не входят в снимок; для них есть `-u`, если их действительно нужно включить.
>
> Перед возвратом посмотрите `git stash list` и нужный diff. `git stash apply 'stash@{0}'` применит снимок и оставит запись, поэтому можно проверить результат до удаления stash. Если файл за это время менялся, возможен конфликт. Для возвращения состояния staging отдельно нужен `--index`. Stash локален и годится для краткого переключения, а не для длительной передачи работы коллеге.

> [!followup]- Как найти потерянный коммит через git reflog?
>
> Reflog показывает, куда локально указывали HEAD и другие ссылки. После ошибочного reset или rebase найдите состояние перед операцией: `git reflog --date=local`, затем проверьте конкретный ID через `git show <id>`. Создайте спасательную ветку на этом ID до следующего переписывания истории.
>
> Например, reset передвинул ветку с C на B. Запись HEAD до reset указывает на C, и `git branch rescue-work <id-C>` снова делает его доступным. Не копируйте вслепую `HEAD@{1}`: переключения и другие команды могут изменить относительный номер. Reflog не синхронизируется между клонами, записи истекают, а незакоммиченные изменения не становятся объектами только из-за наличия reflog.

> [!followup]- Как различаются режимы git reset --soft, --mixed и --hard?
>
> При reset к коммиту `--soft` перемещает HEAD, оставляя индекс и рабочие файлы. `--mixed`, режим по умолчанию, ещё сбрасывает индекс, но сохраняет файлы. `--hard` приводит к целевому коммиту и индекс, и рабочее дерево; незакоммиченные изменения отслеживаемых файлов могут пропасть. Мешающие восстановлению неотслеживаемые пути тоже могут быть удалены.
>
> Например, `--soft HEAD~1` позволяет переделать последний локальный коммит, сохранив его изменения в staging. При `--mixed HEAD~1` эти изменения можно заново выбрать для staging. Перед любым режимом проверьте статус, нужную ветку и целевой коммит. В опубликованной общей истории обычно используйте `revert`: он добавляет обратный коммит, не перемещая прежние.

## Какие проверки должен выполнять CI?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверки должны воспроизводимо подтвердить согласованное изменение: установить зависимости, проверить типы и правила кода, выполнить нужные тесты и сборку. Результат относится к конкретной версии и окружению. После выпуска выполни smoke-проверку пользовательского сценария в рабочем окружении.
>
> Изменение формы требует проверки типов и нужных сценариев отправки, а новая сборка — воспроизводимой установки по lockfile. При выпуске сверь артефакт и настройки production с проверенной версией.
>

> [!followup]- Зачем CI нужен lockfile и что проверяет npm ci?
>
> `package.json` задаёт намерение и диапазоны, а lockfile фиксирует выбранное дерево, включая транзитивные зависимости. CI устанавливает его командой `npm ci`: при несовместимости манифеста и lockfile команда завершается ошибкой вместо переписывания lockfile. Существующий `node_modules` при установке очищается.
>
> Например, после добавления библиотеки забыли закоммитить обновлённый lockfile. Локальная установка могла исправить его автоматически, а CI показывает, что в репозитории неполная поставка. Фиксируйте также версию Node и npm и существенные настройки установки: платформенные зависимости, флаги и сборка нативных модулей могут давать разные результаты при одинаковом lockfile. Сам lockfile не подтверждает безопасность зависимостей.

> [!followup]- Из чего составить ключ кэша зависимостей в CI?
>
> Ключ должен меняться при изменении входов, от которых зависит содержимое кэша. Для кэша загрузок npm разумная основа — менеджер пакетов, хэш lockfile и среда, если в кэше есть платформенные данные. Для скомпилированных зависимостей важны также архитектура, версия Node и настройки сборки. По возможности кэшируйте загрузки, а дерево зависимостей создавайте установкой по lockfile.
>
> Например, ключ с одним именем ветки переживёт обновление пакетов и может вернуть устаревший `node_modules`. Кэш по хэшу и `npm ci` дают воспроизводимый путь даже при промахе. Запуск без кэша обязан работать. Не помещайте в него токены или приватные данные, которые могут быть доступны менее доверенным workflow.

> [!followup]- Какие артефакты сохранять по итогам CI и сборки?
>
> Сохраняйте результаты, которые нужно исследовать после завершения запуска или перенести между этапами: отчёты тестов, нужные журналы, трассы браузерного теста и готовый пакет поставки. Для деплоя свяжите сборку с commit SHA, запуском CI и digest содержимого. Так окружения получают именно проверенный пакет.
>
> Например, для упавшего теста формы сохраняют отчёт и трассу, а для успешной сборки — контейнер с неизменяемым digest. Трасса помогает локализовать сбой; запуск в production должен брать контейнер, а не пересобирать код заново. Ограничьте доступ и срок хранения: диагностический артефакт может содержать снимки экрана и данные тестовой сессии. Кэш ускоряет работу, но не служит доказательством поставки.

> [!followup]- Как расследовать нестабильную проверку CI?
>
> Сначала сохраните результат первого отказа: версию, журнал, порядок тестов, трассу и окружение. Воспроизведите проверку повторениями на той же версии, отдельно и вместе с соседними тестами. Ищите зависимость от времени, общего состояния, сети или порядка выполнения. Повтор в CI полезен как диагностика: прохождение со второй попытки должно оставаться видимым.
>
> Например, тест отправки ждёт фиксированные 500 мс, а под нагрузкой ответ приходит позже. Надёжнее дождаться наблюдаемого результата, например сообщения и подтверждённой записи, с обоснованным общим сроком. Временный карантин допустим с владельцем, сроком и альтернативной проверкой критичного сценария. Простое увеличение таймаута или числа повторов может скрыть настоящий дефект приложения.

> [!followup]- Как сделать проверку CI обязательной перед выпуском?
>
> Задайте обязательное условие на том этапе, где принимается решение. Для merge это правила ветки и нужный status check для целевой версии. Для выпуска — проверка успешного CI и соответствия его SHA и digest тому артефакту, который реально разворачивается. Убедитесь, что пропуск задачи не выдаёт разрешающий итог вместо необходимой проверки.
>
> Например, тесты прошли для A, затем в ветку добавили B. Результат A не разрешает выпуск B. Если используется очередь слияния, проверяйте версию с актуальной базой, которую очередь собирается принять. После деплоя smoke-проверка подтверждает рабочее окружение и настройки, но не заменяет контроль перед выпуском. Для исключения нужен явный порядок, чтобы отказ проверки не превращался в незаметный обход.

## Чем деплой отличается от включения новой функции для пользователей?

**ID вопроса:** Чем подготовка, развёртывание и включение изменений отличаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> При подготовке создаётся проверенная сборка. Развёртывание размещает её в окружении; включение делает новое поведение доступным пользователям. Переключатели возможностей позволяют разделить эти действия. Для подтверждения результата проверяю установленную версию и реальный сценарий, а не только завершение команды.
>
> Сборка нового экрана может пройти CI, затем попасть на сервер с выключенным flag и только позже стать доступной пользователям. Для каждого этапа нужен свой признак результата: собранный артефакт, запущенная версия и доступный пользовательский сценарий.
>

> [!followup]- Как переносить уже проверенную сборку между окружениями?
>
> Соберите артефакт один раз, запишите его digest и связь с исходным коммитом и передавайте этот же артефакт из тестового окружения в следующее. Настройки, адреса и секреты окружения задавайте при запуске. На каждом этапе сверяйте установленный digest и выполняйте соответствующую проверку сценария.
>
> Например, образ с новой формой проходит staging с тестовым API. В production берут тот же digest, но передают другой адрес API и оставляют флаг выключенным. Это сохраняет доказательство о составе сборки; отдельно проверяется совместимость настроек и API. Если фронтенд встраивает адреса при компиляции, разные окружения могут требовать разных сборок. Тогда проверяйте конкретный production-артефакт до выпуска, а не считайте его эквивалентным по одному SHA исходников.

> [!followup]- Как выбрать между откатом деплоя и отключением функции?
>
> Выберите действие, которое быстрее восстановит рабочий сценарий и совместимо с уже записанными данными. Флаг подходит, если старый путь остаётся рабочим и действительно исключает дефект. Если сбой в общей загрузке приложения, API или конфигурации, может потребоваться вернуть предыдущий проверенный артефакт и настройки либо выпустить совместимое исправление.
>
> Например, новый виджет формы ломается только при включении — выключение флага возвращает прежний виджет. Но если обновлённый API перестал принимать старый формат, оба интерфейса могут продолжить падать после переключения. Перед откатом проверьте миграции, фоновые задачи и состояние записей. После действия выполните сохранение и повторное чтение, затем сравните долю ошибок с уровнем до сбоя.

> [!followup]- Чем работоспособность отличается от готовности после деплоя?
>
> Работоспособность отвечает на вопрос, жив ли процесс и способен ли продолжать работу. Готовность показывает, можно ли направлять на него трафик сейчас. Экземпляр может быть запущен, но ещё прогревать кэш, загружать настройки или не иметь нужного соединения с БД. В таком состоянии readiness должна отказать, а liveness может проходить.
>
> Например, новая версия открыла HTTP-порт, но ещё не принимает запросы сохранения. Маршрутизатор ждёт готовности; перезапускать процесс каждый раз на этапе запуска бессмысленно. После появления готовности выполните пользовательскую smoke-проверку, включая нужную конфигурацию. Probe проверяет ограниченный сигнал и не доказывает, что пользователю включили новую функцию.

> [!followup]- Чем подтвердить деплой, включение функции и её работу?
>
> У каждого шага свой наблюдаемый результат. Деплой подтверждают версией и digest, которые действительно обслуживают запросы в целевом окружении. Включение подтверждают состоянием флага и реальным назначением варианта нужной группе. Работу подтверждает сквозной сценарий с ожидаемым результатом и наблюдение защитных метрик.
>
> Например, команда деплоя завершилась, но часть запросов ещё идёт в старые экземпляры. Ответ с меткой версии или проверка состояния rollout обнаружат это. Затем тестовый пользователь в целевой группе видит новую форму, сохраняет запись и после обновления получает сохранённые данные. Запись в панели флагов не гарантирует, что клиент получил новое значение. Ручная smoke-проверка даёт сигнал о конкретном пути, а не статистическую оценку всего выпуска.

## Как выпускать обновление постепенно и откатить его при ошибке?

**ID вопроса:** Как безопасно включать новую версию?

> [!answer]- Короткий ответ — 30–90 секунд
>
> До включения определяю точную сборку, совместимость данных, проверки готовности, метрики и способ отката. Можно сначала направить на новую версию часть трафика либо подготовить второе окружение. Эти приёмы снижают риск, но не делают несовместимую миграцию обратимой автоматически.
>
> Перед включением новой формы проверяют точную версию, нужный API, сохранение данных и рабочий старый путь. Если новая версия меняет формат данных, возврат старого кода может оказаться недостаточным откатом.
>

> [!followup]- Как использовать SLO для решения о продолжении постепенного выпуска?
>
> До выпуска задайте SLI, который связан с результатом пользователя, и пороги остановки. Сравнивайте новую версию с контрольной на сопоставимом трафике; смотрите ошибки, задержку и расход бюджета ошибок. Для быстрого отказа полезно короткое окно, для умеренного устойчивого ухудшения — более длинное. При превышении заранее заданной границы остановите рост доли и выполните согласованный откат.
>
> Например, SLO требует 99,9% успешных сохранений, а на новой версии доля отказов удерживается около 1%. Это в десять раз выше допустимой доли; общий график может скрыть отклонение при малом canary. Для очень малого трафика несколько запросов недостаточны для вывода. Заранее предусмотрите минимальный объём наблюдения и синтетическую проверку критичного пути.

> [!followup]- Как использовать переключатель возможности для безопасного выпуска?
>
> Разверните код со старым поведением по умолчанию, затем включите новое для выбранной группы. Делайте назначение стабильным на единице, важной сценарию: пользователь, организация или сессия. Проверьте оба пути и возможность быстрого выключения; для серверных действий храните решение там, где его можно применить к запросу последовательно.
>
> Например, новую форму сначала получают сотрудники, потом небольшая доля организаций. При росте отказов флаг возвращает старый интерфейс без пересборки. Если новая ветка уже записала несовместимые данные, выключение не восстановит старый сценарий. Флаг не заменяет проверку прав и план совместимости. После полного выпуска назначьте срок удаления временного флага и старого пути, чтобы команда не поддерживала две версии бесконечно.

> [!followup]- Как выбирать шаги постепенного увеличения доли трафика?
>
> Начните с доли, на которой можно быстро обнаружить серьёзный сбой и ограничить число затронутых пользователей. На каждом шаге дождитесь достаточного числа запросов и прохождения характерных сценариев. Сравните ошибки и задержку по версиям; при превышении порогов остановите рост и верните трафик на устойчивую версию.
>
> Например, новую версию проверяют на внутренней группе, затем на 5%, 25% и 100%. Это возможные ступени, а не универсальное правило: пять процентов от редких операций могут дать слишком мало данных. При состоянии на клиенте назначайте целую сессию или организацию, если переключение версии посреди сценария нарушает совместимость. Для общего хранилища отдельно убедитесь, что старый и новый код могут работать одновременно.

> [!followup]- Как зафиксировать точную версию для выпуска и отката?
>
> Зафиксируйте исходный commit SHA, идентификатор запуска CI и digest собранного артефакта. В манифесте окружения укажите именно digest; отдельно сохраните версию конфигурации, миграций и набор важных флагов. Подготовьте ссылку на предыдущий рабочий артефакт и проверьте, что он остаётся доступным.
>
> Например, тег `stable` может быть переназначен после проверки. Если выпуск ссылается на digest, это не поменяет запущенный образ при повторном развёртывании. Но даже идентичный образ может вести себя иначе с новой схемой БД или конфигурацией. Проверка версии подтверждает состав кода, а сценарий после выпуска подтверждает его работу в этой среде.

## Чем контейнер отличается от виртуальной машины?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Контейнер изолирует процессы и использует ядро хоста. Виртуальная машина получает виртуальное оборудование и собственную операционную систему. Образ контейнера задаёт файловую систему и настройки; запущенный контейнер — экземпляр процесса. Ограничения памяти, процессора и полномочий нужно настраивать отдельно.
>
> Несколько контейнеров приложения могут использовать одно ядро хоста, поэтому отказ или несовместимость ядра затрагивает их иначе, чем отдельные гостевые ОС. Контейнер не даёт сохранность БД, если данные живут только в его удаляемом слое.
>

> [!followup]- Как namespaces и cgroups изолируют процессы контейнера?
>
> Namespaces меняют представление процесса о системе: какие PID, сетевые интерфейсы и точки монтирования он видит. Cgroups группируют процессы для учёта и управления ресурсами, например ограничивают память и CPU. Это две разные задачи: отдельный список процессов сам по себе не задаёт лимит ресурсов.
>
> Например, процесс внутри контейнера видит себя как PID 1 и слушает порт 8080 в своей сети. Ограничение памяти в 256 МБ задаётся cgroup отдельно; при достижении лимита выделение памяти может привести к OOM. На Linux процессы контейнеров по-прежнему используют общее ядро, поэтому для контроля доступа нужны также capabilities, фильтрация системных вызовов и ограничения монтирования.

> [!followup]- Чем образ Docker отличается от запущенного контейнера?
>
> Образ задаёт файловую систему и метаданные запуска: команду по умолчанию, рабочую директорию, пользователя. Контейнер — конкретный экземпляр с собственным состоянием, настройками сети и добавленным слоем записи. Из одного образа можно запустить несколько контейнеров с разной конфигурацией.
>
> Например, два контейнера из одного образа API используют разные адреса базы и независимо пишут временные файлы. Изменение файла в одном контейнере не меняет исходный образ или второй контейнер. Перезапуск того же контейнера может сохранить его слой, но после пересоздания новый экземпляр начинает с образа. Данные, которые должны переживать пересоздание, храните в томе или внешнем сервисе.

> [!followup]- Зачем контейнеру том и какие данные в нём хранить?
>
> Том хранит данные вне слоя записи конкретного контейнера. Docker управляет его размещением, а контейнер получает путь монтирования. При пересоздании можно подключить тот же том, сохранив данные. Приложение должно писать именно в смонтированный каталог.
>
> Например, PostgreSQL хранит данные в каталоге, к которому подключён именованный том. Обновление образа не очищает этот том, но новая версия базы должна поддерживать его формат или пройти миграцию. Том не является резервной копией: удаление тома, ошибка приложения или отказ диска могут уничтожить данные. Сохранность подтверждают пересозданием в тестовой среде и проверкой восстановления из независимой копии.

> [!followup]- Какие ограничения безопасности остаются у контейнеров по сравнению с ВМ?
>
> Linux-контейнеры делят ядро хоста, поэтому изоляция зависит от конфигурации namespaces, полномочий и доступа к ресурсам. Запускайте процесс с минимальными правами, убирайте ненужные capabilities, ограничивайте монтирования и сеть. Не предоставляйте контейнеру управление Docker daemon, если оно не требуется.
>
> Например, сервис чтения отчётов может работать без root, с read-only файловой системой и единственным томом только для чтения. Это уменьшает область возможного ущерба. Виртуальная машина имеет отдельную гостевую ОС и добавляет границу гипервизора; она подходит, когда граница доверия требует более сильного разделения. Ни один вариант не освобождает от обновления базовых компонентов и ограничения прав внутри окружения.

## Как устроен Dockerfile?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Инструкции Dockerfile определяют образ, его слои и настройки. Учитываю контекст сборки, порядок кэшируемых шагов и многоэтапную сборку; в итоговый образ включаю только нужное для работы. Процесс запускаю без лишних привилегий. Секреты не записываю в слои; .dockerignore исключает ненужные файлы из контекста.
>
> Файлы зависимостей копируют и устанавливают до часто меняемого исходного кода, чтобы переиспользовать слой установки. Секрет, скопированный в слой и удалённый позже, может сохраниться в истории образа; нужны предназначенные для сборки механизмы секретов.
>

> [!followup]- Когда в Dockerfile использовать COPY, а когда ADD?
>
> Для обычного переноса файлов используйте `COPY`: оно копирует из контекста, другой стадии, образа или именованного контекста при соответствующих параметрах. `ADD` даёт дополнительные возможности, в том числе распаковку поддерживаемого локального tar и получение удалённого ресурса. Выбирайте его, если нужна именно такая семантика.
>
> Например, `COPY package.json package-lock.json ./` просто переносит манифесты, а `COPY --from=build /app/dist /srv` переносит готовый результат из стадии сборки. Если нужен архив по URL, зафиксируйте его версию и проверьте целостность, например через `ADD --checksum` для поддерживаемого HTTP-источника. Возможность скачивания не делает удалённый ресурс воспроизводимым; не считайте удалённый архив автоматически распакованным как локальный tar.

> [!followup]- Как ENTRYPOINT и CMD совместно задают команду контейнера?
>
> В exec-форме `ENTRYPOINT` удобно закрепить исполняемую команду, а `CMD` задать её аргументы по умолчанию. Аргументы после имени образа в `docker run` заменят `CMD` и будут переданы `ENTRYPOINT`. Без `ENTRYPOINT` команда из `CMD` сама запускает процесс; её тоже можно заменить.
>
> Например, при `ENTRYPOINT ["node", "server.mjs"]` и `CMD ["--port", "8080"]` запуск с `--port 8081` оставит Node и файл, поменяв порт. Exec-форма избегает промежуточного shell, который мог бы не передать сигналы завершения. Если нужен скрипт подготовки, в конце обычно запускают основной процесс через `exec`. Не рассчитывайте, что переменные окружения автоматически подставятся в JSON-массив exec-формы.

> [!followup]- Как повысить воспроизводимость сборки Docker-образа?
>
> Закрепите базовый образ по digest, версии инструментов и зависимости по lockfile. Устанавливайте зависимости командой, которая не переписывает lockfile, ограничьте контекст нужными файлами и явно задайте целевую платформу. Не используйте изменяемые ресурсы без версии или проверки целостности.
>
> Например, тег `node:24` может начать указывать на обновлённый образ; его digest фиксирует проверенную основу. После обновления digest запускайте проверки заново. Lockfile не фиксирует часы сборки, результаты сетевых запросов и платформу. Если нужно байтовое совпадение, уберите также влияние timestamp и недетерминированных шагов и сравните digest независимых сборок. Для обычной поставки надёжнее продвигать один уже проверенный образ, чем полагаться на его повторную сборку.

> [!followup]- Как передать секрет в Docker-сборку, чтобы он не попал в образ?
>
> Используйте BuildKit secret mount: передайте секрет через `--secret` и объявите `RUN --mount=type=secret,id=...` только в шаге, которому он нужен. Файл доступен во время этого шага и не копируется в слой автоматически. `ARG`, `ENV` и временный `COPY` для секрета не подходят: значение может остаться в метаданных, истории или слоях.
>
> Например, токен приватного registry нужен при установке пакетов, но не при запуске приложения. Смонтируйте конфигурацию на шаге установки и переносите в финальный образ только нужный результат. Secret mount не мешает команде самой записать токен в лог, кэш или выходной файл. Ограничьте права токена и проверьте, какие файлы и журналы публикует этот шаг.

## Как контейнеры обмениваются данными и сетью?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Сети и опубликованные порты задают доступ к сервису, тома — сохранение данных вне жизненного цикла контейнера. В пользовательской мостовой сети Docker поддерживает разрешение имён контейнеров; стандартная мостовая сеть имеет другой набор возможностей. localhost внутри контейнера обычно означает сам контейнер, а не хост.
>
> API обращается к БД по имени сервиса в общей сети; `localhost` внутри контейнера означает сам контейнер. Данные БД размещают в устойчивом томе, а наружу публикуют только необходимые порты.
>

> [!followup]- Когда подключать каталог хоста к контейнеру через bind mount?
>
> Bind mount отображает конкретный путь хоста в контейнер. Это удобно для разработки, когда изменения исходников должны сразу быть видны приложению, или для передачи локальной конфигурации. Для данных, которыми управляет Docker и которые нужно переносить между установками, часто удобнее именованный том.
>
> Например, подключите каталог конфигурации к ожидаемому пути с `readonly`, чтобы процесс не мог изменить файлы хоста. Монтирование поверх непустого каталога скрывает файлы, которые уже были в образе: подключение всего проекта поверх `/app` может скрыть установленные зависимости. Путь относится к хосту Docker daemon, а не обязательно к машине, где запущен CLI. Записываемый bind mount давайте только на необходимый каталог.

> [!followup]- Как работает DNS между контейнерами Docker?
>
> В общей пользовательской bridge-сети Docker разрешает имена контейнеров и сетевые алиасы через встроенный DNS. В стандартной сети `bridge` автоматическое разрешение по именам работает иначе: для обычных контейнеров на ней рассчитывать на имена нельзя. Compose по умолчанию создаёт для проекта общую сеть, в которой доступны имена сервисов.
>
> Например, API использует `db:5432`, а не IP контейнера и не `localhost`. После пересоздания БД адрес может измениться, имя остаётся. Уже открытое соединение с прежним экземпляром не переключится само: клиент должен переподключиться и заново разрешить имя. DNS не подтверждает готовность приложения; отдельно проверяйте, что сервис слушает порт и принимает нужные запросы.

> [!followup]- Чем публикация порта Docker отличается от EXPOSE?
>
> `EXPOSE 8080` описывает ожидаемый порт приложения в образе. Он не создаёт доступ через порт хоста. `docker run -p 127.0.0.1:8081:8080` связывает порт 8081 хоста с портом 8080 контейнера. Приложение должно слушать подходящий интерфейс внутри контейнера; публикация не запускает HTTP-сервер.
>
> Например, при локальной проверке открывают `http://127.0.0.1:8081`, а соседний контейнер в общей сети обращается по имени сервиса к 8080 без публикации. Без адреса хоста публикация по умолчанию может сделать порт доступным на всех его интерфейсах. Для БД, нужной только API в той же сети, публикацию обычно не добавляют.

> [!followup]- Как обнаруживать сервисы при изменении адресов контейнеров?
>
> Подключайте сервисы к нужной сети и обращайтесь к стабильному имени или алиасу, а не к IP экземпляра. В Compose таким именем обычно служит ключ сервиса. При замене экземпляра переподключайтесь и повторно разрешайте имя. Если нужен выбор по здоровью и балансировка между несколькими экземплярами, используйте соответствующий механизм среды развёртывания.
>
> Например, после пересоздания `db` приложение может получить разрыв существующего соединения. Новое подключение к `db:5432` найдёт актуальный адрес, если сервис подключён к той же сети. Это не даёт права автоматически повторить операцию с неизвестным исходом: обновление соединения и повтор записи имеют разные контракты. Для нескольких окружений не полагайтесь на случайные имена контейнеров; проверьте область сети и возможные конфликты алиасов.

## Чем проверки готовности и работоспособности отличаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Готовность показывает, может ли экземпляр принимать запросы. Проверка работоспособности помогает определить зависший процесс и необходимость перезапуска. Отказ внешней БД не всегда означает, что сам процесс нужно перезапустить. Неправильная проверка может вызвать лавину перезапусков вместо восстановления.
>
> Приложение может быть живо, но ещё загружать настройки и не принимать запросы. Readiness убирает его из распределения трафика. Liveness не стоит делать зависимой от каждого внешнего сервиса: временный отказ БД может вызвать бесполезную волну перезапусков.
>

> [!followup]- Зачем нужна startup probe и как она связана с readiness и liveness?
>
> Startup probe даёт медленно стартующему приложению время завершить запуск. В Kubernetes до её первого успеха liveness и readiness не выполняются. Если порог отказов startup probe исчерпан, контейнер считается не запустившимся и может быть перезапущен по политике. После успеха readiness управляет трафиком, а liveness обнаруживает отказ уже работающего процесса.
>
> Например, сервису иногда нужны 40 секунд на загрузку индекса, а зависание после запуска хочется обнаруживать быстрее. Отдельная startup probe задаёт больший допуск только запуску. Проверка должна отражать завершение инициализации, а не только открытый сокет. Если запуск зависит от общей БД, тщательно выбирайте условия: её длительная недоступность не должна превращать все экземпляры в непрерывный цикл перезапусков.

> [!followup]- Как организовать корректное завершение работы сервиса?
>
> Обрабатывайте `SIGTERM` один раз: прекратите принимать новую работу, завершите текущую в пределах общего срока, затем закройте пул соединений, фоновые задачи и журналы. Срок приложения должен оставлять запас до принудительного завершения со стороны среды. Длительные операции нужно завершать по контракту или оставлять в состоянии, которое можно безопасно восстановить.
>
> Например, при остановке HTTP-сервис перестаёт принимать новые запросы, даёт уже начатому сохранению закончить транзакцию и только потом закрывает БД. Если соединение пропало до ответа, клиент не знает исход записи и нуждается в сверке или идемпотентности. `SIGKILL` не запускает обработчики очистки. Проверьте сценарий остановки с активным запросом и убедитесь, что процесс не зависает до истечения срока.

> [!followup]- Как прекратить приём новых запросов и дать завершиться текущим?
>
> Переведите экземпляр в режим вывода из трафика, затем перестаньте принимать новые операции на уровне приложения и учитывайте активные. Готовность или удаление endpoint останавливает обычную маршрутизацию, но изменение распространяется не мгновенно. Существующие keep-alive соединения также могут приносить новые запросы; используйте механизмы завершения протокола и явное состояние draining.
>
> Например, при удалении Pod завершайте уже начатое сохранение, а новому запросу, пришедшему до обновления маршрута, отдавайте управляемый отказ. Для WebSocket может понадобиться отдельное уведомление и срок закрытия. После дедлайна завершайте оставшиеся соединения. В тесте наблюдайте два случая одновременно: начатый запрос получает ответ, а новый не принимается. Пробу готовности не используйте вместо учёта незавершённой работы.

> [!followup]- Как должны вести себя проверки при отказе зависимости?
>
> Спросите, может ли экземпляр ещё выполнять свой контракт. Если без зависимости сервис целиком не может отвечать, readiness может временно убрать его из трафика. Если часть маршрутов сохраняет полезную работу, оставьте её доступной и отдавайте контролируемый отказ только на затронутых путях. Liveness должна отражать сбой самого процесса, который имеет смысл лечить перезапуском.
>
> Например, недоступна система отправки почты. Если основная запись заказа работает через устойчивую очередь, сервер может продолжать принимать заказы. Если недоступна обязательная БД, перезапуск всех экземпляров добавит нагрузку и вряд ли восстановит её. Проверки зависимостей должны быть дешёвыми и ограниченными по времени; не превращайте probe каждого Pod в тяжёлый запрос к общей БД.

## Сервис на Linux не отвечает. Как проверить процесс, ресурсы и логи?

**ID вопроса:** Как диагностировать процесс Linux?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверяю состояние процесса, нагрузку процессора, память, открытые файлы, соединения, дисковые операции и журналы. ps, top, ss, df и free помогают проверить конкретные гипотезы. Сначала связываю наблюдение с проблемой; массовое завершение процессов без диагноза может скрыть причину и потерять данные.
>
> При высоком времени ответа сравнивают CPU, ожидание диска, память и очереди. Если процесс почти не использует CPU, увеличение числа ядер не обязано помочь: он может ждать БД или исчерпанный пул соединений.
>

> [!followup]- Как проверить, мешают ли права доступа запуску или работе сервиса Linux?
>
> Определите пользователя и группы процесса, затем проверьте конкретный отказавший ресурс. Для файла проверьте владельца, режим, ACL и право прохода по всем каталогам пути. Сопоставьте сообщение из журнала с попыткой чтения, записи, исполнения или открытия сокета. Проверка под root может скрыть причину.
>
> Например, конфигурация доступна на чтение, но один из родительских каталогов недоступен сервисному пользователю на проход. Файл не откроется, хотя `ls -l` на нём выглядит правильно. Исправьте узкое право на нужном пути, а не выдавайте запись всем. Если Unix-права выглядят корректно, проверьте политику SELinux или AppArmor и ограничения запуска сервиса, прежде чем менять владельца или режим.

> [!followup]- Как использовать сигналы при диагностике неотвечающего сервиса?
>
> Сначала соберите состояние процесса и журналы: завершение может уничтожить полезные следы. Если процесс нужно остановить, используйте штатную команду менеджера сервиса или отправьте `SIGTERM` после проверки PID. Дайте время обработчику, затем проверьте завершение и восстановление сценария. `SIGKILL` применяйте при невозможности штатной остановки и понимании последствий.
>
> Например, зависший обработчик держит соединения, а `SIGTERM` переводит сервис в draining и позволяет закончить текущие транзакции. Если процесс завис в непрерываемом ожидании ядра, даже `SIGKILL` не гарантирует мгновенного исчезновения. Не посылайте `SIGHUP` наугад: перезагрузка конфигурации — соглашение конкретной программы, а не универсальное свойство сигнала.

> [!followup]- Что можно узнать о процессе Linux из /proc?
>
> `/proc/<pid>` показывает состояние процесса глазами ядра. Смотрите `status` для состояния, UID и памяти, `limits` для пределов, `fd` для открытых дескрипторов и `cgroup` для группы ресурсов. Сопоставляйте снимок со временем сбоя и метриками: отдельное значение редко объясняет причину.
>
> Например, сервис перестал принимать соединения, в журнале есть `EMFILE`, а число дескрипторов приблизилось к soft limit. Просмотр типов дескрипторов помогает отличить утечку файлов от накопления сокетов. Снимок меняется во время чтения, а процесс может закончиться и его PID может быть использован вновь. Доступ зависит от прав. Не собирайте полный `environ` в общий отчёт: там могут быть секреты.

> [!followup]- Как проверить ограничения ресурсов у неотвечающего сервиса Linux?
>
> Отделите ресурсы хоста от лимитов конкретного процесса и cgroup. Сверьте `/proc/<pid>/limits`, события и статистику cgroup, журналы ядра и менеджера сервиса. Ищите совпадение с симптомом: исчерпание файловых дескрипторов, OOM или throttling CPU проявляются по-разному.
>
> Например, на хосте свободна память, но контейнер перезапускается. События OOM в его cgroup могут показать, что он достиг собственного `memory.max`. При скачках задержки и низкой загрузке хоста проверьте CPU quota и счётчики throttling. Увеличение лимита может временно восстановить работу, но не объясняет рост потребления. Снимите профиль или проверьте утечку перед постоянным повышением.

## Как устроены права и сигналы в Linux?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Права определяют доступ пользователей и групп к файлам. Сигналы уведомляют процесс о событиях: SIGTERM можно обработать для корректного завершения; SIGKILL не оставляет возможности освободить ресурсы. В контейнере нужно учитывать особую роль PID 1 и передачу сигналов дочерним процессам.
>
> Перед остановкой сервиса отправляют предусмотренный сигнал завершения, чтобы он закончил запросы и закрыл ресурсы. SIGKILL не позволяет выполнить обработчик очистки ресурсов. Права каталога и файла проверяют отдельно, а не открывают всё через 777.
>

> [!followup]- Чем chmod отличается от chown и как выбрать нужную команду?
>
> `chmod` меняет режим доступа к файлу, а `chown` — владельца или группу. Сначала выясните, под каким пользователем работает сервис и какое действие ему нужно. Смена владельца может быть лишней, если достаточно разрешить чтение существующей группе.
>
> Например, конфигурация принадлежит `root:app`, а процесс входит в группу `app`. Режим `640` позволяет процессу читать файл, оставляя запись владельцу. Для прохода по родительскому каталогу проверяйте отдельное право `x`. Перед рекурсивной сменой режима проверьте затронутые пути и ожидаемую схему прав: одна команда может сделать секреты доступными лишним пользователям или лишить сервис доступа.

> [!followup]- Что означает право выполнения для файла и каталога в Linux?
>
> Для обычного файла `x` разрешает попытку прямого запуска. Результат ещё зависит от формата файла, интерпретатора и параметров монтирования. Для каталога `x` означает право проходить по известному имени; `r` позволяет перечислять имена. Для доступа к файлу нужен проход по каждому родительскому каталогу.
>
> Например, у процесса есть чтение `/srv/app/config.json`, но нет `x` на `/srv/app`. Прочитать файл по этому пути он не сможет. Обратный случай тоже возможен: каталог разрешает проход, но запрещает перечисление; известный файл остаётся доступным при подходящих правах. Право `x` на скрипте не исправит неверный shebang или отсутствующий интерпретатор.

> [!followup]- Как umask влияет на права создаваемых файлов и каталогов?
>
> `umask` убирает биты из запрошенного режима при создании: фактическое значение обычно равно `mode & ~umask`. Она действует на новые объекты текущего процесса и наследуется дочерним; существующие права не меняет. Маска также не может добавить бит, которого не запросила программа.
>
> Например, приложение просит режим `666` для файла и `777` для каталога. При маске `027` получатся `640` и `750`. Для чувствительных файлов задавайте нужный режим прямо, не полагаясь только на окружение. В Linux при наследуемой ACL родительского каталога результат определяется правилами ACL и запрошенным режимом; простая формула тогда не описывает весь итог.

> [!followup]- Что должен делать родительский процесс с сигналами и дочерними процессами?
>
> Сигнал, посланный одному PID, сам по себе не рассылается дочерним процессам. Если родитель управляет рабочими процессами, при завершении он должен остановить их по своему контракту и дождаться результата. После выхода ребёнка родитель забирает его статус через семейство `wait`; до этого завершённый процесс может оставаться zombie.
>
> Например, контейнер запускает shell, который запустил сервер отдельным процессом. Остановка контейнера обращается к главному процессу, и сервер может не получить `SIGTERM`, если shell не пересылает его. Для одного сервера используйте exec-форму либо `exec` в скрипте; если потомков несколько, нужен корректный надзор и сбор завершившихся процессов. Проверьте остановку с активным запросом.

## Чем журналы, метрики и трассировки отличаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Журналы описывают отдельные события, метрики — агрегированные числовые показатели, трассировки — прохождение запроса через компоненты. Вместе они помогают объяснить симптом и локализовать причину. Нужны общие идентификаторы запросов, ограничения числа уникальных меток и защита персональных данных.
>
> Пользовательская ошибка сохранения связывается requestId с журналом API, метрикой отказов и trace запроса к БД. Лог описывает конкретный случай, метрика показывает масштаб, trace — путь и длительности; каждый источник отвечает на свой вопрос.
>

> [!followup]- Как выбирать события и трассировки для наблюдаемости?
>
> Сначала определите, что нельзя потерять, а что можно собирать выборочно. Метрики общего числа ошибок и задержек лучше строить из полного потока операций. Для дорогих трасс используйте выборку: решение на входе дешевле, а выбор по завершившейся трассе может сохранить ошибки и медленные случаи ценой буфера и обработки.
>
> Например, сохраняйте небольшой случайный процент обычных трасс и повышенную долю медленных запросов. Так детали редких отказов доступны, но долю ошибок нельзя считать напрямую по этой выборке: она намеренно смещена. Убедитесь, что связанные spans разделяют решение о выборке, иначе трасса окажется обрезанной. Критичные события аудита требуют своего контракта хранения, независимо от диагностической выборки.

> [!followup]- Что записывать в структурированный журнал сервиса?
>
> Записывайте поля, по которым можно фильтровать и связывать события: время, уровень, имя события, сервис, версию, код результата и идентификатор запроса. Добавляйте безопасные значения, полезные для конкретной гипотезы. Стабильный код причины удобнее, чем попытки разобрать произвольный текст сообщения.
>
> Например, `event=form_save_failed`, `reason=validation`, `release=...` и `request_id=...` позволяют найти рост ошибок нужной версии и открыть конкретный запрос. Полный текст формы и заголовок авторизации для этого не нужны. Определите, какие данные можно сохранять, кто видит журналы и как долго. Структурированный формат не означает, что каждое поле нужно индексировать: уникальный ID запроса полезен в логах, но дорог как метка общей метрики.

> [!followup]- Как использовать идентификатор запроса для связи логов и трассировок?
>
> Создайте или примите корректный идентификатор на доверенной границе и внесите его в клиентский ответ и серверные логи. Для распределённой трассировки передавайте стандартный контекст и создавайте отдельный span для каждого участка. Request ID помогает найти конкретный запрос; trace ID связывает работу нескольких сервисов в одно дерево.
>
> Например, пользователь видит код ошибки, поддержка находит по нему лог API и переходит к trace, где виден медленный запрос к БД. Если операция повторилась, отдельный request ID отличает попытки, а стабильный ID операции позволяет связать их. Внешние идентификаторы валидируйте и ограничивайте по размеру, не принимайте их как доказательство личности и не используйте как метку метрики.

> [!followup]- Как связать наблюдаемость фронтенда и сервера?
>
> Измеряйте путь с двух сторон. Браузер видит пользовательское действие, клиентскую ошибку и полную задержку; сервер видит обработку, запись и вызовы зависимостей. Передавайте идентификатор или trace context по согласованной границе и сохраняйте версии клиента и API, чтобы сопоставлять данные.
>
> Например, пользователь нажал «Сохранить», но сервер не получил запроса. Клиентская телеметрия может показать ошибку валидации или сбой сети. При HTTP 500 идентификатор ответа связывает сообщение в браузере с серверным журналом. Клиентская телеметрия неполна: вкладка закрывается, сеть недоступна, сбор блокируется. Серверная телеметрия не показывает, отобразился ли пользователю результат. Для проверки всей цепочки нужны оба наблюдения.

## Что такое SLI, SLO и допустимый объём ошибок?

> [!answer]- Короткий ответ — 30–90 секунд
>
> SLI — измеряемый показатель качества, например доля успешных запросов. SLO — целевое значение за выбранный период. Допустимый объём ошибок показывает, сколько неуспешных операций ещё укладывается в цель. Выбираю показатель результата пользователя, а не только время работы процесса; цель помогает согласовать надёжность и скорость изменений.
>
> Для сохранения формы считают долю запросов, завершившихся успешной записью в заданный срок. Выбор окна, допустимой задержки и исключений нужен до измерения: иначе процент успеха можно менять определением, не улучшая сервис.
>

**Уточнения**

- Как читать перцентили задержки и использовать их в SLO?
- Как определить доступность сервиса как SLI?
- Как посчитать скорость расходования бюджета ошибок?
- Когда сигнал о нарушении SLO должен будить дежурного?

> [!answer]- Если попросят подробнее — SLA и SLO
>
> **Уточнение:** SLA — внешнее обязательство с последствиями нарушения, SLO — целевой уровень, SLI — измерение. Для интерфейса уточни успешность пользовательского сценария: HTTP 200 не доказывает, что форма сохранилась и результат доступен.

> [!followup]- Как читать перцентили задержки и использовать их в SLO?
>
> p95 — граница, быстрее которой завершились примерно 95% измеренных операций; p99 показывает более дальний хвост. Среднее может оставаться хорошим, пока часть пользователей ждёт намного дольше. Для SLO удобно считать долю подходящих операций, завершившихся в заданный срок и с нужным исходом.
>
> Например, p95 сохранения в 250 мс означает, что примерно 5% запросов были медленнее. Это не гарантирует, что самые медленные уложились в секунду. Смотрите вместе с таймаутами и числом измерений; отброшенные таймауты искусственно улучшают картину. Не усредняйте p95 разных экземпляров: для общего перцентиля объедините исходные наблюдения или совместимые бакеты гистограмм.

> [!followup]- Как определить доступность сервиса как SLI?
>
> Определите, что считается хорошим исходом для пользователя, и разделите число таких исходов на число подходящих операций за заданное окно. Правила должны описывать, как учитываются таймауты, ожидаемые клиентские ошибки и частичный отказ. Работающий процесс и открытый порт не означают доступность нужного сценария.
>
> Например, успешное сохранение — подтверждённая запись за две секунды. Неверно заполненная форма может не входить в знаменатель по заранее согласованному правилу, но отказ записи на корректном вводе войдёт как плохой исход. Для низкого трафика добавьте синтетическую проверку, чтобы видеть полный простой без реальных запросов. Смена определения в середине периода делает сравнение ненадёжным.

> [!followup]- Как посчитать скорость расходования бюджета ошибок?
>
> Burn rate — отношение наблюдаемой доли плохих событий к доле, допускаемой SLO. Для цели 99,9% допустимая доля отказов 0,1%. Если сейчас плохих событий 1%, burn rate равен 10: бюджет расходуется в десять раз быстрее целевого темпа при сопоставимом трафике.
>
> Например, при окне 30 дней и устойчивом темпе это соответствует исчерпанию полного бюджета примерно за три дня. Фактический остаток зависит от уже случившихся ошибок и объёма трафика. Смотрите короткое и длинное окна: первое замечает текущий всплеск, второе отсекает одиночные отказы. При редких запросах оценка скачет; учитывайте число операций и синтетические проверки.

> [!followup]- Когда сигнал о нарушении SLO должен будить дежурного?
>
> Оповещайте по ожидаемому ущербу и времени реакции. Если сервис быстро расходует заметную часть бюджета и ухудшение всё ещё идёт, нужен срочный сигнал. Медленный устойчивый расход может породить обычную задачу с владельцем. В уведомлении укажите затронутый SLI, окно, сегмент и ссылку на действия.
>
> Например, резкий рост таймаутов сохранения одновременно виден на длинном и коротком окнах burn rate. Это отличает продолжающийся сбой от уже закончившегося всплеска. Порог по одному запросу на малом трафике даст шум; сочетайте оценку с абсолютным числом случаев или сквозной проверкой. Алерт полезен, когда он помогает выбрать действие, а не просто сообщает, что график изменился.

## После обновления пользователи не могут сохранить форму. Как будете искать причину и восстанавливать работу?

**ID вопроса:** Как расследовать инцидент в рабочем окружении?

> [!answer]- Ответ
> Сначала проверяю, у кого и на каком шаге ломается сохранение: отправляется ли запрос, какой приходит статус и ответ, есть ли ошибка в консоли. Сопоставляю время появления ошибки с обновлением frontend, API и настройками.
>
> Если проблема затрагивает пользователей, отключаю проблемную функцию или откатываю изменение, когда это позволяет восстановить сохранение. Затем воспроизвожу ошибку на конкретных данных, проверяю контракт запроса и ответа, логи по идентификатору запроса и изменения в обработке формы.
>
> После исправления проверяю сохранение и повторное чтение данных, а также поведение формы при отказе. Для найденной причины добавляю проверку, которая воспроизводит этот сбой.

> [!followup]- Что проверите, если API вернул 200, но после открытия формы данные старые?
>
> Сравниваю цепочку «черновик → тело сохранения → ответ → повторное чтение → отображение». Проверяю один и тот же id записи, пользователя и организацию. Если в запрос ушло старое имя, искать запись в БД рано: проблема уже на границе формы. Если отправлено новое, смотрю тело ответа и версию ресурса, а не только статус 200.
>
> Затем читаю запись заново и сравниваю ответ Network с показанным текстом. Ответ содержит новое значение, экран старое — проверяю применение результата, ключ клиентского кэша и локальный черновик. Уже ответ чтения старый — исследую HTTP-кэш, service worker, серверный кэш, реплику или саму запись. Это гипотезы, их различаю заголовками, источником ответа и логами по requestId.
>
> Например, диагностическая ревалидация GET помогает проверить HTTP-кэш, но не очищает store приложения. no-cache требует проверки свежести, а не запрещает хранение. [MDN: HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).
>
> Критерий исправления — новое значение доступно после повторного открытия в предусмотренный контрактом срок. Для асинхронного сохранения сначала проверяется подтверждённый статус операции; повторная отправка без понимания результата может создать дубль.

> [!followup]- Как понять, проблема на клиенте или сервере?
>
> Ищу первую границу, где фактические данные расходятся с ожидаемыми. В браузере проверяю событие отправки, значения формы, URL, метод, тело запроса, статус и содержимое ответа. Затем связываю конкретный запрос с серверным журналом по requestId, времени и версии приложения. Секреты и персональные данные в диагностическую запись не копирую.
>
> Например, поле содержит новое имя, а payload старое — ошибка формирования запроса на клиенте. Payload правильный, но API возвращает нарушение схемы — сравниваю обе стороны с согласованным контрактом: виноватым может оказаться клиент, сервер или их несовместимое обновление. Ответ содержит новое имя, но интерфейс показывает старое — исследую клиентский store, черновик и порядок ответов.
>
> Воспроизведение того же запроса в контролируемой среде помогает отделить UI от API; запрос должен сохранять значимые заголовки, права и данные. Само успешное выполнение через другой инструмент не доказывает исправность браузерного пути: CORS, service worker и состояние клиента отличаются.
>
> При CORS-ошибке сервер мог обработать запрос, но браузер не дал прочитать ответ. Поэтому отсутствие результата в UI не означает отсутствие записи; подтверждение ищу в серверной операции и повторном чтении. [MDN: fetch и CORS](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch#making_cross-origin_requests).

> [!followup]- Что делать, если после отката старый клиент несовместим с новым API?
>
> Верните совместимую пару или восстановите совместимость на одной стороне. Сначала проверьте старый клиент с новым API на конкретном контракте запроса и ответа. Если возможно, быстро верните поддержку старого формата в API, оставив новый для клиентов, которые уже обновились. Если это невозможно, откатывайте согласованный набор кода и настроек только после проверки миграций и новых записей.
>
> Например, старый клиент отправляет `name`, новый API требует `displayName`. Временный совместимый обработчик принимает оба формата и преобразует их во внутреннее поле. После восстановления проверьте создание, повторное чтение и работу обеих клиентских версий, включая оставшиеся в кэше вкладки. На будущее выпускайте расширение контракта до переключения клиента, а удаляйте старый формат после завершения перехода.

## Как не перегрузить сервер повторными запросами?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Задаю общий срок операции и ограничение числа попыток, увеличиваю задержку между ними и добавляю случайный разброс. Ограничиваю одновременные обращения; при неисправном сервисе временно прекращаю новые запросы. Повторы на нескольких уровнях могут перемножаться. При одновременном истечении кэша нужно объединять одинаковые запросы и продумать резервный ответ.
>
> Если все клиенты повторяют отказавший запрос ровно через секунду, они снова создают пик нагрузки. Задержка с разбросом и предел попыток уменьшают синхронные повторы; вложенные повторы клиента и сервиса также могут умножить число обращений.
>

> [!followup]- Как ограничение частоты защищает сервер от повторов?
>
> Задайте лимит запросов за интервал для клиента, организации или маршрута. Алгоритм вроде token bucket разрешает короткий всплеск, но ограничивает устойчивую частоту. При превышении сообщайте управляемый отказ, например HTTP 429 и при наличии понятного времени ожидания `Retry-After`. Клиент должен включить ожидание в общий дедлайн.
>
> Например, десять одновременных повторов допустимы при небольшом запасе токенов, но следующий поток будет ограничен до восстановления запаса. Лимит частоты и лимит параллелизма решают разные задачи: низкая частота может перегрузить сервер долгими запросами. Добавьте границы для обоих случаев и учитывайте попытки повторов в том же бюджете нагрузки.

> [!followup]- Как сбрасывать часть нагрузки при перегрузке и не усилить повторы?
>
> Отказывайте части новых запросов до выполнения дорогой работы, когда очередь, число активных запросов или ресурсы приближаются к пределу. Сохраняйте пропускную способность для критичных операций, если есть явные приоритеты. Возвращайте ответ, по которому клиент может прекратить попытки или отложить повтор, вместо бесконечного ожидания.
>
> Например, при исчерпании пула БД временно отклоняйте тяжёлые отчёты, оставляя сохранение доступным. HTTP 503 отражает временную недоступность; при превышении лимита конкретного клиента подходит 429. Если все клиенты сразу повторяют отказ, сброс нагрузки не спасёт. Используйте бюджет повторов, задержку с разбросом и общий дедлайн, а масштаб отказов наблюдайте отдельно по операциям.

> [!followup]- Когда очередь помогает при перегрузке повторными запросами?
>
> Очередь сглаживает короткий всплеск, если входящий поток затем уменьшается и работа успевает закончиться до дедлайна. Ограничьте размер, возраст элементов и число активных обработчиков; при переполнении явно отклоняйте или вытесняйте работу по контракту. Очередь не добавляет вычислительной мощности.
>
> Например, сервис обрабатывает 50 операций в секунду. Он может пережить краткий всплеск в 70, если после него есть запас. При постоянных 70 очередь растёт, а пользователи получают таймаут и повторяют запросы, увеличивая нагрузку. Не запускайте операцию из очереди после истечения её дедлайна; для устойчивой фоновой обработки с подтверждением приёма используйте отдельный контракт, а не держите HTTP-запрос бесконечно.

> [!followup]- Как отмена запроса уменьшает нагрузку от повторов?
>
> Передавайте единый дедлайн и сигнал отмены через цепочку вызовов. По отмене удаляйте работу, которая ещё в очереди, прекращайте планирование повторов и по возможности останавливайте начатые операции. Перед стартом очередной попытки проверяйте остаток времени, чтобы запрос не пережил интерес вызывающего.
>
> Например, пользователь ушёл со страницы отчёта: браузер отменяет ожидание, а сервер, получив сигнал разрыва и если контракт это допускает, отменяет дорогой запрос к БД. Сам разрыв HTTP не гарантирует остановку серверной работы. Если запись могла завершиться, отмена не означает откат; перед повтором нужен ключ идемпотентности или проверка состояния операции. Сигнал должен распространяться до тех компонентов, которые реально могут освободить ресурсы.

## Как работают цикл событий Node.js и libuv?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Node.js выполняет JavaScript и обслуживает асинхронные операции через цикл событий и libuv. Часть работы выполняет операционная система или пул потоков. Порядок фаз, микрозадач и process.nextTick отличается от браузерной модели. Долгое синхронное вычисление блокирует обработку других запросов.
>
> Синхронный расчёт большого JSON в обработчике Node.js задерживает другие запросы этого процесса. Асинхронный сетевой вызов даёт ждать без такого блокирования, но Promise вокруг CPU-вычисления не меняет место его выполнения.
>

> [!followup]- Когда использовать worker_threads в Node.js?
>
> `worker_threads` позволяют выполнять JavaScript параллельно в отдельных потоках с собственным состоянием выполнения. Используйте их для тяжёлых CPU-задач, которые задерживают цикл событий: расчёта, преобразования больших массивов или кодирования. Для обычного асинхронного сетевого I/O основной поток уже умеет ждать без блокировки.
>
> Например, большой синхронный расчёт отчёта замедляет ответы API. Передайте задачу ограниченному пулу workers и измерьте очередь, задержку и стоимость передачи данных. Создавать новый поток на каждый маленький запрос обычно дороже самой работы. Учитывайте копирование или передачу буферов, обработку падений и отмену. Worker не ускоряет перегруженную БД и не заменяет лимиты параллелизма.

> [!followup]- Почему асинхронный ввод-вывод не блокирует Node.js, а вычисление может?
>
> При асинхронном I/O JavaScript запускает операцию и возвращает управление; ОС или пул libuv выполняет нужную часть, а результат позже обрабатывает цикл событий. Для сокетов обычно используются механизмы готовности ОС, а некоторые файловые, DNS и криптографические операции используют пул. JavaScript-обработчик результата всё равно выполняется в своём потоке.
>
> Например, ожидание ответа БД не держит поток JS, но синхронная обработка большого ответа может задержать все соседние запросы. Пометка функции как `async` или обёртка в Promise не переносит расчёт на другой поток. Измерьте задержку цикла событий и загрузку CPU, затем уменьшите объём вычислений, разбейте работу на части либо вынесите её в worker.

> [!followup]- Как process.nextTick может вызвать голодание других задач Node.js?
>
> Node.js обрабатывает очередь `nextTick` до продолжения цикла событий. Если каждый callback снова ставит себя в эту очередь, до I/O и таймеров дело может не дойти. Замена на бесконечную цепочку микрозадач тоже не даёт циклу нормально продвинуться.
>
> Например, обработчик обходит большую очередь и планирует каждый следующий элемент через `process.nextTick`. При большой нагрузке ответы сокетов задерживаются, хотя сами операции короткие. Обрабатывайте данные ограниченными порциями и уступайте управление через `setImmediate`, либо используйте worker для тяжёлой работы. Точный порядок относительно Promise зависит от контекста выполнения, в том числе от CommonJS или ESM; для предотвращения голодания не опирайтесь на частный порядок вывода.

> [!followup]- Почему при обсуждении цикла событий нужно указывать версию Node.js?
>
> Поведение на границе таймеров и I/O зависит от версии Node и libuv, а порядок наблюдения может зависеть от контекста вызова. Документация Node отмечает изменение с libuv 1.45.0: обработка таймеров в цикле происходит после poll, вместо проходов до и после poll. Поэтому пример из старой версии не стоит выдавать за гарантию текущей.
>
> Например, сравнивая `setTimeout(fn, 0)` и `setImmediate(fn)`, укажите версии через `process.versions` и отметьте, выполняется ли код внутри callback I/O или на верхнем уровне. Для бизнес-логики задайте порядок явной цепочкой действий. Случайный порядок, полученный при нескольких запусках, не становится контрактом среды.

## Как обращаться с секретами при сборке и запуске?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Секреты передаю через предназначенное для них хранилище или защищённый канал. Они не должны попадать в клиентский код, журналы, слои образа или Git. Переменная окружения, встроенная сборщиком в браузерный код, уже доступна пользователю и не является секретом. Важны полномочия, смена ключей и ограничение доступа.
>
> Переменная сборки frontend может быть встроена в доступный браузеру JavaScript. Серверный токен нельзя считать скрытым только потому, что он пришёл из environment; секрет используют на серверной границе и не печатают в CI-журнал.
>

> [!followup]- Как организовать ротацию секретов без остановки сервиса?
>
> Создайте новый секрет, предоставьте его только нужным потребителям и проверьте работу с ним. Когда переход подтверждён, отзовите старый. Для ключей подписи обычно сначала распространяют новый открытый ключ, затем переключают подпись и сохраняют проверку старых токенов до согласованного срока истечения, если ключ не скомпрометирован.
>
> Например, при смене токена CI запустите проверенную задачу с новой версией и убедитесь, что старая больше нигде не используется, прежде чем отзывать её. Запишите время и владельца ротации, без значения секрета. При утечке обычное окно совместимости может быть неприемлемо: отзовите скомпрометированный доступ и отдельно восстановите потребителей по процедуре инцидента.

> [!followup]- Как применить принцип минимальных прав к секретам сборки и запуска?
>
> Выдавайте секрету только нужные операции, ресурсы и срок. Разделяйте сборку, тестовые и рабочие окружения. Привязывайте доступ к отдельной сервисной идентичности и по возможности используйте короткоживущие учётные данные. Секрет должен быть доступен только шагу или процессу, который его использует.
>
> Например, сборке нужен доступ на чтение приватного npm-пакета, но не право публикации в registry и не доступ к рабочей базе. Приложению может быть нужно чтение одной категории данных, но не права администратора БД. Проверяйте не только список выданных прав, но и границы в действии: нужный запрос проходит, соседний ресурс недоступен. Минимальные права уменьшают последствия утечки, но не заменяют ротацию и контроль журналов.

> [!followup]- Как ограничить доступ к секретам в CI?
>
> Разделите проверки недоверенных изменений и шаги с привилегиями. Проверка внешнего PR не должна получать рабочие секреты или токен записи. Деплой запускайте для проверенной версии в защищённом окружении, с разрешениями только на нужный ресурс. По возможности выдавайте короткоживущий доступ на основании идентичности workflow.
>
> Например, линтер и тесты PR выполняются с токеном только для чтения, а job выпуска получает право отправить проверенный образ в конкретный registry. Не исполняйте код из недоверенного PR в привилегированном контексте. Маскирование вывода помогает от случайной печати, но не гарантирует защиты от кода, которому уже дали секрет. Проверяйте также артефакты, кэш и доступ к журналам.

> [!followup]- Могут ли source maps раскрыть секреты или исходный код сборки?
>
> Source map связывает сжатый код с исходным и может включать исходники в `sourcesContent`. Если карта публична, эти данные доступны тому, кто её загрузит. При этом секрет, встроенный в клиентский JavaScript, уже раскрыт независимо от наличия карты. Рабочие токены должны оставаться на сервере.
>
> Например, для разбора ошибок загружайте карты в закрытое хранилище системы мониторинга с привязкой к версии, а публичную выдачу настраивайте отдельно. Проверьте содержимое сборки и права на карты до релиза. Отсутствие ссылки `sourceMappingURL` не ограничивает доступ к файлу, если сервер всё ещё отдаёт его по URL. Карты упрощают диагностику, поэтому их лучше контролировать, чем просто отключать.

## Как проверить контейнер Docker на практике?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверяю выбранный образ, команду, переменные, порты, сеть, тома и ограничения ресурсов. Затем смотрю состояние, журналы, завершение процесса и доступ к нужному сервису. Успешная сборка образа не подтверждает, что контейнер запускается с правильными настройками и отвечает на запросы.
>
> Статус running не подтверждает ответ API: проверяют запрос снаружи, сеть до БД и сохранность данных после пересоздания в контролируемой среде. Неправильный volume может оставить сервис работающим до первого перезапуска.
>

> [!followup]- Для чего в docker run нужны -p и -it?
>
> `-p` публикует порт контейнера на хосте. Для локальной проверки задайте адрес явно, например `-p 127.0.0.1:8080:80`: запрос к 8080 попадёт на порт 80 контейнера. `-i` оставляет stdin открытым, а `-t` выделяет псевдотерминал. Вместе они удобны для интерактивной диагностики.
>
> Например, HTTP-сервис запускают с опубликованным портом, затем проверяют реальным запросом. Для просмотра файлов в уже работающем контейнере можно использовать `docker exec -it`, если внутри есть нужная команда. `-it` не нужен для обычной фоновой работы или скрипта CI и может менять поведение ввода и вывода. Публикация порта не подтверждает, что процесс слушает его.

> [!followup]- Как проверить контекст docker build и правила .dockerignore?
>
> Контекст задаёт файлы, доступные сборке; путь к Dockerfile сам по себе не меняет его. `.dockerignore` в корне контекста исключает ненужные пути до передачи сборщику. Уберите локальные зависимости, отчёты, временные файлы и секреты, но сохраните то, что требуется инструкциям `COPY`.
>
> Например, при `docker build -f docker/app.Dockerfile .` контекстом остаётся корень проекта. Исключённый lockfile не получится скопировать, а лишний `.env` может попасть в контекст при широком `COPY . .`. Проверяйте сборку из чистого checkout и изучайте итоговый образ, если нужно подтвердить состав. `.dockerignore` не предотвращает утечки секрета, который сама команда скачала или вывела в журнал.

> [!followup]- Когда использовать docker cp для проверки контейнера?
>
> `docker cp` копирует файлы между файловой системой контейнера и хостом, в том числе из остановленного контейнера. Это удобно, чтобы забрать отчёт или диагностический файл, не меняя образ. Указывайте точный путь и проверьте правила для каталога назначения, владельца и символических ссылок.
>
> Например, `docker cp app:/var/log/app/report.json ./report.json` забирает файл для локального разбора, если он действительно лежит там. Обычные журналы stdout лучше смотреть через `docker logs`. Копирование внутрь контейнера может временно помочь диагностике, но такая правка пропадёт при пересоздании; постоянное изменение должно прийти из сборки или конфигурации. Не переносите файлы с секретами в общий каталог артефактов.

> [!followup]- Как проверить связь сервисов по именам в Docker Compose?
>
> Compose обычно создаёт общую сеть проекта. В ней используйте имя сервиса и внутренний порт, например `db:5432`. Проверьте, что оба сервиса подключены к одной сети, затем из контейнера API проверьте разрешение имени, TCP-соединение и прикладной запрос к базе.
>
> Например, запись `ports: ["15432:5432"]` даёт хосту порт 15432, но API внутри сети продолжает обращаться к `db:5432`. `localhost` из API ведёт в тот же контейнер. После замены экземпляра БД IP меняется, поэтому приложение должно уметь восстановить соединение по имени. Проверка DNS показывает адрес, а не готовность БД принять сессию.

> [!followup]- Почему depends_on не гарантирует готовность сервиса в Compose?
>
> Обычный `depends_on` задаёт порядок запуска, но запущенный процесс ещё может выполнять инициализацию. Если нужно дождаться готовности при старте, задайте для зависимости подходящий `healthcheck`, а в `depends_on` — условие `service_healthy`. Проверка должна соответствовать тому, что действительно нужно потребителю.
>
> Например, БД уже запущена, но ещё не принимает соединения. Проверка доступности SQL помогает не запускать API преждевременно. Если API зависит от конкретной схемы, открытый порт или успешное соединение ещё не подтверждают завершение миграции. Условие старта также не решает отказ БД после запуска. Приложению нужны ограниченные повторы подключения и понятный режим деградации.

> [!followup]- Когда из контейнера доступен host.docker.internal?
>
> Docker Desktop предоставляет `host.docker.internal` для обращения к хосту. В других установках наличие имени зависит от среды. В Docker Engine можно явно задать соответствие с `--add-host host.docker.internal:host-gateway`, если эта конфигурация подходит и сервис хоста доступен с адреса шлюза.
>
> Например, контейнеру разработки нужно обратиться к локальному отладочному API. Проверьте разрешение имени и подключение из контейнера; сервис, слушающий только loopback на Linux-хосте, может оставаться недоступным по адресу шлюза. Если цель — соседний контейнер, используйте имя сервиса в общей сети. Для переносимого окружения задайте адрес через конфигурацию вместо предположения, что специальное имя есть везде.

## Как управлять зависимостями npm и сборкой?

> [!answer]- Короткий ответ — 30–90 секунд
>
> package.json задаёт зависимости и команды, lockfile фиксирует выбранные версии и помогает воспроизводимости. Для CI обычно использую npm ci с согласованным lockfile. Различаю зависимости времени работы и разработки; проверяю диапазоны версий, совместимость, состояние сборки и её результат. Наличие lockfile само по себе не гарантирует безопасность пакетов.
>
> `npm ci` использует согласованный lockfile для воспроизводимой установки. Но версия Node.js и настройки сборки тоже влияют на результат; совпавшие зависимости не гарантируют одинаковый артефакт в разных средах.

> [!followup]- Что делает npm dedupe и когда он не уберёт дубликаты?
>
> `npm dedupe` (алиас `npm ddp`) перестраивает установленное дерево так, чтобы совместимые зависимости могли использовать общий экземпляр выше по дереву. Он не скачивает новые модули для произвольного обновления версий. Команда может изменить расположение пакетов и lockfile, поэтому просмотрите diff и проверьте сборку.
>
> Например, двум библиотекам нужны диапазоны `^1.2.0` и `^1.3.0`; уже установленная версия 1.4 может удовлетворять обеим. Тогда вложенный дубль не нужен. Для диапазонов `^1` и `^2` один экземпляр не удовлетворяет обоим; ограничения peer dependencies тоже могут потребовать отдельного расположения. Смотрите `npm ls` и размер итоговой сборки: меньше копий на диске не всегда означает меньший браузерный пакет.

> [!followup]- Какую роль в сборке выполняют Vite, webpack и Babel?
>
> Vite организует разработку и сборку приложения, включая dev server и обработку модулей. Webpack строит граф зависимостей и собирает ресурсы по настройкам loader и plugin. Babel преобразует JavaScript по заданным целям; его можно подключить как этап, но он сам по себе не решает задачи dev server и сборки всех ресурсов.
>
> Например, Vue-приложение использует Vite для разработки и выпуска, а отдельный этап Babel нужен только для согласованной трансформации, которую текущий конвейер не делает. Сравнивайте задачи, а не просто список инструментов. Точный механизм сборки Vite меняется между версиями; при вопросе о backend сборщика сверяйтесь с документацией используемой версии. Проверьте итог на целевых браузерах.

> [!followup]- Чем polyfill отличается от преобразования синтаксиса?
>
> Преобразователь меняет синтаксис на понятный целевой среде. Polyfill добавляет отсутствующий API во время выполнения, если его можно воспроизвести. Поддержка синтаксиса и поддержка методов стандартной библиотеки независимы, поэтому задавайте список браузеров и проверяйте обе стороны.
>
> Например, преобразование optional chaining уберёт оператор `?.`, но не добавит `Array.prototype.flat` в старый браузер. Если этот метод действительно нужен, подключите подходящий polyfill или используйте другую реализацию. Глобальные polyfill увеличивают пакет и могут влиять на сторонний код. Некоторые возможности платформы нельзя полностью повторить JavaScript-кодом; проверка на нужном браузере важнее самого наличия настройки сборщика.

> [!followup]- Что должно попадать в devDependencies, а что в dependencies?
>
> В `devDependencies` кладут инструменты разработки, проверки и сборки, которые не нужны при запуске готового продукта. В `dependencies` — пакеты, необходимые приложению в рабочей среде или пользователям опубликованной библиотеки. Смотрите на итог поставки: пакет может понадобиться на стадии сборки, хотя не нужен серверу после неё.
>
> Например, тестовый runner и линтер обычно относятся к `devDependencies`. Если Node-сервер при запуске импортирует драйвер БД, он нужен в runtime и должен остаться при `npm ci --omit=dev`. Для статического фронтенда в рабочее окружение можно доставлять только результат сборки, но стадия сборки всё равно должна иметь нужные инструменты. Проверьте запуск собранного артефакта с реальным набором зависимостей.

> [!followup]- Почему npm lifecycle scripts важны для безопасности цепочки поставки?
>
> Установка зависимости может запускать её код через lifecycle scripts с правами процесса CI или разработчика. Lockfile фиксирует выбранный пакет, но не делает его скрипты безопасными. Просматривайте изменения зависимостей и источников, ограничивайте права и сеть установки, держите секреты выпуска вне шагов сборки.
>
> Например, новый пакет добавил `postinstall`, хотя ожидается только библиотека JavaScript. Проверьте, зачем он нужен. Где проект позволяет, используйте `npm ci --ignore-scripts` и явно запускайте необходимые проверенные шаги. Некоторые нативные зависимости действительно требуют установки или подготовки; после отключения скриптов проверьте сборку и запуск. Анализ уязвимостей полезен, но не заменяет проверку неожиданного кода установки.
