## Что происходит при установке HTTPS-соединения?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Для нового подключения браузер получает адрес сервера, выбирает транспорт и устанавливает защищённое соединение. Для HTTP/1.1 и HTTP/2 обычно используется TCP с TLS; HTTP/3 использует QUIC поверх UDP с интегрированным TLS. DNS-кэш, открытое соединение и возобновление сессии могут сократить путь.
>
> При TLS-рукопожатии стороны согласуют параметры защиты и ключевой материал, сервер подтверждает владение ключом сертификата. Браузер проверяет доверенную цепочку, соответствие имени сервера и срок действия сертификата. После успешного согласования HTTP-сообщения защищены от чтения и незаметной подмены на сетевом пути.
>
> HTTPS не исправляет ошибки приложения, не заменяет авторизацию и не скрывает все сведения о соединении, например IP. При сбое сертификата проверяют hostname, цепочку, срок и часы устройства; отключать проверку ради успешного запроса нельзя считать исправлением.

**Уточнения**

- Почему действующий сертификат другого hostname не подходит?
- Какие шаги могут не повторяться при переиспользовании соединения?
- Защищает ли HTTPS от XSS и неверной проверки прав?

**Продолжение о сертификате:** объясни цепочку доверия, соответствие hostname и срок действия. Что произойдёт при ошибке проверки? Какие данные сравнить при сбое после выпуска? Глубокие алгоритмы TLS для этой роли не требуются.

**Критерии ответа:** Объясняю назначение TLS, проверку сервера, транспорт HTTP/3 и границы защиты HTTPS.

## Чем TCP отличается от UDP?

> [!answer]- Короткий ответ — 30–90 секунд
>
> TCP предоставляет упорядоченный поток байтов с повторной передачей, управлением потоком и перегрузкой. UDP передаёт отдельные датаграммы без этих гарантий. Протокол более высокого уровня может добавить надёжность: например, QUIC работает поверх UDP.
>
> Загрузка документа требует полного и упорядоченного результата. Для живого аудио поздний пакет иногда менее полезен, чем пропущенный, поэтому транспорт выбирают вместе с правилами восстановления и задержки. UDP сам не предоставляет поток данных как TCP.
>

**Уточнения**

- потеря пакетов
- задержка следующих данных из-за ожидания первых (head-of-line blocking)
- установление соединения
- поток байтов и сообщения

## Чем HTTP/1.1, HTTP/2 и HTTP/3 различаются?

> [!answer]- Короткий ответ — 30–90 секунд
>
> HTTP/1.1 обычно работает поверх TCP и повторно использует соединения. HTTP/2 передаёт несколько потоков в одном TCP-соединении, но потеря пакета может задержать их все. HTTP/3 использует QUIC: потеря данных одного потока не обязана задерживать остальные. Версия протокола не отменяет задержки сети и ограничения сервера.
>
> При загрузке множества ресурсов HTTP/2 уменьшает потребность в отдельных соединениях, но потеря TCP-пакета задерживает доступ к последующим байтам всех потоков. В HTTP/3 потоки QUIC восстанавливаются независимо; управление перегрузкой всё равно влияет на всё соединение.
>

**Уточнения**

- сжатие заголовков
- ограничение числа соединений
- приоритеты
- резервный вариант

## Что делает DNS?

> [!answer]- Короткий ответ — 30–90 секунд
>
> DNS сопоставляет имена с записями: адресами, псевдонимами и другими сведениями. Рекурсивный сервер использует кэш и при необходимости запрашивает серверы иерархии. TTL задаёт время кэширования записи. DNS сам по себе не шифрует содержимое сайта и не определяет права пользователя.
>
> При смене адреса API часть клиентов может продолжать обращаться по старой записи до истечения кэша. Поэтому учитывают TTL и период совместной доступности адресов; обновление DNS-записи не доказывает мгновенное переключение всех пользователей.
>

**Уточнения**

- A/AAAA/CNAME
- кэширование отсутствующего результата
- распространение изменений DNS
- разные DNS-ответы для разных сетей

## Как связаны HTTP-методы и идемпотентность?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Метод описывает намерение запроса. GET и HEAD предназначены для чтения; PUT — для задания состояния ресурса, DELETE — удаления, POST — обработки команды или создания, PATCH — частичного изменения. Реализация должна соблюдать эту семантику.
>
> Safe означает, что клиент не запрашивает изменение состояния; серверное журналирование не нарушает это свойство. Идемпотентность означает одинаковый предусмотренный эффект одного и нескольких одинаковых запросов. PUT и DELETE идемпотентны по семантике: второй DELETE может вернуть 404, но удалённый ресурс не появляется заново. Одинаковый статус или отсутствие любых побочных записей не требуются.
>
> POST и PATCH не гарантируют идемпотентность. PATCH с установкой значения может быть идемпотентным, а увеличение счётчика — нет. После потери ответа на запись нельзя считать операцию неуспешной и слепо повторять её: нужен согласованный ключ операции, проверка статуса или иной контракт, исключающий повторный эффект.

**Уточнения**

- Почему повтор DELETE может вернуть 404 и всё равно быть идемпотентным?
- Чем PATCH «установить count=2» отличается от «увеличить count на 1»?
- Что делать после потери ответа POST, если неизвестно, была ли запись создана?

**Критерии ответа:** Различаю safe и idempotent; объясняю повтор DELETE с другим статусом, неидемпотентный PATCH и риск повтора POST.

## Какие HTTP-статусы важно различать?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Статус помогает выбрать поведение интерфейса. 200 — успешный ответ, 201 — создан ресурс, 204 — успех без тела. 304 используется для проверки актуальности кэша и не является новым JSON-телом. fetch обычно возвращает Response даже для HTTP-ошибки: статус проверяют до обработки тела.
>
> 401 означает отсутствие подходящих действительных данных аутентификации; 403 — отказ в доступе. 404 — ресурс не найден или его существование намеренно не раскрывается. 409 обозначает конфликт состояния, 412 — невыполненное предусловие, например If-Match. 422 может передавать ошибки полей по контракту API: ввод сохраняют и связывают ошибки с полями.
>
> 429 сообщает об ограничении частоты; 503 — о временной недоступности. Retry-After, если он есть, помогает выбрать задержку. Повтор всё равно зависит от безопасности операции, числа попыток и актуальности запроса. Нельзя превращать отказ в пустой успешный список или автоматически повторять POST без согласованной защиты от дублей.

**Уточнения**

- Почему catch вокруг fetch не обрабатывает 404 автоматически?
- Чем конфликт версии отличается от ошибки заполнения поля?
- Почему после 503 нельзя безусловно повторять любую запись?

**Критерии ответа:** Выбираю разное поведение UI для 401, 403, 409/412, 422 и 429/503; не вызываю json для 204.

**Изучить:** [[Фронтенд/API браузера/05. Fetch, CORS и сетевые запросы/01. fetch и обработка ошибок|Объяснение и примеры]]

## Как работает HTTP-кэш?

> [!answer]- Короткий ответ — 30–90 секунд
>
> HTTP-кэш повторно использует сохранённый ответ по правилам сервера. Пока ответ свежий по Cache-Control/max-age, его можно использовать без новой передачи тела. Когда нужна проверка актуальности, клиент отправляет условный запрос, например If-None-Match с ETag. Сервер отвечает новым содержимым или 304, и тогда используется сохранённое тело.
>
> `no-cache` разрешает хранение, но требует проверки перед повторным использованием; `no-store` запрещает сохранять этот ответ. `private` ограничивает использование приватным кэшем клиента, а `Vary` указывает, какие заголовки запроса участвуют в выборе варианта ответа.
>
> Для файлов с хешем содержимого подходит длинный срок свежести; изменяемый HTML требует иной политики. Для персональных API нельзя случайно разрешить общедоступный кэш. Проверяю заголовки и реальные запросы в Network, не смешивая HTTP-кэш, Cache API Service Worker и кэш приложения.

> [!example]- Если попросят подробнее
>
> `max-age` задаёт срок свежести. После него клиент может отправить валидатор; 304 означает, что сохранённое тело можно использовать, а не что сервер прислал новое пустое содержимое.
>
> `no-cache` требует проверки перед использованием сохранённого ответа. `no-store` запрещает хранить этот ответ, но не является командой очистить все ранее сохранённые копии. Для персональных ответов отдельно задают правила shared-кэша; наличие cookie само по себе не делает его безопасным.
>
> [MDN: механизмы HTTP-кэша](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).

**Уточнения**

- Почему no-cache не означает «ничего не сохранять»?
- Что произойдёт при совпавшем ETag?
- Почему одинаковый URL с разными представлениями может требовать Vary?

**Критерии ответа:** Различаю freshness и revalidation, no-cache/no-store, понимаю 304 и риск shared cache для персональных данных.

## Чем CDN отличается от кэша браузера?

> [!answer]- Короткий ответ — 30–90 секунд
>
> CDN доставляет и кэширует данные ближе к пользователям; кэш браузера хранится у отдельного клиента. Нужно определить ключ, время хранения, обновление и правила для личных данных. Адреса статических файлов с версией или хэшем упрощают безопасное обновление.
>
> Файл `app.<hash>.js` можно долго кэшировать, потому что новая сборка получает другой адрес. HTML со ссылкой на новую сборку требует иной политики. Общий CDN-кэш персонального кабинета без правильного ключа способен раскрыть чужие данные.
>

**Уточнения**

- Обращение к исходному серверу при отказе CDN
- очистка кэша
- куки
- устаревшее содержимое
- адрес с подписью

## Когда выбирать опрос, длительный запрос, SSE и WebSocket?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Периодический опрос прост, но создаёт лишние запросы. Длительный запрос ожидает событие на сервере перед ответом. SSE передаёт поток событий от сервера по HTTP; WebSocket поддерживает двусторонний обмен сообщениями. Выбор зависит от нужной задержки, направлений обмена, инфраструктуры и восстановления после разрыва.
>
> Для статуса длительного экспорта достаточно опроса или событий сервера. Для чата с обменом в обе стороны подходит WebSocket. При любом выборе нужен сценарий переподключения и восстановления пропущенных событий, иначе транспорт не обеспечивает полноту данных.
>

**Уточнения**

- повторное подключение
- курсор и повторная доставка событий
- проверка личности
- замедление поставщика при перегрузке потребителя
- несколько вкладок

## Что такое REST и чем он отличается от RPC и GraphQL?

> [!answer]- Короткий ответ — 30–90 секунд
>
> REST — архитектурный стиль с ресурсами и единообразным интерфейсом. RPC описывает вызов операций, GraphQL — типизированный запрос нужных полей. Само название не гарантирует удобный API: нужны ясные контракты, ошибки, кэширование и ограничения стоимости запросов.
>
> Заказ можно представить ресурсом с чтением состояния, а команду расчёта сложного тарифа — отдельной операцией. GraphQL удобен для выборки нужных полей, но всё равно требует ограничения стоимости запроса и проверки доступа к данным.
>

**Уточнения**

- N+1
- версионирование
- разбиение на страницы
- изменение данных
- заранее зарегистрированные запросы

## Как проектировать разбиение на страницы?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Смещение просто, но при изменении данных строки могут пропускаться или повторяться, а глубокие страницы дорого читать. Курсор опирается на устойчивый порядок и ключ последней записи. Уточняю порядок при равных значениях, фильтры, согласованность снимка и переходы между страницами.
>
> Для ленты с одинаковыми датами сортируют по паре `(createdAt, id)` и включают её в курсор. Иначе записи на границе страниц могут пропускаться. Курсор не гарантирует неизменный снимок всей выдачи при редактировании данных.
>

**Уточнения**

- постепенная загрузка при прокрутке
- повторяющиеся строки
- общее число записей
- отмена

## Как устроены cookie и атрибуты безопасности?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Сервер устанавливает cookie заголовком Set-Cookie, а браузер хранит её и прикладывает к подходящим запросам заголовком Cookie. Domain задаёт область хостов: без него cookie привязана к установившему её хосту. Path ограничивает пути отправки, но не служит надёжной границей безопасности. Max-Age/Expires задают срок хранения.
>
> Secure ограничивает передачу защищённым соединением; HttpOnly закрывает доступ через document.cookie, сохраняя автоматическую отправку. SameSite управляет отправкой в межсайтовом контексте: Strict наиболее ограничителен, Lax допускает некоторые переходы верхнего уровня, None допускает cross-site отправку и требует Secure. При этом могут действовать дополнительные ограничения браузера. Site и origin — разные понятия: порты и поддомены различают origin иначе, чем site.
>
> Ни один атрибут сам по себе не создаёт безопасную сессию. Сервер проверяет срок и права, защищает изменяющие операции от CSRF и меняет идентификатор сессии в нужные моменты. HttpOnly затрудняет кражу cookie, но XSS может выполнить запрос из уже авторизованной страницы.

**Уточнения**

- Чем host-only cookie отличается от cookie с Domain?
- Почему HttpOnly не предотвращает действие вредоносного кода от имени пользователя?
- Что означают SameSite=Lax, Strict и None, и почему site не равен origin?

**Критерии ответа:** Разделяю Domain/Path, Secure, HttpOnly и SameSite; объясняю, почему cookie может отправиться, хотя JS не может её прочитать.

## Чем проверка личности отличается от проверки прав?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Проверка личности устанавливает, кто действует; проверка прав определяет, разрешено ли ему конкретное действие. Клиентская проверка помогает показывать интерфейс, но сервер обязан проверять каждую чувствительную операцию. Скрытая кнопка не защищает API.
>
> Пользователь с действующей сессией может знать идентификатор чужого заказа. Проверка входа недостаточна: сервер при чтении и изменении проверяет принадлежность заказа или нужное право. Скрытая кнопка на клиенте не защищает этот endpoint.
>

**Уточнения**

- Почему валидная сессия не даёт права читать любой заказ по id?
- Где проверяется принадлежность объекта организации?
- Что должна сделать открытая форма после отзыва права?

**Критерии ответа:** Проверяю право на конкретный объект и действие на сервере; различаю UX клиента и границу доступа.

## Как работают OAuth 2.0 и OpenID Connect?

> [!answer]- Короткий ответ — 30–90 секунд
>
> OAuth 2.0 позволяет делегировать доступ через токены. OpenID Connect добавляет сведения для установления личности пользователя. Для браузерного клиента важно обсудить выдачу кода с PKCE, проверку адреса возврата и устройство сессии. Конкретную схему выбирают по официальным возможностям провайдера и актуальным требованиям безопасности.
>
> При входе через внешний провайдер OpenID Connect позволяет установить личность, а OAuth — получить разрешённый доступ к API. Токен для одного сервиса нельзя автоматически принять в другом: проверяют назначение, издателя и соответствующий протокол.
>

**Уточнения**

- токен доступа, токен обновления и ID-токен
- state/nonce
- BFF
- выход из учётной записи

## Что такое JWT и чего он не гарантирует?

> [!answer]- Короткий ответ — 30–90 секунд
>
> JWT — формат набора утверждений. Подпись защищает целостность при правильной проверке ключа, алгоритма и издателя. Обычный подписанный JWT не шифрует данные и сам по себе не обеспечивает немедленный отзыв. Проверяют срок действия, получателя и издателя; доверие к подписи без этих проверок недостаточно.
>
> Чтение содержимого токена не проверяет его подпись. Изменённое поле роли должно отклоняться при проверке токена, а не приниматься на веру. Данные обычного подписанного токена видны получателю: подпись защищает от изменения, но не шифрует содержимое, поэтому секреты туда не помещают.
>

**Уточнения**

- ротация
- отзыв токена
- хранилище
- непрозрачный токен (opaque token)
- подмена ожидаемого алгоритма проверки подписи

## Как возникает XSS?

> [!answer]- Короткий ответ — 30–90 секунд
>
> XSS возникает, когда недоверенные данные попадают в контекст, где браузер интерпретирует их как исполняемый код. Например, строка комментария, вставленная в innerHTML без подходящей очистки, может изменить DOM и запустить нежелательное поведение. Источник бывает серверным, сохранённым ранее или полностью клиентским.
>
> Защита начинается с безопасного вывода: обычные строки показывать как текст, избегать опасных HTML-sinks, а необходимый rich text очищать проверенным sanitizer с подходящими правилами. Экранирование должно соответствовать контексту; HTML-экранирование не делает произвольный URL или JavaScript безопасным.
>
> CSP — дополнительный слой ограничения исполнения. HttpOnly не даёт JS прочитать cookie, но не делает XSS безвредным: внедрённый код может выполнять действия в уже открытой сессии. Поэтому нужно устранить сам путь исполнения недоверенных данных.

**Уточнения**

- Почему интерполяция текста и v-html имеют разные риски?
- Достаточно ли HttpOnly для защиты действий авторизованного пользователя?
- Когда нужен sanitizer, а когда достаточно textContent?

**Критерии ответа:** Нахожу источник недоверенных данных и опасный sink, выбираю безопасный вывод и объясняю пределы CSP/HttpOnly.

**Изучить:** [[Фронтенд/Инженерные основы/03. Безопасность frontend-приложений/02. XSS, CSRF, CSP и secure cookies|Полное объяснение]]

**Практика:** [[Собеседования/Практика/Vue#Поиск и подсветка текста из API|Проверить на задаче]]

## Как возникает CSRF?

> [!answer]- Короткий ответ — 30–90 секунд
>
> При CSRF чужая страница побуждает браузер выполнить нежелательное действие на сайте, где пользователь уже вошёл. Если браузер автоматически приложит подходящую cookie, сервер может принять запрос за намерение пользователя. Для атаки не обязательно читать ответ.
>
> Сервер защищает изменяющие состояние операции: проверяет CSRF-token или иной согласованный признак намерения, проверяет Origin в подходящих сценариях и настраивает SameSite cookies. Конкретная защита зависит от способа аутентификации и допустимых cross-site потоков. Изменение состояния через GET особенно опасно.
>
> CORS не является универсальной защитой от CSRF: часть запросов можно отправить без разрешения читать ответ. XSS и CSRF также нельзя смешивать: при XSS вредоносный код исполняется в контексте сайта, при CSRF используется автоматически прикладываемая авторизация из чужого контекста.

**Уточнения**

- Почему злоумышленнику не обязательно читать ответ на перевод?
- Что меняется, если токен отправляется приложением в Authorization, а не автоматически cookie?
- Почему SameSite нужно согласовывать с реальными cross-site переходами?

**Критерии ответа:** Объясняю роль автоматически отправляемых credentials и серверной проверки; не считаю запрет чтения CORS достаточной защитой.

**Изучить:** [[Фронтенд/Инженерные основы/03. Безопасность frontend-приложений/02. XSS, CSRF, CSP и secure cookies|Полное объяснение]]

**Практика:** [[Собеседования/Практика/Безопасность#CSRF при переводе денег через JSON API|Проверить на задаче]]

## Что делает CSP?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Политика CSP ограничивает источники и способы загрузки и выполнения ресурсов. Она снижает последствия внедрения кода, но не заменяет безопасную обработку данных. Для встроенных скриптов предпочтительны nonce или хэш вместо широкого разрешения unsafe-inline. Проверяю отчёты нарушений и совместимость с нужными сторонними скриптами.
>
> Разрешение только согласованных источников скриптов и nonce для встроенного кода уменьшает возможности исполнения внедрённого HTML. Политику проверяют на реальном приложении и нарушениях; широкие разрешения ради удаления ошибок могут лишить её нужного эффекта.
>

**Уточнения**

- режим отчётов без блокировки
- strict-dynamic
- frame-ancestors
- развёртывание

## Как защититься от подмены нажатий через iframe?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Ограничиваю встраивание страницы с помощью CSP frame-ancestors или совместимых защитных механизмов. Для разрешённых iframe задаю допустимые источники и минимальные полномочия sandbox. Проверка права на действие на сервере нужна независимо от защиты встраивания.
>
> Страницу подтверждения операции можно запретить встраивать в чужой iframe через frame-ancestors. Защита предотвращает скрытое наложение интерфейса, но не заменяет серверную проверку самой операции и прав пользователя.
>

**Уточнения**

- X-Frame-Options
- sandbox
- postMessage

## Как безопасно хранить токены на клиенте?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Сначала определяю угрозы и устройство сессии. Веб-хранилище доступно при XSS; HttpOnly cookie недоступны JavaScript, но требуют защиты от CSRF. Безопасность не определяется одним местом хранения: нужны ограниченный срок жизни, обновление, отзыв и серверная проверка.
>
> При схеме с HttpOnly cookie клиент не читает токен, а сервер управляет сессией и её отзывом. При доступном JavaScript токене XSS может его извлечь. Решение принимают вместе с контрактом API, CSRF-защитой и моделью угроз.
>

**Уточнения**

- BFF
- несколько вкладок
- выход из учётной записи
- утечка токена в журналы

## Как безопасно принимать файлы?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Размер, содержимое, формат и права проверяю на сервере. Имя файла и Content-Type от клиента не считаю доказательством безопасности. Хранение и выдача не должны позволять исполнять файл как код доверенного сайта. Для больших файлов обсуждаю загрузку частями и продолжение после обрыва; интерфейс показывает состояние и отмену.
>
> Для аватара сервер проверяет фактическое изображение и размер, а не только расширение `.jpg`. Пользовательское имя не используют как доверенный путь хранения. Выдача загруженного HTML с origin приложения может превратить загрузку в XSS.
>

**Уточнения**

- контрольная сумма
- проверка файла на вредоносное содержимое
- адрес с подписью
- выход за разрешённый каталог

## Как проектировать API без N+1 запросов?

## Как проверять безопасность клиентских зависимостей?

## Как задавать повторы и время ожидания запросов?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Определяю общий срок операции, ограничения попыток и понятные исходы. Истечение времени ожидания записи не означает, что сервер её не выполнил: может потребоваться проверка состояния. Повтор должен быть безопасен для данных и ограничен по общей нагрузке.
>
> После таймаута сохранения показывают неопределённый результат и проверяют статус операции, если сервер предоставляет такой контракт. Слепой повтор может создать дубль. Для чтения используют ограниченные попытки, общий срок и отмену при уходе со страницы.
>

**Уточнения**

- увеличение задержки/случайный разброс задержки
- прекращение запросов к неисправному сервису
- отмена
- Retry-After

## Как избежать утечки личных данных в диагностике?

## Что такое same-origin policy и CORS?

> [!answer]- Короткий ответ — 30–90 секунд
>
> Источник (origin) — сочетание схемы, хоста и порта. Правило одного источника ограничивает доступ скрипта к данным другого источника. Через заголовки Access-Control-Allow-* сервер может разрешить браузеру предоставить ответ определённому источнику. Это не проверка личности пользователя и не серверная система прав.
>
> Для ряда запросов к другому источнику браузер сначала отправляет предварительный запрос OPTIONS — preflight: сообщает будущий метод и заголовки, проверяет разрешение и только затем отправляет основной запрос. Некоторые запросы отправляются без preflight; при отсутствии нужного разрешения скрипт всё равно не сможет прочитать ответ.
>
> Исправляют CORS на сервере или согласованном proxy. `mode: "no-cors"` не даёт читать обычный JSON: ответ становится opaque. Для credentials нужен конкретный разрешённый origin и согласованная настройка credentials; wildcard не заменяет её. CORS нельзя считать защитой от всех cross-site действий или CSRF.

**Уточнения**

- Почему запрос работает в Postman, но не из браузера?
- Почему application/json может потребовать предварительный запрос OPTIONS?
- Почему no-cors не исправляет получение JSON?

Практика: [[Собеседования/Практика/Безопасность#CSRF при переводе денег через JSON API|разделить CORS и CSRF]]. Детали заголовков: [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

**Критерии ответа:** Отличаю запрет чтения ответа от запрета отправки запроса, объясняю предварительный запрос OPTIONS и границу ответственности сервера.
