# requestAnimationFrame, requestIdleCallback и оптимизация DOM

> [!summary]
> `requestAnimationFrame()` синхронизирует визуальные изменения с ближайшим кадром. `requestIdleCallback()` позволяет выполнить некритичную работу, когда у браузера есть свободное время, но не подходит для обязательной логики интерфейса.

## requestAnimationFrame

`requestAnimationFrame(callback)` просит браузер вызвать переданный обработчик перед ближайшим обновлением изображения.

```js
let startedAt;
let frameId;
function move(timestamp) {
  startedAt ??= timestamp;
  const elapsed = timestamp - startedAt;
  box.style.transform = `translateX(${Math.min(elapsed / 10, 200)}px)`;
  if (elapsed < 2000) frameId = requestAnimationFrame(move);
}
frameId = requestAnimationFrame(move);
// При закрытии экрана: cancelAnimationFrame(frameId).
```

Использовать для:

- анимаций;
- чтения/записи DOM, связанных с кадром;
- throttling визуальных обновлений, например scroll-позиции.

Не использовать как универсальную замену `setTimeout` для бизнес-логики.

## requestIdleCallback

`requestIdleCallback(callback)` планирует некритичную работу на свободное время браузера.

```js
let idleId;
function work(deadline) {
  while (deadline.timeRemaining() > 0 && queue.length > 0) {
    process(queue.shift()); // одна короткая операция
  }
  if (queue.length > 0) idleId = requestIdleCallback(work);
}
idleId = requestIdleCallback(work);
// При закрытии экрана: cancelIdleCallback(idleId).
```

Использовать для:

- низкоприоритетной аналитики;
- прогрева кешей;
- подготовки данных, которая не нужна для текущего кадра.

Осторожно: callback может выполниться позже, чем ожидается. Для обязательной UI-логики нужен другой механизм.

Если осталось ещё несколько элементов, планируем следующий вызов: один вызов не обработает всю очередь автоматически. Отдельная операция тоже должна быть короткой — `timeRemaining()` не прерывает её выполнение. Пример рассчитан на браузер с `requestIdleCallback`; проверяй поддержку через `'requestIdleCallback' in window`. Для неподдерживаемого браузера можно обрабатывать очередь небольшими порциями через таймер, учитывая, что таймер не сообщает о свободном времени браузера. Обязательную работу не оставляй в этой очереди.

## Практические правила оптимизации DOM

- Делить тяжёлую работу на небольшие части.
- Группировать чтения layout отдельно от записей стилей.
- Для анимаций предпочитать `transform` и `opacity`, если это подходит по смыслу.
- Не запускать бесконечные microtasks.
- Для тяжёлых вычислений рассмотреть [[Фронтенд/API браузера/06. Web Workers/01. Web Workers и main thread|Web Workers и main thread]].

## Частые ошибки

- Делать анимацию через `setInterval()` без связи с кадром.
- Класть тяжёлую работу в `requestAnimationFrame()` и всё равно блокировать кадр.
- Использовать `requestIdleCallback()` для задачи, без которой интерфейс не должен продолжать работу.
- Считать, что `requestAnimationFrame()` гарантирует 60 FPS.

## Как ответить на собеседовании за одну минуту

`requestAnimationFrame()` нужен для визуальных обновлений: браузер вызывает переданный обработчик перед ближайшим кадром, поэтому изменения лучше синхронизируются с отрисовкой. Но сам обработчик выполняется в основном потоке, поэтому тяжёлая работа внутри него всё равно может испортить кадр. `requestIdleCallback()` подходит для некритичной фоновой работы, когда у браузера есть свободное время; его нельзя использовать для обязательной логики, потому что обработчик может быть отложен. Для производительности важно уменьшать лишние расчёты геометрии и перерисовки и не блокировать основной поток.
