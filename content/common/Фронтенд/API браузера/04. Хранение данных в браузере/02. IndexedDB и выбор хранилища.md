# IndexedDB и выбор хранилища

> [!summary]
> IndexedDB позволяет хранить в браузере объекты и находить их по ключам и индексам. Например, в ней можно сохранить каталог товаров для работы без сети. Записи выполняются асинхронно, а несколько связанных изменений можно объединить в транзакцию.

## Зачем понимать тему

Middle frontend-разработчику не всегда нужно писать IndexedDB вручную, но важно понимать, когда её выбрать: offline-first, кэш данных приложения, большие списки, бинарные данные, сложные объекты.

## Базовая модель

Внутри базы IndexedDB создают отдельные хранилища — object stores. Например, в одном можно держать товары, а в другом — черновики заказов. Чтение и запись выполняются асинхронно, внутри транзакций.

Если транзакция меняет несколько записей, ранний успешный запрос ещё не завершает всё сохранение: следующая ошибка может отменить изменения. Поэтому сообщение «Сохранено» показывают после события `complete` транзакции или соответствующего Promise обёртки.

Сетевые данные лучше получить заранее. Если между запросами нативной транзакции ждать `fetch`, браузер может успеть завершить транзакцию, когда у неё больше нет ожидающих операций.

```text
Database
└─ object store: users
   ├─ key: 1 -> { id: 1, name: "Alex" }
   └─ key: 2 -> { id: 2, name: "Maria" }
```

Практически в проектах часто используют тонкую обёртку, например `idb`, потому что нативный callback/event API многословный.

## Синхронные и асинхронные хранилища

| API | Модель | Когда подходит |
| --- | --- | --- |
| `localStorage` | синхронная строковая map | маленькие настройки |
| `sessionStorage` | синхронная строковая map | временное состояние вкладки |
| cookies | хранилище cookie для HTTP-запросов | сессии и серверные признаки |
| IndexedDB | асинхронная база | большие структурированные данные |
| Cache API | асинхронный cache request/response | HTTP-ответы; доступен странице и workers |

## Как выбирать хранилище

- Нужно отправлять значение на сервер автоматически: cookie.
- Нужно сохранить тему или флаг UI: `localStorage`.
- Нужно сохранить состояние только для текущей вкладки: `sessionStorage`.
- Нужно хранить много объектов, offline-данные или искать по ключам: IndexedDB.
- Нужно кэшировать HTTP responses для offline: Cache API; для перехвата запросов страницы часто используют Service Worker.

Ежедневная запись и её черновик хранятся в IndexedDB через Dexie. При сохранении запись обновляется, а соответствующий черновик удаляется в одной транзакции: полезное правило — не оставлять старый черновик рядом с уже сохранённой записью. Облачная синхронизация требует отдельного механизма обмена с сервером. Подробнее: [[Фронтенд/Инженерные основы/10. Данные и надёжность/01. Хранение, транзакции и миграции|Хранение, транзакции и миграции]].

Асинхронный API позволяет не ждать операции синхронно. Но подготовка больших объектов, обработчики и рендер всё ещё могут занимать основной поток.

[Спецификация Cache API](https://w3c.github.io/ServiceWorker/#cache-interface) описывает доступ из Window и Worker; API не требует, чтобы код выполнялся именно внутри Service Worker.

## Частые ошибки

- Использовать `localStorage` как базу данных.
- Писать критичную логику без обработки ошибок quota/permission.
- Смешивать Cache API и IndexedDB: один хранит responses, другой - данные приложения.
- Забывать про миграции схемы IndexedDB.

## Как ответить на собеседовании за одну минуту

IndexedDB я выберу, когда браузеру нужно хранить много объектов, например каталог для поиска без сети. Данные лежат в отдельных object stores; по ключу или индексу можно найти нужные записи. Несколько связанных изменений объединяются в транзакцию.

API асинхронный: пока база выполняет операцию, JavaScript не ждёт её синхронно, как при обращении к `localStorage`. Подготовка больших объектов и их отображение всё ещё требуют времени.

Для одной настройки IndexedDB обычно избыточна — достаточно `localStorage`. Для серверной сессии нужна cookie, а для сохранённых HTTP-ответов подходит Cache API, часто вместе с Service Worker.
