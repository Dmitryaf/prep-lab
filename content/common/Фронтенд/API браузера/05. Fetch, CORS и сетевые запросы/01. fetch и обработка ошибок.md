# fetch и обработка ошибок

> [!summary]
> `fetch()` отправляет запрос и возвращает Promise с ответом сервера. Если сервер ответил 404, ответ всё равно получен: код должен отдельно проверить статус. В `catch` запрос попадёт, например, при сетевом отказе или отмене.

## Базовая модель

```js
const response = await fetch('/api/user');
const user = await response.json();
```

`fetch()` ждёт response headers и возвращает `Response`. Тело читается отдельно: `json()`, `text()`, `blob()`, `arrayBuffer()`.

## Обработка HTTP-статусов

```js
async function loadUser() {
  const response = await fetch('/api/user');

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  return response.json();
}
```

`response.ok` равен `true` для статусов 200-299. `404` или `500` обычно дают fulfilled Promise с `Response`, поэтому статус нужно проверять вручную.

## Сетевые ошибки и ошибки парсинга

```js
try {
  const response = await fetch('/api/user');

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  const user = await response.json();
  render(user);
} catch (error) {
  showError(error);
}
```

В `catch` могут попасть разные причины:

- сетевой отказ;
- блокировка чтения ответа политикой CORS;
- отмена запроса;
- ошибка парсинга JSON;
- вручную брошенная ошибка из-за `!response.ok`.

Для хорошего UI эти случаи часто различают.

## POST с JSON

```js
async function createUser(user) {
  const response = await fetch('/api/users', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(user),
  });

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  return response.json();
}
```

## credentials

По умолчанию `fetch()` передаёт учётные данные, включая подходящие cookies, только в запросах к тому же origin. Для другого origin нужен `credentials: 'include'`. При этом cookies всё равно подчиняются `SameSite`, `Secure` и политике сторонних cookies браузера; этот параметр не обходит ограничения. CORS-заголовки сервера определяют, разрешено ли JavaScript прочитать ответ с учётными данными.

```js
fetch('https://api.example.com/me', {
  credentials: 'include',
});
```

## Частые ошибки

- Ожидать, что `fetch('/missing')` попадёт в `catch` из-за `404`.
- Читать body дважды: `Response` body - поток, его нельзя просто перечитать без специальных приёмов.
- Не различать HTTP-ошибку, сетевой отказ и ошибку разбора JSON.
- Забывать `JSON.stringify()` для JSON body.
- Считать, что `mode: 'no-cors'` "решает CORS". Такой response обычно opaque и недоступен для чтения.

## Как ответить на собеседовании за одну минуту

`fetch()` позволяет отправить HTTP-запрос и получить `Response`. Например, если сервер вернул 404, Promise обычно завершится успешно: браузер получил ответ, хотя нужной страницы нет. Поэтому я проверяю `response.ok` или `response.status`.

Тело читаю отдельно, например через `response.json()`. Это тоже асинхронная операция, и она может завершиться ошибкой, если пришёл неверный JSON. В `catch` также попадают сетевой отказ, отмена и CORS-блокировка.

Если API находится на другом origin и ему нужна cookie, на клиенте указываю `credentials: 'include'`, а сервер разрешает такой ответ через CORS. При этом правила `SameSite`, `Secure` и браузерные ограничения cookie продолжают действовать.
