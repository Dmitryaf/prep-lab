# Same-origin policy, CORS и preflight

> [!summary]
> Правило одного источника ограничивает чтение данных между разными источниками. Через CORS сервер явно указывает браузеру, какому источнику разрешено читать ответ на запрос.

## Origin

Origin состоит из схемы, host и port.

```text
https://example.com:443
scheme  host        port
```

Эти URL имеют разные origin:

```text
https://example.com
http://example.com
https://api.example.com
https://example.com:8443
```

## Same-origin policy

Правило одного источника (same-origin policy) — ограничение браузера: скрипт одного источника не должен свободно читать данные другого.

Важно: браузер может разрешать встраивать некоторые cross-origin ресурсы через теги (`img`, `script`, `link`), но чтение response из JavaScript через `fetch()` ограничено.

## CORS

CORS - протокол на HTTP-заголовках. Сервер отвечает браузеру, можно ли отдать response JavaScript-коду с другого origin.

Упрощённо:

```http
Origin: https://app.example
```

```http
Access-Control-Allow-Origin: https://app.example
```

Если заголовки не разрешают доступ, браузер блокирует JavaScript от чтения response.

## Preflight

Предварительный `OPTIONS` нужен, например, для `PUT`/`DELETE`, заголовка `Authorization` или `Content-Type: application/json`. Запросы `GET`, `HEAD` и `POST` могут обходиться без него, если их заголовки и значения входят в CORS safelist; для `Content-Type` это `text/plain`, `application/x-www-form-urlencoded` и `multipart/form-data`. Один только `credentials: 'include'` предварительный запрос не вызывает. Разрешение может быть сохранено в отдельном preflight-кэше, поэтому `OPTIONS` не обязан повторяться при каждом запросе.

```http
OPTIONS /users
Origin: https://app.example
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type
```

Сервер должен разрешить метод и заголовки:

```http
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Methods: PUT
Access-Control-Allow-Headers: content-type
```

Если preflight не разрешён, основной запрос не будет отправлен.

## Credentials

Для cookies/credentials в cross-origin запросе нужны обе стороны:

```js
fetch('https://api.example.com/me', {
  credentials: 'include',
});
```

И ответ сервера:

```http
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Credentials: true
```

При credentials нельзя использовать wildcard `*` как конкретное разрешение origin.

## Частые ошибки

- Исправлять CORS только на клиенте. Разрешение должен дать сервер.
- Думать, что CORS защищает сервер от получения запроса. CORS в основном защищает чтение response браузерным JavaScript.
- Считать `mode: 'no-cors'` решением: response станет opaque и его нельзя нормально прочитать.
- Использовать `Access-Control-Allow-Origin: *` вместе с credentials.
- Путать same-origin и same-site.

## Как ответить на собеседовании за одну минуту

Представим, что страница с `app.example` запрашивает API на `api.example`. Это разные origin: origin складывается из схемы, хоста и порта. По правилу same-origin policy браузер не даст JavaScript страницы свободно читать ответ другого origin.

Через CORS сервер API сообщает в заголовках, какой странице разрешено прочитать ответ. Для некоторых запросов браузер сначала отправляет OPTIONS — например, если основной запрос использует PUT или заголовок Authorization. Так он проверяет разрешённые методы и заголовки, и только после разрешения отправляет основной запрос.

Поэтому исправление CORS обычно находится в настройках сервера. Клиент выбирает параметры запроса, в том числе нужно ли передавать учётные данные, но разрешение на чтение ответа выдаёт сервер.

> [!note]- Углубление: CORS не заменяет авторизацию
> CORS не является полноценной серверной авторизацией. Сервер всё равно проверяет пользователя, права и защиту от CSRF. Запрос без preflight может уже изменить данные, даже если браузер затем запретит скрипту читать ответ.
