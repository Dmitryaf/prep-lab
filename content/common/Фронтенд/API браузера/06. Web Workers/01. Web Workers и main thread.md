# Web Workers и main thread

> [!summary]
> Web Worker позволяет выполнять JavaScript вне main thread. Это полезно для тяжёлых вычислений, чтобы интерфейс продолжал реагировать на ввод и рендериться.

## Зачем понимать тему

Вопрос о Web Worker часто возникает при обсуждении производительности: что делать, если вычисление мешает интерфейсу отвечать на ввод? Можно уменьшить объём вычислений, разбить работу на части или вынести тяжёлую часть в Web Worker, если обмен данными и устройство приложения это позволяют.

## Базовая модель

Main thread:

```js
const worker = new Worker('/worker.js');

worker.postMessage({ numbers: [1, 2, 3] });

worker.addEventListener('message', (event) => {
  console.log(event.data.sum);
});
```

Worker:

```js
self.addEventListener('message', (event) => {
  const sum = event.data.numbers.reduce((total, number) => total + number, 0);
  self.postMessage({ sum });
});
```

Worker не имеет доступа к DOM. Он общается с main thread через `postMessage`.

## Когда использовать

Подходит:

- парсинг больших файлов;
- обработка изображений/данных;
- сложные вычисления;
- подготовка данных для визуализации;
- работа, которую можно отделить от DOM.

Не подходит:

- прямое изменение DOM;
- исправление медленного network API;
- маленькие операции, где overhead сообщений больше пользы;
- задачи, которым постоянно нужен синхронный доступ к UI-состоянию.

## Передача данных

При `postMessage()` данные передаются между контекстами. Многие значения копируются алгоритмом структурированного клонирования. Некоторые объекты, например `ArrayBuffer`, можно передать другому владельцу, чтобы не копировать большой буфер.

```js
const buffer = new ArrayBuffer(1024);
worker.postMessage(buffer, [buffer]);
```

После transfer исходный buffer в отправителе становится недоступен.

## Частые ошибки

- Ожидать, что worker может делать `document.querySelector()`.
- Выносить в worker слишком мелкую работу.
- Передавать огромные данные копированием и терять выигрыш.
- Не обрабатывать `error` и `messageerror`.
- Считать, что worker автоматически делает приложение быстрее.

## Как ответить на собеседовании за одну минуту

Web Worker выполняет JavaScript в отдельном контексте, чтобы тяжёлые вычисления не блокировали основной поток, занятый событиями, DOM и отрисовкой. У Web Worker нет доступа к DOM, поэтому со страницей он обменивается сообщениями через `postMessage`. Данные обычно клонируются; передаваемые объекты, например большой буфер, можно передать другому владельцу без копирования. Web Worker помогает со сложными вычислениями, но сам по себе не ускоряет сеть и не исправляет устройство интерфейса.

> [!note]- Углубление: типы workers
> Кроме выделенного Worker (dedicated worker), существуют общие Worker (shared workers) и специализированные обработчики worklets. Для большинства интервью достаточно выделенного Worker. Service Worker работает как сетевой посредник и не предназначен для произвольных тяжёлых вычислений интерфейса.

## Практическая задача

Большой CSV-файл парсится 2 секунды и блокирует ввод в форме. Что можно сделать?

> [!question]- Разбор
> Варианты: разбирать данные частями, показывать ход выполнения или вынести тяжёлый разбор в Web Worker. При передаче данных учитывать размер и стоимость копирования. Если результат нужен для DOM, Worker возвращает данные сообщением, а основной поток обновляет интерфейс.

## Как показать начало файла размером 2 ГБ

Сначала уточни задачу: показать первые строки, найти записи или обработать весь файл? Для предпросмотра не нужно читать всё. `file.text()` создаст огромную строку; перенос такого чтения в Worker не устранит расход памяти.

1. Установи лимит предпросмотра, например первые 64 КиБ и до 20 строк.
2. Прочитай только этот участок через `file.slice(...).text()` или stream.
3. Покажи, что результат обрезан. Не сохраняй прочитанные части в растущий массив.
4. При выборе другого файла прекрати старое чтение и не показывай его результат.

Небольшой пример именно **текстового** предпросмотра:

```js
// checked-example: file-preview
async function previewText(file, maxBytes = 65536, maxLines = 20) {
  const bytes = await file.slice(0, maxBytes).arrayBuffer();
  const truncatedBytes = file.size > maxBytes;
  const decoder = new TextDecoder('utf-8');
  const text = decoder.decode(bytes, { stream: truncatedBytes });
  const lines = text.split(/\r?\n/);
  return {
    text: lines.slice(0, maxLines).join('\n'),
    truncated: truncatedBytes || lines.length > maxLines,
  };
}
```

Параметры — положительные целые, кодировка по условию UTF-8. На границе обрезанного участка `stream: true` не выводит незавершённый многобайтовый символ. Память ограничена размером участка и его текстом, а не размером файла. Для обычного Blob нет прерывания `arrayBuffer()`, но здесь чтение ограничено; смену выбранного файла всё равно нужно проверять перед показом результата.

> [!note]- Если попросят подробнее: весь CSV, поиск и Worker
>
> CSV нельзя надёжно разобрать через `split('\n')`: перевод строки может находиться внутри кавычек. Для полноценного просмотра строк нужен потоковый CSV-парсер, который сохраняет состояние между кусками. Читай `file.stream()`, обрабатывай часть и освобождай её; храни только нужное окно строк или агрегат. Ограничь также максимальный размер одной записи.
>
> Если парсинг мешает вводу, перенеси его в Worker. Возвращай ограниченные порции и жди готовности интерфейса перед следующей: очередь сообщений тоже расходует память. Для перехода сразу к строке N нужен индекс смещений или повторный проход; обещать произвольный доступ без стоимости нельзя.

Проверь два эффекта отдельно: память перестаёт расти с объёмом обработанного файла, ввод остаётся отзывчивым. [Blob.stream](https://developer.mozilla.org/en-US/docs/Web/API/Blob/stream) предоставляет поток чтения, но сам по себе не ограничивает размер накопленного результата.
