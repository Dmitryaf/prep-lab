# Service Workers, Cache API и Background Sync

> [!summary]
> Service Worker - браузерный worker, который может перехватывать сетевые запросы страницы в своём scope. Он нужен для offline-сценариев, кэширования ресурсов, push/background возможностей и PWA-поведения.

## Зачем понимать тему

На middle/middle+ интервью могут спросить, чем Service Worker отличается от Web Worker, как работает offline cache, почему обновление Service Worker не всегда мгновенно применяется и куда сохранять отложенные действия.

## Базовая модель

```text
Page -> fetch('/app.js') -> Service Worker -> network/cache
```

Service Worker:

- работает отдельно от страницы;
- не имеет доступа к DOM;
- ограничен scope;
- обычно требует HTTPS;
- может быть остановлен браузером и запущен снова по событию.

## Регистрация

```js
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}
```

Минимальный Service Worker:

```js
self.addEventListener('install', (event) => {
  console.log('install');
});

self.addEventListener('activate', (event) => {
  console.log('activate');
});

self.addEventListener('fetch', (event) => {
  event.respondWith(fetch(event.request));
});
```

## Кэширование через Service Worker

Упрощённое чтение заранее заполненного кэша для GET-запросов к `/assets/` своего origin. Наполнение и очистка кэша здесь не показаны; сам пример не делает приложение доступным offline:

```js
self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);
  if (event.request.method !== 'GET' ||
      url.origin !== self.location.origin ||
      !url.pathname.startsWith('/assets/')) return;

  event.respondWith(
    caches.match(event.request).then((cachedResponse) => {
      if (cachedResponse) {
        return cachedResponse;
      }

      return fetch(event.request);
    })
  );
});
```

Типовые стратегии:

| Стратегия | Когда подходит |
| --- | --- |
| cache-first | статические файлы с версией в адресе |
| network-first | HTML/document или данные, где важна свежесть |
| stale-while-revalidate | быстро показать данные из кэша и обновить на фоне |

Подробные offline-first стратегии лучше вынести в P2/backlog.

## IndexedDB и Cache API

Cache API хранит пары request/response. IndexedDB хранит данные приложения.

Пример:

- `app.css`, `logo.svg`, response `/api/products` как HTTP response -> Cache API;
- очередь несинхронизированных действий, нормализованные товары, настройки -> IndexedDB.

Cache API доступен и странице, и workers. Service Worker нужен для управления сетевыми событиями, а не для самого существования Cache API. [Спецификация](https://w3c.github.io/ServiceWorker/#cache-interface).

## Background Sync

Background Sync позволяет зарегистрировать синхронизацию, чтобы Service Worker попробовал выполнить работу позже, когда сеть восстановится.

Упрощённый сценарий:

1. пользователь отправляет форму offline;
2. приложение сохраняет действие в IndexedDB;
3. регистрирует sync;
4. Service Worker получает событие `sync` и отправляет накопленные действия.

Поддержка Background Sync не везде одинаковая, поэтому нужен запасной способ: повтор при следующем открытии страницы или ручная кнопка "повторить".

## Частые ошибки

- Путать Web Worker и Service Worker.
- Ожидать доступ к DOM из Service Worker.
- Кэшировать HTML cache-first и получать "вечную старую версию".
- Не продумывать invalidation/versioning cache.
- Хранить очередь offline-действий только в памяти Service Worker.
- Считать Background Sync гарантированной во всех браузерах.

## Как ответить на собеседовании за одну минуту

Service Worker — отдельный обработчик, который браузер использует для сетевых запросов страниц в заданной области действия. Он может перехватывать события `fetch`, возвращать ответ из Cache API или обращаться к сети, помогая приложению работать без интернета. В отличие от Web Worker, он предназначен прежде всего для обработки запросов, а не тяжёлых вычислений. Он не имеет доступа к DOM и может быть остановлен браузером, поэтому важное состояние сохраняют в Cache API или IndexedDB. Background Sync позволяет отложить отправку до восстановления сети. Из-за ограниченной поддержки нужен и запасной способ повторить отправку.

> [!note]- Углубление: lifecycle
> Полный жизненный цикл включает установку, ожидание, активацию, обновление, `skipWaiting()` и `clients.claim()`. В P0/P1 достаточно понимать, что новая версия Service Worker не всегда начинает контролировать уже открытые страницы мгновенно. Детальные стратегии обновления стоит вынести во второй проход.

## Практическая задача

Пользователь создаёт комментарий offline. Нужно отправить его позже. Как построить схему?

> [!question]- Разбор
> Сохранить действие в IndexedDB, показать optimistic/pending состояние в UI, зарегистрировать Background Sync при наличии поддержки. В Service Worker на событии `sync` прочитать очередь из IndexedDB, отправить запросы, удалить успешно отправленные элементы. Если Background Sync не поддерживается, повторять при следующем открытии страницы или по ручному действию.
