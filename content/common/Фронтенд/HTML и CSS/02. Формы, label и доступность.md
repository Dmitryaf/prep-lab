# Формы, label и доступность

> [!summary]
> Доступная форма начинается с правильного HTML: `form`, `label`, подходящий `input type`, понятные ошибки и работа с клавиатуры. ARIA помогает в сложных случаях, но не заменяет нативную семантику.

## Базовая форма

```html
<form action="/subscribe" method="post">
  <div class="field">
    <label for="email">Email</label>
    <input id="email" name="email" type="email" required autocomplete="email">
  </div>

  <button type="submit">Подписаться</button>
</form>
```

Что здесь важно:

- `label` связан с input через `for`/`id`;
- `name` нужен для отправки значения;
- `type="email"` дает браузеру подсказки, валидацию и mobile keyboard;
- `required` добавляет базовую constraint validation;
- `button type="submit"` явно задает поведение.

## `label`

`label` увеличивает кликабельную область и дает доступное имя control.

```html
<label>
  <input type="checkbox" name="agreement">
  Я согласен с условиями
</label>
```

Для кастомных checkbox/radio важно не убирать нативный input из доступности. Его можно визуально скрыть аккуратно, но он должен оставаться фокусируемым и связанным с label.

## Input types

| Тип | Когда полезен |
|---|---|
| `text` | обычная строка |
| `email` | email-адрес |
| `password` | пароль |
| `number` | числовой ввод, если подходят его ограничения |
| `tel` | телефон, когда нужен телефонный keyboard |
| `search` | поиск |
| `checkbox` | независимый boolean |
| `radio` | один выбор из группы |
| `date` | дата, если подходит нативный picker |

Не выбирай `number` только потому, что строка состоит из цифр: телефон, индекс и номер карты не являются числами для вычислений.

## Базовая доступность

P0-checklist:

- интерактивные элементы доступны с клавиатуры;
- виден focus state;
- у изображений есть корректный `alt`;
- controls имеют доступные имена;
- ошибки формы связаны с полями;
- цвет не является единственным способом передать состояние;
- порядок DOM соответствует логическому порядку чтения.

## Alt-текст

```html
<img src="/avatar.jpg" alt="Аватар Анны Смирновой">
<img src="/decor.svg" alt="">
```

Информативное изображение получает короткое описание. Декоративное - пустой `alt`, чтобы screen reader его пропустил.

## Keyboard navigation

Нативные `button`, `a href`, `input`, `select`, `textarea` уже умеют получать focus и работать с клавиатуры. Если делаешь custom control, нужно воспроизвести keyboard behavior, focus management, role/state и доступное имя. Поэтому на собеседовании хороший ответ часто начинается с "использовать нативный элемент".

## ARIA basics

ARIA добавляет semantics и states для assistive technologies:

```html
<button
  type="button"
  aria-expanded="false"
  aria-controls="filters"
>
  Фильтры
</button>
```

Практичные правила:

- сначала нативный HTML;
- не добавляй role, который уже есть у элемента;
- ARIA не добавляет поведение: `role="button"` не делает `div` кнопкой;
- `aria-label` полезен, когда видимого текста нет;
- `aria-describedby` связывает control с подсказкой или ошибкой.

## Что значит скрыть элемент от screen reader

`display: none` обычно убирает элемент и с экрана, и из дерева доступности. `aria-hidden="true"` скрывает его от вспомогательных технологий, но оставляет видимым.

Пример: у кнопки есть текст «Удалить» и декоративная иконка. Иконку можно скрыть через aria-hidden, чтобы имя кнопки не читалось дважды. Нельзя так скрывать фокусируемую кнопку или контейнер с активными полями: пользователь клавиатуры попадёт в элемент, который не сможет узнать по озвучиванию.

Обратная задача — визуально скрытая подпись для screen reader. Для неё используют проверенный класс visually-hidden, а не display: none. Доступное имя полезно не только для речи, но и для других средств, включая брайлевский дисплей.

Проверка: пройти форму клавишей Tab, увидеть фокус, проверить имя/роль/состояние в дереве доступности, затем выполнить основной сценарий со screen reader. Автоматическая проверка не заменяет этот проход.

## Form validation

```html
<label for="password">Пароль</label>
<input
  id="password"
  name="password"
  type="password"
  minlength="8"
  aria-describedby="password-hint"
>
<p id="password-hint">Минимум 8 символов.</p>
```

Нативная валидация полезна, но в продукте часто нужна своя логика, локализация и серверная проверка. Ошибки должны быть видимыми и связанными с полем.

> [!note]- Углубление: accessibility tree
> Accessibility tree представляет элементы через роли, имена и состояния для вспомогательных технологий. Это не копия DOM: важны смысл элемента и доступное имя. Проверяй форму клавиатурой и деревом доступности браузера.

## Частые ошибки

- Placeholder вместо `label`.
- Кастомный checkbox без доступного input.
- Убирать focus outline без замены.
- Использовать `div role="button"` без keyboard behavior.
- Писать `alt="image"` или дублировать рядом стоящий текст.
- Показывать ошибку только красной рамкой.

## Как ответить на собеседовании за одну минуту

Доступная форма строится на нативном HTML: `form`, правильный `input type`, `label`, `name`, понятный submit button, visible focus и ошибки, связанные с полями. `label` дает control доступное имя и улучшает кликабельность. ARIA использую как дополнение, когда нативной семантики не хватает, но не как замену поведения. Для изображений пишу осмысленный `alt`, а декоративным ставлю пустой `alt`.

## Вопросы для самопроверки

- Почему placeholder не заменяет label?
- Когда `alt=""` правильнее текста?
- Почему `role="button"` недостаточно?
- Как связать ошибку с полем формы?
- Почему телефон не стоит делать `type="number"`?

## Практические задачи

1. Исправь форму без label.
2. Сделай доступный custom checkbox.
3. Добавь подсказку и ошибку к input через ARIA.

> [!question]- Разбор
> ```html
> <label for="city">Город</label>
> <input id="city" name="city" type="text" aria-describedby="city-error">
> <p id="city-error">Выберите город из списка доставки.</p>
> ```
>
> Для custom checkbox оставь настоящий `<input type="checkbox">`, свяжи его с `label` и стилизуй визуальную часть через CSS.
