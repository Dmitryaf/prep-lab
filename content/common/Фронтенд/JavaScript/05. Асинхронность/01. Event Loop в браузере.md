# Event Loop в браузере

> [!summary]
> Event Loop определяет порядок выполнения кода и обновления интерфейса. Основная модель: текущий синхронный код → микрозадачи до опустошения очереди → возможность обновить экран и перейти к следующей задаче.

## Зачем понимать Event Loop

Event Loop объясняет типовые вопросы:

- почему `Promise.resolve().then(...)` выполняется раньше `setTimeout(..., 0)`;
- почему тяжёлый синхронный код замораживает интерфейс;
- почему бесконечная цепочка microtasks может не дать браузеру перейти к следующей task и отрисовке;
- как `await` влияет на порядок выполнения кода;
- как решать задачи формата “что выведется в console.log”.

## Базовая модель

Задача (`task`) — порция работы, например обработка таймера. Микрозадача (`microtask`) — отложенное продолжение, например обработчик готового Promise. Микрозадачи выполняются после текущего синхронного кода, до следующей задачи; добавленные ими микрозадачи тоже нужно выполнить.

`setTimeout(fn, 0)` планирует задачу на будущее и не прерывает текущий код. Promise не создаёт отдельный поток: его обработчик тоже исполняется в JavaScript. Браузер получает возможность обновить экран, когда код уступает управление; кадр не гарантирован после каждой задачи.

```text
синхронный код → микрозадачи (до пустой очереди)
              → возможность отрисовки / следующая задача
```

## Call Stack

Call Stack — стек вызовов JavaScript. При вызове функции в него добавляется запись о её выполнении. После завершения функции запись убирается, и управление возвращается к месту вызова.

Пока Call Stack занят, браузер не может выполнить другой JavaScript-код из timers, событий или Promise callbacks.

```js
function second() {
  console.log('B');
}

function first() {
  console.log('A');
  second();
  console.log('C');
}

first();
```

Результат:

```text
A
B
C
```

Весь этот код выполняется синхронно внутри одной task.

## Task и task queues

Типичные примеры — таймеры и обработка событий. В учебных задачах ниже считаем выполнение начального кода текущей задачей.

> [!note]- Углубление: очереди и термин macrotask
> В статьях задачу часто называют «макрозадачей»; в HTML Standard используется `task`. У браузера несколько очередей и источников задач, а не одна общая очередь всех событий. Нельзя обещать глобальный FIFO-порядок между любыми источниками.
>
> Микрозадачи выполняются в контрольных точках (microtask checkpoint), не только в конце задачи. Например, такая точка возможна после очистки стека вызовов при возврате из вызываемого браузером скрипта. Синхронный `dispatchEvent`, вызванный из JavaScript, не следует механически приравнивать к пользовательскому клику. Начальные скрипты также не всегда соответствуют отдельной задаче каждый. Для типовых примеров ниже хватает упрощённой модели.

## Microtask Queue

Очередь микрозадач хранит отложенные обработчики. Они выполняются после текущего синхронного кода, до перехода к следующей задаче.

Типичные источники microtasks:

- callbacks `.then()`, `.catch()`, `.finally()`;
- `queueMicrotask()`;
- продолжение `async`-функции после `await`;
- `MutationObserver`.

## Microtask Checkpoint

Контрольная точка — выполнение очереди микрозадач до её опустошения. Если обработчик добавил ещё одну микрозадачу, она попадает в конец очереди и тоже выполняется до следующей задачи. Поэтому бесконечная цепочка микрозадач задерживает таймеры и экран.

## Promise, queueMicrotask и setTimeout

```js
console.log('A');

setTimeout(() => {
  console.log('B');
}, 0);

Promise.resolve().then(() => {
  console.log('C');
});

queueMicrotask(() => {
  console.log('D');
});

console.log('E');
```

Результат:

```text
A
E
C
D
B
```

Что происходит:

1. Синхронно выводятся `A` и `E`.
2. Таймер запланирован как будущая задача.
3. В очереди микрозадач находятся `C`, затем `D`; они выполняются первыми.
4. После них становится возможным выполнение таймера: `B`.

## Microtask создаёт новую microtask

```js
console.log('A');

Promise.resolve().then(() => {
  console.log('B');

  queueMicrotask(() => {
    console.log('C');
  });
});

Promise.resolve().then(() => {
  console.log('D');
});

console.log('E');
```

Результат:

```text
A
E
B
D
C
```

Обработчик `B` добавляет `C` в конец очереди микрозадач. В очереди уже ждёт `D`, поэтому сначала выполнится `D`, затем `C`.

## Связь с async / await

`await` делит `async`-функцию на две части:

- код до первого `await` выполняется синхронно;
- продолжение после `await` планируется как microtask, когда ожидаемое значение готово.

```js
async function run() {
  console.log('B');
  await Promise.resolve();
  console.log('C');
}

console.log('A');
run();
console.log('D');
```

Результат:

```text
A
B
D
C
```

Подробная модель `async / await`: [[Фронтенд/JavaScript/05. Асинхронность/04. async-await|async-await]].

## Влияние на UI

Долгая задача или непрерывная цепочка микрозадач задерживает обработку ввода и обновление экрана. Например, пользователь нажал кнопку, но её обработчик ждёт, пока текущий код закончит работу.

Тяжёлый синхронный код блокирует интерфейс:

```js
button.addEventListener('click', () => {
  const start = Date.now();

  while (Date.now() - start < 3000) {
    // тяжелая синхронная работа
  }

  console.log('done');
});
```

Бесконечная цепочка microtasks тоже опасна:

```js
function loop() {
  queueMicrotask(loop);
}

loop();
```

Такой код постоянно добавляет новую микрозадачу и не даёт перейти к следующей макрозадаче. На практике это может задержать таймеры, обработку событий и обновление экрана.

## requestAnimationFrame и rendering

`requestAnimationFrame()` просит браузер вызвать переданный обработчик перед ближайшим обновлением изображения. Это не «обычная макрозадача» для выполнения бизнес-логики, а API для синхронизации изменений с кадром.

Для этого блока достаточно помнить:

- `requestAnimationFrame()` используют для визуальных обновлений и анимаций;
- тяжёлые tasks и бесконечные microtasks могут задержать кадр;
- подробности этапов построения и отрисовки страницы лучше повторять в [[Фронтенд/API браузера/03. Рендеринг браузера/01. Rendering pipeline и связь с Event Loop|Rendering pipeline и связь с Event Loop]].

## Частые ошибки

### Ошибка 1. Думать, что setTimeout с 0 выполнится сразу

`setTimeout(..., 0)` не прерывает текущий код. Callback попадёт в будущую task и выполнится только после завершения текущей task и microtasks.

### Ошибка 2. Называть все tasks одной очередью макрозадач

Для собеседования можно использовать слово “macrotask”, но лучше уточнять, что в спецификации есть tasks, task queues и task sources.

### Ошибка 3. Считать rendering обычной macrotask

Отрисовка связана с Event Loop, но его не стоит объяснять как обычный обработчик из той же очереди, что `setTimeout`.

### Ошибка 4. Забывать, что microtasks выполняются до опустошения очереди

Если microtask добавляет новую microtask, она тоже будет выполнена до перехода к следующей task.

### Ошибка 5. Смешивать browser Event Loop и Node.js Event Loop

В Node.js есть свои фазы event loop, `process.nextTick()` и `setImmediate()`. Это отдельная P2-тема и не нужна в базовом ответе про браузер.

## Как ответить на собеседовании за одну минуту

Event Loop в браузере координирует выполнение JavaScript и обработку событий. В базовой модели текущая макрозадача выполняет синхронный код до конца через Call Stack — стек вызовов. Примеры: выполнение первоначального `script`, обработчика таймера или события.

Затем браузер выполняет накопившиеся микрозадачи: обработчики готовых Promise, `queueMicrotask()` и продолжения после `await`. Очередь выполняется до опустошения, включая добавленные ею новые микрозадачи.

После этого браузер может перейти к следующей макрозадаче и обновить экран, когда наступит подходящий момент. Поэтому обработчик уже выполненного Promise в таком примере выполняется раньше `setTimeout(..., 0)`.

## Практические задачи

### Задача 1. Базовый порядок

```js
console.log('A');

setTimeout(() => {
  console.log('B');
}, 0);

console.log('C');
```

> [!question]- Разбор
> Результат:
>
> ```text
> A
> C
> B
> ```
>
> Первоначальный `script` — текущая макрозадача. В Call Stack сразу выполняются `console.log('A')`, вызов `setTimeout()` и `console.log('C')`. Обработчик таймера попадает в очередь будущих макрозадач. Очередь микрозадач пуста, поэтому после завершения скрипта Event Loop выполняет макрозадачу таймера и выводит `B`.

### Задача 2. Promise против timer

```js
console.log('A');

setTimeout(() => {
  console.log('B');
}, 0);

Promise.resolve().then(() => {
  console.log('C');
});

console.log('D');
```

> [!question]- Разбор
> Результат:
>
> ```text
> A
> D
> C
> B
> ```
>
> `A` и `D` выполняются в стеке вызовов текущего скрипта. `.then()` добавляет обработчик в очередь микрозадач. `setTimeout()` добавляет будущую макрозадачу. После завершения скрипта Event Loop выполняет микрозадачу `C`, и только потом макрозадачу таймера `B`.

### Задача 3. Новая microtask

```js
Promise.resolve().then(() => {
  console.log('A');

  Promise.resolve().then(() => {
    console.log('B');
  });
});

Promise.resolve().then(() => {
  console.log('C');
});
```

> [!question]- Разбор
> Результат:
>
> ```text
> A
> C
> B
> ```
>
> После синхронного кода в очереди микрозадач уже ждут `A` и `C`. Обработчик `A` добавляет `B` в конец очереди. Поэтому после `A` выполнятся `C`, затем `B`.

### Задача 4. await

```js
async function run() {
  console.log('A');
  await null;
  console.log('B');
}

console.log('C');
run();
console.log('D');
```

> [!question]- Разбор
> Результат:
>
> ```text
> C
> A
> D
> B
> ```
>
> Вызов `run()` начинается синхронно: `A` попадает в Call Stack текущей макрозадачи. На `await null` функция приостанавливается, а продолжение после `await` планируется как микрозадача. Затем текущая макрозадача выводит `D`. После завершения скрипта микрозадача продолжает `run()` и выводит `B`.
