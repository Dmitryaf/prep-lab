# Memory leaks во frontend

> [!summary]
> Утечка памяти возникает, когда объект больше не нужен приложению, но остается достижимым через ссылку.

## Через час вкладка занимает гигабайт: с чего начать

Зафиксируй повторяемый сценарий: открыть и закрыть панель, сменить страницу, выполнить поиск. Сравни память после нескольких повторов и сборки мусора. В снимке памяти `Heap Snapshot` найди растущий тип объектов и посмотри, какие ссылки удерживают их в памяти.

Например, закрытая панель осталась в массиве кэша, или слушатель на window замкнул её данные. Удали ненужную ссылку или подписку и повтори тот же сценарий. Одного падения графика недостаточно: важен исчезнувший рост после повторов.

Пошаговый стенд: [[Фронтенд/Инженерные основы/04. Производительность/03. Практическая диагностика таблицы, ввода и памяти|измерение памяти]]. Общая память вкладки включает не только JS heap; изображения, DOM и другие ресурсы могут требовать отдельной проверки.

## Частые причины

### Долгоживущие замыкания

```js
function createHandler(data) {
  return function handleClick() {
    console.log(data.id);
  };
}
```

Если handler живет долго, он удерживает `data`.

### Обработчики событий

```js
element.addEventListener('click', handler);
```

Если элемент или компонент удален, а listener продолжает удерживать данные, память может не освободиться.

### Таймеры

```js
const timerId = setInterval(update, 1000);
```

Интервалы нужно очищать через `clearInterval(timerId)`.

### Кэши

`Map` с ключами-объектами удерживает ключи и значения сильными ссылками. Для metadata иногда лучше `WeakMap`.

Удалённый DOM-узел со своим listener не обязательно течёт: если вся группа недостижима, сборщик может её освободить. Ищи путь от живого владельца — window, таймера, кэша, активной подписки. Само наличие цикла ссылок не доказывает утечку.

## Профилактика

- удалять event listeners;
- очищать timers;
- отменять подписки;
- ограничивать размер cache;
- использовать `WeakMap` для metadata объектов;
- не держать большие данные в closures без причины.
