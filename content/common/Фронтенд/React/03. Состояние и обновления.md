# Состояние и обновления

[[Фронтенд/React/00. Карта раздела|Карта React]]

Счётчик должен помнить число между вызовами компонента. Обычная переменная при новом вызове создаётся заново, а useState позволяет React сохранить значение. После вызова setter React запланирует обновление. Текущий обработчик при этом продолжит видеть прежнее значение: оно относится к тому рендеру, в котором обработчик был создан.

## Первое состояние

```jsx
const [query, setQuery] = useState('');
const visible = users.filter(user => user.name.includes(query));
// В компоненте: <input value={query} onChange={e => setQuery(e.target.value)} />
```

query хранится между рендерами. visible вычисляется из users/query и не нуждается во втором state. При вводе «Ан» список рассчитывается по новому снимку. useMemo можно добавить после измерений; корректность фильтра от него не зависит.

Начальное значение useState учитывается при создании состояния. `useState(() => expensiveInitialValue())` откладывает вычисление до инициализации; функция должна быть чистой, в StrictMode она может вызываться дополнительно в разработке.

## Почему setState не меняет текущую переменную

Каждый рендер получает свой снимок состояния. В его обработчиках переменная сохраняет это значение.

```js
// Фрагмент обработчика; в этом рендере count равен 0.
setCount(count + 1);
setCount(count + 1);
console.log(count); // 0; следующий count будет 1
```

Оба вызова передали число 1. Если нужно два последовательных прибавления, используй обновление от предыдущего значения:

```js
setCount(n => n + 1);
setCount(n => n + 1); // следующий count будет 2
```

React может объединять обновления в один рендер — это batching. Функции обновления последовательно получают результат предыдущего шага. Они должны быть чистыми: не отправляй из них запросы.

## Почему таймер видит старое состояние

Обработчик и созданный в нём таймер замыкают переменные конкретного рендера. Если count был 0 при запуске таймера, чтение count внутри него позднее по-прежнему даст 0.

Для увеличения счётчика достаточно `setCount(n => n + 1)`. Если нужна самая свежая функция из props для внешней подписки, см. [[Фронтенд/React/06. Refs и работа с DOM#Подписка со свежим callback|подписку и ref]]. Не заменяй весь state на refs: ref не обновляет экран.

## Обновление объекта

```js
setUser(previous => ({ ...previous, name: 'Анна' }));
```

Создаётся новый объект. Присваивание `user.name = 'Анна'` меняет старый снимок, а передача того же объекта в setter может не вызвать нужное обновление. Копировать нужно изменяемую ветку; глубокое клонирование всего состояния обычно излишне.

## Один источник и производные данные

Выбранный документ удобно хранить как id, а сам объект находить в documents. Копия объекта в selectedDocument устареет при обновлении списка. Не храни отдельно isEmpty, если он полностью определяется длиной массива.

Если значения меняются вместе, их удобно объединить в объект или описать переход через reducer. Например, результат загрузки и её статус должны согласовываться. Независимые значения можно оставить отдельно. Когда setter получает прежнее значение по Object.is, React может пропустить обновление, поэтому изменённый объект нужно передавать новой ссылкой.

## Проверка себя

В чём разница двух `setCount(count + 1)` и двух `setCount(n => n + 1)`? Почему новая копия массива с изменённым прежним объектом внутри всё ещё мутирует старый снимок?

> [!question]- Разбор
>
> В первом случае дважды передано одно число; во втором updater-функции последовательно используют результат друг друга. При вложенном изменении копируют и массив, и изменяемый объект: `users.map(user => user.id === id ? { ...user, name } : user)`.
