# Рендер и идентичность

[[Фронтенд/React/00. Карта раздела|Карта React]]

В списке редакторов переставили строки, и введённый текст оказался у другого документа. Чтобы найти причину, нужно различать повторный расчёт интерфейса, изменение DOM и создание нового экземпляра компонента.

## Рендер не равен изменению DOM

Рендер — вычисление нового описания интерфейса. Commit — применение результата. Если текст не изменился, повторный вызов компонента не требует переписывать этот текст в DOM.

```jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(n => n + 1)}>{count}</button>;
}
```

При клике React запоминает новое состояние и снова вызывает Counter. Обычная локальная переменная при таком вызове создаётся заново; state хранится React между вызовами.

Вычисление интерфейса должно быть чистым: не отправляй запрос и не меняй внешний массив в теле компонента. Рендер может быть повторён или отброшен.

## Почему key влияет на состояние

React связывает состояние с местом компонента в дереве, его типом и key. При сортировке строки списка должны узнавать свою сущность:

```jsx
users.map(user => <UserRow key={user.id} user={user} />)
```

Если использовать индекс в изменяемом списке, прежнее состояние строки может остаться на позиции другого пользователя. Случайный key на каждом рендере, наоборот, заставит пересоздавать строку и терять ввод. Индекс допустим для действительно неизменяемого списка без перестановок и удаления.

Изменение key бывает намеренным: `<Editor key={documentId} />` сбрасывает локальный черновик при выборе другого документа. Сначала реши, требуется ли сброс по продуктовым правилам.

Не объявляй функцию компонента внутри другого компонента, если хочешь сохранять её состояние: на каждом вызове возникает новый тип. При этом создание JSX в переменной само по себе новым типом компонента не является.

## Что запускает обновление

Начальный render, обновление собственного state, рендер родителя и изменение читаемого Context — разные причины работы компонента. memo может пропустить часть работы при неизменных props, но не отключает собственное состояние или Context. React выбирает, какие вычисления повторить и какие изменения применить; число console.log не равно числу изменений DOM.

## StrictMode и повторяемость

В разработке StrictMode дополнительно вызывает функции, которые должны быть чистыми, и проверяет очистку effects и callback refs. Это помогает найти мутацию props и потерянную подписку. Дополнительные проверки зависят от расположения StrictMode; не выводи из логов dev-режима точное число вызовов в production.

Условное удаление компонента уничтожает его локальный state. CSS-скрытие оставляет компонент и ресурсы активными. Сохранение черновика при переключении вкладок обеспечивают выбранный владелец данных или механизм сохранения, а не случайный key.

> [!note]- Если попросят подробнее: reconciliation и Fiber
>
> Reconciliation — это сравнение прежнего и нового дерева элементов. По типу и key React понимает, какой компонент продолжает существовать и чьё состояние можно сохранить. Fiber — внутренний механизм, с помощью которого React организует и планирует эту работу. Поэтому вычисление интерфейса может быть повторено или отброшено, а действия вроде запроса нужно выполнять вне рендера.

## Проверка себя

В двух строках локально редактируется текст. Что случится после сортировки с key по id, по индексу и с Math.random()? Почему определение компонента внутри родителя сбрасывает состояние?

> [!question]- Разбор
>
> С key по id черновик останется у своего документа после сортировки. С key по индексу он останется на прежней позиции и может попасть к другому документу. Случайный key заставит создать строку заново, и ввод потеряется.
>
> Если функцию компонента объявлять внутри родителя, при каждом рендере создаётся новый тип компонента и его состояние тоже сбрасывается. Сохранить JSX в переменную можно: это не создаёт новый тип.
