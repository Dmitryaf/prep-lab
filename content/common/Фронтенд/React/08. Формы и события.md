# Формы и события

[[Фронтенд/React/00. Карта раздела|Карта React]]

Форма должна сохранить введённое имя, показать ошибку сервера и позволить повторить отправку. Сначала выбираем владельца значения и правила отправки; библиотека формы не заменяет этот контракт.

## Кто хранит значение поля

В управляемом поле React передаёт `value` и обновляет его через `onChange`. В неуправляемом поле текущее значение хранит DOM; начальное задаётся через `defaultValue`.

```jsx
const [name, setName] = useState('');
// Фрагмент внутри компонента:
return <label>Имя
  <input value={name} onChange={event => setName(event.target.value)} />
</label>;
```

Для управляемого текстового поля начни с пустой строки, а не undefined. Иначе поле может переключиться между режимами. Не храни одно значение одновременно в локальном state поля и state формы без понятного правила синхронизации.

Состояние нескольких шагов размещай выше переключаемых частей. Если переход удаляет компонент с его локальным state, черновик может потеряться. Серверные ошибки не должны очищать ввод. Общий [[Собеседования/Проектирование/Клиентское приложение#Бизнес-форма с согласованием|разбор сложной формы]] одинаково полезен для React и Vue.

## Отправка с сохранением ввода

```tsx
// checked-example: react-form
import { useRef, useState, type FormEvent } from 'react';

export function SaveName({ save }: { save: (name: string) => Promise<void> }) {
  const [name, setName] = useState('');
  const [status, setStatus] = useState<'idle' | 'pending' | 'success' | 'error'>('idle');
  const [error, setError] = useState('');
  const submitting = useRef(false);
  async function submit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (submitting.current) return;
    if (!name.trim()) { setError('Введите имя'); setStatus('error'); return; }
    submitting.current = true;
    setStatus('pending'); setError('');
    try {
      await save(name.trim());
      setStatus('success');
    } catch {
      setError('Не удалось сохранить. Повторите отправку.');
      setStatus('error');
    } finally {
      submitting.current = false;
    }
  }
  return <form onSubmit={submit}>
    <label>Имя для сохранения<input value={name} disabled={status === 'pending'}
      aria-describedby={error ? 'name-error' : undefined}
      onChange={event => { setName(event.target.value); setError(''); setStatus('idle'); }} /></label>
    <button disabled={status === 'pending'} type="submit">Сохранить</button>
    {status === 'pending' && <p role="status">Сохраняем…</p>}
    {status === 'success' && <p role="status">Сохранено</p>}
    {error && <p id="name-error" role="alert">{error}</p>}
  </form>;
}
```

Учебный контракт: одна форма на экране, ввод блокируется на время отправки, save отклоняет Promise при отказе. При ошибке имя остаётся в поле; повторная отправка разрешена. Ref закрывает повторный submit до следующего рендера, state управляет видимым pending. Это не серверная идемпотентность и не гарантия «запись не произошла» при потере ответа.

Если нужно разрешить ввод во время сохранения, сохрани отправленный снимок отдельно и не называй новый черновик сохранённым после завершения старой операции. Для нескольких экземпляров формы статичный id замени на useId. useId связывает label/описания, но не заменяет id сущности в key списка.

## События и неуправляемая форма

onChange получает React-событие. Значение поля удобно прочитать синхронно и передать как строку: не завязывай отложенную работу на event.currentTarget. preventDefault отменяет стандартную отправку формы; stopPropagation управляет распространением события и решает другую задачу. У кнопки, которая не отправляет форму, явно укажи type="button".

Неуправляемый input хранит значение в DOM. При submit его можно прочитать через `new FormData(event.currentTarget)`; полю нужен name. defaultValue задаёт начальное значение и не является командой постоянной синхронизации. Checkbox управляется checked, а не текстовым value. File input читают через files; обычной строкой value выбранный файл не задаётся.

## Actions в React 19

Функция в `<form action={action}>` и useActionState позволяют связать результат операции и pending с формой. Action получает FormData, а функция useActionState дополнительно получает предыдущий state первым аргументом. useFormStatus читает состояние родительской формы из дочернего компонента. Эти API не требуют автоматически Server Function; серверное выполнение зависит от среды.

Ожидаемые ошибки валидации возвращают как данные для интерфейса. Для асинхронного dispatch вне form action нужен подходящий Action/transition-контекст. После успешного form action неуправляемые поля сбрасываются; это важно для требований к сохранению ввода. Сначала разберись с контрактом простой формы выше, затем сравни способ с Actions по официальному примеру.

## Проверка себя

Почему HTTP-ошибка не должна стирать имя? Что означает успешный ответ, если пользователь успел изменить текст после отправки? Чем защита повторного submit отличается от идемпотентного API?

> [!question]- Разбор
>
> Ввод — черновик пользователя. Успех относится к отправленному снимку, а не любому последующему вводу. Локальная блокировка предотвращает часть повторов интерфейса; серверный контракт защищает от повторной доставки, нескольких вкладок и неизвестного исхода запроса.
