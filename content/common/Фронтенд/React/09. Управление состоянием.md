# Управление состоянием

[[Фронтенд/React/00. Карта раздела|Карта React]]

Редактор хранит текст, список показывает выбранный документ, фильтр должен восстанавливаться из URL, а пользователь приходит с сервера. Сложность возникает, когда всё это кладут в один store и теряют правила владения. Выбери источник для каждого значения до выбора библиотеки.

| Значение | Где начать | Почему |
| --- | --- | --- |
| Открыта ли локальная подсказка | useState в компоненте | Другие части экрана не используют значение |
| Выбранная строка и её редактор | Общий родитель | Два потребителя должны видеть один выбор |
| Фильтр, которым делятся ссылкой | URL | Reload и Back должны восстанавливать состояние |
| Тема поддерева | Context с выбранным владельцем | Убирает цепочку промежуточных props |
| Пользователи из API | Кэш серверных данных или loader | Нужны ключ, актуальность и обновление после записи |

## useReducer: правила перехода в одном месте

```tsx
import { useReducer } from 'react';

type Draft = { text: string; saved: string };
type Action = { type: 'change'; text: string } | { type: 'revert' };
function reducer(state: Draft, action: Action): Draft {
  switch (action.type) {
    case 'change': return { ...state, text: action.text };
    case 'revert': return { ...state, text: state.saved };
  }
}
function DraftEditor() {
  const [draft, dispatch] = useReducer(reducer, { text: 'План', saved: 'План' });
  const dirty = draft.text !== draft.saved;
  return <>
    <label>Черновик<input value={draft.text}
      onChange={event => dispatch({ type: 'change', text: event.target.value })} /></label>
    <button disabled={!dirty} onClick={() => dispatch({ type: 'revert' })}>Отменить</button>
  </>;
}
```

После ввода «Новый план» dirty становится true, кнопка активна. Отмена возвращает «План». dirty вычисляется, а не синхронизируется вторым действием. Reducer чистый: сеть и другие эффекты в него не помещают. useReducer организует переходы, но не превращает локальное состояние в глобальное.

## Context доставляет значение

```tsx
import { createContext, useContext } from 'react';
const ThemeContext = createContext<'light' | 'dark'>('light');
function ThemeLabel() {
  const theme = useContext(ThemeContext);
  return <span>Тема: {theme}</span>;
}
// <ThemeContext value="dark"><ThemeLabel /></ThemeContext> — синтаксис React 19.
// В React 18 используется <ThemeContext.Provider value="dark">...</ThemeContext.Provider>.
```

Потребитель читает ближайший provider. Значение по умолчанию применяется при отсутствии provider; оно не подставляется автоматически, если provider передал undefined. Изменение value по Object.is обновляет потребителей. memo не блокирует такое обновление.

Не складывай тему, каждое нажатие клавиши и весь кэш API в один Context. Раздели независимые значения; reducer и Context можно сочетать, передавая состояние и dispatch. Обоснование оптимизаций: [[Фронтенд/React/12. Производительность#Context и мемоизация|Context и мемоизация]].

## Когда нужен внешний store

Он полезен при большом числе независимых потребителей, частых обновлениях, потребности в selectors, диагностике действий или интеграции вне дерева. Redux Toolkit — пример организованных reducers/actions и инструментов; Zustand — пример внешнего store с selectors. Они не обязательны для формы из трёх полей и не заменяют автоматически кэш серверных данных.

Для подписки на внешнее хранилище React предоставляет useSyncExternalStore: он связывает чтение состояния с уведомлениями об изменениях. Для знакомства с Context собственное хранилище создавать не требуется. Пока данные не изменились, снимок состояния должен оставаться тем же; для SSR нужен согласованный снимок на сервере.

## Однонаправленный поток: Flux и Redux

Несколько экранов меняют общий выбор документов. Чтобы видеть причину изменения, интерфейс отправляет описание события — action. Store передаёт прежнее состояние и action чистому reducer; тот возвращает следующее состояние. Подписанные потребители читают нужную часть через selector. Получается цепочка: UI → dispatch(action) → reducer → state → UI.

Flux — подход с однонаправленным потоком данных. Redux развивает эти идеи: хранит состояние в едином store и описывает изменения через reducers. Устройство других реализаций Flux может отличаться.

```js
function selectionReducer(state = { ids: [] }, action) {
  if (action.type !== 'selection/added' || state.ids.includes(action.payload)) return state;
  return { ...state, ids: [...state.ids, action.payload] };
}
const before = { ids: [] };
const after = selectionReducer(before, { type: 'selection/added', payload: 'doc-7' });
const selectCount = state => state.ids.length;
selectCount(after); // 1; before.ids по-прежнему []
```

В примере показан переход состояния через reducer. Запрос выполняется отдельно, а подписка React сообщает компоненту, что выбранные данные изменились. Redux Toolkit помогает организовать эти действия и reducers. Если значение нужно только одному полю, его по-прежнему можно хранить локально.

## Проверка себя

Нужно ли хранить filteredUsers вместе с users и query? Должен ли выход из аккаунта очищать серверный кэш? Почему модульная переменная с текущим пользователем особенно опасна на сервере?

> [!question]- Разбор
>
> filteredUsers можно каждый раз получить из users и query, поэтому отдельная копия не нужна. Кэш API должен учитывать пользователя и организацию: при выходе его очищают или переключают так, чтобы следующий пользователь не увидел чужие данные. На сервере общая переменная опасна тем, что её могут прочитать разные запросы. Сначала реши, кому принадлежат данные и сколько они живут, затем выбирай место хранения.
