# Псевдонимы типов и интерфейсы

> [!summary]
> `type` и `interface` часто описывают похожие object shapes. В реальной работе важнее понимать их практические ограничения и выбрать единый стиль команды.

## Базовая модель

`interface` удобно читать как контракт объекта:

```ts
interface User {
  id: string;
  name: string;
  email?: string;
}
```

`type` задаёт имя любому типу: объекту, объединению, кортежу, функции или конкретному значению.

```ts
type UserId = string;
type Status = 'idle' | 'loading' | 'success' | 'error';
type Point = [number, number];
type User = {
  id: UserId;
  name: string;
};
```

## Практичная разница

| Ситуация | Что обычно выбрать |
|---|---|
| Описать объектный контракт модели или props | `interface` или `type`, по стилю проекта |
| Описать объединение, тип конкретного значения или кортеж | `type` |
| Преобразовать тип с помощью `Pick`, `Omit`, условных или отображаемых типов | `type` |
| Разрешить declaration merging | `interface` |
| Описать публичное API библиотеки, которое расширяют пользователи | часто `interface` |

## Расширение через `extends` и пересечение типов

**ID вопроса:** Extends и intersection

```ts
interface BaseUser {
  id: string;
}

interface AdminUser extends BaseUser {
  role: 'admin';
}

type WithTimestamps = {
  createdAt: string;
  updatedAt: string;
};

type StoredAdmin = AdminUser & WithTimestamps;
```

`extends` расширяет интерфейс свойствами другого интерфейса. Пересечение `&` описывает значение, которое должно соответствовать нескольким типам одновременно.

## Объединение объявлений

**ID вопроса:** Declaration merging

`interface` с одинаковым именем может объединяться:

```ts
interface Window {
  analytics?: {
    track(eventName: string): void;
  };
}
```

Это полезно для расширения глобальных типов и библиотек, но в прикладном коде может неожиданно скрыть конфликт имен.

## Частые ошибки

- Отвечать "`interface` всегда лучше" или "`type` всегда лучше".
- Пытаться описать объединение через `interface`: для этого нужен `type`.
- Думать, что `type` и `interface` появляются во время выполнения программы.
- Смешивать стили без причины в одном модуле.
- Злоупотреблять declaration merging в обычной бизнес-логике.

## Как ответить на собеседовании за одну минуту

И `type`, и `interface` могут описывать объект. `interface` хорош для объектных контрактов и объединения нескольких объявлений. `type` универсальнее: объединения типов, литералы, кортежи, отображаемые и условные типы. В приложении я обычно следую стилю команды: например, `interface` для моделей и props, `type` для объединений и производных типов. Главное - не считать их объектами или проверками, существующими во время выполнения.

## Вопросы для самопроверки

- Почему объединение можно описать через `type`, но не через `interface`?
- Когда declaration merging полезен, а когда опасен?
- Чем `extends` отличается от `&` на практическом уровне?

## Практические задачи

1. Опиши `interface User` и расширь его до `AdminUser`.
2. Опиши `type RequestStatus = ...` для статусов загрузки.
3. Собери `StoredUser` из `User` и timestamps.

> ```ts
> interface User {
>   id: string;

> }
>
> interface AdminUser extends User {
>   role: 'admin';
> }
>
> type RequestStatus = 'idle' | 'loading' | 'success' | 'error';
>
> type StoredUser = User & {
>   createdAt: string;
>   updatedAt: string;
> };
