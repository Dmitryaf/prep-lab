# API, unknown и проверка данных

> [!summary]
> Самая частая ошибка с API в TypeScript - поверить типу без проверки. Ответ сервера приходит во время выполнения программы, поэтому TypeScript может описать ожидаемый контракт, но не доказать, что JSON ему соответствует.

## Базовая модель

Внутри приложения типы полезны как контракт. На внешней границе данные сначала неизвестны:

```text
server JSON -> unknown -> runtime check -> typed domain model
```

## Типизация ответа API

```ts
type UserDto = {
  id: string;
  name: string;
  email?: string;
};

type ApiSuccess<T> = {
  ok: true;
  data: T;
};

type ApiFailure = {
  ok: false;
  error: string;
};

type ApiResult<T> = ApiSuccess<T> | ApiFailure;
```

## Type guard для внешних данных

```ts
function isUserDto(value: unknown): value is UserDto {
  return (
    typeof value === 'object' &&
    value !== null &&
    'id' in value &&
    typeof value.id === 'string' &&
    'name' in value &&
    typeof value.name === 'string' &&
    (!('email' in value) || typeof value.email === 'string')
  );
}
```

Необязательное поле тоже нужно проверять, если оно пришло. Этот guard предназначен для JSON: отсутствие `email` допустимо, строка допустима, `null` и число — нет. Явный `undefined` также отвергается; JSON его не передаёт. Type predicate — обещание автора функции, поэтому компилятор сам не обнаружит неполную проверку.

```ts
isUserDto({ id: '1', name: 'Ada' }); // true
isUserDto({ id: '1', name: 'Ada', email: 'ada@example.test' }); // true
isUserDto({ id: '1', name: 'Ada', email: 123 }); // false
isUserDto({ id: '1', name: 'Ada', email: null }); // false
```

## Загрузка с проверкой

```ts
async function loadUser(id: string): Promise<ApiResult<UserDto>> {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);

  if (!response.ok) {
    return { ok: false, error: `HTTP ${response.status}` };
  }

  const data: unknown = await response.json();

  if (!isUserDto(data)) {
    return { ok: false, error: 'Invalid user payload' };
  }

  return { ok: true, data };
}
```

Пример возвращает `ApiResult` для HTTP-ошибки и неверной структуры, но сетевой сбой или некорректный JSON по-прежнему отклоняют Promise. Вызывающий код должен обработать исключение. Если договорённость проекта — всегда возвращать `ApiResult`, эти ошибки нужно явно преобразовать в `ApiFailure` внутри функции; одна аннотация возвращаемого типа этого не делает.

## Type assertions

`as` говорит компилятору "поверь мне". Это не проверка:

```ts
const user = await response.json() as UserDto;
```

Так можно делать на контролируемых границах или после проверки, но опасно использовать как способ скрыть ошибку типизации.

## Библиотеки валидации

В больших проектах вместо ручных guards часто используют схемы: Zod, Valibot, io-ts и похожие инструменты. В этом проходе они оставлены как P1/P2-тема: для собеседования важнее объяснить саму границу `unknown -> validation -> typed value`.

## В собственных проектах

## Частые ошибки

- Типизировать `response.json()` как `User`, не проверяя фактические данные.
- Возвращать `null`/throw/error object вперемешку без единого `ApiResult`.
- Использовать `any` для API-данных и распространять его по приложению.
- Считать `as User` проверкой во время выполнения.
- Не учитывать `response.ok` и сетевые ошибки.

## Как ответить на собеседовании за одну минуту

Данные извне сначала считаю `unknown`: компилятор не видит JSON, который придёт по сети. Затем проверяю поля функцией проверки типа или валидатором схемы и только после этого использую данные как доменную модель. `as` — утверждение для компилятора, а не проверка во время выполнения. Результат API удобно описать объединением вариантов с общим отличительным полем `ok: true | false`.
