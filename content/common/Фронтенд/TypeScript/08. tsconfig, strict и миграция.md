# tsconfig, strict и миграция

> [!summary]
> `tsconfig.json` задает правила проверки и компиляции TypeScript-проекта. Для собеседования важнее понимать `strict`-семейство и стратегию миграции, чем помнить все опции.

## Базовая модель

`tsconfig.json` отвечает за:

- какие файлы входят в проект;
- какие JavaScript-возможности целить через `target`/`lib`;
- как резолвить модули;
- насколько строго проверять типы;
- генерировать ли JS, declaration files и source maps.

## Минимальный практичный пример

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "skipLibCheck": true,
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  },
  "include": ["src"]
}
```

## Важные опции

| Опция | Практический смысл |
|---|---|
| `strict` | включает набор строгих проверок |
| `noImplicitAny` | запрещает неявный `any`, если TS не смог вывести тип |
| `strictNullChecks` | заставляет учитывать `null` и `undefined` |
| `skipLibCheck` | пропускает проверку `.d.ts` зависимостей; ускоряет сборку, но может скрыть проблемы типов библиотек |
| `baseUrl`/`paths` | задают alias для импортов; должны быть согласованы со сборщиком |

## Типизация библиотек и `.d.ts`

Если библиотека написана на TS, типы часто идут внутри пакета. Если нет, могут понадобиться `@types/...` или свой `.d.ts`.

```ts
declare module 'legacy-widget' {
  export function mount(selector: string): void;
}
```

Такой файл описывает контракт для TypeScript, но не добавляет код, выполняемый в программе.

## Миграция JS -> TS

Практичный порядок:

1. Включить TS в сборку и начать с новых файлов.
2. Типизировать внешние границы: API, props, shared utils.
3. Включить `noImplicitAny`, затем двигаться к `strict`.
4. Заменять `any` на `unknown` там, где данные приходят извне.
5. Не пытаться переписать весь проект одним большим PR.

## Частые ошибки

- Включить alias в `tsconfig`, но забыть Vite/Webpack/Jest/Vitest.
- Отключить `strictNullChecks` и потерять важный класс ошибок.
- Делать `.d.ts` слишком широким через `any`.
- Думать, что `skipLibCheck` исправляет типы зависимостей.
- Мигрировать с массовым `as any`, после чего типизация почти не работает.

## Как ответить на собеседовании за одну минуту

`tsconfig` определяет, как TypeScript проверяет проект. Я стараюсь держать `strict: true`, особенно `noImplicitAny` и `strictNullChecks`. `skipLibCheck` может ускорить проект, но это компромисс. Path aliases нужно синхронизировать со сборщиком и тестами. При миграции я начинаю с границ и новых файлов, постепенно уменьшаю `any`, а внешние данные считаю `unknown`.

## Вопросы для самопроверки

- Что реально включает `strict`?
- Почему `strictNullChecks` важен для frontend?
- Зачем нужны `.d.ts`?
- Почему path aliases могут сломаться во время выполнения программы?

## Практические задачи

1. Объясни, зачем включать `noImplicitAny`.
2. Найди риск в проекте с `paths`, но без alias в Vite.
3. Напиши простой `.d.ts` для legacy-модуля.
