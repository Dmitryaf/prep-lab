# Производительность и тестирование Vue

> [!summary]
> Оптимизация Vue начинается с измерения: размер bundle, количество ререндеров, тяжелые списки, лишние зависимости и утечки. Тесты должны проверять поведение компонента, а не внутреннюю реализацию Vue.

## Базовая оптимизация

Практичные рычаги:

- отложенная загрузка маршрутов и тяжелых компонентов;
- стабильные `key` в списках;
- не хранить лишнее глобально;
- `computed` для производных значений;
- debounce/throttle для частых событий;
- virtual scrolling для больших списков;
- освобождение подписок и отмена запросов;
- code splitting и анализ bundle.

## Оптимизация списков

Если список большой:

- проверь, нужен ли весь список в DOM;
- используй pagination или virtualization;
- не используй index key для изменяемых списков;
- выноси тяжелые элементы в компоненты с понятными props;
- избегай создания новых объектов/functions в горячих местах без нужды.

## P1 Vue-инструменты

- `defineAsyncComponent` - асинхронные компоненты.
- `<Suspense>` - координация async setup, использовать осознанно.
- `<Teleport>` - рендер в другое место DOM, например modal в `body`.
- `<KeepAlive>` - кеширование component instances.
- `v-memo` - пропуск обновления subtree при стабильных зависимостях.
- `shallowRef` - меньше глубокой реактивности для больших структур.

## Memory leaks

Утечки часто появляются из-за:

- забытых глобальных listeners;
- таймеров;
- внешних subscriptions;
- незавершенных запросов;
- наблюдатели и области действия эффектов вне жизненного цикла компонента.

Подробнее про память смотри [[Фронтенд/JavaScript/10. Память и сборка мусора/03. Memory leaks во frontend|Memory leaks во frontend]].

## Тестирование компонентов

Vue Test Utils монтирует компонент и позволяет проверять поведение:

```ts
import { mount } from '@vue/test-utils';
import { describe, expect, it } from 'vitest';
import CounterButton from './CounterButton.vue';

describe('CounterButton', () => {
  it('increments count after click', async () => {
    const wrapper = mount(CounterButton);

    await wrapper.get('button').trigger('click');

    expect(wrapper.text()).toContain('1');
  });
});
```

Пример кнопки — минимальная проверка одного клика, а не стратегия покрытия компонента. Для формы нужны отправка, ошибка и сохранность ввода. Для composable проверяй публичное состояние и очистку ресурсов: [[Фронтенд/Инженерные основы/07. Тестирование/02. Проверка поиска с поздними ответами|Проверка поиска с поздними ответами]] содержит запускаемый пример. Управляемая подмена сети воспроизводит ошибки; отдельная проверка с сервером подтверждает настоящий контракт.

## Частые ошибки

- Оптимизировать без измерения.
- Использовать `v-memo` везде.
- Тестировать внутренние refs вместо observable behavior.
- Не ждать асинхронного обновления DOM через `await`.
- Смешивать unit и e2e цели в одном тесте.

## Как ответить на собеседовании за одну минуту

В Vue я сначала измеряю проблему: размер сборки, повторные рендеры, список, сеть или память. Потом применяю точечные техники: отложенную загрузку маршрутов, асинхронные компоненты, отображение только видимых строк, очистку ресурсов, `computed`, стабильные ключи, иногда `shallowRef` или `v-memo`. В тестах через Vue Test Utils и Vitest проверяю пользовательское поведение компонента и события, а composables - как обычную логику с реактивным состоянием.

- Почему `v-memo` не надо ставить везде?
- Что тестировать в компоненте: refs или поведение?

## Практические задачи

1. Объясни оптимизацию списка товаров.
2. Напиши тест для кнопки, которая emit-ит `save`.
3. Найди причину утечки в компоненте с `setInterval`.

> [!question]- Разбор
> Для большого списка сначала уменьши количество DOM-узлов: pagination или virtualization. `key` должен быть стабильным. Если элемент тяжелый, проверь props и лишние ререндеры. Для interval:
>
> ```ts
> const timerId = window.setInterval(sync, 1000);
> onUnmounted(() => window.clearInterval(timerId));
> ```
