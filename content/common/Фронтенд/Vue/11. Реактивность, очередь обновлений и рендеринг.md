# Реактивность, очередь обновлений и рендеринг

После присваивания значение уже новое, а DOM ещё может быть старым. Чтобы объяснить это, достаточно разделить три действия: изменение данных, планирование работы и обновление экрана.

## Путь от поля до экрана

```text
чтение ref/reactive при выполнении эффекта → запомнить зависимость
изменение зависимости → назначить нужную работу
очередь Vue → выполнить вычисления и обновление компонента
сравнение описания интерфейса → изменить DOM
браузер → layout/paint при необходимости
```

Эффект — выполняемый код, который зависит от реактивных значений. Чтения отслеживаются во время его выполнения. Планировщик Vue определяет момент запуска назначенной работы; это не отдельный поток. [Реактивность](https://vuejs.org/guide/extras/reactivity-in-depth), [термины Vue](https://vuejs.org/glossary/#scheduler).

## Предскажи вывод

Самостоятельный пример для Vue 3.5, выполняемый в ES-модуле с установленным `vue`:

```js
import { ref, computed, watch, nextTick } from 'vue';

const count = ref(0);
const doubled = computed(() => count.value * 2);
const events = [];
const stop = watch(count, (value, old) => events.push([old, value]));

count.value = 1;
count.value = 2;
console.log(count.value, doubled.value, events.length);
await nextTick();
console.log(JSON.stringify(events));
stop();
```

> [!question]- Вывод и причина
> Сначала `2 4 0`, затем массив с одной парой `[0, 2]`. Значение изменяется синхронно, computed при чтении даёт актуальный результат, обычный watcher группирует изменения одного синхронного участка. `flush: 'sync'` дал бы отдельные вызовы при присваиваниях. Это не означает, что любые изменения через любые `await` всегда объединяются.

`nextTick()` ждёт очередного завершения обновлений DOM Vue, но не гарантирует, что браузер уже нарисовал кадр. Для измерений отличай обновление DOM от появления изображения. [Vue: nextTick](https://vuejs.org/api/general.html#nexttick), [watchers](https://vuejs.org/guide/essentials/watchers.html).

## Почему компонент обновился

Компилятор превращает шаблон в функцию рендера. Её результат описывает дерево интерфейса; renderer монтирует его или обновляет существующее. Выполнение функции рендера не обязательно означает замену всех DOM-узлов. Компилятор помогает пропускать работу для статических частей. [Механизм рендеринга](https://vuejs.org/guide/extras/rendering-mechanism).

Учебный сбой: у строки есть локальное поле ввода, список сортируется, ключом служит индекс. Позиция осталась прежней, но запись на ней другая; состояние строки может оказаться у другого элемента. Ключ должен выражать устойчивую идентичность записи, например `row.id`. Он не должен меняться при каждом рендере. Проверка — отредактировать вторую строку, поменять порядок и проверить, к какому ID относится ввод.

## Что именно оптимизировать

| Наблюдение | Следующий вопрос |
|---|---|
| Родитель часто создаёт новые объекты props | Какие дочерние компоненты получают изменившиеся значения? |
| Computed каждый раз возвращает новый объект | Не меняется ли ссылка при неизменном смысле? |
| Тысячи строк одновременно в DOM | Можно ли показывать только нужную часть? |
| Deep watcher обходит большое дерево | Какая конкретная зависимость нужна сценарию? |

В Vue 3.4+ computed может не запускать зависимые эффекты при неизменном результате. Новый объект имеет другую идентичность. Но это не повод вручную кешировать всё: сначала найди дорогую работу. `shallowRef` требует обновлять корневую ссылку, если вложенное значение не реактивно. [Vue: performance](https://vuejs.org/guide/best-practices/performance).

## Store, composable или provide/inject

У формы заказа несколько вложенных полей. Ей нужен общий контекст регистрации полей: provider рядом с формой позволяет двум формам оставаться независимыми. Переиспользуемую реактивную логику можно оформить composable; место создания состояния определит, общее оно или отдельное. Pinia подходит, когда состояние и действия должны принадлежать общей области приложения и использоваться разными экранами. Ни одно название не делает данные сохранёнными на диске.

## Проверка понимания

1. Почему `await nextTick()` не лечит тяжёлую сортировку?
2. Почему изменение `key` сбрасывает локальное состояние, а стабильный ключ полезен при сортировке?
3. Две формы неожиданно делят ввод: где искать создание состояния?

> [!question]- Разбор
> Ожидание обновления не уменьшает объём вычислений. Новый ключ задаёт другую идентичность экземпляра; ключ по ID сохраняет связь с записью. Общее состояние может быть создано на уровне модуля, общего store или слишком высокого provider. Нужно проверить фактического владельца, а не переписать всё на другой API.

Для краткого ответа: «Изменение состояния и изменение DOM происходят не в один момент. Vue отслеживает зависимости, планирует обновления и сохраняет подходящие узлы. Я проверяю владельца состояния, идентичность строк и источник дорогой работы до оптимизации».
