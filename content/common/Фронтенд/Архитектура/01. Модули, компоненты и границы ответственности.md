# Модули, компоненты и границы ответственности

Архитектура начинается не со структуры папок, а с ответственности частей системы и направлений зависимостей.

## На простом сценарии

Пользователь нажал «Сохранить». Компонент показывает поля и ошибку; модель формы хранит ввод; действие сохранения применяет правила; слой хранения записывает результат. Разделение полезно, если можно изменить вид поля без переписывания хранения или проверить правило без запуска браузера.

По текущему коду можно установить границы, но историческое «почему автор выбрал так» требует записи решения. При её отсутствии объяснение преимущества — аргумент или гипотеза, а не восстановленный факт.

## Практическая модель

| Часть | Ответственность |
|---|---|
| App/shell | запуск, глобальные providers, routing, layouts |
| Page | сборка конкретного маршрута и orchestration сценария |
| Feature | законченное пользовательское действие |
| Domain/model | правила предметной области и преобразования |
| Data/API | транспорт, DTO, кэш и жизненный цикл запросов |
| Shared UI | переиспользуемое отображение без знания домена |
| Infrastructure | analytics, storage, monitoring, feature flags |

Это не обязательные названия каталогов. Важнее, чтобы верхние слои могли использовать нижние, а общий код не зависел от конкретной feature.

## Декомпозиция компонентов

Компонент стоит разделять, когда у частей появляются разные причины изменения, независимые состояния, сложные side effects или самостоятельная возможность тестирования.

Необязательно выносить компонент только из-за количества строк. Иногда один последовательный экран понятнее набора мелких обёрток.

## Container, UI и headless logic

- Компонент страницы связывает данные, доступные действия и проверку прав.
- UI-компонент получает явный контракт через props и события.
- Composable или headless-модель содержит реактивную логику без жёсткой разметки.
- Service работает с внешней системой и не становится скрытым store.

## Когда делать shared-компонент

Shared-компонент оправдан, когда повторяется стабильная концепция, а не только похожая разметка. Его API не должен содержать названия сущностей одного продукта или десятки флагов для несовместимых случаев.

## Trade-offs

- Feature-based организация держит сценарий рядом, но требует правил зависимостей.
- Технические слои проще в маленьком проекте, но размазывают большую feature.
- Раннее переиспользование создаёт сложный API.
- Чрезмерная декомпозиция увеличивает число переходов по коду.

## Проверочные вопросы

- Кто владеет состоянием?
- Где находится бизнес-правило?
- Знает ли UI формат backend DTO?
- Можно ли протестировать правило без монтирования страницы?
- Что изменится при появлении второго похожего сценария?
