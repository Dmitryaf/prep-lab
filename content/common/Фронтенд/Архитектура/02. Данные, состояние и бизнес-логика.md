# Данные, состояние и бизнес-логика

Чтобы выбрать место для состояния, сначала выясни, кто его читает и меняет и как долго оно должно жить. Открытое меню обычно достаточно хранить в компоненте, фильтр с возможностью поделиться ссылкой — в URL, а данные заказа с сервера — в слое запросов и кэша.

## Четыре значения, которые легко перепутать

Разделяй четыре значения: текущий ввод формы, сохранённый локальный черновик, принятую локальную запись и подтверждённую серверную версию. После ввода на экране уже новый текст, черновик может ещё ожидать записи, а сервер — хранить предыдущую версию. Это нормальное промежуточное состояние, если интерфейс показывает, какой этап действительно завершён.

## Виды состояния

| Вид | Типичное место |
|---|---|
| Локальное UI | component state |
| Черновик формы | component, form model или composable |
| URL state | route params и query |
| Shared client state | store |
| Server state | query/cache layer |
| Persistent preferences | storage с явной синхронизацией |
| Derived state | computed/selectors вместо копии |

## Как выбрать место

1. Кто читает и изменяет значение?
2. Должно ли оно пережить unmount или navigation?
3. Принадлежит ли истина backend?
4. Нужно ли состояние сериализовать в URL или storage?
5. Что инвалидирует значение?

Глобальный store оправдан для состояния, которое разделяют независимые части приложения или которое образует общий бизнес-процесс. Поле локальной формы не становится глобальным только потому, что используется несколькими дочерними компонентами.

## Где держать бизнес-логику

- UI-логика остаётся рядом с отображением.
- Переиспользуемая реактивная логика может жить в composable.
- Shared state и действия вокруг него — в store/model.
- Чистые бизнес-правила — в функциях domain/model layer.
- Интеграции с API, WebSocket и storage — в data/service layer.
- Критичные проверки прав и целостности повторяются на backend.

## Инварианты

Инвариант — правило, которое должно сохраняться при изменении данных. Например, отправленный заказ нельзя редактировать как черновик. Такое правило удобно вынести в отдельную функцию и проверить независимо от интерфейса: скрытая кнопка или случайный watcher не должны быть единственным местом проверки.

## Частые ошибки

- один store для API cache, форм и модалок;
- дублирование derived state;
- две независимые копии server data;
- composable с неявным singleton-состоянием;
- business rules внутри `disabled` или template condition;
- отсутствие очистки состояния при смене пользователя или контекста.

## Небольшая проверка

После изменения `form.title` надпись на экране обновилась. Какие ещё доказательства нужны, чтобы сказать «запись сохранена и доступна на другом устройстве»?

> [!question]- Разбор
> Новый текст на экране означает, что обновилось состояние формы. Дальше нужно дождаться успешной записи в хранилище и, если данные должны появиться на другом устройстве, подтверждения синхронизации с сервером. При ошибке оставляем ввод в форме, чтобы пользователь мог исправить его или повторить сохранение.
