# API, кэш и синхронизация данных

Data layer связывает UI с внешними источниками и управляет не только запросом, но и полным жизненным циклом данных.

## Простой пример

Открыли редактор, получили документ, начали менять текст, нажали «Сохранить». Пока запрос шёл, текст изменили ещё раз. Если безусловно заменить форму ответом сервера, последний ввод исчезнет. Значит, слой данных должен учитывать, **какую версию отправляли и что успело измениться после отправки**.

## Граница API

- низкоуровневый HTTP/WebSocket client;
- модули по сущностям или features;
- DTO и преобразование в frontend-модель;
- нормализация ошибок;
- query/cache layer;
- команды изменения данных.

Дополнительный repository нужен только тогда, когда действительно скрывает разные источники данных или важную доменную границу.

## BFF: серверный слой под конкретный интерфейс

Экран заказа собирает данные из трёх сервисов, а мобильному клиенту нужен другой состав ответа. Можно дать каждому интерфейсу свой серверный слой: он обращается к сервисам и формирует подходящий ответ. Это Backend for Frontend, или BFF.

Например, браузер запрашивает GET /order-summary/7, BFF получает заказ и сведения о доставке, затем возвращает согласованную модель экрана. Нужно определить таймаут, поведение при частичном отказе и доступ пользователя. Один запрос из браузера не устраняет внутренние отказы.

Обычный клиентский API-модуль работает в браузере; BFF выполняется на сервере. API gateway чаще решает общие задачи входа и маршрутизации, а BFF адаптирует контракт под интерфейс; конкретные продукты могут совмещать роли. Авторизация и бизнес-ограничения не исчезают на нижележащих сервисах.

Цена решения — дополнительный сервис, задержка, выпуск и сопровождение. Если API уже подходит единственному интерфейсу, отдельный BFF может не окупиться. SSR и BFF могут соседствовать, но серверная отрисовка не является обязательной частью этого паттерна.

Вопрос: [[Собеседования/Темы/Архитектура, производительность и тестирование#Когда нужен BFF и где проходит его ответственность?|выбор и границы BFF]].

## Состояния запроса

Сначала опиши, что увидит пользователь:

| Ситуация | Состояние интерфейса |
|---|---|
| Данных ещё нет, запрос идёт | Начальная загрузка |
| Старые данные показаны, запрашиваем новые | Фоновое обновление |
| Запрос успешен, записей нет | Пустой результат |
| Поле не прошло проверку | Ошибка рядом с полем, ввод сохранён |
| Доступ запрещён | Объяснение ограничения доступа |
| Ответ не пришёл | Ошибка сети; результат записи может быть неизвестен |

Частичные или устаревшие данные можно показывать, если их статус понятен. Один `loading` не передаёт эти различия.

## Конкурентные операции

- `AbortController` просит отменить запрос; уже выполненную запись на сервере он не откатывает.
- Номер запроса позволяет не принимать устаревший результат.
- Debounce ждёт паузу во вводе, throttle ограничивает частоту; они не решают конфликт версий.
- Объединение одинаковых запросов убирает лишнее чтение.
- Запрет повторного submit ограничивает действия этого UI, но не других клиентов.
- Очистка ресурсов завершает подписки, когда они больше не нужны.
- Идемпотентный контракт позволяет повторить команду без повторного эффекта, если принимающая сторона его поддерживает. См. [[Фронтенд/Инженерные основы/10. Данные и надёжность/02. Очереди, повторы и неопределённый результат|Очереди, повторы и неопределённый результат]].

## Cache

Кэш — сохранённый результат предыдущего чтения. Определи ключ (что именно прочитано и для какого пользователя), срок свежести и когда результат нужно обновить или удалить. Затем реши, что делать при повторном открытии и ошибке обновления. При смене пользователя нельзя показать персональные данные предыдущего. Кэш ускоряет чтение, но сам не знает, что источник уже изменился.

## Optimistic update

Optimistic update — показать предполагаемый успех до ответа сервера. Например, сразу отобразить отметку, сохранив возможность отмены при ошибке. Нужны признак незавершённой операции, предыдущее значение и согласование с фактическим ответом. Откат старого запроса не должен затереть более новое действие. Если цена ложного успеха велика, сначала дождись подтверждения и только потом показывай успех.

## Realtime и offline

После разрыва WebSocket нужно восстановить соединение и выяснить, какие изменения пропущены: например, перечитать актуальный снимок. Повторные события не должны давать повторный эффект, а порядок обработки должен соответствовать контракту. Offline-режим требует хранения неотправленных изменений, правил конфликта и понятного статуса «ещё не синхронизировано». Открытое соединение само по себе не доказывает актуальность данных.
