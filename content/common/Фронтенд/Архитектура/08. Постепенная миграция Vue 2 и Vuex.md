# Постепенная миграция Vue 2 и Vuex

Нужно обновлять приложение, пока пользователи продолжают работать. Поэтому единица миграции — проверяемый сценарий с понятным возвратом к прежнему поведению.

Учебный пример для требований Bnovo: панель бронирований на Vue 2.7, Vuex и старых компонентах. Это вымышленная система, не описание внутренних решений Bnovo и не утверждение о собственном опыте миграции Vue 2 → Vue 3.

## Сначала зафиксировать границы

Сценарий: открыть бронирование → изменить дату → сохранить → увидеть актуальную запись. Запиши обязательные поля, правила даты, права, запрос и поведение ошибки. Добавь проверки успешного сохранения, отказа, несохранённого ввода и прямого перехода по URL.

Составь список зависимостей: версия Vue, router, store, UI-библиотеки, плагины и сборка. Наличие Composition API в Vue 2.7 не превращает среду выполнения Vue 2 в Vue 3. Options API поддерживается в Vue 3: переписывание синтаксиса не обязано совпадать с обновлением платформы.

## Выбрать путь

| Условие | Подход | Цена |
|---|---|---|
| Зависимости совместимы с migration build | Проверить `@vue/compat`, исправлять предупреждения, переходить по компонентам | Временный режим совместимости и ограничения библиотек |
| Старая библиотека блокирует обновление | Отделить экран границей приложения/маршрута, сохранить явный контракт | Две сборки, интеграция навигации и состояния |
| Маленькое приложение, покрытые сценарии | Обновить целиком в проверяемой ветке | Более крупное изменение и риск пропущенного сценария |

`@vue/compat` — Vue 3 с настраиваемой совместимостью, а не гарантия поддержки любого Vue 2-кода. Сверь ограничения до выбора. [Migration build](https://v3-migration.vuejs.org/migration-build), [breaking changes](https://v3-migration.vuejs.org/breaking-changes/).

## Один вертикальный срез

1. Сохрани API сервиса бронирований; отдели преобразование DTO от компонента.
2. Перенеси один экран со всеми состояниями, включая ошибку и повторное открытие.
3. Проверь изменившиеся контракты компонентов: `v-model`, события, fallthrough-атрибуты и slots. Сравни поведение, а не только внешний вид.
4. Переведи связанный модуль Vuex в Pinia отдельно от остальных модулей, если это уменьшает риск.
5. Включи новый экран ограниченным переключателем и проверь путь возврата.

Vuex и Pinia могут временно сосуществовать. Но у одной сущности должен оставаться один владелец записи. Два независимых store с копиями бронирования создадут конфликт: сохранение в одном не обновит другой. Временный адаптер читает и меняет данные через действующего владельца; «синхронизация двумя watchers» быстро становится отдельной проблемой. [Миграция Vuex → Pinia](https://pinia.vuejs.org/cookbook/migration-vuex.html).

## Матрица совместимости

| Сочетание | Что проверить |
|---|---|
| Старый экран + текущий API | Прежние пользователи продолжают сохранять |
| Новый экран + текущий API | Полный сценарий работает без обязательного нового backend |
| Старый экран + расширенный API | Новые поля не ломают старого клиента |
| Откат экрана + уже записанные данные | Старый клиент способен прочитать результат новой версии |

Если последнее неверно, переключатель сам по себе не даёт безопасный откат. Нужна совместимая запись или отдельно согласованная миграция данных. Выпускать изменение формата данных одновременно с заменой UI без причины не стоит.

## Когда срез закончен

Все состояния сценария проверены; наблюдаемые ошибки можно связать с версией; установлен владелец данных; путь отката реален. Для временного адаптера названо условие удаления: последний потребитель старого интерфейса переведён и проверен. Без этого «временная» совместимость остаётся навсегда.

## Задание

После перевода формы на Pinia список в старом Vuex показывает старую дату. Предложи исправление на текущий релиз и конечную схему. Затем интервьюер добавляет: старый клиент обязан работать ещё месяц.

> [!question]- Разбор
> Найди общий источник записи и чтения. В текущем релизе используй явный адаптер к одному владельцу либо согласованное перечитывание после команды. В конечной схеме перенеси потребителей и убери второй путь. При месяце совместимости сохраняй старый контракт ответа/записи и проверяй обе версии. Не объявляй задержку UI доказательством потери записи.

Краткий ответ: «Сначала защищаю один сценарий и контракты, затем меняю реализацию небольшим срезом. Отдельно проверяю совместимость данных и возможность отката. Миграция закончена, когда удалены временные связи».
