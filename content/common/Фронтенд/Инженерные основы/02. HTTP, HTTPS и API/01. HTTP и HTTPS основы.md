# HTTP и HTTPS основы

> [!summary]
> HTTP — протокол обмена сообщениями между клиентом и сервером. Клиент отправляет запрос, сервер возвращает ответ. HTTPS добавляет защищённый TLS-канал под HTTP.

## Базовая модель

```http
GET /products/10 HTTP/1.1
Host: example.com
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60

{ "id": 10, "title": "Keyboard" }
```

Запрос содержит метод, путь, версию, заголовки и иногда тело. Ответ содержит статус, заголовки и иногда тело.

## Методы

| Метод | Типичный смысл | Важное свойство |
| --- | --- | --- |
| `GET` | получить ресурс | безопасный, обычно кэшируемый |
| `POST` | создать действие или ресурс | обычно неидемпотентный |
| `PUT` | заменить ресурс целиком | идемпотентный по смыслу |
| `PATCH` | частично изменить ресурс | зависит от API |
| `DELETE` | удалить ресурс | обычно идемпотентный |
| `OPTIONS` | узнать возможности | используется в предварительной проверке CORS |

Безопасный метод (`safe`) не запрашивает изменение состояния ресурса: журналирование на сервере при этом допустимо. Идемпотентный метод даёт тот же предполагаемый эффект при повторе одинакового запроса. Статус ответа при повторе может отличаться: повторный `DELETE` может вернуть `404`.

## Статусы

| Группа | Смысл | Примеры |
| --- | --- | --- |
| `2xx` | успех | `200`, `201`, `204` |
| `3xx` | перенаправление или работа с кэшем | `301`, `302`, `304` |
| `4xx` | ошибка клиента | `400`, `401`, `403`, `404`, `409` |
| `5xx` | ошибка сервера | `500`, `502`, `503` |

Важно для frontend: `fetch()` обычно не считает HTTP `404` или `500` rejected Promise. Подробно: [[Фронтенд/API браузера/05. Fetch, CORS и сетевые запросы/01. fetch и обработка ошибок|fetch и обработка ошибок]].

## Headers и cookies

Заголовки передают метаданные: формат тела, кэширование, авторизацию, cookie, CORS и политику безопасности.

Cookies передаются через `Set-Cookie` от сервера и `Cookie` в последующих запросах. В Core важно понимать cookies как часть HTTP/session/security. Browser API-аспект storage уже есть в [[Фронтенд/API браузера/04. Хранение данных в браузере/01. localStorage, sessionStorage и cookies|localStorage, sessionStorage и cookies]].

## Cache headers

Базовые заголовки:

| Заголовок | Для чего |
| --- | --- |
| `Cache-Control: max-age=...` | сколько секунд ответ считается свежим |
| `Cache-Control: no-store` | не сохранять ответ |
| `ETag` | идентификатор версии ресурса для проверки |
| `Last-Modified` | время изменения для проверки версии |
| `If-None-Match` | условный запрос с ETag |
| `If-Modified-Since` | условный запрос по времени изменения |

Если сохранённый ответ устарел, браузер может проверить версию и получить `304 Not Modified` без тела.

## Разбор: кэш после выпуска новой версии

Условия: HTML загружает `app.8f3a.js`; у новой сборки имя `app.9b21.js`. Личные данные приходят отдельно из `/api/me`.

| Ресурс | Выбранный заголовок | Почему |
| --- | --- | --- |
| JS/CSS с хешем содержимого в имени | `Cache-Control: public, max-age=31536000, immutable` | содержимое по этому URL больше не меняется |
| HTML | `Cache-Control: no-cache` и `ETag` | можно сохранить, но перед повторным использованием нужно проверить версию |
| `/api/me` | `Cache-Control: no-store` | в этом сценарии личный ответ не сохраняем в HTTP-кэш |

`no-cache` разрешает хранение и требует проверки перед использованием; `no-store` запрещает хранить ответ. `private` запрещает хранение в общем кэше, например CDN, но разрешает в личном кэше браузера. Поэтому `private` не заменяет `no-store` для чувствительных данных.

Повторное открытие HTML:

```http
GET / HTTP/1.1
If-None-Match: "html-v1"
```

Если версия та же, сервер возвращает `304` без тела, а кэш использует ранее сохранённое тело. Если вышла новая версия — `200` с новым HTML и новым `ETag`. Новый HTML ссылается на новое имя JS, поэтому старый JS не нужно принудительно очищать. При обычном `fetch` браузер сам обрабатывает проверку HTTP-кэша: не надо ожидать пустой `304` и вызывать на нём `json()`.

Старые файлы нельзя удалять сразу при выпуске: открытая вкладка может позже запросить старый динамический модуль. Порядок выпуска и диагностика: [[Собеседования/Практика/Диагностика#Инциденты клиентского приложения|Диагностика клиентского приложения]].

Если ответ зависит от языка из `Accept-Language`, нужен соответствующий `Vary`. Это разделяет варианты ответа в кэше, но не проверяет права пользователя. Персональные ответы не делаем общедоступными в CDN.

> [!important]
> Здесь разобран HTTP-кэш. Данные в Pinia, кэш библиотеки запросов и Cache Storage у Service Worker — отдельные механизмы. `no-store` не очистит уже сохранённый кэш приложения и не запретит собственному коду Service Worker явно сохранить ответ. При выходе очищай личные данные во всех используемых слоях.

## HTTPS

HTTPS — это HTTP, передаваемый внутри TLS-защищённого соединения. Он защищает HTTP path, query, headers, cookies и body от чтения и подмены на сетевом пути, но не скрывает весь сетевой metadata.

### Как устанавливается защищённое соединение

Для нового соединения браузеру нужен адрес сервера и транспорт. HTTP/1.1 и HTTP/2 обычно используют TCP и затем TLS; HTTP/3 использует QUIC поверх UDP с интегрированным TLS. Кэш DNS, уже открытое соединение и возобновление TLS могут сократить путь: это не обязательный полный цикл для каждого запроса.

В TLS-рукопожатии клиент и сервер согласуют параметры защиты и ключевой материал. Сервер предъявляет сертификат и доказывает владение соответствующим закрытым ключом. Браузер проверяет доверенную цепочку, имя сервера и срок действия; после успешного согласования прикладные данные шифруются и защищаются от незаметной подмены. Это проверка канала и сервера, а не прав пользователя на конкретный документ.

Например, сертификат для api.example.com не подходит для другого имени только потому, что он ещё действует. При отказе проверяют hostname, цепочку промежуточных сертификатов, сроки и часы устройства. Отключение проверки убирает гарантию доверия, а не исправляет ошибку настройки.

Прикладной HTTP path, query, headers и body защищены на сетевом пути, но сведения об IP и факте соединения остаются наблюдаемыми. HTTPS также не устраняет XSS, утечки в логах приложения или неверную авторизацию на сервере.

> [!question]- Самопроверка: сертификат верен, но API отвечает 403
>
> TLS уже позволил установить защищённый канал. 403 — прикладной отказ HTTP: нужно проверять сессию, право на действие и объект, а не отключать TLS-проверки. И наоборот, при ошибке сертификата доверенный HTTP-ответ ещё не получен.

## HTTP versions

Для собеседования достаточно:

- HTTP/1.1 — текстовая модель сообщений, persistent connections;
- HTTP/2 — бинарные frames, multiplexing нескольких streams в одном соединении;
- HTTP/3 — работает поверх QUIC/UDP, детали обычно P2 для frontend.

> [!note]- Углубление: HTTP semantics
> Версии HTTP меняют транспортные детали и framing, но базовая семантика request/response, methods, status codes и headers остаётся узнаваемой для frontend-разработчика.

## Частые ошибки

- Считать, что `POST` всегда "безопаснее" `GET`.
- Путать `401` и `403`: сначала про отсутствие/невалидность authentication, второе про недостаток прав.
- Кэшировать персональные responses как public.
- Говорить, что HTTPS скрывает домен, IP и факт соединения.
- Объяснять CORS как серверную авторизацию. CORS — browser permission на чтение response.

## Как ответить на собеседовании за одну минуту

HTTP связывает клиент и сервер: запрос содержит метод, путь и заголовки, ответ — статус и заголовки; у обоих может быть тело. Метод описывает намерение, статус — результат. Заголовки управляют форматом, кэшем и доступом. HTTPS защищает содержимое HTTP с помощью TLS. Для интерфейса нужно проверять статус ответа и выбирать кэширование по типу данных.

## Практическая задача

Как кэшировать `app.8f3a.js` и `/api/me`?

> [!question]- Разбор
> Для файла с хешем — долгий срок и `immutable`, при условии неизменного содержимого по URL. Для `/api/me` в выбранном сценарии — `no-store`. `private` разрешает личное хранение и требует отдельного решения о сроке и чувствительности. Для HTML — проверка версии через `no-cache` и `ETag`.
