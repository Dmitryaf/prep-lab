# REST, GraphQL и WebSocket

> [!summary]
> Для чтения и изменения данных клиенту нужен понятный API. REST обычно организует его вокруг ресурсов, GraphQL позволяет описать нужные поля, а WebSocket поддерживает обмен сообщениями по постоянному соединению.

## REST

В RESTful API адрес обычно обозначает ресурс, а HTTP-метод — действие с ним. Например, по адресу заказа можно получить его данные через GET или удалить заказ через DELETE:

```text
GET    /users
GET    /users/42
POST   /users
PATCH  /users/42
DELETE /users/42
```

REST удобно использовать для обычных операций с ресурсами: чтения, создания, изменения и удаления. Здесь естественно применяются статусы, заголовки и кэширование HTTP.

Иногда ответ содержит больше данных, чем нужно экрану — это over-fetching. Бывает и наоборот: одного ответа не хватает, и приходится делать дополнительные запросы — under-fetching.

## GraphQL

GraphQL даёт клиенту язык запроса: клиент описывает, какие поля нужны.

```graphql
query {
  user(id: "42") {
    id
    name
    avatarUrl
  }
}
```

Плюсы: точное описание полей ответа, удобно для сложных экранов и разных клиентов.

На сервере нужно контролировать доступ к запрашиваемым полям и стоимость запроса: клиент может запросить слишком много вложенных данных. Кэширование и диагностика также требуют отдельной настройки.

## WebSocket

WebSocket создаёт постоянное двустороннее соединение. Подходит для чатов, live dashboards, совместного редактирования, игр и realtime-событий.

```js
const socket = new WebSocket('wss://example.com/feed');

socket.addEventListener('message', (event) => {
  console.log(event.data);
});
```

Недостатки: нужно заново устанавливать оборванное соединение, ограничивать поток сообщений, обновлять авторизацию и продумывать масштабирование и запасной способ связи.

## Как выбрать

| Сценарий | Подход |
| --- | --- |
| CRUD и обычные страницы | REST |
| Сложные экраны с разным набором полей | GraphQL |
| Двусторонний realtime | WebSocket |
| Односторонние server events | SSE, если подходит |
| Простая периодическая актуализация | polling/long polling может быть достаточно |

## Частые ошибки

- Выбирать GraphQL только потому, что он "современнее".
- Использовать WebSocket для редких событий, где достаточно polling.
- Игнорировать HTTP cache в REST.
- Считать GraphQL заменой авторизации.
- Не продумывать reconnect и повторную подписку в WebSocket.

## Как ответить на собеседовании за одну минуту

Для обычного каталога или формы я бы начал с REST: ресурсы имеют понятные адреса, а чтение и изменение выражаются HTTP-методами. GraphQL удобен, когда разным экранам нужны разные наборы связанных полей: клиент описывает их в запросе, а сервер проверяет права и ограничивает стоимость выполнения. WebSocket подходит для постоянного двустороннего обмена, например чата. Для него нужно также восстановление после разрыва и обновление авторизации. Если события редкие, может хватить периодического запроса.
