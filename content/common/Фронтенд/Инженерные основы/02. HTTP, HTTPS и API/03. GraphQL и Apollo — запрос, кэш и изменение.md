# GraphQL и Apollo — запрос, кэш и изменение

GraphQL описывает, какие данные запрашиваются и по какой схеме. Apollo Client помогает выполнять операции и хранить результаты. Чтобы понять экран, нужно различать серверную схему, экземпляр клиента, кэш и локальную форму.

## Одна операция

Учебная схема предполагает поле `booking(id: ID!)` с `id`, `status`, `guestName`. Этот контракт придуман для примера.

```graphql
query Booking($id: ID!) {
  booking(id: $id) {
    id
    status
    guestName
  }
}
```

Имя операции помогает диагностике, переменная передаёт значение отдельно от текста запроса. Query читает, mutation запрашивает изменение. Сгенерированный TypeScript-тип описывает ожидаемую форму, но не выполняет серверную авторизацию и не подтверждает успешный бизнес-результат.

Фрагмент `setup` при уже настроенном Apollo provider и существующей схеме:

```ts
import { ref } from 'vue';
import { useQuery } from '@vue/apollo-composable';
import gql from 'graphql-tag';

const bookingId = ref('b-1');
const { result, loading, error, refetch } = useQuery(
  gql`query Booking($id: ID!) { booking(id: $id) { id status guestName } }`,
  () => ({ id: bookingId.value }),
  { fetchPolicy: 'cache-and-network', errorPolicy: 'all' },
);
```

`result` сначала может отсутствовать. Политика `cache-and-network` допускает результат из кэша и последующий сетевой ответ; нельзя обещать, что первое показанное значение самое свежее. С `errorPolicy: 'all'` UI должен рассматривать данные и ошибку совместно. Это фрагмент использования API, не полный запускаемый проект. [Vue Apollo: useQuery](https://apollo.vuejs.org/api/use-query).

## Почему HTTP 200 недостаточно

Ответ GraphQL может содержать `data` и `errors` вместе. Например, данные бронирования получены, а связанная статистика недоступна. Реши, можно ли показать полезную часть и где объяснить ошибку. Отдельно различай сетевой сбой, ошибку GraphQL и доменный отказ, который схема может вернуть обычными данными. [Формат ответа GraphQL](https://graphql.org/learn/response/).

Повтор mutation после timeout может повторить действие. Нужен контракт принимающего сервиса: ключ идемпотентности или проверка результата. Автоматический retry чтения и команды оплаты — разные решения. См. [[Фронтенд/Инженерные основы/10. Данные и надёжность/02. Очереди, повторы и неопределённый результат|Очереди, повторы и неопределённый результат]].

## Кэш: сущность и список — разные вещи

Нормализованный кэш может хранить объект отдельно, а в результатах запросов — ссылки на него. Ключ объекта зависит от настроек идентичности, обычно типа и ID. Если ID уникален лишь внутри организации, это должно учитываться. [Apollo: cache configuration](https://www.apollographql.com/docs/react/caching/cache-configuration).

Пример проблемы: mutation вернула обновлённое бронирование, но список «активные» всё ещё содержит отменённое. Обновление полей объекта не обязательно меняет состав всех списков. Выбери явный способ: перечитать нужный запрос либо корректно обновить конкретные поля списка. Первый проще и требует сети; второй быстрее, но переносит правила членства в клиентский код.

При выходе и смене пользователя нельзя оставить доступ к персональному кэшу прежней сессии. Отмена фоновых запросов, очистка кэша и изменение авторизации должны составлять согласованный сценарий, иначе поздний ответ снова добавит старые данные.

## Пагинация и ключ списка

Пусть список зависит от `tenantId`, `filter` и `after`. Организация и фильтр различают наборы; курсор выбирает следующую часть того же набора. Политики `keyArgs` и `merge` должны отражать это различие. `keyArgs: false` без учёта фильтра может склеить разные списки. `fetchMore` сам по себе не доказывает правильную сборку страниц. [Apollo: key arguments](https://www.apollographql.com/docs/react/pagination/key-args).

Учебная функция объединяет элементы уже одного и того же набора. Она не заменяет политику Apollo, не проверяет курсоры и предполагает уникальные ID внутри набора:

```js
function mergeItems(existing, incoming) {
  const byId = new Map(existing.map(item => [item.id, item]));
  for (const item of incoming) byId.set(item.id, item);
  return [...byId.values()];
}
```

Задание: пришла страница для фильтра A, пользователь уже выбрал B. Можно ли вызвать `mergeItems` с текущим списком? Что произойдёт, если повторно придёт та же страница?

> [!question]- Разбор
> Сначала проверь идентичность запроса: организация, фильтр и нужная последовательность страниц. Для другого набора объединение недопустимо. Внутри одного набора повторные ID не дублируются, новое значение заменяет прежнее, существующая позиция сохраняется. Но функция не исправляет неправильный порядок страниц и не узнаёт об удалённых сервером элементах.

## Что проверить на интервью

Объясни путь от переменной запроса до отображения, частичный ответ, изменение объекта и состава списка, смену фильтра и повтор команды после timeout. Для каждого назови ожидаемое состояние UI и проверку. Слова «Apollo всё кеширует» недостаточно.
