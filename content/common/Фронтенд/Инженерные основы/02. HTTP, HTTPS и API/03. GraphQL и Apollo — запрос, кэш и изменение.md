# GraphQL и Apollo — запрос, кэш и изменение

С GraphQL клиент перечисляет нужные поля, а сервер проверяет запрос по своей схеме и возвращает результат. Apollo Client отправляет эти операции и сохраняет данные в кэше. Например, экран бронирования может получить из кэша имя гостя, запросить свежие данные и отдельно хранить ещё не сохранённые правки формы.

## Одна операция

В примере серверная схема предоставляет поле `booking(id: ID!)` с `id`, `status`, `guestName`.

```graphql
query Booking($id: ID!) {
  booking(id: $id) {
    id
    status
    guestName
  }
}
```

По имени операции удобно найти запрос в журнале или инструментах разработчика. Переменные передают значения отдельно от текста запроса. Query используют для чтения, mutation — для изменения. Сгенерированные TypeScript-типы помогают обращаться к полям ответа, а права пользователя и результат самого действия всё равно проверяются при выполнении запроса.

Фрагмент `setup` при уже настроенном Apollo provider и существующей схеме:

```ts
import { ref } from 'vue';
import { useQuery } from '@vue/apollo-composable';
import gql from 'graphql-tag';

const bookingId = ref('b-1');
const { result, loading, error, refetch } = useQuery(
  gql`query Booking($id: ID!) { booking(id: $id) { id status guestName } }`,
  () => ({ id: bookingId.value }),
  { fetchPolicy: 'cache-and-network', errorPolicy: 'all' },
);
```

`result` сначала может отсутствовать. Политика `cache-and-network` допускает результат из кэша и последующий сетевой ответ; нельзя обещать, что первое показанное значение самое свежее. С `errorPolicy: 'all'` UI должен рассматривать данные и ошибку совместно. [Vue Apollo: useQuery](https://apollo.vuejs.org/api/use-query).

## Почему HTTP 200 недостаточно

Ответ GraphQL может содержать `data` и `errors` вместе. Например, данные бронирования получены, а связанная статистика недоступна. Реши, можно ли показать полезную часть и где объяснить ошибку. Отдельно различай сетевой сбой, ошибку GraphQL и доменный отказ, который схема может вернуть обычными данными. [Формат ответа GraphQL](https://graphql.org/learn/response/).

Повтор операции `mutation` после тайм-аута может снова выполнить действие. На принимающей стороне нужен ключ идемпотентности или способ узнать результат операции. Повторное чтение данных и повтор команды оплаты требуют разных решений. См. [[Фронтенд/Инженерные основы/10. Данные и надёжность/02. Очереди, повторы и неопределённый результат|Очереди, повторы и неопределённый результат]].

## Кэш: сущность и список — разные вещи

Нормализованный кэш может хранить объект отдельно, а в результатах запросов — ссылки на него. Ключ объекта зависит от настроек идентичности, обычно типа и ID. Если ID уникален лишь внутри организации, это должно учитываться. [Apollo: cache configuration](https://www.apollographql.com/docs/react/caching/cache-configuration).

Пример проблемы: mutation вернула обновлённое бронирование, но список «активные» всё ещё содержит отменённое. Обновление полей объекта не обязательно меняет состав всех списков. Выбери явный способ: перечитать нужный запрос либо корректно обновить конкретные поля списка. Первый проще и требует сети; второй быстрее, но переносит правила членства в клиентский код.

При выходе и смене пользователя нельзя оставить доступ к персональному кэшу прежней сессии. Отмена фоновых запросов, очистка кэша и изменение авторизации должны составлять согласованный сценарий, иначе поздний ответ снова добавит старые данные.

## Пагинация и ключ списка

Пусть список зависит от `tenantId`, `filter` и `after`. Организация и фильтр различают наборы; курсор выбирает следующую часть того же набора. Политики `keyArgs` и `merge` должны отражать это различие. `keyArgs: false` без учёта фильтра может склеить разные списки. [Apollo: key arguments](https://www.apollographql.com/docs/react/pagination/key-args).

Функция объединяет страницы одного набора по уникальному ID. Выбор набора и порядок курсоров проверяются до её вызова:

```js
function mergeItems(existing, incoming) {
  const byId = new Map(existing.map(item => [item.id, item]));
  for (const item of incoming) byId.set(item.id, item);
  return [...byId.values()];
}
```

Задание: пришла страница для фильтра A, пользователь уже выбрал B. Можно ли вызвать `mergeItems` с текущим списком? Что произойдёт, если повторно придёт та же страница?

> [!question]- Разбор
> Ответ для фильтра A нельзя добавлять к текущему списку B. Перед объединением проверяем организацию, фильтр и порядок страниц. Для одного и того же набора функция уберёт повторные ID: обновит значение уже известного элемента, сохранив его позицию. Порядок страниц и удалённые на сервере элементы она не определяет — это нужно учесть отдельно.

## Что проверить на интервью

Проследи один запрос: от значения переменной до данных на экране. Затем разбери частичный ответ, изменение бронирования и списка, смену фильтра и повтор команды после тайм-аута. В каждом случае объясни, что увидит пользователь и как проверить это поведение.
