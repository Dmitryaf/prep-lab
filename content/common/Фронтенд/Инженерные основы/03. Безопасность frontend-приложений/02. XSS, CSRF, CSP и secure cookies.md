# XSS, CSRF, CSP и secure cookies

> [!summary]
> Безопасность клиентской части начинается с понимания границ браузерной защиты. Разработчик должен отдельно продумать вставку HTML, передачу cookie, запросы, меняющие данные, настройки CORS и защитные HTTP-заголовки.

## XSS

XSS — уязвимость, при которой атакующий добивается выполнения нежелательного JavaScript в контексте сайта.

Типичный источник:

```js
comment.innerHTML = userInput;
```

Если ввод не очищен и вставляется как HTML, атакующий может внедрить dangerous markup/script vector.

Защита:

- не вставлять untrusted data через `innerHTML`;
- использовать `textContent` для текста;
- делать context-aware escaping/sanitization;
- использовать проверенные sanitizers;
- включать CSP как дополнительный слой.

## CSRF

CSRF — атака, при которой сайт атакующего заставляет браузер пользователя отправить запрос на другой сайт, где пользователь уже авторизован cookies.

Особенно важно защищать запросы, изменяющие данные: перевод денег, смену электронной почты, удаление записи.

Защита:

- `SameSite` cookies;
- CSRF token;
- проверка `Origin`/`Referer` на сервере;
- не использовать `GET` для изменения состояния;
- дополнительная re-authentication для критичных действий.

## CSP

Content Security Policy (CSP) — защитный HTTP-заголовок, который ограничивает загрузку и выполнение скриптов, стилей, изображений и других ресурсов страницы.

Пример идеи:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

CSP не заменяет исправление XSS, но уменьшает blast radius.

## Secure cookies

| Атрибут | Зачем |
| --- | --- |
| `HttpOnly` | JS не может прочитать cookie |
| `Secure` | cookie отправляется только по HTTPS |
| `SameSite` | ограничивает cross-site отправку |
| `Path`/`Domain` | ограничивают область cookie |
| `Max-Age`/`Expires` | срок жизни |

`SameSite=Lax` часто хороший default, но требования зависят от flow. `SameSite=None` требует `Secure`.

## CORS как смежная тема

CORS не защищает от XSS и не является серверной авторизацией. Он говорит браузеру, можно ли JavaScript-коду одного источника прочитать ответ другого источника. Подробно: [[Фронтенд/API браузера/05. Fetch, CORS и сетевые запросы/02. Same-origin policy, CORS и preflight|Same-origin policy, CORS и preflight]].

## Можно ли безопасно подключить чужой скрипт

Если добавить сторонний `<script>` прямо на страницу, его код выполняется в контексте приложения. Он может читать DOM и доступные JavaScript хранилища. `HttpOnly` запрещает чтение конкретной cookie, но не запрещает скрипту действовать от имени страницы.

Поэтому первый вопрос — действительно ли виджету нужен доступ ко всей странице. Если нет, запускай его в отдельном iframe с минимальными разрешениями:

```html
<iframe
  src="https://widget.example.net/"
  sandbox="allow-scripts"
  title="Внешний виджет"
></iframe>
```

Адрес — пример отдельного сервиса. Такой sandbox разрешает скрипты, но не даёт обычный origin и доступ к данным родителя. Виджету могут потребоваться дополнительные возможности; каждую разрешают по конкретной необходимости. Не передавай ему токен приложения и весь профиль ради одной функции.

CSP помогает ограничить загрузку и выполнение кода, но разрешённый ею скрипт на основной странице не становится изолированным. Если коду нужен полный доступ к приложению, это уже доверенная зависимость: проверяют поставщика, версию и возможность отключения.

> [!note]- Если попросят подробнее: сообщения и ограничения sandbox
>
> Обмен через postMessage требует узкого набора команд и проверки данных. Для обычного отдельного origin проверяют точный origin и `event.source`. У iframe без allow-same-origin origin непрозрачный и в сообщении может быть `"null"`: одного сравнения с `"null"` недостаточно, нужны привязка к конкретному окну и согласованный канал. Не добавляй allow-same-origin только ради удобства проверки; особенно опасна его комбинация с allow-scripts для содержимого того же origin, что родитель.
>
> Iframe не гарантирует ограничение CPU или сетевых обращений виджета. Изоляцию доступа к данным, доступные разрешения и расход ресурсов нужно оценивать отдельно.

См. [разрешения iframe и sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

## Как защитить данные от массового сбора

Скрыть API-адрес или обфусцировать JavaScript недостаточно: клиент получает данные, а запрос можно повторить. Для непубличных данных сервер проверяет права; для массового сбора вводят серверные лимиты, контроль аномалий и ограничение объёма выдачи. CAPTCHA — дополнительная мера с ценой для пользователя.

Если информация открыто доступна любому посетителю, полностью запретить её копирование нельзя. На интервью сначала уточни, защищаем ли закрытые данные или ограничиваем массовое использование публичного сервиса.

## Частые ошибки

- Считать `innerHTML` безопасным, если данные "пришли с нашего API".
- Думать, что `HttpOnly` защищает от CSRF.
- Думать, что CORS защищает сервер от запросов.
- Хранить токен в JS-доступном месте и не иметь понимания, как злоумышленник может выполнить JavaScript на странице.
- Использовать CSP как единственную защиту.

## Как ответить на собеседовании за одну минуту

XSS — это выполнение чужого JavaScript в контексте сайта; клиентская часть снижает риск через безопасную вставку данных, экранирование текста и очистку разрешённого HTML и CSP. CSRF — это нежелательный запрос от браузера авторизованного пользователя, особенно при авторизации через cookie; защита — SameSite, CSRF-токены, проверка Origin/Referer и правильные методы HTTP. Для защищённых cookie настраивают `HttpOnly`, `Secure`, `SameSite`, `Path`, `Domain` и срок жизни. CORS — отдельный механизм браузера, определяющий, можно ли читать ответы другого источника, а не авторизация и не защита от XSS.

## Практическая задача

Cookie session использует `SameSite=None; Secure`. Что обязательно проверить?

> [!question]- Разбор
> Проверить, действительно ли нужен обмен cookie между разными сайтами; включён ли HTTPS; есть ли защита от CSRF для запросов, изменяющих данные; корректно ли настроены CORS credentials, если запросы идут к другому источнику; нет ли лишне широкого `Domain`.
