# Core Web Vitals и загрузка frontend-приложения

> [!summary]
> Производительность интерфейса — это не только «меньше JavaScript». Нужно быстро показать важный контент, быстро реагировать на ввод и не сдвигать интерфейс во время загрузки.

## Core Web Vitals

| Метрика | Что показывает | Типичные причины проблем |
| --- | --- | --- |
| LCP | когда появился крупнейший видимый контент | медленный ответ сервера, тяжёлые изображения, блокирующие отображение CSS/JS |
| INP | задержка реакции страницы на взаимодействия | долгая работа JavaScript, тяжёлые обработчики, принудительный расчёт геометрии |
| CLS | визуальная стабильность | изображения без размеров, поздняя реклама, загрузка шрифтов, вставки сверху |

Это метрики пользовательского опыта. Их нужно связывать с реальными причинами, а не просто запоминать названия.

## Измерение в лаборатории и у пользователей

Лабораторный прогон (например, Lighthouse) воспроизводим и помогает найти причину. Полевые данные — измерения на настоящих устройствах при настоящих сценариях, через CrUX или собственный сбор метрик (RUM). Сопоставляй лабораторный результат с данными пользователей на разных устройствах. Обычный прогон Lighthouse без взаимодействий не измеряет реальный INP; TBT может указать на блокировки, но не заменяет INP.

Ориентиры хорошего качества: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Оценивают 75-й процентиль отдельно для мобильных и настольных устройств: как минимум 75% наблюдений должны укладываться в порог. Не смешивай среднее значение с процентилем.

Учебный случай, числа вымышлены: на ноутбуке LCP 1,4 с, а у мобильных пользователей p75 — 3,6 с. Картинка обнаруживается только после загрузки JS. Проверяем цепочку запросов при замедленных сети и процессоре; делаем картинку доступной из HTML, подбираем размер, убираем ненужную отложенную загрузку. Затем повторяем лабораторный сценарий и сравниваем полевые данные после выпуска на сопоставимой аудитории и периоде. Смена аудитории сама может изменить результат.

Для INP ищем медленное взаимодействие: задержку до обработчика, выполнение обработчика и время до следующей отрисовки. Один вызов `performance.now()` вокруг обработчика не измеряет всю задержку. Практика с таблицей и вводом: [[Фронтенд/Инженерные основы/04. Производительность/03. Практическая диагностика таблицы, ввода и памяти|Практическая диагностика таблицы, ввода и памяти]].

## Загрузка страницы

Упрощённая цепочка:

```text
HTML -> critical CSS -> JS -> data -> images/fonts -> interactive UI
```

Что часто помогает:

- уменьшить JavaScript, необходимый при первом открытии;
- разделить код по страницам и возможностям;
- отложить необязательные скрипты;
- оптимизировать изображения и шрифты;
- настроить HTTP-кэш и CDN;
- не блокировать основной поток тяжёлой работой.
- браузеру можно задать приоритеты по загрузке контента. Preload, prefetch, preconnect

## Bundle size, code splitting и lazy loading

Размер сборки влияет на время загрузки, разбора и выполнения кода.

Разделение кода (code splitting) позволяет не загружать всё сразу. Отложенная загрузка (lazy loading) получает код или ресурсы только при необходимости.

```js
const SettingsPage = () => import('./SettingsPage.js');
```

Слишком мелкие части увеличивают число запросов и служебные расходы; размер выбирают по измерениям.

## Image optimization

Практические правила:

- задавать `width` и `height` или стабильное соотношение сторон;
- использовать современные форматы, если подходят;
- отдавать изображения нужного размера;
- откладывать загрузку некритичных изображений;
- предварительно загружать только действительно критичное LCP-изображение.

## Частые ошибки

- Оптимизировать только Lighthouse score, не понимая пользовательский сценарий.
- Делать lazy loading для LCP-изображения.
- Загружать огромный vendor bundle на каждой странице.
- Не задавать размеры изображений и получать CLS.
- Считать, что SSR автоматически решает performance.

## Как ответить на собеседовании за одну минуту

Начинаю со сценария и измерения: медленно появляется контент, задерживается ввод или сдвигается экран? LCP, INP и CLS помогают разделить эти проблемы. В лаборатории ищу причину, по данным пользователей проверяю масштаб и эффект выпуска. Выбираю точечное изменение: загрузка ресурсов, разделение кода, кэш, сокращение работы основного потока или расчётов геометрии. Не считаю один хороший прогон доказательством качества для всех.

## Практическая задача

Главная картинка hero часто становится LCP и грузится поздно. Что проверить?

> [!question]- Разбор
> Проверить размер и формат изображения, выбор подходящего размера для экрана, приоритет загрузки и время ответа сервера/CDN. Главную картинку, влияющую на LCP, обычно не следует загружать отложенно. Затем проверить заголовки кэширования, CSS и JavaScript, задерживающие отображение, и не скрыта ли картинка до выполнения JavaScript.
