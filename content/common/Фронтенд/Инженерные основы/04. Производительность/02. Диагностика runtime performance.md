# Диагностика runtime performance

## Зачем это знать

Производительность работающего приложения исследуют, когда страница уже загрузилась, но интерфейс тормозит: ввод запаздывает, фильтры подвисают, скролл дергается, таблица долго реагирует на действия пользователя.

На собеседовании важно показать не набор случайных оптимизаций, а диагностический подход: сначала воспроизвести проблему, измерить, отделить JavaScript от расчёта геометрии и отрисовки и только потом менять код.

## Базовая модель

Упрощенно тормоза во время работы приложения обычно лежат в одном из слоев:

- **scripting** - долгие вычисления, сортировки, фильтры, парсинг, тяжелые обработчики событий;
- **расчёт геометрии и отрисовка** — слишком много DOM-узлов, принудительные синхронные пересчёты размеров, дорогие стили и частые изменения геометрии;
- **framework rerendering** - лишние обновления компонентов, нестабильные props, тяжелые computed/watch;
- **data flow** - слишком большой объем данных на клиенте, отсутствие пагинации или виртуализации.

Chrome DevTools Performance помогает увидеть, где уходит время: в JavaScript, расчёт геометрии, перерисовку, сборку слоёв, долгие задачи или обработчики событий.

## Как это встречается в работе

Типичные симптомы:

- поле поиска тормозит на каждом символе;
- большая таблица зависает при сортировке или фильтрации;
- список из тысяч элементов медленно скроллится;
- открытие модального окна вызывает заметный freeze;
- пользовательский input попадает в длинную задачу main thread.

Для большого списка не стоит сразу "оптимизировать Vue/React". Сначала нужно понять, что дороже: вычисления, количество DOM-узлов, перерендеры компонентов или сама стратегия загрузки данных.

## Как диагностировать

Базовый порядок:

1. Воспроизвести конкретный сценарий: ввод, скролл, открытие экрана, сортировка.
2. Записать сценарий в Chrome DevTools Performance.
3. Посмотреть загрузку основного потока, долгие задачи и распределение времени между выполнением JavaScript, расчётом геометрии и отрисовкой.
4. Если проблема в JS - открыть call tree/bottom-up и найти дорогую функцию.
5. Если проблема в отрисовке - проверить количество DOM-узлов, принудительные синхронные пересчёты размеров и частые изменения стилей.
6. Если приложение framework-specific - дополнительно открыть Vue Devtools/React Profiler.
7. Проверить гипотезу маленьким изменением и снова измерить.

Для загрузочных проблем дополнительно смотреть Lighthouse, Network, WebPageTest и Core Web Vitals. Но для задержек в работающем интерфейсе запись во вкладке Performance обычно полезнее одной итоговой оценки Lighthouse.

## Как диагностировать рывки анимации на телефоне

На компьютере выдвижная панель движется плавно, а на телефоне останавливается и перескакивает. Задача — найти работу, из-за которой браузер не успевает показать очередное состояние. Более медленное устройство — условие проявления, но ещё не причина в коде.

### 1. Повторить именно проблемный сценарий

Запиши модель телефона, ОС и браузер, версию приложения, данные, частоту экрана и последовательность действий. Сравнивай одну сборку, по возможности production-сборку без накладных расходов dev-режима. Отметь нагрев, энергосбережение, открытые приложения и загрузку ресурсов: они могут менять результат. Сначала воспроизведи исходные условия, затем меняй их по одному. Если тормозит только первое открытие, отдельно исследуй загрузку, декодирование изображений и подготовку содержимого.

Device Mode меняет условия отображения и ввода на компьютере, а CPU throttling замедляет его процессор. Это полезные приближения, но они не воспроизводят аппаратную платформу телефона целиком. Проверку исправления оставляй за реальным устройством. [Ограничения Device Mode](https://developer.chrome.com/docs/devtools/device-mode#limitations).

### 2. Подключить инструменты к телефону

- **Android и Chrome, в том числе с Windows:** включи отладку по USB (USB debugging) в настройках разработчика телефона, подключи USB-кабель и подтверди подключение. В Chrome на компьютере открой `chrome://inspect/#devices`, проверь Discover USB devices и нажми Inspect у нужной вкладки телефона. Для записи открой Performance именно этой вкладки. Если устройство не обнаружено, проверь кабель и драйвер по официальной инструкции.
- **iPhone и Safari:** включи Web Inspector в дополнительных настройках Safari на iPhone; на Mac включи инструменты разработчика Safari, подключи телефон и выбери его страницу в меню Develop. Этот штатный маршрут требует macOS. Профиль Android на Windows не доказывает поведение Safari на iPhone; при отсутствии Mac эта часть проверки остаётся открытой.

Запиши короткий участок: начало записи → несколько одинаковых открытий/закрытий панели → остановка и сохранение профиля. Не включай дополнительные инструменты без необходимости. В Chrome выключи удалённый Screencast на время измерения: он сам ухудшает частоту кадров. Названия дорожек зависят от браузера и версии инструментов.

Подключение и ограничение Screencast: [Chrome: Android remote debugging](https://developer.chrome.com/docs/devtools/remote-debugging). Подключение iPhone: [WebKit: Web Inspector](https://webkit.org/web-inspector/enabling-web-inspector/).

### 3. Найти кадры, которые не успели отобразиться

В Chrome смотри дорожку Frames: длительности, пропущенные и частично показанные кадры. Найди соответствующий интервал в Main и раскрой работу JavaScript, пересчёт стилей, Layout и Paint. Для дорогой функции используй Bottom-up/Call tree. Смотри отдельные паузы и распределение длительностей: средний FPS может скрывать заметный рывок.

При 60 Гц между обновлениями около 16,7 мс, при 120 Гц — около 8,3 мс. Это время для всего кадра, а не разрешённая длительность JavaScript: браузеру тоже нужно выполнить свою работу. Отсутствие задач длиннее 50 мс не гарантирует плавность — даже более короткая работа может сорвать срок кадра. [Бюджет кадра и rendering pipeline](https://web.dev/articles/rendering-performance), [дорожки кадров и искусственное замедление процессора](https://developer.chrome.com/docs/devtools/performance/reference).

### 4. Проверить одну гипотезу за раз

| Что видно в профиле | Что проверить | Пробное изменение |
| --- | --- | --- |
| Долгий JS совпадает с паузой | Callback анимации, обработчик события, вычисления, обновления Vue/React | Убрать повторную работу, уменьшить данные, разбить вычисления или вынести подходящие вычисления в Worker |
| Layout повторяется внутри кадров | Запись left/top/размеров и чтение геометрии после записи | Измерять до записей, сохранять нужный размер; для перемещения проверить transform без изменения места в потоке |
| Дорогой Paint или raster | Большая перерисовываемая область, изображения, тени и фильтры | По одному упрощать эффект или уменьшать область/ресурс и сравнивать запись |
| Кадры пропускаются при небольшой работе Main | Растеризация, GPU/композиция и размеры слоёв, насколько их показывает инструмент | Проверять упрощение графики и числа/размера слоёв; не объявлять GPU причиной только по свободному Main |
| JS-анимация движется с разной скоростью на разных экранах | Прибавляется ли фиксированный шаг на каждый callback | Рассчитывать прогресс по timestamp requestAnimationFrame, а не по числу вызовов |

transform и opacity часто позволяют избежать layout и paint при обновлении, но не обещают дешёвую анимацию при любом содержимом и размере слоя. will-change применяй точечно после подтверждения пользы: лишние слои тоже расходуют ресурсы. Перенос тяжёлой функции в requestAnimationFrame не делает её дешевле; перенос в Promise не освобождает основной поток. [Диагностика CSS-анимаций](https://web.dev/articles/animations-guide).

### 5. Подтвердить результат на том же телефоне

Повтори исходные действия с теми же данными и условиями, сделай несколько записей до/после. Сравни пропуски и длительности кадров в одинаковом участке, а также исчезновение найденной дорогой работы. Кратко сохрани: устройство и сборка → действие → наблюдение профиля → изменение → результат повторения. Не подставляй вымышленные FPS и миллисекунды.

Проверь также без подключённого профилировщика, что движение визуально плавное, панель правильно открывается и закрывается, сохраняются фокус, касания и прокрутка. Уменьшение движения по prefers-reduced-motion проверяется отдельно; оно не заменяет исправление обычного режима. Если проблема проявлялась при прогреве устройства или под нагрузкой, повтори эти условия. Плавность на одном Android не подтверждает все телефоны и Safari.

## Типичные проблемы

- фильтрация и сортировка большого массива на каждый input без debounce;
- рендер тысяч строк вместо пагинации или виртуализации;
- тяжелые computed/watch, которые пересчитываются чаще, чем ожидается;
- нестабильные props/callbacks, вызывающие лишние перерендеры;
- чтение размеров и положения элементов сразу после изменения DOM, вызывающее принудительный синхронный пересчёт геометрии;
- сложные CSS effects, большие тени, filters или анимации layout-свойств;
- выполнение всей работы в основном потоке, хотя часть можно отложить или вынести.

## Как улучшать

Выбор оптимизации зависит от найденного bottleneck:

- для тяжелого JS - memoization, debounce/throttle, Web Worker, уменьшение объема данных;
- для больших списков - pagination, infinite scroll с контролем DOM, virtualization;
- для отрисовки и расчёта геометрии - меньше DOM-узлов, стабильные размеры, transform/opacity для анимаций;
- для загрузки данных — фильтрация, сортировка и разбиение на страницы на сервере;
- для framework rerendering - стабилизировать inputs, разбить компоненты, убрать лишние watchers/computed.

Если данных много и они будут расти, стратегически лучше не держать всю задачу на клиенте: серверная фильтрация, сортировка и пагинация часто важнее локального micro-optimization.

## Как ответить на собеседовании

Если интерфейс тормозит, сначала воспроизведи конкретный сценарий и запиши его во вкладке Performance в Chrome DevTools. Определи, куда уходит время: на JavaScript, расчёт геометрии или отрисовку. В первом случае проверь тяжёлые вычисления, фильтрацию, сортировку, обработчики и долгие задачи. Во втором — количество DOM-узлов, принудительные пересчёты размеров, дорогие стили и лишние обновления компонентов. Для большого списка можно рассмотреть загрузку порциями, отображение только видимых строк или перенос обработки на сервер. После изменения снова измерь тот же сценарий и сравни результат.

## Частые ошибки

- Начинать с переписывания компонента без профилирования.
- Смешивать скорость первоначальной загрузки и скорость работы уже открытого приложения.
- Смотреть только Network, когда проблема возникает после загрузки.
- Считать, что debounce решает любую проблему с большим списком.
- Подробно разбирать этапы отрисовки в этой обзорной теме, хотя им уже посвящён раздел API браузера.
- Давать Vue/React-specific ответ, не отделив общую причину тормозов.
