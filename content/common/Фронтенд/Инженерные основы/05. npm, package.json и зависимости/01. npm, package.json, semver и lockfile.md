# npm, package.json, semver и lockfile

> [!summary]
> Package.json описывает команды проекта и требования к зависимостям. Lockfile фиксирует конкретное дерево установленных версий. Вместе они помогают команде и CI устанавливать согласованный набор пакетов.

## package.json

Типичные поля:

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest",
    "lint": "eslint ."
  },
  "dependencies": {
    "react": "^19.0.0"
  },
  "devDependencies": {
    "vite": "^7.0.0"
  }
}
```

В scripts записывают команды проекта, например запуск тестов или сборки. Разработчик и CI используют одно имя команды, поэтому способ её выполнения не нужно дублировать в разных местах.

## dependencies, devDependencies и peerDependencies

| Тип | Смысл |
| --- | --- |
| `dependencies` | нужно приложению или пакету во время выполнения |
| `devDependencies` | нужно для разработки, тестов, сборки |
| `peerDependencies` | пакет объявляет совместимость с зависимостью окружения потребителя, например плагин — с Vue |

Начиная с npm 7 обязательные peerDependencies устанавливаются автоматически, когда это возможно; конфликт диапазонов всё равно требует решения. Optional peer не означает обязательную установку.

Сборщик ориентируется на импорты: пакет может попасть в браузерную сборку даже из devDependencies. А разделение зависимостей определяет, что установится в выбранном режиме и что потребуется потребителю библиотеки. Поэтому перенос пакета между разделами сам по себе не уменьшает bundle.

## Semver

Semantic Versioning обычно читают как:

```text
MAJOR.MINOR.PATCH
```

- PATCH — bug fixes без изменения API;
- MINOR — новая совместимая функциональность;
- MAJOR — breaking changes.

`^1.2.3` разрешает версии от `1.2.3` до `<2.0.0`, `~1.2.3` — до `<1.3.0` (без автоматического включения prerelease). Для нулевого major граница уже: `^0.2.3` — `<0.3.0`, `^0.0.3` — `<0.0.4`. Обещание semver не исключает ошибок пакета: обновление всё равно проверяют.

## Lockfile

`package-lock.json`, `pnpm-lock.yaml` или `yarn.lock` фиксируют точные версии всего дерева зависимостей. Поэтому lockfile нужно коммитить для приложения.

Практическая разница:

- `package.json` говорит, какие версии допустимы;
- lockfile говорит, какие версии реально выбраны.

`npm ci` требует согласованного lockfile, завершается ошибкой при расхождении с package.json и не обновляет эти файлы. Перед установкой он удаляет существующий node_modules. Для воспроизводимости фиксируют также версию Node/npm и значимые настройки установки; lockfile сам по себе не делает окружения одинаковыми.

## Частые ошибки

- Удалять lockfile, чтобы "починить" зависимости, без понимания последствий.
- Думать, что `^` всегда безопасен.
- Класть зависимость, нужную при выполнении в `devDependencies` в библиотеке.
- Не различать dependency package и код, попавший в bundle.
- Запускать в CI `npm install` вместо воспроизводимого `npm ci`, когда используется npm lockfile.

## Как ответить на собеседовании за одну минуту

В `package.json` записаны команды проекта и допустимые версии зависимостей. Например, диапазон `^1.2.3` разрешает совместимые по semver обновления до версии 2. Lockfile сохраняет конкретно выбранные версии всего дерева, чтобы другие разработчики и CI устанавливали тот же набор. Для этого используют `npm ci` и согласованные версии Node/npm. `dependencies` нужны при выполнении, `devDependencies` — при разработке и сборке, а `peerDependencies` описывают совместимую зависимость у потребителя, например Vue для плагина.

## Практическая задача

После `npm install` у одного разработчика тесты падают, у другого нет. Что проверить?

> [!question]- Разбор
> Проверить, закоммичен ли lockfile, одинаковая ли версия Node/npm, не изменился ли lockfile локально, используется ли в CI `npm ci`, нет ли побочных действий после установки и зависимостей от конкретной операционной системы.
