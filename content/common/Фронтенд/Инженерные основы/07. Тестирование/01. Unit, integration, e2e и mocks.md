# Unit, integration, e2e и mocks

> [!summary]
> Тесты дают уверенность на разных уровнях: маленькая функция, взаимодействие нескольких частей, полный пользовательский сценарий. Хорошая стратегия сочетает быстрые локальные проверки и несколько полных пользовательских сценариев (e2e).

## Unit, integration и e2e

| Тип | Что проверяет | Плюсы | Минусы |
| --- | --- | --- | --- |
| Модульный (unit) | небольшую функцию или модуль | быстрый и точный | мало уверенности в связях |
| Интеграционный | взаимодействие нескольких частей | ближе к реальности | сложнее подготовка |
| E2E | сценарий в браузере | высокая уверенность | медленнее, дороже, риск нестабильности |

Test pyramid советует держать много быстрых низкоуровневых тестов и меньше дорогих e2e. Для frontend часто говорят ещё о testing trophy: больше ценности могут давать интеграционные тесты поведения UI.

## Что тестировать во frontend

- чистые функции: модульные тесты;
- компоненты и формы: проверки поведения и взаимодействия;
- переходы, вход и оформление заказа: e2e;
- визуальные изменения: сравнение снимков, если есть процесс проверки отличий.

## Mocks

Mock подставляют вместо зависимости, чтобы управлять её поведением в тесте. Например, вместо настоящего API сохранения тест возвращает ошибку и проверяет, что введённый текст остался в форме.

Плюсы:

- тест быстрее и стабильнее;
- можно воспроизвести ошибки;
- не нужен настоящий сервер.

Риски:

- mock может не совпадать с реальным API;
- слишком много mocks проверяют "как написано", а не "что работает";
- e2e с моками не заменяет хотя бы несколько проверок реальной интеграции.

## Один сценарий на разных уровнях

Для формы сохранения уровни дополняют друг друга: unit проверяет валидацию, интеграционный тест — сохранение введённого текста при отказе API, e2e — успешное сохранение и повторное открытие записи через интерфейс. Для гонки удобен Promise, который тест завершает вручную: он воспроизводит нужный порядок без случайных пауз. Практика: [[Собеседования/Практика/Тестирование|практика тестирования]].

## Flaky tests

Частые причины:

- ручные `sleep`;
- race conditions;
- зависимости от порядка тестов;
- реальная сеть;
- нестабильные selectors;
- общее изменяемое состояние между тестами.

## Частые ошибки

- Писать только тесты снимков разметки и считать интерфейс проверенным.
- Проверять детали реализации вместо поведения пользователя.
- Подменять всё и не замечать нарушенный контракт с сервером.
- Не запускать e2e в CI для критичных сценариев.
- Игнорировать нестабильные тесты, пока команда не перестанет доверять проверкам.

## Как ответить на собеседовании за одну минуту

Для формы я проверяю разные части отдельно. Модульный тест проверит функцию валидации, интеграционный — отправку формы и сохранение ввода при ошибке, а e2e — весь путь в браузере до повторного открытия записи. Mock помогает получить нужный ответ или отказ без настоящей сети. Связь с реальным сервером проверяю отдельно, потому что формат mock может устареть. Выбираю тесты по тому, какая ошибка важна для пользователя.

## Практическая задача

Форма логина иногда падает в e2e на CI, но локально зелёная. Что проверить?

> [!question]- Разбор
> Проверить ожидание готовности элементов и ответов, устойчивость селекторов, имитацию сети или тестовый сервер, гонки после отправки формы, изоляцию хранилища и cookie между тестами и зависимость от порядка запуска. Повторное выполнение теста может помочь диагностике, но не заменяет исправление причины нестабильности.
