# Git, pull request workflow и CI-CD

> [!summary]
> Git сохраняет историю изменений. CI автоматически проверяет подготовленную версию, а процесс доставки переносит её в нужное окружение. Успешная сборка и успешная работа пользователя — разные проверки.

## Git basics

Практическая модель:

```text
working tree -> staging area -> commit -> branch -> remote
```

Commit сохраняет снимок подготовленных файлов и ссылку на предыдущие коммиты. Ветка указывает на коммит и передвигается вперёд, когда в неё добавляют изменения. Remote хранит адрес другого репозитория, например общего репозитория команды на GitHub.

## Merge и rebase

`merge` объединяет истории. При расходящихся ветках обычно появляется merge commit. Если целевая ветка просто отстаёт, fast-forward может лишь передвинуть её указатель; отдельного узла слияния тогда нет.

`rebase` переносит commits поверх другой базы и делает историю линейнее.

| Операция | Когда уместна |
| --- | --- |
| merge | сохранить контекст ветвления, безопасно объединить shared branch |
| rebase | обновить свою feature branch перед PR |

Не стоит переписывать историю shared branch без договорённости команды.

## Pull request workflow

Типичный flow:

1. создать task branch от принятой в проекте актуальной базы: например, `develop` или `main`;
2. сделать commits;
3. открыть pull request;
4. пройти review и CI;
5. исправить замечания;
6. merge/squash/rebase merge по правилам команды.

PR — не только "кнопка merge", а место для review, обсуждения риска и автоматических проверок.

## CI-CD

CI обычно запускает:

- install;
- lint/format check;
- typecheck;
- unit/integration tests;
- build;
- e2e/smoke tests для критичных flows.

CD доставляет артефакт дальше: staging, preview, production.

После доставки открой приложение и проверь основной сценарий. Убедись, что JavaScript приходит с правильным MIME-типом, а запрос отсутствующего файла получает 404. Это помогает обнаружить ошибки настройки хостинга, которые не видны при сборке. Разбор: [[Фронтенд/Инженерные основы/10. Данные и надёжность/03. Запуск, готовность и восстановление|Запуск, готовность и восстановление]].

## Deployment risks

Frontend-релиз может сломаться из-за:

- несовместимого API contract;
- неправильных env variables;
- cache/CDN старой версии;
- миграции backend без совместимости;
- feature flag ошибки;
- отсутствия rollback.

## Частые ошибки

- Делать большие PR без ясной зоны review.
- Переписывать историю общей ветки через rebase без согласования.
- Игнорировать красный CI.
- Считать успешный build полноценной проверкой продукта.
- Не иметь preview/staging для рискованных UI flows.

## Как ответить на собеседовании за одну минуту

Git позволяет сохранять изменения и работать над ними в отдельных ветках. Обычно я открываю pull request, прохожу review и автоматические проверки, затем вливаю изменения по правилам команды. Merge объединяет истории, а rebase пересоздаёт коммиты поверх новой базы, поэтому общую историю без согласования не переписывают. CI запускает тесты, проверку типов и сборку. После доставки проверяю конфигурацию, кэш и совместимость с API, а для проблемного выпуска должен быть понятен способ отката.

## Практическая задача

После релиза часть пользователей видит старый JS и новый HTML. Где искать проблему?

> [!question]- Разбор
> Проверить правила кэширования браузером и CDN, файлы с контрольной суммой в имени, заголовки кэширования HTML, Service Worker, порядок выпуска клиентской и серверной частей, согласованность манифеста с доступными файлами и возможность отката. HTML обычно кэшируют ненадолго, а файлы с контрольной суммой в имени — надолго.
