# Docker — сборка, запуск и данные

Образ содержит подготовленную файловую систему и инструкции запуска. Контейнер — запущенный экземпляр с процессом и своим изменяемым слоем. Пользовательские данные, которые должны пережить замену контейнера, хранятся отдельно.

## Разобрать настоящий Dockerfile

1. `dependencies`: копируются package-файлы, выполняется `npm ci`.
2. `build`: добавляются исходники backend/frontend и выполняется сборка.
3. `runtime`: устанавливаются production-зависимости, копируется `dist`, задаётся пользователь `node` и запускается `dist/main.js`.

В финальную стадию не копируется всё дерево сборки. Это уменьшает состав рабочего образа, но не доказывает отсутствие уязвимостей. Копирование package-файлов перед исходниками позволяет переиспользовать подходящий слой установки зависимостей. [Docker: multi-stage builds](https://docs.docker.com/build/building/multi-stage/).

Задание: назови, какие стадии потребуются заново при изменении только исходника и при изменении lock-файла. Затем объясни, почему успешный `npm run build` ещё не доказывает запуск контейнера.

> [!question]- Разбор
> Если предыдущие входы совпали, изменение исходника не требует заново устанавливать зависимости сборки. Изменение lock-файла затрагивает установку зависимостей и зависящие стадии. Запуск дополнительно зависит от итоговых файлов, зависимостей приложения, команды, прав и конфигурации. Использование или пересборку слоя надо смотреть в выводе сборки.

## Во время сборки и выполнения

**ID вопроса:** Build-time и runtime

Если Vite подставил `VITE_API_URL` в клиентский bundle во время сборки, изменение переменной у уже запущенного сервера само по себе не перепишет этот JS. Можно либо пересобрать артефакт, либо заранее спроектировать отдельную публичную конфигурацию времени запуска. [Vite: env variables](https://vite.dev/guide/env-and-mode).

Любое значение, включённое в браузерный код, доступно пользователю. Пароль или приватный токен нельзя сделать секретным именем переменной. Для временного доступа сборки к закрытому registry предусмотрены secret mounts; `ARG` и `ENV` не подходят как механизм сокрытия build-секретов. [Docker: build secrets](https://docs.docker.com/build/building/secrets/).

## Порт, процесс и данные

- `EXPOSE` описывает порт образа; публикация наружу задаётся отдельно.
- Замена контейнера и удаление volume — разные действия. Новая версия кода может работать с прежними данными.
- Несовместимая миграция базы может сделать простой откат образа непригодным.
- Проверка работоспособности, готовность сервиса и успешная доставка сообщения проверяют разные границы.

Простая модель диагностики: контейнер не стартует → команда/файлы/зависимости; стартует, но недоступен → интерфейс прослушивания/порты/прокси; отвечает, но теряет состояние → путь базы/volume/права. Это гипотезы, которые проверяют по наблюдениям.

## Учебный инцидент

После обновления приложения база выглядит пустой. Вводные: старый volume существует, новый контейнер использует другой путь. Как восстановить работу, не потеряв новые записи?

> [!question]- Разбор
> Сначала установи, куда фактически пишет каждая версия, и сохрани обе копии данных. Не подключай старую базу вслепую поверх новых записей. Проверь конфигурацию, доступ и совместимость схемы, затем выбери восстановление или согласование данных. Удаление volume не является диагностическим шагом.

## Как связать с frontend

SPA можно отдавать как статические файлы; Nuxt SSR может требовать работающий серверный процесс. Поэтому «собрать клиентскую часть в контейнер» не определяет способ запуска. Назови артефакт, процесс, конфигурацию, постоянные данные и проверку после доставки.
