# Nuxt — сервер, данные и гидратация

В Nuxt один и тот же экран может сначала строиться на сервере, а затем продолжать работу в браузере. Главный вопрос: какие данные и эффекты принадлежат каждому этапу.

Примеры используют Nuxt 3 для разбора существующих приложений. Поддержка этой ветки завершилась 31 июля 2026; планирование нового приложения и перехода выполняют по поддерживаемой версии. [Состояние поддержки](https://github.com/nuxt/nuxt/blob/main/docs/5.community/6.roadmap.md).

## Путь одного открытия

```text
запрос страницы → сервер получает данные → HTML + сериализованное состояние
              → браузер загружает JS → гидратация → дальнейшие действия
```

Первый клиентский рендер должен соответствовать серверному результату. Если на сервере случайное число одно, а в браузере другое, возникает расхождение. Проблему нужно искать в источнике различия: случайность, время, locale, доступные только браузеру значения или HTML, который браузер исправил. Примеры ниже используют Nuxt 3.

## Как искать причину hydration mismatch

Страница показывает цену `1 200 ₽`, но при запуске приложения Vue сообщает о несовпадении текста. Нужно выяснить, на каком этапе появилось различие. Vue может восстановить часть DOM, поэтому для диагностики нужны исходные данные и первый клиентский рендер, даже если после загрузки цена выглядит правильно.

### 1. Зафиксировать воспроизведение и первый проблемный узел

Открой URL напрямую или перезагрузи страницу: клиентский переход может не проходить тот же путь SSR и гидратации. Сохрани первое предупреждение целиком, указанный DOM-узел, цепочку компонентов и значения server/client, если они приведены. Начинай с первого расхождения: последующие могут быть его следствием. Отметь URL, версию, пользователя, cookies, locale и условия появления. Если ошибка только после выпуска, воспроизводи с соответствующими сборкой и данными.

### 2. Разделить три этапа

| Что сравнить | Как получить | Что это проверяет |
| --- | --- | --- |
| Исходный HTML и переданное состояние | Ответ документа в Network и переданные данные того же открытия | Что действительно прислал сервер |
| DOM перед гидратацией | Пауза перед монтированием клиентского приложения в отладчике; перезагрузка с отключённым JavaScript помогает отдельно проверить разбор HTML | Как браузер разобрал HTML и что успело изменить DOM |
| Ожидаемый первый клиентский результат | Breakpoint в setup/render найденной ветки, проверка props, состояния и условий шаблона | С какими значениями клиент начинает гидратацию |

Не сравнивай серверный ответ только с Elements после полной загрузки: там уже возможны восстановление Vue и более поздние обновления. Открытие исходника отдельным запросом тоже может получить другие данные. С отключённым JavaScript не выполняются ни приложение, ни сторонние скрипты, поэтому такой просмотр сам по себе не исключает вмешательство скриптов при обычной загрузке.

### 3. Проверить источник различия в найденной ветке

| Возможная причина | Как отличить | Что исправлять |
| --- | --- | --- |
| Разные начальные данные | Сопоставить входные параметры компонента, переданные данные, состояние авторизации и результат повторного запроса до первого рендера | Передачу серверного результата клиенту; в Nuxt проверить использование useFetch/useAsyncData и ключи состояния |
| Время, случайность, форматирование | Зафиксировать значение, locale и timezone и повторить открытие | Передать общий исходный результат и согласованный формат; зависящее от браузера отображать после монтирования |
| Условие по window, localStorage или ширине экрана | Сравнить ветки шаблона на сервере и до первого клиентского рендера | Одинаковое начальное состояние; для адаптивного оформления рассмотреть CSS |
| Некорректный HTML | Сравнить HTML ответа с DOM без JavaScript, проверить вложенность | Структуру шаблона: например, браузер вынесет div из p ещё до Vue |
| Сторонний скрипт или расширение | Повторить без расширений, отдельно отключать подозреваемые интеграции и сравнивать DOM до гидратации | Порядок запуска и владельца DOM; библиотеку, меняющую узлы приложения, инициализировать на подходящем клиентском этапе |
| Общее серверное состояние или неверный кэш | Сравнить HTML и переданные данные двух изолированных сессий; проверить, от чего зависит ключ кэша | Изоляцию запросов и персонализированных ответов |

### 4. Сузить пример и исправить причину

В локальном воспроизведении временно подставляй постоянные данные или исключай дочерние ветки по одной. Если расхождение исчезло, верни найденную ветку и проверь выражение, которое даёт разные значения. Для цены сравни сначала число, затем результат его форматирования: различаться могут и данные, и locale.

Пример для Nuxt 3: компонент выводит число, созданное при каждом запуске setup.

```vue
<script setup>
const value = Math.random()
</script>

<template>
  <p>{{ value }}</p>
</template>
```

Сервер и браузер независимо получают числа, которые могут отличаться. Если значение должно прийти с сервера и сохраниться при гидратации, замени объявление:

```ts
const value = useState('hydration-demo-value', () => Math.random())
```

Инициализация выполняется внутри setup, сериализованное серверное значение передаётся клиенту. Ключ относится к этому состоянию: нельзя бездумно использовать его для независимых данных. В обычном Vue без Nuxt передачу начального состояния организует SSR-интеграция.

Для виджета, который по назначению работает только в браузере, допустим ClientOnly или вывод после onMounted с согласованной начальной заглушкой. Отключение SSR всей страницы, setTimeout и подавление предупреждения не объясняют исходное расхождение.

### 5. Проверить исправление

Повтори исходный URL при полной загрузке в тех же условиях; проверь также условия, подтвердившие гипотезу: например, другой часовой пояс или две пользовательские сессии. Проверь текст, структуру и работу кнопок/форм после гидратации, отсутствие связанных предупреждений. Клиентский переход проверь отдельно. Если сбой был в production-сборке, одного успешного dev-открытия недостаточно. Автоматическая проверка такого дефекта должна загружать SSR-страницу и запускать клиент: mount компонента только в браузере не покрывает эту границу.

Механизм расхождений и восстановления: [Vue SSR](https://vuejs.org/guide/scaling-up/ssr.html#hydration-mismatch). Передача значения useState: [Nuxt: state management](https://nuxt.com/docs/getting-started/state-management/).

## Почему запрос выполняется дважды

Обычный вызов `$fetch` в setup без передачи результата через механизм Nuxt может выполниться при SSR и снова при гидратации. `useFetch` и `useAsyncData` позволяют связать получение данных с передачей результата клиенту. Это не обещание «запрос никогда не повторяется»: изменение параметров, refresh и политика загрузки могут запускать новые операции. [useFetch](https://nuxt.com/docs/3.x/api/composables/use-fetch).

Страница при существующем `GET /api/services`:

```vue
<script setup lang="ts">
const { data, status, error, refresh } = await useFetch('/api/services');
</script>

<template>
  <p v-if="status === 'pending'">Загрузка…</p>
  <div v-else-if="error">
    Не удалось загрузить услуги.
    <button type="button" @click="refresh()">Повторить</button>
  </div>
  <pre v-else>{{ data }}</pre>
</template>
```

Для списка задайте контракт ответа и проверьте авторизацию endpoint на сервере.

## Состояние одного пользователя

Общий изменяемый объект на уровне серверного модуля может пережить один запрос и оказаться доступен следующему. Для состояния приложения используй рассчитанный на SSR механизм, например `useState` с ключом внутри контекста Nuxt. Передаваемое клиенту состояние должно быть сериализуемым. [Nuxt: state management](https://nuxt.com/docs/3.x/getting-started/state-management).

Дефект: серверный модуль хранит `currentUser`, обработчик сначала присваивает его, затем ждёт API и читает снова. Другой запрос успевает заменить значение. Исправление — состояние запроса передаётся явно или хранится в изолированном контексте. Один глобальный `ref` не решает изоляцию.

## Браузер и безопасность

`window`, DOM и `localStorage` недоступны при обычном серверном рендере. Чтение браузерных настроек переносится в подходящий клиентский этап с понятным первоначальным состоянием. Клиентское ограничение маршрута не заменяет авторизацию API. Серверные секреты нельзя сериализовать в данные, передаваемые браузеру, или публичную конфигурацию.

## Что именно развёртывается

Статическая генерация выдаёт файлы для хостинга. SSR со стандартным Node preset требует процесса сервера; одного копирования клиентских файлов недостаточно. Есть и другие presets, поэтому команда запуска зависит от выбранной цели. [Nuxt: deployment](https://nuxt.com/docs/3.x/getting-started/deployment).

## Задание

На первом открытии виден пользователь A, после гидратации — B. После клиентского перехода всё нормально. Предложи порядок диагностики и проверку, отличающую общую серверную переменную от обычного устаревшего клиентского кэша.

> [!question]- Разбор
> Сравни исходный HTML и переданные данные, ответы API, cookies и состояние до гидратации. В изолированной тестовой среде сделай параллельные запросы двух пользователей с разными данными; отдельно проверь повторное открытие в чистых сессиях. Не кешируй персонализированный ответ как общий. Пропажа симптома после `ClientOnly` может скрыть причину, а не исправить её.

Краткий ответ: «SSR создаёт HTML, гидратация связывает его с клиентским приложением. Я отдельно проверяю передачу данных, повторные запросы, изоляцию пользователей и одинаковое начальное состояние».
